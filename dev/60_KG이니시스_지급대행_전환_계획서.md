# 정산 지급 PG 전환 — 토스페이먼츠 지급대행(Payouts v2) → KG이니시스 지급대행(신버전 AML) 변경 계획서

- 대상: `dev/완료/정산/44_토스페이먼츠_지급대행_연동_BE_설계서.md`(이하 「토스 설계서」)로 구현된 정산 지급 어댑터 계층을 **KG이니시스 지급대행 API(신버전 · AML)** 로 바꾼다. 정산 산식 · `settlement_payout` 상태(`SCHEDULED → REQUESTED → PAID / FAILED` · `BLOCKED`) · 세 화면은 그대로 두는 것이 원칙이다. 다만 이니시스는 **지급 1건을 우리 참조 id 로 식별하지 않으므로**(1-3) 「정산 1건 = 지시 1회」였던 배치 골격을 **「수취자 · 지급일 = 지급 묶음 1개」** 로 바꾼다(D-1) — 이 계획서에서 가장 큰 변경이다.
- 근거 외부 문서(2026-11-17 조회): KG이니시스 매뉴얼 — 지급대행 신버전(AML) `manual.inicis.com/iniweb/opmall_aml.html` · 구버전 `opmall.html`(신규 신청 종료 · 참고용) · 서비스 안내 `inicis-service.inicis.com/?page_id=748`. 매뉴얼의 **팝업(에러 코드 · HASH · ENC · AML 코드표)은 본문에 없어** 확인하지 못했다 — 이 공백과 추정은 전부 11절 Q 로 모았고 본문에 「(추정)」으로 표시했다.
- 기준 코드: `feat/add` · `35a29595` · 마지막 마이그레이션 V232. 이 계획서가 파는 마이그레이션은 **V233**.
- 결제는 **바꾸지 않는다** — 포트원 V2(토스페이먼츠 허브형) 결제 · 웹훅 · 본인인증은 한 줄도 건드리지 않는다. 바뀌는 것은 「돈을 내보내는 쪽」뿐이다.
- 작성일: 2026-11-17 · @hc · 같은 날 1차 검토 반영(13절)

## 1. KG이니시스 지급대행(신버전 AML) — 조사 결과(사실)

### 1-1. 서비스 성격

- 「전자자금이체업무를 수행하는 오픈마켓 사업자를 대신하여 이니시스에서 거래금액의 지급 및 자금이체를 대행」. 서브몰(하위 판매자) 계좌 · 지급 데이터는 **가맹점(우리)이 관리**하고 자금 보유 · 이체는 이니시스가 한다.
- 구버전(`OpMallUrlConnection.jsp` · EUC-KR · 쿼리스트링)은 **신규 이용 신청 종료** — 신규 가맹점은 신버전(AML)만 연동한다. 이 계획서는 신버전만 다룬다.
- 신청: 이니시스 가맹점관리자 「특약 서비스 추가」 → 견적 · 이용 안내 → 지급 데이터 업로드(API 또는 상점관리자 업로드) → 지급. 수수료 **정액제 / 건당제**(금액 미공개 · Q1).

### 1-2. 엔드포인트(base `https://apiwi.inicis.com/rest/api/openmall`)

| 기능 | 메서드 · 경로 | 성공 코드 |
| --- | --- | --- |
| 서브몰 정보 등록 · 수정 | `POST /upsert` | `SA01` |
| 지급 요청 · 삭제 | `POST /payreq` | `SB01` |
| 송금 결과 조회 | `GET /payresult` | `SC01` |
| 잔액 대사 | `GET /paycheck` | `SD01` |
| 서브몰 AML 상태 조회 | `GET /amlstatus` | `SM01` |

- 공통: `Content-Type: application/json;charset=utf-8` · 헤더 `X-Request-ID`(필수 · 트래킹 id) · `X-API-KEY`(필수 · 가맹점관리자 「상점정보 > 계약정보 > KEY 정보 > 부가서비스 연동 KEY 정보 > 지급대행 서비스 > [조회]」).
- 응답: `code`(4자) · `msg` · 조회는 `data`.
- 방화벽(이니시스 측 IP): `118.129.210.143` · `183.109.71.186` · TLS 1.2 이상. 우리 아웃바운드 허용 목록에 넣는다. 우리 IP 를 이니시스에 등록해야 하는지는 문서에 없다(Q10).
- GET 3종의 파라미터를 쿼리스트링으로 보내는지 본문으로 보내는지 **명시 없음**(Q4).
- **업로드했지만 아직 송금되지 않은 지급 데이터를 조회하는 API 가 없다** — `payresult` 는 송금 결과만 돌려주는 것으로 보인다(Q3). 우리가 무엇을 올렸는지는 우리 기록(D-1 의 `confirmed_amount`)이 유일한 근거다.

### 1-3. 지급 요청(`payreq`)

| 파라미터 | 필수 | 길이 | 뜻 |
| --- | --- | --- | --- |
| `idMerchant` | ○ | 10 | MID |
| `idMall` | ○ | 60 | 판매자 id(우리가 등록한 서브몰) |
| `dtPay` | ○ | 8 | 지급일자 `YYYYMMDD` |
| `amtSupply` | ○ | 10 | 지급금액 |
| `clService` | ○ | 3 | `0` 익일지급 · `2` 당일지급 · `3` 비영업일 |
| `svcDmlCd` | ○ | 3 | `INS` 등록 · `DEL` 삭제 |
| `svcType` | ○ | 3 | `REQ` 지급 · `REF` 환불 |

- **계좌를 보내지 않는다** — 서브몰에 등록된 계좌로 나간다(구버전은 지급마다 계좌를 보냈다). 등록 계좌가 업로드 시점 것인지 **송금 시점 것인지**는 문서에 없다(Q3) — D-1 은 보수적으로 「송금 시점」으로 가정한다.
- **우리 참조 id 를 넣을 자리가 없고 응답에 지급 id 도 없다.** 지급을 가르는 값은 `(idMall, dtPay, clService, svcType)` 뿐이다.
- 「당일 지급건 13시 전, 익일 지급건은 15시 전까지 수정 및 재업로드가 가능합니다. 마지막 저장한 금액으로 최종 정산 금액이 반영됩니다.」(서비스 안내) — **같은 키로 다시 `INS` 하면 덮어쓴다**(추정 · Q3). 그렇다면 같은 합계를 다시 보내는 재시도는 멱등이다.
- 「익일지급」의 `dtPay` 가 **돈이 나가는 날**인지 **업로드 기준일(다음 날 지급)** 인지 문서가 갈리지 않는다(Q2) — D-2 는 전자로 가정하고 설정 하나로 뒤집는다.

### 1-4. 서브몰 등록 · 수정(`upsert`)

| 파라미터 | 필수 | 길이 | 뜻 | 비고 |
| --- | --- | --- | --- | --- |
| `idMerchant` | ○ | 10 | MID | |
| `idMall` | ○ | 60 | 판매자 id | 조회 API 명세에는 **10** 으로 적혀 있다(D-3) |
| `clId` | ○ | 1 | `1` main mall · `2` sub mall | 수취자는 전부 `2` |
| `noComp` | | 10 | 사업자번호(숫자) | 비사업자 인플루언서는 생략 |
| `nmComp` | ○ | 50 | 상호명 | 비사업자는 활동명 · 이름(Q6) |
| `nmBoss` | ○ | 30 | 대표자명 | ENC |
| `nmRegist` | ○ | 50 | 예금주 | ENC · 한글 · 영문 · 숫자 · 공백 · `( ) & / - ' , . ·` 만 |
| `cdBank` | ○ | 3 | 은행코드 | |
| `noAcct` | ○ | 20 | 계좌번호 | ENC |
| `noTel` | ○ | 20 | 휴대전화 | ENC |
| `noEmail` | ○ | 60 | 이메일 | ENC |
| `bthDt` | ○ | 8 | 생년월일 | ENC · **사업자도 필수**(대표자 기준으로 추정 · Q6) |
| `svcDmlCd` | ○ | 3 | `INS` / `UPD` | |
| `svcType` | ○ | 3 | `REQ` / `REF` | 우리는 `REQ` 만 |
| `userHash` | ○ | 64 | 위변조 검증 | 대상 = `현재날짜 + idMerchant + base64Decode(noAcct) + X-API-KEY` · 알고리즘 미기재(64자 → SHA-256 hex 로 추정 · Q4) |

- ENC 는 문서에 「Base64 암호화 대상」이라고만 있다 — 순수 Base64 인지 다른 암호화 뒤 Base64 인지 팝업 미확인(Q4).
- 개인 / 개인사업자 / 법인 구분 필드가 **없다** — 토스 D-14(법인 판정 · 반대 유형 재시도)는 필요 없어진다.
- 예금주 · 계좌 일치를 이니시스가 등록 때 검증하는지 **문서에 없다**(Q7) — 「인플루언서 계좌 실명 확인」(50 설계서)이 이 결과에 기대고 있어 **런칭 차단 항목**이다(D-5).

### 1-5. 송금 결과(`payresult`)

- 요청: `idMerchant` · `idMall`(선택) · `startDtPay` · `endDtPay` · `clService` · `svcType`.
- 응답 `data`: `svcType · idMall · noComp · nmComp · nmBoss · nmRegist · cdBank · noAcct · noTel · dtPay · amtSupply · remitDtPay(송금결과일) · clPay(01 성공 · 이외 실패)`.
- **실패 사유 문구 필드가 없다** — `clPay` 값 목록이 실패 분류의 전부다(Q5). 결과가 언제 조회 가능해지는지(지급일 당일 몇 시?)도 문서에 없다(Q2).

### 1-6. 잔액 대사(`paycheck`)

- 요청: `idMerchant` · `startDtPay` · `endDtPay`. 응답: `noComp · totalAmt(잔액) · idMerchant · payTransDt(조회 기간)`.
- 기간을 받는 「잔액」이 **지금 지급 가능한 금액**인지 **그 기간의 순증감**인지 불명(Q1). 부족하면 **지급일 전일 18시까지** 이니시스 지정 계좌로 입금(서비스 안내 · 계좌번호는 계약 뒤 확정값으로 런북에만 적는다).

### 1-7. AML 상태(`amlstatus`)

- 요청: `idMerchant · idMall · svcType`. 응답: `amlExmnYn`(심사상태 · 코드표 미확인) · `reAmlExmnYn`(재이행 진행) · `amlReExecFromDt / ToDt`(이행 유효기간) · `amlAuthExpiredYn`(`Y` 정상 · `N` 만료 — 이름과 값의 뜻이 반대로 적혀 있다 · Q8) · `amlTransmDt`(심사완료일) · `amlConm · amlCeoNm · amlDtsNo`.
- 정책(서비스 안내): 「7일간 1천만원 이상을 지급받는 서브몰에 대해서만 최초 1회 고객확인 이행 의무」 · 「이행 주기마다 추가 고객확인」 · 「고객확인을 하지 않으면 요청한 지급데이터의 정산이 제한될 수 있습니다」. **고객확인을 누가 · 언제 · 어떻게 시작하는지**는 없다(Q8). 공구 정산을 받는 브랜드는 주 1천만 원을 쉽게 넘으므로 **대부분의 브랜드가 대상**이 된다고 보고 설계한다.

### 1-8. 테스트 환경

- 공개 테스트 서버 · 테스트 MID 없음. 「스테이징 테스트 희망 시, 계약담당자 문의 (스테이징 환경에서는 서브몰 등록상태, 지급내역조회, 자금현황 등 조회 불가)」.

### 4-1. `SettlementPayoutGateway`

```java

                    String scheduleType, long total) {}

record GroupSubmitResult(Outcome outcome, String failCode, String failReason, String requestId) {}

/** outcome — PAID · FAILED · REQUESTED(아직) · pgAmount 가 confirmedAmount 와 다르면 도메인이 닫지 않는다 */

// availableBalance() 유지 · reconcile() 은 이니시스에서 empty · fromWebhook() 은 토스 삭제 때 제거
```

- **계좌는 묶음 명령에 넣지 않는다** — 이니시스는 지급 요청에 계좌를 받지 않고(1-3), 계좌 동기화(`UPD`)는 묶음을 만들기 전에 `SettlementPartnerSyncService` 가 `pg_partner_account_hash` 비교로 한다(D-1 ⑤).
- 플랫폼 몫은 묶지 않고 **도메인이 즉시 `PAID`**(지금은 어댑터 · `call()` 폴백이 하던 일 — 묶음 경로에서는 도메인으로 옮긴다).
- 정산별 `distribute(PayoutCommand)` · `lookup` 은 토스 경로용으로 남겼다가 단계 5 에서 SIMULATED 까지 묶음으로 옮긴 뒤 제거한다.

### 4-2. `SettlementPartnerGateway`

- `partnerRef(payee, refId)` 신규(D-3) — 도메인 `SettlementPartnerIds.partnerRef` 는 위임만.

- 확정 뒤 `ensureForSettlement` 골격 유지. 이니시스는 승인 대기가 없으므로 등록 성공이면 바로 지급 가능 — 토스 때의 「예정일까지 본인인증 기간」이 사라진다.
- 계좌 변경(토스 설계서 4-4): 서브몰의 계좌는 하나다. 미송금 묶음이 있는 동안 `UPD` 를 보내지 않으므로, 새 계좌 행은 그 묶음의 지급일 **다음** 지급일로 간다(같은 날 두 계좌는 불가능). Q3 답이 「업로드 시점 계좌로 고정」이면 이 제약을 풀 수 있다.

| 4 | 길이 검사가 글자 수였다 — 매뉴얼은 byte · 요청은 UTF-8(한글 3byte). 예금주 17 ~ 50자 · 대표자명 11 ~ 30자가 사전 검사를 통과해 이니시스 EB02(유효성)로 거절 → `PARTNER_NOT_READY` 로 배치마다 같은 거절을 되풀이할 수 있었다 | UTF-8 byte 로 센다(예금주 50 · 대표자명 30 · 이메일 60 — ENC 필드는 평문 기준 · 가정). 상호(50byte)는 대조되는 값이 아니어서 막지 않고 글자 경계에서 잘라 보낸다 | `InicisSubMallRegistrar.precheck` · `request` |
| 5 | 매뉴얼 은행코드 표 밖의 은행을 거르지 않았다 — 우리 활성 은행 중 **012 단위농협(지역농축협)** 이 표에 없다(증권사는 이미 비활성) | 표를 상수로 두고 부르기 전에 `UNSUPPORTED_BANK`(은행 이름 · 코드) | `InicisSubMallRegistrar.SUPPORTED_BANK_CODES` |

**고치지 않은 것(기획 · 운영 결정 필요)**

- **사람을 부르는 묶음의 처리 경로가 없다** — 금액 불일치(`AMOUNT_MISMATCH`) · 마감 경과 합계 불일치(`OUT_OF_SYNC`) · 결과 모름이 처리 지연까지 이어진 묶음은 알림만 가고 행이 REQUESTED 로 남는다. 어드민에 이니시스 대사 뒤 「지급 완료(송금일) / 실패로 확정」하는 조치가 필요하다(재분배는 FAILED 행만 받는다). 화면 · 권한 · 증빙을 정해야 해서 API 를 임의로 만들지 않았다.
- **단위농협 계좌 안내** — INICIS 로 전환하면 012 계좌 수취자는 `UNSUPPORTED_BANK` 로 보류된다. 파트너센터 · 쇼룸스튜디오 계좌 등록 화면에서 미리 막거나 안내할지 정해야 한다(은행 목록은 소비자 환불 계좌와 같은 테이블이라 일괄 비활성은 안 된다). 이니시스가 012 를 받는다고 답하면 상수에 넣으면 된다(Q 추가).
- 14-4 의 잠금 순서(선점: 정산 → 묶음 · 결과: 묶음 → 정산) 교착 가능성은 그대로다 — 한쪽이 롤백되고 다음 틱이 다시 해 정합은 깨지지 않는다.

### 14-7. 정합성 · 무결성 검토(2026-11-22)

지급 묶음 경로를 「돈이 두 번 나가거나 기록과 PG 가 어긋나는 길」 기준으로 다시 훑었다.

**안전한 것(확인)**

- 묶음 키 유니크(`uk_payout_group`) · 같은 키 열린 묶음 1개 · 계좌가 다른 행은 다음 지급일(D-1 ⑤) — 같은 이니시스 키(idMall · dtPay · 차수)에 열린 묶음이 둘 생기지 않는다. 새 묶음을 동시에 만들면 유니크 · 교착으로 한쪽이 롤백된다.
- 닫힌 묶음(DELETED · FAILED)은 모두 PG 에 남은 금액이 없다 — 그래서 같은 지급일에 새 차수가 열려도 덮어쓸 것이 없다(결과 모름 뒤 거절은 14-6 #1 로 열린 채 둔다).
- 행 전이 쿼리는 전부 `WHERE status = …` 조건부 UPDATE 다 — 중복 반영 · 경합에서 한쪽만 이긴다(`markPaid` · `markFailed` · `detach*` · `markConfirmedInGroup` · `reschedule`).
- 송금 결과 반영은 묶음 잠금 아래 · 금액이 맞을 때만 닫는다(확정 합계 · 행 합계 · 확정 행 합계 셋 중 하나와 같아야).
- 배포는 단일 인스턴스(docker-compose app 1개 · 스케줄러 공통 전제)다.

**고친 것**

| # | 무엇이 문제였나 | 고친 것 |
| --- | --- | --- |
| 1 | **같은 묶음 전송이 겹친다** — 전송은 준비(잠금) → PG 호출(잠금 없음) → 반영(잠금)이라, 배치와 보류 뒤 재전송 · 재분배(요청 스레드)가 겹치면 PG 에는 늦게 도착한 합계가 남고 우리 확정 합계는 늦게 반영한 쪽을 따른다(어긋나면 마감 뒤 사람 호출 · 빠진 행이 이전 합계로 나갈 수 있다). 같은 수취자의 다른 묶음 둘이 겹치면 서브몰 계좌 정렬(미송금 판정)이 서로를 못 봐 앞 묶음이 바뀐 계좌로 나갈 수 있다 | `SettlementPayoutGroupService.submit` 을 **수취자 단위로 직렬화**(JVM 줄무늬 잠금 64 · 대기 상한 30초 — 넘으면 보내지 않고 다음 수렴). 호출자는 모두 트랜잭션 밖(커밋 뒤 · 스케줄러)이라 DB 잠금과 엇갈리는 교착이 없다. 잠금을 끄면 새 동시성 시험이 실패함을 확인했다 |

**남은 위험(결정 필요)**

- **보류한 행이 PG 에서 빠지지 못한 채 마감되면** — 행은 BLOCKED(묶음 연결 끊김)인데 이니시스는 이전 합계로 그 몫까지 송금한다. `OUT_OF_SYNC` · `AMOUNT_MISMATCH` 알림이 가지만 사람이 놓치고 보류를 풀면 그 행은 **다시 지급된다**. 위 #1 · #3 으로 창이 크게 줄었지만(마감까지 PG 가 계속 실패할 때만) 0 은 아니다. 근본 해법은 ① 보류로 뺀 행에 묶음 연결 · PG 반영 표시를 남겨 송금 결과가 「행 합계 + 뺀 행」이면 그 행을 지급 완료로 기록(지급 뒤 차감 경로로)하고, 그 묶음이 풀릴 때까지 보류 해제를 막는 것 ② 14-6 의 어드민 처리 경로. 둘 다 보류 해제 규칙 · 화면을 바꿔 기획 확인이 필요하다.
- 14-4 의 잠금 순서 교착(정산 → 묶음 / 묶음 → 정산) — DB 가 감지해 한쪽을 롤백하고 다음 틱이 다시 한다. 정합은 깨지지 않는다.
- 다중 인스턴스로 늘리면 #1 의 JVM 잠금과 모든 스케줄러가 분산 잠금(ShedLock 등)을 필요로 한다.
