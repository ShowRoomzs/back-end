## 25. 계약 관리 — 공통 (절차 · 상태 · 권한)

### 25-0. 대상 화면

| 서피스 | 파일 | 상태 수 | 역할 | GNB |
| --- | --- | --- | --- | --- |
| 파트너센터 | `ui-partner-08-contracts` (rev.7) | 26종 | **발신** — 작성 · 검토 요청 · 종결 | #4 계약 관리 |
| 쇼룸 스튜디오 | `ui-studio-08-contracts` (rev.2) | 12종 | **수신** — 확인 · 서명 · 거절 | #3 계약 관리 |
| 어드민 | `ui-admin-01-contracts` (rev.1) | 17종 | **운영** — 검토 · 서명 갱신 · 체결 · 만료 · 재발송 | **#5 계약 관리 (신설 제안)** |

세 화면은 **같은 계약 객체를 다른 권한으로** 다룬다. 컴포넌트(카드 · 폼 행 · 배지 · 스텝퍼 · 서명 박스 · 목록 · 모달 · 이력)는 **문자 단위 동일 마크업**을 쓴다.

---

### 25-1. 확정 절차 — `FE`·`BE`

```
브랜드 작성 → [검토 요청] → 운영자 검토 → 양측 동시 서명 요청
  → 브랜드 · 인플루언서 각각 서명(외부 모두싸인) → 운영자 체결 완료 처리 → 체결완료 · 공구 생성
      (└ 검토 반려 / 거절 / 만료 / 취소)
```

| 항목 | 규칙 |
| --- | --- |
| **서명에 순서가 없다** | 모두싸인이 **기안자 선서명을 지원하지 않는다**(rev.5 확정). 운영자 검토를 통과하면 솔루션이 **양측에 메일·문자를 각각 발송**하고 두 사람이 **각자** 서명한다. rev.2~4의 「발송 = 브랜드 서명」은 **폐기** |
| **[검토 요청]은 발송이 아니다** | 이 버튼은 **서명도 결제도 하지 않는다.** 「발송」이라 부르면 브랜드가 계약서가 나갔다고 오해하는데, 실제로는 **운영자 검토가 먼저**다 |
| **승인 ≠ 발송** | API가 없어 우리 시스템은 서명 요청을 보내지 못한다. **운영자가 모두싸인에 계약 내용을 직접 입력해 보낸 뒤** 승인을 누르고, **승인은 「보냈다」는 기록**이다 |
| **양측 서명만으로 체결되지 않는다** | 운영자가 서명 결과를 확인해 **체결 완료**를 눌러야 계약이 성립하고 **그때 공구가 생성**된다 |
| **결제 단계가 없다** | MVP에서 **플랫폼이 고정 지급비를 중개하지 않는다**(rev.6). 계약 절차 어디에도 결제가 없다 |
| **계약 1건 = 공구 1건** | 체결완료가 **공구 생성 게이트**다 |

### 25-2. 상태 정의 — 9종 · 3서피스 공통 — `FE`·`BE`

**rev.2의 6종에서 3종이 늘었다** — 운영자 검토와 운영자 체결 처리가 절차에 들어왔기 때문이다.

| 상태 | 의미 | 종류 | 배지 색 | 파트너 | 스튜디오 | 어드민 |
| --- | --- | --- | --- | --- | --- | --- |
| 작성중 | 협의항목 입력 중(검토 요청 전 · 임시저장) | 진행 | **중립** | ✅ | **미도착** | **탭 없음** |
| **검토 대기** | 검토 요청 완료, 운영자 확인 중 — 서명 전 | 진행 | **정보** | ✅ | **미도착** | ✅ **조치 큐** |
| **검토 반려** | 운영자가 반려 — 수정 후 재요청(**편집 재개**) | 진행 | **경고** | ✅ | **미도착** | **탭 없음** · 배지만 |
| 서명 진행중 | 검토 통과 · 양측에 서명 요청 발송, 서명 대기 | 진행 | **정보** | 3분기 | 3분기 | ✅ **갱신** |
| **체결 처리 대기** | 양측 서명 완료, 운영자 체결 처리 대기 | 진행 | **정보** | ✅ | ✅ | ✅ **조치 큐** |
| 체결완료 | 운영자 체결 처리 완료 → 계약 성립 · **공구 생성** | 종료(성공) | **성공** | ✅ | ✅ | ✅ |
| 거절 | 일방이 서명 거절 | 종료(실패) | **위험** | ✅ | ✅ | ✅ |
| 만료 | 서명 기한 내 미서명 → **운영자가 확인해 종결** | 종료(실패) | **중립** | ✅ | ✅ | ✅ **조치 큐** |
| 취소 | 서명 완료 전 브랜드 철회 | 종료(실패) | **중립** | ✅ | ✅ | ✅ |

**위 9종이 유일한 값이며 새 값을 만들지 않는다.**

| 항목 | 규칙 |
| --- | --- |
| **같은 상태값은 세 화면에서 같은 색** | 「검토 대기」가 운영자에게는 조치 필요 상태지만 파트너·스튜디오에서 정보색이다. **같은 계약이 세 화면에서 다른 색이면 안 된다**(원칙 ③). 운영자 화면에서 앞세우는 수단은 **조치 큐 카운트 + 정렬**이다 |
| **검토 반려만 경고색** | 진행 상태 중 **유일하게 브랜드 조치로만 풀린다.** 나머지 대기는 아무도 잘못하지 않은 정상 대기라 정보색이다(원칙 ①) |
| **종류 축은 색이 아니다** | 종료(실패) 3종이 같은 분류여도 색은 갈린다 — **거절만 위험**, 만료·취소는 중립. 거절은 상대가 명시적으로 기각한 **부정 결과 확정**이고, 만료·취소는 시간·철회로 닫힌 건이라 **원칙 ②**에 속한다 |
| 체결완료가 성공색인 이유 | 공구 생성 게이트가 열리는 **실질적 성취**다. 문의의 「답변완료」(중립)와 갈리는 지점 |
| **종결 스텝 칩도 배지와 같은 축** | `.stop` 거절(위험) · `.halt` 만료·취소(중립). 같은 화면에서 배지는 중립인데 스텝이 위험색이면 **어느 쪽이 진짜인지 읽을 수 없다** |

**서명 진행중을 쪼개지 않는다**

브랜드도 서명 대기 구간이 생기지만 「내 서명 대기 / 상대 서명 대기」로 **상태값을 쪼개지 않는다** — 한쪽만 서명한 조합이 **넷**(둘 다 미서명 · 나만 · 상대만 · 둘 다)이라 상태값으로 표현하면 **배지가 폭발한다.** 상태는 「서명 진행중」 하나(정보)이고, 누가 어디까지 했는지는 **4스텝 스텝퍼 + 서명 카드 2장**이 보여준다.

v1.3 배지 사전의 **「내 서명 대기 = 경고」 분리는 쓰지 않는다** — 서명은 상대를 기다리는 일이 아니라 **외부 전자서명에서 각자 하는 일**이라 이 화면의 조치 대기로 잡지 않는다.

> **[결정 필요] 체결 후 해지 값이 없다** — 9종 어디에도 체결완료 이후를 닫는 값이 없다. 공구가 이미 진행 중인 계약을 중단해야 하는 상황(재고 소진 · 콘텐츠 미이행 · 분쟁)에서 표현할 상태가 없다. 시안은 **값을 임의로 만들지 않는 규칙에 따라 그리지 않았고**, 현재는 **공구 관리의 「중단」**으로만 처리한다. 해지 값을 추가할지 확정해야 한다.
>

### 25-3. 모두싸인 API 미도입 — 수동 운영 전제 — `BE`

**API 요금제 비용 때문에 웹훅·문서조회 API를 쓰지 않는다**(요금제만 사용). **절차는 rev.5 그대로**이고 화면에 남는 제약만 셋이다.

| # | 제약 | 세 화면의 대응 |
| --- | --- | --- |
| 1 | **서명 링크를 우리가 갖지 못한다** — 모두싸인이 참여자에게 직접 보낸다 | 파트너·스튜디오에서 **서명 버튼을 없앴다.** 누를 대상이 없는 버튼은 **누르고 나서 아무 일도 일어나지 않는 것이 최악**이다. 대신 **`[서명 안내 다시 받기]`**(운영자 재발송 요청)를 두고, 대기 문구에 「메일·문자로 받은 전자서명 링크에서 서명합니다」를 명시한다 |
| 2 | **서명 완료를 실시간으로 받지 못한다** — 웹훅이 없다 | 운영자가 모두싸인에서 확인한 값이 화면에 온다. 서명 카드 하단에 **「확인한 시점 기준 · N 기준」**(`.s-asof`)을 적는다. **참여자별 3분기는 그대로 유지한다** — **값이 늦을 뿐 틀리지 않고**, 늦는다는 사실을 화면이 밝히면 읽을 수 있는 정보가 된다. 밝히지 않으면 방금 서명한 사람이 「왜 반영이 안 됐지」로 오해한다 |
| 3 | **PDF·감사추적인증서가 자동 수신되지 않는다** | 운영자가 **모두싸인에서 내려받아 업로드**한다(어드민 B4). 체결 처리 시 발급됨을 스튜디오 S3c·S11에 명시한다 |

**파생 규칙 2가지**

| 항목 | 규칙 |
| --- | --- |
| **만료가 자동 판정이 아니다** | 기한이 지나도 시스템이 스스로 닫지 못해 **운영자가 확인해 만료 처리**한다. 종결 스텝·이력의 주체를 **「시스템」에서 「운영자」**로 바꿨다 |
| **서명 기한도 우리가 정하지 않는다** | 운영자가 모두싸인에 직접 입력하므로 **기한도 거기서 정해진다.** 우리 화면이 「공구 시작 −3일」 같은 값을 계산해 보여주면 **있지도 않은 규칙이 생기고 모두싸인의 실제 값과 어긋난다.** 어드민 C1에서 **발송 일시와 나란히 입력받고**, 이 값이 만료 판단의 **유일한 기준**이 된다 |

> **API 도입 시 되돌릴 지점을 좁혀 뒀다** — 「기준 시각」 한 줄과 `[서명 안내 다시 받기]` 버튼만 제거하면 되고, **상태값 · 스텝퍼 · 3분기 구조는 건드리지 않는다.** 구조를 수동 운영에 맞춰 바꾸지 않은 것은 나중에 되돌리는 비용을 만들지 않기 위해서다.

### 25-4. 편집 잠금 · 되돌림 — `FE`·`BE`

**편집 잠금 구간**

| 구간 | 편집 |
| --- | --- |
| 작성중 | **가능** |
| **검토 대기 이후 전 구간** | **잠김** |
| **검토 반려** | **다시 열림** — 유일한 예외 |

**잠금 구간이 넓은 이유** — 검토 중에 내용이 바뀌면 **운영자가 본 것과 달라지고**, 서명 중에 바뀌면 **서명 대상이 달라진다.** 서명 진행중 이후 수정하려면 **취소 후 재작성**한다.

**운영자도 고칠 수 없다** — 어드민 화면에 수정 필드가 한 곳도 없다. **양측이 서명할 대상이 바뀌면 안 되기 때문**이며, 문제가 있으면 **반려**한다.

**되돌리는 경로가 2개로 갈린다 — 혼동 금지**

| 액션 | 가능 구간 | 결과 | 버튼 톤 | 사유 입력 |
| --- | --- | --- | --- | --- |
| **요청 취소** | **검토 대기**만 | **작성중으로 복귀** — 종결시키지 않는다 | **주 액션** | 없음 — 내부 되돌림일 뿐 상대에게 통지할 내용이 없다 |
| **계약 취소** | 서명 진행중 · 체결 처리 대기 | **취소(종료·실패)** — 항상 종결 | **위험** | **필수** |

서명 요청이 나간 뒤에는 `[요청 취소]`가 **사라지고** `[계약 취소]`만 남는다.

**회수 미채택** — 작성 스펙 §11의 「발송 취소(회수) → 작성중 복귀」는 채택하지 않는다. 확정 상태표에 취소가 **종료(실패)**로 못박혀 있어 일반적 회수는 표현할 상태가 없다. **검토 대기 한정으로만 부분 부활**했다.

**불가역 조치는 체결 완료 하나뿐** — 운영자의 서명 현황 체크는 **체결 전까지 해제 가능**하다. 오입력한 서명 완료가 양측 화면에 박히면 **되돌릴 경로가 있어야** 한다. 체결 완료를 누른 순간부터 잠긴다(공구가 생성되므로).

### 25-5. 계약 입력 항목 — `FE`·`BE`

브랜드만 입력하며, 스튜디오·어드민에서는 **전부 읽기 전용**이다.

#### 25-5-1. 계약 상대 · 공구 식별

| 필드 | 필수 | 규칙 |
| --- | --- | --- |
| 계약 상대 | **필수** | 드롭다운 · **「연결됨」 상태 상대만** · 스레드 경유 진입 시 **자동 지정 · 변경 불가** |
| 공구명 | **필수** | 텍스트 **2~40자** · **내부 관리용 식별명**이며 공구로 상속 |

**공구명은 소비자에게 보이는 제목이 아니다.** 소비자 노출 제목은 인플루언서가 쇼룸 스튜디오의 공구 게시물에서 따로 작성한다.

#### 25-5-2. 공구 기간

| 필드 | 필수 | 입력 방식 |
| --- | --- | --- |
| 시작 일시 | **필수** | **달력 모달** · 직접 입력 불가 |
| 종료 일시 | **필수** | **달력 모달** · 시작 일시 확정 후에만 열림 |

| 항목 | 규칙 |
| --- | --- |
| **선택 자체를 잠근다** | 제한값은 에러로 알리는 게 아니라 **회색 취소선으로 비활성**한다. 그 결과 **기간 관련 하드 오류 문구가 도달 불가능**해지고, 에러 문구는 직접 입력 필드(공구가)에만 남는다 |
| 모달을 나누는 이유 | 종료의 잠금 범위가 **시작값에 의존**하므로 순서를 강제한다 |
| 달력 표시 | **한 달씩** · `‹ ›` 이동 · 선택 가능일이 없는 방향은 잠금 |
| 시각 | **시 드롭다운(00~23) + 분 드롭다운(5분 단위)** |
| 시작 일시 하한 | **검토 요청일 + 7일 이후** (하드) — ⚠️ §28-8 B 참조 |
| 기간 | **3~30일** (하드) |

#### 25-5-3. 계약 상품 항목

| 열 | 필수 | 규칙 | 스튜디오 라벨 |
| --- | --- | --- | --- |
| 상품 | **필수** | 드롭다운 · **「진열」 상태 상품만** | 동일 |
| 정가 | — | **읽기 전용** · 상품 선택 시 자동 병기 | 동일 |
| 공구가 | **필수** | 부가세 포함 소비자 판매가 · **정가 이하 · 10원 단위** | 동일 |
| 리워드율 | **필수** | **0~90%** · 0.1% 단위 · **상품 항목 단위 차등** | **내 리워드율** |
| 예상 리워드 | — | **자동 계산**(공구가 × 리워드율 · 1개당) | 동일 |
| 최소 물량 | **필수** | 브랜드가 그 상품에 대해 확보를 약속하는 수량 | **브랜드 준비 물량** |

| 항목 | 규칙 |
| --- | --- |
| **출생지 규칙** | 계약 상품 항목이 **공구가·리워드율·최소 물량의 출생지**다. 리워드율은 **상품 항목 단위**이며 **정산이 이 값을 그대로 쓴다.** 공구 기간은 계약 단위이고 공구가 이를 상속한다 |
| 최소 건수 | **1건 이상.** 1건일 때 행 삭제 버튼 비활성 |
| 미선택 행 | 상품을 고르기 전에는 공구가·리워드율·최소 물량 입력 잠금 |
| 상품 변경 | 해당 행의 공구가·리워드율·최소 물량 **초기화** |
| **최소 물량이 상품 단위인 이유** | 상품이 여러 개인 계약에서 계약 하나에 물량 하나면 **어느 상품 몫인지 알 수 없고**, 판매·재고 대조도 상품 단위로만 가능하다 |
| **원가 판정 없음** | 공구가의 원가 이하 여부는 **판정하지 않는다.** 상품 객체에 원가 필드가 없고, 브랜드 원가는 **플랫폼이 알 권리가 없는 정보**다 |

#### 25-5-4. 고정 지급비 — **플랫폼 미중개**

| 필드 | 필수 | 규칙 |
| --- | --- | --- |
| 고정 지급비 | **필수** | 숫자(원) · **0원 허용** · **최대 10,000,000원** |
| **지급 시점** | **필수** | **3택** — 공구 게시물 등록 후 / 공구 종료 후 / 정산 완료 후 |
| 지급 조건 확인 | 조건부 **필수** | **0원 초과 시에만** 노출 · 미체크는 **하드 차단** |

| 항목 | 규칙 |
| --- | --- |
| 성격 | **매출과 무관한 별도 지급액.** 리워드와 합산하지 않는다 |
| **플랫폼은 중개하지 않는다** | **브랜드가 인플루언서에게 직접 지급**하며, 계약서에는 **금액과 지급 시점만** 기재된다. 플랫폼은 대금을 **보관하지도 중개하지도 않는다** |
| **지급 여부를 보증하지 않는다** | 플랫폼이 지급을 확인하거나 보증하지 않는다. **미지급 분쟁은 이슈 스레드에서 운영자 중재**로 다루고 **계약서가 근거**가 된다 |
| 고지 블록 | 0원 초과 시 **접히지 않는 고지 블록 + 확인 체크(필수).** 플랫폼이 보증하지 않는다는 사실 자체를 **계약 전에** 알려야 한다 |
| 미환급 | 지급 이후 콘텐츠 미이행은 **환급되지 않는다.** 회수도 실익이 없어 **사전 고지가 유일한 방어선** |
| **지급 완료 기록** | 브랜드가 지급 후 `[지급 완료 기록]`으로 표시한다. **기록이 없으면 미지급 분쟁 시 근거가 없다** |

**[rev.4→6] 지급 트리거를 브랜드가 고른다** — rev.4는 「게시물 등록 + 운영자 오픈 승인 완료」로 고정했으나, MVP에서 **플랫폼이 지급을 집행하지 않으므로 트리거를 플랫폼이 정할 근거가 없다.**

**[rev.3→6] 선결제 구조는 전면 폐기** — 선결제 내역 카드 · 결제수단 상태 · 선결제 이력을 **전부 삭제**했다. 남은 것은 **금액 + 지급 시점**이고 계약서에 기재되는 값일 뿐이다.

> **받는 쪽에 변화가 더 크다** — 선결제라면 「플랫폼에 돈이 있으니 받는다」지만, **직접 지급이면 브랜드가 안 주면 못 받는다.** 그래서 스튜디오 「내가 받는 금액」 카드에 **플랫폼 미보증 사실과 이슈 스레드·운영자 중재·계약서가 근거**라는 경로를 명시하고, **서명 전에 알아야 할 사실이라 서명 진행중 화면부터** 나온다.
> 

#### 25-5-5. 콘텐츠 의무

| 필드 | 필수 | 규칙 |
| --- | --- | --- |
| 게시 포맷·수량 | **필수** | 피드 / 릴스 / 스토리 각 숫자 · **합계 1 이상** · 플랫폼은 **인스타그램 고정** |
| 게시 완료 기한 | **필수** | 달력 · 기본값 = 공구 종료일 |
| 2차 활용권 | — | 허용 / 불허 · 기본 **허용** |
| 2차 활용 기간 | 조건부 **필수** | **허용일 때만** · 기간 지정(기본 12개월) / 무기한 · **무기한 선택 시 개월 입력 비활성** |
| 브랜드 사전 검수 | — | 있음 / 없음 · 기본 **없음** |
| 비고 | 선택 | 500자 · 2차 활용 **범위**는 문장이라 여기에 적는다 |

| 항목 | 규칙 |
| --- | --- |
| **게시 시점·유지 기간 삭제** | 둘 다 **외부 SNS 연동이 없어 시스템이 확인할 수 없고**, 실제로 다투게 되는 건 **약속한 수량을 언제까지 다 올렸는가** 하나다. 「콘텐츠 제출 기한」을 **「게시 완료 기한」**으로 통합하고 필수로 만들었다 |
| **이행 확인 주체** | **브랜드와 인플루언서가 연결·소통 스레드에서 직접 한다.** 운영자 수기 확인 경로를 두지 않는다 |
| 미이행 처리 | 금전 회수가 아니라 **계정 제재·재계약 차단** |
| **브랜드 사전 검수** | **있음**이면 인플루언서는 게시 전 초안을 스레드로 보내고, **브랜드 확인 없이 올린 콘텐츠는 이행으로 보지 않는다.** 이행 판정의 조건이 바뀌는 항목이라 계약서 문구와 같은 수준으로 화면에 적는다 |
| **명칭** | 「사전 검수」가 아니라 **「브랜드 사전 검수」** — 운영자가 하는 공구 게시물 문구 점검과 이름이 겹쳐 혼동된다 |
| **2차 활용 기간을 되살린 이유** | 비고는 **검증도 구조화도 없는 자유 입력**이라, 기간이 비면 **기한 없는 영구 허용**으로 해석될 여지가 생긴다 |

#### 25-5-6. 정산 조건 요약 — 읽기 전용 · 자동 표시

| 행 | 값 |
| --- | --- |
| 공구가 기준 | 부가세 포함 소비자 판매가 |
| 플랫폼 수수료 | **2%** |
| PG 결제 수수료 | `[자문대기-PG]` 회신 전 · **자리만 표시** |
| 리워드 원천징수 | 비사업자 **3.3% 공제 후 지급** / 사업자는 **세금계산서 발행** — **상대 계정 정보 기반 자동 전환** |
| 고정 지급비 | 입력값 · **리워드와 합산하지 않는 별도 지급액** |

**금액은 전부 공제 전 기준**이며 실지급액은 **정산 관리 소관**으로 넘긴다. 비사업자 원천징수 적용 방식이 세무 확정 전이라 **계약 화면에서 실지급액을 계산해 보여주지 않는다.**

### 25-6. 검증 — 하드 / 경고 2단 — `FE`·`BE`

**하드 — 검토 요청을 막는다**

| # | 조건 | 알림 방식 |
| --- | --- | --- |
| H1 | 공구가 > 정가 | 에러 문구 |
| H2 | 공구가가 10원 단위 아님 | 에러 문구 |
| H3 | 리워드율 0~90% 밖 | 에러 문구 |
| H4 | 공구 기간 3~30일 밖 | **달력에서 선택 차단** |
| H5 | 시작 일시 < 검토 요청일 + 7일 | **달력에서 선택 차단** |
| H6 | 콘텐츠 수량 합계 0 | 버튼 비활성 |
| H7 | 상품 항목 0건 | 버튼 비활성 |
| H8 | 고정 지급비 확인 체크 미완 | 버튼 비활성 |

**경고 — 막지 않고 검토 요청 확인 모달에서 열거 + 체크**

| # | 조건 |
| --- | --- |
| W1 | 할인율 70% 초과 |
| W2 | 리워드율 40% 초과 |
| W3 | 공구 기간 14일 초과 |
| W4 | 시작일이 검토 요청일 + 60일 이후 |
| W5 | 상품 10건 초과 |
| W6 | 고정 지급비 1,000,000원 초과 |

| 항목 | 규칙 |
| --- | --- |
| **에러 문구 vs 비활성** | **필수 미입력은 에러 문구 없이 버튼 비활성**만 한다(프로젝트 절대 규칙). 에러 문구는 **규칙 위반에만** 쓴다 |
| 선제 방어 | 상품을 고르면 **정가를 읽기 전용 열로 병기**하고 **예상 리워드를 자동 계산**해 위반과 오해를 미리 막는다 |
| **경고의 전달 경로** | 통과된 경고는 **운영자에게 전달**된다 — ⚠️ 전달 대상 화면 재확정 필요, §28-8 A |

> ⚠️ **어드민은 이 임계값을 판정하지 않는다.** MVP에 금액·기간 규칙이 없다는 전제로 **검토 체크리스트를 두지 않았다**(§28-2). 파트너센터의 W1~W6과 어드민의 「규칙 없음」 전제가 어긋나므로 §28-8 A에서 함께 정리한다.

### 25-7. 표준 조항 — `BE`·법무

브랜드가 **편집할 수 없으며** 계약서 생성 시 자동 삽입된다. 전문은 별도 모달로 열고 **입력 컨트롤을 하나도 두지 않는다.**

| # | 조항 | 상태 |
| --- | --- | --- |
| 1 | 화장품 표시·광고 준수 | 문안 작성 |
| 2 | 대가관계 표시 의무 | `[자문대기-법률 쟁점A]` |
| 3 | 최저가 정책 | 문안 작성 |
| 4 | 지식재산권 사용 범위 | 문안 작성 |
| 5 | 비밀유지 (종료 후 **1년 존속**) | 문안 작성 |
| 6 | 위반 시 조치 | 문안 작성 |
| 7 | CS 응대 주체 | 문안 작성 |
| 8 | 손해배상·위약금 | `[자문대기-법률]` — **산정 방식·상한 별도** |
| 9 | 준거법·분쟁 (**브랜드 주소지 관할**) | 문안 작성 |

**샘플·단독은 협의 변수가 아니라 표준 조항이다** — 값이 하나로 고정돼 있어(샘플은 항상 무상 제공, 판매는 항상 단독) **선택지를 주는 것 자체가 거짓**이다. 고를 수 없는 항목을 입력 필드로 두면 「아니오」인 계약이 존재하는 것처럼 읽힌다. **두 항목이 마지막이라 「협의 조건」 카드 자체가 없어졌다.**

**유상 샘플의 정산 상계가 불가능한 이유** — ① 자금 방향이 한 방향 ② 비사업자 원천징수 3.3%가 **총액 기준**이라 순액이 음수면 세무 처리가 성립하지 않음 ③ **PG 3자 분배에 음수 배분이 없음.**

> ⚠️ **정합 오류** — 요약 목록과 전문(9조)이 어긋난다. §26-6 #2 참조.

### 25-9. 호칭 — `FE`

| 서피스 | 화면 문구 | 이력 주체 |
| --- | --- | --- |
| 파트너센터 | **어드민** | 「어드민」(익명) |
| 쇼룸 스튜디오 | **운영자** | 「운영자」(익명) |
| 어드민 | **운영자** | **「김운영」(실명)** |

스튜디오가 「운영자」를 쓰는 이유는 **인플루언서가 보는 화면에 사내 용어를 쓰지 않기** 위해서다. 어드민이 「운영자」를 쓰는 이유는 **기존 어드민 20개 파일이 전부 「운영자」**이고 탑바가 "김운영 운영자"이기 때문이다 — 이 파일만 「어드민」이면 한 화면에 두 이름이 생긴다.

**모든 수동 처리에 처리자·시각이 남는다** — 만료 · 체결 · 서명 갱신 · 재발송 전부 기록된다.

> ⚠️ 지침 §4는 "어드민 화면 문구는 「어드민」"으로 기술하고 있다. **§28-8 C 확정 필요.**
