# 결제 연동 앱 전달사항 — 포트원 V2 (React Native)

Oct 5, 2026 · @hc

> 대상: 앱(RN) 개발. 서버는 포트원 V2 연동을 마쳤고, 앱은 **주문서 → 주문 생성 → 결제창 → 결과 확정** 4단계를 붙이면 된다.
> 반품·교환의 **배송비 결제**(3-8)도 같은 결제창을 쓴다.
> 서버 쪽 설계 근거는 `dev/결제 기능 구현 계획서.md`, 실제 스펙은 Swagger `User - Order` · `User - Payment` · `User - Claim` 태그가 기준이다.
>
> **10/5 갱신** — 3-6 주문 상세 신규 필드 · 항목 상태 `RETURNED` · 3-7 부분 환불 안내 · **3-8 반품·교환 배송비 결제(신규)** · 4절 클레임 결제 상태 · 6절 에러 코드 · 7절 규칙 10~11 · 8절 클레임 paymentId · 10절 결제 이후 화면 API

---

## 0. 한눈에

1. **금액은 앱이 만들지 않는다.** 주문 생성 응답의 `payment` 블록을 포트원 SDK에 넘긴다. `storeId`·`channelKey`도 앱에 박지 않는다 — 서버가 주문마다 내려준다.
2. **결제창이 끝나면 성공·실패와 관계없이 `complete`를 부른다.** 서버가 포트원을 직접 다시 조회해 판정한다. 앱이 받은 결과는 참고값일 뿐이다.
3. **최종 상태는 `complete` 응답이나 주문 상세로 판단한다.** `onComplete`가 오지 않아도(앱 종료·웹뷰 크래시) 웹훅이 주문을 완료시키므로, 결제 화면에 돌아오면 주문 상세를 다시 읽는다.
4. **실패 후 다시 결제할 때는 새 주문이 아니라 재시도 API**를 쓴다(`POST /orders/{orderId}/payments`).
5. **결제창은 반품·교환에서도 열린다**(교환 재발송 배송비 · 반려 상품 재발송 배송비). 결제창 재료는 같은 모양이라 같은 변환 함수를 쓰지만, **확정 API가 다르다** — `clm-`로 시작하는 `paymentId`는 `POST /v1/user/claims/payments/{paymentId}/complete`로 보낸다(3-8).
6. 지금은 **테스트 채널**이라 실제 출금은 일어나지 않는다.

## 1. 준비

| 항목 | 내용 |
| --- | --- |
| SDK | `@portone/react-native-sdk` 의 `<Payment request onComplete onError />` |
| PG | 토스페이먼츠(신모듈 · 결제창 일반결제). 카드 + 간편결제 3종(카카오·네이버·토스페이)이 **채널 1개**로 열린다 |
| `redirectUrl` | **넣지 않는다.** RN SDK가 내부에서 `portone://blank`로 덮어쓰고 그 결과를 `onComplete`로 돌려준다. 서버에도 리다이렉트 엔드포인트가 없다 |
| 앱 스킴 | 카드사·간편결제 앱 호출(`kakaotalk://`, `supertoss://`, `intent://` …)은 SDK가 처리한다. 앱 링크 목록은 SDK 플러그인이 `AndroidManifest`·`Info.plist`에 넣는다 |
| iOS 주의 | iOS 15+는 `LSApplicationQueriesSchemes`를 **50개까지만** 읽는다. 목록이 넘치면 카카오톡·네이버·토스·카드사 앱 스킴을 골라 직접 넣어야 한다. 「iOS에서만 카드사 앱이 안 열림」 문의가 오면 먼저 볼 곳 |
| 인증 | 모든 API는 `Authorization: Bearer {accessToken}` (USER) |

### 1-1. 키 · 설정값

**앱에 넣을 포트원 키는 없다.** 결제창에 필요한 값은 전부 주문 생성 응답(`payment` 블록)으로 주문마다 내려온다.

| 값 | 앱이 할 일 | 비고 |
| --- | --- | --- |
| `storeId` (상점 ID, `store-…`) | 응답 값을 쓴다. **앱에 고정하지 않는다** | |
| `channelKey` (채널 키, `channel-key-…`) | 응답 값을 쓴다. **앱에 고정하지 않는다** | 결제수단별로 다를 수 있다. 테스트 → 운영 채널 전환도 서버 설정만 바뀌므로 **앱 재배포가 필요 없다** |
| 가맹점 식별코드 `imp_…` | **쓰지 않는다** | 포트원 V1(아임포트) 값이다. V2 RN SDK는 받지 않는다. V1 예제 코드를 참고하지 말 것 |
| API Secret · 웹훅 시크릿 | **절대 앱에 넣지 않는다** | 서버 전용. 앱 번들에 들어가면 누구나 결제 취소·조회를 호출할 수 있다 |
| 서버 주소 | 환경별 API base URL만 설정 | 운영 `https://api.showroomz.shop` |

앱 쪽 설정은 1절 표의 **SDK 플러그인(앱 스킴 목록)** 뿐이다.

## 3. API

### 3-1. 주문서 — `POST /v1/user/orders/checkout`

C9 진입. **저장하지 않는다.** 장바구니 진입과 바로 구매 중 **하나만** 보낸다.

```json
{ "cartItemIds": [11, 12, 15] }
{ "direct": { "variantId": 301, "quantity": 1, "groupBuyId": 41 } }
{ "cartItemIds": [11], "deliveryAddressId": 7 }
```

- 바로 구매는 `groupBuyId` **필수**(상품 상세 응답의 값).
- `deliveryAddressId` 생략 시 기본 배송지. 기본 배송지도 없으면 `deliveryAddress: null` — **에러가 아니다.** 「배송지 없음」을 그리고 결제 CTA만 잠근다.
- 장바구니 항목 중 마감·품절이 섞여 있으면 400 `CART_ITEM_NOT_PURCHASABLE`로 **전체를 막는다**(조용히 빼지 않는다). C8이 그 항목을 선택에서 빼 주면 정상 경로에서는 안 온다.

**응답**

```json
{
  "deliveryAddress": { "id": 7, "recipientName": "김수민", "phoneNumber": "010-1234-5678", "zipCode": "06234",
                       "address": "서울 강남구 테헤란로 000", "detailAddress": "쇼룸타워 12층 1203호",
                       "memo": "문 앞에 놓아주세요", "isDefault": true },
  "memoPresets": ["문 앞에 놓아주세요", "경비실에 맡겨주세요", "부재 시 연락해주세요", "배송 전 미리 연락해주세요"],
  "groups": [
    { "marketId": 3, "marketName": "라보에이치", "groupBuyId": 41, "groupBuyNumber": "GB-20260901-003",
      "items": [
        { "cartId": 11, "orderProductId": null, "variantId": 301, "productId": 120,
          "productName": "시카 리페어 앰플 30ml", "optionName": "용량: 30ml + 리필 2개", "thumbnailUrl": "https://…",

```

| 필드 | 설명 |
| --- | --- |
| `deliveryAddress.memo` | 저장된 배송 메모 — 요청사항 입력란의 **초기값**으로 쓴다 |
| `groups[]` | 공구(쇼룸) 단위 묶음. **배송비는 그룹마다** 매긴다. 여러 쇼룸을 한 번에 주문하면 그룹이 여럿 |

| `ctaLabel` | 그대로 버튼 문구로 |

### 3-2. 주문 생성 — `POST /v1/user/orders` (201)

```json
{
  "idempotencyKey": "5f1e2b3c-0a1d-4c2e-9b7f-1234567890ab",
  "cartItemIds": [11, 12, 15],
  "deliveryAddressId": 7,
  "deliveryMemo": "문 앞에 놓아주세요",
  "payment": { "method": "CARD", "cardIssuer": "SHINHAN" },
  "expectedTotalAmount": 27900
}
```

| 필드 | 규칙 |
| --- | --- |
| `idempotencyKey` | **필수.** 「결제하기」를 누를 때마다 새 UUID. 단, **같은 요청을 재전송할 때(네트워크 오류·502)는 같은 키**를 쓴다 — 서버가 같은 주문을 돌려준다. 새 키로 재전송하면 주문이 하나 더 생기고 재고가 30분 더 잡힌다 |
| `cartItemIds` / `direct` | 주문서와 같다. 둘 중 하나만 |
| `deliveryAddressId` | 생략하면 기본 배송지. 기본 배송지도 없으면 400 `ORDER_ADDRESS_REQUIRED`(주문서와 달리 여기서는 에러) |
| `deliveryMemo` | 프리셋 또는 직접 입력, 50자 이내 |
| `payment` | `method=CARD`면 `cardIssuer` 필수, `method=EASY_PAY`면 `easyPayProvider` 필수 |
| `expectedTotalAmount` | 주문서의 `summary.totalAmount`. 그 사이 가격·배송비가 바뀌었으면 409 `ORDER_AMOUNT_CHANGED` → 주문서를 다시 불러 그린다 |

**응답**

```json
{
  "orderId": 1147,
  "orderNumber": "20260927-000123",
  "status": "PAYMENT_PENDING",
  "expiresAt": "2026-09-27T14:41:00",
  "payment": {
    "paymentId": "20260927-000123-1",
    "storeId": "store-…",
    "channelKey": "channel-key-…",
    "orderName": "시카 리페어 앰플 30ml 외 2건",
    "totalAmount": 27900,
    "currency": "KRW",
    "payMethod": "CARD",
    "cardCompany": "SHINHAN_CARD",
    "easyPayProvider": null,
    "customer": { "fullName": "김수민", "phoneNumber": "010-1234-5678", "email": "sumin@example.com" }
  }
}
```

- `orderId`·`paymentId`는 **앱이 들고 있어야 한다(로컬 저장 권장).** 결제창 도중 앱이 죽거나 토큰이 만료돼도 이 값으로 `complete`·주문 상세를 부른다.
- `expiresAt` — 결제 대기 만료 시각(기본 30분). 만료되면 서버가 주문을 `EXPIRED`로 내리고 재고를 돌려놓는다. 카드 인증이 진행 중이면 서버가 몇 분 미루기도 하므로 **정확한 시각으로 믿지 말고** 7절 1번(5분 전 잠금)만 지키면 된다.
- `orderName` — 결제창에 뜨는 상품명. 여러 개면 `"첫 상품명 외 N건"`.
- 주문이 만들어진 순간 **재고가 예약**된다. 결제 안 하고 나가도 30분 안에는 다른 소비자가 그 수량을 못 사므로, C9에서 「결제하기」를 누르기 전에는 주문을 만들지 않는다.
- 502 `PAYMENT_GATEWAY_ERROR` — 주문은 만들어졌고 포트원 사전 등록만 실패한 상태다. **같은 `idempotencyKey`로 다시 보낸다.**

### 3-3. 결제창 — `payment` 블록 → SDK `request`

값은 그대로 쓰되, **카드사·간편결제 두 필드는 중첩 객체로 옮겨야 한다.** 서버는 평평하게(`cardCompany`, `easyPayProvider`) 내리고, SDK는 `card.cardCompany` · `easyPay.easyPayProvider` 로 받는다.

```tsx
import { Payment } from '@portone/react-native-sdk';

function toPortOneRequest(p: PaymentWindow) {
  return {
    storeId: p.storeId,
    channelKey: p.channelKey,
    paymentId: p.paymentId,
    orderName: p.orderName,
    totalAmount: p.totalAmount,
    currency: p.currency,          // "KRW"
    payMethod: p.payMethod,        // "CARD" | "EASY_PAY"
    ...(p.payMethod === 'CARD' && p.cardCompany
      ? { card: { cardCompany: p.cardCompany } } : {}),
    ...(p.payMethod === 'EASY_PAY' && p.easyPayProvider
      ? { easyPay: { easyPayProvider: p.easyPayProvider } } : {}),
    customer: {
      fullName: p.customer.fullName,
      phoneNumber: p.customer.phoneNumber,
      ...(p.customer.email ? { email: p.customer.email } : {}),   // null 이면 키를 빼고 보낸다
    },
  };
}

<Payment
  request={toPortOneRequest(order.payment)}
  onComplete={(res) => completePayment(order.payment.paymentId, res)}
  onError={(err) => {
    // SDK 자체 오류(결제창이 아예 안 뜸). 결제는 일어나지 않았다 → C9 유지, 재시도 가능
  }}
/>
```

- `cardCompany` 를 지정하면 결제창이 그 카드사로 바로 열린다. 서버 값(`KRW`, `SHINHAN_CARD`, `KAKAOPAY` …)은 포트원 브라우저 SDK 최신 표기와 같아 변환하지 않는다(`dev/payment-test/index.html`에서 검증). RN SDK 버전 타입이 구표기(`CURRENCY_KRW` 등)를 요구하면 알려 달라.
- `customer.email` 은 개인정보 제3자 제공 동의 범위에 따라 서버 설정으로 빠질 수 있다(`null`). 위처럼 `null`이면 키를 빼고 보낸다.

**`onComplete` 응답** — `{ paymentId, code?, message?, txId?, transactionType }`
- `code`가 **없으면** 결제창이 성공으로 끝난 것, **있으면** 실패·중단(사용자가 닫음, 인증 실패, 한도 초과 등)이다. 어느 쪽이든 3-4 `complete`를 부른다.
- `onError`는 SDK 자체 오류(결제창이 아예 안 뜸)다. 결제는 일어나지 않았으니 C9에 머무르고 같은 `payment` 블록으로 다시 열면 된다.

**사용자가 결제창을 그냥 닫은 경우**(뒤로가기 · 앱 자체 닫기 버튼)
- SDK 콜백이 안 올 수 있다. 앱이 결제 화면을 직접 닫았으면 `complete`를 한 번 불러 상태를 확인한다 — `READY`면 결제 안 된 것이다.
- 결제를 시도한 적 없는(`READY`) 결제는 **같은 `payment` 블록으로 다시 열어도 된다.** `FAILED`가 됐으면 3-5 재시도 API로 새 `paymentId`를 받는다.
- 같은 `paymentId`로 결제창을 **동시에 둘** 띄우지 않는다(앱이 두 번 탭 방지).

### 3-4. 결제 결과 확정 — `POST /v1/user/payments/{paymentId}/complete`

`onComplete`를 받으면 **결과와 관계없이** 부른다. body는 없어도 된다.

```json
{ "clientResult": { "code": null, "message": null, "txId": "0195…" } }
```

`code`·`message`·`txId`는 `onComplete` 응답 값을 그대로 넣는다(성공이면 `code`가 `null`).

**응답** `{ orderId, orderNumber, orderStatus, paymentStatus, failReason }`

| `orderStatus` | `paymentStatus` | 의미 | 앱 처리 |
| --- | --- | --- | --- |
| `PAID` | `PAID` | 결제 완료 | 완료 화면 → 3-6 주문 상세로 그린다 |
| `PAYMENT_PENDING` | `FAILED` | 결제 실패(한도 초과 등) | `failReason` 표시, C9 유지 → 3-5 재시도 |
| `PAYMENT_PENDING` | `READY` | 아직 결제되지 않음 | 아래 「READY 처리」 |
| `EXPIRED` | `EXPIRED` 등 | 결제 대기 시간 초과 | `failReason` 표시 → 주문서부터 다시 |
| 아무거나 | `CANCEL_REQUESTED` · `CANCELLED_MISMATCH` | 서버가 자동 취소함(금액 불일치 · 만료 뒤 결제 · 이미 다른 결제로 완료) | `failReason` 표시. 돈은 자동 환불된다 |

**READY 처리 (권장)**
- `onComplete`에 `code`가 **있으면**(사용자가 창을 닫음·인증 실패) → 결제 안 된 것으로 보고 C9 유지, 재시도 가능.
- `code`가 **없는데** READY면 → 승인 반영이 늦는 경우다. 1~2초 간격으로 `complete`를 몇 번(예: 3회) 다시 부르고, 그래도 READY면 주문 상세 화면으로 보낸다(웹훅이 뒤이어 완료시킨다).

- **멱등이다.** 완료 화면에서 여러 번 불러도 된다.
- **결제 완료(`PAID`) 시 장바구니에서 해당 항목이 자동으로 삭제된다.** 완료 화면으로 넘어가면 장바구니 뱃지·목록을 다시 읽는다. 바로 구매는 장바구니와 무관하다.
- 502 `PAYMENT_GATEWAY_ERROR` — 서버가 포트원 조회에 실패. 상태는 그대로이니 잠시 뒤 다시 부른다.
- 404 `PAYMENT_NOT_FOUND` — 모르는 `paymentId`. 저장해 둔 값이 잘못됐거나 다른 환경(스테이징/운영)의 값이다.

### 3-5. 결제 재시도 — `POST /v1/user/orders/{orderId}/payments` (201)

실패하거나 창을 닫은 뒤 **같은 주문으로** 다시 결제한다. 결제수단을 바꿔도 된다.

```json
{ "payment": { "method": "EASY_PAY", "easyPayProvider": "KAKAOPAY" } }
```

- 응답은 주문 생성과 **같은 모양**이고 새 `paymentId`(`{주문번호}-{시도번호}`)가 들어 있다. 이 `payment` 블록으로 결제창을 다시 연다.
- 이전 결제창이 뒤늦게 결제돼도 서버가 하나만 남기고 나머지는 자동 취소한다. 앱은 신경 쓰지 않아도 된다.
- 409 `PAYMENT_ALREADY_IN_PROGRESS` — 이미 결제 완료된 주문 → 주문 상세로. 409 `ORDER_ALREADY_CLOSED` — 만료·취소된 주문 → 주문서부터 다시.
- 실패 뒤 주문서로 돌아가 「결제하기」를 다시 누르면 **새 주문**이 생겨 재고가 이중으로 잡힌다. C9에 머무르는 동안은 재시도 API를 쓴다.

### 3-6. 주문 상세 — `GET /v1/user/orders/{orderId}`

결제 완료 화면 · 결제 화면 복귀 시 재확인용이고, C10-1 주문 상세 화면도 이 API를 쓴다. 주문서와 같은 모양의 `groups`·`summary`에 다음을 더한다.

```json
{
  "orderId": 1147, "orderNumber": "20260927-000123", "status": "PAID",
  "orderedAt": "2026-09-27T14:11:00", "paidAt": "2026-09-27T14:13:42", "expiresAt": "2026-09-27T14:41:00",
  "deliveryAddress": { "id": null, "recipientName": "김수민", "phoneNumber": "010-1234-5678", "zipCode": "06234",
                       "address": "서울 강남구 테헤란로 000", "detailAddress": "쇼룸타워 12층 1203호", "memo": null, "isDefault": null },
  "deliveryMemo": "문 앞에 놓아주세요",
  "groups": [ { "…": "주문서와 같은 모양. items[].cartId 는 null, items[].orderProductId · status 에 값이 있다" } ],
  "summary": { "productTotal": 38000, "discountTotal": 13100, "deliveryFeeTotal": 3000, "totalAmount": 27900, "itemCount": 1,
               "discountRate": 34 },
  "payment": { "paymentId": "20260927-000123-1", "status": "PAID", "method": "CARD", "methodLabel": "신한카드",
               "cardIssuer": "SHINHAN", "easyPayProvider": null, "amount": 27900, "paidAt": "2026-09-27T14:13:42" },
  "cancellable": true,
  "addressChangeable": true,
  "items": [ { "…": "C10-1 항목 행 — 주문 내역 목록(GET /v1/user/orders)의 items[] 와 같은 모양" } ],
  "itemCount": 1,
  "maskedAddress": { "…": "마스킹된 배송지" },
  "notices": []
}
```

| 필드 | 설명 |
| --- | --- |
| `status` | 주문 상태(4절) |
| `paidAt` · `expiresAt` | 결제 전이면 `paidAt: null`. 만료·취소된 주문도 `expiresAt`은 남아 있다 |
| `deliveryAddress` | **주문 시점 스냅샷** — `id`·`memo`·`isDefault`는 null. 배송지를 나중에 고쳐도 주문에는 반영되지 않는다 |
| `groups[].items[].status` | 저장된 항목 상태 — `PENDING`(결제 대기) · `PAID`(결제 완료) · `PURCHASE_CONFIRMED`(구매 확정 — 배송완료 후 7일 자동) · `CANCELLED` · `RETURNED`(전량 반품). 배송 단계는 여기에 없다 — 화면에는 아래 `items[]`의 표시 상태를 쓴다 |
| `payment` | 주문을 완료시킨 결제. 결제 전이면 살아 있는 결제, 실패만 있으면 마지막 시도. `methodLabel`은 「신한카드」·「카카오페이」처럼 그대로 띄우는 문구 |
| `cancellable` | **지금 취소 버튼을 보여도 되는가.** 결제 전이거나, 결제 후 **모든 항목이 결제완료**이고 브랜드가 아직 상품 준비를 시작하지 않았을 때만 `true`. 취소·만료된 주문, 항목 일부가 취소된 주문은 `false` |
| `addressChangeable` | 배송지를 바꿀 수 있는가 — 결제완료이고 브랜드가 준비를 시작하기 전. `false`면 [배송지 변경]을 그리지 않는다(10절) |
| `items[]` · `itemCount` | C10-1 항목 행(쇼룸 그룹 없는 평면 목록). **표시 상태(`status`·`statusLabel`·`statusSub`)와 버튼(`actions[]`)을 서버가 내린다** — 앱이 상태→버튼 매핑을 들지 않는다. 표시 상태 값: `PAYMENT_PENDING` · `PAID` · `PREPARING` · `SHIPPING` · `RETURNING`(택배 반송) · `DELIVERED` · `CONFIRMED` · `CANCEL_REQUESTED` · `CANCELLED` · `RETURN_IN_PROGRESS` · `EXCHANGE_IN_PROGRESS` · `RETURNED` |
| `maskedAddress` | 마스킹된 배송지 — C10-1은 `deliveryAddress`(원문) 대신 이것을 그린다 |
| `notices[]` | 상단 안내 — 지금은 `CONFIRM_DUE`(구매확정 기한, `date` = 가장 이른 구매확정 예정) 하나. 문구는 앱이 갖는다. 없으면 빈 배열 |
| `summary.discountRate` | 할인율(%) — 상품 금액 기준, 배송비 제외. 주문 상세에만 있다(주문서는 null) |

- 송장·배송 이력은 이 응답에 없다 — 항목의 `TRACK_DELIVERY` 버튼이 배송 조회 API를 연다(10절).
- 결제 완료 화면은 기존처럼 `status`·`payment`·`summary`만 봐도 된다. 새 필드는 C10-1 화면용이다.

### 3-7. 주문 취소 — `POST /v1/user/orders/{orderId}/cancel`

`{ "reason": "단순 변심" }` (선택, 255자). 취소 버튼은 주문 상세의 `cancellable=true`일 때만 노출한다.

| 응답 | 의미 | 앱 처리 |
| --- | --- | --- |
| **200** `status: CANCELLED` | 취소 완료(결제 후였으면 환불까지 완료) | 「주문이 취소되었습니다」 |
| **202** `paymentStatus: CANCEL_REQUESTED` | PG 응답 지연 — 취소가 진행 중 | **「취소 처리 중」으로 그리고** 주문 상세를 다시 읽는다. 서버가 2분 뒤부터 자동으로 마무리한다. 실패로 그리면 안 된다 |
| 409 `PAYMENT_CANCEL_IN_PROGRESS` | 이미 취소 처리 중(중복 탭) | 주문 상세 새로고침 |
| 409 `ORDER_NOT_CANCELLABLE` | 만료·이미 취소된 주문 | 주문 상세 새로고침 |
| 409 `ORDER_CANCEL_WINDOW_CLOSED` | 브랜드가 상품 준비를 시작해 바로 취소 불가 | 메시지 표시. 소비자 **취소 요청** API는 아직 없다(10절) |
| 502 `PAYMENT_CANCEL_FAILED` | PG가 취소를 거절(주문은 그대로) | 「고객센터로 문의해 주세요」 |

응답 body: `{ orderId, status, paymentStatus, message }` — `message`는 그대로 띄워도 되는 문구다.

- 소비자가 이 API로 하는 취소는 **전액**만 된다. 취소되면 재고도 돌아간다.
- **부분 환불**은 반품 환불 · 브랜드가 취소한 항목에서만 생긴다. 앱이 부르는 API는 없다 — 서버가 환불 대상으로 올리고 운영 쪽에서 집행한다. 앱은 주문 내역·상세 항목의 「환불 처리 중」, 반품 상세의 `refund.confirmed`(`false`면 「환불 예정 금액」)를 그대로 그리면 된다.
- 200이 와도 카드사 승인 취소가 명세서에 반영되는 데는 카드사별로 며칠 걸릴 수 있다 — 「환불은 카드사 사정에 따라 3~7일 걸릴 수 있어요」 같은 안내 문구를 두는 게 좋다(PG 일반 안내, 서버가 보장하는 값은 아니다).
- 결제 전 취소(`PAYMENT_PENDING`)는 포트원과 무관하게 즉시 200이다.

### 3-8. 반품·교환 배송비 결제 (신규)

반품·교환에서 고객이 배송비를 **앱에서 결제**하는 경우는 두 가지다. 반품의 고객 귀책 배송비는 환불액에서 빼므로 결제가 없고, 반송 택배비는 고객이 택배사에 직접 낸다(앱이 받지 않는다).

| 언제 | 결제창을 여는 API | 금액 |
| --- | --- | --- |
| **고객 귀책 교환** 요청 시 — 재발송 배송비 | `POST /v1/user/claims` 응답의 `payment` | 요청 폼 `fees.consumerFault` |
| 검수에서 **반려된 상품을 다시 받을 때** — 반려 상품 재발송 배송비 | `POST /v1/user/claims/{claimId}/reship-fee/payments` 응답 전체 | 반품·교환 상세 `reshipFee.amount` |

**주문 결제와 같은 점**
- 결제창 재료는 주문 생성 응답의 `payment` 블록과 **같은 모양**(`PaymentWindow`)이다 → 3-3의 `toPortOneRequest`를 그대로 쓴다. `customer.email`은 항상 `null`이라 키가 빠진다.
- 결제수단은 같은 enum(`method` · `cardIssuer` · `easyPayProvider`)이고, 열려 있는 수단도 주문서의 `paymentMethods`와 같다.
- 결제창이 끝나면 **결과와 관계없이** 확정 API를 부른다. 서버가 포트원을 직접 조회해 판정하고, 앱이 못 불러도 웹훅·정리 배치가 같은 확정을 한다. 멱등이다.
- 금액이 맞지 않거나 이미 다른 시도로 결제된 경우 등 **받을 수 없는 결제는 서버가 자동 취소**한다.

**주문 결제와 다른 점**

| 항목 | 주문 결제 | 반품·교환 배송비 결제 |
| --- | --- | --- |
| `paymentId` | `20260927-000123-1` | `clm-{청구ID}-{시도번호}` (`clm-41-1`) |
| 확정 API | `POST /v1/user/payments/{paymentId}/complete` | **`POST /v1/user/claims/payments/{paymentId}/complete`** (body 없음) |
| 재시도 | 재시도 API(3-5) | 교환: `POST /claims`를 **같은 `idempotencyKey`**로 다시 보낸다(수단 변경 가능). 반려 재발송: 같은 API를 다시 부른다 — 둘 다 새 `paymentId`가 나온다 |
| 미결제 방치 | 30분 뒤 주문 `EXPIRED` | 교환: 30분 안에 결제되지 않으면 **요청 자체가 지워진다**(잡아 둔 교환 옵션 재고도 풀린다). 반려 재발송: 기한(`reshipFee.dueDate`)이 지나도 상품이 폐기되기 전까지 결제할 수 있다 |
| 금액 검증 | `expectedTotalAmount` → 409 `ORDER_AMOUNT_CHANGED` | 교환: `expectedFee` / 반려 재발송: `expectedAmount` → 409 `CLAIM_AMOUNT_CHANGED` |
| 만료 시각 | `expiresAt` | 응답에 없다 |

#### 교환 요청 — `POST /v1/user/claims` (201)

```json
{
  "idempotencyKey": "8f1c0b7e-…",
  "type": "EXCHANGE",
  "deliveryGroupId": 512,
  "items": [ { "orderProductId": 1501, "quantity": 1, "exchangeVariantId": 302 } ],
  "reasonCode": "SIZE_MISMATCH",
  "invoice": null,
  "expectedFee": 3000,
  "payment": { "method": "CARD", "cardIssuer": "SHINHAN" }
}
```

- `deliveryGroupId` · 사유 · 금액은 요청 폼(`GET /v1/user/claims/form?orderProductId=&type=EXCHANGE`)이 준 값을 쓴다. 사유의 `feeBearer`가 `CONSUMER`(단순 변심 · 주문 실수 · 사이즈)면 고객 귀책이다.
- `payment`는 **고객 귀책 교환에서만 필수**다(빠지면 400 `INVALID_INPUT`). 브랜드 귀책 교환과 반품은 `null` — 결제 없이 바로 접수된다.
- 응답 `{ requestId, claimIds, status, payment }`
  - `status = PAYMENT_PENDING` + `payment` 있음 → 결제창을 연다. **결제가 확정돼야 접수된다.**
  - `status = REQUESTED`(송장 나중에) · `COLLECTING`(송장 같이 냄) + `payment: null` → 이미 접수됨. `claimIds`로 상세를 연다.
- 결제 실패 뒤 **내용을 고쳐** 다시 요청하면(새 `idempotencyKey`) 이전 미결제 요청은 지워진다. **수단만 바꿀 때는 같은 키**로 보낸다.
- 502 `PAYMENT_GATEWAY_ERROR` — 결제 준비만 실패했고 요청은 결제 대기로 남아 있다. 같은 `idempotencyKey`로 다시 보낸다.

#### 반려 상품 재발송 배송비 — `POST /v1/user/claims/{claimId}/reship-fee/payments` (200)

```json
{ "method": "EASY_PAY", "easyPayProvider": "KAKAOPAY", "expectedAmount": 3000 }
```

- 결제수단을 `payment`로 감싸지 않고 **평평하게** 보낸다(교환 요청과 다르다).
- 반품·교환 상세의 `reshipFee.state = PAYABLE`일 때만 된다. 그 밖(`WAITING` · `DEDUCTED` · `COVERED` · 이미 결제됨)은 409 `CLAIM_PAYMENT_NOT_REQUIRED`.
- 응답이 곧 결제창 재료(`PaymentWindow`)다. 결제가 확정되면 반려 상품이 「발송 준비 중」으로 넘어간다.

#### 확정 — `POST /v1/user/claims/payments/{paymentId}/complete`

**응답** `{ paymentStatus, requestId, claimIds, claimStatus }`

| `paymentStatus` | `claimStatus` | 앱 처리 |
| --- | --- | --- |
| `PAID` | `REQUESTED` · `COLLECTING` | (교환 요청) 접수 완료 → `claimIds`로 상세(접수 화면) |
| `PAID` | 보지 않는다 | (반려 재발송비) 결제 완료 → 반품·교환 상세 새로고침 |
| `READY` · `FAILED` | `PAYMENT_PENDING` | 결제되지 않음(창 닫음·실패) → 요청 화면으로 돌아간다. 입력 내용은 그대로 두고 다시 요청 |
| `CANCEL_REQUESTED` · `CANCELLED` | — | 서버가 자동 취소함(금액 불일치 · 요청이 이미 지워짐 · 다른 시도로 이미 결제됨). 돈은 자동 환불된다 |

- `claimIds`가 빈 배열이면 요청이 이미 지워진 것이다(30분 경과) — 요청 화면부터 다시.
- 404 `PAYMENT_NOT_FOUND` — 주문 결제 확정 API(`/v1/user/payments/…`)에 `clm-` 결제를 보냈거나 그 반대인 경우에도 난다.
- 502 `PAYMENT_GATEWAY_ERROR` — 조회 실패, 상태는 그대로다. 잠시 뒤 다시 부른다.
- 교환 요청의 항목을 **전부 철회**하면(`POST /claims/{claimId}/withdraw`, 회수 송장 등록 전까지) 결제한 재발송 배송비가 **자동으로 결제 취소**된다.

## 4. 상태값

**주문 `OrderStatus`**

| 값 | 화면 |
| --- | --- |
| `PAYMENT_PENDING` | 결제 대기 |
| `PAID` | 결제 완료 |
| `CANCELLED` | 취소 |
| `EXPIRED` | 만료(결제 시간 초과) |

결제 실패는 주문 상태를 바꾸지 않는다 — 주문은 `PAYMENT_PENDING` 그대로이고 결제만 `FAILED`가 된다.

**결제 `PaymentStatus`** — 앱이 실제로 분기하는 것은 굵게 표시한 값이다.

| 값 | 의미 |
| --- | --- |
| **`READY`** | 결제 대기(결제창 열림·미결제) |
| **`PAID`** | 결제 완료 |
| **`FAILED`** | 결제 실패 — 재시도 가능 |
| `EXPIRED` | 주문 만료로 닫힘 |
| `SUPERSEDED` | 재시도로 새 결제가 발급돼 대체됨 |
| `CANCELLED` | 취소 |
| **`CANCEL_REQUESTED`** | 취소 진행 중 |
| **`CANCELLED_MISMATCH`** | 서버 자동 취소(금액 불일치 등) |
| `CANCEL_FAILED` | 자동 환불 실패 — 운영자가 처리 |

주문 상태는 배송·반품 단계를 담지 않는다. 결제 후 화면의 단계는 주문 상세·주문 내역 `items[]`의 표시 상태(3-6)를 쓴다.

**반품·교환 배송비 결제 `ClaimPaymentStatus`** (3-8 확정 응답의 `paymentStatus`)

| 값 | 의미 |
| --- | --- |
| **`READY`** | 결제 대기 — 결제되지 않음 |
| **`PAID`** | 결제 완료 |
| **`FAILED`** | 결제 실패(창 닫음 포함) — 다시 요청 |
| `CANCEL_REQUESTED` | 자동 취소 진행 중 |
| `CANCELLED` | 결제 취소됨(자동 취소 · 교환 전부 철회) |

## 6. 에러 코드

응답 형식: `{ "code": "ORDER_AMOUNT_CHANGED", "message": "상품 가격 또는 배송비가 변경되었습니다. 주문서를 다시 확인해 주세요." }`
`message`는 사용자에게 그대로 보여 줘도 되는 문구다. 필드 검증 실패(`@NotNull` 등)도 같은 모양으로 오고, 여러 필드가 틀려도 **첫 번째 메시지 하나**만 온다.

| code | HTTP | 언제 | 앱 처리 |
| --- | --- | --- | --- |
| `INVALID_INPUT` | 400 | `cartItemIds`·`direct` 둘 다/둘 다 없음, 카드사·간편결제 미선택, 수량 1~99 벗어남, 메모 50자 초과 등 | 입력 확인 |
| `ORDER_ADDRESS_REQUIRED` | 400 | 배송지 없이 주문 생성 | 배송지 선택 유도 |
| `ORDER_ITEMS_EMPTY` | 400 | 주문할 상품 없음 | |
| `CART_ITEM_NOT_PURCHASABLE` | 400 | 마감·품절·계약에 없는 옵션 | 장바구니로 |
| `INSUFFICIENT_STOCK` | 400 | 재고 부족 | 장바구니로 |
| `PAYMENT_METHOD_UNAVAILABLE` | 400 | 꺼진 결제수단 선택(주문 · 반품·교환 배송비 공통) | 주문서·요청 폼 다시 조회 |
| `ORDER_ACCESS_DENIED` | 403 | 남의 주문·결제 | |
| `ADDRESS_ACCESS_DENIED` | 403 | 남의 배송지 | |
| `ORDER_NOT_FOUND` · `PAYMENT_NOT_FOUND` | 404 | | |
| `ORDER_AMOUNT_CHANGED` | 409 | 주문서와 서버 금액이 다름 | **주문서 다시 조회** 후 재확인 |
| `ORDER_ALREADY_CLOSED` | 409 | 같은 멱등키의 주문 또는 재시도 대상 주문이 만료·취소됨 | 주문서부터 다시(새 멱등키) |
| `PAYMENT_ALREADY_IN_PROGRESS` | 409 | 재시도했는데 이미 결제 완료 | 주문 상세로 |
| `PAYMENT_CANCEL_IN_PROGRESS` · `ORDER_NOT_CANCELLABLE` · `ORDER_CANCEL_WINDOW_CLOSED` | 409 | 3-7 | 주문 상세 새로고침 |
| `CLAIM_AMOUNT_CHANGED` | 409 | 반품·교환 배송비가 화면 값(`expectedFee` · `expectedAmount`)과 다름 | 요청 폼·상세 다시 조회 |
| `CLAIM_PAYMENT_NOT_REQUIRED` | 409 | 반려 재발송비를 낼 상태가 아님(`reshipFee.state ≠ PAYABLE` · 이미 결제됨) | 반품·교환 상세 새로고침 |
| `PAYMENT_GATEWAY_ERROR` | 502 | 포트원 통신 실패 | 주문 생성 · 교환 요청이면 **같은 멱등키로** 재요청, complete면 잠시 뒤 재호출 |
| `PAYMENT_CANCEL_FAILED` | 502 | PG 취소 거절 | 고객센터 안내 |
| (401) | 401 | 토큰 만료 | 토큰 갱신 후 **같은 `orderId`·`paymentId`로 이어서** 진행. 주문은 서버에 남아 있다 |

## 7. 앱이 꼭 지켜야 할 규칙

서버만으로는 막을 수 없는 UX라 앱에서 처리해야 한다.

1. **`expiresAt` 5분 전부터 결제 CTA를 잠근다.** 「주문 시간이 만료됐어요. 다시 주문해 주세요」를 띄우고 주문서부터 다시 시작하게 한다. 만료 직전에 결제를 시작하면 승인 도중 주문이 만료돼 결제 후 자동 환불되는 일이 생긴다.
2. **멱등키는 「새 주문」마다 새로, 「재전송」에는 그대로.** (3-2)
3. **결제 화면으로 돌아오면 주문 상세를 다시 읽는다.** 앱이 백그라운드에 있는 사이 웹훅이 결제를 완료했을 수 있다.
4. **취소 202는 실패가 아니다.** 「취소 처리 중」으로 그린다. (3-7)
5. **금액을 앱에서 계산·조립하지 않는다.** 화면 금액은 주문서 `summary`, 결제 금액은 주문 생성 응답 `payment.totalAmount`.
6. **`complete`는 결과와 관계없이 부른다.** `onComplete`가 실패를 알려도 서버가 최종 판정한다.
7. **`orderId`·`paymentId`를 로컬에 저장해 둔다.** 결제창 도중 앱이 죽어도 재진입 시 주문 상세로 복귀시킬 수 있다. 완료·취소·만료가 확인되면 지운다.
8. **주문 생성은 「결제하기」 탭 한 번에 한 번.** 탭 직후 버튼을 잠근다. 주문이 생기면 재고가 30분 잡히므로 뒤로 갔다 다시 누를 때마다 새 주문을 만들면 안 된다 — 같은 주문이 살아 있으면(`PAYMENT_PENDING`) 재시도 API로 결제창만 다시 연다.
9. **결제 완료 뒤 장바구니를 다시 읽는다.** 서버가 결제된 항목을 지운다(3-4).
10. **확정 API는 `paymentId`로 고른다.** `clm-`로 시작하면 `POST /v1/user/claims/payments/{paymentId}/complete`, 아니면 `POST /v1/user/payments/{paymentId}/complete`. 결제창 컴포넌트를 공용으로 쓸 때 특히 주의한다(3-8).
11. **교환 배송비 결제를 다시 시도할 때 수단만 바꾸면 같은 `idempotencyKey`, 내용을 고치면 새 키.** 새 키로 보내면 이전 미결제 요청이 지워진다(3-8).

- **Swagger** — `User - Order`, `User - Payment`, `User - Claim` 태그. 요청·응답 예시가 들어 있다.

  2. `dev/결제 테스트 시드 (로컬).sql` 실행 → 소비자·진행 중 공구 생성. 소비자 계정 `paytest / Test1234!`(`POST /v1/user/auth/local/login`), 시드 마지막 SELECT가 `variantId`·`groupBuyId`를 알려 준다

## 10. 결제 이후 화면 API

결제 연동 범위는 아니지만, 결제 완료 뒤 이어지는 화면이 쓰는 API다. 상세 스펙은 Swagger, 설계 근거는 `dev/앱 주문 내역/C10_주문내역_주문상세_BE_설계서.md` · `dev/앱 반품 교환/C10-2~5_앱_배송조회_반품교환_BE_설계서.md`.

| 화면 | API | 비고 |
| --- | --- | --- |
| C10 주문 내역 | `GET /v1/user/orders?page=1&size=20` | 최근 6개월, **결제된 적 있는 주문만**(결제 대기·만료·결제 전 취소는 안 나온다). `size` 1~50 |
| C10-1 주문 상세 | `GET /v1/user/orders/{orderId}` | 3-6 |
| C10-1 배송지 변경 | `PATCH /v1/user/orders/{orderId}/delivery-address` `{ "addressId": 55 }` | `addressChangeable`일 때만. 준비 시작 뒤면 409 `ORDER_ADDRESS_NOT_CHANGEABLE`. 배송비는 다시 계산하지 않는다 |
| C10-2 배송 조회 | `GET /v1/user/orders/{orderId}/items/{orderProductId}/tracking` | 항목의 `TRACK_DELIVERY` 버튼 |
| C10-3 반품·교환 요청 | `GET /v1/user/claims/form` → `POST /v1/user/claims` | 배송완료 항목만. 고객 귀책 교환은 결제(3-8) |
| C10-5 반품·교환 상세 | `GET /v1/user/claims/{claimId}` | 회수 송장 `PUT …/collection-invoice` · 철회 `POST …/withdraw` · 교환 배송지 `PATCH …/reship-address` · 반려 재발송비 결제 `POST …/reship-fee/payments`(3-8) |
| C10-4 회수 조회 · C10-2 재발송 배송 조회 | `GET /v1/user/claims/{claimId}/collection-tracking` · `…/reship-tracking` | |

**항목 버튼(`actions[]`)은 내려온 것만 그린다.** 지금 내려가는 것은 `CANCEL` · `TRACK_DELIVERY` · `RETURN_EXCHANGE` · `RETURN_REQUEST` · `EXCHANGE_REQUEST` · `CLAIM_DETAIL`이다.

**아직 없는 것**

| 항목 | 상태 |
| --- | --- |
| 소비자 **취소 요청**(브랜드가 준비를 시작한 뒤) | 앱용 API 없음. 주문 취소는 409 `ORDER_CANCEL_WINDOW_CLOSED`까지만 오고, `CANCEL_REQUEST` · `CANCEL_DETAIL` 버튼도 내려가지 않는다. 브랜드가 반려한 취소 요청은 항목의 `cancelRejection`으로 보인다 |
