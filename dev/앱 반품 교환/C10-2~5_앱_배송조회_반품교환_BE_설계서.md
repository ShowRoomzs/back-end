## 0. 먼저 정한 9가지

### 0-1. 도메인은 35 설계서의 것이고, 이 문서는 **앱 API와 그 차이**만 적는다

`order_claim` · `order_claim_collection` · 상태 전이 · 구매확정 연동은 35 설계서가 정본이다. 다만 35 설계서는 앱 시안이 없을 때 쓰여서 여섯 군데가 시안과 다르다 — 1절에 모으고, 35 설계서 본문에도 `[앱]` 표시로 반영했다(8절 대조표).

### 0-2. 화면의 단위는 **요청(= 한 박스 = `order_claim_collection`)**, 처리의 단위는 항목(`order_claim`)

C10-3은 같은 브랜드의 항목 여러 개를 체크해 **한 번에** 요청하고(「선택한 상품만 한 박스에」), C10-5는 「반품 상품 2개」를 한 화면에 그리되 **항목마다 상태가 갈린다**(일부 반려). 35 설계서 0-5의 회수 그룹이 정확히 이 단위다 — 사유 · 회수 송장 · 수취 주소 · 배송비는 요청에, 상태 · 검수 판정은 항목에 있다.

- API 경로의 키는 `claimId`다(C10 설계서의 `ItemRow.claim.claimId`가 진입점이라). 서버가 그 클레임의 요청 전체를 돌려주고, 요청 단위 동작(송장 등록 · 배송지 변경)은 그 요청에 적용한다.
- **한 요청 = 한 하위주문(브랜드) · 한 유형 · 한 사유**다(35 설계서 N3을 시안이 받았다 — 반품 화면과 교환 화면이 따로이고, 사유는 화면에 하나다).

### 0-3. 회수는 **직접 발송 하나**, 송장은 **요청과 함께 또는 7일 안에**

추적 API가 조회 전용이라 수거 예약이 없다(시안 C10-3 · 35 설계서 3-2와 같은 결론). 달라지는 것은 둘이다.

- **요청할 때 송장을 같이 받는다** — 이미 부쳤으면 요청 순간 「회수중」으로 시작한다(`REQUESTED`를 거치지 않는다).
- **「나중에 입력」은 7일 기한이 붙는다** — 지나면 요청이 **자동 취소**되고 항목은 배송완료로 돌아간다. 35 설계서 §35-9 A-4(소비자 미발송 종결 — 「자동 취소 기한 없음 · 정산이 묶인다 · 런칭 전 확정 필요」)가 이것으로 닫힌다.

### 0-4. 배송비는 **B안** — 반송은 택배사에 직접, 앱이 다루는 돈은 셋뿐

| 돈 | 누가 · 언제 | 앱의 처리 |
| --- | --- | --- |
| 반송 택배비(고객 → 브랜드) | 고객 귀책 = 고객이 **선불**로 택배사에 / 브랜드 귀책 = **착불** | **다루지 않는다** — 안내 문구만(`courierPayment`) |
| 반품 배송비 차감 | 고객 귀책 반품 — 환불액에서 뺀다 | 환불 예정액 계산(1-4) |
| 재발송 배송비 | ① 고객 귀책 교환 — **요청할 때 결제** ② 검수 반려 — 다시 받으려면 결제(또는 환불액 차감 · 선결제분 충당) | PG 결제(1-5 · 3-3) |

금액은 **요청당 한 번**이다(시안: 2개를 골라도 `3,000원 차감`). 35 설계서는 차감을 항목(클레임)마다 스냅샷했다 — 요청으로 옮긴다(1-4).

### 0-5. 재발송 배송비 결제는 **주문 결제와 다른 테이블**을 쓴다

`payment`는 주문에 묶여 있다(`uk_payment_order_attempt` · 확정 시 주문 전이 · `orders.paid_payment_id` · 대사 배치). 여기에 「주문이 아닌 결제」를 섞으면 주문 결제 상태기계의 모든 조회에 구분 조건이 붙는다. `order_claim_payment`를 따로 두고 **포트원 호출부(`PortOnePaymentGateway`)만 재사용**한다(1-5). 덤으로 철회 시 환불이 「그 결제의 전액 취소」가 된다 — 게이트웨이가 전액 취소 전용이어도 된다(C10 설계서 C1의 부분 취소 문제를 건드리지 않는다).

### 0-6. 스캔 이력은 **저장해 둔 것을 읽는다** — 화면이 택배 API를 부르지 않는다

추적 설계서 1-1: 송장당 일 10회를 감시 배치가 정확히 다 쓴다(「운영자 수동 재조회도 만들지 않는다. 여유가 없다」). 앱 화면이 열릴 때마다 조회하면 한도가 깨진다. 폴링이 받은 이력을 `delivery_tracking_event`에 쌓고(1-6) C10-2 · C10-4가 그것을 읽는다. **최신성은 폴링 주기(2시간)만큼**이다 — 시안의 면책 한 줄(「실제 배송 현황과 차이가 있을 수 있어요」)이 이 지연을 덮는다.

### 0-7. 라벨 · 보조 문구 · 할 일 · 버튼은 **서버가 내린다**

C10 설계서 0-4와 같은 규칙. 클레임의 소비자 표시(상태 줄 · 로즈 「할 일」 · 항목 아래 버튼)는 `UserClaimPresenter` 한 곳이 만들고 **주문 내역(C10) · 주문 상세(C10-1) · 클레임 상세(C10-5)가 같은 값을 쓴다**(4-2).

### 0-8. 사유 · 택배사 · 금액은 **폼 API가 내린다** — 앱에 목록을 박지 않는다

시안의 사유는 4종(단순 변심 · 주문 실수 · 상품 파손·불량 · 오배송)이고 기획 §35-3은 5종(「사이즈가 맞지 않음」 · 「오배송 및 배송 지연」)이며, §35-3은 「소비자 앱과 동일 문자열 · enum 단일 소스」를 요구한다. 지금은 둘이 다르다(9절 Q1). 어느 쪽으로 확정되든 앱 배포가 되지 않게 **선택지를 서버가 내린다**(3-1).

### 0-9. 본인 화면에는 원문, 기록 화면에는 마스킹

요청 화면(C10-3)의 「받을 곳」은 지금 고르는 값이라 원문이다. 접수 화면 · 상세(C10-5) · 회수 조회(C10-4)는 스크린샷으로 돌아다니는 기록이라 C10 설계서 3-2의 `OrderAddressMasker` 규칙으로 가린다(김수\* · 010-\*\*\*\*-5678 · 상세 주소 `******`). **브랜드 반품센터 주소는 가리지 않는다** — 송장에 적어야 하는 값이다.

## 1. 35 설계서의 도메인에 더하는 것

클레임 테이블은 아직 배포 전이다(코드에 `OrderClaim*` 없음). 그래서 아래 컬럼은 `ALTER`가 아니라 **35 설계서의 `CREATE` 문에 합친다**. 신규 테이블 둘과 기존 `order_delivery_group`의 컬럼 1개(`base_delivery_fee` — 1-4)만 이 문서의 마이그레이션이다(1-7).

### 1-1. 상태 1종 · 결과 1종 추가

| 추가 | 값 | 의미 |
| --- | --- | --- |
| `ClaimStatus` | `PAYMENT_PENDING`(결제 대기) | 고객 귀책 교환 요청이 재발송 배송비 결제를 기다리는 **임시 상태**. 브랜드 화면 어느 탭에도 나오지 않고(`ALL`에서도 제외), 결제 확정 순간 `REQUESTED`/`COLLECTING`이 된다. 30분 안에 결제가 안 되면 **행을 지운다**(아직 접수된 적 없는 요청이다) |
| `ClaimResult` | `CANCELLED`(요청 취소) | 검수 전에 요청이 사라진 종결 — `cancel_reason`이 까닭을 든다 |

`order_claim.cancel_reason VARCHAR(20) NULL` — `WITHDRAWN`(소비자 철회) / `INVOICE_EXPIRED`(송장 미등록 자동 취소) / `ADMIN`(운영자 직권 — 35 설계서 3-7 `closeByAdmin`. 종전에는 `REJECTED`로 닫았는데, 검수 거절과 섞이면 거절률 집계(§35-9 C-12)가 오염된다).

`CANCELLED`는 환불도 반송도 없다. 항목은 원래 줄(배송완료)로 돌아가고 **반려 줄(`claimRejection`)을 남기지 않는다**(C10 시안: 「자동 취소되면 상세 화면 없이 알림만」).

### 1-2. `order_claim_collection` — 요청 단위 값이 여기로 온다

| 컬럼 | 비고 |
| --- | --- |
| `type` VARCHAR(16) · `reason_code` · `reason_detail` · `fee_bearer` | 요청에 하나다(0-2). `order_claim`의 같은 컬럼은 **목록 조회용 사본**으로 남긴다(브랜드 목록 필터가 클레임 행을 읽는다) |
| `idempotency_key` VARCHAR(64) | `UNIQUE (user_id, idempotency_key)` — 주문 생성과 같은 규약. 재시도가 요청을 둘 만들지 않는다 |
| `invoice_due_at` DATETIME(6) | 회수 송장 등록 기한 = 접수 + `order.claim.invoice-due-days`(7)일의 끝. 스냅샷(35 설계서 0-3과 같은 이유) |
| `return_deduction` INT | 반품 배송비 차감액(1-4) — 고객 귀책 반품만, 아니면 0 |
| `reship_recipient` · `reship_phone` · `reship_zip_code` · `reship_address` · `reship_detail_address` · `reship_memo` | **재발송 수취지 스냅샷** — 교환 새 상품 · 반려 상품이 가는 곳. 기본은 원 주문 배송지의 사본이고, 교환은 요청 때 · 새 상품 출발 전에 바꿀 수 있다(3-6). 35 설계서 N7(「원 주문 배송지 고정」)을 대체한다 |
| `refund_amount` INT NULL · `finalized_at` DATETIME(6) NULL | 묶음 판정 종료 시 확정되는 환불액과 그 시각(1-4) |

회수 송장(`carrier` · `tracking_number` · `invoice_registered_at`)과 반품 수취 주소 스냅샷은 35 설계서 1-4 그대로다.

### 1-3. 잔여 수량 — **거절된 수량은 다시 신청할 수 없다**

C10-2 시안: 「반려된 상품은 반품 · 교환할 수 없어요」. 35 설계서 3-1은 거절 종결 수량이 잔여로 돌아온다고 했다 — 바꾼다.

```
신청 가능 수량 = quantity − returned_quantity − Σ(진행 중 클레임 수량) − Σ(거절된 클레임 수량 — rejected_at IS NOT NULL)
```

철회 · 자동 취소(`CANCELLED`)된 수량은 돌아온다 — 다시 요청할 수 있어야 한다.

**「진행 중 클레임 수량」에서 환불 대기(`REFUND_PENDING`)는 뺀다**(2026-10-05 구현 중 정정) — 반품 검수 통과 순간 `returned_quantity`가 이미 오르므로, 환불 집행 전의 통과 건을 진행 중으로도 세면 같은 수량이 두 번 빠진다(수량 2 중 1개가 통과되면 남은 1개를 신청할 수 없게 된다).

### 1-4. 금액 — `ClaimFeePolicy` · `ClaimRefundCalculator`

**요청 시점의 값(스냅샷)**

| 값 | 규칙(확정 — 2026-10-05 A안 · 9절 Q2) | 저장 |
| --- | --- | --- |
| 반품 배송비 차감 | 고객 귀책 반품이고 그 하위주문이 **무료배송으로 나갔으면**(`free_shipping_applied`) 그 하위주문의 `base_delivery_fee`, 아니면 0. 시안 문구 「무료배송으로 받은 주문을 단순 변심으로 반품하면 최초 배송비 3,000원이 차감돼요」 그대로다. 배송비를 내고 받은 주문은 그 배송비를 환불하지 않는 것으로 같은 효과가 난다 | `collection.return_deduction` |
| 교환 재발송 배송비 | 고객 귀책 교환 = 그 하위주문의 `base_delivery_fee`(편도), 브랜드 귀책 = 0 | `order_claim_charge(EXCHANGE_RESHIP)` |
| 반려 재발송 배송비 | 그 하위주문의 `base_delivery_fee` | `order_claim_charge(REJECT_RESHIP)` — 거절 시점 |
| 환불 예정액(표시) | `Σ(선택 항목 price × quantity) − return_deduction` | 저장하지 않는다 — 조회 때 계산 |

**금액의 기준 시점 = 주문 시점(2026-10-05 결정)** — 세 금액 모두 **마켓의 현재 설정이 아니라 주문할 때의 배송비**를 쓴다.

| 항목 | 내용 |
| --- | --- |
| 왜 | 기존 `order_delivery_group.delivery_fee`는 **실제 부과액**이라 무료배송 주문은 0이다 — 시안의 「최초 배송비」가 남지 않는다. 현재 설정을 읽으면 브랜드가 그사이 배송비를 바꿨을 때 차감액이 상품 상세·결제 화면에서 본 값과 달라진다 |
| 컬럼 | `order_delivery_group.base_delivery_fee` INT NOT NULL DEFAULT 0 — 「주문 시점 기본 배송비(무료배송이어도 원래 값)」. 유료배송 그룹은 `delivery_fee`와 같고, 무료배송 그룹만 다르다 |
| 기록 | `CheckoutService.createOrderTx`의 그룹 저장에서 `GroupShipping.deliveryFee()`(= `market.default_delivery_fee ?: 0` — 부과 전 값)를 함께 넣는다. 계산식은 그대로 — 이미 계산해 두고 버리던 값이다. 이후 불변(`ship_due_at`과 같은 스냅숏) |
| 백필 | 기존 그룹: `free_shipping_applied = 0`이면 `delivery_fee`(정확) · `1`이면 마켓의 현재 `default_delivery_fee`(추정 — 주문 당시 값이 없다) · 마켓 설정이 없으면 0. 지금 데이터는 테스트 결제뿐이라 추정이 문제되지 않는다 — **이 컬럼은 클레임보다 먼저 배포한다**(구현 계획서 S2) |
| 세 금액을 같은 값으로 | 재발송비는 지금 새로 보내는 운임이라 현재값이 맞아 보일 수 있다. 그러나 한 요청 안에서 「최초 배송비 3,000원 차감」과 「재발송 배송비 3,500원」이 섞이면 같은 편도 배송비를 두 값으로 안내하게 된다. 소비자가 주문 때 본 값 하나로 묶는다 |
| 배송비 설정이 없는 마켓 | 주문 때 배송비 0원이었으므로 세 금액 모두 0이다 — 소비자가 0원으로 안내받은 주문이다 |

**금액의 출처 = `default_delivery_fee`(2026-10-05 확정 · A안)** — 마켓 설정 `return_fee` · `exchange_fee`는 반품·교환 금액에 쓰지 않는다. 두 설정과 상품 상세의 표시는 1-8에서 정리한다.

**환불 확정 — 묶음 판정 종료(`finalize`)에서 한 번**

35 설계서는 반품 검수 통과마다 환불 큐에 1행을 세웠다. 차감이 요청 단위가 되면 「어느 항목에서 뺄지」가 판정 순서에 따라 달라지고, 일부 반려의 재발송비 차감(C10-5 「함께 반품한 상품의 환불액에서 재발송 배송비를 빼고 보내드려요」)은 **나머지 항목의 판정을 봐야** 정해진다. 그래서:

```
finalize(collection) — 그 요청의 모든 클레임이 검수 판정을 받은 순간(철회·취소된 것은 빼고 센다)
  passed   = Σ(통과한 반품 클레임의 price × quantity)
  rejected = 거절된 클레임이 있는가

  [반품]
  if passed > 0:
      refund = passed − return_deduction
      if rejected and refund ≥ 재발송비:        # 일부 반려
          refund −= 재발송비 · charge(REJECT_RESHIP) → DEDUCTED · 거절 클레임 REJECT_HOLD → RESHIP_READY
      collection.refund_amount = refund · order_refund_task(CLAIM_RETURN_PASSED, source_id = collection_id, refund) INSERT
  if rejected and charge 가 아직 PENDING:        # 전체 반려(또는 환불액이 재발송비보다 작다)
      결제 필요 — charge.due_at = now + order.claim.reship-pay-due-days(14)일

  [교환]
  if rejected:
      선결제(EXCHANGE_RESHIP = PAID)가 있으면 charge(REJECT_RESHIP) → COVERED · 거절 클레임 → RESHIP_READY
      없으면(브랜드 귀책 0원 요청) 결제 필요 — due_at 발급
```

- 통과한 클레임은 판정 순간 `REFUND_PENDING`으로 가고 `returned_quantity`도 그때 오른다(35 설계서 3-3 그대로) — **환불 큐 행만 종료 시점으로 늦는다.** 같은 박스는 같이 검수되므로 대개 같은 날이고, 검수 기한(2영업일)이 상한이다.
- `completeRefund`(운영자 집행)는 그 요청의 `REFUND_PENDING` 클레임을 **한꺼번에** `COMPLETED(REFUNDED)`로 닫는다.
- 브랜드 화면의 환불 예정액(35 설계서 4-3)은 「상품 금액 − 요청의 차감」을 요청 단위로 보여 준다 — 항목 상세에서는 상품 금액과 「같은 요청에서 N원 차감」을 따로 내린다.
- 거절 클레임이 결제 필요인지는 **종료 시점에야 정해진다.** 그 전(같은 박스의 다른 항목이 아직 검수 중)에는 결제 블록을 열지 않는다(4-2 `REJECTED_WAITING`).

### 1-8. 상품 상세의 반품·교환 배송비 표시 · 마켓 설정 `return_fee` · `exchange_fee` 정리 (A안 확정에 따라)

A안은 계산을 `default_delivery_fee` 하나로 묶는다. 그런데 소비자가 주문 전에 보는 값과 브랜드가 입력하는 값은 아직 옛 설정을 가리킨다 — 둘을 맞춘다.

**상품 상세(C7) — `ProductService.buildDeliveryInfo`**

| 필드 | 지금 | 바꾼 뒤 | 뜻 |
| --- | --- | --- | --- |
| `returnFee` | `market.return_fee`(기본 3,000) | `market.default_delivery_fee ?: 0` | 단순 변심 반품 때 부담하는 **최초 배송비**. 무료배송 주문은 환불에서 차감, 유료배송 주문은 낸 배송비를 돌려받지 않는다 |
| `exchangeFee` | `market.exchange_fee`(기본 6,000 — 왕복) | `market.default_delivery_fee ?: 0` | 단순 변심 교환의 **재발송비(편도)** — 신청할 때 결제 |

- 필드 이름과 타입은 그대로 둔다 — 앱이 이미 이 두 필드를 읽는다. 값과 Swagger 설명(`ProductDto.DeliveryInfo` · `UserProductControllerDocs` 예시 6000 → 3000)만 바꾼다.
- 브랜드 귀책(불량 · 오배송)은 둘 다 0원이다. 고객이 보내는 **반송 택배비는 별도**다(고객 귀책 = 선불로 택배사에 직접 · 브랜드 귀책 = 착불). 이 두 줄은 고정 문구라 FE가 쓴다.
- 상품 상세는 **현재 설정**을 보여 준다(주문 전이다). 주문하면 그 값이 `base_delivery_fee`로 고정되고(1-4), 그 뒤의 반품·교환은 고정된 값으로 계산한다.
- **시안 정정(C7 상품 상세)**: 「교환 · 반품」 행의 「문 앞 회수」 → 직접 발송(위 선불·착불). 「반송비」 행(「법무 확정 대기」) → 위 표의 두 금액 + 반송 택배비 별도 안내. 문구 확정은 기획·법무다(구현 계획서 G5).

**마켓 설정 `return_fee` · `exchange_fee`**

| 항목 | 처리 |
| --- | --- |
| 컬럼 | **남긴다** — `NOT NULL` · 기본값 3,000 / 6,000 그대로. 읽는 코드가 없어진다(상품 상세가 마지막 사용처였다). 삭제는 하지 않는다 — 기존 행·가입 API 호환 |
| 셀러 가입 — `SellerCompleteRegistrationRequest` | 두 필드가 지금 **필수**(`@NotNull`)라 브랜드가 쓰이지 않는 값을 입력하게 된다 → `@NotNull`을 뺀다. 생략하면 `SellerService`가 지금처럼 3,000 / 6,000을 넣는다. Swagger 설명(`SellerAuthControllerDocs` 「반품비 (기본값 3000), 교환비 (기본값 6000)」 · 예시)은 「사용하지 않음 — 반품·교환 금액은 기본 배송비 기준」으로 바꾼다 |
| 가입 화면 | 반품비 · 교환비 입력란을 뺀다(FE · 기획). 기본 배송비가 반품·교환 금액도 정한다는 안내를 기본 배송비 입력란에 둔다 |
| 기본정보 관리(`ui-partner-06`) | 「배송·반품 정책」 서브탭이 「준비중」이다(법률 검토 후 제작). 그 화면을 만들 때 **반품비 · 교환비 입력란을 두지 않는다** — 기본 배송비 하나로 정한다 |

- 기본 배송비는 가입에서 필수(`defaultDeliveryFee @NotNull`)라 신규 마켓은 항상 값이 있다. 「배송비 설정이 없는 마켓」(1-4)은 기존 행에만 있다.
- `SellerService`는 활성 코드다(기획 제외 아님). 가입 흐름이 쓰는 `MarketService`(기획 제외 패키지)는 건드리지 않는다.

| 1′ | (없음) → `REQUESTED` **또는 `COLLECTING`** | 소비자 | 요청 — 송장을 같이 냈으면 `COLLECTING`으로 시작 | 35 설계서 #1 |
| 13 | `REQUESTED` → `COMPLETED(CANCELLED · WITHDRAWN)` | 소비자 | 요청 철회 | `claim_id = ? AND status = 'REQUESTED' AND user_id = ?` |
| 14 | `REQUESTED` → `COMPLETED(CANCELLED · INVOICE_EXPIRED)` | 배치 | `invoice_due_at` 경과 | `collection_id = ? AND status = 'REQUESTED'` — **묶음 전체** |
| 7′ | `RECEIVED` → `REJECT_HOLD` | 브랜드 | 검수 거절 — **결제 필요 여부는 `finalize`가 정한다**(1-4) | 35 설계서 #7 |
| 8′ | `REJECT_HOLD` → `RESHIP_READY` | 시스템 | `finalize`의 차감(`DEDUCTED`) · 충당(`COVERED`) | `collection_id = ? AND status = 'REJECT_HOLD'` |

- **철회는 송장을 넣기 전까지만**이다(시안: 회수중이 되면 「이미 보냈으므로 철회 버튼이 사라진다」). 항목 단위라 한 요청의 두 항목 중 하나만 철회할 수 있다.
- 철회 · 자동 취소의 뒤처리: 교환이면 선점 재고 원복(35 설계서 3-8) · 그 요청에 남은 클레임이 없으면 `EXCHANGE_RESHIP` 결제를 **전액 취소**(`charge → REFUNDED`)한다. 시안 모달: 「결제한 재발송 배송비 3,000원은 결제 취소되고, 상품은 배송완료로 돌아가요」.
- #14가 닫는 순간 그 하위주문의 구매확정 보류가 풀린다 — 35 설계서 3-6의 `confirmIfDue`를 같은 트랜잭션에서 부른다(대개 7일이 이미 지났다).
- #13 · #14는 「보류 클레임」을 없애는 전이다. **기한 ①(파트너센터 「지연」 — 접수 + 2영업일)은 그대로 둔다** — 2영업일에 「지연」으로 보이고 7일에 자동 취소된다(9절 Q4).

## 3. API — 요청 · 변경 (`/v1/user/claims`)

패키지 `showroomz.api.app.claim.{controller, docs, dto, service}`. 컨트롤러는 `UserClaimControllerDocs`를 implements(프로젝트 규약). 인증은 앱 사용자 토큰 · **남의 클레임은 404 `CLAIM_NOT_FOUND`**(존재 비노출 — 35 설계서 4-4와 같다).

| # | 메서드 | 경로 | 화면 |
| --- | --- | --- | --- |
| 1 | GET | `/form` | C10-3 진입 — 폼 데이터 |
| 2 | POST | `` | C10-3 [요청하기] |
| 3 | POST | `/payments/{paymentId}/complete` | 결제창 복귀(교환 선결제 · 반려 재발송비 공용) |
| 4 | PUT | `/{claimId}/collection-invoice` | C10-5 회수 송장 등록 · C10-4 [송장 수정] |
| 5 | POST | `/{claimId}/withdraw` | C10-5 [요청 철회] |

| 7 | POST | `/{claimId}/reship-fee/payments` | C10-5 [3,000원 결제하고 다시 받기] |

조회(상세 · 회수 조회 · 배송 조회)는 4 · 5절.

### 3-1. 폼 데이터 — `GET /form?orderProductId=&type=RETURN|EXCHANGE`

진입 항목이 든 **하위주문의 신청 가능 항목 전부**를 돌려준다(시안: 진입 항목이 체크된 채 같은 브랜드 항목이 함께 나온다).

```
type · deliveryGroupId · brandName
items[]: { orderProductId, productName, optionName, thumbnailUrl, unitPrice, claimableQuantity, preselected,
           exchangeOptions[]: { variantId, optionName, soldOut, current } }      ← 교환만
reasons[]: { code, label, hint, feeBearer(CONSUMER|SELLER), detailRequired, photoAllowed }
carriers[]: { code, label }
returnTo: { name, contact, address, detailAddress }            ← 브랜드 반품 수취 주소(원문)
reshipTo: { recipientName, phone, zipCode, address, detailAddress, memo }   ← 교환만 · 원 주문 배송지(원문)
fees: { consumerFault: { returnDeduction | reshipFee }, sellerFault: 0 }
courierPayment: { CONSUMER: "PREPAID", SELLER: "COLLECT" }      ← 택배비 안내 「선불로 / 착불로 보내주세요」
refundMethodLabel("신한카드 결제 취소") · invoiceDueDays(7) · detailMaxLength(250) · photoMax(10)
```

- **신청 가능 항목** = 그룹이 `DELIVERED`이고 1-3의 신청 가능 수량 ≥ 1. 진입 항목이 신청 불가면 409 `CLAIM_NOT_ELIGIBLE`.
- **수량은 받지 않는다** — 시안에 수량 선택이 없다(「2개 묶음 · 1개」 행을 체크만 한다). 요청은 그 항목의 신청 가능 수량 **전량**으로 접수한다. 도메인은 수량을 받으므로 화면이 생기면 요청 DTO에 필드만 더한다(9절 Q6).
- **사유** — `ClaimReason` 중 `consumerSelectable`인 것. 지금은 4종(`SIZE_MISMATCH` 제외)이고 `hint`가 괄호 설명이다(「상품이 필요 없어짐」 — 교환이면 「다른 옵션이 더 마음에 들어요」처럼 유형별로 다르다). 브랜드 화면에는 `label`만 간다(§35-3 「괄호 설명은 옮기지 않는다」).
- **교환 옵션** — 같은 상품 · 같은 공구의 옵션 중 **공구가가 받은 옵션과 같은 것**만(시안 「같은 가격 옵션만 노출 가정」 — 9절 Q7). 품절은 빼지 않고 `soldOut`으로 내린다(시안: 회색 + 「품절」). `current`(받은 옵션)도 목록에 든다 — 불량·오배송은 같은 옵션으로 다시 받는다.
- **`fees`** — 1-4의 값. 사유를 고르는 순간 앱이 `feeBearer`로 갈라 쓴다. 신청 시 서버가 다시 계산해 검증한다(3-2).
- `refundMethodLabel` = 그 주문의 결제 수단 라벨 + 「 결제 취소」.

### 3-2. 신청 — `POST /v1/user/claims`

```json
{
  "idempotencyKey": "…",
  "type": "EXCHANGE",
  "deliveryGroupId": 911,
  "items": [ { "orderProductId": 1501, "exchangeVariantId": 302 } ],
  "reasonCode": "ORDER_MISTAKE",
  "reasonDetail": null,
  "imageUrls": [],
  "invoice": { "carrier": "CJ", "trackingNumber": "684922013378" },
  "reshipAddressId": 55,
  "expectedFee": 3000,
  "payment": { "method": "EASY_PAY", "easyPayProvider": "KAKAOPAY" }
}
```

| 검증 | 실패 | 시안의 CTA 문구 |
| --- | --- | --- |
| `items` 1개 이상 · 전부 그 하위주문의 내 항목 | 400 · 404 | 「반품할 상품을 선택해 주세요」 |
| 하위주문 `DELIVERED` · 신청 가능 수량 ≥ 1 | 409 `CLAIM_NOT_ELIGIBLE` · `CLAIM_QUANTITY_EXCEEDED` | — |
| 교환: 항목마다 `exchangeVariantId` · 같은 상품 · 같은 가격 | 400 `CLAIM_EXCHANGE_OPTION_INVALID` | 「교환할 옵션을 선택해 주세요」 |
| 교환: **고객 귀책인데 받은 옵션과 같은 옵션** | 400 `CLAIM_EXCHANGE_SAME_OPTION` | 「같은 옵션은 불량 · 오배송일 때만 교환돼요」 |
| 교환 옵션 재고(선점 — 35 설계서 3-8) | 409 `CLAIM_EXCHANGE_OUT_OF_STOCK` | — |
| 사유 선택 가능(`consumerSelectable`) · `detailRequired`면 내용 1~250자 | 400 `CLAIM_REASON_DETAIL_REQUIRED` | 「상세 내용을 입력해 주세요」 |
| 사진 0~10장 | 400 | — |
| `invoice`가 있으면 택배사(`consumerSelectable`) · 형식 | 400 `INVOICE_FORMAT_INVALID` | 「택배사를 선택해 주세요」 등 |
| `expectedFee` = 서버 계산값 | 409 `CLAIM_AMOUNT_CHANGED` | — (금액이 주문 시점 스냅숏이라 브랜드 설정 변경으로는 나지 않는다 — 앱이 귀책을 잘못 가르거나 오래된 폼을 쓴 경우의 방어. 폼을 다시 받는다) |
| 결제가 필요한데 `payment` 없음 | 400 | 「결제 수단을 선택해 주세요」 |

- `invoice = null`이 **「나중에 입력하기」**다. 접수는 되고 `invoice_due_at`까지 4번으로 넣는다.
- 사진은 기존 이미지 업로드 API(`api/app/image`)가 준 URL만 받는다. 사진은 **브랜드 귀책 사유에서만** 받는다(시안: 상세 내용 · 사진 블록이 그때만 열린다) — 고객 귀책 사유에 `imageUrls`가 오면 무시한다.
- 한 트랜잭션에서: 하위주문 · 항목 잠금(35 설계서 3-1) → 그 사용자의 같은 하위주문 `PAYMENT_PENDING` 초안 삭제(전이 0b — 결제 실패 뒤 내용을 고쳐 다시 요청하는 경우 묶인 수량을 푼다) → collection + 항목마다 claim → 첨부 → (교환) 재고 선점 → (결제 필요) charge + payment 행.
- 같은 `idempotencyKey`의 재요청은 **만들지 않고 기존 요청을 돌려준다.** 그 요청이 `PAYMENT_PENDING`이면 결제 시도만 새로 만든다(수단을 바꿔 재시도).

응답

```
{ requestId(collection_id), claimIds[], status(REQUESTED|COLLECTING|PAYMENT_PENDING),
  payment: { paymentId, amount, orderName, … } | null }      ← 포트원 결제창 파라미터(주문 결제와 같은 모양)
```

- `payment = null`이면 접수 완료 — 앱은 `GET /{claimId}`(4-1)로 접수 화면을 그린다(접수 화면과 상세가 같은 데이터다).
- `payment`가 있으면 결제창 → 3번 `complete` → 응답의 `status`가 `REQUESTED`/`COLLECTING`이면 접수 화면, `PAYMENT_PENDING` 그대로면(취소·실패) 요청 화면으로 돌아가 토스트(「결제가 완료되지 않았어요. 입력한 내용은 그대로예요」 — 앱 문구).

### 3-3. 결제 완료 — `POST /payments/{paymentId}/complete`

`ClaimPaymentConfirmService.confirm`(1-5). 멱등이다 — 둘째 호출은 현재 상태를 돌려준다. 응답 `{ paymentStatus, requestId, claimIds[], claimStatus }`.

포트원 웹훅은 기존 수신부가 `payment_id` 접두(`clm-`)로 이쪽에 넘긴다 — 수신 컨트롤러를 따로 만들지 않는다.

### 3-4. 회수 송장 등록 · 수정 — `PUT /{claimId}/collection-invoice`

`{ carrier, trackingNumber }` — 요청(박스) 단위로 적용된다.

| 현재 | 동작 | 조건 |
| --- | --- | --- |
| `REQUESTED`(미등록) | **등록** — 35 설계서 `registerCollectionInvoice` · 전이 #2(묶음 전체 → `COLLECTING`) | `now ≤ invoice_due_at`(지났으면 #14가 이미 닫았다 → 409 `CLAIM_STATE_CHANGED`) |
| `COLLECTING` | **수정** — `updateCollectionInvoice` · 추적 값 초기화 | **아직 추적 이력이 없고**(1-6에 그 송장의 이벤트 0건) `now ≤ invoice_due_at` — 아니면 409 `CLAIM_INVOICE_NOT_EDITABLE` |

- 수정을 「이력이 없을 때」로 좁히는 이유 — 시안이 [송장 수정]을 **조회되지 않음(C10-4 1b)** 에만 둔다. 택배사가 이미 스캔한 송장은 맞는 송장이다. 「수정 기한은 등록 기한(7일)과 같다」(시안).
- 형식 검증은 추적 설계서 3-3 그대로다 — **기본값이 꺼져 있어** 오타 송장도 통과한다. 그 결과가 C10-4 1b(「아직 조회되지 않아요 · 송장 번호 숫자가 빠졌거나…」)이고 그 화면이 안전망이다.
- 수정 기한까지 넘긴 오타 송장은 소비자가 고칠 길이 없다 — 물건이 실제로 도착하면 브랜드가 입고 확인으로 받고(35 설계서 0-7 `receive-before-arrival`), 아니면 1:1 문의 → 운영자 직권이다(9절 Q4).

### 3-5. 철회 — `POST /{claimId}/withdraw`

전이 #13. 본문 없음. 응답은 갱신된 상세(4-1)가 아니라 `{ claimId, status: COMPLETED, result: CANCELLED }` — 앱은 주문 상세로 돌아간다(항목이 배송완료로 복귀).

### 3-6. 교환받을 배송지 변경 — `PATCH /{claimId}/reship-address`

`{ addressId }` — 내 배송지(`delivery_address`)의 값을 `collection.reship_*`에 **복사**한다(스냅샷 — 이후 배송지를 고쳐도 요청은 그대로).

- 조건: 교환이고 그 요청의 진행 중 클레임이 전부 `REQUESTED` · `COLLECTING` · `ARRIVED` · `RECEIVED`. 하나라도 검수를 통과해 `RESHIP_READY`가 됐으면 409 `CLAIM_ADDRESS_NOT_CHANGEABLE` — **브랜드가 재발송 목록을 내려받을 수 있는 시점부터 잠근다.** 시안은 「새 상품이 출발하기 전까지」인데, 출고 작업 중에 주소가 바뀌면 구 주소로 나간다(9절 Q8).
- C13-2 「배송지 선택」 화면 자체는 기존 `GET /v1/user/delivery-addresses`를 쓴다 — 서버가 새로 만들 것이 없다. 선택 화면에서 [새 배송지 추가]도 기존 `POST`다.
- 요청 화면(C10-3)에서의 변경은 이 API가 아니다 — 아직 요청이 없으므로 앱이 `reshipAddressId`를 들고 있다가 신청(3-2)에 싣는다.
- 반품의 반려 상품 재발송지는 바꾸지 못한다(시안에 없다 — 원 주문 배송지 사본).

### 3-7. 반려 후 재발송 배송비 결제 — `POST /{claimId}/reship-fee/payments`

`{ method, cardIssuer?, easyPayProvider?, expectedAmount }` → `order_claim_payment` 행을 만들고 결제창 파라미터를 돌려준다. 결제 뒤는 3번이다.

- 조건: 그 요청의 `REJECT_RESHIP` charge가 `PENDING`이고 **`finalize`가 끝났다**(1-4). 아니면 409 `CLAIM_PAYMENT_NOT_REQUIRED`.
- **기한(`due_at`)이 지나도 받는다** — 지난 뒤에는 고지가 나가고 보관 기한이 흐를 뿐, 폐기 기록 전이면 결제가 곧 「반환 요청」이다(35 설계서 2절).
- 결제되면 그 요청의 `REJECT_HOLD` 클레임이 전부 `RESHIP_READY`로 가고 브랜드의 재발송 탭에 「거절 반송」으로 뜬다.

### 3-8. 에러 코드(신규)

`CLAIM_REASON_DETAIL_REQUIRED` · `CLAIM_EXCHANGE_SAME_OPTION` · `CLAIM_AMOUNT_CHANGED`(409) · `CLAIM_INVOICE_NOT_EDITABLE`(409) · `CLAIM_WITHDRAW_NOT_ALLOWED`(409 — 이미 회수중) · `CLAIM_ADDRESS_NOT_CHANGEABLE`(409) · `CLAIM_PAYMENT_NOT_REQUIRED`(409).

재사용: 35 설계서 4-4의 `CLAIM_NOT_FOUND` · `CLAIM_STATE_CHANGED` · `CLAIM_NOT_ELIGIBLE` · `CLAIM_QUANTITY_EXCEEDED` · `CLAIM_EXCHANGE_OPTION_INVALID` · `CLAIM_EXCHANGE_OUT_OF_STOCK` · `INVOICE_FORMAT_INVALID` · 결제의 `PAYMENT_NOT_FOUND` · `PAYMENT_GATEWAY_ERROR`.

## 4. 반품 · 교환 상세 — `GET /v1/user/claims/{claimId}` (C10-5 · 접수 화면)

### 4-1. 응답

```
requestId · type · requestedAt · completedAt(nullable) · orderId · orderNumber
guide: { visible, courierPayment(PREPAID|COLLECT) }                 ← 「유의해 주세요」 박스
items[]: {
  claimId, focused(진입한 claimId), brandName, productName, optionName, exchangeOptionName(교환), quantity,
  amount, thumbnailUrl,
  phase, statusLabel, statusSub, statusSubTone(ACTIVE|MUTED),
  actions: [ { type, label } ],
  rejection: { reasonLabel, legalNote, sellerMessage, evidenceImageUrls[], rejectedAt } | null
}
info: {
  reasonLabel, methodLabel("고객 직접 발송"),
  collectionInvoice: { carrier, carrierLabel, trackingNumber } | null, invoiceDueDate(미등록일 때),
  reshipInvoice: { carrierLabel, trackingNumber } | null,
  pickupFrom(마스킹 — 반품만 「반품 수거지」), returnTo(원문 — 「반품/교환 도착지」),
  reshipTo(마스킹 — 교환 「교환받을 배송지」), reshipAddressChangeable
}
refund(반품): { paidAmount, returnDeduction, approvedAmount(일부 반려), reshipDeduction(일부 반려),
               amount, confirmed(예정/확정), refundMethodLabel }
exchangePayment(교환): { reshipFee, paidAmount, methodLabel("신한카드" | "결제 없음") }
reshipFee: { state(PAYABLE|WAITING|PAID|DEDUCTED|COVERED), amount, dueDate, paidAt, methodLabel,
             storage: { noticeCount, storageDueAt, phase } | null } | null      ← 반려가 있을 때
```

| 시안 요소 | 필드 |
| --- | --- |
| 26.10.04(일) 13:31 · 주문번호 · [주문 상세] | `requestedAt` · `orderNumber` · `orderId` |
| 반품 상품 N개 | `items.size()` — **요청의 클레임 전부**(철회·취소된 것은 뺀다). 일부 반려 화면이 반려 1 + 승인 1을 같이 그린다 |
| 유의 박스 | `guide.visible` — 그 요청에 `REQUESTED`·`COLLECTING` 클레임이 있을 때. 문구는 앱(선불/착불만 값으로 갈린다) |
| 상품 위 상태 줄 · 상품 아래 버튼 | `items[].statusLabel` · `statusSub` · `actions`(4-2) |
| 반려 사유 블록 | `items[].rejection` — 사유 · 법적 근거 한 줄 · 브랜드 증빙 사진 · 「○○의 메시지」 |
| 상품 다시 받기 | `reshipFee`(4-3) |
| 신청 정보 | `info` — 「완료 일시」는 `completedAt`, 없으면 앱이 「검수 후 표시돼요」 |
| 회수 송장 「미등록 · 10.11(일)까지 등록해 주세요」 | `collectionInvoice = null` + `invoiceDueDate` |
| 환불 정보 / 결제 정보 | `refund` / `exchangePayment` |

- `rejection.reasonLabel`은 `ClaimRejectReason` 라벨, `sellerMessage`는 `reject_detail`(약관 제20조③ 「그대로 전달」), 사진은 `order_claim_attachment(owner = SELLER)`. `legalNote`(「전자상거래법상 청약철회 제한 사유에 해당해요」)는 거절 사유 enum이 드는 고정 문구다 — 사유별 문구는 법무 확정 대기(9절 Q11).
- `refund.confirmed` — 운영자 집행 전에는 예정액(1-4의 계산), 집행 뒤에는 `refunded_amount`. 라벨 「환불 예정 금액」 ↔ 「환불 금액」은 앱이 이 값으로 가른다. 전체 반려는 `amount = 0`.
- `refund`의 일부 반려 줄: `paidAmount`(반려 상품 금액 — 환불 제외 · 앱이 취소선) · `returnDeduction` · `approvedAmount` · `reshipDeduction` · `amount`.
- 시안 하단 「주문 시 사용한 쿠폰·적립금은 반품 완료 즉시 돌려드려요」는 **내리지 않는다** — 쿠폰은 기획 제외 범위이고 적립금 기능이 없다(9절 Q12).
- `CANCELLED`로 끝난 요청도 열린다(알림 딥링크 · `statusLabel = 요청 취소`) — 주문 내역에는 진입점이 없다.

### 4-2. 소비자 표시 단계 — `UserClaimPhase` · `UserClaimPresenter`

저장 상태(35 설계서 1-2) + 유형 + charge 상태에서 유도한다. **C10 · C10-1의 항목 행도 이 표를 쓴다**(C10 설계서 1-2가 이 표를 참조한다 — 「목록 보조」 열).

- **로즈는 고객이 해야 할 일이 있을 때만**이다(시안) — `REQUESTED` · `REJECTED_PAY` 둘. 이 둘에만 `todo`가 붙고, 기한이 지나도 `REJECTED_PAY`의 `todo`는 남는다(날짜 없이 「재발송 배송비 결제 필요」).
- 시안에 없는 줄(`INSPECTING` · `APPROVED` · `RESHIP_PREPARING` · `REJECTED_WAITING` · `REJECTED_DISPOSED`)의 문구는 잠정이다(9절 Q13). 시안은 「회수중 → 반품 완료」로 건너뛰지만 그 사이에 검수와 환불 집행이 실재한다.
- 버튼 타입: `WITHDRAW` · `REGISTER_COLLECTION_INVOICE` · `TRACK_COLLECTION`(C10-4) · `TRACK_RESHIP`(C10-2) · `INQUIRY`(C12 — 문의 생성에 `orderId`를 넘긴다 · 기존 API). `PAY_RESHIP_FEE`는 항목 버튼이 아니라 하단 고정 CTA라 `reshipFee.state = PAYABLE`로 그린다.

### 4-3. 「상품 다시 받기」 — `reshipFee`

| `state` | 조건 | 시안 |
| --- | --- | --- |
| `PAYABLE` | `REJECT_RESHIP` charge `PENDING` · `finalize` 완료 | 결제 수단 블록 + CTA 「3,000원 결제하고 다시 받기」 · 「10.23(금)까지 결제해 주세요」(`dueDate`) |
| `WAITING` | 거절은 났는데 `finalize` 전 | 블록 없음 — 4-2 `REJECTED_WAITING` |
| `DEDUCTED` | 환불액에서 차감 | 「함께 반품한 상품의 환불액에서 재발송 배송비 3,000원을 빼고 보내드려요」 |
| `COVERED` | 교환 선결제분으로 충당 | 「요청 때 결제한 배송비로 다시 보내드려요 · 추가 결제는 없어요」 |
| `PAID` | PG 결제 완료 | 「재발송 배송비 3,000원 · 카카오페이 결제 완료 (10.10)」 |

- `PAYABLE`이고 `dueDate`가 지났으면 `storage`를 함께 내린다 — 35 설계서 1-9의 `ClaimStoragePolicy` 값(고지 횟수 · 보관 기한 · 단계). 시안 문구 「2회 이상 다시 안내드리고, 마지막 안내일로부터 3개월 동안 상품을 보관해요」의 실제 날짜가 이것이다(§35-9 C-13 「미결제 고지 수신 · 보관 기한 안내」).
- **결제 기한(14일)과 보관 기한(최종 고지 + 3개월)은 다른 날짜다.** 결제 기한은 「이 날까지 내면 아무 일도 없다」이고, 지나면 고지가 시작된다(1-5 `due_at`).

## 5. 배송 조회 · 회수 조회

### 5-1. 엔드포인트

| 메서드 | 경로 | 화면 | 추적 대상 |
| --- | --- | --- | --- |
| GET | `/v1/user/orders/{orderId}/items/{orderProductId}/tracking` | C10-2 | 그 항목이 든 하위주문의 송장 |
| GET | `/v1/user/claims/{claimId}/reship-tracking` | C10-2 | 재발송 송장 — 교환 새 상품 · 반려 상품 |
| GET | `/v1/user/claims/{claimId}/collection-tracking` | C10-4 | 회수 송장 + 브랜드 검수 단계 |

송장이 키인 화면이지만 **경로는 소유자(주문 항목 · 클레임)로 연다** — 송장 번호만으로 조회하게 두면 남의 배송 이력이 열린다.

### 5-2. C10-2 배송 조회 응답

```
state(DELIVERED|IN_TRANSIT|NOT_SHIPPED) · context(ORDER|EXCHANGE_RESHIP|REJECT_RESHIP) · contextLabel · contextNote
headline: { date, text, sub }
stageIndex(-1 ~ 2)                     ← 3구간 바: 배송 시작 · 배송중 · 배송 완료
orderedAt · orderId
item: { brandName, productName, optionName, quantity, amount, thumbnailUrl }
carrier: { code, label, tel, trackingUrl } | null · trackingNumber | null
scans[]: { location, description, occurredAt }      ← 최신순 전체
shipDueAt · groupBuyEndAt              ← NOT_SHIPPED 일 때만
```

| `state` | 조건 | `headline` | `stageIndex` |
| --- | --- | --- | --- |
| `NOT_SHIPPED` | 송장 없음(`NEW` · `PREPARING`) | 「배송 준비 중이에요」 · sub = 발송 안내 | −1(전부 빈 칸) |
| `IN_TRANSIT` | 송장 있음 · 미완료 | `date` = 도착 예정일(없으면 null) · 「도착 예정이에요」 / 「상품이 배송중이에요」 · sub = 최종 위치·시각 | 이력 0건 = 0, 있으면 1 |
| `DELIVERED` | `delivered_at` 존재 | `date` = 배송완료일 · 「상품 배송이 완료되었어요」 | 2 |

- **도착 예정일**은 C10 설계서 1-2의 `DeliveryArrivalEstimator`를 그대로 쓴다 — 주문 내역의 「09.17 도착 예정」과 같은 날짜여야 한다. 재발송 송장은 집화 시각을 1-6의 첫 이벤트에서 읽는다.
- **이력은 전부 내리고 앱이 접는다**(최근 4건 + 「이력 전체 보기 (N건)」) — 페이지가 필요한 양이 아니다.
- `context`가 재발송이면 `contextLabel`(「교환 상품 발송」 / 「반려 상품 재발송」)과 `contextNote`(「교환한 새 상품이에요. 배송이 완료되면 교환이 끝나요.」 / 「검수에서 반려되어 다시 보내드린 상품이에요. 반려된 상품은 반품 · 교환할 수 없어요.」)를 서버가 내린다. 재발송의 `item`은 **실제로 가는 물건**이다 — 교환이면 새 옵션, 반려면 원래 옵션(35 설계서 3-4 「보낼 상품·옵션」과 같은 규칙).
- `NOT_SHIPPED`의 `shipDueAt`은 `order_delivery_group.ship_due_at`, `groupBuyEndAt`은 그 공구의 종료 시각. 문구 「공동구매는 마감 후 일괄 발송돼요」는 발송 방식 미결(34 설계서 7절 #3)에 걸려 있어 앱 고정 문구로 둔다.
- FAQ 4건은 앱 고정이다(시안 남은 결정 ③ — C16 고객센터와 동기화되면 그쪽 API).
- 택배 연동이 꺼져 있으면(`delivery.tracker.enabled = false`) 이력이 영영 0건이다 — 화면은 서지만 비어 있다. **연동 활성화가 이 화면의 런칭 게이트다**(35 설계서 0-7과 같은 처지).

### 5-3. C10-4 회수 조회 응답

```
type · trackable · stageIndex(-1 ~ 4) · stages[5]: ["접수","이동 중","도착","검수","환불"|"새 상품"]
headline: { date, text, sub }
requestedAt · claimId
item: { brandName, productName, optionLabel("30ml + 리필 2개 → 30ml + 리필 1개") , thumbnailUrl }
carrier: { code, label, tel, trackingUrl } · trackingNumber · invoiceRegisteredAt
sender(마스킹 — "김수* · 서울 강남구") · receiver("{브랜드} 반품센터")
events[]: { source(COURIER|BRAND), description, occurredAt }     ← 최신순 · 택배 이력 + 브랜드 이력을 시각순으로 섞는다
invoiceEditable
```

| `stageIndex` | 조건 | `headline` |
| --- | --- | --- |
| −1 | 송장은 등록됐는데 택배 이력 0건 | `trackable = false` · 「아직 조회되지 않아요」(1b) |
| 0 접수 | 이력 있음 · 최고 단계가 집화까지 | 「접수되었어요」 |
| 1 이동 중 | 배송중 단계 | `date` = 도착 예정일 · 「도착 예정이에요」 |
| 2 도착 | `ARRIVED`(추적상 브랜드 도착 · 입고 확인 전) | 「브랜드에 도착했어요」 |
| 3 검수 | `RECEIVED` | `date` = 입고 확인일 · 「도착해서 검수 중이에요」 |
| 4 완료 | 검수 통과 이후 | `date` = 판정일 · 「검수가 끝나 환불이 진행돼요」 / 「…새 상품이 출발했어요」 |

- 검수 **거절**이면 `stageIndex = 3`에서 멈추고 `headline` = 「검수에서 반려되었어요」 · sub = 「반품 상세에서 사유를 확인해 주세요」 — 시안에 없는 경우다(9절 Q13). 5번째 칸(환불/새 상품)을 채우면 거짓이 된다.
- **브랜드 이력**(`source = BRAND` — 시안의 회색 [브랜드] 표시)은 `order_claim_history`의 `RECEIVED`(「입고 · 검수 시작」) · `INSPECTION_PASSED`(「검수 완료 · 환불 진행」 / 「검수 완료 · 새 상품 출발」) · `INSPECTION_REJECTED`(「검수 완료 · 반려」)다. 택배 이력은 1-6.
- 요청에 항목이 여럿이어도 화면의 `item`은 진입한 클레임 하나다 — 택배 구간은 박스 공통, 검수 구간은 그 항목의 것이다.
- `invoiceEditable` = 3-4의 수정 조건. `true`면 [송장 수정]이 C10-5의 등록 화면을 값이 채워진 채 다시 연다(`carrier` · `trackingNumber`가 이 응답에 있다).
- 1b의 「등록 일시」 = `invoiceRegisteredAt`. 원인 3가지 박스는 앱 고정 문구.
- `sender`는 원 주문 배송지에서 이름(마스킹)과 시·구까지만 만든다 — 실제 발송지가 아니라 「누가 보냈는지」의 표기다.
