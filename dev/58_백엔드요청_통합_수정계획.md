## 2. 운영 지표 장애(1-1)

### 2-1. 코드에서 찾은 위험 요소

원인은 아직 확정하지 못했다. 코드를 읽어서 찾은 위험 요소는 다음 다섯 개다.

1. **요청 하나가 무겁다.** `AdminMetricsQueryService.getMetrics` · `getTabs`(:65-92)는 각각 `Facts`를 두 번(현재 · 비교 기간) 계산한다. `MetricsFactsCalculator.compute`는 쿼리 30여 개를 **하나의 읽기 트랜잭션** 안에서 돌리고, 계산이 끝날 때까지 커넥션 하나를 잡고 있다.
2. **같은 계산이 동시에 여러 번 돈다.** 캐시는 10분이지만 single-flight가 아니다(`facts()` :106-116). 화면은 `/metrics`와 `/metrics/tabs`를 같이 부른다. 캐시가 비어 있을 때는 같은 기간을 동시에 2번 이상 계산하고, 재시도나 탭 전환이 겹치면 계산이 계속 쌓인다.
3. **쿼리 범위가 기간과 무관하다.** `openedGroupBuys()`와 `concludedContracts(to)`(`MetricsQueryRepository:140-158`)는 기간과 상관없이 전부 읽는다. 재공구 판정(`supply()` :109-116)은 「기간 중 종료된 공구 × 전체 공구」 이중 루프다.
4. **기간 열에 인덱스가 없다.** `orders.paid_at` · `order_claim.requested_at` · `one_to_one_inquiry.answered_at` · `group_buy_post.reviewed_at` · `users.created_at` · `order_refund_task.failed_at` · `settlement_adjustment.opened_at` · `group_buy.opened_at`에 이 열로 시작하는 인덱스가 없다.
5. **시간 제한이 하나도 없다.** 쿼리 타임아웃 · JDBC `socketTimeout` · Hikari 설정이 없다(`application*.yml`). Hikari 풀은 기본값 10개다. 서버 자원도 작다(`docker-compose.yml`): 앱 힙 256MB(:49), MySQL 컨테이너 350MB · 버퍼 풀 128MB(:18 · :24).

**추정되는 경로**
- 지표 계산이 커넥션을 오래 잡는다. 2번 때문에 그 수가 늘어난다.
- 풀이 바닥나서 다른 API가 커넥션을 기다린다. 「26 ~ 90초」는 Hikari 기본 대기 30초 + 재시도와 맞는다.
- 여기에 MySQL 메모리 한도와 `socketTimeout` 0(무한 대기)이 겹치면, 스레드가 응답 없는 소켓에서 끝없이 기다리다가 전체가 응답하지 않게 된다. 4시간 뒤 수동으로 재시작될 때까지 풀리지 않은 것과 맞는다.

**이 추정은 재현으로 확인한다.**

## 3. 시간대(1-2 ~ 1-7)

### 3-1. 지금 상태

- 운영 JVM은 UTC다(컨테이너 기본값 · `TimeZone.setDefault` 없음). DB 컨테이너도 `TZ: UTC`다. `LocalDateTime.now()`는 UTC 벽시계이고, 그대로 저장된다.
- `JacksonConfig`(:15)는 모든 `LocalDateTime`에 `Z`를 붙인다. **이벤트 시각은 이 방식이 맞다.**
- 틀린 곳은 세 종류다.
  - **KST 날짜로 만든 기한.** `now.toLocalDate()`(UTC 날짜)에 `atTime(23:59:59)`를 붙인다. 날짜와 시각이 둘 다 9시간씩 어긋난다. 예: 10-27(화) 통지 → `2026-10-30T23:59:59Z` → 화면 「10.31까지」. 맞는 값은 `2026-10-30T14:59:59Z`다.
  - **「오늘」 경계.** `now.toLocalDate().atStartOfDay()`가 KST 09:00이다.
  - **`Z` 없는 개별 패턴.** `OrderDto.TIME_PATTERN` 등은 UTC 값을 시간대 표시 없이 내린다. FE가 이를 KST로 읽어서 날짜가 하루 앞당겨진다.
- **로컬 테스트는 JVM이 KST라서 이 버그가 테스트에서 드러나지 않는다.** `build.gradle`의 test 태스크에 시간대 설정이 없다. 개발자 PC 시간대(KST)로 돈다.

### 3-2. 규약 — 이렇게 정한다(D1)

| 구분 | 규칙 |
| --- | --- |
| 저장 · 비교 | `LocalDateTime` = UTC 벽시계. **지금 그대로 둔다**(데이터 이행이 필요 없다). |
| 응답 | 전부 `…Z`. `Z` 없는 개별 `@JsonFormat` 패턴을 없앤다(3-4). |
| 입력 | `…Z` · `+09:00` 같은 오프셋은 UTC로 환산해서 받는다. 오프셋이 없는 값은 UTC로 본다(지금 저장 동작과 같다). |
| 날짜(`LocalDate`) | KST 날짜다. 입력(`endsOn` · `defectNoticedOn` · 목록 기간 `from/to`)도 KST 날짜다. |
| KST 의미 계산 | `KstDates` 하나로만 한다 — 「오늘」 · 「그날 0시」 · 「그날 23:59:59」 · 「그날 HH:mm」을 UTC 벽시계로 바꾼다. |

FE 요청서가 권장한 방식(「기한을 KST로 계산한 뒤 UTC 순간으로 바꿔 저장 · 비교 · 응답」)과 같다.

### 3-3. 헬퍼와 교체 대상(1-2 · 1-3 · 1-4 · 1-5 · 1-7)

`global/utils/KstDates`에 메서드를 더한다. 서버 시간대는 지금처럼 `ZoneId.systemDefault()`로 해석한다. 그래서 로컬(KST)과 운영(UTC)이 같은 순간을 만든다.

```java
public static LocalDate today(LocalDateTime serverNow)              // = toKstDate(serverNow)
public static LocalDateTime startOfDay(LocalDate kstDate)            // KST 00:00 → 서버 시각
public static LocalDateTime endOfDay(LocalDate kstDate)              // KST 23:59:59 → 서버 시각
public static LocalDateTime at(LocalDate kstDate, LocalTime kstTime) // KST HH:mm → 서버 시각
```

### 3-5. 입력 규약(1-6 ② ③)

- `JacksonConfig`에 `LocalDateTime` 역직렬화기를 더한다. `Z`나 오프셋이 있으면 UTC로 환산하고, 없으면 그대로 받는다. Jackson 기본 역직렬화기는 끝의 `Z`를 떼고 읽지만 `+09:00`은 거부한다.
- Swagger에서 시각 필드를 「(Asia/Seoul)」이라고 적은 설명을 「UTC(…Z)」로 고친다: `CartDto:193` · `OrderDto:337` · `ContractDetailResponse:126-127` · `ContractDocumentDownloadResponse:24` · `ContractUpdateRequest:44-45`. 「일수는 서버 now(Asia/Seoul) 기준」 같은 **일수 계산 설명은 맞으므로 그대로 둔다**(`GroupBuyDetailResponse:92` · `CreatorGroupBuyDetailResponse:88`).
- **공구 일정(D3)**: 계약 `groupBuyStartAt/EndAt`은 문서상 KST 입력이다. 그런데 `GroupBuyLifecycleScheduler`는 이 값을 UTC `now()`와 비교한다. FE가 문서대로 KST 벽시계를 보냈다면 공구가 9시간 늦게 열리고 닫힌다. 개발 DB에서 `group_buy.start_at · end_at`(그리고 계약 쪽 값)이 KST 벽시계로 저장됐는지 먼저 본다. 예를 들어 종료 시각이 `23:59:00`으로 끝나는 행이 대부분이면 KST 입력이다. 그렇다면 V219에 `−9h` 이행을 넣고, 파트너 FE의 UTC 전송 전환과 같은 배포로 낸다.
- 초안 승인 `approvedAt`(1-6 ③)은 같은 규약을 따른다. FE가 UTC로 보내면 기본값 `now()`와 기준이 같아진다.

## 10. FE에 미리 알릴 것(호환이 깨지는 변경)

1. **시각 규약(1단계)**
   - 모든 시각 응답은 `…Z`(UTC)다. 소비자 주문 · 클레임 · 취소, 게시물 DTO, 어드민 게시물 모니터링에 새로 `Z`가 붙는다.
   - 기한 값이 9시간 앞당겨진다. 이제 정확한 값이다.
   - 시각 입력은 UTC(`Z` 또는 오프셋)로 보낸다. 날짜(`LocalDate`)는 KST 날짜 그대로다.
   - 공구 일정 입력(D3)도 UTC다.
2. **값 · 필드**
   - `ReshipFeeState`에 `WAIVED` · `CANCELLED`가 추가된다.
   - 필수가 된다: `defectNoticedOn` · `SuspendRequest.endsOn` · 직권 취소의 `counterpartyConsentConfirmed`.
   - `BASIC_INFO_TAB`의 `sub`가 소문자 탭 키로 바뀐다.
   - `hiddenCount` → `exposureSuspendedCount`(1릴리스 병행). 철회 카드 `withdrawnBy*`(`agreedBy*` 1릴리스 병행).
3. **라벨**: 「계약 성립」 · 「지급 정지 · 계정 이용 정지」 · 「운영자 확인 완료」 · 「재발송 배송비」 · 배지 「환불 실패 / 분배 실패」.
4. **Swagger 스키마 이름**: `UserOrderAction` · `UserClaimAction`.
