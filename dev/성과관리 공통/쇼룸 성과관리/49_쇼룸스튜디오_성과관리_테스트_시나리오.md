## 1. 범위와 판정 기준

- **대상**: 스튜디오 조회 API 3개(`GET /v1/creator/performance` · `/summary` · `/{groupBuyId}`), 원천 로그 적재 3곳(상품 상세 조회 API `POST /v1/user/products/{productId}/views` · 결제 완료 시 게시물 귀속 · 팔로우/언팔로우 이력), `ShowroomVisitSource.PRODUCT_DIRECT_LINK`. 스튜디오 고유 규칙인 상태 3종 접기 · 리워드 단계 · KPI 모집단 · 분포 가림 · 블록 `estimated` 도 함께 본다.
- **범위 밖**:
  - 공통 리더(`GroupBuyPerformanceReader`)의 하위주문 분류 · 건 단위 검산 · 게시물 지표 산식 → 48 파트너 테스트(PF1 ~ PF10)가 소유한다. 여기서는 **스튜디오 응답에 맞게 옮겨졌는지**만 본다.
  - 정산 산식 · 확정 · 지급 · 조정 협의 흐름 → 44(ST · SA). 이 문서는 정산 행과 협의 행을 **SQL 시드**로 넣고 성과 응답만 본다.
  - 쇼룸 현황 화면(§22-4) · 이슈 스레드 화면(스튜디오 11) · 재협업 스레드 생성 · 알림.
- **아래 케이스는 테스트 명세이고 통과 기록이 아니다.** 실행할 때 TC마다 `PASS / FAIL / BLOCKED / NOT RUN`과 실행 환경, 빌드, 일시, 증빙(응답 JSON)을 남긴다.
- 성과는 **조회할 때 계산한다**(스냅샷이 없다). 원천 행을 바꾸면 곧바로 다음 응답이 바뀐다. 그래서 「확정 뒤 숫자가 움직이지 않는다」는 정산 행이 지키는 성질이고, 이 문서는 정산 행이 있으면 정산 값을 쓰는지 확인하는 것으로 이를 본다(SL-02).
- 집계 구간은 `[group_buy.start_at, COALESCE(ended_at, end_at))` 이고 **반열림**이다. 테스트 지원의 `endGroupBuy()`(`moveTo`)는 상태를 SQL로 `ENDED`로 옮기면서 `ended_at = end_at` 으로 채운다. 시드 공구의 `end_at` 은 미래(오늘 + 4일)이므로 경계 · 기간 케이스는 `start_at · end_at · ended_at` 을 직접 넣는다.
- 시각은 서버 `Asia/Seoul` 기준이다. 목록 · 요약의 기간은 `LocalDate.now()` 기준이므로 종료일 시드는 오늘에서 상대값으로 넣는다.

### 1-4. 공통 확인 방법

1. **상태 세 곳 일치** — 목록 행 `status · statusLabel · statusTone`, 상세 `groupBuy.*`, 요약 `statusCounts` 의 칸이 같은 공구에서 같은 값이어야 한다. 톤은 `NEUTRAL · WARNING · SUCCESS` 셋뿐이다(정보 · 위험 톤이 나오면 실패).
2. **null과 0을 구분한다** — null은 「—」(잰 적 없음 · 미확정)이고 0은 측정된 0이다. 비율은 분모가 0이면 null이다. 「0 대신 null」이 기대인 칸을 0으로 받으면 실패다.
3. **「예정」 플래그 일괄 대조** — `kpi.confirmedSales.estimated` · `kpi.conversionRate.estimated` · `kpi.repeatRate.estimated` · `kpi.genderEstimated` · `funnel.estimated` · `sales.estimated` · `consumers.estimated` · `followers.conversionEstimated` 여덟 개가 **모두 같은 값**(정산 행이 없으면 true)이어야 한다. `traffic` · `kpi.followerDelta` 에는 플래그가 없다.
4. **돈 칸** — `Money.stage ≠ CONFIRMED` 이면 `amount = null` 이고 `originalAmount` 에 원래(또는 예정) 금액이 있다. `rewardBar.fixedFee` 는 상태와 관계없이 `CONFIRMED · 300,000 · 「브랜드 직접 지급」` 이다.
5. **파트너 전용 필드가 없어야 한다** — 상세 JSON에 `delivery` · `breakdown` · 원가 · 수익 · ROAS · 정산액(브랜드 수취액) · 반품률 · 취소/반품 사유 키가 **없어야** 한다. 조정 협의 응답 권한(`permissions · canAccept · canReject · canCounter`)도 없어야 한다.
6. **금지 표기** — 응답 어디에도 언팔로우 수가 없어야 한다(증감 `delta` 만). 유입 경로 `label` 에 「인스타그램」이 없어야 한다(`PROFILE_LINK = 「프로필 쇼룸 링크」`).
7. **파트너 12와 교차** — 같은 공구를 셀러 토큰으로 `/v1/seller/performance/{id}` 조회해 확정 거래액 · 판매 수량 · 쇼룸 방문(명) · 경로별 방문 · 게시물 조회 · 구매확정 건이 같은지 본다(같은 리더를 쓴다). **재구매율은 달라도 된다** — 스튜디오는 같은 인플루언서, 파트너는 같은 브랜드 기준이다(설계 0-11).
8. **에러 응답** — HTTP 상태와 응답 `code` 를 함께 본다. `INVALID_INPUT_VALUE` 의 응답 `code` 는 `INVALID_INPUT` 이다.
9. **조회 API는 부수 효과가 없다** — 조회 전후로 `settlement · settlement_adjustment · order_delivery_group · creator_follow_event` 행 수와 값이 같아야 한다.
10. 시안 · 설계서 · 코드가 충돌하면 9절에 적고, 어느 쪽으로도 임의로 통과시키지 않는다.

## 3. 목록 — `GET /v1/creator/performance`

준비: 모집단 공구 4건 — A `SETTLED`(종료 −10일 · 리워드 큼 · 전환율 낮음) · B `SETTLED`(종료 −20일 · 리워드 작음 · 전환율 높음) · C `ADJUSTING`(종료 −5일) · D `COLLECTING`(종료 −1일). 브랜드명은 A · B · D = `글로우랩`, C = 다른 브랜드.
