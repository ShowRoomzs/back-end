## 1. 범위와 판정 기준

- 대상: `/v1/seller/performance` 엔드포인트 **4개** — `GET /group-buys`(목록 L1 · L2) · `GET /summary`(KPI 8 · 상태 칩) · `GET /group-buys/{groupBuyId}`(상세 D1 ~ D4 · D1-C · D1-D) · `PUT /group-buys/{groupBuyId}/cost`(원가 — **유일한 쓰기** · 응답 = 저장 뒤 상세). 공용 리더 `GroupBuyPerformanceReader` 와 상태 파생 `PerformanceStatus` 를 함께 다룬다.
- 성과 화면은 **돈을 계산하지 않는다**(설계 0-1). 정산이 있으면 확정 거래액 · 정산액 · 리워드는 `settlement` 저장값과 **같아야** 하고, 이 문서는 산식이 맞는지가 아니라 **같은 값을 읽었는지 · 값마다 상태(`FigureState`)가 맞는지 · 분모가 맞는지**를 본다.
- 아래 케이스는 **테스트 명세**이며 통과 기록이 아니다. 공유 수(원천 로그 없음) · 실제 조정 합의 경로로 만든 D4 · FE 문구처럼 지금 판정할 수 없는 것은 13절에 적고, 스텁 · `NOT_AVAILABLE` 을 목표 동작의 통과로 기록하지 않는다.
- 시각은 서버 `Asia/Seoul`. 정산 생성 · 확정 · 지급 배치는 `application-test` 에서 꺼져 있고 `SettlementTestSupport.generate(now) · confirm · pay` 를 **직접 호출**한다. 상태 전이만 필요한 케이스는 기존 PF6 처럼 SQL 로 `settlement.status` 를 옮겨도 되지만, 그 경우 판정 기록에 「SQL 전이」라고 적는다.
- 성과 상태는 **저장하지 않고 파생**한다(정산 행 없음 = 집계 중). 그러므로 상태 전이 케이스는 성과 테이블이 아니라 정산 행을 바꾸고 다시 조회한다.

D4 의 `original` 이 4,712,800 이 아니면 성과가 수수료를 따로 계산하고 있다는 뜻이다(0-1 위반 · 13 #14).

### 1-4. 공통 확인 방법

1. 지표는 전부 `PerformanceFigure { value, state, original, basis }` 다. **값 · 상태 · 원래 값 · basis 넷을 같이** 본다. `value = null` 은 「—」이고 0 은 측정된 0 이다 — 둘을 바꿔 쓰면 실패다.
2. 정산이 있는 공구는 매번 `settlement` 행(`confirmed_sales_amount · brand_payout_amount · reward_amount · original_reward_amount · *_deduction`)과 응답 숫자를 대조하고, 파트너 13 `GET /v1/seller/settlements/{settlementId}` 의 `breakdown` 과 상세 `settlement.breakdown` 이 같은지 본다.
3. 목록 행 ↔ 상세 KPI 는 같은 리더 경로(`readRows` · `read`)라 같은 값이어야 한다(XC-01).
4. 실패 요청은 HTTP 상태 + 응답 `code` 를 보고 `group_buy_cost` · `group_buy_cost_item` 행 수와 값이 그대로인지 본다. **주의** — `INVALID_INPUT_VALUE` 의 응답 `code` 는 `INVALID_INPUT` 이다.
5. 응답에 소비자 식별값(이름 · 연락처 · `user_id` · 주문 번호)이 **없는지** 매 상세 케이스에서 본다(§47-2 분포만).
6. 원가 · 수익 값은 `/v1/seller/**` 밖으로 나가면 안 된다 — 스튜디오 · 어드민 응답에서 원가 키를 찾는 검사를 CO-12 에서 한다.
7. 시안 · 설계서 · 코드가 충돌하면 14절에 기록하고 어느 쪽으로도 임의 통과시키지 않는다.
