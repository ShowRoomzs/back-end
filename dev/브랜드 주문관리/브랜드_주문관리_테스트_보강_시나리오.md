# 브랜드 주문관리 — 테스트 보강 시나리오

- 대상: `/v1/seller/orders` 전량 · 결제 훅(하위주문 탄생·소비자 취소) · 추적/구매확정 배치 · 환불 큐 적재까지(34 설계서 범위).
- 근거: [`34_파트너센터_주문관리_BE_설계서.md`](34_파트너센터_주문관리_BE_설계서.md) · [`../전체플로우_통합테스트_시나리오.md`](../전체플로우_통합테스트_시나리오.md)(E2E-0 · A~E · X).
- 작성 방법: 현행 자동 테스트(2절)의 `@DisplayName`을 코드 경로(컨트롤러 → 서비스 → 리포지토리 WHERE 절)와 대조해 **분기·규칙·경합 중 검증이 없는 것**만 골랐다. 이미 검증된 것은 다시 적지 않는다.
- 아래 케이스는 **테스트 명세**이며 통과 표시가 아니다. 「현행 동작」은 코드를 읽어 추적한 값이고, 기대와 다르면 10절에 판정 요청으로 올렸다 — 임의로 통과시키지 않는다.
- 작성일: 2026-10-03

## 0. 진행 현황 — 2026-10-03 반영

- **F1~F4 수정 완료** — 4건 모두 기존 테스트 기대값 그대로 녹색(1-1절 「처리」 열).
- **판정 요청 N5~N11은 10절의 권장안으로 반영했다.** 단 N8의 「택배사 빈칸 차단」은 의도된 흐름임을 확인해 현행 유지했다(10절). 「현행 동작」 열은 반영 전 코드 기준 기록으로 남긴다.
- **검증** — 주문 관련 테스트(`api.seller.order` · `api.scenario` · `domain.order` · `api.app.order` · `ShowroomzApplicationTests`) 241건 통과 · 1건 비활성(D-08). 전체 1,876건 실행에서도 이 변경으로 인한 실패는 없었다.
- **자동 테스트는 CX-08을 뺀 전 케이스를 구현했다**(11절). CX-08(생성 컬럼 UNIQUE)은 통합 테스트 DB가 H2라 생성 컬럼이 없어 자동 테스트에서 제외한다 — 실 MySQL 스키마 검증(`ShowroomzApplicationTests`)이나 수동 라운드 몫이다.
- TR-02의 「한 건에서 예외가 나도 나머지 확정」은 구매확정 단건에 예외를 주입할 수단이 없어 자동 테스트에서 뺐다. 같은 격리 구조(건별 try/catch)는 TR-01이 추적 배치에서 검증한다.

| N10 | 그룹 상태와 무관한 취소 요청 승인 | CANCELLED·SHIPPING·DELIVERED 그룹의 PENDING 요청도 승인 | 승인·거부 UPDATE WHERE에 「그룹 NEW·PREPARING」 — 0행인데 요청이 PENDING이면 409 `ORDER_STATE_CHANGED` · 소비자 전액 취소 수렴 시 PENDING 요청을 **`VOIDED`**(신규 상태값 · 결정자 없음)로 닫는다 · `countPendingCancelByStatus`는 결제된 NEW·PREPARING만 · 상세 `canDecideCancelRequest`도 작업 큐에서만 | CX-01 · CX-05 |
| N11 | 송장 수정과 추적 반영의 경합 | 구 송장 결과로 배송완료 전이 가능 | 추적 반영 전이 6종(`touchTracking` · 배송완료 · 반송 감지 · 반송 완료 · 배지 설정 · 배지 해제) WHERE에 폴링 당시 `(carrier, tracking_number)` 일치 조건 · 불일치면 그 회차 결과를 버린다 | TR-03 |

> SH-03은 처음에 「정상으로 내려가면 확정 요청 전체가 400」을 결함으로 봤으나, FE가 셀에서 택배사를 고른 뒤 보내는 흐름이라 결함이 아니다. 테스트는 「빈칸 → `carrier: null` 정상 분류 → 미선택 확정은 400 → 고른 택배사로 확정」을 고정한다.
>
> `VOIDED`는 `order_cancel_request.status`(VARCHAR(16))에 들어가는 새 값이다. 스키마는 그대로이고, V149의 컬럼 주석(`PENDING, APPROVED, REJECTED`)만 낡았다 — 다음 마이그레이션에서 주석을 고친다.
