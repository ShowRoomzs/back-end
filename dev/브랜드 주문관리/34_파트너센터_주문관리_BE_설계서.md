## 0. 먼저 정한 7가지

### 0-1. 하위주문 = `order_delivery_group` — 새 테이블을 만들지 않는다

기획의 단위 3층(주문 / **하위주문 = 공구·브랜드별 배송 단위** / 주문 항목 = SKU)은 결제 모듈이 이미 그대로 깔아 두었다 — `orders` / `order_delivery_group`(키가 공구) / `order_product`. 이 화면의 목록 기본 단위인 하위주문은 **`order_delivery_group`에 이행 상태·송장·시각 컬럼을 더해서** 만든다.

- 별도 `sub_order` 테이블을 만들면 같은 배송 단위가 두 곳에 생기고, 결제·정산·판매 집계(`OrderGroupBuySalesReader`)가 보는 축과 어긋난다.
- 타 브랜드 몫 비노출은 `market_id`가 이미 그룹에 있어 WHERE 한 줄이다.

### 0-2. 취소 요청은 **이행 상태가 아니라 별도 테이블**이다

기획 §34-1이 못박았다 — "처리 후 **원래 이행 상태로 돌아가야** 하므로 같은 필드에 덮어쓰면 복귀점이 사라진다." 그러므로 `fulfillment_status`에 `CANCEL_REQUESTED` 값을 **만들지 않는다.** `order_cancel_request` 행의 존재(PENDING)가 곧 오버레이 플래그이고, 승인·거부 후 그룹 상태는 **한 번도 바뀐 적이 없으므로** 복귀가 자동이다. 탭 이동(취소 요청 탭 편입·복귀)은 조회 조건으로 해결된다.

같은 원리로 **오버레이 전부를 상태값으로 만들지 않는다** — 집화 확인 필요·추적 정지는 감시 배치가 채우는 `tracking_alert` 열(이행 상태와 별 축), 발송기한 경과는 파생값, 구매확정 후 클레임은 반품·교환 모듈의 몫이다.

### 0-3. 돈의 시점·방향을 바꾸는 전이는 **브랜드 API에 아예 없다**

§34-0 설계 원리 그대로다. 아래는 **엔드포인트 자체를 만들지 않는다** — 권한 검사로 막는 게 아니라 표면적을 없앤다.

| 전이 | 주체 | 이 설계에서 |
| --- | --- | --- |
| 배송중 → 배송완료 | 추적 배치 / 운영자 직권 | 배치(3-3) · 어드민 API는 범위 밖, `delivered_source` 컬럼만 준비 |
| 배송완료 → 구매확정 | D+7 배치 | 배치(3-4) |
| 환불 집행 | 운영자 | `order_refund_task` 큐 행만 만든다(1-9) — 집행 API 없음 |
| 반송 후속 | 시스템 → 운영자 큐 | 배치가 감지·큐 편입, 브랜드 액션 0 |

브랜드 API가 바꾸는 것은 **준비 시작 · 송장 등록/수정 · 직권 취소 · 취소 요청 승인/거부** 네 가지뿐이고, 그중 돈이 걸린 승인·직권 취소도 **환불 예정 기록까지만** 간다.

### 0-4. 택배 연동은 **포트** — 스펙이 미확정이라 인터페이스와 스텁을 먼저 만든다

연동 업체 스펙(송장 형식 판정 API · 반송/입고 코드 · 택배사 코드 매핑)이 §34-13 #16으로 미결이다. 30 설계서의 판매 포트와 같은 방식 — `DeliveryTrackerPort` 인터페이스에 **형식 검증 · 추적 조회** 두 책임을 걸고, 구현 전에는 `delivery.tracker.enabled=false`의 Noop 스텁이 **"판정 불가"를 돌려준다.**

- 스텁 기간의 송장 등록: 형식 검증을 **통과로 간주하지 않고 생략으로 기록**한다(검증 생략 여부를 이력 detail에 남긴다). 전역 중복·상태 재확인은 포트와 무관하므로 그대로 돈다.
- 스텁 기간에는 **배송완료 자동 전환·배송 이상 감지·반송 감지가 전부 멈춘다** — 배송중에 쌓인다. **연동 활성화가 런칭 게이트다**(6절 P5).

### 0-5. 파생값은 저장하지 않는다 — 단, **배치가 판정한 사실**은 저장한다

| 값 | 처리 | 이유 |
| --- | --- | --- |
| 발송기한 경과 | 파생 — `NOW() > ship_due_at AND shipped_at IS NULL` | 기한(`ship_due_at`)이 저장돼 있으면 경과는 언제나 계산된다 |
| 구매확정 예정 D-N | 파생 — `delivered_at + 7일` | 〃 |
| 탭 카운트·요약 바 | 파생 — COUNT 쿼리 | 동시 갱신 요구가 "같은 트랜잭션의 같은 데이터를 읽는다"로 충족된다 |
| **집화 확인 필요 · 추적 정지** | **저장** — `tracking_alert` | "24시간 미조회"는 **추적 API를 호출해 본 결과**다. 조회 시점마다 API를 때릴 수 없고, 판정 시각·이력이 필요하다 |
| 배송완료·반송 감지 | **저장** + 이력 | 상태 전이 그 자체 |

### 0-6. 요약 바의 모듈 밖 칸은 **`null`이지 0이 아니다**

요약 바 5칸 중 `입고 확인`·`재발송·교환`은 반품·교환 관리(`11-claims` 미제작) 소관이다. 30 설계서 0-6과 같은 규칙 — 없는 모듈의 값은 `null`로 내린다. `0`은 "처리할 일이 없다"는 **거짓 정보**다.

### 0-7. 신규 탭 `판매 취소`는 **시안대로 열어 두되, 취소 시점 상태를 기록**한다 — §34-13 #1

약관 제18조②는 직권 취소를 상품준비중에 한정하지만 시안은 신규 탭 일괄 바에도 `판매 취소`를 두었고, 택일이 대표 확정 대기다. 서버는 **NEW·PREPARING 둘 다 허용**으로 집행한다:

1. 환불 방향이라 소비자에게 불리하지 않다 — 막아서 지키는 이익이 없다.
2. `status_at_cancel`을 기록해 두므로, 어느 쪽으로 확정되어도(신규 제거 / 별도 유형 / 동시 처리) **데이터는 이미 구분돼 있다.** 확정이 "신규 불가"면 서비스 가드 한 줄 추가로 끝난다.

취소율 집계(제재)는 운영정책 `[근거 대기]`(§34-13 #8)라 **집계 테이블을 만들지 않는다** — `cancel_type`으로 소급 집계 가능하다.

### 1-3. 탭 ↔ 조회 조건 — 서버가 소유한다

`OrderTab` enum 9종. 탭이 기본 기간·기본 정렬까지 소유한다(파라미터 생략 시 적용).

| 탭 | 조건 | 기본 기간 | 기본 정렬 |
| --- | --- | --- | --- |
| `ALL` | 상태 전체 | 1개월 | 최신순 |
| `NEW` | `NEW` **AND 취소 요청 PENDING 없음** | 7일 | **오래된순** |
| `PREPARING` | `PREPARING` AND 〃 | 7일 | **오래된순** |
| `CANCEL_REQUESTED` | 취소 요청 PENDING **존재**(이행 상태 무관 — 실제로는 NEW/PREPARING) | 7일 | **오래된순** |

## 2. 상태 전이 — 전부 조건부 UPDATE

결제 모듈(`OrderRepository.markPaid` 등)과 같은 수법이다 — **현재 상태를 WHERE에 넣은 UPDATE 1행 확인**이 경합의 최종 방어선이고, JPA 더티 체킹으로 전이하지 않는다. `OrderDeliveryGroupRepository`에 전이 메서드를 모은다.

| # | 전이 | 주체 | 트리거 | WHERE 조건 |
| --- | --- | --- | --- | --- |
| 1 | `PENDING` → `NEW` | 시스템 | PAID 전이(기존 트랜잭션에 편입 — 5-1) | `status='PENDING'` |
| 2 | `NEW` → `PREPARING` | 브랜드 | 준비 시작 / 발주서 다운로드(항상 — 3-1) | `status='NEW'` **AND 취소 요청 PENDING 없음** |
| 3 | `PREPARING` → `SHIPPING` | 브랜드 | `N건 송장 등록` 확정 | `status='PREPARING'` AND 〃 |
| 4 | `SHIPPING` → `RETURNING` | 배치 | 반송 코드 | `status='SHIPPING'` |
| 5 | `SHIPPING` → `DELIVERED` | 배치 / 운영자 | 추적 완료 / 직권(어드민 범위 밖) | `status='SHIPPING'` |
| 6 | `DELIVERED` → `CONFIRMED` | 배치 | `delivered_at + 7일` | `status='DELIVERED'` |
| 7 | `NEW`·`PREPARING` → `CANCELLED` | 소비자/브랜드 | 전 항목 취소 확정 | 각 상태 |

- **역방향 전이가 하나도 없다** — 준비 시작 되돌리기 없음(§34-4), 배송중→준비중 복귀 없음(§34-5 rev.7), 반송은 환불 종결.
- #2·#3의 「취소 요청 PENDING 없음」: 요청이 걸린 하위주문은 작업 큐에서 빠져 있지만, **엑셀 업로드·다건 선택의 레이스**(요청이 선택 직후 도착)를 서버가 막아야 한다. 검사 후 UPDATE가 아니라 `NOT EXISTS` 서브쿼리를 UPDATE WHERE에 넣는다.
- 다건 액션(준비 시작·송장 등록·직권 취소)은 **행 단위 부분 성공** — 0행 UPDATE로 떨어진 행만 사유와 함께 제외하고 나머지는 진행한다(§34-5 하드 차단 표의 "그 행만 제외" 규칙과 일치).
- `RETURNING`에서 나가는 전이가 **없다** — 구매확정 불가(타이머 취소 = DELIVERED가 아니므로 배치 대상에서 자연 제외), 환불로 종결(그룹 상태는 RETURNING에 머물고 환불 집행·정산 제외는 환불 큐와 정산 모듈이 본다). 종결 상태를 따로 만들지 않는다 — 반송 탭은 조회 탭이고, 정산 제외는 `RETURNING || return_detected_at IS NOT NULL`로 판정된다.

| 생성 | Apache POI SXSSF로 xlsx 스트리밍 — **`build.gradle`에 `org.apache.poi:poi-ooxml` 추가**(현재 없음) |
| 행 단위 | **주문 항목**(SKU) — 수취인·주소는 하위주문 값 반복. 옵션·수량이 항목 축이라 항목이 행이어야 옮겨 적지 않는다 |
| 대상 범위 | **결제된 NEW·PREPARING만**(선택 건·탭 전체 모두) — 발주서는 신규·상품준비중 탭의 액션이다(§34-3). 결제 전·발송 이후 주문의 개인정보를 다시 반출하지 않는다. 그 밖의 탭으로 열면 대상 없음(`PURCHASE_ORDER_EMPTY`) |
| 상한 | `order.purchase-order-max-groups`(2,000) — 넘으면 조용히 자르지 않고 400 `PURCHASE_ORDER_TOO_MANY` |
| 준비 시작 | **항상** — 대상 중 `NEW` 행에 전이 #2를 **같은 트랜잭션**에서. 이력 `PREPARE_STARTED`(detail 「발주서 다운로드」) |
| 빠지는 행 | 전이가 0행인 `NEW`(결제 취소 선점 · 그 사이 도착한 취소 요청 · 상태 변경)는 **파일에서도 뺀다** — 발주서에 실린 하위주문은 전부 `PREPARING`이다. 다 빠지면 `PURCHASE_ORDER_EMPTY` |
| 처리 순서 | ① 대상 조회(일반 SELECT) ② `NEW` 행에 전이 #2 — **하위주문 id 오름차순** ③ 남은 행의 주문(수취인 · 연락처 · 우편번호 · 주소 · 요청사항)을 **잠금 읽기**(`PESSIMISTIC_READ` → MySQL `FOR SHARE`)로 **다시 읽어** 엑셀 행을 만든다 |
| 이력 | `purchase_order_download_log` INSERT(`prepare_started = true`) — 트랜잭션 안(반출 기록이 빠지면 안 된다) |
| 템플릿 | `GET/PUT /purchase-order/template` — `market_purchase_order_template` upsert. 기본정보 관리 화면이 같은 API를 쓴다 |

**발주서 = 준비 시작(2026-10-05 결정 · C10 설계서 U14)** — 기획 §34-4는 「다운로드와 함께 준비 시작 처리」 기본 ON · OFF면 다운로드만(견적·재고 확인용)이다. 이것을 없앤다.

- **왜**: 소비자 배송지 변경(C10 설계서 3-6)은 「취소되지 않은 하위주문이 전부 `NEW`」일 때만 열린다. `NEW`인 채로 나간 발주서는 그 뒤 바뀐 주소를 모른다. 발주서와 준비 시작을 묶으면 **발주서에 실린 주문은 배송지가 바뀌지 않는다** — 반출 표시 컬럼이나 「주소 변경됨」 알림이 필요 없다.
- **다운로드만 하던 용도**(견적·재고 확인)는 목록 행 확장(상품 · 옵션 · 수량 — 4-1)으로 본다. 개인정보 없이 볼 수 있다.
- **기획·시안 정정**: 발주서 모달(E1)의 체크박스를 지우고, 신규 탭에서 열 때 그 자리에 준비 시작 고지(E8과 같은 「소비자 취소권이 닫힌다」)를 둔다. 기획 §34-4의 「분리하면 같은 주문을 두 번 고른다」 논거는 그대로 산다.
- **과도기**: 구 FE가 `startPreparation: false`를 보내면 **400 `INVALID_INPUT`** — 모르는 필드로 조용히 무시하면 「다운로드만」을 고른 브랜드의 주문이 준비 시작되고 소비자 취소권이 닫힌다(되돌리기 없음). `null` · `true`는 받는다. FE가 필드를 지운 뒤 DTO에서 뺀다.
- **③을 다시 읽는 이유 둘**: ⓐ MySQL 기본 격리(REPEATABLE READ)에서 일반 SELECT는 ①의 스냅숏을 본다 — ①과 ② 사이에 커밋된 배송지 변경을 놓친다. 잠금 읽기는 최신 커밋값을 읽는다. ⓑ 전이 UPDATE가 영속성 컨텍스트를 비운다(`clearAutomatically`) — ①에서 읽은 주문 엔티티·프록시로 행을 만들지 않는다(전체플로우 통합 시나리오 0-11의 500과 같은 뿌리).
- **배송지 변경과의 경합**: 두 경로 모두 **하위주문(id 오름차순) → 주문** 순서로 잠근다 — 교착이 없다. 다운로드의 전이가 먼저 잡으면 변경은 `PREPARING`을 보고 409, 변경이 먼저 잡으면 다운로드는 그 커밋을 기다렸다가 ③에서 새 주소를 싣는다.
- 상품준비중 탭에서 다시 받는 발주서는 전이가 없다(이미 `PREPARING`) — 그 주문들도 배송지 변경이 닫혀 있으니 내용이 낡지 않는다.

### 3-2. 송장 등록 — 검사 4단 중 서버는 ③·④

①(입력 중 정제) ②(형식·화면 내 중복)는 FE다. 서버는:

**③ `POST /shipments` — 확정 시점**

```
행마다:
  1. carrier·trackingNumber 존재(빈 값 행은 FE가 이미 제외 — 왔으면 400 아닌 행 제외)
  2. 형식 — DeliveryTrackerPort.validateInvoice() (스텁이면 생략 기록)
  3. 전역 중복 — 종결 전 상태의 (carrier, tracking_number) 존재 시 제외,
     사유에 겹치는 주문번호를 지목: 「ORD-NNNNN에 이미 등록된 번호입니다」
  4. 전이 #3 조건부 UPDATE — 0행이면 「주문 상태가 변경되었습니다」로 제외
  5. 성공 행: shipped_at = now · 이력 INVOICE_REGISTERED
응답: { succeeded: n, movedTo: "SHIPPING", errors: [{deliveryGroupId, code, message}] }
```

부분 성공이 원칙이다 — 오류 행 때문에 나머지를 막지 않는다. 결과 배너(몇 건이 어디로)는 이 응답으로 그린다.

**엑셀 일괄 업로드 — `POST /shipments/parse`** (multipart xlsx · 최대 1,000행)

- **상태를 바꾸지 않는다** — 파싱·분류만 하고 행 배열을 돌려준다. 확정은 FE가 셀을 채운 뒤 같은 `POST /shipments`를 타므로 **확정 지점이 하나**다(§34-5 「채우기」 라벨의 서버 쪽 대응).
- 분류(E3): 정상 / 이미 배송중 / 송장번호 중복(겹치는 주문 병기 — **내 마켓 주문일 때만**, 타 브랜드 주문이면 「다른 주문에 이미 등록된 번호입니다」) / 주문번호 없음·내 마켓 아님(같은 사유로 — 존재 여부를 구분해 주면 타 브랜드 주문 탐색에 쓰인다) / **신규(준비 대기) 주문 — 준비 시작 전이라 등록 불가**(rev.7 철회 반영) / 파일 안 같은 하위주문 반복(`ORDER_DUPLICATE_IN_FILE` — 첫 정상 행만 남긴다). 택배사 칸이 비면 `carrier: null`로 정상 분류한다 — 목록 셀의 「택배사 일괄 적용」으로 채운 뒤 확정한다.
- 숫자 셀은 자릿수 그대로 읽는다 — 일반 서식의 12자리 숫자를 지수 표기로 읽으면 엉뚱한 송장이 정상 행이 된다.
- `GET /shipments/template` — 양식 xlsx(주문번호 · 택배사 · 송장번호).

**송장 수정 — `PATCH /{id}/shipment`**

- 허용: `SHIPPING`만(배송완료 전) · `RETURNING` 불가 — WHERE에 박는다.
- 목록 셀 편집은 `tracking_alert = PICKUP_UNCONFIRMED` 행만 열리지만(FE), 상세의 `송장 수정`은 배송중 전체라 **서버 가드는 상태만** 본다.
- 효과: carrier/tracking 교체 · `tracking_alert`·`last_tracking_at` 리셋 · `shipped_at` **유지**(발송기한 판정값은 최초 등록 시각 — 수정으로 기한 위반이 세탁되면 안 된다) · 이력 `INVOICE_UPDATED`(구→신).

### 3-3. 배송 추적 — `DeliveryTrackerPort` + 감시 배치

**포트** — `global/delivery/tracker/DeliveryTrackerPort.java`

```java
public interface DeliveryTrackerPort {
    ValidationResult validateInvoice(DeliveryCarrier carrier, String trackingNumber); // VALID / INVALID / UNAVAILABLE
    Optional<TrackSnapshot> track(DeliveryCarrier carrier, String trackingNumber);
    // TrackSnapshot: lastEventAt · delivered(deliveredAt) · returnDetected · returnCompleted
}
```

구현은 연동 업체 스펙 확정(#16) 후. 그전에는 `NoopDeliveryTracker`(`UNAVAILABLE` · `Optional.empty()`).

**추적 반영은 폴링 당시 송장에만** — 폴링(트랜잭션 밖)과 반영 사이에 셀러가 송장을 고칠 수 있다. 반영 전이 6종(`last_tracking_at` 갱신 · 배송완료 · 반송 감지 · 반송 완료 · 배지 설정 · 배지 해제)은 WHERE에 폴링 당시 `(carrier, tracking_number)`를 넣고, 0행이면 그 회차 결과를 버린다 — 구 송장의 배송완료가 새 송장에 덮이면 구매확정 타이머가 잘못 돈다.

**`OrderDeliveryTrackingScheduler`** — `global/scheduler` · 주기 설정값(잠정 30분 · `order.tracking.poll-interval`). `delivery.tracker.enabled=false`면 기동하지 않는다.

| 대상 | 판정 | 처리 |
| --- | --- | --- |
| `SHIPPING` · `RETURNING` 전 행 | `track()` 호출 | `last_tracking_at` 갱신 |
| 〃 | `returnDetected` | 전이 #4 → `return_detected_at` · 이력 — **반송 사유는 저장하지 않는다**(API가 코드·시각만 준다 — §34-6) |
| `RETURNING` | `returnCompleted` | `return_completed_at` · `order_refund_task(RETURN_COMPLETED)` INSERT · 이력 — 운영자 큐 편입 |
| `SHIPPING` | `delivered` | 전이 #5 → `delivered_at`(추적상 완료 시각) · `delivered_source='TRACKER'` · 이력 |
| `SHIPPING` · alert 없음 | `shipped_at + 24h` 경과 && 이벤트 0건 | `tracking_alert='PICKUP_UNCONFIRMED'` · 이력 1회 |
| `SHIPPING` | `last_tracking_at + 7일` 경과 | `tracking_alert='STALLED'` · 이력 1회 |
| alert 행 | 이벤트 재개 | `tracking_alert = NULL`(해제 이력은 두지 않는다 — 소음) |

24시간·7일은 설정값으로 뺀다(`order.tracking.pickup-alert-hours=24` · `stall-alert-days=7`) — §34-13 #17이 김화창 확인 대기라 코드 상수로 박지 않는다.

**분실·누락에 플랫폼은 관여하지 않는다**(약관 제17조③) — 추적 정지의 서버 처리는 **배지와 송장 수정 허용뿐**이다. 분실 신고 폼·증빙 테이블을 만들지 않는다(rev.6 폐기 반영). 거래플로우 v1.3의 「송장 등록 +28일 자동 구매확정」 폴백은 **약관 근거가 없어 구현하지 않는다** — §34-13 #4가 확정되면 구매확정 배치에 조건 하나를 더한다.

### 3-4. 구매확정 — `PurchaseConfirmScheduler`

- 매시: `fulfillment_status='DELIVERED' AND delivered_at <= now - 7일` → 전이 #6.
- 같은 트랜잭션에서 그룹의 **미취소 항목**을 `PAID → PURCHASE_CONFIRMED`로 전이(`OrderProductRepository.transitionByGroup`) · 이력 `PURCHASE_CONFIRMED`.
- `RETURNING`은 `DELIVERED`가 아니므로 **타이머 취소가 구조적으로 성립**한다 — 별도 플래그 불요.
- 7일은 약관 제19조① 값이라 상수로 박되 enum 아닌 설정값(`order.confirm.days=7`)으로 둔다 — 약관 개정은 코드 배포 없이 따라간다.
- 구매확정 탭의 「정산」 열(`정산 대상 · 공구 종결 후 일괄` 등)은 **정산 모듈 범위** — 이번 응답은 `settlement: null`로 내린다(0-6 규칙).

### 3-5. 취소 3경로

| 경로 | 이 설계의 범위 | 처리 |
| --- | --- | --- |
| ① 소비자 취소(준비 시작 전) | **기존 앱 API에 게이트 추가**(5-2) | PG 자동 취소(기존 경로) + 그룹 `CANCELLED(CONSUMER)` + 재고 원복(기존 `StockReleaser`) |
| ② 취소 요청 → 승인/거부 | 브랜드 API | 아래 |
| ③ 브랜드 직권 취소 | 브랜드 API | 아래 |

**② 승인 — `POST /cancel-requests/{requestId}/approve`**

```
1. 요청 조건부 UPDATE: status PENDING → APPROVED **AND 그룹 NEW·PREPARING** (0행 — 요청이 이미 결정됐으면 409 `CANCEL_REQUEST_ALREADY_DECIDED`, 요청은 PENDING인데 그룹이 작업 큐를 벗어났으면 409 `ORDER_STATE_CHANGED` · 발송 뒤 취소는 반품 경로다)
2. 대상 항목: order_product PAID → CANCELLED (cancel_type='REQUEST_APPROVED') — 항목별 조건부
3. 항목 재고 원복 — variant_id 오름차순(StockReleaser와 같은 잠금 순서) · 진행 중 공구면 다시 팔린다
4. 그룹 미취소 항목 0이면 그룹 → CANCELLED (전이 #7) — 전 항목 승인일 때만 취소 탭
5. order_refund_task(CANCEL_REQUEST_APPROVED, 요청분 합계) INSERT — 환불은 운영자
6. 이력 CANCEL_REQUEST_APPROVED
```

승인해도 **남은 항목의 그룹 상태는 그대로**다(NEW/PREPARING) — 0-2의 복귀가 여기서 실현된다. 취소율 미반영은 `cancel_type`이 구분한다.

**② 거부 — `POST /cancel-requests/{requestId}/reject`** — `reason` 필수(소비자 전달). 요청 행 전이만, 항목·그룹 불변. 이력 기록. 그룹 조건(NEW·PREPARING)은 승인과 같다.

> 거래플로우 v1.3의 **「2영업일 방치 → 운영자 대행 취소」**(§34-13 #6)는 약관 근거 대기 + 어드민 범위라 구현하지 않는다. `requested_at`이 있으므로 어드민 큐 쿼리로 언제든 세울 수 있다. 이 화면의 「경과」 열도 `requested_at` 파생이다.

**③ 직권 취소 — `POST /cancel`** — `{deliveryGroupIds[], reasonCode, consumerMessage}`

- 허용 상태 `NEW`·`PREPARING`(0-7) — `status_at_cancel` 기록.
- `consumerMessage` 필수 — 사유와 함께 소비자에게 그대로 전달(약관 제18조②). 전달 자체는 알림 모듈 연계로 두고 **컬럼에 보존**이 먼저다(`cancel_reason_detail`).
- 하위주문 **전 항목** 취소 → 그룹 `CANCELLED(SELLER_DIRECT)` · 재고 원복 · `order_refund_task(SELLER_DIRECT_CANCEL, 항목 합 + 배송비)` · 이력.
- 걸려 있는 취소 요청 PENDING이 있으면 **선처리 요구**로 409 — 직권 취소가 요청을 암묵 승인/소멸시키면 소비자 통지 문구가 갈라진다.

### 3-6. 발송기한

| 항목 | 처리 |
| --- | --- |
| 기산점 | **결제완료 시각** — PAID 전이 때 `ship_due_at = paid_at + market.shipping_lead_days` **스냅샷**. 이후 마켓 설정을 바꿔도 기존 주문 기한은 불변(귀책 판정값이다) |
| 판정 | `shipped_at`(송장 등록 시각) — 집화 아님. 송장 수정이 `shipped_at`을 유지하는 이유(3-2) |
| 경과 | 파생 — 응답에 `shipDueAt` · `shipOverdue: boolean`. 신규·상품준비중·전체 탭 열 + 정렬 지원 |
| 출처 | `Market.shippingLeadDays`(가입 시 필수 입력 — 이미 존재)로 **집행**. §34-13 #3(계약 「발송 방식 2종」 — 마감 후 일괄 발송)이 확정되면 기산 로직만 바뀐다 — 스냅샷 컬럼이라 소급 영향 없음 |
| 마감 시각·공휴일·영업일 | `[근거 대기]` — 1차는 **달력일·자정 기준**으로 집행하고 미결에 둔다(7절) |

제재 집계(§34-13 #5)는 만들지 않는다 — `ship_due_at`과 `shipped_at`이 다 있으므로 소급 집계 가능.

## 5. 기존 코드에 따라오는 수정

### 5-1. PAID 전이 훅 — 하위주문의 탄생

`PaymentTransitions`의 PAID 전이(마크 성공 분기) **같은 트랜잭션**에 추가:

1. 그룹 전이 #1(`PENDING → NEW`) · `sub_order_number` 발급 · `ship_due_at` 스냅샷(마켓별 `shipping_lead_days` — 그룹의 `market` 조인).
2. 이력 `PAID` append.

주문 만료·결제 전 취소 경로: 그룹은 `PENDING`에 머물고 셀러 조회가 `orders.status='PAID'`를 전제하므로 **그룹 상태를 건드리지 않는다**(기존 `StockReleaser`의 항목 CANCELLED 전이로 충분).

### 5-2. 사용자 주문 취소 게이트 — `OrderCommandService.cancelOrder`

현재는 PAID 주문을 무조건 전액 취소한다. **전 그룹이 `NEW`일 때만** 허용으로 바꾼다:

- 하나라도 `PREPARING` 이후면 409 `ORDER_CANCEL_WINDOW_CLOSED` — 앱은 취소 요청(C10)으로 안내.
- 성공 시(PG 취소 확인 후 `cancelPaid`와 같은 트랜잭션) 그룹 전부 `CANCELLED(CONSUMER)` + 이력. 그 주문에 걸린 검토 중 취소 요청은 `VOIDED`로 닫는다 — 남겨 두면 취소된 그룹에 「검토 중」이 붙어 탭 카운트와 목록이 어긋나고, 승인하면 0원 환불 큐가 선다.
- `claimUserCancel` 선점 WHERE에 `NOT EXISTS(준비 시작 그룹)`을 넣는다 — 선점과 준비 시작의 레이스에서 **소비자 취소권 종료가 먼저면 취소가 진다**(약관의 방향과 일치).

주문 단위 부분 취소(일부 하위주문·항목만 PG 부분 취소)는 소비자 앱 C10 범위다 — 이 게이트는 기존 전액 경로의 오동작(준비 시작 후 자동 전액 취소)만 막는다.

### 5-3. 판매 포트 — 공구 정산 게이트가 처음으로 채워진다

30 설계서 0-6의 「미종결 주문 건수」가 이제 계산 가능하다: **미종결 = 그룹이 `CONFIRMED`·`CANCELLED`가 아닌 것**(RETURNING은 환불 집행 완료 전까지 미종결). `GroupBuySalesReader` 구현(`OrderGroupBuySalesReader`)에 미종결 카운트 메서드를 추가한다 — 공구 「정산 확인」 게이트가 거짓으로 열리던 `Optional.empty()` 구간이 닫힌다.
