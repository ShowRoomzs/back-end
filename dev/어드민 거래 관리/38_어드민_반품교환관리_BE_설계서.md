## 0. 먼저 정한 7가지

### 0-1. 06b는 **파트너 11의 조회를 그대로 쓰고 열 둘만 더한다** — 새 조회 로직이 없다

§38-0 「브랜드 큐와 같은 탭 · 같은 건수」. CS 통화에서 운영자와 브랜드가 같은 단계 이름 · 같은 건수를 봐야 하므로, 어드민이 따로 집계하면 반드시 어긋난다. 그래서 `SellerClaimQueryService`의 `searchClaims` · `summarize` · `getClaimForAdmin`을 **`marketId = null`(전 브랜드)로 부르는 것**이 06b 조회의 전부다.

| 파트너 11 (이미 있는 것) | 06b가 더하는 것 |
| --- | --- |
| `SellerClaimListItem`(탭 공통 superset) | `brandName` · `feeBearer` · `feeBearerLabel` · `faultChangedToSeller` |
| `SellerClaimSummaryResponse`(KPI · 탭 7 · 유형) | 그대로(어드민 전용 KPI 없음) |
| `SellerClaimDetailResponse`(반려 6항목 · 타이머 · 이력) | `brandName` · `feeBearer` · `canAcceptDispute` |
| `ClaimTab` 7종 · 탭별 기본 정렬 | 그대로 |

**신규 테이블 0개 · 신규 컬럼 0개.** 1009 수정계획 V174(반려 6항목 · `split_from_claim_id` · `opened_by`) · V175(`inspect_notice_count`)가 이미 06b가 읽는 열을 다 만들어 두었다.

### 0-2. 운영자가 **실행하는 일은 하나**다 — 반려 이의 인용

§38-0. 회수 · 입고 · 검수 · 재발송은 소비자와 브랜드의 일이고, 신청 단계 반려는 없다. 독촉 버튼도 없다(기한 경과는 `OrderOverdueNoticeService`가 영업일마다 횟수를 센다 — 06d). 기각은 버튼이 아니라 **소통 스레드 답변**이므로 API가 없다.

그래서 06b의 쓰기 API는 `POST /v1/admin/claims/{claimId}/dispute-acceptance` 하나다. 1009 수정계획 8-3은 `POST …/refund-tasks`로 적었지만, 06a B5의 `refund-tasks`(운영자가 항목 · 금액을 고르는 일반 사유 환불)와 **효과가 다르다**(반려 클레임 종결 · 재발송비 청구 소멸이 같이 일어난다) — 다른 이름으로 가른 것이 맞다.

### 0-3. 인용은 **「반품 승인과 같아지는 것」** — 돈은 여기서 나가지 않는다

§38-5 「인용의 효과 — 셋이 한 번에」. 인용 트랜잭션 하나가 ① 재발송비 청구 소멸 ② 운영자 사유 환불 큐 편입(`OPERATOR_REASON · DISPUTE_ACCEPTED · PENDING`) ③ 클레임 종결(`COMPLETED · REFUNDED`)을 한다. **집행은 06c(§39) 재확인 다이얼로그에서만** 한다 — 운영자 사유 환불은 PG 자동 환불과 달리 자동 재시도도 없다(수정계획 Q3).

상품은 브랜드 창고에 그대로 남는다(반송 없음). `order_product.returned_quantity`를 더해 잔여 수량에서 뺀다 — 통과 반품과 같다.

### 0-4. **반품 · 반려 보류**만 받는다 — 교환 반려 이의는 기획 전

시안 「확인 필요 ⓒ」 · §38-8 A-7. 교환 반려는 환불이 아니라 **원래 상품 반송**이 기본이라 인용의 효과가 정의되지 않았다. 가드는 `type = RETURN ∧ status = REJECT_HOLD`이고, 반송이 이미 시작된 반려(`RESHIPPING` 이후)도 받지 않는다. 그 밖은 전부 `409 CLAIM_STATE_CHANGED`다.

### 0-5. 폐기는 **표기도 액션도 두지 않는다** — 코드는 보존

§38-1 #5(2026.10.05) 「약관 반영 전까지 폐기하지 않는다」. 도메인에는 35 설계서 때 만든 `disposeAfterStorage`(고지 2회 이상 · 보관 기한 경과 가드) · `disposed_at` · `StoragePhase.EXPIRED` · `ClaimEventType.DISPOSED`가 남아 있지만 **어떤 컨트롤러도 부르지 않는다**(파트너 · 어드민 · 앱 전부). 06b에 폐기 API를 만들지 않고, 응답의 `storage.phase = EXPIRED`는 FE가 「폐기 가능」으로 그리지 말고 「기한 경과 · 약관 반영 후 처리」로 그린다(7절 #8).

### 0-6. 소비자 이의는 **1:1 문의**로 들어온다 — 클레임과의 연결은 아직 없다

§38-5 「이의 출처 — 1:1 문의 · 원문 · 문의 번호 · 사진 · 접수 시각을 ④블록에」. 현재 `one_to_one_inquiry`에는 `order_id`만 있고 `claim_id`가 없다. 그래서 상세 ④ 「소비자 이의」 블록 · 목록 보조줄 「소비자 이의 접수」 · 요약 「반려 이의 N건」 · 사이드바 배지는 **지금 내릴 수 없다**. 연결 경로 자체가 미결(§38-8 B-12)이라 7절 #1에 설계만 적고 구현은 확정 뒤로 둔다. 그때까지 운영자는 반려 보류 탭에서 문의 번호를 보고 인용 폼의 「근거」에 적는다.

### 0-7. 패키지는 `api.admin.transaction` — 06a~06d가 한 묶음

1009 수정계획 8절은 `admin.order · admin.claim · admin.refund · admin.exception`으로 적었으나, 실제 구현은 GNB 「6 거래 관리」 하나를 `api.admin.transaction`에 모았다(`AdminOrderController` · `AdminClaimController` · `AdminRefundController` · `AdminOrderExceptionController`). DTO도 `AdminTransactionDto` 한 파일에 06b · 06c · 06d가 같이 있다. 운영자 id는 `AdminOrderController.operatorId(principal)`를 공유한다.

## 1. 도메인 — 06b가 읽는 것 (35 설계서 · 1009 수정계획의 결과)

새로 만드는 테이블 · 컬럼은 없다. 06b가 **어느 열을 어느 화면에 쓰는지**만 적는다.

### 1-1. `order_claim` — 06b 열 매핑

| 시안 열 · 블록 | 읽는 열 · 계산 | 비고 |
| --- | --- | --- |
| 접수번호 `CLM-NNNN` | `claim_id` → `claimNumber()` | PK 표기 |
| 유형 | `type` (`RETURN` · `EXCHANGE`) | 탭이 아니라 `types` 필터 |
| 소비자 | `user_id` → `consumerName` | **파트너는 전체 표기** — 어드민 마스킹은 7절 #6 |
| **브랜드**(어드민 전용) | `delivery_group.market_name` | 스냅샷 |
| 상품 · 옵션 · 수량 | `order_product` · `quantity` · `exchange_option_name` | 교환은 「A → B」 |

| 운영자 개설(B4) | `opened_by = OPERATOR` · `open_reason` · `opened_by_admin_id` | 목록 보조줄 · 상세 ① |
| 구매확정 타이머 | `order_delivery_group.confirm_paused_at` → `purchaseConfirm{paused, remainingDays, dueAt}` | 「정지 · 남은 N일」 |
| 종결 · 금액 | `result` · `completed_at` · `refunded_amount` | 완료 탭 `outcome` · `amount` |

### 1-2. 상태 · 탭 — 파트너와 같다

`ClaimStatus` 10종 · `ClaimTab` 7종(35 설계서 1-2 · 1-3). 라벨은 1009에서 「거절」→「반려」로 바뀌었다(`REJECT_HOLD = 반려 보류` · `ClaimResult.REJECTED = 반려 종결`). 결제 대기(`PAYMENT_PENDING` — 고객 귀책 교환의 선결제 전)는 어느 탭에도 없고 어드민 상세에서도 `404`다(`getClaimForAdmin`이 거른다).

완료 탭(`DONE`)은 **환불 대기(`REFUND_PENDING`) · 재발송 중(`RESHIPPING`) · 종결(`COMPLETED`)**의 합이다 — 「브랜드가 할 일이 끝난 것」. 시안 A1 완료 3건과 같은 기준이다.

### 1-3. 금액 — `ClaimRefundCalculator`(앱 설계서 1-4)

```
환불 = 통과한 상품 금액 − 반품 배송비 차감(고객 귀책 ∧ 무료배송 주문 · 요청당 1회 · 주문 시점 편도 배송비)
일부 반려 ∧ 환불 ≥ 재발송비 : 환불 −= 재발송비   (반려 상품을 결제 없이 돌려보낸다)
환불 < 재발송비            : 빼지 않는다 — 소비자가 따로 결제(Q15)
```

§38-4의 식(`상품 − 최초 배송비 − 재발송비`)과 같다. 「3,000원」은 고정값이 아니라 **`order_delivery_group.base_delivery_fee`**(주문 시점 스냅샷)다 — §38-8 A-3(3,000원의 출처)의 답은 「브랜드 기본 배송비 · 주문 때 본 값」이다. 상세 `refund{itemAmount, requestDeduction, requestExpectedAmount, basisLabel}`가 이 식을 그대로 내린다(검수 전 = 예정 · 판정 후 = 확정).

### 1-4. 기한 · 영업일 · 자동 취소 — 전부 설정값(`application.yml order.claim`)

| 키 | 값 | 06b 표시 |
| --- | --- | --- |
| `collect-due-business-days` | 2 | 회수 대기 방치(`collect_due_at`) · KPI `overdue` |
| `inspect-due-business-days` · `inspect-due-basis` | 2 · `RECEIVED` | 검수 기한(`inspect_due_at`) · 「검수 지연」 |

## 2. API — `/v1/admin/claims` (권한 `ADMIN`)

컨트롤러 `AdminClaimController implements AdminClaimControllerDocs` · 서비스 `AdminClaimService` · DTO `AdminTransactionDto`(06b 부분).

| # | 메서드 · 경로 | 시안 | 설명 |
| --- | --- | --- | --- |
| 1 | `GET /v1/admin/claims` | A1 · A2 · A3 | 목록 — 파트너 11과 같은 조건 · 같은 행 + 어드민 열 |
| 2 | `GET /v1/admin/claims/summary` | 탭 건수 · 툴바 | KPI 4 · 탭 7 · 유형 2 — 전 브랜드(또는 `marketId`) |
| 3 | `GET /v1/admin/claims/{claimId}` | B1~B4 | 상세 — 파트너 상세 + 브랜드 · 귀책 · `canAcceptDispute` |
| 4 | `POST /v1/admin/claims/{claimId}/dispute-acceptance` | B2 | **반려 이의 인용** → 운영자 사유 환불 편입 |

### 2-1. 목록 — `GET /v1/admin/claims`

**쿼리** — `SellerClaimController`의 목록과 같고 `marketId`만 더해졌다.

| 파라미터 | 값 | 비고 |
| --- | --- | --- |
| `marketId` | 선택 | 없으면 전 브랜드 |
| `tab` | `ALL`(기본) · `COLLECT_WAIT` · `COLLECTING` · `INSPECTION` · `RESHIP` · `REJECT_HOLD` · `DONE` | 탭이 상태 집합과 기본 정렬을 소유 |
| `types` | `RETURN` · `EXCHANGE` 집합 | 시안 「유형 전체 / 반품 / 교환」 셀렉트 |
| `reason` | `ClaimReason` | 파트너 필터 호환(시안에는 없음) |
| `from` · `to` | ISO 날짜 · 기준은 **신청일시** | 기본 최근 30일 · 상한 365일 · 역전은 `ORDER_SEARCH_RANGE_INVALID` |
| `keyword` | `CLM-NNNN`이면 PK 조회 · 그 외는 **주문번호 정확 일치** | 브랜드명 · 소비자명 검색은 없다 — 7절 #2 |
| `page` · `size` | `PagingRequest` | `size` 상한은 `order.list-page-size-max`(기본 100 · yml 미지정) — 시안의 20 · 50은 FE 선택지(§38-9 #6) |

**정렬** — `OrderClaimRepositoryImpl.primaryOrder`: 작업 탭(회수 대기 · 회수 중 · 입고·검수 · 재발송 · 반려 보류)은 `stage_entered_at` **오래된 순**, 조회 탭(전체 · 완료)은 **최신 순**. 시안의 정렬 셀렉트(신청일시 최신순 / 경과 오래된순)와 「검수 지연 상단 고정」은 서버에 없다 — 7절 #3.

**응답** — `PageResponse<AdminTransactionDto.ClaimListItem>`

```json
{
  "claim": { "...SellerClaimListItem 전체 — claimId · claimNumber · type · consumerName · productLabel · quantity · reasonLabel · status · statusLabel · stage · elapsedDays · overdue · openedByOperator · openReason · collection · inspectDueAt · reshipFee · rejectReasonLabel · storage · outcome · amount · actions · orderItems ..." },
  "brandName": "데일리랩",
  "feeBearer": "CONSUMER",
  "feeBearerLabel": "소비자 귀책",
  "faultChangedToSeller": false
}
```

- `claim.statusTone`은 파트너 기준으로 전부 `NEUTRAL`이다. 시안 06b의 색 규칙(정보 기본 · 검수 지연만 경고 · 완료 성공 · 반려 종결 중립)은 **FE가 `stage` · `overdue` · `outcome`으로 고른다** — 파트너 11과 같은 행을 쓰기로 했으므로 톤 열을 둘로 만들지 않는다.
- `claim.actions`(입고 확인 · 검수 · 재발송 등록)는 **파트너 버튼**이다. 어드민 FE는 무시한다 — 어드민 액션은 상세의 `canAcceptDispute` 하나뿐.
- 반려 보류 탭(A3)의 열은 같은 행에서 `shipLabel`(보관 중인 상품) · `rejectReasonLabel` · `rejectedAt` · `reshipFee` · `storage{noticeCount, lastNoticeAt, storageDueAt, phase}`로 그린다.

구현 메모 — `AdminClaimService.getClaims`는 파트너 행을 받은 뒤 `findAllById`로 클레임을 한 번 더 읽어 어드민 열을 붙이고, `PageResponse`를 같은 쪽수 정보로 다시 싼다. 행이 50건 이하라 쿼리 2회면 된다.


| 항목 | 규칙 |
| --- | --- |
| 가드 | `type = RETURN ∧ status = REJECT_HOLD` — 아니면 `409 CLAIM_STATE_CHANGED`(「반려 보류 중인 반품만 이의를 인용할 수 있습니다」). 교환 반려는 받지 않는다(0-4) |
| `amount` | 필수 · 1 이상 · **운영자 입력** — 명세는 「수정 불가 · 귀책 브랜드 → 차감 없음」이라 서버 계산으로 바꿔야 한다(7절 #4) |
| `detail` | 필수 · 500자 — 이력 · 환불 관리 「근거」에 남는다 |
| 사유 | 명세의 셀렉트 3종(반려 이의 인용 / 위해성 리콜 / 기타) 중 이 API는 **항상 `DISPUTE_ACCEPTED`**다. 리콜 · 기타는 06a B5 `refund-tasks`로 낸다 |
| 멱등 | 두 번 부르면 두 번째는 상태 가드에서 409 |

**트랜잭션 — `OrderClaimService.acceptRejectionDispute`** (한 트랜잭션 · 회수 묶음 행 잠금)

1. `order_claim_collection` `SELECT … FOR UPDATE` — 같은 박스의 다른 판정과 직렬화.
2. 같은 박스에 **다른 반려 보류가 없으면** `REJECT_RESHIP` 청구(`PENDING`)를 `VOID`로 — 「재발송비 결제 요청 취소」. 다른 반려 보류가 남아 있으면 청구는 그 건의 것이므로 건드리지 않는다.
3. `OrderFulfillmentService.enqueueOperatorRefund` — `order_refund_task(source = OPERATOR_REASON, source_id = claimId, origin = OPERATOR, reason = DISPUTE_ACCEPTED, status = PENDING, requested_by = adminId)` + 하위주문 이력 `REFUND_ENQUEUED_BY_OPERATOR` + `RefundTaskEnqueuedEvent`.
4. `OrderClaimRepository.closeRejectedByDispute` — 조건부 UPDATE(`RETURN ∧ REJECT_HOLD`) → `COMPLETED · REFUNDED · refunded_amount = amount · completed_at = now`. 0행이면 409(동시 변경).
5. `order_product.returned_quantity += quantity` · 전량이면 항목 상태 `RETURNED`.
6. 클레임 이력 `DISPUTE_ACCEPTED`(actor `ADMIN` · `「27,200원 · 근거」`) → `ClaimHistoryRecordedEvent` 발행.

| 명세 | 구현 |
| --- | --- |
| ① 귀책 브랜드로 변경 | **없음** — `fee_bearer` · `fault_changed_to_seller`를 바꾸지 않는다(7절 #4) |
| ② 재발송비 결제 요청 취소 | ✅ 2단계 |

## 3. 흐름 — 06b에서 보이는 클레임의 일생

06b는 조회 화면이라 전이의 주인은 다른 서피스다. 운영자가 **어느 단계에서 무엇을 보는지**만 적는다.

```
소비자 신청(앱) ─▶ REQUESTED 회수 대기 ──(송장 7일 미입력)──▶ COMPLETED·CANCELLED(INVOICE_EXPIRED)
   │ 운영자 대신 개설(06a B6 · opened_by = OPERATOR)
   ▼
COLLECTING 회수 중 ─▶ ARRIVED 도착 ─▶ RECEIVED 검수 대기 ──(입고 + 2영업일 초과)──▶ 「검수 지연」 · 자동 알림 N회 · 06d
   ▼ 브랜드 검수(파트너 11)
   ├─ 통과 ─▶ REFUND_PENDING ─▶ PG 자동 환불 ─▶ COMPLETED·REFUNDED             (반품)
   │                       └▶ RESHIP_READY ─▶ RESHIPPING ─▶ COMPLETED·EXCHANGED (교환 · 타이머 7일 새로)
   ├─ 일부 반려 ─▶ 원 행 통과(위) + 분할 행 반려(아래) · 재발송비는 통과분 환불에서 차감
   └─ 반려 ─▶ REJECT_HOLD 반려 보류 ─┬─ 소비자 재발송비 결제 ─▶ RESHIP_READY ─▶ … ─▶ COMPLETED·REJECTED
                                     ├─ 미결제 고지 N회 → 보관 기한(고지 2회 + 3개월) · 폐기 없음
                                     └─ 소비자 이의(1:1 문의) ─▶ ★ 운영자 인용(06b B2) ─▶ COMPLETED·REFUNDED + 환불 큐 → 06c 집행
```

★ 표시가 06b의 유일한 쓰기다. 기각은 소통 스레드 답변(상태 변화 없음).
