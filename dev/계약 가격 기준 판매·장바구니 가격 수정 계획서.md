## 1. 개요 · 범위

**지금 상태** — 계약의 공구가는 공구 게시물 카드(`GroupBuyPostCardLoader`)에만 보인다. 카드를 탭해 C7에 들어가는 순간 정가·할인율 0%가 되고, 장바구니·합계도 정가다. 셀러가 상품 정가를 고치면 담긴 금액이 바뀐다.

**목표** — 게시물에서 본 가격이 상세 → 옵션 시트 → 장바구니 → 주문서 → 결제까지 같은 값으로 이어지고, 체결 이후에는 셀러가 무엇을 고쳐도 변하지 않는다.

| 접점 | 지금 | 이번에 |
| --- | --- | --- |
| C7 `GET /v1/common/products/{id}` | `product.sale_price`(정가) | `?groupBuyId=` → 해석기. 옵션별 `salePrice`·`regularPrice`·`discountRate` |
| 옵션 시트 `GET …/{id}/variants` | `variant.sale_price` | `?groupBuyId=` → 해석기 |
| 장바구니 담기·수정 | `variantId + quantity` | `+ groupBuyId`(필수). 담을 수 있는지 = 공구 진행 중 ∧ 계약에 옵션 있음 ∧ 상품 구매 가능 |
| 장바구니 목록·합계·배송비 | `variant.sale_price`, 마켓 단위 그룹 | 해석기, **공구 단위 그룹** + D-day |
| 주문서·주문 생성 | 없음(결제 계획서) | 결제 계획서가 만들되 단가는 해석기 |
| 셀러 상품 가격 수정 | 장바구니 금액이 바뀜 | 영향 없음 |

**선행 조건** — 옵션 계획서 PR A(`contract_item_option` + 옵션 정가 스냅샷). 해석기가 옵션 판매가(공구가 + 옵션가)를 내려면 옵션 행이 있어야 한다.

**범위 밖** — 주문서·주문 생성·결제 확정 코드(결제 계획서 PR 3~5), 상품 검색 목록·C1 홈의 가격 표시(9절 미결 ①), 쿠폰(기획 제외).

## 2. 가격이 흐르는 경로

```
계약(CONCLUDED · 불변)
  contract_item.group_buy_price ─┐
  contract_item.regular_price   ├─▶ GroupBuyPriceResolver(groupBuyId, variantId)
  contract_item_option.regular_price ┘         │ salePrice = 공구가 + (옵션 정가 − 상품 정가)
                                               │ regularPrice = 옵션 정가 스냅샷
        ┌──────────────────────────────────────┼──────────────────────────────┐
        ▼                                      ▼                              ▼
  C7 상세 · 옵션 시트                  장바구니 목록 · 합계             주문서 · 주문 생성 (결제 계획서)
  (?groupBuyId)                       (cart.group_buy_id)              (cart.group_buy_id · direct.groupBuyId)
                                                                              │
                                                                       order_product.price 스냅샷
```

셀러 상품 관리(`product.regular_price`·`sale_price`·variant 재생성)는 이 그림의 어느 화살표에도 닿지 않는다. 계약 스냅샷은 검토 요청·복제 때만 갱신되고 그 둘은 체결 전 상태에서만 열린다.

## 3. 도메인 · 마이그레이션

### 3-1. `cart` 변경

| 컬럼 | 변경 |
| --- | --- |
| `group_buy_id` | BIGINT **NULL** FK → `group_buy` (`ON DELETE RESTRICT`). NULL은 백필에서 귀속을 못 정한 옛 행뿐이다 — 새로 담는 행은 항상 채운다 |
| `cart_uk` | `(user_id, variant_id)` → `(user_id, variant_id, group_buy_id)`. 같은 옵션을 다른 공구에서 담으면 두 줄이다 — 가격도 리워드 귀속도 다른 두 건이다 |

**백필** — 같은 마이그레이션에서 한다.

```sql
UPDATE cart c
   SET group_buy_id = (
     SELECT gb.group_buy_id FROM group_buy gb
       JOIN contract_item ci ON ci.contract_id = gb.contract_id
       JOIN product_variant v ON v.product_id = ci.product_id
      WHERE v.variant_id = c.variant_id
        AND gb.status IN ('PREPARING','READY','IN_PROGRESS','SUSPENSION_SCHEDULED')
      GROUP BY gb.group_buy_id
     HAVING COUNT(*) = 1 LIMIT 1)   -- 활성 공구가 정확히 1개일 때만
 WHERE c.group_buy_id IS NULL;
```

활성 공구가 둘 이상인 상품의 행은 NULL로 남고 목록에서 「마감」으로 보인다. 사용자는 삭제 뒤 게시물에서 다시 담는다. 백필 전에 대상 건수를 본다(9절 미결 ②).

| 파일 | 내용 |
| --- | --- |
| `V142__alter_cart_add_group_buy_id.sql` | 컬럼·FK·유니크 키 교체·백필 |

번호는 잠정이다. 옵션 계획서가 V139~V141, 결제 계획서가 V139~V143을 잡아 두었다 — 결제 계획서 PR 1에서 `cart.group_buy_id`(V143)를 빼고 이 문서가 든다. **먼저 머지되는 쪽이 번호를 가져간다.**

### 3-2. 엔티티 · 리포지토리

| 코드 | 변경 |
| --- | --- |
| `Cart` | `@ManyToOne GroupBuy groupBuy`(nullable). 생성자에 공구 추가. `updateVariant`는 공구를 바꾸지 않는다 — 옵션 변경은 같은 공구 안에서만이다 |
| `CartRepository` | `findByUserAndVariant` → `findByUserAndVariantAndGroupBuy`. 목록 조회에 `groupBuy`·`groupBuy.contract`를 fetch join — 그룹 머리(D-day·공구명)와 해석기 조인이 같은 쿼리를 탄다 |
| `ContractItemOptionRepository.findByGroupBuyIdAndVariantIdIn` | 옵션 계획서 5-1. 장바구니 목록은 **공구별로 variant를 묶어 한 번씩** 부른다 — 항목마다 부르면 N+1이다 |

## 4. C7 상세 · 옵션 시트

`GET /v1/common/products/{id}?groupBuyId=41` · `GET /v1/common/products/{id}/variants?variantIds=…&groupBuyId=41`

| 상황 | 가격 | 응답 `groupBuyId` |
| --- | --- | --- |
| `groupBuyId` 있음 · 공구 `isOngoing(now)` · 계약에 이 상품 있음 | 해석기. 상품 `salePrice` = 대표 옵션의 `salePrice`, `regularPrice` = 대표 옵션 정가 스냅샷, `discountRate = DiscountRate.of(그 둘)` | 41 |
| `groupBuyId` 있음 · 공구가 없거나 종료·미시작 · 계약에 없음 | 계약으로 바꾸지 않는다(지금처럼 `product.sale_price`). 상세는 열린다 | null |
| `groupBuyId` 없음 · 상품의 진행 중 공구 **1개** | 그 공구로 위 첫 줄과 같다 | 그 공구 id — 앱은 담기에 이 값을 싣는다 |
| `groupBuyId` 없음 · 0개 또는 2개 이상 | 계약으로 바꾸지 않는다 | null |

- `variants[]`에서 계약에 옵션 행이 없는 variant(옵션 계획서의 「살 수 없는 옵션」)는 `isOutOfStock: true`. C7에 「이 공구에서 판매하지 않음」을 그릴 자리가 없다.
- 「진행 중 공구 N개」는 `GroupBuyRepository.findActiveStatusesByProductIds`와 같은 조인으로 `IN_PROGRESS`·`SUSPENSION_SCHEDULED`만 센다(`GroupBuyStatus.isSelling`). 준비중 공구는 상세는 열려도(`isConnected`) 가격을 정하지 않는다 — 시작 전 공구가로 담기면 시작 전 결제가 된다.
- 상품 단위 `PriceInfo`·옵션 단위 `VariantInfo`·재고 조회 `ProductVariantStockResponse` 세 곳이 같은 `GroupBuyPrice`에서 값을 꺼낸다. `buildPriceInfo(regular, sale)` 시그니처는 그대로 두고 인자만 바꾼다.
- `groupBuyId`가 null로 돌아오는 상세에서 담기를 누르면 앱은 `groupBuyId` 없이 담기를 부르게 되고 5-1에서 400이다. 앱은 이 경우 담기 버튼 대신 「게시물에서 구매해 주세요」를 그린다(9절 미결 ③ — 앱 규칙).

## 5. 장바구니

### 5-1. 담기 · 수정

`POST /v1/user/cart` `[{ variantId, quantity, groupBuyId }]` · `PATCH /v1/user/cart/{cartItemId}` `{ variantId?, quantity? }`

| 판정 | 순서 · 결과 |
| --- | --- |
| `groupBuyId` 없음 | 400 `INVALID_INPUT_VALUE` — 「공구를 지정해 주세요」. 옛 앱은 이 배포 이후 담기가 막히므로 **앱과 같이 배포** |
| 공구 없음 · `isOngoing(now)` 아님 | `CART_ITEM_NOT_PURCHASABLE`(GROUP_BUY_CLOSED 문구) |
| 해석기 empty(계약에 이 옵션 없음) | `CART_ITEM_NOT_PURCHASABLE` — 「이 공구에서 판매하지 않는 옵션이에요」. 조작된 `groupBuyId`(다른 브랜드 공구)도 여기서 걸린다 — 계약에 그 상품이 없다 |
| 상품 구매 가능(`requirePurchasable`) · 재고 · 수량 상한 | 지금과 같다 |
| 병합 | `findByUserAndVariantAndGroupBuy`. 같은 옵션·다른 공구는 합치지 않는다 |
| 수정에서 옵션 변경 | 새 variant도 **같은 공구의 해석기**로 판정한다. 공구는 바꿀 수 없다 |

판정 순서는 「공구 → 계약 → 상품 → 재고」다. 공구가 끝났는데 재고 부족 문구가 먼저 나가면 사용자가 헛수고한다.

### 5-2. 목록 · 합계 · 배송비

`GET /v1/user/cart`

| 지점 | 변경 |
| --- | --- |
| 그룹 키 | 마켓 → **공구**(`cart.group_buy_id`). NULL 행은 마켓 키로 묶고 `isClosed: true`. 응답 `CartGroup`에 `groupBuyId`·`groupBuyNumber`·`groupBuyTitle`(계약 공구명)·`endAt`·`dDay` 추가. D-day는 `GroupBuyPostCardLoader.dDay`와 같은 식 |
| 항목 가격 `CartItem.price` | 해석기 `GroupBuyPrice` → `regularPrice`·`salePrice`·`discountRate`. `maxBenefitPrice = salePrice` |
| `lineSaleTotal`·`calculateSummary`·`buildGroupShipping`·`marketsShortOfFreeShipping` | `variant.getSalePrice()` → 해석기 값. 배송비·무료배송 기준은 여전히 마켓 설정(`Market.defaultDeliveryFee`·`freeShippingThreshold`)이고 **집계 단위만 공구**다 |
| `unavailableReason` | 앞에 두 판정 추가 — `group_buy_id` NULL 또는 공구가 `isOngoing` 아님 → `GROUP_BUY_CLOSED`; 해석기 empty → `GROUP_BUY_CLOSED`. 그 뒤 기존 상품·재고 판정 |
| 추천 상품 `RecommendedProduct.price` | 그대로 `product` 가격 — 특정 공구에 귀속되지 않은 카드다(9절 미결 ①) |

해석기 호출은 목록당 공구 수만큼이다 — `carts`를 공구별로 묶어 `resolveByProduct`가 아니라 `findByGroupBuyIdAndVariantIdIn(groupBuyId, variantIds)`로 한 번에 읽고 `Map<variantId, GroupBuyPrice>`를 돌려 쓴다.

### 5-3. 가격이 바뀐 것을 사용자에게 알리는가

알리지 않는다. 계약은 체결 뒤 불변이라 **담은 뒤 가격이 바뀌는 경우가 없다.** 지금 코드에 있던 「담을 때와 다른 가격」 문제는 원천을 옮기는 것으로 사라진다. 공구 연장(`end_at` 변경)도 가격을 건드리지 않는다.

## 6. 결제 계획서와의 접점

| 결제 계획서 | 이 문서 이후 |
| --- | --- |
| 0절 「주문 단가」 · 9-1 ① | 그대로 — 단가 = `GroupBuyPrice.salePrice`, 정가 = `GroupBuyPrice.regularPrice` |
| PR 1 `cart.group_buy_id`(V143) | **이 문서 3-1로 이동.** 결제 PR 1에서 뺀다 |
| PR 2 귀속 경로(C7 에코·담기 `groupBuyId`·그룹 키·D-day) | **이 문서 4·5절로 이동.** 결제 PR 2는 없어진다 |
| 7-1 `OrderPricingCalculator` | `CartService`의 합계 코드를 옮길 때 이미 해석기를 쓰고 있다. 주문서(`checkout`)는 장바구니 진입이면 `cart.group_buy_id`, 바로 구매면 `direct.groupBuyId`로 같은 맵을 만든다 |
| 4-6 「`groupBuyId` 없음 · 진행 중 공구 2개 이상 → 판매는 막지 않는다」 | **재검토 필요.** 공구가 둘이면 단가도 둘이라 귀속 미정 주문은 단가 미정 주문이다. 담기가 `groupBuyId`를 필수로 받으므로 장바구니 경로에서는 생기지 않고, 바로 구매도 필수로 맞추길 권한다(9절 미결 ④) |
| 3-2 `order_product.regular_price` | `GroupBuyPrice.regularPrice`(옵션 정가 스냅샷) |

## 7. 「상품 가격을 고쳐도 변하지 않는다」를 지키는 것

| 층 | 무엇이 지키나 | 확인 |
| --- | --- | --- |
| 계약 스냅샷 | 체결 이후 `contract_item`·`contract_item_option`의 정가·공구가를 쓰는 코드가 없다 | 통합 테스트 — 체결된 계약의 상품 정가·옵션 정가를 바꾼 뒤 계약 상세·해석기 값이 그대로 |

## 9. 미결 사항 · 작업 순서

### 9-1. 미결

1. **공구에 귀속되지 않는 화면의 가격.** 상품 검색 목록(`/v1/common/products`)·C1 홈·장바구니 추천·팔로잉 피드의 상품 카드는 `product.sale_price`(정가)를 보여 준다. 공구 게시물 카드만 계약 공구가다. 카드에 「공구가부터」를 보이려면 「상품의 진행 중 공구 중 최저 공구가」 같은 규칙이 필요한데 기획이 없다. 이번 범위 밖으로 두고 정가 표시를 유지한다.
2. **백필 대상 건수.** `SELECT COUNT(*) FROM cart` 및 활성 공구 2개 이상 상품에 걸린 행 수를 운영 DB에서 본 뒤 배포한다. NULL로 남는 행이 많으면 앱에 「다시 담아 주세요」 안내가 필요하다.
3. **앱 측 규칙.** ⓐ 담기·바로 구매에 `groupBuyId` 필수 ⓑ C7 응답 `groupBuyId`가 null이면 담기 대신 「게시물에서 구매」 안내 ⓒ 장바구니 그룹 머리에 공구명·D-day. 서버만으로 막을 수 없는 UX다.
4. **결제 계획서 4-6의 귀속 미정 주문.** 6절 — 바로 구매도 `groupBuyId` 필수로 맞추고 `attribution_unresolved` 경로를 없애길 권한다. 결제 계획서 수정 시 반영.
5. **공구 연장·직권 중단 통지 중(`SUSPENSION_SCHEDULED`)의 담기.** `isSelling`이 참이라 담긴다. 명세가 「통지 뒤에도 판매는 그대로」라 맞지만, 중단 집행 시각 직전 담긴 행은 결제에서 마감으로 걸린다(결제 4-6 「주문 뒤 30분」과는 다른 경우 — 주문 전이다). 지금 규칙 그대로 두고 문구만 확인.
