## 1. 범위와 판정 기준

- 대상: 정산 공통 도메인(생성 · 산식 · 확정 · 3자 분배 · 조정 협의 · 증빙 · 차감 · 배치 7종) + 서피스 4곳의 엔드포인트 **35개** — 어드민 `/v1/admin/settlements` 11 · 파트너 `/v1/seller/settlements` 6 + 조정 6 · 스튜디오 `/v1/creator/settlements` 9 + 조정 6 · 어드민 20b 이슈 탭(기존 스레드 엔드포인트 확장 + `by-thread`). 연계 화면(공구 상세 · 06a · 06c)의 정산 블록을 함께 다룬다.
- 돈은 **PG 3자 분배**로 나가고 코드에는 포트만 있다. 테스트 · QA 환경은 `settlement.payout.mode=SIMULATED`(즉시 `PAID`)이고, 결과 미확인(`REQUESTED`) · 분배 실패는 **가짜 게이트웨이**(`FakeSettlementPayoutGateway`)로 재현한다. `PG` 모드 어댑터는 미구현이라 운영 프로필은 기동되지 않는다(13절 A-1).
- 아래 케이스는 **테스트 명세**이며 통과 기록이 아니다. 알림 발송 · PG 실연동 · 운영자 열람 로그처럼 모듈이 아직 없는 동작은 13절에 적고, 지금 호출되지 않는다는 이유로 통과 처리하지 않는다.
- 시각은 서버 `Asia/Seoul`. 영업일 = 주말 제외 + `business_holiday` 테이블(`BusinessCalendar.replaceRegisteredHolidays` 로 테스트에서 고정). 배치는 `application-test` 프로필에서 전부 꺼져 있고 서비스 · 배치 클래스의 `tick()` · `run(now)` 를 **직접 호출**한다 — 시각을 인자로 받는 메서드를 쓰고 `LocalDateTime.now()` 에 기대지 않는다.
- 세 서피스(어드민 · 파트너 · 스튜디오)는 **같은 `settlement` 행**을 읽는다. 한 케이스에서 쓰기가 일어나면 세 서피스의 숫자가 같은지 반드시 교차 확인한다(공통 확인 방법 2).

### 1-3. 공통 확인 방법

1. 쓰기 한 번마다 **DB 행 · 이력 · 세 서피스 응답**을 같이 본다. 정산 행(`settlement.status · confirmed_at · payout_due_date · 금액 컬럼`) · 수취자 3행(`settlement_payout.status · due_date · attempt · 계좌 스냅샷`) · 증빙 행 · 차감 행 · `settlement_history`.
2. 숫자는 어드민 07b `breakdown` ↔ 파트너 `breakdown.brandPayoutAmount` ↔ 스튜디오 `breakdown.creatorPayoutAmount` 가 같은 행에서 나왔는지 본다. 07b `payouts.check.balanced = true`(검산)가 기준이다.
3. 버튼 노출은 서버 플래그다 — 어드민 `actions { canRedistribute, canVerifyInvoice, canRegisterBrandInvoice, canDownloadStatement }` · 파트너 `actions { canRequestAdjustment, canRespondAdjustment, canDownloadStatement, canDownloadTaxInvoice }` · 스튜디오 `review.canRequestAdjustment · items.downloadAvailable · withholding.receiptAvailable` · 조정 `permissions { canAccept, canReject, canCounter, canSend }`. `false` 면 **숨김/비활성**이고 커맨드는 다시 검사한다.
4. 실패 요청은 HTTP 상태 + 응답 `code` 를 보고, 정산 · 수취자 · 증빙 · 협의 · 스레드 · 카드 · PG 지시 · 파일 저장 건수에 **부수 효과가 없는지** 본다. **주의** — `INVALID_INPUT_VALUE` 의 응답 `code` 는 `INVALID_INPUT` 이다(enum 이름이 아니다). 그 밖의 정산 코드는 enum 이름 = 응답 `code`.
5. 돈이 움직이는 케이스는 매번 **PG 지시 횟수 · 지시 행 수 · `settlement_payout.pg_reference / fail_code / attempt` · `paid_at` · 공구 `status`** 를 같이 본다. 같은 행에 지시가 두 번 가면 실패다.
6. 이력의 주체: 생성 · 확정 · 지시 · 차감은 `SYSTEM`, PG 결과는 `PG`, 운영자 조치(재분배 · 대조 · 발행본 등록)는 `ADMIN`(+ 이름), 당사자 조치(조정 요청 · 응답 · 승인번호 제출)는 `SELLER · CREATOR`. 「정산 확정 · 김운영」 같은 운영자 확정 이력은 **있으면 안 된다**(12절 #1).
7. 알림(`SettlementNotifier`)은 스텁이다 — **발송 여부를 판정에 넣지 않는다**. 훅 호출 여부만 필요하면 스파이로 본다.
8. 시안 · 설계서 · 코드가 충돌하면 13절에 기록하고 어느 쪽으로도 임의 통과시키지 않는다.
