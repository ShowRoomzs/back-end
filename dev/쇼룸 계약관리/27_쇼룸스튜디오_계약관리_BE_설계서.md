## 0. 먼저 정한 6가지

### 0-1. 스튜디오는 **읽기 서피스**다 — 쓰기 API가 셋뿐이다

§27-1이 다섯 가지 차이를 말하지만 백엔드에서 남는 결론은 하나다. **인플루언서가 계약 객체에 쓸 수 있는 값은 세 가지밖에 없다.**

| 쓰기 | 바꾸는 값 | 상태 전이 |
| --- | --- | --- |
| 거절 | `close_*` 4종 | `SIGNING` → `DECLINED` |
| 서명 안내 다시 받기 | `contract_resend_request` 1행 | **없음** |
| 상세 최초 진입 | `creator_viewed_at` | **없음** |

그 외 전부 — 조건 수정 · 서명 · 새 계약 작성 · 계약 취소 · 지급 완료 기록 · 재작성 — 은 **엔드포인트를 만들지 않는다.** §27-4가 "화면 어디에도 조건 입력 필드를 두지 않는다"로 못박았고, 없는 화면에 대응하는 API가 열려 있으면 **화면이 보장한 제약을 서버가 배신**한다.

그래서 이 설계서에는 **하드 검증 H1~H8도, 경고 W1~W6도 없다.** 검증할 입력값이 없다.

### 0-2. **가시성 규칙이 이 설계서의 본체**다

§27-1 #1 — "스튜디오가 볼 수 있는 최초 상태는 서명 진행중"이고 작성중 · 검토 대기 · 검토 반려는 **브랜드 전용**이다.

그런데 이 계약들은 **`creator_id`가 이미 채워져 있다.** 브랜드가 작성중 화면에서 계약 상대를 고르는 순간 박힌다(§25-5-1). 즉 **`WHERE creator_id = :me`만으로 조회하면 브랜드가 아직 보내지도 않은 계약이 인플루언서 목록에 뜬다.** 검토 반려된 계약 — 운영자가 문제를 지적해 브랜드에게 되돌린 계약 — 까지 보인다.

**가시성은 필터가 아니라 권한이다.** 조회·조작 전 경로가 예외 없이 같은 판정을 통과한다(1-1).

### 0-3. 「내 서명 완료」는 **우리가 쓰는 값이 아니다**

S11(내 서명 완료 모달)은 화면상 인플루언서의 행위 직후에 뜨지만, `creator_signed_at`을 쓰는 주체는 **어드민**이다(§25-3 #2 · 파트너 설계 전이 7). 모두싸인 API가 없어 서명 완료를 실시간으로 받지 못하기 때문이다.

| 우리가 만들지 않는 것 | 실제 경로 |
| --- | --- |
| `POST /contracts/{id}/sign` | 모두싸인이 메일·문자로 보낸 링크 — **우리 시스템 밖** |
| 서명 완료 콜백 수신 | 운영자가 모두싸인에서 확인 → 어드민 API로 입력 |

**그러므로 S11 모달은 서버가 띄우는 것이 아니다.** 스튜디오 화면은 서명 페이지로 나갔다가 돌아온 뒤 상세를 다시 조회하는데, 그 시점의 `creatorSignedAt`은 **아직 NULL일 가능성이 높다**(운영자가 확인하기 전이므로). 시안이 서명 카드에 「운영자 확인 시점 기준」을 박은 이유가 이것이다.

→ **서버는 S11을 위한 별도 API를 두지 않고**, FE가 서명 링크 복귀 시점에 자체적으로 띄운다. 서버가 할 일은 응답에 `signature.asOf`를 **항상 싣는 것**이다 — "방금 서명했는데 왜 반영이 안 됐지"를 화면이 스스로 해명할 수 있어야 한다.

### 0-4. 같은 계약이지만 **응답은 파트너와 다르다** — 라벨이 아니라 구성이

§27-1 #4가 "같은 값이 파트너센터에서는 내는 돈, 스튜디오에서는 받는 돈"이라고 적었다. 이것을 "FE가 라벨만 바꾸면 된다"로 읽으면 안 된다. **서버가 내리는 필드 집합 자체가 다르다.**

| 구분 | 파트너 | 스튜디오 |
| --- | --- | --- |
| `payout`(내가 받는 금액) 블록 | **없음** | **있음** — 고정 지급비 + 상품별 리워드율 + 정산 시점 + **미보증 고지** |
| `fixedFee.paidAt`(지급 완료 기록) | 쓰기 가능 | **읽기만** · 종결 3종에선 **안 내린다** |
| 브랜드 쪽 환불·정산 이력 | 해당 | **내리지 않는다** — §27-5 "내 자금이 아니다" |
| `history[]` | 전량 | **화이트리스트 필터**(6-4) |
| `permissions` | 7종 | **5종** · 교집합이 거의 없다 |

**필터링을 FE에 맡기지 않는다.** 브랜드의 내부 이력(작성중 저장 · 검토 요청 · 검토 반려 사유)이 응답 JSON에 실려 나가면, 화면에 안 그려도 **이미 유출된 것**이다. 검토 반려 사유는 운영자가 브랜드에게만 한 지적이다.

### 0-5. 종결 3종은 **주체가 다르고 서버가 내리는 값도 다르다**

§27-6의 표를 서버 관점으로 옮기면 이렇게 된다.

| 상태 | `close_actor_type` | 사유 | 스튜디오 응답 |
| --- | --- | --- | --- |
| `DECLINED` | `CREATOR` | **내가 입력** | 사유 카드 노출 · 「내가 끝낸 계약」 |
| `EXPIRED` | `ADMIN` | **없음**(NULL) | 사유 카드 없음 · 재발송은 **브랜드만** |
| `CANCELED` | `SELLER` | **브랜드가 입력** | 사유 카드 노출 · 「내 조치 없음」 |

세 값 모두 `contract` 한 테이블의 같은 컬럼에 들어가고, **서버는 `closure` 블록을 그대로 내리면 된다.** 화면 문구의 주체 전환(「내가」 / 「브랜드가」)은 `closeActorType` 하나로 FE가 고른다 — 문구를 서버가 짓지 않는다.

**단, 종결 3종에서 `payout` 블록은 `null`로 내린다**(§27-6 "「내가 받는 금액」 카드는 노출하지 않는다"). 값을 내리고 FE가 숨기는 방식은, 숨기는 조건을 FE가 틀리면 **성립하지 않은 계약의 금액이 「내가 받는 금액」으로 보이는** 사고가 된다. 콘텐츠 의무(`content`)는 반대로 **그대로 내리고** `obligationAlive: false`를 함께 준다 — 카드는 남기되 "효력 없음"으로 표기하는 것이 §27-6이다.

### 0-6. 신규 테이블 **0개** · 마이그레이션 **1개**

파트너 설계 0-1이 "파트너 API만 먼저 열더라도 컬럼은 다 판다"고 한 결과, 스튜디오가 필요로 하는 컬럼은 **전부 이미 있다.**

| 스튜디오가 쓰는 값 | 이미 있는 것 |
| --- | --- |
| 받은 일시 | `signature_requested_at` |
| 내 서명 기한 | `signature_deadline_at` |
| 내 서명 · 브랜드 서명 | `creator_signed_at` · `brand_signed_at` · `signature_as_of` |
| 거절 | `closed_at` · `close_actor_type` · `close_reason_code` · `close_reason_memo` |
| 열람 기록 | `creator_viewed_at` |
| 재발송 요청 | `contract_resend_request.requester_type = 'CREATOR'` |
| 이력 | `contract_history` (`CREATOR_SIGNED` · `DECLINED` 등 이미 정의) |

**「받은 일시」를 위해 별도 컬럼을 만들지 않는다.** 서명 요청 발송 시각이 곧 도착 시각이고(시안 S3 스텝퍼: 서명 요청 발송 08.13 16:40 = 헤더 "08.13 16:40 받음"), 두 컬럼을 두면 **같은 사실이 두 곳에 기록되어 어긋날 자리**가 생긴다.

필요한 것은 인덱스 하나다 — 스튜디오 목록의 **기본 정렬이 「받은 순」**인데(시안 S1) 파트너 설계의 인덱스 5종에 `(creator_id, signature_requested_at)`이 없다. 기존 `(creator_id, status, signature_deadline_at)`은 「서명 기한순」 전용이라 이 정렬을 타지 못한다.

| 파일 | 내용 |
| --- | --- |
| `V122__add_contract_creator_received_index.sql` | `INDEX (creator_id, signature_requested_at DESC)` |

## 1. 가시성 — 「도착한 계약」의 정의

### 1-1. 판정식

```sql
creator_id = :me
AND signature_requested_at IS NOT NULL
AND status IN ('SIGNING','CONCLUSION_PENDING','CONCLUDED',
               'DECLINED','EXPIRED','CANCELED')
```

**두 조건을 모두 건다.** 상태 집합만으로도 논리적으로는 충분하다 — 전이표(파트너 설계 3-1)상 `CANCELED`는 `SIGNING`·`CONCLUSION_PENDING`에서만, `EXPIRED`는 `SIGNING`에서만 나오므로 종결 3종은 이미 서명 요청 이후다. 그럼에도 `signature_requested_at IS NOT NULL`을 함께 거는 이유는, **전이표가 나중에 늘어날 때 이 판정이 조용히 틀리는 것을 막기 위해서**다. §25-2의 [결정 필요](체결 후 해지 값)가 열려 있고, 어드민 쪽에 검토 대기 단계의 종결 경로가 하나라도 추가되면 **서명 요청도 받지 않은 계약이 인플루언서 목록에 종결 상태로 나타난다.**

`DRAFT` · `REVIEW_PENDING` · `REVIEW_REJECTED`는 **집합에 없다.** 브랜드 전용 3종이다.

**판정은 메서드 하나에 둔다** — `CreatorContractReader.requireReceived(creatorId, contractId)`. 목록·상세·거절·재발송·문서·조항 **여섯 경로가 전부 이것을 통과**하고, 리포지토리에 `findByCreatorId` 같은 **판정 없는 조회 메서드를 두지 않는다.** 한 곳만 빠져도 미발송 계약이 나간다.

### 1-2. 미도착 계약은 **403이 아니라 404**

| 상황 | 응답 |
| --- | --- |
| 남의 계약 | `404 CONTRACT_NOT_FOUND` |
| 내 `creator_id`가 박혀 있지만 **아직 도착 전**(`DRAFT`·`REVIEW_PENDING`·`REVIEW_REJECTED`) | `404 CONTRACT_NOT_FOUND` |
| 도착했으나 이미 종결 | **200** — 종결 계약도 읽을 수 있다(S7·S8·S9) |

403은 **"있는데 못 본다"**는 뜻이다. 그 응답을 주면 인플루언서가 **브랜드가 자기 앞으로 계약을 작성 중이라는 사실**을 알게 된다. 검토 반려된 계약이라면 "나한테 보내려다 운영자에게 막혔다"까지 읽힌다. 계약번호가 `CTR-YYYYMMDD-NNN`으로 추측 가능하므로(파트너 설계 1-7) **존재 여부 자체를 숨긴다.**

### 1-3. 탭 ↔ 상태 매핑 — **파트너와 다르다**

| 탭 코드 | 상태 집합 | 시안 S1 카운트 |
| --- | --- | --- |
| `ALL` | 위 6종 전체 | 8 |
| `SIGNING` | `SIGNING` | 2 |
| `CONCLUSION_PENDING` | `CONCLUSION_PENDING` | 1 |
| `CONCLUDED` | `CONCLUDED` | 2 |
| `CLOSED` | `DECLINED`, `EXPIRED`, `CANCELED` | 3 |

**파트너의 `SIGNING` 탭은 `SIGNING` + `CONCLUSION_PENDING` 묶음이지만 스튜디오는 쪼개져 있다.** 시안 S1의 탭 바에 「서명 진행중 2」와 「체결 처리 대기 1」이 **각각 서 있고** 합이 3이다. 같은 탭 코드가 두 서피스에서 다른 집합을 가리키므로, **탭 매핑 enum을 두 서피스가 공유하지 않는다** — `SellerContractTab`과 `CreatorContractTab`을 따로 둔다. 하나로 합치고 `if (surface == CREATOR)`로 갈라놓으면 어느 쪽이 기준인지 읽을 수 없다.

작성중 탭은 **코드에 존재하지 않는다.** "0건으로 표시"가 아니라 값 자체가 없다(§27-1 #1).

## 2. 목록 — `GET /v1/creator/contracts`

### 2-1. 파라미터

| 이름 | 값 | 기본 |
| --- | --- | --- |
| `tab` | 1-3의 5종 | `ALL` |
| `keyword` | **공구명 + 브랜드명** | — |
| `sort` | `RECEIVED_DESC` · `DEADLINE_ASC` · `START_AT_ASC` | `RECEIVED_DESC` |
| `PagingRequest` | 20 / 50 | 20 |

- `RECEIVED_DESC`(받은 순) = `signature_requested_at DESC` — **파트너의 `CREATED_DESC`와 다른 컬럼**이다. §27-1 #3 "「생성일」 → 「내 서명 기한」. 생성일은 브랜드의 사정이다"가 정렬에도 그대로 적용된다. **스튜디오 응답에는 `createdAt`을 아예 싣지 않는다.**
- `DEADLINE_ASC`(서명 기한순) = `signature_deadline_at ASC` · **NULL은 뒤로**. 종결 계약은 기한이 의미 없다.
- `keyword`의 브랜드명은 **스냅샷이 아니라 `market` 조인**으로 본다. 계약에는 브랜드명 스냅샷 컬럼이 없다(상품명·정가만 스냅샷 — 파트너 설계 0-5).

### 2-2. 「내 서명 기한」 열 — 서버가 **표시 종류**를 내린다

시안 S1의 이 열은 한 종류가 아니다.

| 행 | 표시 | 실제 조건 |
| --- | --- | --- |
| 여름 수분 세럼 | `2026.08.21 23:55` (경고색) | `SIGNING` · 내 서명 없음 |
| 가을 앰플 | `내 서명 완료` | `SIGNING` · 내 서명 있음 |
| 퓨어랩 립밤 | `양측 서명 완료` | `CONCLUSION_PENDING` |
| 글로우 크림 · 여름 미스트 | `서명 완료` | `CONCLUDED` |
| 봄 클렌저 · 클렌징 오일 | `—` | `DECLINED` · `CANCELED` |
| 수분 토너 | `기한 경과` | `EXPIRED` |

여섯 갈래가 **상태 × 서명 조합**으로 갈린다. 파트너 설계가 `entryMode` · `statusTone`을 서버가 내려준 것과 같은 이유로 — **FE가 이 표를 복제하면 서버 판정과 어긋난다** — 서버가 판정해 내린다.

```json
"deadline": { "type": "DEADLINE", "deadlineAt": "2026-08-21T23:55:00", "tone": "warning" }
```

| `type` | 의미 |
| --- | --- |
| `DEADLINE` | 기한 날짜를 그린다 (`deadlineAt` 필수) |
| `MY_SIGNED` | 「내 서명 완료」 |
| `BOTH_SIGNED` | 「양측 서명 완료」 |
| `SIGNED` | 「서명 완료」(체결완료) |
| `PASSED` | 「기한 경과」(만료) |
| `NONE` | 「—」 |

**`tone`만 서버가 주고 문구는 FE가 고른다.** 파트너 설계 4-1의 "서버가 `(공구명 미입력)`을 지어내지 않는다"와 같은 선이다 — **표시 문자열이 아니라 판정 결과**를 내린다.

**`tone`은 `type = DEADLINE`일 때만 `warning`이 될 수 있다.** 기한이 임박했다는 사실은 내 서명이 남아 있을 때만 의미가 있고, 시안이 "기한이 지나면 **만료(중립 종결)**이지 부정 결과 확정이 아니므로 위험색을 쓰지 않는다"고 적었으므로 **`danger`는 이 열에 존재하지 않는다.**

> ⚠️ **임박 임계값이 미정 — 미결 #1.** 시안은 첫 행만 경고색이고 기준을 적지 않았다. §28-8 D #9(서명 기한 임박 알림 D-3 · D-1)가 확정되면 **알림 시점과 같은 값**을 써야 한다 — 알림이 D-3에 오는데 색은 D-1에 바뀌면 둘 중 하나가 거짓말이 된다. 확정 전까지 **D-3 기준으로 집행**하고 상수를 한 곳에 둔다.

### 2-3. 목록 항목

```
contractId · contractNumber · title · brandName · itemCount
startAt · endAt · receivedAt
status · statusLabel · statusTone
deadline{ type, deadlineAt, tone }
```

- `entryMode`는 **없다.** 스튜디오에 작성 모드가 없으므로 진입은 항상 상세다(§27-1 #2). 행 전체 클릭이고 관리 열도 없다.
- `title`은 항상 값이 있다 — 공구명은 검토 요청 시 필수 검증을 통과했다(파트너 설계 2-2). 파트너 목록의 `(공구명 미입력)` 문제는 스튜디오에 도달하지 않는다.

### 2-4. 빈 상태(S2)는 서버가 구분하지 않는다

S2는 "받은 계약이 없습니다 + 연결·소통 안내"인데, **주 CTA가 없으므로 서버가 내려야 할 추가 데이터가 없다**(§27-1 #2). `totalCount = 0`이면 FE가 그린다. 연결코드 안내는 기존 `GET /v1/creator/connections/code`가 이미 있다 — 계약 API가 연결코드를 함께 내리지 않는다.

### 2-5. 이전/다음 이동

시안 상세 헤더에 `[‹ 이전] [다음 ›]`이 있다. 이 두 건은 **현재 목록의 정렬·필터 안에서의 이웃**이므로, 상세 API가 목록 조건을 모른 채로는 계산할 수 없다.

→ `GET /v1/creator/contracts/{id}`가 `tab` · `keyword` · `sort`를 **선택 쿼리 파라미터로 받아** `prevContractId` · `nextContractId`를 함께 내린다. 파라미터가 없으면 두 값은 `null`이고 FE는 버튼을 비활성한다.

목록 전체를 다시 조회하지 않는다 — 정렬 키 기준 **앞뒤 1건씩만** 뽑는 쿼리 두 방이면 된다.

## 3. 요약 — `GET /v1/creator/contracts/summary`

```json
{ "tabCounts": { "ALL": 8, "SIGNING": 2, "CONCLUSION_PENDING": 1,
                 "CONCLUDED": 2, "CLOSED": 3 },
  "actionRequiredCount": 1 }
```

### 3-1. `actionRequiredCount` — **파트너와 정의가 다르다**

§27 최상단: GNB #3 계약 관리 **배지 = 내 서명이 필요한 계약 건수**. 목록 헤더의 「총 8건 · 내 서명이 필요한 계약 1건」도 같은 값이다.

```sql
status = 'SIGNING' AND creator_signed_at IS NULL
```

**`brand_signed_at`을 조건에 넣지 않는다.** 시안 S1에서 서명 진행중 2건 중 배지는 1이고, 세지 않은 나머지 1건은 「내 서명 완료」 행이다 — 즉 **브랜드 서명 여부와 무관하게 내 서명만 남았으면 센다.**

이것이 §27-2의 핵심이다. **"S3a는 「내 차례」가 아니라 「내 몫이 남은 것」이다 — 순서가 아니라 각자 한다."** S3(양측 미서명)에서도 내 몫은 똑같이 남아 있다. 파트너가 B4c(상대만 서명함) **하나만** 배지에 넣은 것과 반대인데, 대칭이 깨져서가 아니라 **파트너 쪽 시안에 「상대가 서명하면 내가 서명한다」는 순서 감각이 남아 있었고 스튜디오 rev.2가 그것을 명시적으로 폐기**했기 때문이다(§27-2 "rev.5에서 서명 순서가 사라졌다").

| 넣지 않는 것 | 근거 |
| --- | --- |
| `SIGNING` AND `creator_signed_at IS NOT NULL` (S3b) | §27-2 "내 할 일이 없고 되돌릴 수도 없어" |
| `CONCLUSION_PENDING` (S3c) | 운영자 대기 — 내가 할 수 있는 일이 없다 |
| `CONCLUDED` · 종결 3종 | 조치 아님 |

### 3-2. 목록과 분리한다

파트너 설계 4-4와 같은 이유 — GNB 배지는 계약 화면 밖에서도 폴링된다. 다만 스튜디오 쪽이 더 중요하다: **배지가 가리키는 것이 「기한이 있는 내 조치」**라서, 계약 화면에 들어오지 않는 인플루언서가 이 숫자만 보고 움직인다. 놓치면 만료다.

## 4. 상세 — `GET /v1/creator/contracts/{id}`

### 4-1. 화면 8종이 응답 하나를 쓴다

S3 · S3a · S3b · S3c · S6 · S7 · S8 · S9 — **분기는 FE가 값으로 고른다.** 서버가 `viewPhase: "S3a"` 같은 값을 만들지 않는다. §25-2가 「서명 진행중을 쪼개지 않는다」고 한 이유가 그대로 적용된다 — 조합을 값으로 만들면 조합이 늘 때마다 값이 는다.

FE의 분기 근거는 두 필드다.

| 화면 | `status` | `brandSignedAt` | `creatorSignedAt` |
| --- | --- | --- | --- |
| S3 | `SIGNING` | NULL | NULL |
| S3a | `SIGNING` | **있음** | NULL |
| S3b | `SIGNING` | NULL | **있음** |
| S3c | `CONCLUSION_PENDING` | 있음 | 있음 |

> 「브랜드도 나도 서명함」인데 상태가 아직 `SIGNING`인 조합이 **실재할 수 있다.** 운영자가 두 번째 서명을 체크하는 시점과 상태를 `CONCLUSION_PENDING`으로 올리는 시점이 같은 트랜잭션이 아니면 생긴다. **어드민 API에서 두 체크가 모두 차면 같은 트랜잭션에서 상태를 올리도록** 못박는다(파트너 설계 전이 7). 스튜디오 FE는 이 조합을 S3c로 그리면 되지만, 서버가 보장하는 편이 낫다.

### 4-2. 응답 구조

```
contract     번호 · 공구명 · 상태(3필드) · 기간 · 일수 · receivedAt
             brand{ marketId, name, threadId }
stepper      4단 — reviewApprovedAt · signatureRequestedAt
             · signedCount(0~2) · concludedAt
signature    deadlineAt · brandSignedAt · creatorSignedAt · asOf
payout       고정 지급비 + 상품별 리워드율 + 정산 시점 + 미보증 고지   ← 스튜디오 전용
content      feed/reels/story · dueDate · secondaryUse · preReview · note
             · obligationAlive
items[]      상품명 · 정가 · 공구가 · myRewardRate · 예상리워드 · brandSupplyQuantity
fixedFee     amount · trigger · triggerLabel · paymentState
settlement   platformFeeRate=2 · pgFeeRate=null · withholdingType
closure      closedAt · actorType · reasonCode · reasonLabel · memo
groupBuy     groupBuyId · 생성 여부
documents[]  type · downloadUrl            ← CONCLUDED에서만 비어 있지 않다
permissions  canDecline · canRequestResend · canOpenThread
             · canDownloadDocuments · canOpenGroupBuy
history[]    화이트리스트 필터 적용(6-4)
navigation   prevContractId · nextContractId
```

**`items[]`의 필드명을 스튜디오 관점으로 바꾼다** — `myRewardRate` · `brandSupplyQuantity`. §25-5-3의 스튜디오 라벨 열이 「내 리워드율」 · 「브랜드 준비 물량」이다. 값은 같지만 **응답 DTO를 파트너와 공유하지 않는다** — 공유하면 언젠가 파트너 전용 필드가 하나 붙고 그게 스튜디오로 샌다.

**`review` 블록이 없다.** 검토 요청 시각 · 승인 시각 · **반려 사유**가 거기 들어 있다. 스튜디오는 스텝퍼의 「운영자 검토 통과」에 `reviewApprovedAt` 하나만 필요하므로 `stepper`로 옮기고 **나머지는 내리지 않는다.**

### 4-3. `payout` — 「내가 받는 금액」

§27-1 #4가 이 카드와 「내가 해야 할 일」을 **상품 항목보다 위**에 두라고 한 이유는 "서명 여부를 판단하는 근거가 그 둘"이기 때문이다. 순서는 FE가 그리지만, **서버는 이 블록을 상태에 따라 통째로 `null`로 만든다**(0-5).

```json
"payout": {
  "fixedFeeAmount": 1200000,
  "fixedFeeTrigger": "POST_REGISTERED",
  "fixedFeeTriggerLabel": "공구 게시물 등록 후",
  "rewardRates": [ { "productName": "수분진정 세럼", "rate": 15.0 } ],
  "settlementTiming": "GROUP_BUY_ENDED",
  "platformGuaranteed": false,
  "disputeChannel": { "threadId": 4012 }
}
```

| 필드 | 근거 |
| --- | --- |
| `platformGuaranteed: false` | §27-5 미보증 고지 · §25-5-4 "플랫폼이 지급을 확인하거나 보증하지 않는다" |
| `disputeChannel.threadId` | "미지급 시 **이슈 스레드 · 운영자 중재 · 계약서가 근거**" — 문구만 두면 인플루언서가 어디로 가야 하는지 모른다. **스레드로 바로 가는 id**를 내린다 |
| 노출 시점 | `SIGNING`부터. §27-5 "서명 전에 알아야 할 사실이라 서명 진행중 화면부터" |

`platformGuaranteed`를 상수 `false`로 내리는 것이 낭비처럼 보이지만, **MVP 전제가 바뀌면(플랫폼 중개 도입) 이 한 필드로 화면이 갈린다.** 문구를 FE에 하드코딩하면 그날 스튜디오 · 파트너 · 어드민 세 곳을 고쳐야 한다.

**선결제 관련 필드는 응답에 존재하지 않는다** — §27-5 "rev.6에서 플랫폼 미중개가 확정돼 전부 지웠다". 테이블에도 없다(파트너 설계 1-1).

**실지급액은 계산하지 않는다**(§25-5-6). `withholdingType`만 내리고(`Creator.businessType` → `INDIVIDUAL`이면 `WITHHOLDING_3_3`, `BUSINESS`면 `TAX_INVOICE`) 금액 계산은 정산 소관이다. 스튜디오는 이 값이 파트너보다 중요하다 — **세후 얼마를 받는지가 이 사람의 실제 관심사**인데, 세무가 확정되기 전에 숫자를 지어내면 그 숫자로 서명을 결정하게 된다.

### 4-4. `fixedFee.paymentState` — 「지급 전」을 못박는 자리

§27-5가 "체결완료 = **지급 전**임을 상태 카드에 못박는다 — 체결을 입금으로 오해하면 분쟁이 된다"고 했고, 종결 3종은 "**지급 없음**"으로만 표기한다.

| `paymentState` | 조건 |
| --- | --- |
| `NOT_YET` | `CONCLUDED` · `fixed_fee_paid_at IS NULL` |
| `RECORDED_BY_BRAND` | `CONCLUDED` · `fixed_fee_paid_at IS NOT NULL` |
| `NONE` | 종결 3종 — **계약이 성립하지 않아 지급 없음** |

**`RECORDED_BY_BRAND`라는 이름을 쓴 이유** — 이 값은 브랜드가 `[지급 완료 기록]`을 누른 사실일 뿐 **입금 사실이 아니다.** 플랫폼은 지급을 확인하지 않는다(§25-5-4). 서버가 이 값을 `PAID`로 이름 붙이면 스튜디오 화면이 「지급 완료」로 그리고, **실제로 안 들어온 돈이 들어온 것으로 표시**된다. 그 상태에서 분쟁이 나면 화면이 브랜드 편에서 거짓말을 한 셈이 된다.

**`fixed_fee_paid_at` 원시값은 스튜디오에 내리지 않는다** — 상태 enum만 내린다.

> ⚠️ 시안 S6는 이 값을 「지급 전」으로만 그리고 **브랜드 기록이 반영된 상태를 그리지 않았다.** 화면이 없는 상태값이라 FE 확정이 필요하다 — 미결 #4.

### 4-5. 서명 카드와 기준 시각

```json
"signature": {
  "deadlineAt": "2026-08-21T23:55:00",
  "brandSignedAt": null,
  "creatorSignedAt": null,
  "asOf": "2026-08-13T17:00:00"
}
```

**`asOf`는 `SIGNING` · `CONCLUSION_PENDING`에서 항상 값이 있어야 한다.** 어드민이 서명 현황을 갱신할 때 `signature_as_of`를 필수로 받지만, **서명 요청 발송 직후 아직 한 번도 갱신하지 않은 계약은 NULL**이다. 이때는 **`signature_requested_at`으로 대체**해 내린다 — 「발송 시점 기준, 아직 확인 전」이 사실이고, NULL을 내리면 화면이 기준 시각 줄을 통째로 못 그려 §25-3 #2의 해명 장치가 사라진다. 그 줄이 없으면 방금 서명한 사람이 "왜 반영이 안 됐지"로 오해한다.

**서명 링크는 응답에 없다.** 우리가 갖고 있지 않다(§25-3 #1). 대기 문구의 「메일·문자로 받은 전자서명 링크」는 고정 문구이고, 서버가 내릴 URL이 없다.

### 4-6. `permissions` — 스튜디오 5종

| 키 | 조건 |
| --- | --- |
| `canDecline` | `status = SIGNING` **AND** `creator_signed_at IS NULL` |
| `canRequestResend` | `status = SIGNING` **AND** `creator_signed_at IS NULL` |
| `canOpenThread` | 연결이 살아 있고 스레드가 있으면 **항상** — 종결 3종 포함 |
| `canDownloadDocuments` | `status = CONCLUDED` AND 문서 2종 존재 |
| `canOpenGroupBuy` | `group_buy_id IS NOT NULL` |

**`canDecline`과 `canRequestResend`의 조건이 같다.** 둘 다 "내 서명이 아직 남아 있을 때"다 — S3b에서 액션이 `[스레드에서 협의하기]` 하나로 줄어드는 것이 §27-2가 명시한 규칙이고, 재발송도 이미 서명한 사람에게는 보낼 이유가 없다.

**`canOpenThread`가 종결 후에도 `true`인 것이 §27-1 #5의 결론**이다 — "회복 경로는 `[스레드에서 협의하기]` 하나". S7·S8·S9 셋 다 이 버튼 하나만 남는다. 연결이 끊겼으면(`ConnectionStatus != CONNECTED`) `false`이고 FE는 버튼을 숨긴다. 시안 S7의 「연결 상태: 연결됨 유지」가 이 판정의 표시다.

**`canCreateGroupBuy`는 없다.** 공구를 만드는 쪽은 브랜드다(시안 S6 「연결된 공구: 브랜드 생성 대기」). `canOpenGroupBuy`는 이미 생성된 공구로 **이동**할 뿐이다.

**`canSign`도 없다.** 누를 대상이 없는 버튼은 만들지 않는다(§25-3 #1).

## 5. 쓰기 3종

### 5-1. 거절 — `POST /v1/creator/contracts/{id}/decline`

```json
{ "reasonCode": "CONDITION_RENEGOTIATION", "memo": "..." }
```

**전이**: `SIGNING` → `DECLINED` · `close_actor_type = CREATOR`

**조건부 UPDATE에 서명 조건을 함께 건다.**

```sql
UPDATE contract
   SET status='DECLINED', closed_at=:now, close_actor_type='CREATOR',
       close_reason_code=:code, close_reason_memo=:memo
 WHERE contract_id=:cid AND creator_id=:me
   AND status='SIGNING' AND creator_signed_at IS NULL
```

`rowsAffected = 0`이면 `409`. **`creator_signed_at IS NULL`이 WHERE에 있어야 하는 이유** — §27-2 S3b의 "되돌릴 수도 없어(서명 후 거절 불가)"가 화면에서는 버튼 부재로 표현되지만, **내가 거절 모달을 열어 둔 사이에 운영자가 내 서명을 체크**하면 화면은 여전히 열려 있다. 서명한 계약이 거절로 종결되면 **모두싸인에는 내 서명이 남고 우리 시스템은 거절인** 상태가 된다.

| 항목 | 규칙 |
| --- | --- |
| 허용 상태 | `SIGNING` **만** — `CONCLUSION_PENDING`은 **409**(양측 서명이 끝났다) |
| 사유 구분 | **필수** (5종) |
| 메모 | **선택** — 시안 S5에 `*` 없음 |
| 부수 효과 | 이력 `DECLINED` append · **브랜드에 통지** · 연결은 **건드리지 않는다** |

**거절 사유 5종** (`ContractDeclineReason`)

| enum | 화면 |
| --- | --- |
| `CONDITION_RENEGOTIATION` | 조건 재협의 필요 |
| `SCHEDULE_MISMATCH` | 일정이 맞지 않음 |
| `NOT_FIT_SHOWROOM` | 상품이 내 쇼룸과 맞지 않음 |
| `CONTENT_BURDEN` | 콘텐츠 의무가 과함 |
| `ETC` | 기타 |

**브랜드의 취소 사유 5종과 별도 enum이다.** 값이 하나도 겹치지 않고(취소는 재고 부족 · 일정 변경 · 협의 중단 …), 한 enum에 합치면 **거절 모달에 브랜드용 선택지가 뜰 수 있는 구조**가 된다. `close_reason_code` 컬럼은 공유하되 **해석은 `close_actor_type`이 정한다** — 이것이 0-5에서 `closeActorType`을 반드시 내리는 또 하나의 이유다.

**사유는 브랜드에게 그대로 전달된다**(시안 S5 고지). 서버가 가공하지 않는다.

> ⚠️ **`ETC` + 메모 없음이 허용된다** — 브랜드는 "기타"만 받고 아무것도 알지 못한 채 재발송 여부를 판단해야 한다. 파트너 취소는 `ETC`면 메모를 필수로 걸었는데(파트너 설계 4-3) 여기는 시안에 `*`가 없어 **시안을 따른다.** 대칭이 깨진 지점이라 §28-8 D #10(거절 사유 확정)에서 함께 정리한다 — 미결 #2.

**연결을 끊지 않는다.** 시안 S7 "거절은 **이 계약만** 종결시킵니다 — 연결이 끊기지는 않습니다". 거절 서비스가 `Connection`을 쓰기 대상으로 참조하지 않게 한다.

### 5-2. 재발송 요청 — `POST /v1/creator/contracts/{id}/resend-request`

- 상태 **불변**. `contract_resend_request` 한 행이 생길 뿐이다(`requester_type = 'CREATOR'`).
- 허용 조건은 `permissions.canRequestResend`와 같다. 그 밖은 `409`.
- **중복 억제**: 미처리(`handled_at IS NULL`) 요청이 이미 있으면 새 행을 만들지 않고 기존 요청을 `200`으로 돌려준다(파트너 설계 3-6과 같은 규칙). 횟수 제한 정책은 §28-8 D #7로 미정이다.
- **실제 재발송은 우리가 하지 않는다.** 운영자가 모두싸인에서 한다(§25-3 #1). 응답 문구가 「재발송했습니다」가 되면 안 된다 — **「요청했습니다」**다. 이 구분이 흐려지면 인플루언서가 오지 않을 메일을 기다린다.

### 5-3. 열람 기록 — 별도 API를 만들지 않는다

`creator_viewed_at`은 파트너 B7(만료 상세)의 **"계약서 열람 기록 없음"**의 근거다. 만료에는 상대 메모가 없어 그 공백을 이 사실이 메운다(파트너 설계 4-5).

| 안 | 문제 |
| --- | --- |
| `POST /{id}/view`를 FE가 호출 | FE가 호출을 빠뜨리거나 순서를 바꾸면 **브랜드 화면이 「열람 안 함」으로 거짓말**을 한다. 열람 여부는 FE가 선택할 사실이 아니다 |
| **상세 `GET`의 부수 효과** ← 채택 | GET이 쓰기를 한다는 점이 걸리지만, **최초 1회 CAS**라 멱등이다 |

```sql
UPDATE contract SET creator_viewed_at = :now
 WHERE contract_id = :cid AND creator_viewed_at IS NULL
```

- `REQUIRES_NEW` 트랜잭션으로 분리하고 **실패해도 조회 응답을 깨지 않는다.** 열람 기록 때문에 계약서가 안 열리면 본말이 뒤집힌다.
- `contract_history`에는 **남기지 않는다.** 이력 카드에 「상대가 열람함」이 뜨면 브랜드가 인플루언서의 접속을 들여다보는 화면이 된다. 시안 어디에도 그 항목이 없다. 브랜드가 보는 것은 **열람 여부 한 줄**(B7)뿐이다.

## 6. 응답에서 **덜어내는 것**

### 6-1. 브랜드 내부 정보

| 필드 | 이유 |
| --- | --- |
| `createdAt`(작성일) | §27-1 #3 "생성일은 브랜드의 사정이다" |
| `reviewRequestedAt` · `rejectReasonCode` · `rejectReasonDetail` | 운영자가 브랜드에게만 한 지적 |
| `warningFlags`(W1~W6) | 운영자 전달용(§25-6) · 인플루언서에게 "이 계약은 리워드율이 높다"를 알릴 근거가 없다 |
| `sourceContractId`(재작성 출처) | 브랜드의 내부 이력 |
| `fixedFeeNoticeAgreedAt` | 브랜드가 고지를 확인한 시각 |
| `version`(낙관적 락) | 스튜디오는 계약을 수정하지 않는다 |

### 6-2. 금액 중 「내 자금이 아닌 것」

§27-5 종결 3종 — **"브랜드 쪽 환불 이력은 표시하지 않는다"**. MVP에 선결제가 폐기되어 실제 환불 데이터는 없지만(§25-5-4), **정산·환불 모듈이 붙을 때 계약 상세 응답에 얹지 않는다**는 규칙을 지금 적어 둔다. 계약 응답의 금액 필드는 **인플루언서가 받을 돈** 아니면 **계약서에 적힌 조건값**뿐이다.

### 6-3. 표준 조항 — 경로가 파트너와 다르다

`GET /v1/creator/contracts/{id}/clauses` — **계약에 고정된 버전을 읽는다.**

파트너는 작성 중(조항 버전 미고정)에도 전문을 봐야 해서 계약과 무관한 `/contracts/clauses` 경로가 필요했다. **스튜디오가 보는 계약은 전부 `clause_version_id`가 고정된 뒤**이므로(검토 요청 시 고정 — 파트너 설계 1-6), 계약에 매달린 경로가 더 정확하다. 문안이 개정된 뒤에 **내가 서명한 계약의 조항과 화면에 뜨는 조항이 달라지면 안 된다.**

입력 컨트롤이 하나도 없는 읽기 전용 응답이다(§25-7).

### 6-4. 이력 화이트리스트

`contract_history`는 16종 `event_type`을 담지만 스튜디오에 내리는 것은 **7종**이다.

| 내린다 | 화면 문구(시안) |
| --- | --- |
| `SIGNATURE_SENT` | 서명 요청 도착 · 운영자 검토 통과 |
| `BRAND_SIGNED` | 브랜드 서명 완료 |
| `CREATOR_SIGNED` | 내 서명 완료 |
| `SIGNATURE_UPDATED` | 양측 서명 완료 확인 |
| `CONCLUDED` | 체결완료 · PDF·인증서 발급 |
| `DECLINED` / `EXPIRED` / `CANCELED` | 종결 |
| *(연결 성립)* | **계약 이력이 아니다** — `Connection.responded_at`에서 읽어 **맨 아래 한 줄로 합성** |

| 내리지 않는다 | 이유 |
| --- | --- |
| `CREATED` · `REVIEW_REQUESTED` · `REVIEW_REQUEST_CANCELED` | 발송 전 브랜드 내부 행위 |
| `REVIEW_APPROVED` · `REVIEW_REJECTED` | 운영자–브랜드 간 · 승인 사실은 `SIGNATURE_SENT` 문구에 흡수된다 |
| `RESEND_REQUESTED` | 브랜드가 요청한 건이 섞인다 |
| `FIXED_FEE_PAID` | 브랜드의 기록 행위 — 4-4의 상태값으로만 |
| `GROUP_BUY_CREATED` | 브랜드 소관 |

**필터를 쿼리에 박는다** — 서비스에서 전량 조회 후 걸러내면 걸러내기 전 목록이 메모리에 존재하고, 다음 사람이 디버깅용 직렬화를 한 줄 넣는 순간 유출된다.

**`actor_type = ADMIN`의 표시명은 「운영자」**(§25-9). 파트너는 같은 값을 「어드민」으로 그린다. 서버는 `actorType`만 내리고 **문구는 서피스가 고른다** — 파트너 설계 1-6이 정한 그대로다.

## 7. 신규 `ErrorCode`

파트너 설계 4-7의 12종에 더해 **4종**. 나머지(`CONTRACT_NOT_FOUND` · `CONTRACT_STATUS_CONFLICT` · `CONTRACT_DOCUMENT_NOT_FOUND`)는 그대로 쓴다.

| 코드 | HTTP | 문구 |
| --- | --- | --- |
| `CONTRACT_NOT_RECEIVED` | 404 | 존재하지 않는 계약입니다. |
| `CONTRACT_ALREADY_SIGNED` | 409 | 이미 서명한 계약은 거절할 수 없습니다. |
| `CONTRACT_DECLINE_NOT_ALLOWED` | 409 | 지금은 거절할 수 없는 상태입니다. |
| `CONTRACT_RESEND_NOT_ALLOWED` | 409 | 서명이 필요한 계약에서만 요청할 수 있습니다. |

**`CONTRACT_NOT_RECEIVED`의 문구가 `CONTRACT_NOT_FOUND`와 같다.** 1-2의 결론 때문이다 — 미도착과 부재를 **화면에서 구분할 수 없어야** 한다. 코드를 따로 두는 것은 **서버 로그에서만** 구분하기 위해서다. 두 사건은 운영상 의미가 완전히 다르다(전자는 정상 동작, 후자는 잘못된 링크).

## 8. 연계 · 알림

### 8-1. 연계

| 방향 | 대상 | 내용 |
| --- | --- | --- |
| 입력 | `domain/contract` | **전량 읽기** — 스튜디오는 계약 모델을 확장하지 않는다 |
| 입력 | `domain/connection` + `domain/message` | 브랜드명 · 연결 상태 · **`MessageThread`(connection 1:1)** → `threadId` |
| 입력 | `member/creator` | `businessType` → `withholdingType` |
| 출력 | `contract_resend_request` | 어드민 재발송 요청 큐 |
| 출력 | 알림 | 브랜드에게 거절 통지 |

**`threadId` 해석** — `contract.connection_id` → `MessageThread.connection_id`(UNIQUE)로 1:1이다(`src/main/java/showroomz/domain/message/entity/MessageThread.java`). 상세 응답에 **`connectionId`가 아니라 `threadId`를 내린다.** `[스레드에서 협의하기]`가 §27-1 #5에서 **유일한 회복 경로**로 지정됐는데, FE가 connectionId로 스레드를 한 번 더 조회해야 하면 그 한 번이 실패할 수 있다. 스레드가 아직 열리지 않았으면 `null`이고 `canOpenThread = false`다.

### 8-2. 알림 — 인플루언서가 받는 것

| 계기 | 내용 |
| --- | --- |
| 서명 요청 발송(어드민) | **계약이 도착했다** — 이 알림이 없으면 인플루언서는 도착 사실을 모른다 |
| **서명 기한 임박** | §28-8 D #9 미정(D-3 · D-1) — **만료는 인플루언서에게 기회 손실**이다 |
| 브랜드 서명 완료 | S3 → S3a 전환 |
| 취소(브랜드) | 내 조치가 없어진 사실 |
| 체결 완료 | 공구가 생성될 수 있게 된 사실 |

**채널이 미정이다**(파트너 설계 미결 #6). 스튜디오는 웹이지만 `Creator`는 `Users`를 통해 `DeviceToken`과 이어져 있어 **기존 푸시 인프라가 기술적으로는 닿는다.** 그러나 인플루언서가 앱을 설치했다는 보장이 없고, **서명 기한 임박 알림은 도달하지 않으면 계약이 만료된다** — 도달을 보장하지 못하는 채널만으로 이 알림을 설계하면 안 된다.

→ **훅 자리만 만들고 발송은 스텁**으로 둔다. 다만 **기한 임박만은 다른 알림과 달리 스케줄러가 필요**하다는 점을 적어 둔다. §25-3이 "만료가 자동 판정이 아니다"라고 한 것은 **상태를 자동으로 닫지 말라**는 뜻이지 **알리지 말라**는 뜻이 아니다. 상태를 바꾸지 않는 알림 배치는 그 규칙과 충돌하지 않는다 — 미결 #3.

## 9. 구현 단계 (PR 분할)

**전제: 파트너 설계 P1(마이그레이션 V116~V121 + 엔티티)이 먼저 들어가 있어야 한다.** 스튜디오는 테이블을 만들지 않는다.

| 단계 | 내용 | 산출물 |
| --- | --- | --- |
| **Q1** | `V122` 인덱스 + 가시성 판정(`CreatorContractReader`) + `CreatorContractTab` | — |
| **Q2** | 목록 · `summary` · `deadline` 판정 | S1 · S2 |
| **Q3** | 상세 — `payout` · 이력 화이트리스트 · `permissions` · 조항 · 열람 기록 | S3 · S3a · S3b · S3c · S6 |
| **Q4** | 거절 + 재발송 요청 + 문서 다운로드 | S5 · S7 · S8 · S9 |

패키지는 `showroomz.api.creator.contract.{controller, docs, dto, service, type}`이고, 컨트롤러는 `CreatorContractControllerDocs`를 implements 한다(문서 어노테이션은 docs 인터페이스에).

**Q3까지는 쓰기가 없다**(열람 기록 제외). 어드민 API가 아직 없어 계약이 `SIGNING`에 도달하지 못하는 동안에도 **Q1~Q3는 안전하게 배포**된다 — 볼 계약이 없을 뿐 화면이 깨지지 않고, 그 상태가 정확히 S2(빈 상태)다.

**Q4는 어드민 P7(서명 현황 갱신)과 순서 의존이 없다.** 거절은 `creator_signed_at IS NULL`에서만 가능하고 그 값은 어드민이 채우므로, 어드민 API가 없으면 **모든 계약이 거절 가능한 상태**다 — 기능상 문제가 아니라 **테스트가 한쪽 분기만 탄다**는 뜻이라, S3b 경로는 스테이징에서 값을 직접 넣어 확인한다.
