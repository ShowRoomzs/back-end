## 0. 먼저 정한 8가지

### 0-1. 클레임은 **새 테이블**이고, 하위주문의 이행 상태를 건드리지 않는다

34 설계서 0-2와 같은 원리다 — 반품·교환은 배송완료(`DELIVERED`) 위에 얹히는 오버레이이고, 끝나면 하위주문은 원래 길(구매확정)로 돌아가야 한다. `fulfillment_status`에 값을 더하지 않는다. `order_claim` 행의 존재가 곧 플래그다.

- 단위는 **주문 항목(SKU) + 수량** — 접수번호 1건 = `order_claim` 1행 = `order_product` 1건의 일부 또는 전량(§35-0).
- 반품과 교환은 **한 테이블 · `type` 열**이다 — 검수까지 흐름이 같다(§35-0). 테이블을 나누면 목록·카운트·기한이 전부 UNION이 된다.

### 0-2. 저장 상태는 9종, 화면 단계는 6종 — **탭 매핑은 서버가 소유한다**

기획의 단계 6종만으로는 두 구간이 표현되지 않는다(§35-9 A-6): ① 반품 검수 통과 ~ 운영자 환불 집행 ② 재발송 송장 등록 ~ 도착. 「저장하지 않고 넘어가는」 선택지는 없다 — 그 사이에 돈과 물건이 움직인다. 그래서 저장 상태는 실제 사건대로 두고(1-2), 탭은 그 위의 조회 조건으로 만든다(1-3).

**두 구간은 완료 탭에 넣고 결과 열이 「환불 대기」 「재발송 중」을 말한다.** 근거:

- 시안 A5 「송장을 등록하면 완료 처리」(행이 재발송 탭을 떠난다)와 D2·A7 「도착 = 교환 완료」(결과가 확정된다)를 **둘 다 만족**한다.
- 작업 탭(입고·검수 · 재발송)의 카운트가 KPI와 같아진다 — 탭에 「할 일 없는 행」이 섞이지 않는다.

대표 확정이 다르게 나면 `ClaimTab`의 매핑 한 줄을 고친다(7절 N1).

### 0-3. 「지연」은 파생값, **기한은 스냅샷으로 저장**한다

34 설계서 0-5·3-6과 같다. `지연 = NOW() > 기한 AND 판정 시각 IS NULL`은 계산이지만, 기한 자체(`collect_due_at` · `inspect_due_at`)는 전이 시점에 계산해 **저장**한다 — 영업일 규칙이 `[근거 대기]`(§35-9 #10)라 나중에 규칙이 바뀌어도 이미 발급된 기한(귀책 판정값)이 소급해 움직이면 안 된다.

### 0-4. 돈을 움직이는 전이는 브랜드 API에 없다

§35-0 그대로 — 브랜드 API가 바꾸는 것은 **입고 확인 · 검수 통과 · 검수 거절 · 재발송 송장 등록/수정** 다섯 가지뿐이다. 승인·수락·신청 거절 · 회수 송장 등록 · 금액 입력 · 환불 실행은 **엔드포인트를 만들지 않는다.** 검수 통과는 `order_refund_task` 큐 행까지만 간다(34 설계서 1-9의 큐를 그대로 쓴다).

### 0-5. 회수 그룹은 **`order_claim_collection`** — 회수 송장의 주인이다

「같은 박스로 오는 항목」(§35-2)은 소비자가 한 번에 신청한 묶음이고, 회수 송장은 박스에 하나다. 송장을 클레임마다 복제하면 소비자 정정이 N행 수정이 된다. 그래서 회수 단위를 테이블로 두고(1-4) **1건짜리 신청도 항상 1행**을 만든다 — 분기가 없다.

**표시 단위일 뿐 처리 단위가 아니다** — 상태는 클레임 행에만 있다. 회수 송장 입력·도착은 그 묶음의 클레임을 한 트랜잭션에서 같이 옮길 뿐이고, 입고 확인부터는 항목마다 갈린다.

### 0-6. 건수의 단위는 **항목(클레임)** 이다

시안 정정 §35-10 #3(탭·KPI는 그룹 단위 3, 목록 헤더는 항목 단위 5)을 항목 단위로 통일한다 — 검수·거절·재발송이 전부 항목마다이므로 「오늘 할 일 몇 건」은 항목 수가 맞다. 회수 그룹은 응답의 `collection` 블록으로 FE가 묶어 그린다(4-1). 그룹 단위로 확정되면 카운트 쿼리의 `COUNT(*)` → `COUNT(DISTINCT collection_id)`(회수 대기·회수 중 탭만).

### 0-7. 택배 연동 스텁 기간에는 **브랜드 입고 확인이 도착 감지를 겸한다**

회수 도착·재발송 도착은 `DeliveryTrackerPort`가 알려 준다(34 설계서 0-4). 스텁(`delivery.tracker.enabled=false`) 동안은 「추적상 도착」이 영원히 오지 않으므로:

- **입고 확인**은 `ARRIVED`뿐 아니라 `COLLECTING`에서도 허용한다(`order.claim.receive-before-arrival=true` · 연동 활성화 후 false로 내린다). 상세의 `actions.canConfirmReceipt`가 이 설정을 반영하므로 FE 분기는 없다.
- **재발송 도착**은 운영자 직권 완료(도메인 진입점 3-7)로만 닫힌다 — 34 설계서의 배송완료 직권과 같은 처지다. **연동 활성화가 여기서도 런칭 게이트다.**

### 0-8. 사유 번복은 **만들지 않는다** — 시안의 2판정으로 집행

§35-9 A-1(약관 제20조②의 3판정 ↔ 시안 2판정)은 대표 확정 대기다. 시안이 최신이므로 통과/거절 2판정으로 만든다. 약관 쪽으로 확정되면 상태 1개(`EXCHANGE_FEE_PENDING`)와 판정 API 1개가 더해진다 — `status`가 VARCHAR라 마이그레이션은 없다.

### 1-2. `ClaimStatus` — 9종

`domain/order/type/ClaimStatus.java`. 배지 톤은 서버가 내린다 — **전부 중립**(§35-2 「단계 배지는 진행 순서일 뿐」)이고 상세 헤더의 결과 배지만 성공/중립으로 갈린다.

| enum | 라벨 | 진입 | 주체 | 브랜드 액션 |
| --- | --- | --- | --- | --- |
| `REQUESTED` | 회수 대기 | 소비자 신청(자동 수락) | 소비자 | 없음 |
| `COLLECTING` | 회수 중 | 소비자 회수 송장 입력 | 소비자 | 없음(0-7 예외) |
| `ARRIVED` | 입고 확인 전 | 추적상 브랜드 도착 | 시스템 | **입고 확인** |
| `RECEIVED` | 검수 대기 | 입고 확인 | 브랜드 | **검수 통과 / 거절** |
| `REFUND_PENDING` | 환불 대기 | 반품 검수 통과 | 브랜드 | 없음 — 운영자 집행 대기 |

| `REJECT_HOLD` | 거절 보류 | 검수 거절 | 브랜드 | 없음 — 소비자 결제 대기 |
| `COMPLETED` | 완료 | 종결 | 운영자 / 시스템 | 없음 |

`ARRIVED`·`RECEIVED`가 화면 단계 「입고·검수」의 하위 상태 2종(`입고 확인 전` / `검수 대기`)이다 — 관리 열 버튼이 이 값으로 교체된다.

**결과 `ClaimResult` 3종**(완료일 때만 · 전부 중립색 — 단, 상세 헤더 배지는 시안대로 환불 완료·교환 완료 = 성공, 거절 종결 = 중립): `REFUNDED`(환불 완료) / `EXCHANGED`(교환 완료) / `REJECTED`(거절 종결 — 반송 완료 또는 보관 종료).

### 1-3. `ClaimTab` — 7종 · 탭이 조건과 기본 정렬을 소유한다

## 2. 상태 전이 — 전부 조건부 UPDATE

34 설계서 2절과 같은 수법 — **현재 상태를 WHERE에 넣은 UPDATE의 1행 확인**이 경합의 최종 방어선이다. 전이 메서드는 `OrderClaimRepository`에 모으고 엔티티에 두지 않는다. 모든 전이가 `stage_entered_at = now`를 같이 쓴다.

| # | 전이 | 주체 | 트리거 | WHERE |
| --- | --- | --- | --- | --- |
| 1 | (없음) → `REQUESTED` | 소비자 | 신청 — INSERT | 하위주문 `DELIVERED` · 잔여 수량(3-1) |
| 2 | `REQUESTED` → `COLLECTING` | 소비자 | 회수 송장 입력 | `collection_id = ? AND status = 'REQUESTED'` — **묶음 전체** |
| 3 | `COLLECTING` → `ARRIVED` | 배치 | 추적상 도착 | `collection_id = ? AND status = 'COLLECTING'` + 폴링 당시 송장 일치 |
| 4 | `ARRIVED` → `RECEIVED` | 브랜드 | 입고 확인 | `status = 'ARRIVED'`(0-7 설정 시 `IN ('COLLECTING','ARRIVED')`) `AND market_id = ?` |
| 5 | `RECEIVED` → `REFUND_PENDING` | 브랜드 | 반품 검수 통과 | `status = 'RECEIVED' AND type = 'RETURN'` |
| 6 | `RECEIVED` → `RESHIP_READY` | 브랜드 | 교환 검수 통과 | `status = 'RECEIVED' AND type = 'EXCHANGE'` |
| 7 | `RECEIVED` → `REJECT_HOLD` | 브랜드 | 검수 거절 | `status = 'RECEIVED'` |
| 8 | `REJECT_HOLD` → `RESHIP_READY` | 소비자 | 재배송비 결제 | `status = 'REJECT_HOLD'` |
| 9 | `RESHIP_READY` → `RESHIPPING` | 브랜드 | 재발송 송장 등록 | `status = 'RESHIP_READY'` |
| 10 | `REFUND_PENDING` → `COMPLETED(REFUNDED)` | 운영자 | 환불 집행 | `status = 'REFUND_PENDING'` |
| 11 | `RESHIPPING` → `COMPLETED(EXCHANGED / REJECTED)` | 배치 / 운영자 | 재발송 도착 | `status = 'RESHIPPING'` + 폴링 당시 송장 일치 — 결과는 `rejected_at`으로 가른다 |
| 12 | `REJECT_HOLD` → `COMPLETED(REJECTED)` | 운영자 | 보관 종료 | `status = 'REJECT_HOLD'` |

- **역방향 전이가 없다** — 입고 확인·판정·송장 등록 어느 것도 되돌리지 않는다. 거절은 제출 = 즉시 확정이다(§35-5).
- #2·#3이 묶음 단위인 것은 박스가 하나이기 때문이고, #4부터는 항목 단위다. 묶음 안 한 건만 먼저 입고 확인해도 된다.
- 다건 액션(#4 · #9)은 **행 단위 부분 성공** — 0행 UPDATE 행만 사유와 함께 제외한다. 판정(#5~#7)은 **단건만** 받는다 — 근거가 건마다 다르다(34 설계서 1-5의 승인·거부와 같은 이유).
- #8의 기간 내 미결제는 **자동 전이하지 않는다** — 약관 제20조⑤가 처분 전 통지·최고를 요구하고 기간·방법이 운영정책 대기(§35-9 #7·#8)다. 배치가 기계적으로 닫으면 절차를 건너뛴다. `storage_due_at`은 「N일 남음」 표시와 어드민 큐의 기준으로만 쓰고, 종결은 운영자의 #12다.

## 3. 흐름별 설계

### 3-1. 신청 — 도메인 진입점 `OrderClaimService.request` (앱이 부른다)

```
입력: userId · deliveryGroupId · type · items[{orderProductId, quantity, reasonCode, reasonDetail,
      exchangeVariantId?, imageUrls[]}]
1. 하위주문 소유·상태 — fulfillment_status = DELIVERED 만(구매확정 전). 아니면 CLAIM_NOT_ELIGIBLE
2. 항목 잠금 — order_product 를 id 오름차순 SELECT … FOR UPDATE
3. 잔여 수량 = quantity − returned_quantity − Σ(진행 중 클레임 수량) ≥ 신청 수량. 아니면 CLAIM_QUANTITY_EXCEEDED
4. 사유 — detailRequired 사유인데 내용이 비면 400
5. 교환 — 같은 상품의 다른 옵션인지 검증 · 교환 옵션 재고 선점(3-8)
6. collection 1행(반품 수취 주소 스냅샷) + 항목마다 claim 1행
   (fee_bearer · claim_fee · refund_expected_amount · collect_due_at 스냅샷)
7. 첨부 · 이력 REQUESTED
```

- 한 번의 신청은 **한 하위주문 · 한 유형**이다 — 유형이 섞이면 박스는 같아도 「반품 3 · 교환 2」가 한 묶음 머리에 들어가 시안의 그룹 행(유형 1칸)이 깨진다. 사유는 항목마다 다를 수 있다(시안 A1).
- 「진행 중」 = `status <> 'COMPLETED'`. 환불로 끝난 수량은 `returned_quantity`가 이미 빼고 있고, 교환 완료·거절 종결된 수량은 소비자 손에 있으므로 잔여로 돌아온다 — 재신청을 받을지는 창(구매확정 전)이 결정한다.
- 구매확정 후 사후 클레임(§35-9 #11)은 **받지 않는다** — 1번 조건이 막는다. 확정되면 조건 완화 + 정산 환수가 따라온다(이 설계 범위 밖).

### 3-2. 회수 — 소비자 발송 · 추적 자동 갱신

| 사건 | 처리 |
| --- | --- |
| 회수 송장 입력(`registerCollectionInvoice`) | 형식 검증(`DeliveryTrackerPort.validateInvoice` — 스텁이면 생략 기록) → collection에 저장 → 전이 #2(묶음 전체) → 이력 |
| 오입력 정정(`updateCollectionInvoice`) | `COLLECTING`인 동안만 · `invoice_registered_at` 유지 · 추적 값 리셋 · 이력 |
| 추적 폴링 | `ClaimTrackingScheduler`(3-5) — `last_tracking_at` · `last_tracking_label` 갱신 |
| 도착 | `arrived_at` 저장 → 전이 #3 → 이력 `ARRIVED` |

- 회수 송장의 **전역 중복 검사는 하지 않는다** — 소비자가 편의점 택배 등으로 받은 번호이고, 겹치는 주문번호를 지목해 줄 상대가 없다. 형식 검증만 한다.
- 브랜드는 이 구간에서 읽기만 한다. 부당해 보여도 회수를 멈출 API가 없다(0-4) — 창구는 연결·소통의 운영자 문의이고 이 모듈은 링크만 제공한다.

### 3-3. 입고 확인 · 검수 판정

**입고 확인 — `POST /receive`** `{claimIds[]}`

- 행마다 전이 #4 → `received_at` · `received_by` · `inspect_due_at` 발급(1-7) → 이력.
- 응답은 34의 `BatchActionResponse`를 재사용한다 — `{succeeded, skipped[{id, reason}]}`.

**검수 통과 — `POST /{claimId}/inspection/pass`**

| 유형 | 같은 트랜잭션에서 |
| --- | --- |
| 반품 | 전이 #5 → `order_product.returned_quantity += quantity`(조건부 UPDATE — `returned_quantity + q <= quantity`) → 전량이면 항목 `PAID → RETURNED` → `order_refund_task(CLAIM_RETURN_PASSED, claim_id, refund_expected_amount)` INSERT → 이력 |
| 교환 | 전이 #6 → 이력. 재고는 신청 때 이미 선점돼 있다(3-8) |

- 반품된 물건의 **재고는 원복하지 않는다** — 돌아온 상품을 다시 팔 수 있는지는 브랜드의 판단이고(개봉·불량), 취소(34 설계서 3-5)와 달리 물건이 한 번 나갔다 왔다.
- 항목 반영 시점이 환불 집행이 아니라 **검수 통과**인 이유 — 판매가 무효가 된 시점이 여기다. 취소 요청 승인이 항목을 먼저 `CANCELLED`로 내리고 환불 큐를 세우는 것(34 설계서 3-5)과 같은 순서다.

**검수 거절 — `POST /{claimId}/inspection/reject`** `{reasonCode, detail, evidenceImageUrls[]}`

- 세 필드 전부 필수 — 증빙 1장 이상 · 상한 `order.claim.evidence-max=5`. 비면 400(`CLAIM_REJECT_INCOMPLETE`). FE는 버튼 비활성으로 막지만 서버가 정본이다.
- 전이 #7 → `reject_*` · `rejected_at` · `storage_due_at` → 증빙 첨부(`SELLER`) → `order_claim_charge(RESHIP_FEE, PENDING)` INSERT → 교환이면 **선점 재고 원복**(교환 무효화) → 이력.
- 재배송비 금액: `market.default_delivery_fee`(잠정 — 반품비·교환비 산정과 같이 §35-9 #9). 결제 링크 발송은 어드민 몫이고 여기서는 행만 선다.
- 소비자 전달(사유·설명·증빙)은 앱이 클레임 상세에서 읽는다 — 전달용 사본을 만들지 않는다. 알림 발송은 알림 모듈 연계로 둔다.

### 3-4. 재발송 — 34 설계서 3-2의 송장 패턴을 그대로

**확정 — `POST /reshipments`** `{items[{claimId, carrier, trackingNumber}]}`

```
행마다:
  1. 형식 — DeliveryTrackerPort.validateInvoice()
  2. 전역 중복 — 종결 전 하위주문의 송장 + RESHIPPING 클레임의 재발송 송장 양쪽을 본다.
     겹치면 제외 — 내 마켓 건일 때만 겹치는 번호(주문번호/접수번호)를 지목
  3. 전이 #9 조건부 UPDATE — 0행이면 「상태가 변경되었습니다」로 제외
  4. 성공 행: reship_* 저장 · 이력 RESHIP_INVOICE_REGISTERED
응답: { succeeded, errors[{claimId, code, message}] }
```

- 빈 값 행은 FE가 제외하고, 왔다면 조용히 건너뛴다(§35-7 「빈 값 조용히 제외」).
- **등록해도 완료가 아니다** — `RESHIPPING`으로 가고 결과는 도착 때 확정된다(0-2 · 시안 정정 #2). 탭 안내 문구 「등록하면 완료 처리」는 FE가 「등록하면 재발송 중으로 넘어가고, 도착하면 완료됩니다」로 바꾼다.

**목록 다운로드(E1) — `POST /reshipments/export`** `{claimIds[]?, columns[], saveAsDefault}`

| 항목 | 처리 |
| --- | --- |
| 대상 | `RESHIP_READY`만 — `claimIds`가 없으면 현재 필터 전체. 0건이면 400 `CLAIM_EXPORT_EMPTY` |
| 컬럼 | `ClaimReshipColumn` — 기본 7종 `CLAIM_NUMBER` · `RECIPIENT` · `PHONE` · `ZIP_CODE` · `ADDRESS` · `PRODUCT_NAME` · `OPTION` + 추가 6종 `QUANTITY` · `RESHIP_REASON` · `REQUESTED_AT` · `ORDER_NUMBER` · `GROUP_BUY_NAME` · `CLAIM_TYPE`. 순서 = 엑셀 좌→우 |
| **상품명·옵션** | **보낼 물건**을 쓴다 — 교환 재발송은 `exchange_option_name`, 거절 반송은 원래 옵션. 화면의 「보낼 상품·옵션」 열과 같은 값이어야 거절 건에 새 옵션을 보내는 사고가 안 난다 |
| 수취지 | 원 주문의 배송지(`orders` 스냅샷) — 교환·반송 모두 |
| 꼬리 열 | 선택 컬럼 뒤에 빈 **「택배사」 「송장번호」** 2열을 항상 붙인다 — 이 파일을 채워 다시 올리는 왕복이 전제다 |
| 기록 | `purchase_order_download_log(kind = 'CLAIM_RESHIP')` — 트랜잭션 안 |
| 기본값 | `saveAsDefault`면 템플릿 upsert. 조회·저장은 `GET/PUT /reshipments/export/template` |

**일괄 업로드(E2) — `POST /reshipments/parse`** (multipart xlsx · 최대 `order.shipment-upload-max-rows`)

- **상태를 바꾸지 않는다** — 분류해서 행 배열만 돌려주고, 확정은 FE가 셀을 채운 뒤 같은 `POST /reshipments`를 탄다. 버튼 라벨은 「N건 목록에 채우기」(시안 정정 #2).
- 열은 **머리글로 찾는다**(「접수번호」 「택배사」 「송장번호」) — 컬럼 구성이 브랜드마다 달라 위치가 고정이 아니다. 셋 중 하나라도 없으면 400.
- 분류: 정상 / 접수번호 없음·내 마켓 아님(같은 사유로 — 존재 여부를 가르지 않는다) / 재발송 대기가 아님 / 송장 중복 / 파일 안 같은 접수번호 반복(첫 정상 행만) / 택배사 미지원 명칭. 숫자 셀은 자릿수 그대로 읽는다. `ShipmentExcelParser`의 셀 읽기를 공용 유틸로 올려 쓴다.

**송장 수정 — `PATCH /{claimId}/reshipment`** — `RESHIPPING`만 · `reship_registered_at` 유지 · 추적 값 리셋 · 이력에 구→신.

**도착** — 전이 #11.

| 재발송 사유 | 결과 | 같은 트랜잭션에서 |
| --- | --- | --- |
| 교환 재발송 | `EXCHANGED` | `order_delivery_group.confirm_restart_at = 도착 시각`(구매확정 7일 재시작) · 정산 금액 불변 |
| 거절 반송 | `REJECTED` | 없음 — 환불 없음. 하위주문은 원래의 구매확정 타이머로 돌아간다 |

### 3-5. `ClaimTrackingScheduler`

`global/scheduler`. 주기·가동 조건은 `OrderDeliveryTrackingScheduler`와 같은 설정을 쓴다(`delivery.tracker.enabled=false`면 기동하지 않는다).

| 대상 | 판정 | 처리 |
| --- | --- | --- |
| `COLLECTING` 묶음(collection) | `track()` | `last_tracking_at` · `last_tracking_label` 갱신 |
| 〃 | `deliveredAt` 존재 | 전이 #3 |
| `RESHIPPING` 클레임 | `track()` | `reship_last_tracking_at` 갱신 |
| 〃 | `deliveredAt` 존재 | 전이 #11 |

- 반영 전이는 WHERE에 **폴링 당시 `(carrier, tracking_number)`** 를 넣는다 — 폴링과 반영 사이의 송장 정정에 구 송장 결과가 덮이지 않게(34 설계서 3-3).
- 재발송 건의 **배송 이상·반송**(§35-9 A-6 후단)은 감지하지 않는다 — 처리 정책이 미정이다. `reship_last_tracking_at`이 있으므로 「추적 정지」 판정은 확정 후 조건 한 줄로 붙는다.

### 3-6. 구매확정과의 연동 — 진행 중 클레임이 타이머를 세운다

| 규칙 | 구현 |
| --- | --- |
| 진행 중 클레임이 있는 하위주문은 **구매확정하지 않는다** | `confirmPurchase`·`findIdsToConfirm`의 WHERE에 `NOT EXISTS (order_claim WHERE delivery_group_id = g.id AND status <> 'COMPLETED')` |
| 교환 완료 후 7일 재시작 | 기준 시각을 `COALESCE(confirm_restart_at, delivered_at)`으로 |
| 전량 반품 항목 | `RETURNED`라 그룹 구매확정 때 `PAID → PURCHASE_CONFIRMED` 전이 대상에서 자연 제외 |
| 그룹의 **전 항목이 `RETURNED`·`CANCELLED`** | 구매확정할 것이 없다 — 그래도 그룹은 `CONFIRMED`로 닫는다(종결 표현을 따로 만들지 않는다 · 정산은 유효 수량 0으로 본다). 34 설계서 N2의 재검토 결론이다 |

- 신청과 구매확정 배치의 경합: 신청(3-1)은 그룹이 `DELIVERED`인지 **INSERT와 같은 트랜잭션에서 그룹 행을 잠그고** 확인한다. 배치의 조건부 UPDATE가 먼저면 신청이 지고(`CLAIM_NOT_ELIGIBLE`), 신청이 먼저면 배치의 `NOT EXISTS`가 건너뛴다.
- **소비자 미발송 방치가 정산을 묶는다**(§35-9 A-4) — 이 구조에서 `REQUESTED`가 영원히 남으면 구매확정이 안 된다. 자동 취소 기한은 대표 확정 대기라 만들지 않았다. 확정 전까지는 「지연」 표시 + 어드민 직권 종결(3-7 `closeByAdmin`)이 유일한 출구다. **런칭 전 확정 필요.**

### 3-7. 도메인 진입점 — 앱·어드민이 부를 것

`domain/order/service/OrderClaimService`. 컨트롤러 없이 서비스와 테스트까지 이번에 만든다.

### 3-8. 교환 옵션 재고

| 시점 | 처리 |
| --- | --- |
| 신청 | 교환 옵션(`exchange_variant_id`) 재고를 **선점(차감)** — 부족하면 `CLAIM_EXCHANGE_OUT_OF_STOCK`. C10의 「교환 불가 (재고 없음)」이 이 판정이다 |

### 4-1. 목록 행 DTO — 탭 공통 superset

```
claimId · claimNumber("CLM-3021") · type · typeLabel
consumerName(전체 표기) 
productName · optionName · exchangeOptionName(교환만) · productLabel("데일리 선크림 50ml → 리필")
shipLabel(재발송·거절 보류 탭의 「보낼 상품·옵션」/「보관 중인 상품」 — 3-4 규칙)
quantity
reasonCode · reasonLabel · consumerAttachmentCount
status · statusLabel · stage(탭 코드) · statusTone(NEUTRAL)
requestedAt · stageEnteredAt · elapsedDays · overdue
collection: { collectionId, size, leadClaimNumber, carrier, carrierLabel, trackingNumber,
              lastTrackingLabel, lastTrackingAt, arrivedAt }
receivedAt · inspectDueAt
reshipReason(EXCHANGE|REJECT_RETURN|null) · reshipReasonLabel · reshipCarrier · reshipTrackingNumber
rejectReasonLabel · sellerEvidenceCount · rejectedAt · storageDueAt · storageDaysLeft
outcome: { code(REFUND_PENDING|RESHIPPING|REFUNDED|EXCHANGED|REJECTED), label, final } · amount · completedAt
actions: { canConfirmReceipt, canInspect, canRegisterReshipment }
orderItems[](전체 탭 행 확장 ▸): productName · optionName · orderedQuantity · claimedQuantity · price · itemStatusLabel
orderSummary("3개 항목 중 1개 신청")
```

- **회수 그룹** — 행은 클레임이고 묶음은 `collection.size > 1`로 FE가 그린다(「CLM-3021 외 2건」 = `leadClaimNumber` + `size − 1`). 같은 묶음이 인접하도록 정렬의 2차 키에 `collection_id`, 3차 키에 `claim_id`를 넣는다. 페이지 경계에서 묶음이 갈릴 수 있다 — `size`가 전체 건수를 말하므로 머리 행은 정확하고, 20건 페이지에서 드문 경우라 묶음 단위 페이징을 따로 만들지 않는다.
- `amount` — 완료 탭 「금액」: `refunded_amount`, 환불 대기면 예정액, 교환·거절이면 null(FE가 「—」).
- `orderItems`는 **그 하위주문의 항목 전체**다 — 신청분과 살아 있는 분이 갈려야 한다(§35-2). `itemStatusLabel`은 반품 신청 / 교환 신청 / 구매확정 / 배송완료 / 취소 / 반품. 하위주문 id로 한 번에 읽는다(N+1 없음).
- 연락처는 목록에 싣지 않는다 — 상세에 **마스킹**해서만(4-3).

### 4-2. 요약 — `GET /summary`

```json
{
  "kpi": { "collectWait": 3, "inspection": 2, "reship": 1, "overdue": 1 },
  "tabCounts": { "ALL": 12, "COLLECT_WAIT": 3, "COLLECTING": 2, "INSPECTION": 2, "RESHIP": 1, "REJECT_HOLD": 1, "DONE": 3 },
  "typeCounts": { "RETURN": 7, "EXCHANGE": 5 }
}
```

- KPI와 탭 카운트는 **검색 조건과 무관한 전체 기준**이다(시안 A0s) — 기간 필터도 타지 않는다. `typeCounts`도 같다.
- `overdue` = 기한 ① 초과 + 기한 ② 초과. 0건이면 FE가 경고 톤을 뺀다(시안 정정 #5).
- 대탭 카운트(「반품·교환 관리 12」)는 `tabCounts.ALL`.

### 4-3. 상세 — `GET /{claimId}`

- **신청 정보**: 접수번호 · 유형 · 소비자(이름 + **연락처 마스킹** `010-****-4412`) · 상품·옵션 · 교환 옵션(+ 「같은 상품의 다른 옵션 맞교환 · 차액 없음」은 FE 고정 문구) · 수량 · 사유 · `exchangeFeeCharged`(교환 — `claim_fee > 0`) · 상세 내용 · 신청일시 · 회수 송장(소비자 입력) · 입고 확인 시각 · **검수 기한**(`inspectDueAt`).
- **환불 예정액**(반품): `refundExpectedAmount` · `refundBasisLabel`(1-8) — 표시만.
- **소비자 첨부** `consumerAttachments[]` · **브랜드 증빙** `sellerEvidences[]`.
- **처리 결과 카드**(`DONE`): 환불 — 금액 · 산식 · 집행 일시·주체 / 교환 — 보낸 옵션 · 재발송 송장 · 도착 · `confirmDueAt`(재시작 예정일) / 거절 — 거절 사유 · 증빙 · 반송 송장 · 반송 완료 또는 보관 종료.
- **처리 이력** `history[]` 최신순 · 주체 라벨.
- `actions`: `canConfirmReceipt` · `canPass` · `canReject` · `canRegisterReshipment` · `canUpdateReshipment` — 버튼 노출의 정본은 서버다.
- 연락처 마스킹은 `OrderAddressMasker`(C10 설계서 3-2)의 연락처 규칙을 쓴다. **재발송 수취 정보(원문)는 상세에 싣지 않고 엑셀(E1)에만** 나간다 — 반출은 로그가 남는 경로 하나로 모은다.
- 회수 대기·회수 중·재발송·거절 보류의 상세는 시안이 없지만(시안 정정 #6) 같은 DTO로 열린다 — 없는 블록이 null일 뿐이다.
