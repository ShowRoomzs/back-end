## 1. 개요 · 범위

이 계획은 **C9 결제 화면의 백엔드**다 — 주문서를 그리고, 주문을 만들고, 포트원 결제창을 열 재료를 내리고, 결제 결과를 확정한다. 지금 `orders`·`order_product`는 리뷰(V36)를 위해 만든 선행 테이블이라 **주문을 생성하는 API가 없고**, 금액·배송지·결제 정보 컬럼도 없다. 이 문서가 그 빈자리를 채운다.

| 화면 · 진입 | 이번에 할 일 | 현재 상태 |
| --- | --- | --- |
| C8 [주문하기 (N)] → C9 | 선택한 장바구니 항목으로 주문서 조회·주문 생성 | 장바구니 조회·합계는 완료(`CartService`). 넘길 곳이 없다 |
| C7 [바로 구매] → C9 | `variantId + quantity + groupBuyId`(필수) 한 줄로 주문서 조회·주문 생성 | 상세의 판매 가능 판정은 완료. 넘길 곳이 없다 |
| C9 주문서 | 배송지(기본 배송지·변경)·요청사항·주문 상품·결제수단·금액 | 배송지 API 완료(`/v1/user/delivery-addresses`) |
| C9 결제 CTA | `paymentId`·금액·채널키를 내려 포트원 결제창을 열게 한다 | 없음 |
| 결제 완료 → 복귀 | 앱 확인 요청 + 웹훅으로 주문을 `PAID`로 | 없음 |
| 결제 전 취소 · 배송 전 취소 | 주문 취소 → 포트원 전액 취소 → 재고 복원 | 없음 |

**범위 밖** — 마이 「주문 내역·주문 현황」 화면(주문 조회 API 하나는 이번에 두되 목록·필터는 다음), 배송·반품·교환 상태 머신, 셀러 「판매 관리」, 정산, 부분 취소, 가상계좌·계좌이체·휴대폰 결제(C9 남은 결정 ⑤), 쿠폰·포인트(⑥), 결제 완료 푸시 알림.

## 2. 포트원 연동 방식

### 2-1. 결제 흐름

```
앱                          서버                                 포트원
│ POST /orders/checkout ────▶│ 장바구니·상품 검증, 금액 계산      │
│◀── 주문서(금액·배송지) ─────│                                    │
│                            │                                    │
│ POST /orders ─────────────▶│ 재고 차감 · orders PAYMENT_PENDING │
│                            │ payment READY(paymentId 발급)      │
│                            │ POST /payments/{id}/pre-register ─▶│ 금액 고정
│◀── paymentId·금액·채널키 ──│                                    │
│                            │                                    │
│ requestPayment(SDK) ───────┼───────────────────────────────────▶│ 결제창 · 인증
│◀─────────────── 결과(성공/실패/리다이렉트) ─────────────────────│
│                            │◀──── 웹훅 Transaction.Paid ────────│
│ POST /payments/{id}/complete ▶│ GET /payments/{id} ─────────────▶│ 상태·금액 재조회
│                            │ 금액 == 주문금액 ∧ status == PAID  │
│                            │ → orders PAID (조건부 UPDATE)      │
│◀── 주문 완료 응답 ──────────│                                    │
```

- **주문 생성과 결제창 열기를 분리**한다. 주문이 먼저 있어야 결제 실패·이탈 뒤에도 "무엇을 사려 했는지"가 남고, 만료 스케줄러가 재고를 돌려놓을 근거가 생긴다.
- **complete와 웹훅은 같은 함수를 부른다** — `PaymentConfirmService.confirm(paymentId)`. 어느 쪽이 먼저 와도 포트원을 다시 읽고, 조건부 UPDATE로 한 번만 전이한다. 둘째 호출은 0행 갱신으로 끝나고 현재 상태를 돌려준다.
- **사전 등록(pre-register)** 은 포트원이 결제창의 `totalAmount`를 서버가 등록한 금액과 대조해 다르면 결제를 거절하게 한다. 서버 재검증과 겹치는 이중 방어지만, 잘못된 결제가 **일어나지 않는** 쪽이 **취소하는** 쪽보다 싸다.
- 앱은 React Native라 결제창은 포트원 RN SDK의 웹뷰 안에서 열리고 닫힌다(2-4). 리다이렉트 복귀 경로는 없다 — 앱은 `onComplete`로 받은 `paymentId`를 들고 complete를 부른다.

### 2-2. 결제수단 매핑

C9는 **카드(카드사 선택) · 간편결제(카카오·네이버·토스)** 둘이다. 서버는 자체 enum으로 받고 포트원 코드로의 변환은 `PortOnePaymentGateway` 한 곳에서만 한다 — 앱이 포트원 코드를 알 필요가 없고, PG를 바꿔도 앱 스펙이 안 바뀐다.

| 서버 enum | 포트원 V2 `payMethod` | 부가 값 | 채널 |
| --- | --- | --- | --- |
| `PaymentMethod.CARD` + `CardIssuer` | `CARD` | `card.cardCompany` (카드사 코드) | 토스페이먼츠 신모듈 채널 |
| `PaymentMethod.EASY_PAY` + `EasyPayProvider.KAKAOPAY` | `EASY_PAY` | `easyPay.easyPayProvider` | 〃 (허브형) |
| `… NAVERPAY` | `EASY_PAY` | 〃 | 〃 |
| `… TOSSPAY` | `EASY_PAY` | 〃 | 〃 |

- **PG는 토스페이먼츠, 포트원 결제모듈은 「신모듈 · 결제창 일반결제 · V2」** 로 정했다(2026-09-27). 카카오·네이버·토스페이는 토스페이먼츠 **허브형 간편결제**라 PG 계약 하나로 열리고 **채널키도 1개**다. 직연동(간편결제사와 개별 계약)은 매출이 커져 수수료를 따로 협상할 때 검토한다.
- 그래도 채널키를 앱에 고정하지 않고 **주문 생성 응답에 그 주문의 결제수단에 맞는 `channelKey`를 실어** 내린다. 설정은 결제수단별 키 맵(6-2)으로 두고 지금은 네 값이 같은 키다 — 나중에 간편결제 하나를 직연동으로 떼거나 PG를 바꿔도 앱 스펙이 안 바뀐다.
- `CardIssuer`는 C9 목록 10개(신한·삼성·현대·KB국민·롯데·하나·BC·NH농협·우리·카카오뱅크)를 그대로 enum으로 둔다. 포트원 `CardCompany` 코드 값은 SDK 타입 정의로 확정한다(구현 시 확인 항목).
- 포트원 응답의 실제 결제수단(`method`)은 그대로 `payment.pg_method_json`에 남긴다. 사용자가 고른 것과 PG가 실제로 처리한 것이 다를 수 있다(간편결제 안의 카드 결제 등).

### 2-3. 검증 원칙

1. **금액은 서버만 만든다.** 주문서·주문 생성·결제 확정 세 지점이 모두 같은 `OrderPricingCalculator`를 쓴다(7-1).
2. **결제 확정은 포트원 조회 결과만 믿는다.** 앱이 보낸 성공 응답도, 웹훅 본문도 트리거일 뿐이다. `GET /payments/{paymentId}`의 `status`·`amount.total`·`currency`·`storeId`를 주문과 대조한다.
3. **불일치는 자동 취소한다.** `status == PAID`인데 금액이 다르거나, 주문이 `EXPIRED`·`CANCELLED`면 즉시 전액 취소 API를 부르고 `payment.status = CANCELLED_MISMATCH`로 남긴다. Sentry `error` 레벨.
4. **웹훅은 서명 검증 → 멱등 → 처리** 순이다. 서명이 틀리면 401로 끊고 본문을 읽지 않는다. `webhook-id`는 유니크 저장(`payment_webhook_event`)으로 중복을 거른다.
5. **`paymentId`는 재사용하지 않는다.** 결제 실패 뒤 다시 시도하면 `payment` 행을 새로 만든다(`attempt + 1`). 포트원 쪽 상태와 우리 행이 1:1이어야 조회·취소가 헷갈리지 않는다. **한 주문에 살아 있는(`READY`) 결제는 항상 하나다** — 새 시도는 이전 `READY`를 `SUPERSEDED`로 내린 뒤에만 만든다(5-1).
6. **주문이 "어느 결제로" 완료됐는지 기록한다** — `orders.paid_payment_id`. 포트원이 `PAID`라고 해도 그 결제가 주문의 결제가 아니면(이전 시도가 뒤늦게 결제됨) 자동 취소 대상이다.
7. **외부 호출은 DB에서 선점한 뒤 부른다.** 취소·자동 취소는 `payment` 행을 `CANCEL_REQUESTED`로 조건부 전이한 쪽만 포트원을 부른다. 동시 호출은 둘째가 0행이라 외부로 나가지 않는다.
8. **결과를 모르는 외부 호출은 실패로 적지 않는다.** 취소 API 타임아웃은 "취소됐을 수도, 안 됐을 수도" 있는 상태다. `CANCEL_REQUESTED`로 두고 웹훅·포트원 재조회로 수렴시킨다. `FAILED`는 포트원이 명시적으로 거절한 경우뿐이다.

### 2-4. 앱 결제창 — React Native SDK

앱은 React Native다. 포트원 `@portone/react-native-sdk`의 `<Payment request={…} onComplete={…} onError={…} />`를 쓴다. SDK 소스(`SdkDelegate.tsx`)로 확인한 동작은 다음과 같다.

```
1. SDK가 react-native-webview 안에 브라우저 SDK(cdn.portone.io/v2/browser-sdk.js)를 띄우고 requestPayment를 부른다
2. request의 redirectUrl은 SDK가 'portone://blank'로 덮어쓴다 — 앱·서버가 정할 수 없다
3. 결제창이 끝나 portone://blank?paymentId=…&code=…&message=…로 이동하면
   onShouldStartLoadWithRequest가 가로채 쿼리를 객체로 풀어 onComplete(response)를 부른다
4. 간편결제·카드사 앱 스킴(intent:// · kakaotalk:// · supertoss:// …)은 SDK가 Linking으로 열고,
   없으면 스토어로 보낸다. 앱 링크 목록은 SDK 플러그인이 AndroidManifest·Info.plist에 넣는다
```

- **서버 리다이렉트 엔드포인트는 두지 않는다.** 결제 결과는 앱 안에서 `onComplete`로 끝나고, 앱은 그 `paymentId`로 `POST /v1/user/payments/{paymentId}/complete`를 부른다. `onComplete`의 `code`·`message`는 5-4의 `clientResult`에 실어 보낸다.
- **`onComplete`는 힌트일 뿐이다.** 웹뷰가 죽거나 앱이 백그라운드로 내려가 `onComplete`가 오지 않아도 웹훅이 주문을 `PAID`로 올린다(2-1). 앱은 결제 화면으로 돌아왔을 때 `GET /v1/user/orders/{orderId}`로 상태를 다시 읽는다.
- **iOS 앱 스킴 상한.** iOS 15 이상은 `LSApplicationQueriesSchemes`를 50개까지만 읽는다. SDK 플러그인 목록이 넘치면 카카오톡·네이버·토스·카드사 앱 스킴만 골라 직접 넣는다 — 앱 팀 작업이지만 결제 실패 문의가 오면 먼저 볼 곳이다.
- 서버가 앱에 내리는 `payment` 블록(5-3)에는 `redirectUrl`이 없다. SDK가 무시하므로 넣어도 해가 없지만, 있으면 "서버가 리다이렉트를 받는다"는 오해를 낳는다.


- **`cart.group_buy_id`** — **가격 계획서로 구현됨(V142 · 가격 계획서 3-1·9-4).** 유니크 `(user_id, variant_id, group_buy_id)`. 같은 옵션이라도 공구가 다르면 다른 줄이다 — 리워드가 다른 사람에게 가는 두 건이다. 주문은 이 값을 그대로 귀속으로 쓴다.
- **`order_delivery_group`의 키는 공구다.** C8 주석대로 배송비·마감일·발송 시점이 공구마다 다르다. 배송비 자체는 그 공구의 마켓 설정(`Market.defaultDeliveryFee`·`freeShippingThreshold`)에서 읽는다. 주문에 총액 하나만 남기면 "이 공구 배송비가 얼마였나"를 나중에 복원할 수 없고, 정산·판매 관리가 공구별 배송비를 못 읽는다.
- **`order_product.group_buy_id`** — `GroupBuySalesReader` 주석이 "주문에 공구 귀속이 필요하다 — 지금은 없다"고 적어 둔 바로 그 컬럼이다. 그룹에도 있지만 상품 행에 비정규화해 두는 것은 판매 집계 쿼리가 조인 없이 돌아야 하기 때문이다. 컬럼은 **nullable**이지만 기존 리뷰용 시드 행 백필 때문일 뿐이고, 신규 행은 서비스가 항상 채운다 — 귀속 미정 주문 경로는 없다(4-6).
- **배송지는 스냅샷**이다. `DeliveryAddress`를 FK로 걸면 사용자가 배송지를 지우거나 고친 뒤 주문 상세가 바뀐다. 계약이 상품명·정가를 복사하는 것과 같은 이유다(`ContractItem` 주석).
- **`payment.payment_id`는 문자열 PK**다 — 포트원 `paymentId`와 같은 값이라 웹훅·조회에서 조인 없이 바로 찾는다.

## 4. 상태 규칙

### 4-1. 주문 상태 — `OrderStatus`

```
PAYMENT_PENDING ──complete/webhook(PAID·금액 일치)──▶ PAID ──사용자 취소(배송 전)──▶ CANCELLED
      │                                                 │
      ├── 만료 스케줄러(expires_at 경과) ──▶ EXPIRED      └── (다음 단계: 배송 상태는 order_product에서)
      └── 사용자 취소(결제 전) ──────────▶ CANCELLED

* PAYMENT_PENDING에서 결제 실패는 주문 상태를 바꾸지 않는다 — payment 행만 FAILED가 되고 다시 시도할 수 있다.
* EXPIRED · CANCELLED 뒤에 PAID 결제가 발견되면 주문은 그대로 두고 결제만 자동 취소한다(2-3 ③).
```

| 전이 | 조건부 UPDATE (`WHERE status = …`) | 부수 효과 (같은 트랜잭션) |
| --- | --- | --- |
| → `PAID` | `status = 'PAYMENT_PENDING'` → `status = 'PAID', paid_payment_id = :paymentId, paid_at = now` | `order_product.status = PAID`, 장바구니에서 해당 항목 삭제(`order_product.cart_id`로), `OrderPaidEvent` 등록(커밋 뒤 발행) |
| → `EXPIRED` | `status = 'PAYMENT_PENDING' AND expires_at <= now` | 재고 복원(1회 규칙), `order_product.status = CANCELLED`, `payment READY` → `EXPIRED` |
| → `CANCELLED` (결제 전) | `status = 'PAYMENT_PENDING'` | 재고 복원, `payment READY` → `CANCELLED` |
| → `CANCELLED` (결제 후) | `status = 'PAID' AND 배송 전` | **포트원 취소가 확인된 뒤**에 전이(5-6). 재고 복원 |
| → `CANCELLED` (PG 측 취소 수렴) | `status = 'PAID' AND paid_payment_id = :paymentId` | confirm이 포트원 `CANCELLED`를 읽었을 때(4-5 ⑤). 재고 복원 |

- 모든 전이는 **리포지토리 조건부 UPDATE**로 경합을 막고, 통과한 트랜잭션만 엔티티 부수 필드를 채운다 — 공구 상태 전이(`GroupBuy` 주석 · 설계서 3-4)와 같은 방식이다. `@Version`은 두지 않는다. 웹훅과 complete가 동시에 와서 둘 중 하나가 낙관적 락 예외로 500을 내는 것보다 0행 갱신으로 조용히 끝나는 쪽이 맞다.
- **부수 효과는 전이와 같은 트랜잭션**이다. 장바구니 삭제가 별도 트랜잭션이면 둘째 호출이 또 지우려다 없는 행을 만나거나, 전이는 됐는데 장바구니가 남는다. `order_product`에 `cart_id`(nullable) 스냅샷을 두어 "그 주문이 어느 장바구니 행에서 왔는지"로 지운다 — `cartItemIds`를 다시 받지 않는다.
- **`OrderProductStatus`** 는 `PENDING`(결제 대기) · `PAID`(신규) · `PURCHASE_CONFIRMED` · `CANCELLED`. `UserService`의 탈퇴 차단은 `NOT IN (PURCHASE_CONFIRMED, CANCELLED)`라 `PENDING`·`PAID`가 모두 "진행 중"으로 잡힌다. 만료된 주문은 `CANCELLED`로 내려가므로 30분 넘게 탈퇴를 막는 일은 없다.

### 4-2. 결제 상태 — `PaymentStatus`

```
READY ──▶ PAID
  ├────▶ FAILED              (포트원 FAILED · 웹훅 Transaction.Failed)
  ├────▶ EXPIRED             (주문 만료 · 결제창 미완료)
  ├────▶ SUPERSEDED          (재시도로 새 paymentId 발급 — 이 시도는 더 이상 주문의 결제가 아니다)
  └────▶ CANCELLED           (결제 전 주문 취소)
SUPERSEDED ──▶ PAID          (이전 시도가 뒤늦게 결제됐는데 주문이 아직 PAYMENT_PENDING — 주문의 결제로 받아들인다)
PAID ──▶ CANCEL_REQUESTED ──▶ CANCELLED            (사용자·운영자 취소 · 포트원 취소 확인 뒤)
                           ├▶ PAID                 (사용자 취소를 포트원이 명시적으로 거절 — payment_cancel FAILED · 주문은 그대로)
                           └▶ CANCEL_FAILED        (자동 취소를 포트원이 명시적으로 거절, 또는 재시도 상한 도달 — 운영자 처리 대기 · 종결)
PAID ──▶ CANCEL_REQUESTED ──▶ CANCELLED_MISMATCH   (금액 불일치 · 만료 후 결제 · 다른 시도가 이미 완료 → 시스템 자동 취소)
SUPERSEDED · EXPIRED · CANCELLED 상태에서 포트원 PAID 발견 ──▶ CANCEL_REQUESTED ──▶ CANCELLED_MISMATCH
```

- **`CANCEL_REQUESTED`는 선점 표시**다. 포트원 취소 API는 이 전이를 통과한 트랜잭션이 커밋된 뒤에만 부른다. 동시에 취소를 누르거나 confirm 둘이 동시에 불일치를 판정해도 외부 호출은 한 번이다(4-7).
- **`CANCEL_FAILED`는 "시스템이 돌려주지 못한 돈"** 이다. 자동 취소를 포트원이 거절했거나(예: PG 정산 마감 뒤라 취소 불가) 수렴 재시도가 상한에 닿은 결제다. 사용자에게 돌려줘야 할 돈이 PG에 묶여 있으므로 Sentry `error` + 운영 대시보드 첫 줄(4-8)에 오르고, 운영자가 PG 콘솔에서 처리한 뒤 상태를 닫는다. 이 상태가 없으면 수렴 루프가 영원히 돈다.
- **종결 상태**(`PAID`·`FAILED`·`CANCELLED`·`CANCELLED_MISMATCH`·`CANCEL_FAILED`)에서는 confirm이 포트원을 부르지 않는다. **`SUPERSEDED`·`EXPIRED`는 "뒤늦게 결제됐을 수 있는" 상태**라 confirm이 어느 경로(complete·웹훅)로 오든 한 번은 조회한다 — 옛 결제창의 `onComplete`가 앱에서 complete를 부르는 경우가 실제로 있고, 그때 단락시키면 앱은 "실패"로 그리고 사용자는 다시 결제한다. 비용은 조회 1회다.
- **`SUPERSEDED`가 결제되면 주문의 결제로 받아들인다.** 재시도 뒤 이전 창이 먼저 결제를 끝내는 경우다. 주문이 아직 `PAYMENT_PENDING`이면 그 돈은 이 주문의 돈이 맞고, 환불했다가 다시 받게 하는 것보다 낫다. 새 시도가 뒤이어 결제되면 `paid_payment_id` 불일치로 그쪽이 자동 취소된다. 주문의 결제가 항상 "가장 최근 시도"라는 보장은 **없고**, "정확히 하나"라는 보장만 있다.

포트원 `status`와의 대응:

| 포트원 | 우리 `payment` | 주문 |
| --- | --- | --- |
| `READY` / `PENDING` | 그대로 | 그대로 |
| `PAID` | 4-5 ③ 검증 → `PAID` 또는 자동 취소 | `PAYMENT_PENDING` → `PAID`(내 결제일 때만) |
| `FAILED` | `FAILED` | 그대로 — 재시도 가능 |
| `CANCELLED` | `CANCELLED`(`CANCEL_REQUESTED`였으면 수렴) · `CANCELLED_MISMATCH`(자동 취소였으면) | 주문 `PAID` ∧ `paid_payment_id` = 이 결제 → **주문 `CANCELLED` + 재고 복원**(PG 콘솔 취소·타임아웃 수렴). 주문 `PAYMENT_PENDING` → 그대로(재시도 가능) |
| `PARTIAL_CANCELLED` | 이번 범위 밖 — 로그 + Sentry 경고, 상태 유지 | 그대로 |
| `VIRTUAL_ACCOUNT_ISSUED` | 채널을 열지 않아 오지 않는다 — 오면 경고 | 그대로 |

### 4-3. 재고 — 주문 생성 시 예약

```sql
UPDATE product_variant SET stock = stock - :qty
 WHERE variant_id = :id AND stock >= :qty
```

- 0행이면 `INSUFFICIENT_STOCK`. 한 주문의 여러 항목 중 하나라도 실패하면 트랜잭션을 롤백해 앞서 차감한 것도 되돌린다.
- **`variant_id` 오름차순으로 차감한다.** 항목이 여럿인 주문 둘이 A,B와 B,A 순으로 잠그면 MySQL 데드락이다. 정렬하면 잠금 순서가 같아져 한쪽이 기다렸다 통과한다.
- **복원은 주문당 1회다.** `StockReleaser.release(orderId)`는 먼저 `UPDATE orders SET stock_released_at = now WHERE order_id = :id AND stock_released_at IS NULL`을 치고, **1행일 때만** 항목마다 `stock = stock + :qty`를 한다. 만료·취소·불일치 취소 세 경로가 같은 메서드를 쓰지만, 이미 `EXPIRED`로 복원된 주문에 뒤늦게 결제가 도착해 자동 취소되는 경로에서는 0행이라 **두 번 늘지 않는다**.
- `is_out_of_stock_forced`(관리자 강제 품절)는 차감과 무관하게 주문 생성 검증에서 막는다(`CartService.unavailableReason`과 같은 판정).
- 재고가 0이 되면 `GroupBuySaleState`(공구 게시물 배지)와 C7 `isOutOfStock`이 **저장 없이 파생**되므로 별도 동기화가 없다.

### 4-4. 만료 스케줄러

`OrderExpirationScheduler` — 1분 주기(`0 * * * * *`, KST), `GroupBuyLifecycleScheduler`와 같은 골격(단일 인스턴스 · 행마다 별도 트랜잭션 · 1회 상한 200건 · 예외는 로그 후 다음 회차). `groupbuy.scheduler-enabled`처럼 `order.expiration-scheduler-enabled`로 통합 테스트에서 끈다.

```
findIdsToExpire: status = PAYMENT_PENDING ∧ expires_at <= now   (인덱스 (status, expires_at))
expire(id):      ① 살아 있는 payment(READY)가 있으면 포트원 GET 1회 (트랜잭션 밖)
                    PAID          → 만료하지 않고 confirm(paymentId)로 넘긴다 (잃어버린 결제 구제)
                    PENDING       → 승인 진행 중(카드사 인증 등). 만료를 미룬다 — expires_at += 5분, 최대 3회
                    404 · READY   → ② (404는 "사전 등록만 되고 결제창을 연 적 없음" — 가장 흔한 만료 사유)
                    통신 실패     → expiry_check_failures += 1. 3 미만이면 이번 회차 건너뜀, 3이면 ②
                 ② 조건부 UPDATE(PAYMENT_PENDING → EXPIRED) → 재고 복원(1회 규칙) → payment READY → EXPIRED
```

- **만료 전 포트원 1회 조회**가 "잃어버린 결제" 보정이다. complete도 웹훅도 안 온 결제(앱 종료 + 웹훅 유실)를 자동 취소해 버리는 대신 살린다. 비용은 만료 건당 조회 1회다.
- **404를 조회 실패로 다루지 않는다.** 대부분의 만료 주문은 C9에서 이탈해 결제창을 연 적이 없는 주문이고, 포트원은 사전 등록만 된 `paymentId`에 404 또는 `READY`를 돌려준다(어느 쪽인지는 구현 때 실 응답으로 확인 — 9절 미결 ⑫). 둘 다 "결제 안 됨"이라 즉시 만료한다. 이걸 통신 실패로 세면 모든 만료가 3분씩 늦어진다.
- **`PENDING`이면 만료를 미룬다.** 29분 50초에 결제창을 열어 카드사 인증 중인 소비자를 30분 정각에 만료시키면 3분 뒤 승인된 결제를 자동 취소·환불하게 된다. 돈은 안 새지만 "결제했는데 취소됨"이다. `expires_at`을 5분씩 최대 3회 미룬다(`expiry_deferrals` 컬럼). 그래도 안 끝나면 만료하고 2-3 ③에 맡긴다. 앱 쪽 규칙도 필요하다 — `expiresAt` 5분 전부터 결제 CTA를 잠그고 "주문 시간이 만료됐어요. 다시 주문해 주세요"를 띄운다(앱 팀 전달).
- 만료 직전에 결제가 성공해 웹훅이 스케줄러 뒤에 도착하는 경합은 ①과 2-3 ③으로 닫힌다.
- 만료된 주문의 `payment`가 포트원에서 아직 `READY`면 굳이 포트원에 취소를 보내지 않는다. 승인되지 않은 결제는 취소 대상이 아니다.
- **같은 스케줄러의 둘째 단계 — 취소 수렴.** `payment.status = CANCEL_REQUESTED ∧ next_cancel_retry_at <= now`인 행을 포트원에 재조회한다.

```
포트원 CANCELLED            → 4-5 ⑤로 수렴 (CANCELLED 또는 CANCELLED_MISMATCH)
포트원 PAID                 → 취소 API 재호출 (멱등 — "이미 취소됨"은 성공)
                              성공 → 수렴 · 명시적 거절 → CANCEL_FAILED · 타임아웃 → 아래 재시도 규칙
재시도 규칙                 cancel_attempts += 1 · next_cancel_retry_at = now + 2분 × 2^(attempts−1)  (2·4·8·16·32분)
                              cancel_attempts = 5 도달 → CANCEL_FAILED + Sentry error
```

- 취소 타임아웃(5-6)이 여기서 풀린다. **끝이 있어야 한다** — 상한 없이 2분마다 부르면 포트원 장애 때 호출이 쌓이고, 정산 마감으로 영구 거절되는 결제는 영원히 돈다. `CANCEL_FAILED`는 "시스템이 못 했으니 사람이 하라"는 종결이다.
- 첫 재조회 2분·상한 5회는 잠정값이다(9절 미결 ⑪).

### 4-8. 일일 대사 · 운영 가시성

4-1~4-7의 장치는 전부 **"요청이 우리 서버에 도달했다"** 를 전제한다. 웹훅이 포트원 재시도 상한까지 실패하고, 앱도 죽고, 만료 전 조회도 통신 장애로 3회 실패하면 포트원에는 `PAID`인데 우리 DB에는 `EXPIRED`인 결제가 남고 **아무 장치도 그것을 다시 보지 않는다.** 마지막 안전망은 정기 대사다.

**`PaymentReconciliationScheduler`** — 매일 05:00 KST, 전날 00:00~24:00(KST) 구간을 대사한다. `order.reconciliation-enabled`로 끈다.

```
① 포트원 결제 목록 API로 구간의 결제 전량 조회 (status ∈ PAID · CANCELLED · PARTIAL_CANCELLED, 페이지네이션)
② payment 테이블의 같은 구간(created_at 기준 ± 1일 여유)과 paymentId로 대조
③ 어긋남 4종을 payment_reconciliation_issue 에 INSERT (같은 paymentId·kind는 갱신)
   PORTONE_PAID_NOT_OURS      포트원 PAID · 우리 status ∉ {PAID, CANCEL_REQUESTED}   → 즉시 confirm(paymentId) 호출로 자동 수렴 시도, 안 되면 남긴다
   PORTONE_CANCELLED_NOT_OURS 포트원 CANCELLED · 우리 status ∈ {PAID}               → 즉시 confirm 호출(4-5 ⑤)
   OURS_PAID_NOT_PORTONE      우리 PAID · 포트원에 없거나 PAID 아님                  → 사람이 본다 (있어서는 안 되는 상태)
   AMOUNT_DIFF                둘 다 PAID인데 금액 다름                                → 사람이 본다
④ 결과 요약(구간 건수 · 어긋남 건수 · 종류별)을 로그 + Sentry(어긋남 1건 이상이면 warning)
```

- **자동 수정은 confirm을 다시 부르는 것뿐이다.** confirm은 멱등이고 포트원을 다시 읽으므로, 대사가 발견한 건은 대부분 "confirm이 한 번도 안 불린" 건이라 그것으로 닫힌다. 그 밖은 사람이 본다 — 대사 배치가 상태를 직접 쓰기 시작하면 두 소스가 서로를 고치는 루프가 생긴다.
- 포트원 목록 API의 조회 구간·페이지 한도는 구현 때 확인한다(9절 미결 ⑫).

**운영 가시성** — 어드민 화면은 미결(9절 ⑧)이지만, 다음 다섯 값은 **첫 릴리스부터** 센다. `PaymentHealthScheduler`(10분 주기)가 조회해 임계값을 넘으면 Sentry `warning`을 올린다. 같은 쿼리를 운영자가 직접 돌릴 수 있게 `dev/` 아래 SQL로도 남긴다.

| 지표 | 쿼리 | 임계값 |
| --- | --- | --- |
| 취소 미수렴 | `payment.status = CANCEL_REQUESTED ∧ cancel_requested_at < now − 30분` | 1건 이상 |
| 운영자 처리 대기 | `payment.status = CANCEL_FAILED` (미해결) | 1건 이상 — 매 회차 반복 경고 |
| 자동 취소 발생 | `CANCELLED_MISMATCH` 최근 24시간 | 3건 이상 (1~2건은 정상 범위 — 만료 직후 결제) |
| 웹훅 처리 실패 | `payment_webhook_event.result = FAILED ∧ attempts >= 3` | 1건 이상 |
| 대사 미해결 | `payment_reconciliation_issue.resolved_at IS NULL` | 1건 이상 |

이 다섯 개가 0이면 결제 시스템이 스스로 수렴하고 있다는 뜻이고, 하나라도 0이 아니면 그 줄이 운영자가 오늘 볼 곳이다.

### 4-5. 결제 확정 — `PaymentConfirmService.confirm(paymentId)`

```
① payment 행 조회 — 없으면 PAYMENT_NOT_FOUND (웹훅이면 IGNORED로 기록)
② 단락 — payment.status ∈ {PAID, FAILED, CANCELLED, CANCELLED_MISMATCH, CANCEL_FAILED}면 포트원을 부르지 않고 현재 상태 반환.
   SUPERSEDED · EXPIRED는 경로(complete · 웹훅)와 무관하게 ③으로 (뒤늦은 결제 감지 — 4-2)
   CANCEL_REQUESTED는 ③으로 (수렴 기회)
③ 포트원 GET /payments/{paymentId}                                   ← 트랜잭션 밖
④ 포트원 PAID:
   검증 = storeId 일치 ∧ currency == KRW ∧ amount.total == payment.amount
   (a) 검증 통과 → 트랜잭션 {
         UPDATE orders SET status='PAID', paid_payment_id=:pid, paid_at=now
           WHERE order_id=:oid AND status='PAYMENT_PENDING'                    → n행
         n=1 → UPDATE payment SET status='PAID' WHERE payment_id=:pid AND status IN ('READY','SUPERSEDED')  → m행
               m=0 → 불변식 위반 (주문은 이 결제로 PAID인데 결제 행이 전이 불가 상태) → T4 롤백 + Sentry error
               m=1 → order_product PAID · 장바구니 삭제 · OrderPaidEvent 등록(AFTER_COMMIT)
         n=0 → 주문을 다시 읽는다:
               orders.paid_payment_id == :pid  → 이미 내가 완료한 것(둘째 호출). 아무것도 안 함
               그 밖(EXPIRED · CANCELLED · 다른 결제로 PAID) → (b)로
       }
   (b) 검증 실패 또는 "내 결제가 아님" → 트랜잭션 {
         UPDATE payment SET status='CANCEL_REQUESTED', cancel_requested_at=now, mismatch_reason=…
           WHERE payment_id=:pid AND status IN ('READY','PAID','SUPERSEDED','EXPIRED','CANCELLED')  → n행
       }
       n=1 → 커밋 뒤 포트원 전액 취소 호출(4-7 ③) → 성공·"이미 취소됨" → CANCELLED_MISMATCH · Sentry error
                                                    → 명시적 거절 → CANCEL_FAILED · Sentry error (운영자 처리)
                                                    → 타임아웃 → CANCEL_REQUESTED 유지, 4-4 둘째 단계가 수렴
       n=0 → 다른 호출이 이미 선점. 아무것도 안 함
⑤ 포트원 CANCELLED:
   UPDATE payment SET status = (mismatch_reason IS NULL ? 'CANCELLED' : 'CANCELLED_MISMATCH')
     WHERE payment_id=:pid AND status IN ('PAID','CANCEL_REQUESTED')           → 선점
   통과 시 UPDATE orders SET status='CANCELLED', cancelled_at=now
     WHERE order_id=:oid AND status='PAID' AND paid_payment_id=:pid            → 통과 시 재고 복원(1회 규칙)
   (주문이 PAYMENT_PENDING이면 결제만 CANCELLED — 재시도 가능)
⑥ 포트원 FAILED → UPDATE payment SET status='FAILED', fail_code, fail_message WHERE status='READY'
⑦ 포트원 READY/PENDING → 아무것도 하지 않음. 응답은 현재 주문 상태
⑧ raw_response 저장 — 상태 전이와 무관하게 별도 짧은 트랜잭션
```

- **잠금 순서**: `orders` 행을 `SELECT … FOR UPDATE`로 먼저 잡고 포트원을 호출하지 **않는다** — 외부 HTTP를 락 안에 두면 웹훅·complete가 서로를 수 초씩 기다린다. 포트원을 먼저 읽고, 전이는 조건부 UPDATE 하나로 끝낸다. 둘째 호출은 조회 결과가 같고 UPDATE 0행이라 그대로 현재 상태를 돌려준다.
- **④(a)의 `n=0` 분기가 이중 결제를 막는다.** 재시도로 두 결제창이 열려 둘 다 결제되면, 첫째가 `paid_payment_id`를 채우고 둘째는 0행 → "내 결제가 아님" → 자동 취소. `paid_payment_id` 없이 `status='PAID'`만 보면 둘째 confirm이 "이미 완료됐네"로 조용히 끝나 **돈이 두 번 들어온 채 남는다**.
- **④(b)의 선점이 이중 취소를 막는다.** confirm 둘이 동시에 불일치를 판정해도 `CANCEL_REQUESTED` 전이는 하나만 통과하고, 외부 취소 호출은 한 번이다.
- **②의 단락이 complete 남용을 막는다.** 앱이 완료 화면에서 complete를 반복해 불러도 종결된 결제는 포트원으로 나가지 않는다.
- 앱이 보낸 결제창 결과(성공·실패 코드)는 **로그·`payment.fail_code` 힌트로만** 쓴다. 포트원 조회가 `FAILED`가 아닌데 앱이 실패라고 하면 조회 결과를 따른다.

### 4-6. 공구 귀속 · 상태 판정 시점

**귀속은 진입 경로가 정한다.** 한 상품이 진행 중 공구 둘에 걸리는 것은 정상이다 — 크리에이터 둘이 같은 브랜드 상품을 각자 공구로 판다. 이때 "어느 공구의 주문인가"는 리워드(`contract_item.reward_rate`가 계약마다 다르다)·판매 실적·정산 게이트·중단 판정을 가르는 값이고, 그 답은 **소비자가 어느 게시물에서 왔느냐**다. 서버가 "지금 진행 중인 공구" 중에서 고르는 것은 추측이다.

```
C5 공구 게시물 ─▶ C7 상품 상세 (?groupBuyId=41) ─▶ 장바구니 담기 { variantId, quantity, groupBuyId: 41 }
                                                ─▶ 바로 구매     { variantId, quantity, groupBuyId: 41 }
                                                                          │
                                        주문 생성: 항목의 groupBuyId를 검증만 한다 ◀┘
```

| 진입 | `groupBuyId` | 주문 생성이 하는 일 |
| --- | --- | --- |
| C5 → C7 → 담기·바로 구매 (정상 경로) | 있음 | 판정 순서는 `CartService.requirePurchasable`과 같다(공구 → 계약 옵션 → 상품 → 재고). ① `group_buy.isOngoing(now)` ② 그 공구 계약에 **이 옵션**이 있음 — `GroupBuyPriceResolver.resolveVariants(groupBuyId, variantIds)`에 없으면 「이 공구에서 판매하지 않는 옵션이에요」 ③ 상품 자체가 구매 가능 — 하나라도 아니면 `CART_ITEM_NOT_PURCHASABLE` |
| 바로 구매에 `groupBuyId` 없음 | 없음 | `INVALID_INPUT_VALUE` — 「공구를 지정해 주세요」(장바구니 담기와 같은 문구) |
| 장바구니의 귀속 없는 옛 행 | NULL | 장바구니에서 `GROUP_BUY_CLOSED`로 선택되지 않는다. 요청에 섞여 오면 `CART_ITEM_NOT_PURCHASABLE` |

- **귀속 미정 주문 경로는 없다(2026-09-27 변경).** 공구가 둘이면 단가도 둘이라 귀속 미정 주문은 단가 미정 주문이다(가격 계획서 6절·9-1 ④). 장바구니 담기가 이미 `groupBuyId`를 필수로 받으므로 바로 구매도 맞춘다. 서버가 「진행 중 공구가 1개면 그것」을 추측하는 코드는 두지 않는다.
- 검증 ②가 있어야 한다 — `groupBuyId`는 앱이 보내는 값이라 조작될 수 있다. 다른 브랜드의 공구를 실어 와도 그 계약에 이 옵션이 없어 여기서 걸린다.
- C7 상세 API는 `groupBuyId`를 받아 응답에 그대로 되돌려 주고(7-3), 앱은 담기·바로 구매에 그 값을 싣는다. 주문서 응답의 `groups[].groupBuyId`도 이 값이다.

**상태 판정은 주문 생성 시각이 기준**이다. 항목마다 `product.groupBuyStatus.isPurchasable()`(진행중만) ∧ `displayStatus.isVisible()` ∧ 귀속 공구 `group_buy.isOngoing(now)`를 검사한다.
- 주문 뒤 30분 안에 공구가 끝나도 결제는 유효하다. 마감 직전에 주문한 소비자가 결제창에서 튕겨 나오면 안 된다. 공구 명세서 §16조④2도 "중단 집행 이전 결제 완료 정상 주문"을 인정한다.
- 직권 중단(`SUSPENDED`) 집행 뒤의 `PAID` 주문은 그대로 둔다 — 취소·환불은 "브랜드가 부담 · 판매 관리에서 개별 처리"(명세서 29-4). 공구 모듈은 주문을 건드리지 않는다.

### 4-7. 트랜잭션 경계

원칙 하나 — **외부 HTTP는 트랜잭션 안에 두지 않는다.** DB에서 선점(조건부 UPDATE)하고 커밋한 뒤 부르고, 결과를 별도 짧은 트랜잭션으로 적는다. 아래 표가 경계의 전부다. `@Transactional` 메서드 안에서 게이트웨이를 호출하는 코드는 리뷰에서 막는다.

| 흐름 | 트랜잭션 | 커밋 뒤 | 실패 시 |
| --- | --- | --- | --- |
| ① 주문 생성 (5-3) | T1 `REQUIRES_NEW`: 주문번호 시퀀스 행 잠금 → 번호 채번 → 커밋 (번호 공백 허용) <br> T2: 항목 검증 → 재고 차감(정렬) → `orders`·그룹·상품·`payment READY` INSERT | 포트원 사전 등록 → 성공 시 T3: `payment.pre_registered_at` | T2 실패 → 전부 롤백(재고 포함). 사전 등록 실패 → 주문은 남고 502, 재요청이 다시 시도(5-3) |
| ② 결제 확정 (4-5) | 없음 — 포트원 GET | T4: 조건부 전이 + 부수 효과(장바구니·`order_product`·이벤트 등록) <br> T5: `raw_response` 저장 | 포트원 GET 실패 → 502, 상태 불변 |
| ③ 자동 취소 (4-5 ④b) | T6: `payment → CANCEL_REQUESTED` 선점 | 포트원 취소 → T7: `CANCELLED_MISMATCH` + `payment_cancel` | 타임아웃 → T7 없음. 4-4 둘째 단계가 수렴 |
| ④ 사용자 취소 (5-6) | T8: 주문 `PAID` 검증 + `payment → CANCEL_REQUESTED` 선점 + `payment_cancel REQUESTED` INSERT | 포트원 취소 → T9: 조건부 전이(주문 `CANCELLED` · 결제 `CANCELLED` · `payment_cancel SUCCEEDED`) + 재고 복원 | 거절 → T9': `payment → PAID` 복귀 · `payment_cancel FAILED`. 타임아웃 → 그대로, 스케줄러 수렴 |
| ⑤ 만료 (4-4) | 없음 — 포트원 GET(살아 있는 결제가 있을 때) | T10: 조건부 전이 + 재고 복원 + `payment → EXPIRED`. `PENDING`이면 T10' `expires_at += 5분, expiry_deferrals += 1` | GET 실패 → T10'' `expiry_check_failures += 1`, 3 미만이면 이번 회차 건너뜀 |
| ⑧ 취소 수렴 (4-4 둘째) | 없음 — 포트원 GET | `CANCELLED` → T9와 같은 전이. `PAID` → 취소 재호출 → 성공 시 T9 · 거절·상한 시 T15: `CANCEL_FAILED` · 타임아웃 시 T15': `cancel_attempts += 1, next_cancel_retry_at` | 외부 실패는 전부 T15'로만 기록 |
| ⑨ 일일 대사 (4-8) | 없음 — 포트원 목록 GET | 어긋남마다 T16: `payment_reconciliation_issue` UPSERT → `confirm(paymentId)`(②) | 목록 조회 실패 → 이번 날 건너뛰고 Sentry warning |
| ⑥ 웹훅 (5-7) | T11 `REQUIRES_NEW`: 이벤트 행 INSERT(`RECEIVED`) 또는 재수신 갱신 | confirm(②) → T12: 이벤트 `PROCESSED`/`IGNORED`/`FAILED` | ② 예외 → T12에 `FAILED` + 응답 코드는 5-7 규칙 |
| ⑦ 결제 재시도 (5-1) | T13: `payment READY → SUPERSEDED` 조건부 UPDATE(0행이면 `PAYMENT_ALREADY_IN_PROGRESS` 아님 — 살아 있는 결제가 없으면 그냥 진행) → `MAX(attempt)+1` → 새 `payment READY` INSERT | 포트원 사전 등록 → T14: `pre_registered_at` | ① 과 같다 |

- **`OrderPaidEvent`는 `@TransactionalEventListener(AFTER_COMMIT)`** 으로 받는다. 알림·정산 훅이 T4 안에서 실패해 결제 확정이 롤백되면 안 되고, 커밋 전에 나가면 수신자가 아직 없는 주문을 읽는다.
- **주문번호 채번을 `REQUIRES_NEW`로 떼는 이유** — 시퀀스 행 잠금을 T2와 합치면 재고 차감·INSERT가 끝날 때까지 다른 주문이 번호를 못 받아 주문 생성이 직렬화된다. 계약·공구 번호는 빈도가 낮아 합쳐도 됐지만 결제는 다르다. T2가 롤백되면 번호 하나가 비는데, 주문번호는 연속성을 약속한 적이 없다.
- **`idempotency_key` 유니크 위반은 예외가 아니라 신호**다. 같은 키의 요청 둘이 동시에 "기존 없음"을 통과하면 둘째 INSERT가 `DataIntegrityViolationException`으로 터진다. 이걸 잡아 기존 주문을 다시 읽어 첫 응답과 같은 것을 돌려준다(5-3). 500으로 올리면 앱은 "주문 실패"로 그리는데 실제로는 주문이 있다.
- 스케줄러는 기존과 같이 단일 인스턴스·분산 락 없음이다. 모든 단계가 조건부 UPDATE라 인스턴스가 둘이 돼도 이중 전이는 없고, 이중 **외부 호출**만 선점(③④)이 막는다.

### 5-2. `POST /v1/user/orders/checkout` — 주문서

**요청** — 두 진입 중 하나만 채운다. 둘 다 있거나 둘 다 없으면 `INVALID_INPUT_VALUE`.

```json
{ "cartItemIds": [11, 12, 15] }
{ "direct": { "variantId": 301, "quantity": 1, "groupBuyId": 41 } }
{ "cartItemIds": [11], "deliveryAddressId": 7 }
```

- 장바구니 진입은 `groupBuyId`를 따로 받지 않는다 — `cart.group_buy_id`에 이미 있다. 바로 구매는 `groupBuyId`가 **필수**다 — 없으면 400(4-6).
- `deliveryAddressId` 생략 시 기본 배송지. 기본 배송지도 없으면 `deliveryAddress: null` — C9 「배송지 없음」 상태를 그린다(에러가 아니다. 주문서는 열리고 CTA만 잠긴다).
- 장바구니 항목 중 살 수 없는 것(마감·품절)이 섞여 있으면 **`CART_ITEM_NOT_PURCHASABLE`로 막는다**. C8은 그 항목을 선택에서 빼고 있어 정상 경로에서는 오지 않는다. 주문서에서 조용히 빼면 금액이 이유 없이 준다.

**응답**

```json
{
  "deliveryAddress": { "id": 7, "recipientName": "김수민", "phoneNumber": "010-1234-5678",
                       "zipCode": "06234", "address": "서울 강남구 테헤란로 000", "detailAddress": "쇼룸타워 12층 1203호",
                       "memo": "문 앞에 놓아주세요", "isDefault": true },
  "memoPresets": ["문 앞에 놓아주세요", "경비실에 맡겨주세요", "부재 시 연락해주세요", "배송 전 미리 연락해주세요"],
  "groups": [
    { "marketId": 3, "marketName": "라보에이치", "groupBuyId": 41,
      "items": [ { "cartId": 11, "variantId": 301, "productId": 120, "productName": "시카 리페어 앰플 30ml 리필 2개 세트 기획",
                   "optionName": "용량: 30ml + 리필 2개", "thumbnailUrl": "…", "quantity": 1,
                   "price": { "regularPrice": 38000, "salePrice": 24900, "discountRate": 34 } } ],
```

- `summary`의 네 값이 C9 「결제 금액」 4줄이다. `price`·`discountRate`는 `ProductDto.PriceInfo`·`DiscountRate.of`를 그대로 쓴다.

### 5-3. `POST /v1/user/orders` — 주문 생성

**요청**

```json
{
  "idempotencyKey": "5f1e…-uuid",
  "cartItemIds": [11, 12, 15],            // 또는 "direct": { "variantId", "quantity", "groupBuyId" }
  "deliveryAddressId": 7,
  "deliveryMemo": "문 앞에 놓아주세요",
  "payment": { "method": "CARD", "cardIssuer": "SHINHAN" }
  // 또는 "payment": { "method": "EASY_PAY", "easyPayProvider": "KAKAOPAY" }
}
```

- 검증 순서: 배송지 소유 → 항목 구매 가능·공구 귀속(4-6) → 수량 상한(`CartDto.MAX_QUANTITY`) → 금액 계산 → 재고 차감(4-3, 정렬) → `orders`·그룹·상품·`payment READY` 저장 → **커밋** → 포트원 사전 등록 → `pre_registered_at` 기록(4-7 ①). 사전 등록 실패는 주문을 롤백하지 않고 `PAYMENT_GATEWAY_ERROR`(502)를 낸다 — 재고는 잡혀 있고 주문은 만료 스케줄러가 정리하거나, 앱이 같은 키로 재요청하면 다시 시도한다.
- **`idempotencyKey` 처리** — 같은 `(user_id, idempotencyKey)`의 주문이 있으면 새로 만들지 않고 그 주문으로 응답을 **다시 조립**해 돌려준다(첫 응답을 저장해 두지 않는다 — `channelKey`·`storeId`는 설정에서, 나머지는 주문에서 나온다). 그 주문의 `payment`가 `pre_registered_at IS NULL`이면 사전 등록을 다시 시도한다. 포트원이 "이미 등록된 paymentId"로 거절하면 등록 금액이 같을 때 성공으로 본다. 만료·취소된 주문이면 `ORDER_ALREADY_CLOSED`. 동시 요청 둘이 모두 INSERT에 들어가면 둘째의 유니크 위반을 잡아 같은 경로로 돌려보낸다(4-7).
- 앱이 보낸 `totalAmount`는 **받지 않는다**. 대신 주문서 응답의 `totalAmount`를 `expectedTotalAmount`로 보내게 해 서버 계산과 다르면 `ORDER_AMOUNT_CHANGED`(409)로 알린다 — 주문서를 열어 둔 사이 가격·배송비가 바뀐 경우 화면을 새로 그리게 한다.

**응답**

```json
{
  "orderId": 1147, "orderNumber": "20260927-000123", "status": "PAYMENT_PENDING", "expiresAt": "2026-09-27T14:41:00",
  "payment": {
    "paymentId": "20260927-000123-1", "storeId": "store-…", "channelKey": "channel-key-…",
    "orderName": "시카 리페어 앰플 30ml 리필 2개 세트 기획", "totalAmount": 27900, "currency": "KRW",
    "payMethod": "CARD", "cardCompany": "…", "easyPayProvider": null,
    "customer": { "fullName": "김수민", "phoneNumber": "010-1234-5678", "email": "…" }
  }
}
```

`expiresAt`은 KST `yyyy-MM-dd'T'HH:mm:ss`다 — `CartGroup.endAt`과 같은 `@JsonFormat`을 단다. 전역 Jackson 설정이 UTC라 형식 없이 내리면 KST 값이 UTC로 읽힌다. 5-5의 `paidAt`도 같다.

앱은 `payment` 블록을 RN SDK `<Payment request>`에 그대로 넘긴다. **금액을 앱이 조립하지 않는다.** `redirectUrl`은 SDK가 정하므로 내리지 않는다(2-4).

### 5-4. `POST /v1/user/payments/{paymentId}/complete`

**요청** `{ "clientResult": { "code": null, "message": null, "txId": "…" } }` — RN SDK `onComplete`가 돌려준 값. 없어도 된다(앱 재진입 후 재확인).

**응답** `{ "orderId", "orderNumber", "orderStatus": "PAID" | "PAYMENT_PENDING" | "EXPIRED" | "CANCELLED", "paymentStatus": "PAID" | "FAILED" | "READY" | …, "failReason": "…" }`

- 4-5의 결과를 그대로 돌려준다. `orderStatus`가 `PAID`면 앱은 완료 화면, `paymentStatus`가 `FAILED`면 C9로 돌아가 재시도(5-1 결제 재시도), `PAYMENT_PENDING`+`READY`면 결제창이 아직 열린 것으로 보고 잠시 뒤 다시 부른다.
- 본인 주문만(`orders.user_id`). 아니면 `ORDER_ACCESS_DENIED`.

### 5-5. `GET /v1/user/orders/{orderId}`

주문서 응답과 같은 모양의 `groups`·`summary`에 `status`·`orderNumber`·`paidAt`·`deliveryAddress`(스냅샷)·`deliveryMemo`·`payment`(수단 라벨 · 카드사/간편결제 · `paidAt`)를 더한다. `InquiryOrderSummary`(1:1 문의의 주문 카드)와 마이 「주문 내역」이 이 응답을 재사용한다.

### 5-6. `POST /v1/user/orders/{orderId}/cancel`

`{ "reason": "…" }`. `PAYMENT_PENDING`이면 즉시 취소(조건부 전이 + 재고 복원). `PAID`이면 배송 전(현재는 `order_product.status == PAID` 전부)일 때만 아래 순서다(4-7 ④).

```
T8  주문 PAID ∧ 배송 전 검증
    UPDATE payment SET status='CANCEL_REQUESTED', cancel_requested_at=now
      WHERE payment_id = orders.paid_payment_id AND status='PAID'     → 0행이면 PAYMENT_CANCEL_IN_PROGRESS(409)
    INSERT payment_cancel (REQUESTED, requested_by=USER, amount=전액)
커밋
포트원 POST /payments/{id}/cancel
    성공 · "이미 취소됨"  → T9  주문 CANCELLED(조건부) · 결제 CANCELLED · payment_cancel SUCCEEDED · 재고 복원(1회) → 200
    명시적 거절           → T9' 결제 PAID 복귀 · payment_cancel FAILED → PAYMENT_CANCEL_FAILED(502)
    타임아웃·통신 오류    → 아무것도 바꾸지 않음 → 202 { "status": "CANCEL_REQUESTED" }
```

- **타임아웃은 실패가 아니다.** 포트원이 실제로 취소했는데 우리가 `PAID`로 되돌리면 환불된 주문이 배송된다. `CANCEL_REQUESTED`로 둔 채 202를 돌려주고, 4-4 둘째 단계(2분 뒤 재조회·재요청)나 `Transaction.Cancelled` 웹훅(4-5 ⑤)이 수렴시킨다. 앱은 202를 받으면 "취소 처리 중"으로 그리고 주문 상세를 다시 읽는다.
- **동시에 두 번 누르면** 둘째는 T8에서 0행이라 `PAYMENT_CANCEL_IN_PROGRESS`다. 외부 호출은 한 번이다.
- 포트원 취소 API는 같은 결제에 대해 멱등이다 — 이미 취소된 결제에 다시 부르면 "이미 취소됨"이 온다. 이것을 성공으로 수렴시킨다.

### 5-7. `POST /v1/webhooks/portone`

```
헤더  webhook-id · webhook-timestamp · webhook-signature   (Standard Webhooks, HMAC-SHA256)
본문  { "type": "Transaction.Paid" | "Transaction.Failed" | "Transaction.Cancelled" | …,
        "timestamp": "…", "data": { "transactionId", "paymentId", "storeId" } }
```

1. 원문 바이트로 서명 검증(SDK `Webhook.verify`). 실패 → 401, 본문 파싱 안 함. `timestamp`가 5분 밖이면 거절.
2. **T11(`REQUIRES_NEW`)** — `webhook-id`로 이벤트 행을 INSERT(`RECEIVED`). 이미 있으면 `result`를 본다: `PROCESSED`·`IGNORED`면 **200 + 아무것도 안 함**(진짜 중복). `RECEIVED`·`FAILED`면 `attempts + 1`로 갱신하고 **다시 처리**(이전 시도가 중간에 죽었거나 일시 장애였다).
3. `data.paymentId`로 `payment` 조회. 없으면 T12에 `IGNORED`(다른 환경의 결제일 수 있다 — 로그만) → 200.
4. `Transaction.Paid`·`Failed`·`Cancelled` → 4-5 `confirm(paymentId)` 호출. 나머지 타입은 T12에 `IGNORED`로 기록만.
5. **응답 코드는 실패의 종류로 정한다.**

| 결과 | 이벤트 `result` | 응답 | 이유 |
| --- | --- | --- | --- |
| 정상 처리 · 0행 수렴 | `PROCESSED` | 200 | |
| 모르는 결제 · 관심 없는 타입 | `IGNORED` | 200 | 재시도해도 같다 |
| 포트원 GET 타임아웃 · DB 데드락 등 **일시 장애** | `FAILED` + `error_message` | **500** | 포트원이 재전송하고, 2번 규칙으로 다시 처리한다 |
| 우리 코드의 버그(예외) | `FAILED` | 500 | 재전송이 같은 예외를 내겠지만 Sentry에 두 번 찍히는 게 "조용히 잃는 것"보다 낫다. 포트원 재시도 상한 뒤엔 운영자가 이벤트 테이블에서 본다 |

- 이전 판 "항상 200"은 **웹훅 유실과 같은 결과**였다 — 일시 장애에 200을 주면 포트원은 다시 보내지 않고, 우리 유니크 키는 재처리를 막는다. 처리를 못 했으면 못 했다고 말해야 재시도가 온다.
- 웹훅 도착 순서는 믿지 않는다. `Failed` 뒤에 `Paid`가 와도, `Cancelled`가 `Paid`보다 먼저 와도 confirm은 포트원 현재 상태를 읽어 판정하므로 결과가 같다.

## 6. 포트원 게이트웨이 · 설정

### 6-1. 게이트웨이 추상화

```
api/app/order/service/
  CheckoutService            주문서 조회 · 주문 생성 · 취소
  OrderPricingCalculator     금액 계산 (CartService와 공유 — 7-1)
  PaymentConfirmService      confirm(paymentId) — complete·웹훅 공용
  StockReserver / StockReleaser
domain/payment/
  entity  Payment · PaymentCancel · PaymentWebhookEvent
  type    PaymentStatus · PaymentMethod · CardIssuer · EasyPayProvider
  repository …
global/payment/portone/
  PortOnePaymentGateway      (인터페이스) preRegister · getPayment · cancel · verifyWebhook · channelKeyFor(method)
  PortOneV2Gateway           SDK 구현 (@ConditionalOnProperty portone.enabled=true)
  FakePaymentGateway         테스트·로컬 무자격 실행용 (enabled=false) — 조회는 항상 PAID/지정 금액
  PortOneProperties
```

- **SDK(`io.portone:server-sdk`)를 먼저 쓴다.** 웹훅 서명 검증·응답 타입이 들어 있다. SDK가 막히는 지점이 생기면 `RestClient`(Spring 6.1)로 같은 인터페이스를 구현해 교체한다 — 서비스 계층은 인터페이스만 본다. 버전은 구현 시 Maven Central 최신으로 고정한다.
- 포트원 호출 타임아웃은 연결 3초 · 읽기 10초. 조회 실패는 `PAYMENT_GATEWAY_ERROR`로 올리고 주문 상태는 바꾸지 않는다 — 웹훅이 다시 온다.
- `FakePaymentGateway`는 `EmptyGroupBuySalesReader`처럼 **없는 것을 대신하는 빈 구현**이 아니라 **시나리오를 지정하는 테스트 더블**이다. 통합 테스트에서 금액 불일치·FAILED·중복 웹훅을 만들어 낸다.

### 6-2. 설정

```yaml
# PortOneProperties.java — 결제 연동 (포트원 V2)
portone:
  enabled: ${PORTONE_ENABLED:true}                 # false면 FakePaymentGateway — 자격 없는 로컬·CI
  store-id: ${PORTONE_STORE_ID}
  api-secret: ${PORTONE_API_SECRET}                # V2 API Secret — Authorization: PortOne {secret}
  webhook-secret: ${PORTONE_WEBHOOK_SECRET}        # 콘솔 웹훅 설정의 시크릿
  channel-keys:                                    # 토스페이먼츠 허브형이라 지금은 네 값이 같은 키다(2-2)
    card: ${PORTONE_CHANNEL_CARD}
    kakaopay: ${PORTONE_CHANNEL_KAKAOPAY:${PORTONE_CHANNEL_CARD}}   # 비워 두면 카드 채널을 따라간다. 명시적으로 끄려면 "-"
    naverpay: ${PORTONE_CHANNEL_NAVERPAY:${PORTONE_CHANNEL_CARD}}
    tosspay: ${PORTONE_CHANNEL_TOSSPAY:${PORTONE_CHANNEL_CARD}}

order:
  payment-timeout-minutes: ${ORDER_PAYMENT_TIMEOUT_MINUTES:30}
  expiration-scheduler-enabled: true
  cancel-retry-base-minutes: 2                     # 취소 수렴 첫 재시도 간격 — 2·4·8·16·32분 (4-4)
  cancel-retry-max-attempts: 5                     # 도달 시 CANCEL_FAILED
  reconciliation-enabled: true                     # 일일 대사 05:00 KST (4-8)
  health-check-enabled: true                       # 운영 지표 10분 주기 (4-8)
```

- `.env`에 `PORTONE_*` 키를 추가한다(`.env`는 gitignore 대상). 로컬은 포트원 **테스트 채널**(실결제 없음)로 붙인다.
- 웹훅 URL은 콘솔에 `https://api.showroomz.shop/v1/webhooks/portone`으로 등록한다. 로컬 개발은 ngrok 등 터널을 쓰거나 `FakePaymentGateway`로 complete 경로만 검증한다.
- 포트원 웹훅 발신 IP 허용 목록은 **두지 않는다**. 서명 검증이 이미 위조를 막고, IP 목록은 바뀌면 조용히 웹훅이 끊긴다.

### 6-3. 보안

- `/v1/webhooks/portone` 공개 + CSRF 제외(이미 stateless). 요청 본문은 원문 바이트로 읽어 서명을 검증한다 — Jackson으로 먼저 파싱하면 공백·순서가 바뀌어 서명이 안 맞는다.
- 결제 완료·취소·주문 상세는 모두 `orders.user_id == 인증 사용자`. 어드민 경로는 이번 범위 밖.
- `raw_response`·`payload` JSON에는 카드번호가 오지 않는다(포트원은 마스킹된 BIN·발급사만 돌려준다). 그래도 응답 DTO에는 싣지 않는다.
- API Secret은 로그에 남기지 않는다. `PortOneV2Gateway`의 예외 메시지에 요청 헤더를 포함하지 않는다.

## 7. 기존 코드 영향

### 7-1. `CartService` 금액 계산 공통화

`CartService.calculateSummary`·`buildGroupShipping`·`lineSaleTotal`·`unavailableReason`을 `OrderPricingCalculator`(또는 `domain/order/service`)로 옮기고 `CartService`는 이를 호출한다. C8 하단 요약·C9 주문서·주문 생성 금액이 **한 식**에서 나와야 한다. 계산 규칙은 바꾸지 않는다 — 배송비 설정은 마켓에서, 무료배송 기준, 선택 항목만 합산.

그룹 키 공구 전환 · 병합 판정 `findByUserAndVariantAndGroupBuy` · 그룹 머리 D-day · 해석기 가격은 **가격 계획서로 이미 구현됐다**(9-4). 남은 것은 **옮기는 것 하나**다 — `priceOf`(공구별 일괄 해석)·`unavailableReason`·`requirePurchasable`·`calculateSummary`·`buildGroupShipping`·`lineSaleTotal`을 `OrderPricingCalculator`로 옮기고, 입력을 `Cart`가 아니라 `(groupBuyId, variantId, quantity)` 줄로 일반화한다. 장바구니 줄·바로 구매 한 줄·주문 상품 줄이 같은 형태로 들어간다. `CartServiceTest`가 무수정으로 통과해야 한다(선행 수정 계획서 3-2).

### 7-2. 판매 관리 포트 구현 — `GroupBuySalesReader`

`order_product.group_buy_id`가 생기므로 `EmptyGroupBuySalesReader`를 `OrderGroupBuySalesReader`로 바꾼다.

| 메서드 | 이번 구현 | 비고 |
| --- | --- | --- |
| `readSales` | `orders.status = PAID` 기준 건수·금액·상품별 수량 | 취소 반영 — `CANCELLED` 제외 |
| `countOrdersSince` | `paid_at >= since` | 스튜디오 「숨김 이후 0건」이 처음으로 실값을 받는다 |
| `countOneToOneInquiriesSince` | 문의의 `order_id` 조인 | `InquiryService`가 이미 주문을 연결한다 |
| `readClosure` | **empty 유지** | 배송·반품 상태가 없어 "종결"을 판정할 수 없다. 0을 돌려주면 정산 게이트가 거짓으로 열린다(포트 주석 0-6) |

## 9. 미결 사항 · 작업 순서

### 9-1. 미결

1. ~~**공구가 vs 옵션 판매가**~~ — **별도 계획서로 이관(2026-09-27).** 조사 결과 `product_variant.sale_price`는 옵션 생성 시 정가를 복사한 값이라 **계약의 공구가가 소비자 가격에 반영되는 경로가 없다.** 「계약 상품 옵션 단위 공구가 수정 계획서」가 계약을 옵션 단위로 바꾸고 `GroupBuyPriceResolver`로 소비자 가격을 계약에서 읽게 한다. 이 문서의 `OrderPricingCalculator`(7-1)는 `sale_price` 대신 그 해석기를 쓴다 — 주문 단가 = 해당 공구 계약의 옵션 공구가. 0절 「주문 단가」 행의 `sale_price` 결정은 이것으로 대체된다. 순서: 옵션 계획서 PR A·D → 결제 PR 3(결제 PR 2는 가격 계획서로 흡수돼 없다).
2. **개인정보 제3자 제공 동의**(C9 남은 결정 ②) — 포트원·PG에 넘기는 `customer`(이름·전화·이메일) 범위. 법무 결과에 따라 `customer` 블록에서 이메일을 뺄 수 있게 설정으로 둔다.
3. ~~**한 상품이 진행 중 공구 둘에 걸린 경우**~~ — **확정(2026-09-27).** 겹침은 정상이고 귀속은 진입 경로(`groupBuyId`)가 정한다(4-6). 귀속 미정 주문 경로는 없앴다(4-6). 남은 것 하나: 같은 마켓의 공구 둘이 한 주문에 섞이면 배송비가 두 번 붙는다(공구별 발송이 원칙이라 그렇게 잡았다 — **장바구니 합계와 같은 규칙**이라 C8과 C9 금액은 일치한다). 실제로 합포장한다면 배송비 합산 규칙이 필요하다 — C9 남은 결정 ④와 같은 계열.
4. **결제 완료 알림**(푸시·알림함) — 알림 모듈에 주문 타입을 추가할지. 이번 범위 밖으로 두되 `OrderPaidEvent`(Spring 이벤트)만 발행해 붙일 자리를 만든다.
5. **배송 전 취소 허용 기준** — 지금은 `order_product.status == PAID` 전부를 "배송 전"으로 본다. 셀러 판매 관리(발송 처리)가 생기면 `PREPARING` 이후는 막아야 한다.
6. ~~**`redirectUrl` 처리 경로**~~ — **확정(2026-09-27).** 앱은 React Native이고 포트원 RN SDK가 `redirectUrl`을 내부에서 처리한다. 서버 리다이렉트 엔드포인트 없음. 2-4 참고.
7. **주문번호 형식** — `yyyyMMdd-NNNNNN`으로 잡았다. 마이 화면 시안이 다른 형식을 쓰면 시퀀스 폭만 바꾼다.
8. **웹훅 재시도 실패 운영 화면** — `payment_webhook_event.result = FAILED`를 보는 어드민 화면이 없다. 당분간 Sentry 경고로 대신한다.
9. **브랜드 정산 방식 — PG 계약 전에 결정.** 쇼룸즈가 소비자 결제를 받아 브랜드에 나눠 지급하면 전자금융거래법상 PG업(전자지급결제대행업) 등록 대상이다(2024-09 개정으로 플랫폼 정산 대행이 명시됐고, 정산자금 외부관리 의무가 2026-12 전액 적용). 초기에는 **PG 지급대행(서브몰 정산)** 으로 피하는 것이 표준이다 — 토스페이먼츠 「정산지급대행」은 브랜드를 하위 판매자로 등록하고 구매확정 후 영업일 3일에 PG가 직접 지급한다. 이게 확정되면 ⓐ 셀러 가입·마켓에 하위 판매자 등록(사업자·정산 계좌·서브몰 ID) ⓑ 주문 항목의 판매자 귀속을 PG에 전달(`order_delivery_group.market_id`가 근거) ⓒ 구매확정 = 지급 트리거 ⓓ 지급 후 환불의 상계 규칙이 정산 모듈 요구사항이 된다. 크리에이터 리워드를 **브랜드 대금에서 떼어** 지급한다면 그것도 3자 정산 대행이라 같은 문제가 생긴다 — 쇼룸즈 수수료 안에서 지급하면 문제없다. 이 구분이 먼저다. 계약 상담 시 첫 질문으로 둔다.
10. **셀러 재고 수정과 예약의 충돌.** 셀러 상품 관리는 옵션 재고를 **절대값**으로 저장한다. 주문 예약으로 100 → 97이 된 사이 셀러가 "100"으로 저장하면 예약 3개가 사라지고, 만료 복원이 오면 103이 된다. 결제 범위 밖이지만 상품 관리가 재고 수정을 증감(delta)으로 바꾸거나, 저장 시점의 예약 수량을 빼는 보정이 필요하다. 상품 관리 소관으로 넘긴다.
11. **취소 수렴 간격·상한.** 4-4 둘째 단계의 첫 간격 2분·상한 5회는 잠정값이다. 포트원 취소 API의 실제 지연 분포를 스테이징에서 보고 조정한다.
12. **포트원 API 실 응답 확인 항목(구현 시).** ⓐ 사전 등록만 되고 결제창을 연 적 없는 `paymentId`의 `GET /payments/{id}` 응답이 404인지 `READY`인지 ⓑ `PENDING` 상태가 카드 인증 진행 중에 실제로 나오는지, 아니면 창을 닫을 때까지 `READY`인지(후자면 4-4의 미루기가 작동하지 않으므로 앱 CTA 잠금이 유일한 방어가 된다) ⓒ 결제 목록 API의 조회 구간 상한과 페이지 크기 ⓓ 이미 취소된 결제에 취소를 다시 보낼 때의 응답 코드(성공으로 수렴시킬 값).
13. **앱 측 규칙 전달.** `expiresAt` 5분 전 결제 CTA 잠금(4-4), 취소 202 응답의 "취소 처리 중" 표시(5-6), 완료 화면 재진입 시 주문 상세 재조회(2-4). 서버만으로 막을 수 없는 UX다.
