## 0. 먼저 정한 10가지

### 0-1. 이슈 스레드는 **정산의 사건**이다 — 패키지는 `domain.settlement.adjustment`

§42-0 「이슈 스레드는 정산 금액을 바꾸는 유일한 경로라 소통 스레드(§36)가 아니라 정산 옆에 둔다」. 구 구조(30 설계 1-9)는 이슈를 **공구**의 사실(`group_buy_issue`)로 두었다 — 개설 계기가 공구 종료였기 때문이다. 새 구조의 개설 계기는 **정산 확인 기간의 조정 요청**이고, 종결 결과는 **정산 금액**이다. 그래서 협의 · 제안 테이블은 정산 도메인에 두고, 공구는 `group_buy_id`를 비정규화 열로만 가진다(목록 표시 · 검색용). 공구 이력(`group_buy_history`)에는 **쓰지 않는다** — 조정 요청 · 합의 · 확정은 **정산 이력**(`settlement_history` · 어드민 설계서 1-8)의 사건이고, 포트(1-7)를 통해 정산이 적는다.

**구 `GroupBuyIssue`(`SETTLEMENT_AMOUNT`) · `GroupBuyIssueService.open` 은 쓰지 않는다.** 그래서 「같은 공구에 다른 유형 이슈가 열려 있으면 조정 요청이 막힌다」(열린 이슈 1건 제약)는 문제가 생기지 않는다 — 파트너 · 스튜디오 설계서가 미결로 적었던 항목이 이 결정으로 닫힌다.

### 0-2. 정산 본체는 **포트**다 — 구현은 정산 모듈 · 테스트는 가짜 포트

30 설계 0-6 · 32 설계 8-2 와 같은 결정이다. 이 모듈이 정산에서 **읽는** 것(정산 번호 · 확인 기간 · 원래 리워드 · 조정 상한 · 실지급 미리보기)과 정산에 **쓰는** 것(전액 보류 · 합의 금액 확정 · 원래 금액 확정 · 이력)을 `SettlementAdjustmentPort` 하나로 모은다(1-7). 구현은 `domain.settlement.service.SettlementAdjustmentPortAdapter`(어드민 설계서 4-2)다. **통합 테스트는 가짜 포트로 돈다**(9-2) — 정산 모듈의 생성 · 확정 흐름 없이 이 설계의 전부를 검증할 수 있어야 정산과 병행 구현이 된다. 마이그레이션은 V179(정산 본체) 뒤 **V180** 이라 머지 순서만 정산이 앞선다.

### 0-3. **협의 1건 + 제안 N건** — 응답은 제안 행에 기록된다

정산 1건에 협의(`settlement_adjustment`)는 **딱 1건**이다(§42-1 「정산 1건에 협의 1건 · 종결 후 같은 사안 재요청 불가」) — `settlement_id UNIQUE`가 건다. 협의 안에서 「조정 요청 → 다른 금액 제안 → 다른 금액 제안 → 동의」가 오가므로 **금액이 든 글은 전부 제안**(`settlement_adjustment_proposal`)이다. 첫 요청은 `seq = 1`인 제안이고, 다른 금액 제안은 이전 제안을 `COUNTERED`로 닫고 `seq + 1`을 만든다. 동의 · 반대는 **제안의 상태 변화**다(`ACCEPTED` · `REJECTED`) — 별도 응답 테이블을 두지 않는다. 「버튼은 최신 요청 카드에만」(§42-2)이 **최신 제안 = 열린 제안 하나**라는 모델에서 바로 나온다.

### 0-4. 스레드는 **기존 메시지 도메인에 `ThreadKind` 하나**를 더한다 — 새 채팅 테이블 없음

30-1 수정계획 1절이 만든 자리 그대로다 — 3자 스레드는 그 쌍의 PAIR 연결에 `thread_kind`만 달리해 붙는다. `ThreadKind.SETTLEMENT_ADJUSTMENT`(`subject_id = group_buy_id`)를 더하면 접근 판정 · 목록 · 안 읽은 수 · 첨부 규칙(20개 · 500MB · `AllowedAttachmentExtensions`)이 연결 기준으로 그대로 동작한다. 양측 목록에 「같은 상대의 줄이 여러 개」가 생기는 것도 이미 `ThreadListItem.kind`가 답하고 있다. 구 `GROUP_BUY_ISSUE` · `GROUP_BUY_FULFILLMENT` 값은 **보존**한다(기존 행 · 7절).

### 0-5. 절차는 **시스템 카드**, 카드의 상태는 **참조 객체(제안)에서 읽는다** — 36 설계 0-3 그대로

§42-5 「절차는 시스템 카드, 대화는 말풍선」. 카드는 `message` 행이고(`messageType = SYSTEM`), 생성 시점 스냅샷은 `card_payload`에, **버튼이 남았는지 · 어떻게 응답됐는지**는 `ref_type = SETTLEMENT_ADJUSTMENT_PROPOSAL`로 가리킨 제안 행에서 읽는다(`MessageCardReader` 확장 · 5절). 그래서 「이전 카드는 응답 결과로 굳는다」가 카드를 고쳐 쓰는 일 없이 성립한다. 어드민 · 파트너 · 스튜디오가 **같은 `CardView`**를 받아 각자 DTO로 옮긴다 — 운영자 개인 식별자는 이 카드들에 아예 없다(운영자 조치가 없다).

### 0-6. 금액의 정본은 **정산**이다 — 이 모듈은 **비교만** 한다

조정할 수 있는 값은 **인플루언서 리워드(공급가 · 부가세 별도) 하나**다(§42-1). 범위 상한(어드민 설계서 4-1 — 「조정 후 브랜드 수취액 ≥ 0」 · 10원 미만 절사)과 실지급 미리보기(원천징수 · 부가세 · 브랜드 수취액)는 **정산이 계산**해 포트로 내려 준다. 이 모듈은 개설 시점의 상한을 `max_reward_amount`로 **박아 두고**(정산은 금액 확정 뒤에만 생기므로 협의 중 바뀌지 않는다) 제안마다 `0 ≤ amount ≤ max`만 본다. 산식이 바뀌어도 이 모듈의 코드는 바뀌지 않는다.

### 0-7. 운영자 쓰기 엔드포인트는 **0개**다

§42-4 「하는 일 — 없다」. 어드민은 **열람 · 목록 · 정보 패널**뿐이고, 기존 전송 엔드포인트(`POST /v1/admin/threads/{id}/messages`)는 이 종류의 스레드에 403 `THREAD_OPERATOR_READ_ONLY`를 낸다. 구 M1(조정안 제시) · M2(답변 기한 설정) · M3(운영자 이슈 직접 개설 — `POST /v1/admin/group-buys/{id}/issues`)은 이 설계가 끄는 대상이다(7절). 어드민 탭 배지는 **항상 0**이다 — 운영자 차례가 없다.

### 0-8. 종결은 두 가지뿐이고 둘 다 **조건부 UPDATE 한 문장이 승자**다

합의(동의)와 기한 만료(배치)가 **같은 순간** 올 수 있다 — 마감 23:59:59 직전의 동의와 00:00의 만료 배치. 둘 다 `UPDATE settlement_adjustment SET status = … WHERE id = ? AND status = 'OPEN'`을 먼저 치고, 0행이면 물러난다(동의는 409 `SETTLEMENT_ADJUSTMENT_STATE_CHANGED` · 배치는 건너뜀). 제안의 응답도 같다 — `WHERE proposal_id = ? AND status = 'PENDING'`. 동의 → 포트 `confirmByAgreement` → 카드 2장 → 알림이 **한 트랜잭션**이다(§42-2 「시스템에서 동시에」). 정산 쓰기가 실패하면 협의도 종결되지 않는다.

### 0-9. 기한은 **`BusinessCalendar` 하나** · 마감 시각은 **설정값**이다

`deadline_at = addBusinessDays(opened_at.date, 10)` + `settlement.adjustment.deadline-time`(기본 **23:59:59** — 어드민 시안 · §46 B-4 파트너 · 스튜디오 18:00과 충돌 → 설정값으로 흡수). D-N은 `businessDaysBetween(today, deadline.date)`(기준일 다음 날부터 센다 — 09.04 기준 09.17 마감 = D-9 · 어드민 A1과 일치). 기한은 **개설 시 한 번 계산해 저장**하고 **연장하지 않는다**(§42-3). 공휴일 테이블이 나중에 바뀌어도 저장된 기한은 그대로다 — 양측에 통지한 날짜가 흔들리면 안 된다.

### 0-10. 구 이슈 · 이행 확인 코드는 **「끄되 지우지 않는다」** — 이 설계가 그 정리 지점이다

36 설계 10절이 「이슈 스레드 기획이 나온 뒤 그 설계에서 일괄 정리한다」고 미뤄 둔 자리다. 1009 수정계획 6-2가 이행 확인에 적용한 규칙(엔드포인트 `@Hidden` + 항상 409 · 판정 `false` 고정 · 테이블 · enum 보존)을 **운영자 · 브랜드 이슈 개설**에도 똑같이 적용한다(7절). `GroupBuyIssueType.SETTLEMENT_AMOUNT`가 새 구조와 이름이 겹치지만 **지우지 않는다** — 기존 행이 있을 수 있고, CLAUDE.md 규칙이 「삭제 금지」다.

### 1-4. 상태 전이

**협의** — 나가는 전이는 둘뿐이다.

| From | To | 계기 | 조건부 UPDATE | 부수 효과(같은 트랜잭션) |
| --- | --- | --- | --- | --- |
| — | `OPEN` | 조정 요청(2-1) | INSERT(`settlement_id UNIQUE`) | 포트 `holdForAdjustment`(정산 `REVIEWING → ADJUSTING` · 전 수취자 `HELD` · 정산 이력) · 스레드 개설 · 카드 2장(개설 · 요청) · 알림 |
| `OPEN` | `AGREED` | 동의(2-3) | `WHERE status = 'OPEN'` | 제안 `ACCEPTED` · `agreed = final = amount` · 포트 `confirmByAgreement`(정산 재계산 · `PAYOUT_SCHEDULED` · 지급 예정일) · 카드 2장(동의 · 합의 완료) · 알림 |
| `OPEN` | `EXPIRED` | 기한 만료 배치(6-2) | `WHERE status = 'OPEN' AND deadline_at < :now` | 열린 제안 `CLOSED` · `final = original` · 포트 `confirmByExpiry` · 카드 1장(기한 만료) · 알림 |

**제안**

| From | To | 계기 | 조건부 UPDATE |
| --- | --- | --- | --- |
| — | `PENDING` | 요청 · 다른 금액 제안 | INSERT(`UNIQUE(adjustment_id, seq)`) |
| `PENDING` | `ACCEPTED` | 상대의 동의 | `WHERE status = 'PENDING'` |
| `PENDING` | `REJECTED` | 상대의 반대 | 〃 |
| `PENDING` | `COUNTERED` | 상대의 다른 금액 제안 | 〃 — 새 제안 INSERT와 같은 트랜잭션 |
| `REJECTED` | `ACCEPTED` | **반대한 쪽이 마음을 바꿈**(파트너 C3 「나중에 생각이 바뀌면 상대의 요청에 다시 동의」) | `WHERE status = 'REJECTED' AND seq = (최신 seq)` |
| `REJECTED` | `COUNTERED` | 반대 뒤 **누구든** 다른 금액 제안(스튜디오 C3 「상대가 다시 제안」 · 파트너 C3 「다른 금액을 제안」) | 〃 |
| `PENDING` | `CLOSED` | 협의 만료 | 협의 전이와 같은 트랜잭션 |

`REJECTED` 제안은 **최신 제안인 동안만** 되살릴 수 있다 — 새 제안이 생기면 `COUNTERED`로 닫힌다. 반대 뒤의 차례 · 버튼 화면은 **시안에 없다**(§46 A-9) — 위 두 줄이 이 설계의 **잠정** 답이다(10-2 #1).

### 1-5. 차례(turn) — 뷰어 기준 판정식 · 서버가 정한다

```
latest = seq 최대 제안
if adjustment.status != OPEN                   → CLOSED            (배지 = AdjustmentStatus 톤)
elif latest.status == PENDING:
    viewer == latest.proposer                  → THEIR_TURN(정보)  「상대 응답 대기」
    else                                       → MY_TURN(경고)     「내 응답 필요」
else  # latest.status == REJECTED
                                               → OPEN_FLOOR(중립)  「협의 중」 — 양측 모두 제안 가능 · 반대한 쪽은 동의도 가능
```

**버튼 권한**(3-8 `permissions`) — 전부 `OPEN ∧ now ≤ deadline_at` 전제.

| 권한 | 식 |
| --- | --- |
| `canAccept` | `latest.status ∈ {PENDING, REJECTED} ∧ viewer ≠ latest.proposer` |
| `canReject` | `latest.status == PENDING ∧ viewer ≠ latest.proposer` |
| `canCounter` | `(latest.status == PENDING ∧ viewer ≠ latest.proposer) ∨ latest.status == REJECTED` |

「내가 보낸 요청 카드에는 처음부터 버튼이 없다」(T1)는 `viewer == proposer`에서 셋 다 false가 되어 나온다. 어드민 뷰어는 **항상 셋 다 false**다.

### 1-6. 기한 · D-N

| 값 | 계산 | 예(어드민 A1 — 개설 2026-09-03 목 14:10) |
| --- | --- | --- |
| `deadline_at` | `calendar.addBusinessDays(opened_at.toLocalDate(), deadlineBusinessDays).atTime(deadlineTime)` | 09.04 · 07 · 08 · 09 · 10 · 11 · 14 · 15 · 16 · **17** → `2026-09-17T23:59:59` ✓ |
| `remainingBusinessDays`(D-N) | `calendar.businessDaysBetween(today, deadline_at.toLocalDate())` — 오늘 다음 날부터 마감일까지 · 마감일 당일 = 0(FE 「D-day」) · 마감 경과(만료 배치 전 최대 10분 구간)도 0이다 — 이 메서드는 음수를 돌려주지 않는다 · 종결 뒤에는 **null** | 09.04 기준 9(D-9 ✓) · 09.08 기준 7(D-7 ✓) |
| `notice_due_at` | 마감일의 **직전 영업일** + `noticeTime`(기본 10:00) — `BusinessCalendar.previousBusinessDay(LocalDate)` **신규 1메서드**(하루씩 물러나 `isBusinessDay`인 첫 날 · `notice-business-days-before`만큼 반복). 기존 `latestStartToFinishBefore`는 「D에 시작하면 target 전날까지 끝나는 D」라 뜻이 다르다(09.17 → 09.15를 돌려준다) — 쓰지 않는다 | `2026-09-16T10:00` — A4 「09.16(수) D-1 통지」 ✓ |

- 시안 검산 — 스튜디오 09.02(수) → 09.16 ✓ · 07.20(월) → 08.03 ✓. **파트너 T1은 어긋난다** — 08.29(토) 요청 → 10영업일은 **09.11**인데 시안은 09.12다(10-1 #2 · 주말 요청의 기산). 어드민 · 스튜디오가 맞으므로 이 설계는 「기산일 불산입 · 다음 영업일부터 10영업일」로 간다 — 정산 확인 기간의 기산(어드민 설계서 0-10)과 같은 규칙.
- D-1을 **역일**(스튜디오 T4 08.02 일요일 안내)로 할지 **영업일**로 할지는 §46 B-4 미결 — 설정값 `notice-business-days-before`(기본 1 · 영업일)로 두고, 역일로 확정되면 계산식 한 줄만 바꾼다. 주말에 통지하면 읽지 못한다는 이유로 영업일을 기본으로 골랐다.
- 날짜 유틸은 `BusinessCalendar`에 `previousBusinessDay` 한 메서드만 더한다 — 별도 달력 클래스를 만들지 않는다. 공휴일 정본은 그대로 `business_holiday` 테이블 + `BusinessHolidayLoader`다.

## 2. 흐름 — 커맨드 4종 · 배치 2종

전부 `domain.settlement.adjustment.service.SettlementAdjustmentService` 한 클래스다. 파트너 · 스튜디오 API 서비스는 **당사자(`SettlementParty` · id)만 바꿔** 같은 메서드를 부른다(`GroupBuyFulfillmentService`가 측만 바꿔 불리던 것과 같은 결정 — 규칙이 두 벌이 되면 한쪽만 고쳐진다). 메서드 진입 시 협의 행을 `PESSIMISTIC_WRITE`로 잠근다(2-2~2-4) — 조건부 UPDATE는 최종 방어선이고, 잠금은 「제안 두 개가 동시에 seq 2를 받는」 경합을 선검사 단계에서 정리한다.

### 2-1. 조정 요청 — `request(settlementId, party, partyId, amount, reason, now)`

| 순서 | 동작 | 실패 |
| --- | --- | --- |
| ① | `port.find(settlementId)` → empty면 404 `SETTLEMENT_NOT_FOUND` | — |
| ② | 당사자 검사 — `party == SELLER ? s.marketId == partyId : s.creatorId == partyId` — 남의 정산은 **404**(존재를 알리지 않는다 · 파트너 · 스튜디오 조회와 같은 규칙) | 404 `SETTLEMENT_NOT_FOUND` |
| ③ | `s.inReviewWindow` | 409 `SETTLEMENT_ADJUSTMENT_WINDOW_CLOSED` |
| ④ | `reason` trim 후 비면 400 `SETTLEMENT_ADJUSTMENT_REASON_REQUIRED` · 길이 > 설정값 400 `INVALID_INPUT_VALUE` | — |
| ⑤ | `0 ≤ amount ≤ s.maxRewardAmount` · `amount ≠ s.rewardAmount`(같은 금액 요청은 협의가 아니다) | 400 `SETTLEMENT_ADJUSTMENT_AMOUNT_OUT_OF_RANGE`(응답 `detail`에 상한을 싣는다) |
| ⑥ | 스레드 개설 — `threadPort.openAdjustmentThread(groupBuyId, marketId, creatorId)` → PAIR 연결이 끊겼으면 **503 `GROUP_BUY_THREAD_UNAVAILABLE`**(기존 코드 · HTTP 503 · 10-2 #4) | — |
| ⑦ | 협의 INSERT(`saveAndFlush`) — `settlement_id UNIQUE` 충돌 → 409 `SETTLEMENT_ADJUSTMENT_ALREADY_EXISTS` | `DataIntegrityViolationException` 변환 |
| ⑧ | 제안 INSERT `seq = 1 · PENDING` | — |
| ⑨ | `port.holdForAdjustment(settlementId, adjustmentId, now)` — 0행이면 409 `SETTLEMENT_ADJUSTMENT_WINDOW_CLOSED`(자동 확정 배치가 먼저 지나갔다) → **전체 롤백** | — |
| ⑩ | 카드 2장 — `OPENED`(보낸 사람 = 시스템 `ADMIN · 0`) · `REQUEST`(보낸 사람 = 요청자) · 제안 `card_message_id` 갱신 | 멱등키 5-3 |
| ⑪ | 알림 `REQUESTED` → 상대(8-2) · 운영자 알림 없음(열람만) | — |

응답 `{ adjustmentId, threadId, proposalId, deadlineAt }`. 정산 상세는 이 응답의 `threadId`로 연결·소통 화면으로 보낸다(「첫 글은 조정 요청 카드」). **금액은 바뀌지 않는다** — 정산 `reward_amount`는 원래 값 그대로다(스튜디오 D2 「원래 금액 · 합의 결과에 따라 바뀝니다」). 차액 선지급도 없다.

**운영자는 이 메서드를 부르지 않는다** — 어드민에 엔드포인트가 없다(0-7).

### 2-2. 다른 금액 제안 — `counter(adjustmentId, party, partyId, amount, reason, now)`

| 순서 | 동작 | 실패 |
| --- | --- | --- |
| ① | 협의 잠금 조회 · 당사자 검사 | 404 `SETTLEMENT_ADJUSTMENT_NOT_FOUND` · 403 `SETTLEMENT_ADJUSTMENT_ACCESS_DENIED` |
| ② | `status == OPEN ∧ now ≤ deadline_at` | 409 `SETTLEMENT_ADJUSTMENT_CLOSED` · 409 `SETTLEMENT_ADJUSTMENT_DEADLINE_PASSED` |
| ③ | `canCounter(viewer)`(1-5) | 409 `SETTLEMENT_ADJUSTMENT_NOT_YOUR_TURN` |
| ④ | 범위 검사(2-1 ⑤) · `amount ≠ latest.reward_amount` | 400 `…_OUT_OF_RANGE` · 400 `SETTLEMENT_ADJUSTMENT_AMOUNT_UNCHANGED`(같은 금액이면 「동의」를 눌러야 한다 — 잠정 규칙 · 10-2 #2) |
| ⑤ | `UPDATE proposal SET status = COUNTERED, responded_at, responder_* WHERE id = latest ∧ status IN (PENDING, REJECTED)` → 0행 409 `SETTLEMENT_ADJUSTMENT_STATE_CHANGED` | — |
| ⑥ | 새 제안 INSERT `seq = latest.seq + 1 · PENDING`(`reason` 선택) | UNIQUE 충돌 → 409 `…_STATE_CHANGED` |
| ⑦ | 카드 `COUNTER`(보낸 사람 = 제안자) · `port.recordEvent(ADJUSTMENT_COUNTERED)` | — |
| ⑧ | 알림 `COUNTERED` → 상대 | — |

**합의 기한은 건드리지 않는다**(§42-3 「연장 없음」). 응답에 `deadlineAt`을 그대로 돌려줘 FE가 「기한은 그대로」를 확인한다.

### 2-3. 동의 — `accept(adjustmentId, proposalId, party, partyId, now)`

| 순서 | 동작 | 실패 |
| --- | --- | --- |
| ① ~ ③ | 2-2와 같다(`canAccept`) · `proposalId == latest.id`가 아니면 409 `…_STATE_CHANGED`(화면이 옛 카드를 들고 있다) | — |
| ④ | `UPDATE proposal SET status = ACCEPTED, responded_at, responder_* WHERE id = ? ∧ status IN (PENDING, REJECTED)` → 0행 409 | — |
| ⑤ | `UPDATE adjustment SET status = AGREED, agreed_reward_amount = :amt, final_reward_amount = :amt, closed_at = :now WHERE id = ? ∧ status = OPEN` → 0행 409 `…_STATE_CHANGED`(만료 배치가 먼저였다 · 0-8) | — |
| ⑥ | `port.confirmByAgreement(settlementId, adjustmentId, amt, now)` — 정산 금액 변경 · 보류 해제 → 지급 예정 | 정산 쪽 예외 → 전체 롤백 |
| ⑦ | 카드 2장 — `ACCEPTED`(보낸 사람 = 동의한 쪽 · 스튜디오 T3 「누가 언제 무엇에 동의했는지」) · `AGREED`(시스템 · 결과) | — |
| ⑧ | 알림 `AGREED` → 양측 | — |

**운영자 승인 단계가 없다**(§42-2). 동의 응답은 **불가역**이다 — 되돌리는 엔드포인트를 만들지 않는다.

### 2-4. 반대 — `reject(adjustmentId, proposalId, party, partyId, now)`

| 순서 | 동작 |
| --- | --- |
| ① ~ ③ | 2-2와 같다(`canReject` — `PENDING`만) |
| ④ | `UPDATE proposal SET status = REJECTED, responded_at, responder_* WHERE id = ? ∧ status = PENDING` → 0행 409 |
| ⑤ | 카드 `REJECTED`(보낸 사람 = 반대한 쪽 · **사유 없음** · §42-2) · `port.recordEvent(ADJUSTMENT_REJECTED)` |
| ⑥ | 알림 `REJECTED` → 제안자 |

협의 상태는 **그대로 `OPEN`**이다 — 반대는 종결이 아니다. 차례는 `OPEN_FLOOR`가 된다(1-5).

### 2-5. 배치 2종 — 6절

D-1 통지(`notifyDeadline`) · 기한 만료(`expire`). 둘 다 행마다 별도 트랜잭션 · 조건부 UPDATE · 실패는 로그 후 다음 회차.

## 3. 파트너센터 · 쇼룸 스튜디오 API

권한 — 파트너 `SELLER`(`/v1/seller/**`) · 스튜디오 `CREATOR`(`/v1/creator/**`). 패키지 `api.seller.settlement.{controller, docs, dto, service}` · `api.creator.settlement.…` — 정산 관리 전체(파트너 · 스튜디오 설계서)와 같은 패키지에 조정 컨트롤러를 따로 둔다. 컨트롤러 `SellerSettlementAdjustmentController implements SellerSettlementAdjustmentControllerDocs`(스튜디오 `CreatorSettlementAdjustmentController` 동형). 두 서피스의 요청 · 응답 DTO는 **같은 모양**이다 — 공통 record는 `api.common.settlement.dto`에 두고 두 컨트롤러가 함께 쓴다(`MessageCardResponse`와 같은 규칙). 마켓 · 크리에이터 해석은 각 설계서의 접근 가드(`SellerSettlementAccessGuard` · `getCurrentUserEmail() → Creator`)와 같다.

### 3-1. 엔드포인트 — 서피스당 6개

| Method | Path(파트너 — 스튜디오는 `/v1/creator/…`) | 설명 | 시안 |
| --- | --- | --- | --- |

| GET | `/v1/seller/threads/{threadId}/adjustment` | 스레드의 고정 카드 + 제안 목록 + 내 권한(3-4) | `.iss-pin` · 카드 버튼 |

### 3-2. 미리보기 — `GET …/settlements/{id}/adjustment/preview`

```json

  "settlementId": 1206, "settlementNumber": "STL-2609-006",
  "canRequest": true, "reviewEndsAt": "2026-09-05T23:59:59",
  "originalRewardAmount": 150528, "maxRewardAmount": 898600,
  "input": { "rewardAmount": 180528 },

- `rewardAmount` 생략 시 `input` · `preview`는 null, 나머지(상한 · 원래 값)만 내린다 — 모달이 열릴 때 「0원 ~ N원 안에서 입력할 수 있습니다」를 그릴 값이다.
- `canRequest = inReviewWindow ∧ 협의 없음`. false면 버튼 비활성(§42-1 「에러 문구 없이 버튼 비활성」) — 서버는 이유를 `cannotRequestReason`(`REVIEW_CLOSED` · `ALREADY_ADJUSTING`)으로 함께 내리되 FE는 쓰지 않아도 된다.
- 숫자는 전부 **정산 포트의 계산값**이다(0-6 · 전 항목 절사 — 위 수치는 시안 더미를 절사 규칙으로 다시 계산한 값이라 시안의 반올림 숫자와 1원 다를 수 있다 · 리워드 +30,000 이면 부가세 +3,000 까지 브랜드 수취액에서 빠진다 → 822,886 − 33,000 = 789,886 · 상한 = floor10((822,886 + 150,528 + 15,052) ÷ 1.1) = 898,600). 요청 전 모달의 입력 즉시 계산은 이 엔드포인트를 **디바운스로 호출**한다 — FE 가 산식을 들지 않는다.

| DTO | 추가 | 값 |
| --- | --- | --- |
| `ThreadListItem`(파트너 · 스튜디오) | `adjustment` (nullable) | `kind == SETTLEMENT_ADJUSTMENT`일 때 `{ adjustmentId, status, statusLabel, turn, turnLabel, turnTone, deadlineAt, remainingBusinessDays }` — 목록 줄의 「[이슈] 정산 조정 요청 · 내 응답 필요」 · 배지 색을 FE가 조립한다 |
| `MessageItem.card`(`MessageCardResponse`) | `Detail` 필드 · `Action` 확장 | 5-4 |
| `ThreadSummaryResponse` | 변경 없음 | 안 읽은 수에 이슈 스레드도 들어간다 — 시스템 카드는 `ADMIN · 0`이 보낸 사람이라 **양측 모두에게 안 읽음**으로 센다(원하는 동작). 「내 응답 필요」는 **이 배지**(연결·소통 GNB)가 센다 — 정산 관리 GNB 배지는 세지 않는다(공통 결정 #19) |

목록 정렬 · 페이징 · 검색은 그대로다. 종결 이슈도 목록에 남는다(1-3 — `ThreadStatus`를 바꾸지 않는 이유).

### 3-7. 전송 가드 — 종결 스레드는 **읽기 전용**

`SellerThreadService.sendMessage` · `CreatorThreadService.sendMessage` · 첨부 presign 앞에 한 줄 — `thread.getKind() == SETTLEMENT_ADJUSTMENT`이면 `adjustmentRepository.findByThreadId(thread.id)`의 `status.isClosed()`에 409 `SETTLEMENT_ADJUSTMENT_CLOSED`(「종결된 이슈에는 메시지를 보낼 수 없습니다」). 판정은 `domain.settlement.adjustment.service.SettlementAdjustmentThreadGuard.requireWritable(thread)` 한 곳에 두고 두 서비스가 부른다. `MessageThreadService.sendMessage` 자체는 건드리지 않는다 — 카드 등록(시스템)은 종결 트랜잭션 안에서 종결 **직후**에도 들어가야 하기 때문이다.

### 3-8. 권한 판정 — 서버가 전부 한다

`AdjustmentPermissionPolicy`(domain 서비스 · 1-5 식) → 3-4 `permissions`. FE는 식을 들지 않는다. `canSend = !status.isClosed()`.

## 4. 어드민 — 20b 이슈 스레드 탭

36 설계 3절의 엔드포인트 6종을 **확장**한다 — 새 경로는 없다. 패키지 `api.admin.thread`에 `AdminIssueThreadQueryService` · `AdminIssuePanelAssembler`를 더하고 DTO는 `AdminThreadDto`에 record를 추가한다.

### 4-1. 목록 — `GET /v1/admin/connections/threads?tab=ISSUE&state=&keyword=`

| 파라미터 | 값 |
| --- | --- |
| `tab` | `AdminChannelTab`(현재 `BRAND` · `INFLUENCER`)에 **`ISSUE`** 추가(36 설계 3-1 「이슈 스레드 기획 후 추가」). `ISSUE`는 `connectionType`이 없다(PAIR 연결에 붙는다) — `of(ConnectionType)`은 그대로 두고 `ISSUE`는 `AdminThreadQueryService`가 분기한다 |

| `page` · `size` | 기존 |

원천은 `settlement_adjustment` JOIN `message_thread` JOIN `group_buy`(공구명) JOIN `market` · `creator`. 정렬 `thread.last_message_at DESC NULLS LAST`. 응답은 기존 `PageResponse<ChannelListItem>`에 **`issue`** 필드를 더한다.

```

`badgeLabel`은 **운영자 기준**이다 — `OPEN` = 「응답 대기」(정보 · 당사자 차례) · `AGREED` = 「합의 · 금액 변경」(성공) · `EXPIRED` = 「기한 만료 · 원래 금액」(중립) — §42 「목록 배지」 그대로. `unreadCount`는 **항상 0**이다(운영자는 참가자가 아니다 · 0-7).

### 4-2. 요약 — `GET /v1/admin/connections/summary`

`issue` 탭 `{ unreadMessages: 0, pendingCards: 0, openCount: N, closedCount: M }` — 36 설계 3-2가 `null`로 비워 둔 자리를 채운다. `openCount` · `closedCount`는 seg 숫자다. 게시물·소통 GNB 배지에는 **더하지 않는다**(§42-4 「1:1 미답만」).

### 4-4. 메시지 열람 · 전송 · 읽음

`AdminThreadAccess`에 메서드를 **더한다**(36 설계 2-1 「확정되면 이 클래스에 판정을 더한다」).

| 메서드 | 허용 | 쓰는 엔드포인트 |
| --- | --- | --- |
| `requireOperatorChannel` | (기존) CONNECTION ∧ OPERATOR_* | 전송 · presign · complete · 카드 액션 |
| **`requireReadable`** | OPERATOR 채널 **또는** `kind == SETTLEMENT_ADJUSTMENT` **또는** `kind == CONNECTION ∧ PAIR ∧ 그 쌍에 협의가 있음`(4-5) | `GET …/info` · `GET …/messages` · 첨부 다운로드 · `POST …/read` |

### 4-5. 브랜드–인플루언서 1:1 스레드 열람 — **이슈가 있는 쌍만** · 읽기 전용

§42 「1:1 브랜드–인플루언서 스레드는 열람만 — 실제 경로는 이슈 패널의 [브랜드–인플루언서 1:1 스레드 열람] 하나」. §36-9 A-2(PAIR 열람 범위) 미결의 **이 설계 안의 답**이다.

| 항목 | 규칙 |
| --- | --- |
| 허용 조건 | `thread.kind == CONNECTION ∧ connection.type == PAIR ∧ EXISTS(settlement_adjustment WHERE market_id = c.market.id AND creator_id = c.creator.id)` — 상태 무관(종결 뒤에도 CS 문의가 온다) |
| 범위 | 그 쌍의 PAIR 스레드 **전량**(과거 대화 포함) — 「분쟁 발생 시 운영자가 열람할 수 있습니다」 고지의 범위가 「대화」다 |
| 쓰기 | 없다 — 403 |
| 읽음 | **쓰지 않는다** — PAIR 스레드에 ADMIN 참가자 행을 두지 않는다(13-14 §13-4 모니터링 열람 규칙). `POST …/read`는 이 스레드에 **204 no-op** |
| 목록 | 없다 — 패널 링크로만 들어간다(「이슈가 없는 쌍의 대화를 목록으로 훑는 기능은 두지 않았다」). `tab=ISSUE` 목록에 PAIR 스레드가 섞이지 않는다 |
| 감사 로그 | §36-9 C-17 미결 — 이 설계는 **열람 로그를 남기지 않는다**(10-2 #6). 코드에 운영자 열람 로그 테이블이 **없다**(어드민 설계서 5-5 확인) — 확정되면 그때 테이블을 만든다 |

### 4-6. `openIssueThreads[]` — 36 설계 3-4 보강

`MessageThreadRepository.findOpenGroupBuyThreadsOf`에 `t.kind = SETTLEMENT_ADJUSTMENT ∧ EXISTS(adjustment OPEN)`를 OR로 더한다. 구 두 종류의 조건은 **그대로**(기존 행). `OpenIssueThread.kind` 설명에 새 값을 더한다. 이제 클릭 목적지(20b)가 있으므로 「링크만」 메모를 지운다.

## 6. 배치 — `SettlementAdjustmentDeadlineScheduler`

`global.scheduler` · `@ConditionalOnProperty(prefix = "settlement.adjustment", name = "scheduler-enabled", matchIfMissing = true)` · `@Scheduled(cron = "0 */10 * * * *", zone = "Asia/Seoul")`(취소 요청 자동 승인 배치 · 정산 자동 확정 배치와 같은 10분 주기 — 분 단위 정확도가 필요하지 않다). 단일 인스턴스 · 분산 락 없음 · 행마다 별도 트랜잭션 · 예외는 로그 후 삼킨다(`GroupBuyLifecycleScheduler` 규칙).

### 6-1. D-1 통지 — `notifyDeadline(id, now)`

| 순서 | 동작 |
| --- | --- |
| 조회 | `status = OPEN ∧ notice_sent_at IS NULL ∧ notice_due_at <= :now` · `LIMIT batch-size` |
| ① | `UPDATE adjustment SET notice_sent_at = :now WHERE id = ? ∧ notice_sent_at IS NULL ∧ status = OPEN` → 0행이면 종료 |
| ② | 카드 `DEADLINE_NOTICE`(멱등키 5-3) — 「{기한}까지 합의가 없으면 원래 금액으로 확정됩니다」 · `port.recordEvent(ADJUSTMENT_DEADLINE_NOTICED)` |
| ③ | 알림 `DEADLINE_D1` → 양측 |

`notice_due_at`이 이미 지난 협의가 열리는 경우는 없다(개설 + 10영업일 안에 D-1이 있다). 통지 배치가 꺼져 있다가 켜지면 밀린 건을 한 번에 처리한다 — 멱등키가 중복을 막는다.

### 6-2. 기한 만료 — `expire(id, now)`

| 순서 | 동작 |
| --- | --- |
| 조회 | `status = OPEN ∧ deadline_at < :now` · `LIMIT batch-size` |
| ① | 협의 `PESSIMISTIC_WRITE` 조회 |
| ② | `UPDATE adjustment SET status = EXPIRED, final_reward_amount = original_reward_amount, closed_at = :now WHERE id = ? ∧ status = OPEN ∧ deadline_at < :now` → 0행이면 종료(동의가 먼저였다 · 0-8) |
| ③ | `UPDATE proposal SET status = CLOSED, responded_at = :now WHERE adjustment_id = ? ∧ status IN (PENDING, REJECTED)` |
| ④ | `port.confirmByExpiry(settlementId, adjustmentId, now)` — 원래 금액 확정 · 보류 해제 → 지급 예정(정산 `confirmed_at` = 기한 다음 날 00:00 규칙값) |
| ⑤ | 카드 `EXPIRED` — 「원래 계약 금액(150,528원)으로 확정 · 보류 해제 · 이슈 종결」 |
| ⑥ | 알림 `EXPIRED` → 양측 |

**간주 규칙이 없다**(§42-3) — `REJECTED`든 `PENDING`이든 결과는 같다. 「무응답 = 동의」 분기를 만들지 않는다.

### 6-3. 시각 보정

마감 `23:59:59` 뒤 첫 틱은 `00:00`~`00:10` 사이다 — 어드민 A4 「기준 시각 09.18 00:00」과 맞는다. 협의 `closed_at`은 배치 실행 시각, 정산 `confirmed_at`은 규칙값(기한 다음 날 00:00), 카드 문구의 「합의 기한(09.17 23:59)」은 `deadline_at`이다 — 세 값을 섞지 않는다.

### 8-2. 알림 — `SettlementNotifier`(어드민 설계서의 스텁 하나를 같이 쓴다)

`GroupBuyNotifier`와 같은 **훅 자리만 두는 스텁**이다(채널 미정 · 26 미결 #6). 정산 쪽 이벤트(생성 · 확정 · 지급 · 세금계산서 · 차감)와 **같은 클래스**에 조정 메서드를 더한다 — 호출 지점만 박는다.

| `adjustmentCountered` | 상대 | 2-2 ⑧ |
| `adjustmentRejected` | 제안자 | 2-4 ⑥ |
| `adjustmentAgreed` | 양측 | 2-3 ⑧ |
| `adjustmentDeadlineD1` | 양측 | 6-1 ③ |
