## 0. 먼저 정한 7가지

### 0-1. 어드민은 30·31 설계 위에 선다 — **신규 테이블은 0개, 보강 컬럼은 8개**다

30 설계 0-1이 "파트너 API만 먼저 열더라도 테이블은 **어드민 판정(직권 중단·소명·숨김·정산 확인)까지** 수용하도록 판다"고 했다. 대조한 결과 어드민 판정 6종이 쓰는 자리는 거의 다 있다.

| 어드민 쓰기 | 쓰는 곳 (30 · 31 설계) |
| --- | --- |
| 오픈 승인·반려 | `group_buy_post.review_status` · `reviewed_*` · `reject_reason_*` (30 · 1-8) |
| 게시물 숨김·해제 | `group_buy_post.hidden_*` · `unhidden_*` (30 · 1-8) |
| 직권 중단 통지·집행·철회·긴급 | `group_buy_admin_suspension` (30 · 1-7) |
| 중단·조기 마감 요청 판정 | `group_buy_change_request.status` · `decided_*` · `decision_reason` (30 · 1-6) |
| 이슈 스레드 개설 | `group_buy_issue` (`opener_type = ADMIN`) (30 · 1-9) |
| 정산 확인 | **공구에 두지 않는다** — 정산 모듈 포트(30 · 5-2) |

시안과 대조해 **빠진 자리가 8개** 나왔다(1절). 전부 "판정의 근거를 남기는 컬럼"이다 — 무엇을 보고 숨겼나(판본), 통지 시점 판매가 얼마였나(증가분의 기준점), 집행 판단을 무엇으로 했나(집행 사유). 30 설계 P1이 **아직 머지되지 않았으므로** 원안 마이그레이션에 넣는다(1-7).

### 0-2. 조건은 한 글자도 못 고친다 — **쓰기 API가 받는 것은 판정과 사유뿐**이다

§32-0 "하지 않는 것 — 공구 생성·삭제 / 조건 변경 / 기간 연장 승인 / 게시물 본문 수정 / 고정 지급비 집행". 28 설계 0-1과 같은 원칙을 공구에 옮긴다.

| 만들지 않는 API | 근거 | 대신 있는 것 |
| --- | --- | --- |
| 공구 생성·삭제 | §29-1 — 체결 트랜잭션에서만 생긴다 | — |
| 공구가·리워드율·최소 물량·기간 수정 | §29-1 "어드민도 못 고친다" | 조건을 바꾸려면 중단 + 새 계약 |
| **기간 연장 승인** | §29-6 "당사자 합의 값이라 제3자 판단 근거가 없다" | 연장 **조회 카드**(B2a) |
| **게시물 본문 수정** | §29-8 "고치면 작성자가 누구인지 흐려진다" | 숨김 + 스레드로 수정 요청 |
| 게시물 삭제 | §29-8 `[확장 가능]` — 원문은 분쟁 근거 | 숨김 |
| 고정 지급비 집행·기록 | §29-9 "플랫폼은 지급을 알 수 없다" | 계약 금액 **읽기 전용** 표기 |
| 조치 없이 독촉 | §32-6 "버튼이 있으면 눌러 놓고 처리했다고 여긴다" | 지연 감시는 **표시**만 |
| 정산 보류 해제 | §32-6 "보류 해제는 정산 관리 소관" | 정산 관리 딥링크 |
| 목록 일괄 처리 | §32-1 "목록에 실행 액션을 두지 않는다 — 모든 판정은 모달을 거친다" | 목록 응답에 `permissions` 없음 |

**조건 필드를 받는 엔드포인트가 존재하지 않는다는 것 자체가 규칙의 집행**이다(28 설계 0-1). "운영자니까 언젠가 필요할 것"이라며 열어 두면 양측이 서명한 조건이 바뀔 수 있는 시스템이 된다.

### 0-3. 공구가 끝나는 경로가 **다섯 개**다 — 부수 효과는 **한 메서드**가 한다

| # | 경로 | 소유 | 결과 |
| --- | --- | --- | --- |
| ① | 기간 종료 | 30 스케줄러 | `ENDED` · `COMPLETED` |
| ② | 조기 마감 요청 승인 | **이 설계** | `ENDED` · `EARLY_CLOSED` |
| ③ | 중단 요청 승인 | **이 설계** | `SUSPENDED` |
| ④ | 직권 중단 집행 | **이 설계** | `SUSPENDED` |
| ⑤ | 긴급 직권 중단 | **이 설계** | `SUSPENDED` |

그런데 종결이 일으키는 일은 경로와 무관하게 같다 — 대기 중인 연장을 닫고, 검토 중인 요청·통지를 닫고, 게시물을 내리고(31 설계 2-9), 상품 공구 상태를 재동기화하고(30 설계 1-11), 이행 확인 기한을 확정한다. 30 설계 3-3의 스케줄러 `end`가 이 일을 **한 경로에만** 하고 있다.

다섯 경로가 각자 부수 효과를 구현하면 **반드시 한 곳이 하나를 빠뜨린다.** 빠뜨렸을 때 생기는 일이 전부 조용하고 치명적이다:

| 빠뜨린 것 | 결과 |
| --- | --- |
| 상품 resync | **중단된 공구의 상품이 계속 결제된다** |
| 게시물 투영 | 끝난 공구의 게시물이 소비자 피드에 남는다 |
| 대기 연장 `EXPIRED` | 스튜디오 조치 큐(31 · 1-3)에 끝난 공구가 남는다 |
| 검토 요청 `LAPSED` | **어드민 조치 큐가 0이 되지 않는다**(30 · 1-6) |

→ **`GroupBuyTerminator.terminate(...)` 하나로 모으고, 30 설계 스케줄러 `end`도 이 메서드를 호출하도록 바꾼다**(8-1). 어드민이 종결 경로 넷을 소유하므로 이 공용화는 어드민 설계의 몫이다.

### 0-4. 조치 큐 = **「내가 눌러야 다음으로 가는 것」** — 서버가 한 식으로 판정한다

§32-1 "큐에 「상대가 움직여야 풀리는 건」이 섞이면 그 큐를 **0으로 만들 수 없다.**" 이 한 문장이 큐의 정의다.

같은 판정이 시안 **네 곳**에 나온다 — GNB 배지(「5 공구 관리 5」) · 탭 배지(「조치 필요 5」) · 툴바 요약(「오픈 승인 2 · 중단 요청 1 · …」) · 목록 상단 고정·경고 배경. 31 설계 1-3과 같은 판단으로 **`AdminGroupBuyQueuePredicate` 하나가 QueryDSL 식을 만들고 네 곳이 그 식을 그대로 쓴다.** 두 벌을 두면 배지는 5인데 상단 고정 행은 4인 화면이 된다.

그리고 28 설계 0-5와 같이 **큐 카운트는 목록이 아니라 `summary`가 내린다** — 검색어가 걸린 카운트는 "처리할 건이 남아 있다"는 사실을 가린다.

### 0-5. 판정은 **판본을 박는다** — 승인 후 자유 수정 체계의 필연적 귀결

31 설계가 "승인 후 인플루언서 자유 수정"(인플 제14조⑤)을 받아들이면서 `group_buy_post_revision`을 만들었다. 게시물 본문이 **판정 도중에도 바뀔 수 있는** 체계가 된 것이다. 그러면 운영자의 판정은 "이 글에 대해 내린 것"이어야 한다.

| 판정 | 박는 판본 | 없으면 생기는 일 |
| --- | --- | --- |
| 숨김 | `hidden_revision_no` | 숨긴 뒤 인플루언서가 고치면 **숨긴 이유가 된 문장이 어디에도 없다** — 분쟁 시 "그런 문장은 없었다"를 반박할 수 없다 |
| 숨김 해제 | `unhidden_revision_no` + **요청 시 판본 대조** | 운영자가 A판을 읽고 해제를 누르는 사이 B판(원래 문구)으로 되돌아가면 **같은 문구가 다시 열린다** — §29-8 규칙 ③이 막으려던 바로 그 일 |
| 직권 중단 통지 | `notice_revision_no` | 1호(법령 위반)는 대개 게시물 문구다(D-4). 소명이 "이미 삭제했다"고 주장할 때(시안 B2c) **통지 시점 본문과 현재 본문을 대조**할 기준이 없다 — 시안의 「수정 전후 본문 대조 ↗」가 가리키는 것이 이것이다 |

오픈 승인은 판본을 박지 않는다 — `PENDING` 동안 수정이 불가하므로(31 설계 2-5) 승인 대상은 **`reviewed_at` 이전 마지막 `SUBMITTED`**로 유일하게 정해진다(31 설계 2-6).

### 0-6. **시각이 여는 버튼은 서버가 시각으로 판정**한다 — 기한 계산은 `BusinessCalendar` 하나

시안에 "기한이 차면 저절로 열린다"가 셋이다 — `[중단 집행]`(소명 기한) · M6 날짜 칩(3영업일 이전 잠금) · 정산 지연 감시(종료 +30일). 셋 다 **FE 시계로 판정하면 안 된다.** 운영자 PC 시계가 1시간 빠르면 소명 기한 전에 집행이 열린다.

- 버튼 활성은 `permissions`가, 날짜 선택지는 `admin-suspension/notice-options`가 **서버 `now`(Asia/Seoul)** 로 내린다.
- 영업일 계산은 31 설계 4-4의 **`BusinessCalendar`를 그대로 쓴다.** 오픈 승인 SLA · 소명 기한 · 집행 예정 하한이 전부 같은 달력을 써야 한다 — 시안이 이미 두 가지 셈법을 섞고 있다(6-1 ⚠️).

### 0-7. **판단 근거 숫자는 포트에서 오고, 없으면 `null`이다**

어드민 화면은 세 서피스 중 **숫자로 판단하는 유일한 화면**이다 — 요청 후 증가분(B3) · 통지 후 증가분(B2c) · CS 문의 건수(B3) · 소진율(B4) · 품절 문의(B4) · 미종결 건수(B5). 30 설계 0-6 "없는 값은 `null`이지 0이 아니다"가 여기서 가장 무겁다.

| 숫자 | 0으로 내리면 운영자가 읽는 뜻 |
| --- | --- |
| 요청 후 증가분 `+0` | "요청 이후 팔리지 않는다 — 중단해도 손해가 없다" |
| CS 문의 `0` | "하자 주장이 실재하지 않는다 — 반려해도 된다" |
| 미종결 `0` | "정산해도 된다"(30 설계 0-6) |

**판정 화면에서 거짓 0은 오판으로 직행한다.** 포트가 비어 있으면 `null`을 내리고 FE는 「집계 불가」로 그린다.

## 1. 모델 보강 — 30·31 설계 대비 **8개 컬럼**

### 1-1. `group_buy` — `fulfillment_agreed_at` 1개

| 컬럼 | 타입 | 비고 |
| --- | --- | --- |
| `fulfillment_agreed_at` | DATETIME(6) NULL | 3자 스레드가 **양측 동의로 종결**된 시각 — 연결·소통이 통보(8-4) |

30 설계는 `fulfillment_resolved_at`("양측 동의 종결 시각") 하나로 **합의와 보류 해제를 같은 사건**으로 보았다. 시안 B5a가 둘을 가른다.

```
이슈 스레드 종결 · 이행 합의      2026.08.21 14:30 · 운영자(김운영) 중재 · 양측 동의
정산 보류 해제 — 양측 동의로 종결  2026.08.21 14:35 · 운영자(김운영) · 정산 관리
```

§32-6 "합의는 게시물·소통 모니터링, **보류 해제는 정산 관리** 소관". 합의(당사자 행위)와 해제(정산 관리의 처리)가 다른 화면에서 다른 시각에 일어나므로 **두 시각을 따로 둔다.**

| 컬럼 | 뜻 | 쓰는 곳 |
| --- | --- | --- |
| `fulfillment_agreed_at` (신규) | 양측이 동의했다 | 연결·소통 → `recordFulfillmentAgreement` |
| `fulfillment_resolution_note` (30) | 무엇으로 합의했나 — **당사자 합의이지 운영자 판정이 아니다**(제20조④) | 같은 호출 |
| `fulfillment_resolved_at` (30) | 정산 보류가 풀렸다 | 정산 모듈 → `releaseFulfillmentHold` |

**정산 보류 파생식(30 설계 1-9)은 `fulfillment_resolved_at` 기준을 유지한다.** 합의가 끝났어도 정산 관리가 풀기 전까지는 보류다 — 시안 14:30~14:35 사이가 그 상태다.

### 1-2. `group_buy_admin_suspension` — 5개 + 상태값 1개

### 2-1. 가시성 — **필터가 없다**

어드민은 모든 공구를 본다. 조건은 **인증뿐**이다 — `SecurityConfig`의 `/v1/admin/**` → `RoleType.ADMIN`이 이미 막고 있고, 처리자 식별은 28 설계와 같이 `UserPrincipal.getUserId()` → `Seller`(`RoleType.ADMIN`)로 한다.

공구는 계약 체결 트랜잭션에서 생기므로(30 설계 0-2) 계약의 `DRAFT` 같은 "아직 도착하지 않은 단계"가 없다. 28 설계 2-1의 가시성 조건에 해당하는 줄이 **공구에는 필요 없다.**

| 큐 코드 | 라벨 | 조건 | 다음 차례가 운영자인 이유 |
| --- | --- | --- | --- |

**넣지 않는 것** — §32-1이 셋을 명시했다.

| 대상 | 다음 차례 |
| --- | --- |
| 게시물 숨김 | 인플루언서(고칠 권한) |
| 소명 대기 중(미제출 · 기한 전) | 브랜드 |
| 이행 미합의(정산 보류) | 3자 스레드 · 정산 관리 |

> ⚠️ **「소명 기한이 지났는데 미제출」은 큐에 넣는다 — 시안이 그리지 않은 경우다.** §32-1은 "소명 대기 중(미제출) — 다음 차례가 브랜드다"로 뺐다. 그런데 기한이 지나면 브랜드는 더 이상 소명할 수 없고(30 설계 4-6 `APPEAL_DEADLINE_PASSED`), 제17조④ "미제출 시 **기존 자료를 기준으로 최종 판정**"의 판정자는 운영자다. 집행은 자동이 아니므로(30 설계 0-5) 이 건을 큐에서 빼면 **아무도 누르지 않는 통지**가 종료일까지 남는다. 큐의 원리("내가 눌러야 다음으로 가는 것")를 그대로 적용한 결과이고, 라벨은 「소명 검토」로 유지한다(13-1 #20).

**`PENDING` 게시물이 `PREPARING`에서만 존재하므로** 조건에 상태를 붙이는 것이 중복처럼 보이지만 남긴다 — 7-2 #2의 "시작 시각이 지난 준비중"에서 30 설계가 전이를 바꾸면 이 가정이 깨진다. 조건이 스스로 서 있어야 한다.

**네 큐는 서로 배타적이다** — 한 공구가 두 큐에 동시에 들 수 없다.

| 조합 | 불가능한 이유 |
| --- | --- |
| 오픈 승인 × 요청 | 오픈 승인은 `PREPARING`, 요청은 `READY`·`IN_PROGRESS`에서만 생긴다 |
| 중단 요청 × 조기 마감 요청 | 생성 컬럼 UNIQUE — 공구당 `PENDING` 1건(30 · 1-6) |
| 요청 × 소명 검토 | 통지가 있으면 `SUSPENSION_SCHEDULED`이고 요청 차단(30 · 4-5) · **통지 전 검토 중 요청이 있으면 통지를 막는다**(6-2) |

→ **`actionRequiredCount` = 큐 4개의 합 = 조치 필요 탭의 행 수**가 항상 성립한다. 28 설계(계약)는 큐 합과 행 수가 다를 수 있었다. 공구는 같아야 하고, 테스트로 고정한다(12절).

### 2-4. 정렬

| `sort` | 시안 | 정의 |
| --- | --- | --- |
| `ACTION_REQUIRED_FIRST` (기본) | 조치 필요 우선 | ⓪ 큐 해당 여부 ① `group_buy.created_at DESC` ② `group_buy_id DESC` |
| `CREATED_DESC` | 최근 등록순 | ① ② |
| `END_AT_ASC` | 종료 임박순 | ⓪ 비종결 먼저 ① 비종결은 `end_at ASC` · 종결은 `ended_at DESC` ② `group_buy_id DESC` |

- **「상단 고정」은 정렬 키 ⓪이지 별도 목록이 아니다.** 페이지 경계를 넘어도 규칙이 유지되고, 조치 행이 20건을 넘으면 1페이지가 전부 조치 행이 된다 — 그게 맞다.
- **경고 배경은 FE가 탭으로 끈다.** 서버는 행마다 `actionRequired`를 내리고, `ACTION_REQUIRED` 탭에서는 FE가 배경을 그리지 않는다(§32-1 "조치 필요 탭은 고정·배경을 쓰지 않는다"). 정렬은 탭과 무관하게 같다 — 조치 탭에서는 ⓪이 전부 같아 자연히 최근 등록순이 된다(시안 A2 행 순서와 일치).
- **「종료 임박순」의 종결 건 처리** — 31 설계 1-2와 같은 문제다. 순수 `end_at ASC`면 끝난 지 두 달 된 공구가 맨 위에 온다.

### 2-5. 검색 — 4축

`keyword` — **공구명(`contract.title`) · 공구번호 · 브랜드명(`market`) · 쇼룸명(`creator`)**(§32-1). 파트너(인플루언서명)·스튜디오(브랜드명)와 달리 **양측을 다 찾는다.** 계약번호는 넣지 않는다 — 시안이 4축을 명시했고, 계약번호로 찾을 일은 계약 관리에서 한다.

**`nearestDeadlines` — 큐마다 기한의 뜻이 다르다**

| 큐 | 기한 | 근거 |
| --- | --- | --- |
| `OPEN_REVIEW` | `addBusinessDays(submitted_at의 날짜, SLA)` 23:59:59 | B1 "SLA 영업일 3일 · 기한 2026.08.19 (D-2)" |
| `APPEAL_REVIEW` | `execute_scheduled_at` | A2 "소명 검토 1건(… · **집행 예정** 09.25)" |
| `SUSPEND_REQUEST` · `EARLY_CLOSE_REQUEST` | **없음** | §33-1 #2 — 검토 SLA 미정. 기한을 지어내지 않는다 |

- 큐마다 **가장 이른 1건**만 내린다. A2의 요약 문구 "최단 기한 D-1 (…) · 소명 검토 1건(…)"은 FE가 이 배열로 조립한다.
- **요청 두 큐에 기한이 없다는 것이 정보다** — FE는 그 둘을 최단 기한 후보에서 빼고 건수만 말한다. SLA가 확정되면 이 배열에 행이 생길 뿐 구조는 바뀌지 않는다.
- **`OPEN_REVIEW` 기한은 판정이 아니라 표시다.** 초과해도 자동 처리하지 않는다(§33-1 #1 ⓐ — 시안도 "기한 표시만").

**`settlementWatch` — 조치와 다른 축**(§32-1 "정산 지연 감시는 다른 축이라 요약 줄에 남긴다")

| 필드 | 정의 |
| --- | --- |
| `watchingCount` | `ENDED` 전체 — 정산이 끝나지 않은 종료 공구 |
| `overdueCount` | `ENDED` ∧ `ended_at + watch-days <= now` |
| `nearest` | 감시 기한이 가장 이른 `ENDED` 1건 · `reached` = 기한 도달 여부 |

- **`overdueCount > 0`이어도 `actionRequiredCount`에 더하지 않는다** — §32-6 "지연 감시는 경고 톤을 **실제로 30일을 넘긴 뒤에만** 쓴다"는 **톤 규칙**이지 큐 규칙이 아니다. 기한을 넘겨도 운영자가 이 화면에서 누를 버튼이 없다(독촉 버튼 없음). 큐에 넣으면 0으로 만들 수 없다.
- 톤은 FE가 `reached`로 고른다 — 도달 전 정보, 도달 후 경고.
- `SUSPENDED` 공구의 정산 지연은 여기서 세지 않는다 — 13-2 #12.

> ⚠️ **시안 A3의 "지연 감시 1건"은 같은 화면의 「종료 2」와 맞지 않는다.** 어느 1건을 세는지 정의가 없다. 서버는 **감시 중(전체 `ENDED`) · 기한 초과 · 가장 이른 1건** 셋을 따로 내리고, 문구는 FE가 고른다(13-1 #3).

**GNB 배지 = `actionRequiredCount`.** A3 "좌측 GNB 배지도 사라진다" — 0이면 FE가 배지를 그리지 않는다. 30 설계 4-3 · 31 설계 3-3과 같이 GNB는 공구 화면 밖에서도 폴링되므로 **목록과 분리된 가벼운 쿼리**여야 한다 — 큐 4개는 `COUNT` 4회, 탭 카운트는 `GROUP BY status` 1회 + 큐 합.

### 4-3. `readiness` · `openReview` — B1

게이트 판정은 30 설계 4-4의 `gates[3]`를 쓰되 **어드민 관점의 `state`**를 준다(31 설계 4-3 "서피스가 판정한다").

| 게이트 | `state` (어드민) |
| --- | --- |
| ① 최소 물량 | `DONE`(시각 · 브랜드명) / `WAITING` |
| ② 게시물 | `DONE`(제출 시각 · 쇼룸명) / `WAITING`(미작성·작성중) / **`REJECTED`**(반려 후 재등록 대기) |
| ③ 오픈 승인 | 게시물 `PENDING` → **`MY_TURN`** / `APPROVED` → `DONE` / 그 외 `WAITING` |

`tone`은 `MY_TURN`일 때만 `warning`이다(§29-4 "내 차례인 줄만 경고 톤").

```json
"openReview": {
  "submittedAt": "2026-08-16T09:41", "slaBusinessDays": 3,
  "dueAt": "2026-08-19T23:59:59", "daysLeft": 2,
  "startAt": "2026-08-22T10:00", "overdue": false
}
```

- **`dueAt`과 `startAt`을 한 블록에 싣는다** — §32-2 "기한 D-2와 시작일을 함께 적어 **승인이 늦으면 공구가 열리지 않는다**는 연결을 말한다". FE가 두 블록에서 찾아 붙이게 하지 않는다.
- `dueAt` = `addBusinessDays(2026-08-16, 3)` = 08.19(수) — 16일(일)은 세지 않고 월·화·수. 31 설계 4-4 B2 식과 같은 계산이다.
- **B1의 "승인 → 준비완료"는 확정이 아니다** — 게이트 ①이 아직이면 승인해도 `PREPARING`에 남는다. 시안 B1은 ①이 끝난 경우만 그렸다. 승인 응답에 **전이 결과**(`status`)를 실어 FE가 "준비완료가 되었습니다" / "브랜드 물량 확인을 기다립니다"를 고른다(5-1).
- **`startOverdue`** — 시작 시각이 이미 지난 `PREPARING`(30 · 7-2 #2). 승인하면 다음 tick에 **단축된 기간으로** 바로 열린다. 운영자에게 이 사실을 보여줘야 한다 — FE 경고 문구의 근거값이다.

- **원문 전체를 그대로** 내린다(§32-2 "제목·본문·담긴 상품 · 사진 없음"). 요약·잘라내기 없음.
- **담긴 상품은 `items[]`를 쓴다** — 게시물의 상품 = 계약 상품 전부(30 · 1-8). 상품 칩 = `items[].productId` → 상품 관리 상세 딥링크(§32-2 "마스터 값을 바로 대조").
- **`disclosureText`는 31 설계 2-8의 `GroupBuyDisclosure.text()`** — 심사 기준 「대가관계 표시 훼손」을 판정하려면 운영자가 **실제로 붙는 문구**를 봐야 한다.
- `postNumber` — 시안 「POST-GB-20260802-104」. 게시물 번호 체계가 30·31 설계에 없다 → `POST-GB-{제출일}-{post_id}`로 **표시 전용 파생**(저장하지 않는다). 확정 전까지 파생값이라 형식이 바뀌어도 데이터 영향이 없다(13-2 #16).
- `editCount` = `group_buy_post_revision`의 `EDITED` 개수 · `latestRevisionNo` = 최대 `revision_no`. **숨김 해제 요청에 이 값을 되돌려 받는다**(5-4).
- `hidden.hiddenDays` — B2b "숨김 경과 6일" · §32-5 "**경과일**을 세어 방치를 드러낸다". 양끝 포함 일수(31 · 4-9).
- `hidden.ordersSinceHidden` — B2b "숨김 이후 유입 없음 · 08.12 09:05 이후 증가 0". 31 설계 8-1의 `countOrdersSince`. **포트가 비어 있으면 `null`**(0-7) — 이 값이 거짓 0이면 "숨김이 판매를 멈췄다"는 사실 주장이 된다.
- **종결 후에도 원문을 내린다**(§32-7 "종료·조기 마감·중단·정산완료 4개 종결 화면 모두"). `closedBy`로 FE가 하단 문구("중단으로 내려간 게시물이다")를 고른다.

### 4-5. `sales` · `activeRequest.decisionBasis` — 판단 근거

**`sales` — 상태별**

| 상태 | `sales` | 시안 |
| --- | --- | --- |
| `PREPARING` · `READY` | `null` | 체크리스트 자리 |
| `IN_PROGRESS` · `SUSPENSION_SCHEDULED` | `LIVE` | B2 · B2a · B2b · B2c 4칸 그리드 |
| `ENDED` | **`null`** | B5 계열에 4칸 그리드가 없다 · 정산 예정은 `afterEnd.settlement`(4-8) |
| `SETTLED` | `SETTLED` | 30 · 4-4와 같다 |
| `SUSPENDED` | **`null`** | B6에 그리드가 없다 · 접수분 건수는 `closure`(4-9) |

`ENDED`의 `null`은 파트너(§30-4)와 같고 스튜디오(`PROVISIONAL`)와 다르다. 어드민 시안이 파트너 쪽을 택했다.

**`decisionBasis` — B3 중단 요청**

```json
"decisionBasis": {
  "ordersAtRequest": 142, "ordersNow": 159, "ordersSinceRequest": 17,
  "quantityNow": 241, "amountNow": 6402300,
  "inquiries": { "total": 12, "defectRelated": null }
}
```

- **요청 시점 스냅샷(30 · 1-6 `sales_order_count_at_request`)과 현재값의 차**. §32-4 "요청 시점 대비 재계산". 둘 중 하나라도 포트에서 못 받으면 `ordersSinceRequest = null`.
- **`inquiries.total`** — §32-4 "CS 문의 건수 — **하자 주장의 실재를 재는 유일한 지표**". 출처 둘을 합한다.

| 출처 | 조건 | 지금 가능한가 |
| --- | --- | --- |
| 상품 문의(`product_inquiry`) | `product_id ∈ 계약 상품` ∧ `created_at >= 요청 시각` | ✅ 테이블이 있다 |
| 1:1 문의(`one_to_one_inquiry`) | `order_id ∈ 이 공구의 주문` ∧ `created_at >= 요청 시각` | ❌ 주문에 공구 귀속이 없다(30 · 5-1) |

1:1 문의 쪽이 비면 **`total = null`** 이다. 상품 문의만 세서 내리면 "12건"이 "3건"으로 줄어 보이고, 운영자는 그 숫자를 하자 주장의 반증으로 읽는다. **부분 합을 전체 합처럼 내리지 않는다.**

- **`defectRelated`는 항상 `null`이다** — 시안 "하자 관련 4건". 상품 문의 유형(`ProductInquiryType`: 옵션·성분·재입고·배송·기타)에도, 1:1 문의 유형(`CsCategory` 5종)에도 **하자 분류가 없다.** 키워드 매칭으로 지어내면 "있지도 않은 규칙이 있는 것처럼" 보인다(§32-2). 분류가 생기면 채운다(13-2 #14).

**`decisionBasis` — B4 조기 마감 요청**

```json
"decisionBasis": {
  "quantityNow": 500, "preparedQuantity": 500, "sellThroughRate": 100,
  "ordersNow": 318, "amountNow": 13515000,
  "soldOutInquiriesSinceRequest": 9,
  "originalEndAt": "2026-08-22T23:59", "endAtIfApproved": "now"
}
```

- **`preparedQuantity` = 계약 상품 `minQuantity`의 합** — §32-4 "판매 수량 / **준비 물량**을 한 줄에 붙여 소진율을 즉시". 브랜드가 게이트 ①에서 확인한 것이 이 값이다. 실제 보유 재고(`product_variant.stock`)가 아니다(30 · 4-6 "서버는 재고를 판정하지 않는다").
- 상품이 여러 개면 **합계로 한 줄**을 내리고 `items[]`의 상품별 `minQuantity`와 `sales.itemQuantities[]`로 FE가 상품별 소진율을 그릴 수 있게 둔다.
- **`soldOutInquiriesSinceRequest`** — §32-4 "품절 문의 건수로 「지금 남겨두면 생기는 손해」를 잰다". 상품 문의 `type = RESTOCK`(재입고) ∧ 계약 상품 ∧ 요청 이후. **상품 문의 테이블만으로 셀 수 있는 유일한 판단 근거**다 — P1부터 값이 나온다.
- `endAtIfApproved: "now"` — B4 "승인 시 종료 2026.08.19 **즉시**". 서버가 날짜를 박지 않는다 — 승인 버튼을 누르는 시각이 종료 시각이다.

**`activeRequest.elapsed`** — B3 "검토 경과 5일". `ChangeRequestElapsedFormatter`(`api/admin/changerequest`)와 **같은 표기 규칙**을 쓴다 — 어드민의 경과 표기가 화면마다 다르면 안 된다. 판정(SLA)은 하지 않는다(§33-1 #2).

### 4-6. `adminSuspension` — B2c

```json
"adminSuspension": {
  "id": 7, "kind": "NOTICE", "clause": "ART17_1_LAW", "clauseLabel": "제17조① 1호 법령 위반",
  "noticeBody": "게시물 본문에 “모발 손상이 회복됩니다”, …",
  "noticedAt": "2026-08-08T10:30", "noticedByName": "김운영", "elapsedDays": 3,

  "appeal": {
    "content": "지적하신 두 문장은 08.12 15:40에 이미 삭제했고 …",
    "submittedAt": "2026-08-12T17:05", "submittedByName": "이현",

  }

```

- **`salesSinceNotice`** — §32-3 "「통지만으로 판매가 멈추지 않는다」를 **통지 후 증가분**과 함께". 1-2의 스냅샷 기준. 포트가 비면 `null`.
- **`noticeRevisionNo`와 `post.latestRevisionNo`가 다르면** 통지 후 게시물이 바뀐 것이다 — 「수정 전후 본문 대조 ↗」는 이 두 판본으로 `GET /post/revisions`(5-5)를 연다. 브랜드 소명이 "이미 삭제했다"(시안)면 운영자가 **실제로 삭제됐는지** 판본으로 확인한다.
- `appeal.submittedByName` — 시안 "퓨어랩 담당자 **이현**". 소명 제출자 셀러 계정의 이름. 브랜드 명의(`market.name`)와 다른 값이다.
- **첨부 URL을 상세에 싣지 않는다** — 다운로드 URL은 유효기간이 있어(28 설계 5분) 상세 응답에 박으면 화면을 오래 열어 둔 운영자가 만료된 링크를 누른다. 목록만 내리고 클릭 시 `GET …/attachments/{id}`로 발급한다. `status = UPLOADED`인 첨부만 내린다.

### 4-7. `extension` — B2a 조회 카드

30 설계 4-4의 `extension` 블록을 그대로 쓴다. 어드민은 **판정하지 않으므로 `permissions`에 연장 관련 키가 없다**(§32-4 "운영자 액션 버튼이 없다").

`beforeTotalDays` · `afterTotalDays`는 B2a "14일 · 연장 요청 시 21일". 상한(30일) 판정은 요청 시점에 끝났다(30 · 4-6).

### 4-8. `afterEnd` — B5 · B5a · B5b

```json
"afterEnd": {
  "fulfillment": {
    "brandToCreator": { "result": "FULFILLED", "reason": null, "checkedAt": "2026-08-08T11:04",
                        "checkedByName": "글로우랩", "auto": false,
                        "target": { "duties": ["SHOWROOM_POST","FEED","REELS","STORY"],
                                    "counts": { "feed": 1, "reels": 1, "story": 3 } } },
    "creatorToBrand": { "result": "UNFULFILLED", "reason": "교환 재발송이 11건 지연되고 …",
                        "checkedAt": "2026-08-09T16:20", "checkedByName": "예린 뷰티", "auto": false,
                        "target": { "duties": ["ORDER_DELIVERY"] } },
    "dueAt": "2026-08-10T23:59:59", "duePassed": true, "autoConfirmOnTimeout": false,
    "threadId": 5521, "agreedAt": null, "resolutionNote": null, "resolvedAt": null,
    "onHold": true
  },
  "settlement": { "stage": "WAITING", "stageSource": "PORT",
                  "blockers": ["UNCLOSED_ORDERS", "FULFILLMENT_DISPUTE"],
                  "watch": { "dueAt": "2026-09-06", "elapsedDays": 12, "reached": false },
                  "preview": { "provisionalSalesAmount": 12096000, "rewardRates": [12], "rewardAmount": null } },
  "orderClosure": { "totalCount": 312, "closedCount": 294,
                    "unclosed": [ { "stage": "EXCHANGE_RESHIP_PENDING", "label": "교환 재발송 대기", "count": 11 },
                                  { "stage": "RETURN_REVIEW", "label": "반품 심사", "count": 7 } ] },
  "openIssue": null

```

**① 방향으로 이름 짓는다 — `mine`/`theirs`가 아니다.** 파트너·스튜디오는 "내가 상대를 확인한 결과"(30 · 4-6, 31 · 4-7)지만 운영자에게는 "나"가 없다. 시안 그대로 **`brandToCreator` · `creatorToBrand`**.

**② `blockers` — 「왜 아직 정산이 안 되나」를 서버가 판정한다**

| 코드 | 조건 | 카드 | 성격 |
| --- | --- | --- | --- |
| `UNCLOSED_ORDERS` | 미종결 > 0 | 주문 종결 현황(레일) | **정산 선행 조건 미충족** |
| `FULFILLMENT_PENDING` | 한쪽이라도 이행 확인 행 없음 | 이행 확인 카드 | 선행 조건 미충족 |
| `FULFILLMENT_DISPUTE` | `onHold` (30 · 1-9 파생식) | 이행 확인 카드 | **정산 보류** |
| `CLOSURE_UNKNOWN` | 판매 포트가 비어 미종결을 알 수 없음 | — | 판정 불가(0-7) |

- **§32-6 "사유가 둘이면 카드도 둘"을 서버가 보장한다** — FE가 세 블록을 뒤져 사유를 세게 두면 "하나만 보이면 나머지를 찾아 헤맨다"가 재현된다. B5 = `[UNCLOSED_ORDERS, FULFILLMENT_DISPUTE]` · B5a·B5b = `[UNCLOSED_ORDERS]`.
- **코드 이름이 보류와 선행 조건을 가른다** — D-3("미종결 주문은 보류가 아니라 **정산 선행 조건 미충족**이라 성격이 다르다")에 서버가 먼저 답해 둔다. 화면이 둘을 같은 "정산이 멈춘 사유"로 묶는 것은 FE 문구 문제이고, 데이터는 섞이지 않는다.
- **`CLOSURE_UNKNOWN`이 있는 동안 `canConfirmSettlement`는 `false`다** — 30 설계 7-3 "`isSettlementReady`는 empty면 `false`".

**③ 무응답 표기 — `auto`와 `duePassed`**

§32-6 "한쪽이 **무응답 → 자동 이행**이면 **그 사실을 반드시 적는다** — 「확인한 적 없다」는 분쟁이 나면 이 한 줄이 근거다". `auto = true` 행은 `checkedByName = null`이고 FE는 "무응답 → 자동 이행"으로 쓴다.

그런데 30 설계 1-9가 자동 이행을 **스위치로 꺼 두었다**(D-1 · 기본 꺼짐). 스위치가 꺼진 동안 시안 B5b의 "인플루언서 무응답 → 자동 이행" 줄은 **나오지 않고**, 대신 `creatorToBrand = null` ∧ `duePassed = true`가 된다. 이때 `blockers`에 `FULFILLMENT_PENDING`이 남아 **정산이 무기한 열리지 않는다** — 13-2 #9에서 다룬다. `autoConfirmOnTimeout`을 내려 FE가 B5b 힌트("무응답은 이행으로 처리됩니다")를 스위치와 다르게 말하지 않게 한다(31 · 4-7과 같은 이유).

**④ B5a — 합의는 결과 표시이지 판정이 아니다**

| 필드 | 출처 | 시안 |
| --- | --- | --- |
| `agreedAt` | `group_buy.fulfillment_agreed_at`(1-1) | "합의 2026.08.21 14:30 · 3자 스레드 종결" |
| `resolutionNote` | `fulfillment_resolution_note` | "합의 결과 — 브랜드가 교환 재발송 11건을 …" |
| `resolvedAt` | `fulfillment_resolved_at` | "보류 해제 · 2026.08.21 · 정산 관리에서 처리" |

**미이행 행은 그대로 `UNFULFILLED`다.** 시안 "이행 — 미이행 제출 2026.08.09 → **합의로 이행 전환** 2026.08.21"은 확인 결과가 바뀐 것처럼 읽히지만, 이행 확인은 **불가역**이다(제20조② · 30 · 1-9). 서버는 행을 고치지 않고 **`result = UNFULFILLED` + `agreedAt != null`** 조합을 내리며, 「합의로 해소」 표기는 FE가 이 조합으로 만든다(13-1 #13). 바꾸면 "누가 언제 미이행을 제출했는가"라는 분쟁 근거가 덮인다.

**⑤ `settlement.stage` — 정산 상태머신은 읽기만 한다**

| `stage` | 뜻 | 출처 |
| --- | --- | --- |
| `WAITING` | 정산 대기 | 정산 포트 · 포트가 없으면 `ENDED`에서 파생 |
| `CONFIRMED` | 운영자 확인 | **정산 포트만** |
| `TRANSFERRED` | 이체 완료 | `SETTLED` 상태 |

§32-6 "정산 상태머신은 어드민에만 있다" — 이 "어드민"은 **어드민 서피스**이지 **공구 테이블**이 아니다. 30 설계 5-2가 "정산 상태머신은 공구에 두지 않는다 · 공구가 아는 것은 `SETTLED` 하나"로 정했다. `stageSource = DERIVED`면 FE는 중간 단계를 확정값처럼 그리지 않는다.

- **파트너·스튜디오 응답에 `stage`를 싣지 않는다** — "중간 단계를 노출하면 운영자 내부 절차가 새어 나간다"(§32-6). 30·31 설계에 이미 없다. 이 필드는 **어드민 DTO에만** 존재한다.

**⑥ `preview` — 리워드는 확정 대기**

§32-6 "리워드를 **확정 대기**로 두고 **잠정 금액을 쓰지 않는다**". `rewardAmount`는 **항상 `null`** 이고 `rewardRates`(계약 상품 리워드율의 중복 제거 목록)만 내린다. 시안 "확정 판매액 **잠정** 12,096,000원"은 판매 포트의 취소·반품 반영 매출이다 — 이것도 포트가 비면 `null`.

**⑦ `orderClosure` — 미종결만 쪼갠다, 종결 경로는 쪼개지 않는다**

| 시안 | 이 설계 |
| --- | --- |
| "종결 294건 · 구매확정 271 · 환불 19 · 거절 확정 4" | **`closedCount`만** — 경로별 내역을 내리지 않는다 |
| "미종결 18건 · 교환 재발송 대기 11 · 반품 심사 7" | **`unclosed[]` 단계별** |

§29-11 "경로별 내역은 **판매 관리 소관.** 공구 화면은 **남은 건수만** 센다 — 같은 표를 다시 그리면 두 화면의 숫자가 어긋난다" · §32-6 "경로별 내역은 판매 관리 소관". 시안이 종결 경로(구매확정·환불·거절 확정)를 그린 것은 이 규칙과 정면으로 부딪친다(13-1 #12).

미종결 단계별 건수는 31 설계 8-1이 "§29-11과 충돌하지 않는다 — **남은 건이 어디에 걸려 있나**"로 판단한 것과 같다. 다만 31 설계는 두 칸(`awaitingShipment` · `inReturnOrExchange`)으로 고정했고, 어드민 시안은 **다른 쪼갬**(교환 재발송 대기 · 반품 심사)을 그렸다. 서피스마다 다른 칸을 요구하므로 **판매 포트가 단계 목록(`stage` · `label` · `count`)을 돌려주고 서피스가 필요한 만큼 묶게** 31 설계 8-1의 포트 시그니처를 바꾼다(11-1). 단계 enum은 판매 관리가 소유한다.

### 4-9. `closure` — B6 · 종결 화면

```json
"closure": {
  "closeType": "SUSPENDED", "endedAt": "2026-07-18T17:40", "source": "REQUEST",
  "reasonLabel": "상품 하자", "reasonDetail": "동일 로트 이물 혼입",
  "requester": { "type": "SELLER", "name": "무드코스메틱", "requestedAt": "2026-07-18T09:22" },
  "decidedByName": "김운영", "decisionReason": "생산 로트 하자가 확인되어 …",
  "acceptedOrderCount": 87,
  "adminBasis": null
}
```

- **§32-7 B6 "종결 유형 · 사유 · 요청자 · 승인자 · 접수분 처리 · 판매 리워드 6개"** — 판매 리워드 문구("접수분 기준 그대로 정산 · 잔여 기간 청구권 소멸 · 제16조④2")는 규칙 고지라 FE 상수다.
- `source` — `REQUEST`(요청 승인) / `ADMIN_NOTICE`(통지 → 집행) / `ADMIN_EMERGENCY`(긴급). 30 설계 4-4와 같은 값. `ADMIN_*`이면 `requester = null` · `adminBasis{ kind · clauseLabel/emergencyLabel · body · executionNote }`.
- `acceptedOrderCount` — "접수분 87건 · 회수·환불 진행". **판매 포트** · 비면 `null`. 「판매 관리에서 처리 ↗」는 FE 딥링크(11-3).
- **조기 마감도 `closure`를 채운다** — `ENDED`이지만 `closeType = EARLY_CLOSED`면 요청자·승인자·사유가 필요하다. 시안에 조기 마감 종결 화면이 없다(13-1 #4).
- **액션이 없다** — `permissions`가 전부 `false`(이슈 개설 제외 · 4-10).

> ⚠️ **B6 경고문 "이미 지급된 고정 지급비 150,000원은 플랫폼이 회수해 주지 않습니다"** — 금액을 박아 "이미 지급된"이라고 단정하면 **플랫폼이 알 수 없는 지급 사실**(§29-9)을 화면이 주장하게 된다. 서버는 지급 여부를 내리지 않는다. 문구는 "지급됐다면 플랫폼이 회수해 주지 않습니다"처럼 조건형이어야 한다(13-1 #17).

### 4-10. `permissions` — 12종

| 키 | 조건 | 시안 |
| --- | --- | --- |
| `canApproveOpen` · `canRejectOpen` | `PREPARING` ∧ 게시물 `PENDING` | B1 |
| `canHidePost` | 게시물 `APPROVED` ∧ 숨김 아님 ∧ 공구 `READY`·`IN_PROGRESS`·`SUSPENSION_SCHEDULED` | B2 계열 |
| `canUnhidePost` | 숨김 중 ∧ 공구 비종결 | B2b |
| `canNoticeSuspension` | `IN_PROGRESS` ∧ `PENDING` 요청 없음 ∧ **통지 가능 창이 있음**(6-1) | B2 · B2a · B2b |
| `canEmergencySuspend` | `IN_PROGRESS` · `SUSPENSION_SCHEDULED` | B2 계열 · B2c |
| `canExecuteSuspension` | `NOTICED` ∧ `now > appeal_deadline_at` ∧ **`now >= execute_scheduled_at`** | B2c |
| `canWithdrawSuspension` | `NOTICED` | B2c |
| `canApproveRequest` · `canRejectRequest` | `PENDING` 요청 존재 ∧ 공구가 요청 가능 상태 | B3 · B4 |
| `canOpenIssue` | `ENDED`·`SETTLED`·`SUSPENDED` ∧ 열린 이슈 없음 | B5 · B5b |
| `canConfirmSettlement` | `ENDED` ∧ `blockers = []` ∧ 정산 포트 `stage = WAITING` | B5 계열 |

**불가 사유를 함께 내린다** — `canNoticeSuspension = false`일 때 `noticeUnavailableReason`(`REQUEST_PENDING` · `NO_WINDOW_BEFORE_END` · `STATUS`). 특히 `NO_WINDOW_BEFORE_END`(종료까지 3영업일 + 소명 기한이 안 남음)는 **운영자가 긴급 경로로 새는 가장 흔한 이유**가 될 것이다 — 버튼이 왜 잠겼는지 모르면 열려 있는 `[긴급 중단]`을 누른다. 사유를 보여 줘야 "그러면 기다리거나 요청을 판정하라"는 판단이 선다.

**`canExecuteSuspension`의 시각 조건이 시안보다 하나 많다** — 6-3에서 다룬다.

**실행 API는 같은 판정 메서드(`AdminGroupBuyPermissionPolicy`)를 다시 호출해** 409로 막는다(30 · 4-5).

### 4-11. `history[]` — 전량 + 게시물 수정 합성

```json
{ "eventType": "POST_HIDDEN", "actorType": "ADMIN", "actorDisplayName": "김운영",
  "detail": "표시광고법 위반 문구", "occurredAt": "2026-08-12T09:05" }
{ "eventType": "POST_EDITED", "actorType": "CREATOR", "actorDisplayName": "민재 셀렉트",
  "detail": "2회차 · 재승인 없음", "occurredAt": "2026-08-09T14:22", "synthetic": true, "revisionNo": 3 }
```

- **이벤트 전량**을 내린다 — 31 설계 6-2의 화이트리스트를 쓰지 않는다. 소명(`APPEAL_SUBMITTED`) · 요청 메모 · 물량 확인 detail이 전부 운영자에게 가는 정보다.
- **`POST_EDITED`는 합성 행**이다(1-4 ③). `group_buy_post_revision(kind = EDITED)`를 `occurredAt` 기준으로 병합 정렬한다. `synthetic: true`로 저장된 이벤트가 아님을 밝힌다 — 이력 내보내기·감사 로그가 생길 때 두 종류를 섞어 세지 않게.
- **B1의 두 줄**("오픈 승인 요청 접수" + "공구 게시물 등록", 같은 시각) — 30 설계는 `POST_SUBMITTED` 한 이벤트다. 서버가 이벤트를 쪼개지 않는다(13-1 #5).
- **정렬: 최신순**(시안 "처리 이력 최신순"). 파트너·스튜디오와 같다.

## 5. 판정 API — 오픈 승인 · 게시물

### 5-1. 오픈 승인 — `POST /{id}/open-review/approve`

바디 없음.

| 순서 | 내용 |
| --- | --- |
| 1 | `group_buy` → `group_buy_post` 순으로 **`PESSIMISTIC_WRITE`**(31 · 2-7 잠금 순서) |
| 2 | `canApproveOpen` — 아니면 409 `GROUP_BUY_OPEN_REVIEW_NOT_PENDING` |
| 3 | `review_status = APPROVED` · `reviewed_at = now` · `reviewed_by` · **반려 필드는 보존** |
| 4 | 이력 `OPEN_APPROVED`(ADMIN · 실명) |
| 5 | `GroupBuyReadiness.promoteIfSatisfied`(30 · 3-2) — 게이트 ①이 이미 끝났으면 **이 요청이 `READY`를 만든다** · 상품 resync |
| 6 | 통지 — 인플루언서(승인) · 브랜드 · `READY`가 됐으면 양측 준비완료 |

```json
{ "groupBuyId": 41, "status": "READY", "postStatus": "SCHEDULED", "openAt": "2026-08-22T10:00" }
```

- **응답에 전이 결과를 싣는다** — 4-3. 게이트 ①이 남아 있으면 `status: "PREPARING"`.
- **반려 필드를 지우지 않는다** — 31 설계 2-4와 같은 이유(재심사 맥락). 승인 후 게시물 카드에는 `rejection`을 내리지 않는다 — 상세 조립 시 `review_status = APPROVED`면 `rejection = null`. 과거 반려는 이력에 있다.
- **지급 문구가 없다** — §32-2 "오픈 승인의 결과는 **공구가 열리는 것 하나**". 응답·통지·이력 어디에도 고정 지급비를 언급하지 않는다(§29-9).
- **승인 후 게시물 노출은 이 API가 하지 않는다** — `READY`의 게시물은 「예약」이고 `post.status = DRAFT` 그대로다. 노출은 스케줄러 오픈이 `GroupBuyPostExposure.sync`로 한다(31 · 2-9).

### 5-2. 오픈 반려 — `POST /{id}/open-review/reject`

```json
{ "reasonCode": "AD_EFFECT_ASSERTION",
  "detail": "“여름철 건조함이 사라집니다” 문장이 효과를 단정하는 표현입니다. …" }
```

| 검증 | 실패 |
| --- | --- |
| `canRejectOpen` | 409 `GROUP_BUY_OPEN_REVIEW_NOT_PENDING` |
| `reasonCode` 7종 | 400 |
| **`detail` 필수** · 1,000자 — **`ETC`가 아니어도** | 400 `GROUP_BUY_REJECT_DETAIL_REQUIRED` |

- `review_status = REJECTED` · `reject_reason_code` · `reject_reason_detail` · `reviewed_at/by` 덮어쓰기.
- 공구는 **`PREPARING` 그대로**(§29-3 "반려 — 준비중에서 멈춤").
- 이력 `OPEN_REJECTED` · detail = 사유 **라벨**(스튜디오 화이트리스트가 라벨까지 내린다 — 31 · 6-2). 설명 원문은 이력에 넣지 않는다 — 이력 detail 500자에 들어갈 글이 아니고, 게시물 행에 있다.
- 통지 — 인플루언서 · 브랜드(게이트가 멈췄다는 사실).

**`detail`이 사유와 무관하게 필수인 이유** — §32-2 "고칠 문장을 지목하지 않으면 **재등록이 반복된다**". 28 설계 6-2(계약 반려 `reasonDetail` 무조건 필수)와 같다. 사유 코드만으로는 "어느 문장"을 말할 수 없다.

**반려 횟수를 세지 않는다** — §33-1 #3(재등록 횟수 제한) 미정.

### 5-3. 게시물 숨김 — `POST /{id}/post/hide`

```json
{ "reasonCode": "AD_EFFECT_ASSERTION",
  "detail": "“모발 손상이 회복됩니다” 문장이 효과를 단정하는 표현입니다. …",
  "observedRevisionNo": 3 }
```

| 순서 | 내용 |
| --- | --- |
| 1 | `group_buy` → `group_buy_post` 잠금 |
| 2 | `canHidePost` — 아니면 409 `GROUP_BUY_POST_NOT_HIDEABLE` / `GROUP_BUY_POST_ALREADY_HIDDEN` |
| 3 | `detail` **필수**(§29-8 규칙 ②) · 1,000자 |
| 4 | `hidden_at/by` · `hidden_reason_*` · **`hidden_revision_no = 현재 최신 판본`** · `unhidden_*` 비움 |
| 5 | `GroupBuyPostExposure.sync` → `post.status = DRAFT` |
| 6 | 이력 `POST_HIDDEN`(ref_id = post_id) · 통지 — 인플루언서(사유·설명) · 브랜드 |

- **`observedRevisionNo`는 검증하지 않고 기록 대조에만 쓴다.** 운영자가 판본 3을 보고 숨김을 눌렀는데 그사이 판본 4가 생겼으면, 숨김은 **여전히 유효**하다 — 문제 문장이 4에서 지워졌어도 3이 소비자에게 노출됐던 사실은 남는다. `hidden_revision_no`는 **서버가 잠금 안에서 읽은 최신 판본**을 박고, 두 값이 다르면 응답에 `revisionAdvanced: true`를 실어 FE가 "숨기는 사이 게시물이 수정됐습니다 — 최신 본문을 확인하세요"를 띄운다.
- **공구 상태는 바뀌지 않는다**(§29-8 규칙 ① · §32-5 "「공구는 멈추지 않는다」를 고지"). 상품 resync 없음.
- **`READY`에서도 받는다** — §29-8 규칙 ④는 "종결 상태 비활성 · 승인대기 중 버튼 없음" 둘만 막았다. 승인 후 시작 전에 문제를 발견하면 **숨긴 채로 열리게** 할 수 있어야 한다 — 오픈 tick의 투영(31 · 2-9)이 `HIDDEN`을 `DRAFT`로 유지한다.
- **숨김 중에는 양측 요청이 막힌다**(30 · 4-5 · 31 · 4-8). 이 API가 하는 일은 아니지만 운영자가 알아야 하는 결과다 — M5 경고문에 없다(13-1 #16).

### 5-4. 숨김 해제 — `POST /{id}/post/unhide`

```json
{ "expectedRevisionNo": 4 }
```

| 순서 | 내용 |
| --- | --- |
| 1 | `group_buy` → `group_buy_post` 잠금 |
| 2 | `canUnhidePost` — 아니면 409 `GROUP_BUY_POST_NOT_HIDDEN` |
| 3 | **최신 판본 ≠ `expectedRevisionNo`** → 409 `GROUP_BUY_POST_CHANGED_SINCE_VIEW` |
| 4 | `unhidden_at/by` · `unhidden_revision_no` |
| 5 | `GroupBuyPostExposure.sync` → 판매 중이면 `PUBLISHED` |
| 6 | 이력 `POST_UNHIDDEN` · 통지 — 인플루언서 · 브랜드 |

**해제만 판본을 검증하는 이유** — §29-8 해제 경로는 "인플루언서가 고치면 운영자가 **바뀐 본문을 읽고** 해제"다. 운영자가 판본 4(고친 글)를 읽는 사이 인플루언서가 판본 5(원래 문구)로 되돌리면, 검증 없는 해제는 **판본 5를 연다** — §29-8 규칙 ③ "자동 복귀하면 같은 문구로 되돌려도 다시 열린다"가 막으려던 일이 수동 해제에서 재현된다. 잠금 + 판본 대조가 **읽은 글 = 여는 글**을 보장한다.

- **"고쳤는가"를 서버가 판정하지 않는다** — 해제 조건에 `latestRevisionNo > hidden_revision_no`를 걸지 않는다. 숨김이 잘못이었다고 운영자가 판단할 수 있어야 한다. 판단은 사람이 하고 서버는 **무엇을 보고 판단했는지**만 박는다.
- **해제 사유를 받지 않는다** — 시안에 해제 모달이 없고 §29-8도 요구하지 않는다. 판본 번호가 사실상의 근거 기록이다.

### 5-5. 판본 목록 — `GET /{id}/post/revisions`

```json
[ { "revisionNo": 1, "kind": "SUBMITTED", "title": "…", "content": "…", "createdAt": "2026-08-02T10:12" },
  { "revisionNo": 2, "kind": "EDITED",    "title": "…", "content": "…", "createdAt": "2026-08-05T16:02" },
  { "revisionNo": 3, "kind": "EDITED",    "title": "…", "content": "…", "createdAt": "2026-08-09T14:22" } ]
```

- 31 설계 2-6이 "스튜디오 API로 열람하지 않는다 · **어드민 설계가 읽는다**"로 넘긴 자리다.
- **차분(diff)을 서버가 계산하지 않는다.** §33-1 #13 "승인 후 대규모 수정 포착 — 수정 이력 열람 · **차분 비교**"가 미정이다. 원문 판본만 내리고 대조는 FE가 두 판본을 나란히 놓는다 — 차분 알고리즘(문장·단어·글자 단위)은 기획이 정할 표시 규칙이다.
- 판본마다 **표지**를 붙여 내린다 — `approved`(승인된 판) · `hiddenAt`(숨김 기준 판) · `noticedAt`(통지 기준 판). B2c 「수정 전후 본문 대조」가 "통지 판 vs 최신 판"을 바로 고를 수 있게.
- 게시물 수가 공구당 1개이고 판본은 수십 개 수준이라 **페이징하지 않는다.**

## 6. 판정 API — 직권 중단 3단계 + 긴급

### 6-1. 날짜 규칙 — `BusinessCalendar` 하나 · 시안은 두 셈법을 섞었다

```
addBusinessDays(D, n) = D 다음 날부터 세어 n번째 영업일    ← 31 설계 4-4 · 기준일 불산입
```

| 값 | 계산 |
| --- | --- |
| 소명 기한 하한 | `addBusinessDays(통지일, 3)` 23:59:59 — 제17조④ |
| 집행 예정 하한 | ① 날짜가 `addBusinessDays(통지일, 3)` 이상(제17조② "최소 3영업일 전 통지") **그리고** ② **소명 기한보다 엄격히 뒤**(+ `min-gap-after-appeal`) — 소명 기한 하한이 ①의 23:59:59이므로 실제로는 ②가 묶는다 |
| 집행 예정 상한 | **`end_at`보다 앞** — 30 설계 7-2 #3이 넘긴 검증 |

> ⚠️ **시안이 같은 파일 안에서 영업일을 두 가지로 셌다.**
>
> | 화면 | 기준일 | 시안 값 | 기준일 불산입(31 설계) |
> | --- | --- | --- | --- |
> | B1 오픈 승인 SLA | 08.16(**일**) 09:41 | 08.19(수) | 17·18·19 → **08.19** ✅ |
> | M6 소명 기한 | 08.08(**토**) 10:30 | 08.13(목) | 10·11·12 → **08.12** ❌ |
>
> M6은 "토요일에 보낸 통지의 **수신일은 월요일**"로 보고 월요일을 불산입한 셈이다(11·12·13). 법적으로도 가능한 해석이지만 **한 달력에 두 규칙이 있으면 안 된다** — 오픈 승인 기한과 소명 기한이 서로 다른 날을 가리킨다. **31 설계에서 확정한 기준일 불산입으로 통일**하고, "비영업일 발송 통지의 수신일" 해석은 법무 확인으로 올린다(13-2 #8). 해석이 바뀌면 `BusinessCalendar`의 기준일 보정 **한 줄**만 바뀐다.

**M6 날짜 선택지는 서버가 내린다** — `GET /{id}/admin-suspension/notice-options`

```json
{ "today": "2026-08-08",
  "appealDeadline": { "default": "2026-08-12T23:59:59", "min": "2026-08-12T23:59:59" },
  "executionDates": [
    { "date": "2026-08-11", "selectable": false }, { "date": "2026-08-12", "selectable": false },
    { "date": "2026-08-13", "selectable": true },  { "date": "2026-08-14", "selectable": true },
    { "date": "2026-08-17", "selectable": true },  { "date": "2026-08-18", "selectable": true } ],
  "latestExecutionBefore": "2026-08-18T23:59",
  "available": true, "unavailableReason": null }
```

- §32-3 "3영업일 이전 날짜를 **회색 취소선으로 잠근다**(에러 문구 없이 고를 수 없게)" · "**주말이 영업일에서 빠지는 것이 칩에 그대로 보인다**". 칩 목록(주말 제외 · 잠금 여부)을 FE가 달력 규칙으로 다시 계산하면 공휴일 목록(31 · 4-4 설정값)을 FE도 가져야 한다. **서버가 칩을 만든다.**
- `executionDates`는 **영업일만** 나열한다(시안 칩에 15·16일이 없다). 목록 끝은 `end_at` 전날까지.
- `available = false`면 M6을 열 수 없다 — 4-10 `NO_WINDOW_BEFORE_END`.
- **「직접 입력」도 서버가 같은 규칙으로 검증한다**(6-2) — 칩은 편의이고 규칙은 POST가 집행한다.

### 6-2. 사전 통지 — `POST /{id}/admin-suspension/notice` (M6)

```json
{ "clause": "ART17_1_LAW",
  "executeScheduledAt": "2026-08-14T10:00",
  "appealDeadlineAt": "2026-08-13T23:59:59",
  "noticeBody": "게시물 본문에 “모발 손상이 회복됩니다”, … 기한 내 소명자료를 제출하면 검토 후 철회할 수 있습니다." }
```

| 검증 | 실패 |
| --- | --- |
| `IN_PROGRESS` | 409 `GROUP_BUY_STATUS_CONFLICT` |
| **`PENDING` 중단·조기 마감 요청 없음** | 409 `GROUP_BUY_REQUEST_DECIDE_FIRST` |
| `clause` 4호 | 400 |
| `noticeBody` 필수 · 2,000자 | 400 |
| `appealDeadlineAt >= addBusinessDays(오늘, 3) 23:59:59` | 400 `GROUP_BUY_SUSPENSION_SCHEDULE_INVALID` |
| `executeScheduledAt`의 날짜 `>= addBusinessDays(오늘, 3)` ∧ `executeScheduledAt > appealDeadlineAt + gap` | 〃 |
| `executeScheduledAt < end_at` | 〃 |

**한 트랜잭션**

| 순서 | 내용 |
| --- | --- |
| 1 | `group_buy` 잠금 → 조건부 UPDATE `IN_PROGRESS → SUSPENSION_SCHEDULED` |
| 2 | `group_buy_admin_suspension` INSERT `kind = NOTICE` · `status = NOTICED` · 1-2 스냅샷(판매 · 판본) — **생성 컬럼 UNIQUE 위반 = 409 `GROUP_BUY_SUSPENSION_ALREADY_NOTICED`** |
| 3 | 이력 `SUSPENSION_NOTICED` · detail "{호 라벨} · 집행 예정 MM.DD HH:mm · 소명 기한 MM.DD" |
| 4 | 통지 — 브랜드(본문 · 기한) · 인플루언서(31 · B13) |

- **게시물 투영·상품 resync 없음** — 중단 예정도 판매 중이다(31 · 2-9 "예고만으로 게시물이 내려가지 않는다"). 30 설계 1-11 동기화에서 `SUSPENSION_SCHEDULED`는 `IN_PROGRESS`로 매핑된다.
- **검토 중 요청이 있으면 통지를 막는 이유** — 통지 후 공구는 `SUSPENSION_SCHEDULED`인데 요청 승인은 `IN_PROGRESS`/`READY`에서만 출발한다(30 · 3-1). 막지 않으면 요청은 **판정 불가 상태로 큐에 박혀** `end_at`의 `LAPSED`만 기다린다. 게다가 중단 요청이 걸려 있다면 운영자가 원하는 결과(중단)는 **요청 승인이 즉시** 준다 — 3영업일 통지보다 빠르다. "요청을 먼저 판정하라"가 맞다. 이 조건이 2-3의 **큐 배타성**을 보장한다.
- **숨김 중에도 받는다** — 시안 B2b 레일에 `[직권 중단 사전통지]`가 있다. §32-5 "직권 중단은 그 아래 남지만 문구 문제에 판매를 끊는 것은 과잉이다" — 막지는 않되 순서를 FE가 정한다.
- **대기 중인 연장은 그대로 둔다** — 스튜디오는 중단 예정에서 응답할 수 없다(31 · 5-1). 철회되면 다시 응답 가능, 집행되면 `GroupBuyTerminator`가 `EXPIRED`로 닫는다.
- **실행 버튼 인디고 · "판매가 멈추지 않는다"는 FE 문구지만, 사실은 서버가 상태로 보장한다** — 통지는 `status`를 `SUSPENSION_SCHEDULED`로 바꿀 뿐 구매 판정(30 · 1-11 `IN_PROGRESS` 매핑)을 건드리지 않는다.

> ⚠️ **시안 M6의 소명 기한 선택지 「08.14 (금) 23:59」는 같은 모달의 집행 예정 기본값 「08.14 10:00」보다 늦다.** 소명 기한이 집행 뒤면 운영자는 소명을 읽기 전에 집행할 수 있고, 브랜드는 **이미 중단된 공구에 소명**하게 된다. 서버는 `executeScheduledAt > appealDeadlineAt`을 강제한다(13-1 #7). `min-gap-after-appeal`(검토 시간)은 `[근거 대기 ⑨]`라 0으로 둔다.

> ⚠️ **사유 3호(게시물 무단 변경)는 브랜드에 물을 수 없다**(C-2). 서버는 3호를 막지 않는다 — 3호에는 「공급불능 · 중대 의무 불이행」도 같이 묶여 있어 호 단위로 막으면 정당한 사유까지 막힌다. 대신 **3호 선택 시 응답에 `clauseCaution: "C2_POST_ALTERATION"`** 을 실어 FE가 "게시물 변경을 이유로 삼는다면 브랜드가 소명할 수 없는 사유입니다"를 띄우게 한다. C-2 개정 시 이 필드를 걷는다.

### 6-3. 집행 — `POST /{id}/admin-suspension/execute`

```json
{ "executionNote": "소명의 삭제 주장을 확인했으나 08.14 현재 본문에 동일 취지 표현(“탈모 개선”)이 남아 있어 집행합니다." }
```

| 검증 | 실패 |
| --- | --- |
| `NOTICED` 통지 존재 | 409 `GROUP_BUY_SUSPENSION_NOT_NOTICED` |
| `now > appeal_deadline_at` | 409 `GROUP_BUY_SUSPENSION_EXECUTION_NOT_DUE` |
| **`now >= execute_scheduled_at`** | 〃 |
| `executionNote` 필수 · 1,000자 | 400 `GROUP_BUY_DECISION_REASON_REQUIRED` |

**`GroupBuyTerminator.terminate(SUSPENDED, source = ADMIN_NOTICE)`** → 통지 행 `EXECUTED` · `executed_at/by` · `execution_note` · `closing_admin_suspension_id` · 이력 `SUSPENDED_BY_ADMIN` · 양측 통지(집행 사유 포함).

**① 집행 사유를 필수로 받는다 — 시안에 집행 모달이 없다.** B2c(소명 제출됨)의 힌트가 "소명이 타당하면 철회하고, 그대로면 집행합니다 — **어느 쪽이든 사유가 브랜드에 전달됩니다**"라고 말한다. 철회는 M7이 사유를 받는데 집행은 받을 자리가 없다. 제17조④ "소명 … 최종 판정"에서 **소명을 낸 브랜드는 그 소명이 왜 받아들여지지 않았는지**를 들어야 한다 — 받지 않으면 소명 절차가 형식이 된다. 모달 추가(M8)를 요청한다(13-1 #9).

**② 시각 조건이 시안보다 하나 많다 — `execute_scheduled_at`.** §32-3 · 시안 B2c는 "`[중단 집행]`은 **소명 기한** 전까지 비활성 · 기한이 차면 저절로 열린다"라고만 했다. 그러나 제17조②는 통지에 **집행 일시**를 적게 했고, 운영자가 그 일시보다 **먼저** 집행하면 통지 내용과 다른 시각에 판매를 끊은 것이 된다. 시안 예시에서 소명 기한(08.13 23:59)과 집행 예정(08.14 10:00) 사이 10시간이 그 구간이다. **두 조건을 모두 건다** — 6-2가 `집행 예정 > 소명 기한`을 강제하므로 실제로 버튼을 여는 것은 집행 예정 시각이다. B2c 힌트 문구를 "집행 예정 일시가 되면 열립니다"로 정정 요청(13-1 #8).

**③ 자동 집행하지 않는다** — 30 설계 0-5 "기한 도달 = 버튼 활성이지 자동 집행이 아니다". 집행 예정 시각이 지나도 운영자가 누르지 않으면 `SUSPENSION_SCHEDULED`가 유지되고, 조치 큐 `APPEAL_REVIEW`에 남는다(2-3). `end_at`이 먼저 오면 스케줄러가 `ENDED` + 통지 `LAPSED`(30 · 3-3).

### 6-4. 철회 — `POST /{id}/admin-suspension/withdraw` (M7)

```json
{ "reasonCode": "RECTIFIED",
  "detail": "지적한 두 문장이 삭제된 것을 현재 본문에서 확인했습니다. 같은 표현이 다시 등록되면 사전 통지 없이 긴급 중단될 수 있습니다." }
```

| 검증 | 실패 |
| --- | --- |
| `NOTICED` 통지 존재 | 409 `GROUP_BUY_SUSPENSION_NOT_NOTICED` |
| `reasonCode` 4종 · `detail` 필수 1,000자 | 400 |

- 통지 행 `NOTICED → WITHDRAWN` · `withdrawn_at/by` · `withdraw_reason_code` · `withdraw_detail`.
- 공구 조건부 UPDATE `SUSPENSION_SCHEDULED → IN_PROGRESS`. **`end_at` 불변** — "공구는 원래 일정대로"(M7).
- 이력 `SUSPENSION_WITHDRAWN` · detail = 철회 사유 라벨 · 양측 통지.
- **소명 기한 전에도 철회할 수 있다** — 소명 없이도 운영자가 스스로 시정을 확인했거나 오판을 깨달았을 수 있다(시안 ⓕ "브랜드가 스스로 시정했을 때 — 운영자 판단"). 시안 M7은 소명 제출 후만 그렸지만 막을 규칙상 근거가 없다.
- **재통지** — "같은 사유로 다시 통지하려면 절차를 처음부터"(M7). 생성 컬럼 UNIQUE는 `NOTICED`만 제한하므로 새 `NOTICE` 행이 생긴다. **3영업일이 다시 흐른다** — 서버는 이전 통지를 기준으로 기한을 단축하지 않는다.

### 6-5. 긴급 직권 중단 — `POST /{id}/admin-suspension/emergency` (M4)

```json
{ "emergencyReason": "CONSUMER_HARM",
  "body": "게시물에 의료적 효능 표현이 반복 확인되어 판매를 중단합니다. 접수된 주문은 정상 배송하되 신규 판매는 차단됩니다." }
```

| 검증 | 실패 |
| --- | --- |
| `IN_PROGRESS` · `SUSPENSION_SCHEDULED` | 409 `GROUP_BUY_STATUS_CONFLICT` |
| `emergencyReason` 3종 — **`ETC` 없음** | 400 |
| `body` 필수 · 2,000자 | 400 |

**한 트랜잭션**

| 순서 | 내용 |
| --- | --- |
| 1 | `group_buy_admin_suspension` INSERT `kind = EMERGENCY` · **`status = EXECUTED`로 바로** · `emergency_reason` · `notice_body = body` · 스냅샷 · `executed_at = noticed_at = now` |
| 2 | 진행 중 `NOTICED` 통지가 있으면 → **`SUPERSEDED`** |
| 3 | `GroupBuyTerminator.terminate(SUSPENDED, source = ADMIN_EMERGENCY)` — 검토 중 요청 `LAPSED`까지 |
| 4 | 이력 `SUSPENDED_EMERGENCY` · detail "**긴급** · {사유 라벨}" · **사후 통지** 양측 |

- **`SUPERSEDED`를 `LAPSED`와 나누는 이유** — `LAPSED`는 "공구 기간이 먼저 끝나 판정할 대상이 사라졌다"(30 · 1-7)이고, `SUPERSEDED`는 "운영자가 더 강한 조치로 대체했다"이다. 제재 이력(1-2 철회 코드와 같은 이유)에서 둘의 뜻이 다르다.
- **§32-3 "「긴급」을 제목·버튼·이력 문구 모두에"** — 이력 detail의 "긴급"은 서버가 박는다. 30 설계가 이벤트 타입을 `SUSPENDED_EMERGENCY`로 나눠 두어 통계에서도 긴급이 섞이지 않는다.
- **`READY`에서는 받지 않는다** — 시안 "진행중·중단 예정 어디서든". 시작 전 공구는 판매가 없어 "피해 급증"이 성립하지 않고, 필요하면 브랜드 중단 요청(30 · 4-6 C4)이 `READY`를 받는다.
- **판정 권한 체크 지점을 명시한다**(9-2).

> ⚠️ **M4 "집행 후 지체 없이 사후 통지되며 **브랜드는 소명을 제출할 수 있습니다**"** — 긴급 집행 후에는 공구가 이미 `SUSPENDED`이고 **재개 불가**(제16조③ · 제17조⑤)다. 소명이 받아들여져도 되돌릴 경로가 없다. 소명 API는 `NOTICED` 통지만 받으므로(30 · 4-6) 긴급 건에는 소명 버튼이 뜨지 않는다. 사후 이의는 **이슈 스레드**가 받는다(canOpenIssue — 4-10). 문구 정정 요청(13-1 #10).

## 7. 판정 API — 중단 · 조기 마감 요청

### 7-1. 승인 — `POST /{id}/change-requests/{requestId}/approve`

```json
{ "decisionReason": "생산 로트 하자가 확인되어 신규 판매를 중단합니다. 접수된 159건은 브랜드가 회수·환불로 처리하고, 판매 리워드는 접수분 기준으로 정산합니다." }
```

**`requestId`를 경로에 받는다** — 운영자는 **특정 요청**을 읽고 판정한다. `/{id}/active-request/approve`처럼 "지금 걸린 요청"을 판정하게 하면, 운영자가 요청 A를 읽는 사이 A가 `LAPSED`되고 요청 B가 들어온 경우 **읽지 않은 B를 승인**한다(드물지만 공구당 PENDING 1건 제약이 시간축에서 교체를 막지는 않는다).

| 검증 | 실패 |
| --- | --- |
| 요청이 이 공구 소속 ∧ `PENDING` | 409 `GROUP_BUY_CHANGE_REQUEST_NOT_PENDING` |
| `decisionReason` 필수 · 1,000자 | 400 `GROUP_BUY_DECISION_REASON_REQUIRED` |

| 요청 | 공구 전이 | 종결 |
| --- | --- | --- |
| `SUSPEND` | `READY` · `IN_PROGRESS` → `SUSPENDED` | `Terminator(SUSPENDED, source = REQUEST)` · 이력 `SUSPENDED` |
| `EARLY_CLOSE` | `IN_PROGRESS` → `ENDED` | `Terminator(ENDED, EARLY_CLOSED)` · `ended_at = now` · 이력 `EARLY_CLOSED` |

- 요청 행 `APPROVED` · `decided_at/by` · `decision_reason` · 공구 `closing_change_request_id`.
- **`decisionReason`은 양측에 간다**(§32-4 M2 "요청자에게는 승인 통보, **상대에게는 처음 듣는 결론**"). 조기 마감도 같다 — 인플루언서의 남은 판매일이 사라진다.
- **조기 마감 승인에도 사유를 필수로 받는다** — 시안 B4에 조기 마감 승인 모달이 없다. 결과가 정상 종결이어도 인플루언서에게는 **처음 듣는 종료**다. M3와 같은 형태의 모달을 요청한다(13-1 #18).
- **`READY`에서 중단 승인** — 요청 시점 `READY`였고 지금도 `READY`면 판매가 없으므로 M2 경고문 5개 중 "접수분 배송 의무"가 공허하다. `statusAtRequest`와 현재 `status`로 FE가 경고문을 고른다(30 · 4-6 C4).

**경합** — 30 설계 3-4의 "오픈 vs 중단 요청 승인(준비완료)" · "조기 마감 승인 vs 스케줄러 종료"를 조건부 UPDATE가 막는다. 스케줄러가 이기면 요청은 `LAPSED`이고 승인 API는 409 `CHANGE_REQUEST_NOT_PENDING`을 받는다. **오픈이 이기면**(10:00:00 경합) 요청은 여전히 `PENDING`이고 공구는 `IN_PROGRESS`다 — 승인은 **`IN_PROGRESS` 출발로 다시 시도하면 된다.** 전이 FROM 집합이 `{READY, IN_PROGRESS}`라 첫 시도에서 이미 통과한다(잠금 후 현재 상태를 읽으므로).

### 7-2. 반려 — `POST /{id}/change-requests/{requestId}/reject`

```json
{ "decisionReason": "제출된 사진으로는 로트 전체의 하자로 보기 어렵습니다. 개별 교환으로 대응하고, 동일 사례가 5건 이상 접수되면 다시 요청해 주세요." }
```

- 요청 행 `REJECTED` · 공구 **불변**(§32-4 M3 "요청만 기각되고 공구는 일정대로").
- 이력 `SUSPENSION_REQUEST_REJECTED` / `EARLY_CLOSE_REQUEST_REJECTED`.
- 통지 — **요청자 + 상대 모두**. 상대는 요청 사실을 이미 통지받았다(30 · 5-4 · 스튜디오 B10 "브랜드 중단 요청 검토 중"). 시작을 알렸으면 끝도 알려야 한다 — 알리지 않으면 상대는 요청이 아직 살아 있다고 믿고 판매를 소극적으로 운영한다.
- **재요청 조건을 서버가 구조화하지 않는다** — §32-4 "재요청 조건을 함께 적도록 **유도**". 조건은 `decisionReason` 문장 안에 있다. 조건을 필드로 받으면(예: "동일 사례 N건 이상") 서버가 그 조건을 **판정해야 하는 것처럼** 보이고, 판정할 데이터(하자 분류 · 4-5)가 없다.
- 반려 후 재요청은 막지 않는다(30 · 4-6) — §33-1 #4 남용 방지 미정.

## 8. 종결 · 정산 · 이슈

### 8-1. `GroupBuyTerminator` — 종결 경로 5개의 공용 부수 효과

```java
// domain/groupbuy/service/GroupBuyTerminator.java
public void terminate(GroupBuy gb, Termination t, Actor actor, LocalDateTime now) {
    int changed = groupBuys.terminate(gb.getId(), t.fromStatuses(), t.toStatus(),
            t.endedAt(), t.closeType(), t.closingRequestId(), t.closingAdminSuspensionId());
    if (changed == 0) throw new BusinessException(GROUP_BUY_STATUS_CONFLICT);
    extensions.expirePending(gb.getId(), now);                               // 대기 연장 → EXPIRED (SYSTEM)
    changeRequests.lapsePendingExcept(gb.getId(), t.closingRequestId(), now); // 검토 중 요청 → LAPSED
    suspensions.closeNoticedExcept(gb.getId(), t.closingAdminSuspensionId(), t.noticeFate(), now);
    if (t.toStatus() == ENDED) gb.fixFulfillmentDueAt(t.endedAt().plus(fulfillmentDue)); // 30 · 1-9
    postExposure.sync(gb, now);                                               // 31 · 2-9 → DRAFT
    productSync.resync(contractProductIds(gb));                               // 30 · 1-11
    history.record(gb, t.historyEvent(), actor, t.historyDetail(), now);
    notifier.terminated(gb, t, actor);
}
```

| 경로 | `toStatus` | `endedAt` | `closeType` | 통지 행 처리(`noticeFate`) |
| --- | --- | --- | --- | --- |
| 스케줄러 종료 | `ENDED` | **`end_at`**(30 · 3-3) | `COMPLETED` | `LAPSED` |
| 조기 마감 승인 | `ENDED` | `now` | `EARLY_CLOSED` | 없음(통지 중엔 요청 불가) |
| 중단 요청 승인 | `SUSPENDED` | `now` | `SUSPENDED` | 없음 |
| 직권 중단 집행 | `SUSPENDED` | `now` | `SUSPENDED` | 자기 자신 `EXECUTED` |
| 긴급 | `SUSPENDED` | `now` | `SUSPENDED` | 다른 `NOTICED` → `SUPERSEDED` |

- **30 설계 3-3의 스케줄러 `end`를 이 메서드 호출로 바꾼다** — 30 설계 P3가 먼저 구현되면 리팩터링, 아니면 처음부터 이 메서드로. 어느 쪽이든 **종결 부수 효과를 구현한 곳은 이 메서드 하나**여야 한다.
- **테스트 1순위** — 다섯 경로 각각에 대해 "상품 `groupBuyStatus` 재계산 · `post.status = DRAFT` · 대기 연장 `EXPIRED` · 검토 요청 `LAPSED` · 조치 큐 0" 다섯 단언. 경로 × 단언 25칸을 매트릭스로 고정한다.
- **조기 마감 = `ENDED`라서 이행 확인 기한이 생긴다** — 정상 종료와 같이 양측 이행 확인 → 정산. `SUSPENDED`는 이행 확인이 없다(30 · 4-5 `canCheckFulfillment = ENDED`).

### 8-2. 정산 확인 — `POST /{id}/settlement/confirm` 🚧 착수 게이트

§32-0 ⑥ "정산 확인 — B5 · B5a · B5b". 운영자가 정산대기 → **운영자 확인**으로 넘기는 버튼이다.

| 항목 | 규칙 |
| --- | --- |
| 조건 | `canConfirmSettlement` — `ENDED` ∧ `blockers = []` ∧ 포트 `stage = WAITING` |
| 처리 | **`GroupBuySettlementGateway.confirm(groupBuyId, operatorId)` 위임** — 공구 테이블에 쓰지 않는다 |
| 공구 상태 | **불변** — `SETTLED`는 이체 완료 통보(30 · 5-2 `markSettled`)가 만든다 |
| 이력 | 공구 이력에 쓰지 않는다 — 정산 모듈의 이력이다 |

**정산 모듈이 없으면 이 API를 배포하지 않는다.** §33-4 #1 "`[보류-정산구조]` 자금 흐름 A/B 미확정 — **정산 화면 3종 착수 게이트**". 버튼 판정(`canConfirmSettlement`)은 포트가 비면 `false`이므로 FE는 항상 비활성으로 그린다 — 거짓으로 열리지 않는다.

**공구에 `settlement_confirmed_at`을 두지 않는 이유** — 30 설계 5-2 "정산 상태머신은 공구에 두지 않는다". 운영자 확인을 공구에 두면 **정산 모듈과 공구가 같은 사실을 각자 가진다** — 정산 관리에서 확인을 취소(이중 승인 반려 · §33-1 #12)하면 공구 쪽 값이 거짓이 된다.

**이중 승인(§33-1 #12)** — 정산 모듈의 판단이다. 이 API는 포트에 위임할 뿐이라 이중 승인이 도입돼도 **이 설계는 바뀌지 않는다** — 포트가 `stage = CONFIRMED` 대신 `PENDING_SECOND_APPROVAL` 같은 값을 돌려주면 FE가 스테퍼에 반영한다.

### 8-3. 이슈 스레드 개설 — `POST /{id}/issues`

```json
{ "issueType": "SETTLEMENT_AMOUNT", "content": "정산 예정 금액에 대해 양측 이견이 있어 스레드를 엽니다. …" }
```

- 30 설계 4-6의 이슈 개설 서비스 메서드를 **`opener_type = ADMIN`** 으로 호출한다 — 스튜디오 이행 확인(31 · 5-4)과 같이 **서비스를 재구현하지 않는다.** 열린 이슈 1건 제약(생성 컬럼 UNIQUE) · 스레드 포트 동일 트랜잭션도 그대로다.
- **허용 상태가 파트너보다 넓다** — `ENDED` · `SETTLED` · `SUSPENDED`. §32-6 "B5b 이슈 버튼 — 남긴다 · 이행 확인이 끝난 뒤에도 열 수 있다". `SUSPENDED`는 긴급 건의 사후 이의 창구다(6-5).
- **정산 보류를 걸지 않는다**(30 · 4-6) — 이슈는 "정산과 무관한 이견"이다(§29-10).
- **B5a의 「종결된 스레드 보기」는 이 API가 아니다** — 이행 확인 3자 스레드(`afterEnd.fulfillment.threadId`)로 가는 FE 딥링크다.

> 🚧 **스레드 포트 선행** — 30 설계 5-3 `message_thread.connection_id` UNIQUE 문제. 포트 없이 열지 않는다(30 · P7 · 31 · S5와 같은 조건).

### 8-4. 합의 통보 수신 — 연결·소통 → 공구

어드민 공구 화면은 합의를 **처리하지 않는다**(§32-6 "합의는 게시물·소통 모니터링 소관"). 공구가 받는 통보만 정의한다.

| 통보 | 호출 | 공구에서 |
| --- | --- | --- |
| 이행 3자 스레드 **양측 동의 종결** | `GroupBuyCommandService.recordFulfillmentAgreement(gbId, agreedAt, note)` | `fulfillment_agreed_at` · `resolution_note` · 이력 `FULFILLMENT_AGREED`(SYSTEM) |
| 정산 **보류 해제** | `GroupBuyCommandService.releaseFulfillmentHold(gbId, operatorId, releasedAt)` | `fulfillment_resolved_at` · 이력 `FULFILLMENT_RESOLVED`(ADMIN · 정산 관리) |

- **합의 없이 보류 해제가 오면 거부한다** — `fulfillment_agreed_at IS NULL`이면 409. 제20조⑤ "양측 모두 동의해야 종결·보류 해제" — 정산 관리가 합의 전에 보류를 풀 경로를 공구가 받아 주면 제20조⑤가 무너진다. **D-2(보류 출구 없음)의 답이 나올 때까지 이 가드를 둔다**(13-2 #10).
- **`resolution_note`는 당사자 합의 문장이다** — 제20조④ "회사의 중재 의견에 금액 조정은 포함되지 않는다". 필드 이름도 `decision`이 아니라 `resolution`이다. 누가 쓰는가(합의 내용을 요약해 넣는 주체)는 연결·소통 설계가 정한다.
- **두 통보는 멱등이다** — 같은 값으로 두 번 오면 무시한다(조건부 UPDATE `WHERE agreed_at IS NULL`).

## 9. 동시성 · 권한

### 9-1. 어드민은 **유일한 다중 사용자 서피스**다

28 설계 15-2 "어드민은 세 서피스 중 유일하게 다중 사용자". 공구에서는 운영자 둘 + 브랜드 + 인플루언서 + 스케줄러가 **같은 공구에 동시에 쓴다.**

**잠금 순서 — `group_buy` → `group_buy_post` → 사실 테이블**(31 · 2-7이 넘긴 규칙). 어드민의 모든 판정 API가 이 순서를 지킨다. 뒤집으면 스튜디오 게시물 쓰기와 교착이 난다.

| 경합 | 막는 것 | 결과 |
| --- | --- | --- |
| 운영자 A 승인 vs 운영자 B 반려 | `group_buy_post` 잠금 후 `PENDING` 재확인 | 늦은 쪽 409 `OPEN_REVIEW_NOT_PENDING` |
| 오픈 승인 vs 브랜드 물량 확인 | `group_buy` 잠금 후 게이트 판정(30 · 3-2) | 늦은 쪽이 `READY`를 만든다 |
| 숨김 vs 인플루언서 수정 | `group_buy_post` 잠금 | 수정이 먼저면 숨김은 새 판본을 박는다(`revisionAdvanced`) |
| **해제 vs 인플루언서 수정** | 잠금 + `expectedRevisionNo` 대조 | 수정이 먼저면 해제 409 — **읽은 글만 연다**(5-4) |
| 통지 vs 브랜드 중단 요청 | `group_buy` 잠금 · 통지는 `PENDING` 요청 부재 확인 · 요청은 `SUSPENSION_SCHEDULED` 차단(30 · 4-5) | 한쪽만 통과 |
| 집행 vs 철회(운영자 둘) | `NOTICED` 조건부 UPDATE | 한쪽 0행 → 409 `SUSPENSION_NOT_NOTICED` |
| 집행 vs 긴급 | 둘 다 `SUSPENSION_SCHEDULED`에서 출발 | 한쪽 409 `STATUS_CONFLICT` |
| 요청 승인 vs 스케줄러 종료 | 조건부 UPDATE(30 · 3-4) | 종료가 이기면 요청 `LAPSED` → 승인 409 |
| 소명 제출 vs 철회 | 소명은 `NOTICED` 조건부 UPDATE | 철회가 먼저면 소명 409 `APPEAL_NOT_OPEN` |

**`@Version`을 쓰지 않는다** — 28 설계는 서명 갱신에 낙관적 락을 썼다(편집 폼이 있어서). 공구 어드민에는 **값을 편집하는 폼이 없고** 전부 "상태 X에서 Y로" 판정이라 조건부 UPDATE + 행 잠금으로 충분하다.

### 9-2. 권한 분리 — **자리만 만든다**

§33-1 #11 "**판정 권한을 최고관리자로 한정할지** — 중단은 소비자 주문을 끊는 조치다" (대표 확정 대기). 28 설계 13-3과 같은 처리.

```java
// AdminGroupBuyAccess
public void requireSalesStoppingPermission(Long operatorId) {
    // 최고관리자 한정 정책 확정 시 이 지점에서 역할을 추가로 검사한다. (§33-1 #11)
    operatorName(operatorId);
}
```

| 호출하는 API | 이유 |
| --- | --- |
| 중단 요청 승인 · 직권 중단 집행 · 긴급 | **판매를 실제로 멈추는 3종** — 시안의 "꽉 찬 위험색" 기준과 같다(§32-3 "버튼 색의 판정 기준은 「실제로 판매가 멈추는가」") |

**버튼 색 기준과 권한 기준을 같은 선에 두는 이유** — 기획이 이미 "판매가 멈추는가"로 조치의 무게를 갈랐다(M6·M7·M3 인디고 / M4·M2 위험색). 권한이 확정될 때 그 선이 다른 곳에 그어질 가능성은 낮다. 조기 마감 승인은 인디고(정상 종결)라 넣지 않는다.

**운영자 식별** — `AdminContractAccess.operatorName`과 같은 로직(`Seller` · `RoleType.ADMIN` · 이름 없으면 「운영자」)이 필요하다. 계약 쪽 클래스를 공구가 참조하지 않도록 **`api/admin/common`에 `AdminOperatorResolver`로 추출**하고 계약도 이를 쓰게 한다 — 두 벌이 되면 한쪽만 최고관리자 검사가 붙는다.

- **필수 미입력은 FE 버튼 비활성**이다(시안 "필수 미입력 절대 규칙" · §32-3). `*_REQUIRED` · `SCHEDULE_INVALID`는 FE가 정상이면 **보이지 않는 에러**이고, 그래도 서버는 막는다(30 · 4-7).
- **`EXECUTION_NOT_DUE`도 보이지 않아야 한다** — 버튼이 비활성이고 "에러 문구를 띄우지 않는다"(§32-3). 운영자 PC 시계가 서버보다 빠른 경우에만 드러난다 — 그게 이 에러가 존재하는 이유다(0-6).
- **`CHANGED_SINCE_VIEW`만은 운영자에게 보이는 게 정상이다** — 경합의 정상 결과이고 문구가 다음 행동(다시 읽기)을 말한다.

### 11-4. 알림 — 어드민이 **보내는** 것 (`GroupBuyNotifier` 스텁)

30 설계 5-4 · 31 설계 8-3의 훅 목록에서 **발신자가 운영자인 것**을 채운다. 발송은 스텁(채널 미정).

| 이벤트 | 받는 쪽 | 내용 |
| --- | --- | --- |
| 오픈 승인 | 인플루언서 · 브랜드 | 준비완료가 됐으면 시작 일시 |
| 오픈 반려 | 인플루언서 · 브랜드 | 사유 · 설명(인플루언서만) |
| 숨김 · 해제 | 인플루언서 · 브랜드 | 숨김 사유 · 설명(인플루언서만) |
| 직권 중단 통지 | 브랜드 · 인플루언서 | 본문 · 집행 예정 · **소명 기한(브랜드만)** |
| 집행 · 긴급 | 양측 | 집행 사유 / 긴급 사유 · **사후 통지** |
| 철회 | 양측 | 철회 사유 · 설명 |
| 요청 승인 · 반려 | **요청자 + 상대** | `decisionReason` |

**어드민이 받는** 것(30 · 31 설계가 발신): 게시물 제출(오픈 승인 대기열) · 숨김 중 게시물 수정(31 · 2-5) · 중단·조기 마감 요청 · 소명 제출 · 미이행 제출 · **종료 +30일 미정산**(지연 감시). 수신 채널은 어드민 GNB 배지(`summary`)가 1차다 — 푸시 채널이 없는 동안에도 배지는 동작한다.

**지연 감시 알림은 스케줄러가 필요하다** — §29-11 "종료 +30일에 어드민 알림". 30 설계 3-3 `tick()`에 `watchSettlementDelay()`를 더한다: `ENDED ∧ ended_at + 30d <= now ∧ 미통지` → 알림 1회. **중복 발송 방지 플래그가 필요하다** → `group_buy.settlement_watch_notified_at` 컬럼을 1-1에 더할지, 알림 모듈의 발송 로그로 판정할지는 **알림 채널 확정 시**(13-2 #15). 그 전까지는 `summary.settlementWatch.overdueCount`가 유일한 감시 수단이다.
