## 0. 먼저 정한 12가지

### 0-1. 대상은 `Users` 중 `roleType = USER` 다 — 어드민 소비자 목록과 같은 모집단

어드민 소비자 목록(`AdminUserQueryRepository`)은 이미 `RoleType.USER` 만 센다. 정지 · 해제도 같은 모집단만 받는다 — 그 밖(`GUEST` · `CREATOR`)은 404 `USER_NOT_FOUND`. 인플루언서는 `CreatorStatus` 축으로 §53 이 정지한다.

`CREATOR` 의 `Users.status` 를 `SUSPENDED` 로 바꾸면 안 되는 이유가 코드에 있다 — `PublicShowrooms.visible()` 이 `users.status = NORMAL` 을 조건으로 걸어 **쇼룸이 통째로 사라진다**(53 설계서 「정지는 숨기지 않는다」와 정면충돌). 소비자 정지를 `USER` 에 한정하면 이 부작용이 생기지 않는다.

회원 상태 축은 `UserStatus { NORMAL · SUSPENDED · WITHDRAWN }` 그대로다. `DORMANT` 는 세팅하는 코드가 없다(개발계획 6-1) — 손대지 않는다.

### 0-2. 정지는 **행**이다 — `user_sanction` · `user_status_history` 는 전이 로그로 계속 쓴다

브랜드 `brand_sanction` · 인플루언서 `creator_sanction` 과 같은 골격 — 정지 1건 = 1행(해제까지) · **열린 정지 = `released_at IS NULL`** · 회원당 최대 1건(생성 컬럼 UNIQUE). `users.status = SUSPENDED` 는 이 행에서 **파생해 저장**한다(가드가 열 하나로 읽는다).

개발계획 2-6 의 「`user_status_history` 에 `reason_type` · `actor_id` · `appeal_inquiry_id` 를 더한다」안은 **이 설계로 대체한다**. 전이 로그는 「지금 열린 정지의 사유 · 처리자 · 소명 문의」를 답하려면 최신 행을 거꾸로 찾아야 하고, 앱이 쓰는 **안내 시트 확인 · 해제 토스트 확인** 시각을 둘 자리가 없다. 브랜드 · 인플루언서와 모양이 같아야 어드민 화면 3종이 같은 규칙으로 읽힌다.

`user_status_history` 는 지우지 않고 **정지 · 해제 때도 계속 쓴다** — 목록 정지 탭의 「최근 30일 신규 정지」(`countNewlySuspended`)가 이 표를 읽는다.

### 0-3. 차단 범위의 정본은 §51-1 이다 — 로그인은 막지 않는다 · 서버 가드 10지점

§25-4 는 「로그인 · 주문 차단 / 문의 작성 허용」이었고 §51-1(v0.44)은 「**로그인 허용 · 새로 벌이는 일만 차단** — 이미 결제한 주문의 청약철회 · 반품 권리는 정지로 제한할 수 없다」이다. 뒤의 것을 따른다(13절 #2).

「숨기지 않고 비활성 + 안내」는 앱의 일이고, 서버는 그 행위를 **409 `USER_SUSPENDED`** 로 거부한다(4절). 시안을 본 사람만이 아니라 API 를 직접 부르는 사람도 막혀야 정지가 성립한다. 가드는 `users.status` 만 본다 — 정지 행을 읽지 않는다(뜨거운 경로).

### 0-4. 사유는 §25-4 의 6종 · 앱에는 **정형 사유만** — 앱 노출 문구는 enum 의 별도 필드

`UserSuspensionReason` 6종(욕설·비방 · 반품 남용 · 부정 주문 의심 · 결제 도용 의심 · 신고 다수 접수 · 기타). 「기타」만 상세 사유 필수. 상세 사유는 **앱에 내리지 않는다**(§51-6).

C20 시안의 사유 예시는 「운영정책 위반」인데 6종에 없다. 소비자에게 「결제 도용 의심」을 그대로 보일지 포괄 문구로 덮을지는 기획 확인 사항이다(13절 #1). 그래서 enum 이 `label`(어드민) · `appLabel`(앱) 두 필드를 든다 — 지금은 §51-6 「정형 사유 그대로」대로 **같은 값**이고, 결정이 바뀌면 enum 한 곳이다.

### 0-5. 해제 사유는 소비자 전용 `UserReleaseReason` 3종 — 필수 · 상세 없음

§25-4 해제 3종 `UserReleaseReason { RESOLVED("소명 확인 완료") · MISTAKE("오처리 정정") · TERM_ENDED("제재 기간 종료") }`. 브랜드 · 인플루언서가 함께 쓰는 `SanctionReleaseReason` 에 값을 더하지 않는다 — 인플루언서 해제 모달 옵션(`reason-options`)이 바뀌고 문구도 §25-4 와 다르다(15절 #1 · 처음 안은 공유 enum 에 `TERM_ENDED` 추가였다).

- 소비자 해제 모달은 시안이 있다 — 사유 **필수**(브랜드처럼 비면 `RESOLVED` 로 채우지 않는다).
- **상세 사유란 없음**(§25-4) — `release_note` 열을 두지 않는다.
- 정지 기간이 없으므로 `TERM_ENDED` 는 운영자가 「충분히 지났다」고 판단해 고르는 라벨일 뿐이다 — 자동 해제 배치 없음(13절 #4).

### 0-6. 앱 상태는 **API 하나**로 — 화면별 플래그를 만들지 않는다

배너(1a) · 비활성 버튼(1b) · 유형 노출(1d) · 배지(1f)는 전부 「지금 정지인가」 하나로 갈린다. `GET /v1/user/account-status` 가 상태 · 정형 사유 · 정지 일시 · 1회 노출 두 가지를 내리고(3절), 상품 상세 · 피드 응답에 `canPurchase` 같은 필드를 흩뿌리지 않는다. 할 수 없는 것 / 할 수 있는 것 목록(1c)은 고정 문구라 FE 가 든다.

### 0-7. 「1회 노출」 두 가지는 **서버가 기록**한다 — 정지 행의 두 시각

§51-6 데이터 행 「첫 로그인 1회 자동 시트 노출 여부 · 해제 토스트 1회 노출 여부 `[신규제안]`」. 기기 저장소에 두면 재설치 · 기기 변경마다 다시 뜨고, 두 기기에서 각각 뜬다. 정지 행에 `notice_acked_at` · `release_notice_acked_at` 을 두고 앱이 보여준 뒤 확인 API 를 부른다.

「첫 로그인 직후」는 **정지 후 첫 앱 진입**으로 읽는다 — 토큰이 살아 있어 다시 로그인하지 않는 사용자(대부분)도 정지를 알아야 한다. 정지 행이 열린 채 `notice_acked_at IS NULL` 이면 다음 상태 조회에서 `noticePending = true`.

### 0-8. 「계정 이용 정지」 문의 유형은 `CsCategory` 에 넣지 않는다 — 문의에 `sanction_id` 를 단다

§51-4 ⚠️ 「(1) §17-2-1(FAQ 와 같은 5종 · enum 단일 소스 · 기타 미운영)을 깨는 조건부 6번째 유형」. `CsCategory` 는 FAQ 카테고리 · 1:1 유형 · 어드민 유형 탭이 `values()` 로 도는 단일 소스다 — 값을 더하면 FAQ 에 「계정 이용 정지」 칩이 생긴다.

반려 이의(`claim_id` · V176)와 같은 방식으로 간다. 소명 문의 = **`type = ACCOUNT` + `sanction_id`(열린 정지)** 인 1:1 문의다. 앱은 요청에 `sanctionAppeal: true` 를 실어 보내고, 서버가 유형 · 관련 주문 칸을 고정하며 정지 행을 붙인다(5절). 화면에 보이는 유형명은 응답의 `typeName = "계정 이용 정지"` 다. 집계상으로는 「계정」 유형에 들어가므로 FAQ 연계(「어떤 유형이 많은가 → 어떤 FAQ 를 보강할까」)가 깨지지 않는다.

이렇게 하면 해제 모달의 **「소명 문의 번호」**(§25-4)가 자동으로 연결된다 — 개발계획 6-4 「자동 vs 수동」은 **자동**으로 닫힌다.

### 0-9. 정지 중 탈퇴는 막지 않는다 — 열린 정지는 닫지 않고, 같은 계정으로 재가입하면 되살아난다

소비자 탈퇴는 셀프서비스다(§25-5) · 정지 중에도 개인정보 삭제 요구를 막을 근거가 없다. 그런데 지금 `SocialLoginService.loginOrSignup` 은 `WITHDRAWN` 회원이 같은 소셜 계정으로 들어오면 **즉시 `NORMAL` 로 복구**한다 — 그대로 두면 「탈퇴 → 재가입」 한 번으로 정지가 풀린다(§51-3 「정지를 피하려고 탈퇴하는 길이 없다」의 소비자판).

그래서 탈퇴는 정지 행을 **닫지 않고**, 복구 경로가 열린 정지를 보면 `SUSPENDED` 로 되돌린다(6절). 탈퇴 회원에는 운영자 조치가 없다(§25-5) — 정지 · 해제 모두 409.

### 0-10. 알림은 **실제로 보낸다** — 소비자는 푸시 인프라가 있다

브랜드 · 인플루언서 알림은 수신 경로가 없어 로그 스텁이다. 소비자는 다르다 — `PushSender`(FCM) · `DeviceTokenRepository.findUserTokens`(「본인 앞으로 가는 통지」 — 팔로우 게시물 수신 토글과 무관)가 이미 있다. `UserSanctionNotifier` 가 커밋 뒤 정지 · 해제 푸시를 보낸다(8절). 발송 실패는 조치를 되돌리지 않는다.

### 0-11. 메모 누적 · 처리 이력은 인플루언서 · 브랜드와 **같은 골격** — 기존 데이터는 백필한다

`user_admin_memo`(누적 · 300자 · 작성자 본인 24시간 · soft delete) · `user_admin_history`(이 모듈의 사건만 저장 · 남의 사건은 읽을 때 합친다). 브랜드와 다른 점 하나 — `USERS.ADMIN_MEMO` 는 **활성 API**(`PATCH /memo`)가 써 온 컬럼이라 기획 제외 보존 대상이 아니다. 값이 있는 회원은 **메모 1행으로 이관**하고(작성자 · 시각 미기록을 그대로 표기) 컬럼은 DROP 하지 않는다. 옛 `PATCH /status` 로 남은 정지 · 활성 전이도 이력으로 이관한다(10절).

### 0-12. 기존 `PATCH /{userId}/status` · `PATCH /{userId}/memo` 는 제거한다

개발계획 3절의 결정 그대로 — 「변경할 상태 셀렉트를 두지 않는다」(§25-4)가 API 에도 적용된다. 목적지가 하나인 조치는 `POST /suspend` · `POST /release` 로 나누고, 덮어쓰기 메모는 누적 메모 API 로 바꾼다. 활성 엔드포인트 제거이므로 어드민 FE 전환과 같은 배포에 묶는다(11절 #6).

## 2. 어드민 — 정지 · 해제

도메인 서비스 `domain.member.user.service.UserSanctionService` 가 한 트랜잭션에서 정지 행 · 회원 상태 · 전이 로그 · 처리 이력을 함께 바꾼다. 어드민 서비스 `AdminUserCommandService` 는 운영자 id(`UserPrincipal`) · 이름(`AdminOperatorResolver.operatorName`)을 확인해 넘기기만 한다(52 · 53 과 같은 분업 — 도메인이 api 의 운영자 해석기를 부르지 않는다).

### 2-1. 정지 `POST /v1/admin/users/{userId}/suspend`

입력 `{ reason: UserSuspensionReason, reasonDetail?: ≤500 }`.

1. `reason == null` → 400 `INVALID_INPUT_VALUE` · `OTHER ∧ detail 공백` → 400 `USER_SUSPEND_DETAIL_REQUIRED`.
2. 회원 행 잠금(`UserRepository.findForUpdate` 신규) — 없거나 `roleType ≠ USER` 면 404 `USER_NOT_FOUND`(0-1).
3. `WITHDRAWN` → 409 `USER_SANCTION_WITHDRAWN` · `SUSPENDED` 이거나 열린 정지 행이 있으면 409 `USER_ALREADY_SUSPENDED`.
4. `user_sanction` INSERT · `users.status = SUSPENDED` · `user_status_history`(NORMAL → SUSPENDED · `reason` = 사유 코드).
5. 이력 `SUSPENDED`(`detail` = 사유 라벨 + 상세 · `ref = sanction`).
6. 커밋 뒤 `UserSanctionNotifier.suspended(userId, reason.appLabel)`(8절).

응답은 **상태 카드**(2-3) — 상세 전체를 다시 부르지 않게.

### 2-2. 정지 해제 `POST /v1/admin/users/{userId}/release`

입력 `{ reason: UserReleaseReason }` — **필수**.

1. `reason == null` → 400 `USER_RELEASE_REASON_REQUIRED` · 3종 밖의 값 → 400 `INVALID_INPUT`(역직렬화 실패).
2. 회원 행 잠금 · `WITHDRAWN` → 409 `USER_SANCTION_WITHDRAWN` · `≠ SUSPENDED` → 409 `USER_NOT_SUSPENDED`.
3. 열린 정지 행이 있으면 `release(...)` — **없어도 상태는 되돌린다**(옛 `PATCH /status` 로 정지된 회원 · 52 구현 메모 #4 와 같은 이유 — 영원히 풀리지 않는 회원을 만들지 않는다).
4. `users.status = NORMAL` · `user_status_history`(SUSPENDED → NORMAL · `reason` = 해제 사유 코드).
5. 이력 `SUSPENSION_RELEASED`(`detail` = 해제 사유 라벨).
6. 커밋 뒤 `UserSanctionNotifier.released(userId)`.

해제는 **회원 상세에서만** 한다(§51-4) — 1:1 문의 답변 화면에 해제 버튼을 만들지 않는다. 해제 판단의 근거(소명 문의)는 상세의 상태 카드가 링크로 보여준다(2-3).

### 2-3. 상세 응답 — `GET /v1/admin/users/{userId}` 에 더하고 빼는 것

| 필드 | 내용 |
| --- | --- |
| `statusCard.status` | `UserStatus` |
| `statusCard.sanction` | 열린 정지 행 — `{ sanctionId · reason · reasonLabel · reasonDetail · suspendedAt · suspendedByName · appealInquiries[{ inquiryId · answered · createdAt }] }` · 없으면 `null`. `appealInquiries` = `one_to_one_inquiry.sanction_id = 이 정지` 최신순 — 해제 모달의 「소명 문의 번호 · 클릭 이동」(§25-4). 탈퇴 회원도 열린 정지가 있으면 그대로 보인다(0-9) |

### 2-4. 어드민 1:1 문의 — 소명 표시

`AdminInquiryDto.ListItem · DetailResponse` 에 `sanctionAppeal: boolean` · `sanctionId` 를 더하고, 소명 문의의 `typeName` 은 「계정 이용 정지」로 내린다(유형 탭 집계는 `ACCOUNT` 그대로 — 0-8). 상세에는 이미 있는 회원 id 로 소비자 상세 이동이 된다. 목록 정렬 · 필터(「소명 미확인」 상단)는 시안이 없어 두지 않는다(13절 #12).

## 5. 1:1 문의 — 「계정 이용 정지」 소명 유형

### 5-1. 등록 `POST /v1/user/inquiries` — `sanctionAppeal` 추가

`InquiryRegisterRequest` 에 `sanctionAppeal: Boolean`(선택). `true` 면 `InquiryService.registerInquiry` 가:

1. 회원 `SUSPENDED` ∧ 열린 정지 행 존재 — 아니면 409 `SANCTION_APPEAL_NOT_AVAILABLE`(정지 중이 아니면 이 유형이 목록에 없다 — §51-6 1d).
2. 모양 고정 — `type == ACCOUNT` · `orderId == null` · `claimId == null`, 어긋나면 400 `INVALID_INPUT_VALUE`(반려 이의의 `requireDisputeShape` 와 같은 방식 · 「관련 주문 칸 비노출」).
3. 같은 정지에 **답변 전 소명 문의가 이미 있으면** 409 `SANCTION_APPEAL_ALREADY_EXISTS` — 반려 이의 `CLAIM_DISPUTE_ALREADY_EXISTS` 와 같은 규칙(13절 #8). 앱은 3-1 `pendingAppealInquiryId` 로 미리 그 문의로 보낸다.
4. 저장 시 `sanction_id = 열린 정지`. 내용 1,000자 · 사진 5장은 기존 검증 그대로.

`sanctionAppeal` 이 없거나 `false` 면 기존 동작 — 정지 회원도 다른 5종 유형 문의를 그대로 쓸 수 있다(문의는 허용 범위).

### 5-2. 수정 · 삭제 · 조회

- 수정 — 소명 문의는 유형 · 주문이 고정이다(내용 · 사진만). 반려 이의의 수정 분기와 같은 자리에 둔다. 정지가 해제된 뒤에도 답변 전이면 고칠 수 있다(이미 접수된 문의다).
- 삭제 — 기존 규칙(답변 전만).
- 앱 목록 · 상세 응답(`InquiryListResponse · InquiryDetailResponse`)에 `sanctionAppeal: boolean` · 소명 문의의 `typeName` 은 「계정 이용 정지」.
- 유형 목록 `GET /v1/common/inquiries/categories` 는 **바꾸지 않는다**(비로그인 공용 · 5종 단일 소스). 6번째 항목은 정지 상태를 아는 앱이 붙인다(0-6 · 13절 #14).

## 10. 마이그레이션 — V204 하나

`V204__create_user_sanction_and_admin_memo.sql`

1. `user_sanction` · `user_admin_memo` · `user_admin_history` 생성(1-2 · 1-3).
2. `one_to_one_inquiry` `sanction_id` + 인덱스(1-4).
3. **메모 이관** — `ADMIN_MEMO` 가 공백이 아닌 회원마다 1행: `author_id = NULL` · `author_name = '이전 단일 메모(작성자 미기록)'` · `content = ADMIN_MEMO` · `created_at = 마이그레이션 시각`. 시각을 `MODIFIED_AT` 으로 추정하지 않는다 — 그 값은 닉네임 · 인증 갱신에도 바뀌어 메모 시각이 아니다(「없는 데이터를 만들지 않는다」).
4. **옛 상태 변경 이관** — `user_status_history` 중 `new_status = 'SUSPENDED'` → `SUSPENDED` · `new_status = 'NORMAL'` → `SUSPENSION_RELEASED` 를 `user_admin_history` 로 복사(`actor_type = ADMIN` · `actor_id/name = NULL` · `detail = '이전 방식 처리 — 사유 · 처리자 미기록'` · `created_at` 원본). 탈퇴 행은 7-2 가 읽으므로 옮기지 않는다.
5. 옛 정지 회원(`status = SUSPENDED`)에 `user_sanction` 행은 **만들지 않는다** — 사유를 지어내지 않는다. 3-1 · 2-2 가 행 없는 정지를 견딘다.

`USERS.ADMIN_MEMO` 는 DROP 하지 않는다(2단계 마이그레이션의 2단계 — 시점 미정).
