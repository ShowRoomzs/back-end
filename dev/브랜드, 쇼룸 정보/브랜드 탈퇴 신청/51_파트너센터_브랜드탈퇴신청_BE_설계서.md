## 1. 먼저 정한 8가지

### 1-1. 경로는 `/v1/seller/basic-info` 아래 — 스튜디오(50 4절)와 같은 모양

| 스튜디오(구현됨) | 파트너(이 설계) |
| --- | --- |
| `GET /v1/creator/basic-info/account` → `withdrawal` 블록 | `GET /v1/seller/basic-info/account` → `withdrawal` 블록 |
| `POST /v1/creator/basic-info/withdrawal-requests` | `POST /v1/seller/basic-info/withdrawal-requests` |
| `POST …/withdrawal-requests/{requestId}/cancel` | `POST …/withdrawal-requests/{requestId}/cancel` |
| `POST …/withdrawal-requests/{requestId}/acknowledge`(S8 반려 확인) | **없음** — 브랜드에는 반려 화면이 없다(§51-5 「회원 화면 없음 — 어드민 M3 사유가 알림으로 발송」 · 7-3) |

FE 가 두 서피스의 탈퇴 카드를 같은 컴포넌트 규칙으로 그릴 수 있게 `state · satisfiedCount · totalCount · conditions[] · breakdown[] · pendingRequest` 이름을 스튜디오와 맞춘다.

### 1-2. 판정은 `BrandWithdrawalEligibility` 하나, 내역은 표시 전용 클래스

52 0-5 · 4-1 의 원칙 그대로 — 신청 화면 체크리스트 · 신청 API · 어드민 승인 재검증이 **같은 판정식**을 쓴다. 화면에 필요한 내역(상태별 건수 · 기한 · 스레드 id)은 `CreatorWithdrawalChecklist` 와 같은 패턴의 **`BrandWithdrawalChecklist`(표시 전용)** 가 만들고, 탈퇴 가능 여부는 판정하지 않는다.

- **불변식**: 조건 행의 `count` = 내역 `count` 합 = `evaluate()` 의 그 조건 건수. 테스트로 고정한다(10절 WD-04).

### 1-3. 테이블 · 마이그레이션 없음

`brand_withdrawal_request`(V199)에 신청 · 취소에 필요한 컬럼이 전부 있다(`reason` · `message` · `requester_name` · `canceled_at` · `pending_key` UNIQUE). 반려 확인 컬럼(스튜디오 `result_acknowledged_at`)은 브랜드 반려 화면이 없으므로 **두지 않는다**.

### 1-4. 대기 중 잠금 = 「열린 신청 행이 있다」 — 회원 상태를 바꾸지 않는다

§51-0 「탈퇴 신청 심사는 회원 상태와 다른 축」. 신청해도 `market.status` 는 `ACTIVE`(또는 `SUSPENDED`) 그대로이고, 잠금은 `brand_withdrawal_request.status = PENDING` 행의 유무로 판정한다. 취소 · 반려되면 행이 대기가 아니게 되므로 **잠금이 자동으로 풀린다** — 해제 코드가 따로 없다(52 4-2 와 같은 결론).

가드는 `BrandSanctionGuard`(정적 유틸 · `market.status` 만 본다)와 달리 **DB 조회가 필요**해서 `@Component BrandWithdrawalGuard` 로 둔다(7절). `CreatorSanctionGuard` 가 같은 이유로 컴포넌트다.

### 1-5. 정산 조건은 **브랜드 몫** 기준으로 센다 — 기존 식 보정(결정 D-1)

현재 조건 ④ = `settlement.status ≠ PAID` 건수 + 회수 대기 차감. 그런데 정산 상태는 **세 수취자(브랜드 · 인플루언서 · 플랫폼) 행이 전부 끝나야** `PAID` 가 된다(`PayoutStatus.SETTLED` · 44 어드민 1-4). 그래서 다음 두 경우 **브랜드 몫은 이미 지급 완료인데 탈퇴가 막힌다**:

| 경우 | 정산 상태 | 브랜드 행 | 인플루언서 행 | 브랜드가 할 수 있는 일 |
| --- | --- | --- | --- | --- |
| 인플루언서 계좌 확인 중 · 세금계산서 미확인 · 주민번호 미등록 | `PAYOUT_SCHEDULED` | `PAID` | `BLOCKED` | 없음 — 인플루언서가 풀어야 한다 |
| 인플루언서 몫 분배 실패 | `PAYOUT_FAILED` | `PAID` | `FAILED` | 없음 — 파트너 화면엔 `PAID` 로 접혀 보인다(`toPartyStatus`) |

두 번째는 특히 나쁘다 — 파트너 정산 관리에는 「지급 완료」로 보이는데 탈퇴 체크리스트는 「진행 중 정산 1건」이라고 한다. 브랜드는 무엇을 해야 하는지 알 수 없다(시안 4-G 「막는 이유를 건수로 말한다」 위반).

**제안 식**: 조건 ④ = **브랜드 수취자 행(`settlement_payout.payee = BRAND`)이 `PAID · NOT_APPLICABLE` 이 아닌 정산 건수** + 회수 대기 차감(`ClawbackSide.BRAND · PENDING`).

- 확정 전 정산(`REVIEWING · ADJUSTING`)의 브랜드 행은 `WAITING · HELD` 라 그대로 잡힌다 — 정산 확인 중 · 조정 협의는 여전히 조건이다.
- 브랜드 몫이 분배 실패(`FAILED`) · 지급 보류(`BLOCKED` — 계정 정지 포함)면 잡힌다 — 4-G2 그대로.
- 정산마다 브랜드 행은 정확히 1개다(`SettlementGenerationService` 가 생성 시 BRAND · CREATOR · PLATFORM 3행을 만든다).
- **어드민 승인 재검증도 같은 식으로 바뀐다**(판정식이 하나라서) — 의도한 결과다. 52 4-1 표의 `UNSETTLED` 행 정의를 이 절로 갱신한다.

D-1 을 「유지」로 정하면 4-4 내역에 `OTHER_PARTY_PENDING`(「상대 몫 지급 대기 — 기다리면 풀림」) 행을 더해 건수를 맞춘다. 식은 그대로 둔다.

### 1-6. 「운영팀에 문의 ↗」 = 운영팀 채널 스레드 id — 조회는 읽기 전용

4-G 계약 행의 「서명 진행중 — 운영팀에 문의 ↗」와 차감 대기 행은 브랜드의 운영팀 1:1 채널(`ConnectionType.OPERATOR_MARKET`)로 보낸다. `OperatorChannelService.requireMarketChannel` 은 **없으면 만든다**(쓰기)라 GET 에서 부르지 않는다 — `connectionRepository.findByTypeAndMarket(OPERATOR_MARKET, market)` → 그 스레드 id 를 읽기만 하고, 없으면 `null`(FE 는 소통 메뉴로 보낸다). 가입 승인 때 채널이 만들어지므로(`ensureMarketChannel`) 실제로는 거의 항상 있다.

### 1-7. 정지 중에도 신청할 수 있다 — 조건은 그대로

§51-5 · 4-G2. `BrandWithdrawalService.request` 는 이미 정지를 검사하지 않는다. 정산 정보 불일치 정지면 브랜드 몫이 `BLOCKED(BRAND_SUSPENDED)` 라 조건 ④가 풀리지 않는다 — 「정지를 피하려고 탈퇴」하는 길이 없다. 내역 행이 그 이유와 `[정산 정보 수정하기]` 대상을 내린다(4-4).

### 1-8. 4-I 「신청자」는 로그인 이메일이다

시안 4-I 의 신청자 칸은 `brand@example.com` 이다. 행의 `requester_name` 은 52 가 정한 **담당자명 스냅샷**(어드민 심사 카드 · 파기 후 표시용)이라 다른 값이다. 응답에는 둘 다 내린다 — `requesterEmail` = 현재 `seller.email`. 대기 중에는 이메일 변경이 잠기므로(7절) 신청 시점 이메일과 같다. 이메일을 행에 새로 저장하지 않는다(1-3).

## 2. API 개요

`SellerBasicInfoController`(`/v1/seller/basic-info` · 권한 `SELLER`)에 2개를 더하고 1개의 응답을 넓힌다. 문서는 `SellerBasicInfoControllerDocs` 에 둔다(CLAUDE.md — 컨트롤러는 매핑만).

| 메서드 | 경로 | 요청 | 응답 | 시안 |
| --- | --- | --- | --- | --- |
| GET | `/account` | — | 200 `AccountInfoResponse`(**`passwordChangeable` · `identityLock` · `withdrawal` 추가**) | 4-A ~ 4-I |
| PATCH | `/account/password` | (기존) | (기존) · 대기 중 409 `BRAND_WITHDRAWAL_PENDING` | 4-I |
| PATCH | `/account/email` | (기존) | (기존) · 대기 중 409 `BRAND_WITHDRAWAL_PENDING` | 4-I |
| POST | `/withdrawal-requests` | `{ reason?, message? }` | 201 `{ requestId, requestedAt }` | 4-H |
| POST | `/withdrawal-requests/{requestId}/cancel` | — | 204 | 4-I |

현재 판매자 식별은 컨트롤러의 `getCurrentSellerEmail()` → 서비스의 `getMyMarket(email)` 이다(같은 컨트롤러의 기존 관례). 마켓이 없으면 404 `MARKET_NOT_FOUND`.

```jsonc
  "requesterName": "김담당",           // 행 스냅샷(1-8)
  "requesterEmail": "brand@example.com"
}
```

**`state` 판정**(위에서부터 첫 번째)

1. `PENDING` 신청 행이 있다 → `PENDING` + `pendingRequest` · `identityLock = WITHDRAWAL_PENDING`.
2. `BrandWithdrawalEligibility.evaluate(marketId)` 가 전부 0 → `AVAILABLE`, 아니면 `BLOCKED`.

- `conditions` 는 **상태와 무관하게 항상** 내린다(스튜디오와 같다 — 4-F 는 충족 상태로 남는다). 4-I 는 체크리스트를 그리지 않지만 응답은 같다.
- 4-G 와 4-G2 의 구분은 상태가 아니라 정산 내역 행의 키(4-4 `PAYOUT_BLOCKED` · `reasonCode = BRAND_SUSPENDED`)다.
- 탈퇴 브랜드(`WITHDRAWN`)는 로그인할 수 없어 이 응답에 도달하지 않는다(52 4-3 — 이메일 치환 · 비밀번호 폐기).
- `emailChangeable` 의 의미가 넓어진다(잠금 반영). 월 1회 제한 문구는 FE 가 `identityLock == null ∧ !emailChangeable` 일 때만 띄운다.

**조회 비용**: 판정식 쿼리 5개 + 내역 쿼리 4개(4절) + 신청 행 1 + 채널 1 + 작성중 계약 1. 계정 탭을 열 때만 돈다 — 캐시하지 않는다.

## 4. 조건 내역 — `BrandWithdrawalChecklist`(신규 · 표시 전용)

`domain.member.brand.service.BrandWithdrawalChecklist.read(marketId) → List<Condition>` — `CreatorWithdrawalChecklist` 와 같은 레코드 모양(`Condition(condition, count, breakdown)` · `Breakdown(...)`) 에 브랜드 화면이 요구하는 필드를 더한다.

조건 행 공통:

```jsonc
{
```

### 4-4. ④ 진행 중 정산 — `UNSETTLED` · `target = SETTLEMENTS`

1-5(D-1 제안 식) 기준. 브랜드 수취자 행과 정산 행을 함께 읽는다.

| `key` | `label` | `group` | 대상 | 추가 필드 |
| --- | --- | --- | --- | --- |
| `REVIEWING` | 정산 확인 중 | `WAIT` | `settlement.status = REVIEWING` | `expectedDate` = MIN(`review_due_at`) 의 날짜 — 「확인 기간이 끝나면 자동 확정」 |

| `PAYOUT_FAILED` | 분배 실패 | `OPERATOR` | 확정 후 · 브랜드 행 `FAILED` | 운영자 재분배(44 M3) 대기 |
| `CLAWBACK_PENDING` | 차감 대기 | `OPERATOR` | `settlement_clawback` · `BRAND` · `PENDING` | 7-5 · 미결 Q2 |

**`PAYOUT_BLOCKED` 사유별 `group` · `target`**

| `reasonCode` | `group` | `target` | 시안 |
| --- | --- | --- | --- |
| `BRAND_SUSPENDED` | `MY_ACTION` | `SETTLEMENT_ACCOUNT` | **4-G2** 「계정 정지(정산 정보 불일치)로 브랜드 몫 지급이 멈춰 있습니다 · 정산 정보 수정하기 ↗」 — 정지 사유 라벨은 `GET /business` 의 `sanction.reasonLabel` 과 같은 값을 `reasonLabel` 뒤에 붙인다(정지 행 1회 조회) |

| 그 밖(`PARTNER_NOT_READY` · `PAYOUT_CONTRACT_BLOCKED` · 알 수 없는 코드) | `OPERATOR` | `null` | 운영팀 문의 |

**쿼리(신규 2)**

```java
// SettlementPayoutRepository — 브랜드 몫이 끝나지 않은 정산을 상태 · 보류 사유별로
@Query("SELECT p.status, p.failCode, COUNT(p), MIN(p.dueDate) FROM SettlementPayout p, Settlement s "
     + "WHERE p.settlementId = s.id AND s.market.id = :marketId "
     + "AND p.payee = showroomz.domain.settlement.type.SettlementPayee.BRAND "
     + "AND p.status NOT IN (showroomz.domain.settlement.type.PayoutStatus.PAID, "
     + "                     showroomz.domain.settlement.type.PayoutStatus.NOT_APPLICABLE) "
     + "GROUP BY p.status, p.failCode")
List<Object[]> countBrandOpenPayoutsByStatus(@Param("marketId") Long marketId);

// SettlementRepository — 확정 전(REVIEWING · ADJUSTING) 건수 · 가장 이른 확인 기한
@Query("SELECT s.status, COUNT(s), MIN(s.reviewDueAt) FROM Settlement s WHERE s.market.id = :marketId "
     + "AND s.status IN (showroomz.domain.settlement.type.SettlementStatus.REVIEWING, "
     + "                 showroomz.domain.settlement.type.SettlementStatus.ADJUSTING) GROUP BY s.status")
List<Object[]> countBeforeConfirmForMarket(@Param("marketId") Long marketId);
```

- 브랜드 행 `WAITING · HELD` 는 확정 전 정산의 행이라 두 번째 쿼리가 센다 — 첫 번째 쿼리 결과에서 `WAITING · HELD` 는 **내역에 쓰지 않는다**(이중 집계 방지). 합계 불변식: `REVIEWING + ADJUSTING + (SCHEDULED · REQUESTED · BLOCKED · FAILED 의 합) + 차감 대기 = 판정식 ④`.
- `ADJUSTING.items[]` = 조정 협의 중인 정산 id 목록 → `SettlementAdjustmentReader.findBySettlementIds(ids)` 로 `threadId · deadlineAt` · `turnFor(summary, SettlementParty.BRAND)`(44 이슈 스레드 1-5)를 붙인다. 시안은 조정 협의를 일괄 「내 응답 필요」로 묶지만(「응답하면 빨리 끝나므로 할 일로 표시」), 개별 건의 실제 차례는 `turn` 으로 같이 내린다 — 상대 차례인 건에 「내 응답 필요」를 붙일지는 FE 문구 판단.

**판정식 보정(D-1 채택 시)** — `BrandWithdrawalEligibility.evaluate` 의 `UNSETTLED` 한 줄:

```java
// before
settlementRepository.countUnpaidForMarket(marketId) + clawbackRepository.countPendingForMarket(marketId)
// after — 브랜드 수취자 행 기준(1-5)
settlementPayoutRepository.countBrandOpenForMarket(marketId) + clawbackRepository.countPendingForMarket(marketId)
```

`countBrandOpenForMarket` = 위 첫 번째 쿼리의 `COUNT` 합(같은 WHERE). 확정 전 정산도 브랜드 행이 `WAITING · HELD` 라 이 쿼리에 들어간다 — 판정식은 쿼리 하나로 끝나고, 내역만 두 쿼리로 나눠 그린다.

## 5. `POST /v1/seller/basic-info/withdrawal-requests` — 신청(M5)

```json
{ "reason": "BUSINESS_CLOSED", "message": "그동안 감사했습니다." }
```

```java
@Schema(description = "탈퇴 사유 — 「선택하지 않음」은 보내지 않는다(null)")
private BrandWithdrawalReason reason;

@Size(max = 1000, message = "남기실 말씀은 1,000자 이내로 입력해 주세요.")
private String message;
```

- 두 필드 모두 **선택**(4-H 「사유는 선택 입력이고 미선택도 신청할 수 있다」 · §51-5 브랜드 사유 선택). 바디가 비어도(`{}`) 신청된다. 모르는 사유 코드 → 400(Jackson enum 역직렬화 · 기존 `INVALID_INPUT_VALUE` 처리기).
- 길이 1,000 = 컬럼 `message VARCHAR(1000)`. 시안에 글자 수 표시가 없다 — FE 카운터는 이 값을 쓴다(D-6).
- 확인 문구 타이핑 · 비밀번호 재확인 **없음**(4-H 「차단 조건 4개 통과가 이미 관문」).

**처리** — `SellerWithdrawalService.request(sellerEmail, body)` → `BrandWithdrawalService.request(marketId, reason, message, now)`(기존 · 52 4-2). 한 트랜잭션:

1. 마켓 잠금(`BrandSanctionService.lockBrand`) — 같은 브랜드의 신청 · 취소 · 어드민 승인 · 정지를 한 줄로 세운다.
2. `WITHDRAWN` → 409 `BRAND_WITHDRAWN`(로그인이 막혀 실제로는 도달하지 않는다).
3. 열린 신청 → 409 `BRAND_WITHDRAWAL_ALREADY_PENDING`(4-I 「탈퇴 재신청 불가」 · 더블 클릭).
4. `eligibility.requireEligible` → 409 `BRAND_WITHDRAWAL_CONDITION_UNMET` + 응답 최상위 `unmet { CONDITION: count }`(`ConditionUnmetException` · 52 15-#6). FE 는 버튼을 막아 두므로 이 응답은 「화면을 연 뒤 상황이 바뀐」 경우다 — 계정 탭을 다시 읽어 4-G 로 그린다.
5. 행 INSERT(`requester_name` = 담당자명 스냅샷) · 이력 `WITHDRAWAL_REQUESTED`(actor BRAND · detail 「사유: {라벨}」).
6. 201 `{ requestId, requestedAt }` — FE 는 `GET /account` 를 다시 읽어 4-I 를 그린다(스튜디오와 같은 흐름).

- **정지 중 신청 허용**(1-7) — 정지 검사를 넣지 않는다.
- 경합: 마켓 행 잠금 + `pending_key` UNIQUE 이중 방어. 잠금이 먼저 줄을 세우므로 UNIQUE 위반은 정상 경로에서 나지 않는다.
- 알림: 신청 접수를 브랜드 · 운영자에게 알리지 않는다(시안 없음). 어드민 목록 `withdrawalPending` 필터 · 상세 심사 카드가 받는다(52 9-1).

## 6. `POST /v1/seller/basic-info/withdrawal-requests/{requestId}/cancel` — 신청 취소(4-I)

- 바디 없음 · 204. 처리 = `BrandWithdrawalService.cancel(marketId, requestId, now)`(기존): 마켓 잠금 → 신청 행 잠금(`findForUpdate`) → 마켓 불일치 · 없음 404 `BRAND_WITHDRAWAL_NOT_FOUND`(다른 브랜드의 id 도 404 — 존재 여부를 흘리지 않는다) → `PENDING` 아님 409 `BRAND_WITHDRAWAL_NOT_PENDING` → `CANCELED` · `canceled_at` · 이력 `WITHDRAWAL_CANCELED`(actor BRAND).
- 취소 즉시 잠금이 풀린다(1-4) — 같은 트랜잭션 커밋 뒤 비밀번호 변경 · 계약 작성 · 재신청이 바로 된다.
- 어드민이 막 승인한 뒤의 취소: 승인이 마켓을 먼저 잠갔으므로 취소는 `NOT_PENDING` 409 — 그리고 승인으로 로그인이 끊겼으므로 다음 요청부터 401 이다. 막 반려된 뒤의 취소도 409 — FE 는 계정 탭을 다시 읽는다(4-F/4-G 로 돌아간다).
- 「운영자 처리 전까지」(§51-5 · 4-I)만 취소할 수 있다는 규칙은 `PENDING` 검사가 그대로 집행한다. 철회 가능 구간 자체는 기획 미정(파트너 06 [미정] ②) — 이 설계는 「처리 전까지」로 둔다.

| 탈퇴 재신청 | `BrandWithdrawalService.request` | — | 기존 `BRAND_WITHDRAWAL_ALREADY_PENDING` 그대로 |

**「공구 생성」 지점이 따로 없는 이유** — 공구는 계약 체결에서만 생긴다(`GroupBuy.createFrom(contract)`). 신청 시점에 체결 전 계약(검토 대기 · 반려 · 서명 진행중 · 체결 처리 대기)이 0 이어야 하고(조건 ②), 대기 중에는 검토 요청이 막히므로 새 체결이 생길 길이 없다. 진행 중 공구도 0 이라(조건 ①) 공구 오픈 게이트도 필요 없다.

**막지 않는 것**(시안 「계정은 그대로 사용할 수 있다」): 작성중 계약 수정 · 삭제 · 검토 요청 취소 · 상품 등록 · 수정 · 주문 · 클레임 처리 · 상품 문의 답변 · **정산 조정 응답**(오히려 해야 한다) · 담당자 · CS · 배송 정책 · 사업자 정보 · 정산 계좌 **변경 요청**(4-G2 의 해소 경로) · 스레드 · 인플루언서 연결 요청(D-4).

### 7-3. 반려 결과 — 시안 없음, 필드만 내린다

§51-5 는 브랜드 반려를 「회원 화면 없음 — 알림으로 발송」으로 정했다. 그런데 알림은 지금 스텁이라(8절) **브랜드는 반려 사실도 사유도 알 길이 없다** — 4-I 카드가 사라지고 체크리스트(4-F/4-G)로 돌아갈 뿐이다. 그래서:

- `withdrawal.lastRejection` = 가장 최근 신청 행이 `REJECTED` 이고 열린 신청이 없을 때 `{ requestId · rejectedAt · reasonCode · reasonLabel · note }`(`BrandWithdrawalRejectReason.label` · `reject_note` — 어드민 M3 「브랜드에 전달할 안내」). 확인 컬럼이 없으므로 **다음 신청 전까지 계속 내려간다**.
- 그릴지 · 어떻게 그릴지는 FE · 기획 판단(D-2). 서버는 재료만 둔다 — 컬럼을 늘리지 않는다.

### 7-4. 테스트 영향

- `SellerBasicInfoServiceTest`(`@InjectMocks`)에 `@Mock BrandWithdrawalGuard` 추가 — 없으면 생성자 주입이 `null` 을 넣어 NPE.
- `SellerContractCommandService` 는 이미 `CreatorSanctionGuard` 를 주입받는다 — 같은 방식으로 1개 더한다.

### 7-5. 승인 시점과 대기 중 사이의 틈

신청 트랜잭션은 마켓을 잠그지만 계약 작성 · 검토 요청은 마켓을 잠그지 않는다. 신청 커밋 직전에 들어온 검토 요청이 통과할 수 있다 — **어드민 승인이 판정식을 다시 돌려**(52 4-3 ②) 그 건을 잡고 운영자는 「체결 전 계약 잔존」으로 반려한다. 가드에 마켓 잠금을 더하지 않는다(계약 경로 전체가 잠금 경합에 들어간다 — 틈의 대가보다 크다).

## 8. 결과 메일 — 스텁을 `MailService` 로 잇는다(결정 D-3)
