## 1. C-1 제주 추가비 분리

### 1-1. 왜 한 칸으로는 안 되나(기획 근거)

제주는 항공 · 해상 운임이 따로 붙어 육상 도서산간과 금액대가 다르고, 택배사 요금표도 따로 나온다. 한 칸이면 브랜드가 둘 중 높은 값을 넣어 한쪽 소비자가 과다 부담한다. 기본정보 관리(ui-partner-06) · 상품 상세(C7 「제주 +3,000원 · 도서산간 +5,000원」)가 이미 두 값을 나눠 그린다.

### 1-2. 저장 — `market.jeju_surcharge`

`remote_area_surcharge` 와 같은 모양으로 둔다.

| 컬럼 | 타입 | 기본 | 의미 |
| --- | --- | --- | --- |
| `jeju_surcharge` | `INT NOT NULL` | `0` | 제주 추가비(원) |
| `remote_area_surcharge`(기존) | 그대로 | 그대로 | 의미만 좁아진다 — **제주를 뺀** 도서산간 추가비 |

`Market` 엔티티:

```java
@Column(name = "jeju_surcharge", nullable = false)
private Integer jejuSurcharge = 0;
```

### 1-3. 기존 마켓 백필

지금 `remote_area_surcharge` 에 들어 있는 값은 **제주를 포함한** 금액이다. 새 컬럼을 0으로 두면 제주 소비자가 보는 추가비가 하루아침에 0원이 된다. **같은 값을 복사**해 지금 표시를 그대로 유지하고, 나누는 것은 브랜드가 기본정보 관리에서 한다(Q2).

```sql
-- V200__alter_market_add_jeju_surcharge.sql
-- 온보딩 §6 · 기본정보 §15-10 — 제주 추가비를 도서산간 추가비에서 분리한다.
ALTER TABLE market
    ADD COLUMN jeju_surcharge INT NOT NULL DEFAULT 0;

-- 기존 한 칸(도서산간)은 제주를 포함한 값이었다 — 제주에도 같은 값을 넣어 소비자 표시가 바뀌지 않게 한다.
UPDATE market SET jeju_surcharge = remote_area_surcharge;
```

### 1-4. 요청 필드 — `SellerCompleteRegistrationRequest.jejuSurcharge`

「제주 먼저」 — 필드 · Swagger 예시 모두 `remoteAreaSurcharge` **앞**에 둔다.

```java
@Min(value = 0, message = "제주 추가비는 0 이상이어야 합니다.")
@Schema(description = "제주 추가비 (선택 · 미입력 시 0원)", example = "5000", nullable = true)
private Integer jejuSurcharge;

@Min(value = 0, message = "도서산간 추가비는 0 이상이어야 합니다.")
@Schema(description = "도서산간 추가비 — 제주 제외 (선택 · 미입력 시 0원)", example = "5000", nullable = true)
private Integer remoteAreaSurcharge;
```

`SellerService#completeRegistration`:

```java
market.setJejuSurcharge(request.getJejuSurcharge() != null ? request.getJejuSurcharge() : 0);
market.setRemoteAreaSurcharge(request.getRemoteAreaSurcharge() != null ? request.getRemoteAreaSurcharge() : 0);
```

### 1-5. 같은 컬럼을 읽고 쓰는 곳 — 같이 바꾼다

온보딩에서 받은 값을 이후 **기본정보 관리에서 고칠 수 있어야** 한다(§6-4 「이후 수정은 기본정보관리(§15-10)에서 계속 가능」). 컬럼을 온보딩에서만 쓰면 브랜드가 제주 값을 다시 바꿀 길이 없다. 그래서 아래는 이 설계서 범위다. 모두 **필드 추가**라 하위 호환이다.

| 위치 | 변경 |
| --- | --- |
| `SellerBasicInfoDto.DeliveryPolicyResponse` | `jejuSurcharge`(`remoteAreaSurcharge` 앞) · `remoteAreaSurcharge` 설명 「제주 제외」 |
| `SellerBasicInfoDto.UpdateDeliveryPolicyRequest` | `jejuSurcharge` — `@Min(0)` · nullable · 비우면 0 |
| `SellerBasicInfoService#getDeliveryPolicy` · `#updateDeliveryPolicy` | 읽기 · 쓰기 한 줄씩(`null → 0` — 도서산간과 같은 규칙) |
| `SellerBasicInfoControllerDocs`(46행 부근) | 「도서산간 추가비」→「제주 추가비 · 도서산간 추가비」 |
| `ProductDto.DeliveryInfo` · `ProductService#buildDeliveryInfo` · `UserProductControllerDocs` | `jejuSurcharge` 추가 — C7 「제주 +3,000원 · 도서산간 +5,000원」의 재료. 앱이 아직 안 그려도 무해 |
| `AdminBrandDto.DeliveryPolicy` · `AdminBrandQueryService#deliveryPolicy` | `jejuSurcharge` 추가 — 어드민 브랜드 상세 시안의 「(제주 포함)」 표기는 기획 쪽 미반영(§52 A-19 → §55 D-27) · 값은 먼저 내린다 |

`DeliveryPolicy` 는 record 라 생성자 인자 순서가 바뀐다 — 호출처는 `AdminBrandQueryService` 한 곳이다(테스트 포함 재컴파일로 확인).

### 1-6. 하지 않는 것

- **권역 판정 · 부과**: 「권역 판정은 우편번호 자동 · 겹치면 제주 우선」(ui-partner-06)은 결제 쪽 일이다. 지금 `OrderPricingCalculator` · `CheckoutService` 는 도서산간 추가비도 **부과하지 않는다**(표시 전용). 제주도 똑같이 표시만 한다. 부과가 들어오는 날 두 값을 같이 쓴다 — 우편번호 목록은 ui-partner-06 의 `[미정] ③`.

## 2. C-2 발송 기한 필수화

### 2-1. 현재와 기획

| | 현재 | 기획 |
| --- | --- | --- |
| 필수 여부 | 선택 — 생략하면 `ShipDuePolicy.DEFAULT_BUSINESS_DAYS`(3) 저장 | **필수** — §6-4 표 「필수」 · §6-6 필수 8개에 포함 · 시안 B 빈칸 에러 |
| 범위 | 1~7 | 최대 7(시안 `min=1 max=7`) |
| 미입력 문구 | — | 「발송 기한을 입력해 주세요.」 |

### 2-2. 변경

```java
@NotNull(message = "발송 기한을 입력해 주세요.")
@Min(value = 1, message = "발송 기한은 1~7영업일로 입력해 주세요.")
@Max(value = 7, message = "발송 기한은 1~7영업일로 입력해 주세요.")
@Schema(description = "발송 기한 — 공구 마감 후 N영업일(주말·공휴일 제외) · 1~7. "
        + "소비자 상품 상세에 「공구 마감 후 N영업일 이내 발송」으로 자동 표시된다", example = "3")
private Integer shippingLeadDays;
```

`SellerService` 는 기본값 분기를 지우고 `market.setShippingLeadDays(request.getShippingLeadDays())` 로 쓴다. 기본정보 관리의 `UpdateDeliveryPolicyRequest.shippingLeadDays` 가 이미 같은 세 어노테이션 · 같은 문구다 — 두 화면의 서버 규칙이 같아진다.

### 2-3. ⚠️ B-16(「기본 3」 vs 「빈칸 필수」)은 서버 규칙에 영향이 없다

기획이 표시한 충돌(§6-4 ⚠️ → (3) §55 B-16)은 **FE 의 초기 표시값** 문제다 — 기본정보 관리는 저장값이 없으면 3을 보여 주고, 온보딩 표 · 시안 B 는 빈칸이다(정작 시안 A 는 `value="3"` 으로 채워 둔다). 어느 쪽으로 정해지든 **서버는 「반드시 보낸다 · 1~7」** 하나다. FE 가 3을 미리 채우면 그 3이 그대로 온다.

### 2-4. 호환성

`shippingLeadDays` 를 빼고 보내던 클라이언트는 **400** 을 받는다. 온보딩 화면은 이번 시안으로 같이 바뀌므로 FE 배포와 묶는다(8절). 이미 온보딩을 마친 브랜드(`isNewMember = false`)는 이 API 를 다시 부르지 않으니 영향이 없다.

### 2-5. 발송 기한 이력(`market_ship_lead_history`)은 쓰지 않는다

52 설계서 0-14 — 이력은 기본정보 관리에서 **값이 바뀔 때만** 남긴다. 온보딩은 최초 설정이지 변경이 아니다. 어드민 「08.20 2→3 변경」 보조줄은 첫 변경부터 생긴다.

## 3. C-3 · D-1 무료배송 기준금액 · 문구

### 3-1. D-1 미입력을 0으로 저장하는 결함

```java
// SellerService#completeRegistration — 현재
market.setFreeShippingThreshold(
        request.getFreeShippingThreshold() != null ? request.getFreeShippingThreshold() : 0
);
```

0이 「무료배송 없음」이 아니다. 결제 계산은 `threshold != null && 합계 >= threshold` 로 무료배송을 판정한다(`OrderPricingCalculator#groupShipping` 253행 · `#summarize` 224행). **0이면 모든 주문이 무료배송**이 되고, 그 결과로

- 장바구니 · 결제에서 기본 배송비가 부과되지 않는다(브랜드 배송비 수입 0),
- 하위주문이 `free_shipping_applied = true` 로 남아 단순 변심 반품 때 기본 배송비가 환불에서 **차감**된다(`ClaimFeePolicy#returnDeduction`),
- 상품 상세에 「0원 이상 구매시 무료배송」 재료가 내려간다.

기획은 무료배송 기준금액을 「선택 · 기본값 없음」으로 두고(제주 · 도서산간의 「미입력 시 0원 적용」과 구분), 기본정보 관리는 이미 「비우면 무료배송 없음 = `null`」로 저장한다. 온보딩만 다르다.

```java
// 변경 — 기본정보 관리와 같은 규칙
market.setFreeShippingThreshold(request.getFreeShippingThreshold());
```

`@Schema` 설명도 「무료배송 기준금액 — 비우면 무료배송 없음」으로 바꾼다(`nullable = true`).

**기존 데이터** — 지금까지 온보딩에서 이 칸을 비운 브랜드는 `free_shipping_threshold = 0` 으로 남아 있다. 브랜드가 일부러 0을 넣은 경우(= 항상 무료배송)와 구분할 수 없으므로 **마이그레이션으로 일괄 수정하지 않는다**. 운영 DB 에서 건수부터 확인하고 처리 방식을 정한다(Q3).

```sql
-- 확인용(마이그레이션 아님)
SELECT m.market_id, m.market_name, m.default_delivery_fee, m.free_shipping_threshold
FROM market m JOIN seller s ON s.seller_id = m.seller_id
WHERE m.free_shipping_threshold = 0 AND s.role_type = 'SELLER';
```

| 상세 주소 — 주소 검색 전 비활성(D-21 미결) | 서버는 `@NotBlank` 하나. 화면 순서 제약은 서버가 알 수 없다 |
| 수취인 연락처 규칙이 §4 담당자 연락처와 다름(§6-3) | 이미 별도 정규식이다(`^01(?:0\|1\|[6-9])-\d{3,4}-\d{4}$` ↔ 담당자 `^010-\d{4}-\d{4}$`). 공용 유틸로 묶지 않는다 — 기획 요구와 같다 |
| 승인 후 재로그인 시 강제 진입(§6-1) | 이미 그렇다 — `loginSeller` 가 `isNewMember = true` 면 access 토큰 대신 `registerToken` 을 내리고, `refreshToken` 도 `REGISTER_EXPIRED` 로 막는다 |

## 부록. 관찰 — 이번 범위 밖

- **`registerToken` 유효 5분**(`SellerService.REGISTER_TOKEN_EXPIRY_MSEC`) — 주소 검색 포함 11칸을 채우다 5분을 넘기면 제출이 401 `REGISTER_EXPIRED` 로 끝나고 재로그인해야 한다. 입력값은 FE 가 들고 있으므로 데이터 손실은 없지만 체감 실패다. 크리에이터 · 소비자도 5분이라 함께 볼 문제.
- **수취인 이름 길이** — 기획은 「자릿수 제한 없음」인데 컬럼은 `VARCHAR(64)` 다. 64자를 넘기면 400 이 아니라 DB 오류(500)다. 화면에서 나올 일이 드물어 이번에는 두지만, 고친다면 `@Size(max = 64)` 하나다.
