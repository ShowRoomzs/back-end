## 1. 먼저 정한 7가지

### 1-1. 새 경로 `/v1/creator/basic-info` — `GET /v1/creator/profile` 은 건드리지 않는다

브랜드의 `/v1/seller/basic-info`(`SellerBasicInfoController`)와 같은 자리 · 같은 패키지 모양(`api.creator.basicinfo`)으로 둔다. `/v1/creator/profile`(`MyShowroomResponse`)은 실명 · 생년월일 · 휴대폰 · 통장 사본 URL 을 원값으로 내리는데, 스튜디오 어느 화면이 그 필드를 쓰는지 서버에서 확인할 수 없다. 응답을 고쳐 깨뜨리는 대신 **이 화면의 정본은 새 API** 로 두고, `/profile` 의 원값 필드 정리는 FE 확인 후 따로 한다(Q4).

### 1-2. 「실명 확인」 = 토스 셀러 등록 · 수정의 계좌 검증

예금주 조회 API 는 없다. 토스 `POST /v2/sellers` 가 계좌를 검증해 `INVALID_ACCOUNT_INFO` · `NOT_SELLER_ACCOUNT` · `BANK_ACCOUNT_VERIFICATION_FAIL` 로 거절하는 것이 유일한 검증이다(44 토스 설계서 0절). 그리고 지금도 지급 직전에 같은 검증이 돈다 — 계좌가 틀리면 지급일에 `ACCOUNT_HOLDER_MISMATCH` 로 터진다. 그래서 `[변경하고 실명 확인]`은 **저장 + 커밋 직후 인플루언서 셀러 `ensure`** 다. 같은 검증을 지급일이 아니라 변경 시점에 당겨 오는 것이다.

| PG 결과(`PartnerResult`) | 계좌 확인 상태 | 이유 |
| --- | --- | --- |
| `APPROVED` · `PENDING(IDENTITY_VERIFICATION_REQUIRED · KYC_REQUIRED)` | `VERIFIED` | 셀러가 만들어졌다(또는 갱신됐다) = 계좌 검증 통과. 본인인증 문자 · KYC 는 계좌와 다른 축이고 **기존 보류 사유가 따로 막는다** |
| `FAILED` + 계좌 사유(`ACCOUNT_HOLDER_MISMATCH` · `ACCOUNT_INVALID` · `UNSUPPORTED_BANK` · `BANK_REJECTED` · `ACCOUNT_MISSING`) | `FAILED`(+사유 코드) | 다른 계좌로 바꿔야 풀린다 |
| 그 밖의 실패(PG 장애 · `FORBIDDEN_SELLER_MODIFY` · 프로필 미완성 `PARTNER_NOT_READY`) | `VERIFYING` 유지 | 계좌 문제가 아니다 — 재시도(6-4) |
| `SIMULATED`(Noop · `isExternal() = false`) | `VERIFIED` 즉시 | 개발 · 테스트 환경 |

- ⚠️ **확인 주체**(§50-3 · §55 A-6) — 통장 사본은 이 설계에서 **아무도 보지 않는다**. 시안 · 어드민 05 rev.7(「인플루언서 계좌 변경은 운영자 확인 없이 저장」)을 따른 것이고 약관 인플 제11조②(「회사 승인」)와는 다르다. 승인제로 정해지면 1-5 의 같은 큐에 `SETTLEMENT_ACCOUNT` 유형 인플루언서 행을 쓰고, 승인 시점에 이 절의 확인을 부르면 된다 — 테이블은 그대로 받는다.
- 온보딩 계좌도 같은 확인을 탈지는 Q1 — 지금 온보딩은 아무 확인 없이 저장하므로 T1 「실명 확인 완료 · 확인일 2026.07.02」의 근거가 코드에 없다.

### 1-3. 확인 상태는 `creator` 컬럼, 확인 중 지급 보류는 `PayoutBlockPolicy` 사유 하나

- `CreatorAccountVerificationStatus { UNVERIFIED · VERIFYING · VERIFIED · FAILED · CHANGE_REQUIRED }` 를 `creator` 에 둔다(2-2). 계좌가 인플루언서당 1개라 별도 테이블이 필요 없다.
- 「확인이 끝날 때까지 지급 예정 건 입금 보류」(T6)는 53 의 정지 연동과 **같은 틀**이다 — 새 상태 · 운영자 버튼 없이 `PayoutBlockReason.CREATOR_ACCOUNT_UNVERIFIED` 를 더하고, 상태가 `VERIFYING · FAILED · CHANGE_REQUIRED` 면 `PayoutBlockPolicy.blockReasons` 가 이 사유를 낸다(6-5). 확정 · 지급 배치 앞단이 같은 식을 쓰므로 두 지점이 저절로 막힌다.
- 변경 순간 이미 `SCHEDULED` 인 행은 정책이 다시 보지 않으므로 훅이 `BLOCKED` 로 옮기고, 확인이 끝나면 훅이 다시 판정해 푼다 — `CreatorSettlementSanctionHook` 과 같은 구조다(6-6).
- `UNVERIFIED`(확인 이력 없는 기존 회원)는 **막지 않는다** — 오늘과 같은 동작(확정 · 지시 때 PG 동기화가 같은 검증을 한다)을 유지한다.
- **어느 계좌로 나가나** — 인플루언서 지급 행은 계좌를 **지시 시점에** 스냅샷한다(`markRequested` · 브랜드만 확정 때 고정 — 44 토스 0-5). 그래서 보류됐다 풀린 행은 **새 계좌**로, 이미 `REQUESTED` 인 행은 **이전 계좌**로 나간다. T6 의 「이미 지급이 끝난 건은 영향이 없습니다」와 맞는다.

### 1-4. 예금주는 본인 인증 실명 고정 — 상호 명의 계좌는 1차에 받지 않는다

개인사업자의 대표자는 본인이다 — §16-2a 대조 기준이 「등록증의 대표자명 = 본인확인 실명」이다. 그러니 **실명 계좌는 비사업자 · 개인사업자 모두에 유효**하다. 상호 명의 계좌를 받으려면 상호 수집 · 예금주 입력란 · 검증 경로가 필요한데 셋 다 없다(T2 예금주는 잠김 · 상호는 「받지 않는 정보」 · §50-3 ⚠️ · §55 B-9). PG 셀러 등록도 `holder = realName` 이다(`SettlementPartnerSyncService#prepareCreator`).

- 그래서 T5 · T9 · T10 시안의 「소연컴퍼니」 계좌는 1차 데이터로 생기지 않는다. T10 「변경 필요」는 **응답 계약에는 두되**(`CHANGE_REQUIRED` · 승인 시 예금주 규칙 검사 한 줄 · 8-3 ④) 1차에는 도달하지 않는다. B-9 가 상호 명의를 열면 그때 도달한다. 기획 회신 R-2.
- 예금주 열을 지금 만들지 않는다 — 값이 항상 `real_name` 이라 정보가 없다.

### 1-5. 사업자 구분 변경 요청은 브랜드 변경 요청 테이블을 넓혀 쓴다 — 큐가 하나다

§16-2a 는 인플루언서 요청이 **같은 큐**로 들어온다고 정했다 — 요청자 열(브랜드 / 인플루언서) · 요청 유형 4종 · 배지 합산(9 → 11) · 경과 정렬 고정 · 탭 안 이전 / 다음 · `CHG-YYYY-NNNN`. 그래서 `brand_change_request` 에 `requester_type` · `creator_id` · `requested_secret_enc` 를 더하고 `market_id` 를 NULL 허용으로 바꾼다(2-4). 이미 유형별로 갈라 둔 enum 이 값 추가로 받는다 — `ChangeRequestField.of(type)` · `ChangeRequestRejectReason.supports(type)`.

- **대안(별도 테이블 + UNION) 기각** — 두 테이블에 걸친 경과 정렬 페이지네이션, `/{requestId}` 경로의 id 충돌, 요청 코드 일련번호를 두 테이블이 나눠 세는 문제가 생긴다. 큐가 하나라는 기획을 테이블 하나가 그대로 받는다.
- **대가** — `BrandChangeRequest.market` 이 nullable 이 된다. 어드민 서비스의 `getMarket()` 호출 6곳에 요청자 분기가 들어간다(8절). 테이블 · 엔티티 이름의 「Brand」는 그대로 둔다 — 이름 변경 비용이 이득보다 크다(Q5).

### 1-6. 「다음 정산부터」는 정산 생성 스냅샷이 이미 만든다 — 승인이 지우면 안 되는 값이 있다

정산은 생성 때 `settlement.creator_business_type` 을 스냅샷하고(`SettlementGenerationService` 132 ~ 146행), 원천징수율과 지급 보류 분기가 그 스냅샷을 읽는다(`Settlement#isBusinessCreator`). 승인은 `creator.business_type` 만 바꾸므로 **이미 생성된 정산(확인 기간 중 포함)은 기존 구분**으로 끝나고 다음 정산부터 새 구분이 적용된다 — 시안 「다음 정산부터」 · §16-2a 「기존 구분 유지 정산 N건」 그대로다.

그런데 **이전 구분의 정산이 현재 회원 값을 읽는 곳**이 있다.

- `PayoutBlockPolicy` 는 비사업자 스냅샷 정산에서 **현재** `creator.resident_registration_number_enc` 를 본다 — 사업자 전환 승인 때 주민번호를 지우면 아직 지급 전인 비사업자 정산이 `RESIDENT_NUMBER_MISSING` 으로 막히고, 다음 해 원천세 신고 자료도 깨진다.
- 비사업자 전환 뒤에도 그 사이 확정된 사업자 정산은 세금계산서를 발행해야 지급된다(T9 고지) — 사업자등록번호 · 등록증이 남아 있어야 한다.

그래서 승인은 **값을 덮어쓰지 않고 구분만 바꾼다**(7-5 표). 화면은 현재 구분에 맞는 카드만 그린다.

### 1-7. 탈퇴는 이미 있는 도메인 위에 API 만 얹는다

신청 · 취소(`CreatorWithdrawalService`), 조건 판정(`CreatorWithdrawalEligibility` — 스튜디오 체크리스트 · 어드민 심사 카드 · 승인 재검증 공용), 대기 중 제약(`CreatorSanctionGuard` — 새 연결 수락 · 계약 서명 요청 4지점)이 이미 있다. 이 설계가 더하는 것은 화면용 조건 내역(A-6 · A-7)과 반려 확인 컬럼(A-5)뿐이다.

### 2-4. `brand_change_request` — 요청자 일반화

> **[계획서 2-2 — 16 정본]** 컬럼은 16 2-1 을 따른다 — 암호문 `resident_number_enc` · CHECK 제약 · `version` · 인플루언서 행 `requester_name = NULL` · 항목 키 `CREATOR_BUSINESS_REG_NUMBER` · `CREATOR_RESIDENT_NUMBER` · `current_value` 는 코드 저장. 마이그레이션은 V203.

| 변경 | 내용 |
| --- | --- |
| `requester_type VARCHAR(16) NOT NULL DEFAULT 'BRAND'` | `ChangeRequesterType` |
| `creator_id BIGINT NULL` + FK | `requester_type = CREATOR` 일 때만 |
| `market_id` → NULL 허용 | `requester_type = BRAND` 일 때만 |
| `requested_secret_enc VARCHAR(255) NULL` | 비사업자 전환의 **주민등록번호 암호문**. 항목 테이블(`current_value · requested_value`)에는 평문을 둘 수 없다. 승인 때 `creator` 로 옮기고 **승인 · 반려 · 취소 즉시 NULL** — 처리된 요청이 고유식별정보를 들고 있지 않게 한다 |
| `creator_pending_key` 생성 컬럼 + UNIQUE | 열린 요청은 **인플루언서당 1건**(방향 무관 — 방향은 현재 구분이 정한다). 기존 `uk_brand_change_request_pending(market_id, type, pending_key)` 는 `market_id` 가 NULL 이면 묶이지 않으므로 따로 둔다 |

- 행 의미는 그대로다 — 재요청은 새 행(§16-6) · 결과 배너는 `result_acknowledged_at`(§15-7 · `isBannerVisible()`) · 증빙 1건(`evidence_file_*` — 등록증 / 폐업사실증명원). 인플루언서 요청의 `requester_name` 은 **쇼룸명 스냅샷**(목록 「요청자」 열), `reason` 은 NULL(스튜디오 모달에 사유 입력이 없다).
- 요청 코드는 기존 `generateRequestCode()`(`CHG-{연도}-` 접두 건수 + 1)를 **두 요청자가 같이** 쓴다. 지금도 동시 생성 시 UNIQUE 충돌 가능성이 있는 방식이라 인플루언서 쪽도 같은 위험을 갖는다 — 충돌 시 1회 재시도(부록 4).

**`state` 판정**(위에서부터 첫 번째)

1. `PENDING` 신청이 있다 → `PENDING` + `pendingRequest`(S7). 요청일 · 사유 · 기한(`due_date`)은 신청 행 그대로.
2. 가장 최근 신청(`requested_at` 기준)이 `REJECTED` ∧ `result_acknowledged_at IS NULL` → `REJECTED` + `rejection`(S8). `reasonLabel` = `CreatorWithdrawalRejectReason.label` · `note` = `reject_note`(운영자가 남긴 안내 — 시안의 「퓨어랩 립밤 공구의 정산 조정 협의가 …」 문장).
3. `CreatorWithdrawalEligibility.evaluate(creatorId).eligible()` → `AVAILABLE`(S5) / `BLOCKED`(S4).

`conditions` 는 상태와 무관하게 **항상** 내린다 — S5 는 「체크리스트는 사라지지 않고 충족 상태로 남는다」, S8 은 `[확인]` 뒤 체크리스트로 돌아간다. 조건 행의 링크(공구 관리 · 계약 관리 · 정산 관리)는 FE 라우팅이다.

**조건 내역 — `CreatorWithdrawalChecklist`(신규 · 표시 전용)**

| 조건 | `breakdown` 키(라벨은 enum) | 식 |
| --- | --- | --- |
| ① 끝나지 않은 공구 | `PREPARING` · `READY` · `IN_PROGRESS` · `SUSPENSION_SCHEDULED` · `AWAITING_ORDER_CLOSURE` | 앞 4개 = `group_buy.status` 별 건수 · 마지막 = 판정식과 **같은** 「종료 · 중단 ∧ 정산 없음 ∧ 미종결 주문 > 0」(`GroupBuySalesReader.readClosure`) |
| ② 끝나지 않은 계약 | `SIGNING`(서명 진행중) · `CONCLUSION_PENDING`(체결 처리 대기) · `CONCLUDED`(체결완료) | 앞 2개 = 판정식 그대로 · `CONCLUDED` = 체결완료 ∧ **연결 공구(`group_buy.contract_id` 1:1)가 ①의 집합에 든다** |
| ③ 미정산 | `REVIEWING` · `ADJUSTING` · `PAYOUT_SCHEDULED` · `PAYOUT_FAILED` | `settlement.status ≠ PAID` 를 상태별로(판정식 그대로) |

- 건수가 0 인 내역 키는 내리지 않는다(시안은 남은 것만 적는다). `count` = 내역 합 · `satisfied` = `count == 0`.
- **불변식** — `eligible == 세 조건 모두 satisfied`. ②에 `CONCLUDED` 를 더해도 그 계약의 공구가 이미 ①에 잡혀 있으므로 판정이 바뀌지 않는다(체결완료 계약의 공구가 미종결 ⇔ ① > 0). 판정은 기존 `CreatorWithdrawalEligibility` **한 메서드**만 쓰고, 이 리더는 화면 내역만 만든다 — 테스트로 둘이 어긋나지 않음을 고정한다(14절 AC-04).

### 4-2. `PATCH /v1/creator/basic-info/account/business-email`

```json
{ "businessEmail": "soyeon@example.com" }
```

```java
@NotBlank(message = "업무 이메일을 입력해 주세요.")
@Size(max = 512, message = "업무 이메일은 512자 이내로 입력해 주세요.")
@Email(message = "이메일 형식이 올바르지 않습니다.")
@Pattern(regexp = "^[^@\\s]+@[^@\\s]+\\.[^@\\s]+$", message = "이메일 형식이 올바르지 않습니다.")
private String businessEmail;
```

- `@Email` 만으로는 시안 S3 의 `soyeon@example` 이 **통과한다**(Hibernate Validator 는 점 없는 도메인을 허용한다). 도메인에 점을 요구하는 패턴을 더한다. 문구는 S3 그대로.
- 미입력은 FE 가 `[저장]` 비활성으로 막는다(S2) — 서버는 같은 규칙을 400 으로 다시 본다.
- 앞뒤 공백 제거 후 저장 · 200 + 4-1 응답. 같은 값이면 저장 없이 200.
- **인증 메일 확인 없음 · 즉시 저장**(Q2 · §50-6 ①). **중복 검사 없음**(Q3 — 시안은 「중복 오류 문구도 같은 자리」라고 했지만 무엇과의 중복인지 정의가 없다).
- 처리 이력은 남기지 않는다 — 어드민 인플루언서 상세의 처리 이력 이벤트에 이메일 변경이 없다.

### 4-3. `POST /v1/creator/basic-info/withdrawal-requests`

```json
{ "reason": "활동 중단" }
```

- `reason` 필수 · 공백 제거 후 1 ~ 500자 → `CreatorWithdrawalService.request(creatorId, reason, now)` 그대로(조건 재판정 · 열린 신청 1건 · 이력 `WITHDRAWAL_REQUESTED` · `due_date = +5영업일`).
- **사유 선택지는 정의되지 않았다**(§55 B-13) — S6 은 드롭다운인데 목록이 없다. 그래서 서버는 **문자열**을 받고, FE 는 고른 선택지의 라벨을 그대로 보낸다. 목록이 확정되면 `reasonCode` enum 을 더하고 `reason_code` 컬럼을 그때 판다(53 1-3 의 자리).
- 응답 201 `{ requestId, requestedAt, dueDate }`.
- 반려 안내를 닫지 않은 채 다시 요청하면 그 반려 행의 `result_acknowledged_at` 을 같은 트랜잭션에서 채운다 — 새 요청을 냈다는 것 자체가 반려를 읽었다는 뜻이다.

| 경우 | 응답 |
| --- | --- |
| 사유 공백 | 400 `CREATOR_WITHDRAWAL_REASON_REQUIRED`(기존) |
| 500자 초과 | 400 `INVALID_INPUT_VALUE`(기존 메시지) |
| 열린 신청 있음 | 409 `CREATOR_WITHDRAWAL_ALREADY_PENDING`(기존) |
| 조건 미충족 | 409 `CREATOR_WITHDRAWAL_CONDITION_UNMET` + 「진행중 공구 1건 · …」(기존 `Result.summary()`) |

**정지 중 신청은 허용**한다(§51-5 「정지 중 신청 — 허용 · 조건은 그대로」 · 기존 서비스도 막지 않는다).

### 4-4. `POST …/withdrawal-requests/{requestId}/cancel`

`CreatorWithdrawalService.cancel(creatorId, requestId, now)` 그대로 → 204. 남의 신청 · 없음 404 `CREATOR_WITHDRAWAL_NOT_FOUND` · 처리된 신청 409 `CREATOR_WITHDRAWAL_NOT_PENDING`. 취소하면 열린 신청 행이 없어지므로 `CreatorSanctionGuard` 의 대기 중 제약(새 연결 수락 · 계약 서명 요청)이 **같은 순간** 풀린다(S7 「취소하면 제약도 함께 풀린다」).

### 4-5. `POST …/withdrawal-requests/{requestId}/acknowledge`

- 본인 신청 ∧ `REJECTED` → `result_acknowledged_at = now`. 이미 채워져 있으면 그대로 204(멱등).
- `REJECTED` 가 아니면 409 `CREATOR_WITHDRAWAL_NOT_REJECTED`(신규).
- 반려 사유 · 이력은 운영자 쪽에 그대로 남는다(S8 「사유와 이력은 운영자 쪽에 보존」) — 이 호출은 표시 플래그만 바꾼다.

```
 ⑤ CreatorAccountPayoutHook.hold(creatorId, now) — SCHEDULED → BLOCKED(CREATOR_ACCOUNT_UNVERIFIED) · 정산 이력 PAYOUT_BLOCKED
 ⑥ AfterCommit → CreatorAccountVerificationService.verify(creatorId)
```

응답 200 = 5-1 의 정산 정보(`verification.status = VERIFYING`). 확인 결과는 비동기로 반영되고 FE 는 다시 조회한다.

**하지 않는 것** — 진행 중 지급이 있다고 변경을 막지 않는다(§50-6 ②-A ㉢ — 시안은 「허용 + 보류」). 지급 예정일이 가까우면 「입금 후에 변경하는 것이 안전합니다」(T6)는 FE 문구다.

### 6-3. 확인 — `CreatorAccountVerificationService.verify(creatorId)`

`domain.settlement.service` 에 둔다 — PG 셀러 동기화(`SettlementPartnerSyncService`)와 지급 보류 훅을 함께 부르는 자리라 정산 도메인이 소유한다.

```
verify(creatorId)
 ① 읽기 트랜잭션: prepareCreator(creator) — 현재 계좌로 프로필 · 계좌 지문(hash) 생성
      프로필 사전 검사에서 계좌 사유(ACCOUNT_INVALID · UNSUPPORTED_BANK · ACCOUNT_MISSING)로 막히면 → FAILED(코드)로 ③
 ② 트랜잭션 밖: gateway.isExternal() == false 면 APPROVED 로 간주 / 아니면 gateway.ensure(profile)
      — 연결이 없으면 셀러를 **만든다**(Q1) · 있으면 계좌만 수정
 ③ 쓰기 트랜잭션: creator FOR UPDATE
      · 지금 계좌 지문 ≠ ①의 지문 → 결과 버림(그 사이 또 바뀌었다 — 뒤 호출이 판정한다)
      · 1-2 표대로 markAccountVerified(now) / markAccountFailed(code) / 그대로(VERIFYING)
      · 셀러 연결 저장(link — 기존 메서드)
 ④ VERIFIED 면 CreatorAccountPayoutHook.release(creatorId, today, now)
```

- `SettlementPartnerSyncService` 에는 `verifyCreatorAccount(creatorId)` 를 더해 ① ~ ②를 맡기고, 44 토스 설계서 4-3 이 예고한 `onCreatorAccountChanged` 자리를 이 메서드가 채운다(브랜드 `onBrandAccountChanged` 와 달리 **연결이 없어도 부른다**).
- 외부 호출은 트랜잭션 밖 · 읽기 · 쓰기는 각각 짧은 트랜잭션 — 기존 동기화 구조 그대로(44 토스 0-11).
- 예외는 밖으로 내지 않는다(로그). 계좌 변경 자체는 이미 커밋됐다.

### 6-4. 재시도 — `VERIFYING` 이 남는 경우

| 원인 | 풀리는 때 |
| --- | --- |
| PG 일시 장애 · 타임아웃 | 지급 배치 앞단(`SettlementPayoutService.releaseBlocked` — 영업일 10:00)에 **0단계** `retryVerifying()` 을 더한다 — `VERIFYING` 인플루언서를 최대 N명 다시 `verify` |
| `FORBIDDEN_SELLER_MODIFY`(그 셀러에 `REQUESTED` 지급이 있어 토스가 수정을 거절) | 그 지급이 끝난 뒤 같은 배치 앞단 재시도 |
| 프로필 미완성(`PARTNER_NOT_READY` — 예: 휴대폰 없음) | 계좌 문제가 아니므로 `VERIFYING` 으로 남는다 — 07b 보류 사유 「정산 계좌 확인 중」이 운영자에게 보인다 |

영업일 하루 한 번이면 장애 직후 변경한 인플루언서는 다음 영업일까지 「확인 중」이다. 더 촘촘히 돌릴지는 Q10.

### 6-5. `PayoutBlockPolicy` — 사유 하나 추가

| 구간 | 효과 |
| --- | --- |
| 확정 | 인플루언서 지급 행 `BLOCKED`(기존 `SettlementConfirmService` 분기) · 브랜드 · 플랫폼 몫은 예정대로 |

### 6-6. `CreatorAccountPayoutHook` — 보류 · 해제

`CreatorSettlementSanctionHook` 을 그대로 본뜬다(호출자 트랜잭션 합류 · `MANDATORY`).

- `hold(creatorId, now)` — `findScheduledForCreator` → `holdScheduled(id, CREATOR_ACCOUNT_UNVERIFIED)` · 정산 이력 `PAYOUT_BLOCKED`(「인플루언서 몫 · 정산 계좌 확인 중」).
- `release(creatorId, today, now)` — 사유가 `CREATOR_ACCOUNT_UNVERIFIED` 이거나 사유 없이 `BLOCKED` 인 인플루언서 행을 `PayoutBlockPolicy` 로 **다시 판정**한다. 남은 사유가 없으면 `SCHEDULED(due = max(지급 예정일, 오늘))`, 남으면(세금계산서 확인 전 · 정지 등) 이 사유 코드만 지우고 보류 유지. 이력 `PAYOUT_HOLD_RELEASED`.
- 배치 앞단의 `releaseIfUnblocked` 는 **사업자 건을 풀지 않는다**(운영자 M4 몫) — 그래서 사업자 인플루언서의 계좌 확인 보류는 배치에 맡기지 않고 이 훅이 직접 푼다. 정지 훅이 같은 이유로 직접 푸는 것과 같다.
- `FAILED` 는 풀지 않는다 — 다른 계좌로 다시 변경해야 한다.

### 6-7. 계좌 확인 실패의 표시

시안에 실패 화면이 없다(§50-3 「예금주 불일치는 실명 확인 절차의 응답이라 이 화면에서 다루지 않는다」). 서버는 `verification.status = FAILED` · `failReason` 만 내리고, 화면 문구는 기획 회신(R-4)으로 넘긴다. 알림 훅은 `CreatorMemberNotifier.accountVerificationFailed(creatorId, reasonLabel)`(로그 스텁 · 발송 인프라 없음).

## 7. 사업자 구분 변경 — 스튜디오(T4 ~ T10)

### 7-1. `POST /v1/creator/basic-info/business-type-change-requests`

```jsonc
// T7 개인사업자로
{ "targetType": "BUSINESS", "businessRegistrationNumber": "123-45-67890",
  "evidenceFileUrl": "https://…/creator-document/….pdf", "evidenceFileName": "사업자등록증_뷰티소연.pdf", "evidenceFileSize": 1258291 }
// T8 비사업자로

  "evidenceFileUrl": "https://…/creator-document/….pdf", "evidenceFileName": "폐업사실증명원_소연컴퍼니.pdf", "evidenceFileSize": 430080 }
```

`targetType` 을 명시로 받는다 — 방향은 현재 구분이 정하지만, 두 탭에서 동시에 누르는 경우 명시값이 현재 구분과 맞는지 서버가 확인해야 엉뚱한 방향의 요청이 생기지 않는다.

| 검증 | 응답 |
| --- | --- |
| `targetType` 누락 | 400 `INVALID_INPUT_VALUE` |
| `targetType` = 현재 구분 | 409 `CHANGE_REQUEST_BUSINESS_TYPE_MISMATCH`(신규) |
| BUSINESS — 등록번호 `^\d{3}-\d{2}-\d{5}$` | 400 「사업자등록번호 형식이 올바르지 않습니다. (예: 123-45-67890)」(온보딩 문구 · 하이픈 포함 표기 규칙) |
| INDIVIDUAL — `ResidentRegistrationNumber.normalize` = null | 400 「주민등록번호를 정확히 입력해 주세요.」(온보딩 문구 · 원문을 메시지에 싣지 않는다) |
| 증빙 URL · 파일명 · 크기 누락 | 400 `CHANGE_REQUEST_EVIDENCE_REQUIRED`(기존) |
| `evidenceFileSize` > 10MB | 413 `FILE_SIZE_EXCEEDED` + 업로드와 같은 10MB 문구(9-1 — 업로드에서 이미 막지만 서버가 한 번 더) |
| 열린 요청 있음 | 409 `CHANGE_REQUEST_ALREADY_PENDING`(기존 · 생성 컬럼 UNIQUE 위반도 같은 코드로 변환) |
| 탈퇴 회원 | 409 `CREATOR_WITHDRAWN` |

미입력은 화면에서 `[변경 요청]` 비활성만이다(T7 · T8) — 위 400 은 API 직접 호출 방어선이다.

**막지 않는 것** — 계좌 변경 중 · 계좌 확인 실패 · 정지 중 · 탈퇴 심사 중에도 요청할 수 있다. §50-2 「버튼은 모든 상태에서 같은 자리」이고, 두 절차가 동시에 진행되지 못할 이유가 없다. 주민번호 앞 6자리와 본인 인증 생년월일을 서버가 대조하지 않는다 — 대조는 운영자가 서류로 한다(§16-2a).

**트랜잭션**

```

 ② requestCode = generateRequestCode()(브랜드와 같은 일련번호 · 2-4)
 ③ BrandChangeRequest.createForCreator(code, creator, type, requesterName = showroomName, evidence…)
      + 항목(대조표 「현재 값 / 변경 요청 값」)
        TO_BUSINESS  : CREATOR_BUSINESS_TYPE「개인 (비사업자)」→「개인사업자」 · CREATOR_BUSINESS_REGISTRATION_NUMBER — → 「123-45-67890」
        TO_INDIVIDUAL: CREATOR_BUSINESS_TYPE「개인사업자」→「개인 (비사업자)」 · CREATOR_RESIDENT_REGISTRATION_NUMBER — → 「900101-*******」
      + TO_INDIVIDUAL 이면 requested_secret_enc = PersonalDataCipher.encrypt(정규화 13자리)
 ④ 닫지 않은 이전 결과(APPROVED · REJECTED)가 있으면 acknowledge — 새 요청이 옛 반려 배너를 대신한다
 ⑤ 201 { requestId, requestCode, status: "PENDING", requestedAt }
```

요청 DTO 의 `toString()` 은 온보딩 DTO 처럼 주민번호를 `****` 로 가린다(요청 로깅에 고유식별정보가 남지 않게).

### 8-2. 상세 — `GET /v1/admin/change-requests/{requestId}`

기존 `DetailResponse`(항목 대조표 · 증빙 · 처리 이력 · 이전 / 다음)에 인플루언서 요청일 때만 두 블록을 더한다.

- 사업자 상태(계속 · 휴업 · 폐업) 국세청 조회는 붙이지 않는다 — 시안은 홈택스 수동(§16-8 ⓖ).

### 8-3. 승인 — `POST /v1/admin/change-requests/{requestId}/approve`

`ChangeRequestApplier` 가 `requesterType` 으로 갈라 `CreatorBusinessTypeChangeApplier`(신규 · 같은 패키지)를 부른다.

```
 ① 요청 잠금 · PENDING 확인(기존)
 ② creator FOR UPDATE · WITHDRAWN 이면 409 CREATOR_WITHDRAWN
    현재 구분 ≠ 요청의 출발 구분이면 409 CHANGE_REQUEST_BUSINESS_TYPE_MISMATCH(그 사이 다른 경로로 바뀌었다)
 ③ 7-5 표대로 convertToBusiness(brn, evidenceUrl) / convertToIndividual(decrypt 없이 암호문 그대로 이전, masked, now)
 ④ 예금주 규칙 검사 — 위반이면 markAccountChangeRequired()(→ 정책이 이후 정산을 막는다 · T10) · 1차는 위반이 생기지 않는다(1-4)
 ⑤ request.approve(operatorId) · requested_secret_enc = NULL
 ⑥ 인플루언서 처리 이력 BUSINESS_TYPE_CHANGE_APPROVED(운영자 · 「개인 (비사업자) → 개인사업자 · CHG-2026-0031」)
 ⑦ AfterCommit: PG 셀러 재등록(8-5) · 결과 메일(업무 이메일) · 스튜디오 배너는 result_acknowledged_at NULL 로 자연 노출
```

- 정산 쪽에는 **아무것도 하지 않는다** — 적용 시점은 생성 스냅샷이 만든다(1-6).
- 「되돌리려면 인플루언서가 다시 요청해야 합니다」(C7b) — 되돌리는 어드민 경로를 만들지 않는다.
- 부분 승인 없음(§16-4 · 항목 전체 승인 / 반려).

### 8-4. 반려 — `POST /v1/admin/change-requests/{requestId}/reject`

- 사유는 `ChangeRequestRejectReason.supports(type)` 로 거른다 — 브랜드 사유는 인플루언서 요청에 못 쓴다(기존 `CHANGE_REQUEST_REJECT_REASON_TYPE_MISMATCH`). `GET /reject-reasons?type=TO_BUSINESS` 가 C8b 목록을 그대로 내린다.
- `OTHER` 만 상세 필수 · 500자(기존). 반려 즉시 `requested_secret_enc = NULL`.
- 인플루언서 처리 이력 `BUSINESS_TYPE_CHANGE_REJECTED`(detail = 사유 라벨) · 결과 메일 · 스튜디오 T4a / T9a 배너(사유 문장 + 상세 그대로 — §16-5 「가공 없이 전달」).
- 대기 기간 없이 즉시 재요청 가능(§16-2a) — 반려 행은 남고 새 요청은 새 행이다.

### 8-5. PG 셀러 유형 — 토스는 사업자번호 · 유형을 바꿀 수 없다 `[근거 대기-PG]`

토스 셀러 수정(`POST /v2/sellers/{id}`)은 **사업자번호 · 유형 불변**이다(44 토스 설계서 0절 표). 그대로 두면 이미 셀러가 연결된 인플루언서는 승인 뒤 첫 동기화(계좌 변경 · 확정 · 지시)에서 사업자 블록이 붙은 수정 요청이 거절되고 지급이 `BLOCKED` 로 멈춘다. 그래서 승인 직후 **새 유형의 셀러를 새 참조 id 로 등록**해야 한다.

- 제안: `creator.pg_partner_generation`(INT · 기본 1) 하나를 두고 `partnerRef = {prefix}creator-{creatorId}` 뒤에 세대 2 부터 `-g{n}` 을 붙인다(토스 7 ~ 20자 안 · `t-creator-1234567-g2` 20자). 승인 ⑦에서 세대 + 1 · 기존 셀러 id 는 처리 이력 detail 에 남기고 연결 필드를 비운 뒤 `verify(creatorId)` 로 새 셀러를 만든다. 옛 셀러 삭제는 44 의 미결 L-5(탈퇴 · 폐업 시 셀러 삭제)와 같이 간다.
- 확인할 것: ① 이전 구분 정산의 지급을 **새 유형 셀러**로 보내도 되는가 ② 개인사업자 셀러의 본인인증 문자가 다시 가는가(첫 지급 지연) ③ 같은 사람(같은 휴대폰)으로 셀러 2개가 공존할 수 있는가. 답이 오기 전에는 **P4 를 운영에 내지 않는다**(Q6). 컬럼은 답을 보고 V201 에 넣거나 따로 판다.

### 8-6. 어드민 인플루언서 상세 연계

`AdminCreatorDto` 의 `pendingBusinessTypeChange`(지금 `Object` · 항상 null)를 `{ changeRequestId, requestCode, type, requestedAt }` 레코드로 바꾸고, 그 인플루언서의 `PENDING` 인플루언서 요청에서 채운다 — 정산 정보 카드의 「변경 요청 확인 중 ↗」. 처리 이력 이벤트 2종은 이미 enum 에 있다(2-1).

## 부록. 관찰 — 이번 범위 밖

1. **소비자 앱 탈퇴가 인플루언서 승인제를 우회한다** — `/v1/user/**` 는 `CREATOR` 도 들어오고, `UserService#withdrawUser` 는 진행 중 **주문**만 본다. 인플루언서가 앱에서 탈퇴하면 `users.status = WITHDRAWN` → `PublicShowrooms.visible()` 이 쇼룸을 숨기는데 `creator.status` 는 `ACTIVE` 로 남고, 진행 중 공구 · 미정산이 있어도 막히지 않는다. §51-5 「셀프 즉시 탈퇴 없음」과 정면으로 어긋난다 → Q7.
2. **계좌번호 15 ~ 16자리** — 기획 · 온보딩은 10 ~ 16자리를 받지만 토스는 계좌번호 14자를 넘으면 받지 않는다(44 토스 4-2 ① 사전검사 `ACCOUNT_INVALID`). 지금은 지급일에 터지고, 이 설계 뒤에는 변경 직후 `FAILED` 로 드러난다. 상한을 14로 줄일지는 은행별 실제 자리수와 같이 기획 확인.
3. **서류가 공개 URL 이다** — 통장 사본 · 사업자등록증 · 폐업사실증명원이 `ImageService` 를 거쳐 CloudFront 공개 URL 로 저장 · 응답된다. 고유식별정보가 담긴 서류라 presigned(만료형) 조회로 바꾸는 것이 맞다 — 브랜드 서류와 함께 별건으로. 서버가 서류 URL 이 우리 버킷에서 왔는지 검사하지 않는 것도 같은 묶음이다(임의 URL 저장 가능).
4. **요청 코드 동시 생성** — `generateRequestCode()` 는 `count + 1` 이라 동시에 두 건이 들어오면 UNIQUE 충돌로 한쪽이 500 이 된다. 인플루언서 요청이 같은 일련번호를 쓰면서 확률이 조금 오른다 — 충돌 시 1회 재시도(또는 시퀀스 테이블)를 P4 에 같이 넣는다.
5. **`CreatorSanctionGuard` 에 스튜디오 화면용 상태가 없다** — 53 4-2 가 예고한 `GET /v1/creator/profile` 의 `sanction` 블록이 아직 없다. 스튜디오 정지 화면이 오면 이 설계의 계정 조회 응답에 붙이는 쪽이 자연스럽다.
