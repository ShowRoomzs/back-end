## 1. 범위와 판정 기준

- 대상: 스튜디오 `/v1/creator/basic-info/**` **11개** 엔드포인트 + 연계 지점 — 서류 업로드(`POST /v1/creator/images?type=CREATOR_DOCUMENT`) · 어드민 변경 요청 큐의 **승인 · 반려**(스튜디오 반영 확인 목적) · 어드민 탈퇴 반려(S8 재료) · 지급 보류(`PayoutBlockPolicy` · `CreatorAccountPayoutHook` · 지급 배치 앞단 0단계 `retryVerifying`) · 탈퇴 대기 중 제약(`CreatorSanctionGuard`) · 마이그레이션 V201 ~ V203.
- 범위 밖: 어드민 변경 요청 상세의 대조표 · `compareItems` · `approvalImpact` 세부(16 설계서 8절이 정본 — 여기서는 큐 편입과 승인 · 반려 결과만 본다) · 탈퇴 **승인 · 반려 판정 자체**(53) · PG 셀러 재등록(S6) · 알림 **발송**(`CreatorMemberNotifier` 로그 스텁) · FE 전용 항목(50 설계서 12절).
- 테스트 · QA 환경은 `settlement.payout.mode=SIMULATED` 다. 이때 PG 셀러 게이트웨이는 `isExternal() = false` 라 **계좌 확인이 즉시 통과**한다. 실패 · 장애 · 대기 결과는 `FakeSettlementPartnerGateway`(`failFor(payee, code, reason)` · `approveFor(payee)` · `calls(payee)`)로 재현한다.
- 계좌 변경 응답(`PUT …/settlement-account`)은 **커밋 전 상태**(`VERIFYING`)다. 실명 확인은 커밋 뒤(`AfterCommit`)에 돌므로 결과는 `GET …/settlement` 를 **다시 불러** 본다. 통합 테스트는 트랜잭션 없는 MockMvc 호출이어야 AfterCommit 이 실행된다.
- 아래 케이스는 **테스트 명세**이며 통과 기록이 아니다. 모듈이 없는 동작(알림 발송 · 토스 실연동 · S6 재등록)은 14-3에 적고, 지금 호출되지 않는다는 이유로 통과 처리하지 않는다.
- 시각은 서버 `Asia/Seoul`. 영업일 = 주말 제외 + `business_holiday`. 탈퇴 처리 기한 `due_date` = 신청일 + **5영업일**(`CreatorWithdrawalService.APPROVAL_DUE_BUSINESS_DAYS`). API 는 `LocalDateTime.now()` 를 쓰므로 날짜를 고정해야 하는 케이스는 도메인 서비스를 `now` 인자로 직접 부른다.

### 1-3. 공통 확인 방법

1. 쓰기 한 번마다 **DB 행 · 처리 이력 · 스튜디오 응답**을 같이 본다. `creator`(계좌 · 확인 상태 · 구분 · 주민번호 컬럼) · `creator_withdrawal_request` · `brand_change_request`(+ 항목) · `creator_settlement_account_history` · `creator_admin_history`(53 처리 이력) · `settlement_payout` · `settlement_history`.
2. 실패 요청은 HTTP 상태 + 응답 `code` 를 보고 **부수 효과가 없는지**(행 · 이력 · 보류 · 상태 불변) 본다. **주의 — 응답 `code` 가 enum 이름과 다른 것**: `INVALID_INPUT_VALUE` → `INVALID_INPUT` · `INVALID_FILE_EXTENSION` → `INVALID_FILE_TYPE`. 그 밖의 코드는 enum 이름 = 응답 `code`.
3. **원값이 응답에 없어야 한다** — 실명 · 휴대폰 · 계좌번호 전체 · 주민번호 뒤 7자리 · 주민번호 암호문은 응답 본문 문자열 검색으로 확인한다(마스킹 필드 값만 보는 것으로는 부족하다).
4. 버튼 노출은 서버 값이다 — `withdrawal.state` · `actions.businessTypeChange`(`REQUEST_TO_BUSINESS · REQUEST_TO_INDIVIDUAL · CANCEL`) · `actions.accountChange`(항상 `true`).
5. 지급이 걸린 케이스는 매번 **인플루언서 · 브랜드 · 플랫폼 3행의 `status · fail_code · due_date`** 와 정산 이력 `PAYOUT_BLOCKED / PAYOUT_HOLD_RELEASED` 건수를 같이 본다. 브랜드 · 플랫폼 행이 움직이면 실패다.
6. 알림(`CreatorMemberNotifier`)은 스텁 — 발송 여부를 판정에 넣지 않는다. 호출 여부만 필요하면 스파이로 본다.
7. 시안 · 설계서 · 코드가 충돌하면 15절에 기록하고 어느 쪽으로도 임의 통과시키지 않는다.

## 13. 끝까지 도는 흐름(E2E) — 시안 상태 순회

한 테스트에서 단계마다 `GET /account` · `GET /settlement` 를 다시 불러 1-2 판정표의 필드를 확인한다.

| ID | 흐름 | 단계마다 볼 것 |
