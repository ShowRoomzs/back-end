## 1. 순서를 이렇게 정한 이유

### 1-1. 16과 50이 같은 기능을 서로 다르게 설계했다 — 코드보다 정본이 먼저다

인플루언서 사업자 구분 변경(§16-2a)을 16은 **어드민 쪽에서**, 50은 **스튜디오 쪽에서** 설계했는데, 둘 다 `brand_change_request` 일반화 · 스튜디오 요청 API · 어드민 승인 · 반려까지 각자 끝까지 그렸다. 테이블 컬럼 이름 · 생성 컬럼 문법 · API 경로 · 에러 코드 · 응답 모양 · 마스킹 방식 · PG 처리가 27군데에서 다르다(2-2). 어느 한쪽을 정하지 않고 착수하면 S3 · S5 에서 되돌아가야 한다. 그래서 **S0 을 코드 작업보다 앞에** 둔다.

### 1-2. 마이그레이션 번호가 충돌하고, V194 ~ V198 은 쓸 수 없다

- 06 = V200, **16 = V200**(충돌), 50 = V201(V200 을 06 몫으로 비워 둠).
- Flyway 설정(`application-local.yml` · `application-prod.yml`)에 `out-of-order` 가 없다(기본 `false`). V199 가 적용된 DB 에 **V194 ~ V198 을 나중에 넣으면 검증 실패로 부팅되지 않는다**. 52 설계서가 그 번호를 「동시 진행 작업 몫」으로 남겨 두었지만, 실제로 쓰인 적이 없다. 새 번호는 전부 **V200 이상**이다.
- 50 은 V201 하나에 세 테이블을 다 넣었지만 스스로 「단계별로 넣으면 V201 · V202 … 로 쪼갠다」고 적었다. 단계와 번호를 1:1 로 맞춘다(2-1).

### 1-3. 단계 사이의 실제 의존

| 뒤 단계 | 앞 단계에서 필요한 것 | 근거 |
| --- | --- | --- |
| S3 → S4 | `creator.account_verification_status` 등 컬럼(V202) · 정산 정보 조회 응답(계좌 변경 결과를 다시 읽는 곳) | 50 2-2 · 6-2 「응답 200 = 5-1 의 정산 정보」 |
| S3 → S5 | ① 주민번호 마스킹 형식 `900101-*******`(비사업자 전환 항목 값이 이 형식으로 `Creator` 에 옮겨진다) ② 로그인 인플루언서의 `CREATOR_DOCUMENT` 업로드(증빙) ③ `resident_number_registered_at` 컬럼 ④ 배너가 들어갈 `GET /basic-info/settlement` | 50 9-2 · 9-1 · 2-2 · 5-1 |
| S4 → S6 | `SettlementPartnerSyncService.verifyCreatorAccount` — 재등록 뒤 새 셀러를 이것으로 만든다 | 50 8-5 |

| S2 ↔ S3 | 같은 `api/creator/basicinfo` 컨트롤러 · Docs · DTO 를 나눠 쓴다 → **병행하면 충돌** — 순서대로 | 50 3절 |
| S1 ↔ 나머지 | 겹치는 파일 없음 — 06 은 `Market` · `SellerService` · `SellerBasicInfo*` · `ProductDto` · `AdminBrand*` 만, 16/50 은 `Creator` · `changerequest` · `settlement` · `api/creator` 만 | 06 7절 · 16 7절 · 50 11절 |

주민번호 마스킹을 바꾸면 영향받는 곳은 `CreatorAuthService:114`(온보딩 저장)와 `MyShowroomResponse:110`(`/v1/creator/profile`) 두 곳뿐이다. 50 의 진단과 같다.

### 1-4. 값과 위험

- **S1 을 맨 앞에** 둔다 — 지금 운영 중인 **금전 결함**(온보딩에서 무료배송 기준금액을 비우면 그 브랜드의 모든 주문이 무료배송 · 06 D-1)을 담고 있고, 규모가 가장 작고, 다른 단계와 독립이다.
- **S5 는 S6 없이 운영에 내지 않는다** — 토스 셀러는 사업자번호 · 유형을 수정할 수 없다(50 8-5 · 44 토스 0절). 이미 셀러가 연결된 인플루언서의 구분 변경을 승인하면 다음 셀러 동기화가 거절되어 **지급이 멈춘다**. 16 의 「수정 시도 → 실패 시 `PARTNER_NOT_READY`」로는 풀리지 않는다.
- S4 는 지급 동작을 바꾼다(새 보류 사유) — 단독 배포는 가능하지만 정산 운영에 미리 알린다.
