## 1. 계약 — 성립 시점 · 공구 생성 · 해지 · 취소 동의 · 서명 기한 · 초안 승인 기록

### 1-0. 먼저 정한 것

1. **성립 일시는 새 열이다.** `concluded_at` 은 `CONCLUDED` 전이 시각(= 공구 생성 처리 시각)으로 그대로 두고, **`established_at`(양측 서명 완료 시각)** 을 더한다. `concluded_at` 의 뜻을 바꾸면 44 정산 · 1017 성과 · 운영 지표가 읽는 「체결」 시각이 흔들린다. 「계약 성립 일시」가 필요한 자리(공구 이력 맨 아래 줄 · 세 역할 상세 스텝 · 해지 화면 · 계약서 PDF)는 전부 `established_at` 을 쓴다.
2. **`CONCLUSION_PENDING` 값은 그대로 두고 라벨만 「공구 생성 대기」** 로 바꾼다. DB 저장 문자열이고 세 역할 FE 가 값으로 분기한다. `CONCLUDED` 라벨 「체결완료」는 유지(시안도 그대로).
3. **해지는 상태다**(`TERMINATED` · 「해지」 · 종결 · 중립). 성립 뒤(`CONCLUSION_PENDING` · `CONCLUDED`) 공구가 오픈되기 전까지만. `CANCELED`(취소)는 **`SIGNING` 만** 남긴다 — 성립된 계약을 「취소」하는 길을 닫아 두 종결이 겹치지 않게 한다(`ADMIN_CANCELABLE = {SIGNING}`). `CONCLUSION_PENDING` 의 취소 → 해지로 흡수(14절 Q2).
4. **해지 사유 체계는 두 겹이다** — 당사자 요청 사유(파트너 09 C4 4종 = 기존 `SuspensionReasonCode` 재사용 · 08 C9 자유 입력은 그 메모) · 운영자 해지 사유(어드민 C7 4종 = 신규 `ContractTerminationReasonCode`). B9 「사유 구분 + 메모」 = 요청의 사유 코드 라벨 + 메모. 네 화면의 불일치(14절 충돌 1)를 이렇게 닫는다.
5. **상대방 동의는 운영팀 채널에서 사람이 확인한다**(기-06 · 05). 시스템은 ① 요청이 들어오면 **상대방 운영팀 채널에 「계약 취소/해지 동의 확인」 카드**를 붙이고 ② 운영자가 처리할 때 **「상대방 동의를 운영팀 채널에서 확인함」 체크**를 요구하고 ③ 결과 카드를 **양측** 채널에 붙인다. 동의 자체를 버튼 · 상태로 받지 않는다(시안 「카드에는 버튼이 없다 · 동의는 답글로」).
6. **서명 기한 기본값은 서버가 제안만 한다**(기-07). 모두싸인에 입력하는 사람은 운영자고 값은 운영자 입력이 진실이다. 제안값 = `group start_at − 3일 23:55`(설정값). 검증은 기존(발송 시각보다 뒤)만.
7. **초안 승인 기록은 브랜드가 쓴다**(기-30). 시안에 입력 화면이 없어 가정이지만(14절 Q5) 「브랜드 사전 검수 · 기록 전용 · 출처 스레드」라는 설명이 주체와 출처를 정한다. 운영자 · 인플루언서는 읽기만.

### 1-4. 해지 — 요청(파트너) · 처리(어드민) · 공구 종결

**셀러 요청** — `POST /v1/seller/contracts/{id}/termination-request` `{ reasonCode: SuspensionReasonCode, memo }` · `DELETE …/termination-request`(철회 · PENDING 만) · 공구 화면 09 B3 의 [해지 요청] 은 **같은 API** 를 `contractId` 로 부른다(공구 → `contract_id`).

- 조건: 내 계약 · `status ∈ TERMINABLE` · 공구가 없거나 `GroupBuyStatus ∈ {PREPARING, READY}` · PENDING 요청 없음 · **내 정지 중이면 허용**(해지는 새로 벌이는 일이 아니라 거두는 일 — 1017 8-0 원칙 · 14절 Q3). 위반 → 409 **`CONTRACT_TERMINATION_NOT_ALLOWED`** / 중복 → 409 **`CONTRACT_TERMINATION_ALREADY_PENDING`**.
- 효과: 행 PENDING · 이력 `TERMINATION_REQUESTED`(SELLER · detail = 사유 라벨) · **상대방(인플루언서) 운영팀 채널에 `CONTRACT_CLOSE_CONSENT_REQUEST` 카드**(1-6) · `consent_card_id` · 알림 `CONTRACT_TERMINATION_REQUESTED`(인플루언서) · 어드민은 로그(1017 14-2 #10 — 어드민 알림함 없음 · 어드민 계약 목록에 **「해지 요청」 큐** 추가 아래).
- 계약 상태는 바뀌지 않는다(「처리 전까지 체결완료 유지」). 공구 `GroupBuyPermissionPolicy.isRequestBlocked` 에 **PENDING 해지 요청**을 더해 중단 · 연장 요청과 겹치지 않게 한다.
- 공구가 오픈되면(`GroupBuyLifecycleService#open`) PENDING 요청을 `LAPSED` — 「공구가 오픈되면 중단 요청으로 바뀝니다」(C9 안내)는 FE 문구 · 서버는 요청을 닫고 알림 1건.
- **오픈 승인과의 관계** — PENDING 해지 요청이 있는 공구의 `AdminGroupBuyCommandService#approveOpen` 은 **막지 않는다**(해지는 운영자가 상대 의사를 확인해 처리하는 일이고, 승인은 다른 운영자 화면이다). 대신 어드민 공구 상세 · 오픈 승인 큐 행에 **`terminationRequested { requestId, requesterName, requestedAt }`** 경고를 싣고, 승인 응답 `warnings[] += TERMINATION_REQUEST_PENDING`. 오픈이 되면 위 규칙으로 LAPSED(14절 Q30).
- 인플루언서 요청(`CREATOR`)은 모델만 열어 두고 API 는 만들지 않는다(스튜디오 S10 은 안내 화면 · 14절 Q4).

**어드민 처리** — `POST /v1/admin/contracts/{id}/terminate`

### 1-7. 서명 기한 기본값(기-07) · 정지 중 기한 경과(B3-s)

## 3. 반품 · 교환 비용 구조(기-18 변경 · 기-20 · 기-32)

### 3-0. 먼저 정한 것

1. **운임 기준은 이미 주문 스냅샷 `base_delivery_fee`(편도) 다** — 시안의 「상품 배송비로 자동 계산」은 구현돼 있다. 이 절이 하는 일은 ① 마켓 `return_fee · exchange_fee` 와 그 입력 · 표시 **폐기** ② **일부 반품 재판정**과 그 원천(무료배송 기준 스냅샷) ③ 재발송 배송비의 **제주 · 도서산간 추가비** ④ 이중 차감 방지 넷이다.
2. **「상품 배송비」= 마켓 기본 배송비.** `Product` 에 배송비 열이 없고 시안 03 · 06 도 마켓 단위 입력이다. 상품별 배송비는 만들지 않는다.
3. **정책 적용 시점 = 결제 시점 스냅샷**(기-20). 무료배송 기준금액 · 권역 추가비를 주문 그룹에 스냅샷하고, 주문 상세 · 클레임 · 정산은 **마켓 현재 값을 다시 읽지 않는다**(`OrderAssembler:112` 수정).
4. **권역 판정은 우편번호**(06 「플랫폼이 자동 분류 · 겹치면 제주 우선」). 제주 = 우편번호 `63000 ~ 63644` 코드 판정 · 도서산간 = 운영 등록 테이블(초기 비어 있음 → 추가비 0). 주문 배송비에도 같은 추가비를 **부과하는 것은 이 설계 범위**다 — 재발송비에만 더하고 주문엔 안 더하면 소비자가 같은 주소로 두 값을 본다(14절 Q10).

## 4. 검수 3갈래 · 귀책 변경 운임 정산 · 초과 환급 송금 · 자동 입고(기-17 · 기-93 · 보완)

### 4-0. 먼저 정한 것

1. **운임 정산은 기록이 먼저다.** 귀책이 바뀔 때 소비자에게 청구 · 환급하는 운임과 브랜드 정산에 반영할 금액을 **`order_claim_freight_adjustment` 한 행**으로 남기고, 환불액 · 추가 결제 · 정산 「± 운임 정산」 줄이 전부 이 행을 읽는다. 06b B2 · 06c M3 · 07b D3 · C10-5 가 「같은 산식」이라고 적은 것을 한 테이블로 보장한다.
2. **운임 금액은 전부 정액 = 그 그룹의 `base_delivery_fee`**(기-93 보완 · 「소비자가 실제 쓴 운임이 아니다」). 착불 운임(브랜드가 낸 회수 운임)도 같은 정액으로 청구한다.
3. **사유 번복 = 검수 통과 + 귀책을 소비자로 전환.** 새 판정 종류(`ClaimInspectionResult.REASON_OVERTURNED`)지 새 흐름이 아니다 — 반품은 환불 진행(차감 늘어남) · 교환은 결제 대기(재발송 배송비 + 착불 운임) 뒤 재발송. 반려(`REJECT`)와 다르다(상품은 받아들인다).
4. **환불이 원래 결제액을 넘는 부분은 PG 가 못 돌려준다.** 초과분은 `order_refund_task` 에 **`method = BANK_TRANSFER`** 행으로 분리해 「송금 대기」 큐에 올리고, 운영자가 송금 뒤 계좌 · 완료를 기록한다. 시스템은 송금하지 않는다. 브랜드 정산에는 「− 운임 정산」으로 회수한다(플랫폼이 선지급 → 브랜드 정산 차감).
5. **자동 입고는 영업일 기준 N**(설정 · 미정 → 가정 3) · 기산 = `collection.arrived_at`(회수 추적 도착). 자동 입고 뒤 검수 기한 2영업일은 기존 규칙.

### 4-2. 자동 입고 — `ClaimAutoReceiveScheduler`

- 매시 10분(`0 10 * * * *`) · 대상 `order_claim_collection` 중 항목이 `ARRIVED` ∧ `arrived_at + order.claim.auto-receive-business-days(3 · 미정)` 영업일의 23:59:59 < now → `OrderClaimService.receive(SYSTEM)` → `RECEIVED` · `auto_received = 1` · `inspect_due_at` 2영업일(기존) · 이력 `AUTO_RECEIVED` · 브랜드 알림 `CLAIM_AUTO_RECEIVED`(「도착 N영업일 경과 · 자동 입고 · 검수 기한 MM.DD」).
- `receive-before-arrival` 설정은 그대로(브랜드가 먼저 누르면 자동 입고는 없다).
- A4 「검수 기한 2영업일」 기산 어긋남(토요일 입고 → 08.26)은 `BusinessDayCalculator.dueAt`(다음 영업일부터 N) 규칙이 맞고 시안 예시가 틀린 것으로 본다(14절 Q13).

### 4-5. 초과 환급 — 송금 대기 큐 · 06c M3

- `RefundTransitions.claim`(및 운영자 환불 편입 `checkRefundable`)에서 환불 합계가 `cancellableAmount` 를 넘으면 **FAILED 대신 분리**: PG 취소 행(`method = PG_CANCEL` · `cancellableAmount` 까지) + **`BANK_TRANSFER` 행**(초과분 · `status = PENDING` · 라벨 「송금 대기」 · `source` 는 원 환불 source 그대로 · `freight_adjustment.settled_via = BANK_TRANSFER` · `refund_task_id`). `REFUND_AMOUNT_EXCEEDED` 는 운임 정산이 아닌 일반 운영자 환불에만 남긴다.

## 8. 인플루언서 계좌 변경 → 변경 요청(기-22)

### 8-0. 먼저 정한 것

1. **기존 `brand_change_request` 테이블 · `ChangeRequest` 모델을 쓴다**(이미 `requester_type = CREATOR` · V203). 유형 **`CREATOR_ACCOUNT`**(15자 · VARCHAR(20) 안) 추가. 어드민 목록 API 는 공용이라 그대로 섞여 나온다(요청 유형 라벨 「계좌 변경 (인플루언서)」).
2. **확인 중 기존 계좌 유지 + 지급 보류** — 어드민 C4b 「이미 지급 요청이 나간 정산은 기존 계좌 · 다음 지급부터 새 계좌」와 스튜디오 T2a 「확인 끝날 때까지 지급 예정 1건 보류」는 **같은 말**로 읽는다: PG 에 지급 요청이 이미 나간 건은 그대로, 아직 안 나간 `SCHEDULED` 건은 **보류**(`CREATOR_ACCOUNT_UNVERIFIED` 재사용 · 라벨 「정산 계좌 확인 중」). 14절 충돌 2. **2026-10-24 보강**(55 계획서 S1): 요청 중에는 계좌 확인 상태가 기존 값이라 지급 배치 재판정 · 세금계산서 대조가 보류를 풀어 **확인 전에 기존 계좌로 지급**했다 — `PayoutBlockPolicy` 가 열린 계좌 변경 요청(`PendingAccountChangeReader` 포트)도 보류 사유로 본다. 요청 중에 새로 확정되는 정산도 보류된다.
3. **승인 뒤에도 토스 셀러 검증은 돈다.** 운영자 확인(통장 사본 · 예금주 = 실명)은 사람 검수, 토스 검증은 PG 계좌 실존 검사 — 둘 다 거친다. 상태 라벨만 「운영자 확인」으로.
4. **온보딩 첫 계좌 등록은 그대로**(즉시 저장 + 토스 검증) — 변경 요청은 「변경」에만(14절 Q23).
