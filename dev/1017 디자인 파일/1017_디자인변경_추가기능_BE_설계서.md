## 1. 알림함 — `domain.notification` 공통 저장소

### 1-0. 먼저 정한 8가지

1. **테이블은 하나다** — `notification(recipient_type, recipient_id)`. 소비자 · 브랜드 · 인플루언서 알림함의 행 모양(제목 · 본문 · 이동 대상 · 읽음 · 시각)이 같고, 다른 것은 보관 기간(소비자 90일 · 파트너 30일 · 스튜디오 30일)과 광고성 여부뿐이다. 수신자별 테이블 셋을 만들면 발생 지점 60여 곳이 세 가지 저장 코드를 든다.
2. **운영팀 채널 시스템 카드 · `post_notification_log` 는 그대로 둔다.** 카드는 소명의 맥락(대화)이고 알림함은 「처리 결과 한 줄 + 이동」이다 — 시안이 정지 알림을 「연결·소통 › 운영팀 채널 · 정지 카드」로 보내는 것이 그 관계다. `post_notification_log` 는 게시물 통지 이력(§24-6 영구 보존)이라 보관 기간이 다르다 — 게시물 통지는 이력을 남기면서 알림함 행도 함께 쓴다.
3. **문구는 발생 시점에 굳힌다**(제목 · 본문 · 대상명). 뒤에 공구명 · 상품명이 바뀌어도 알림은 「그때 그 말」이어야 한다(`post_notification_log.payload` 와 같은 원칙).
4. **이동 대상은 `{targetType, targetId}` 로만 내리고 상태를 재현하지 않는다**(파트너 시안 ③) — FE 가 현재 상태의 상세로 보낸다. 삭제된 대상(④)은 FE 가 상세 404 를 받아 토스트 「이미 삭제된 항목입니다」로 처리한다 — 서버가 매 조회마다 60종 대상의 생존을 확인하면 목록이 가장 무거운 요청이 된다.
5. **읽음은 행 단위, 배지는 두 규칙이다.** 파트너 · 스튜디오 배지 = **안 읽은 수**([모두 읽음] = 전부 `read_at` 세팅). 소비자 배지 = **목록 진입 뒤 새로 온 수**(C11 「목록에 들어오면 종 아이콘 숫자 배지만 초기화 · 로즈 점은 탭해야 사라짐」) → `users.notification_badge_seen_at` 이후 생성된 행 수. 두 숫자가 다르다는 것을 응답 필드 이름으로 드러낸다(`badgeCount` vs `unreadCount`).
6. **소비자만 푸시가 간다.** `DeviceToken` 은 `Users` 소유다 — 셀러는 `Users` 가 없어 토큰이 없고, 인플루언서는 소비자 앱 계정에 토큰이 있을 수 있으나 스튜디오 알림을 소비자 앱 푸시로 보내지 않는다(시안 「알림 외부 발송 — 결정 대기」). 파트너 · 스튜디오는 **인앱 알림함만** · 폴링은 FE(60초).
7. **광고성 판정은 유형(enum)이 든다** — 팔로우 쇼룸 새 공구 · 새 게시물 · 마감 임박 · 혜택 4종만 `advertising = true`. 이 네 유형은 ① 토글 동의가 있어야 행 자체를 만들고(C11 「광고 수신 미동의면 광고성 행이 빠진다」) ② 푸시 제목 앞 `(광고)` · 본문 끝 「수신거부: 마이 > 설정 > 알림」 ③ **21:00~08:00 미발송**(outbox 지연) ④ 새 게시물은 **하루 묶음**이다. 거래 알림은 즉시 · 항상.
8. **발생 지점은 기존 포트 뒤로 숨긴다.** `MemberNotifier` · `ContractNotifier` · `GroupBuyNotifier` · `SettlementNotifier` 인터페이스는 그대로 두고 **구현체를 `NotificationPublisher` 호출로 바꾼다**(로그 스텁 교체). 포트가 없는 지점(연결 수락 · 운영팀 답장 · 게시물 승인 등)만 호출을 새로 심는다. 호출은 전부 `AfterCommit.run` 안이거나 `@TransactionalEventListener(AFTER_COMMIT)` 다 — 알림이 조치를 되돌리지 않는다.

### 1-6. 소비자 발송 규칙 — `NotificationPublisher` · outbox

```
NotificationPublisher.publish(NotificationCommand)            ← 도메인 트랜잭션 안(행 insert)
  ├ 광고성 · 토글 미동의           → 행을 만들지 않는다(C11 「광고성 행이 빠진다」)
  ├ dedup_key 충돌                → 무시(마감 임박 · 묶음 재진입)
  └ afterCommit:
       ├ USER · 거래 알림          → PushSender.send(findUserTokens) 즉시 · 실패는 로그만
       ├ USER · 광고성 · 묶음 아님  → outbox(send_after = now, 야간이면 다음 08:00 KST)
       ├ USER · 광고성 · 새 게시물  → outbox upsert(digest_key = FOLLOW_POST:{creatorId}:{date}) · digest_count++ · 알림함 행은 묶음 대표 1행을 갱신(「새 게시물 3개」)
       └ SELLER · CREATOR          → 푸시 없음

NotificationPushOutboxScheduler  ── 1분마다: sent_at IS NULL AND send_after <= now → 발송 · sent_at · 실패 attempt++(3회 뒤 포기 · last_error)
NotificationRetentionScheduler   ── 매일 04:00: USER 90일 · SELLER/CREATOR 30일 지난 행 삭제 · outbox 7일
GroupBuyEndingNoticeScheduler    ── 매일 10:00: end_at ∈ [내일 00:00, 내일 24:00) · IN_PROGRESS → 수신자 = cart.group_buy_id 보유자 ∪ wishlist(product → contract_item → group_buy) 보유자 · 토글 ON · dedup GB_ENDING:{userId}:{groupBuyId}
```

- 묶음 발송 시각 **가정값 20:00**(야간 제한 직전 · 하루치가 모임). 시안은 「하루에 한 번」만 정했다(12절 Q).
- 야간 제한은 **광고성 푸시에만** 적용된다 — 알림함 행은 즉시 생긴다(목록에서는 바로 보인다).
- `findFollowerTokens` 의 동의 조건을 유형별 열로 바꾼다 — 게시물은 `follow_post_push_agree`, 공구 오픈은 `follow_group_buy_push_agree`(2절).

## 2. 소비자 알림 설정 4토글(C15) · 동의 이력 · D-1

### 2-1. 현재 → 변경

| 토글(시안) | 현재 | 변경(V206) |
| --- | --- | --- |
| 팔로우 쇼룸 새 공구 | 없음(게시물 토글이 「새 공구나 게시물」을 겸함) | `users.follow_group_buy_push_agree BIT NOT NULL` · `follow_group_buy_push_agreed_at DATETIME(6) NULL` |
| 팔로우 쇼룸 새 게시물 | `follow_post_push_agree`(기본 **true**) | 열 유지 · `follow_post_push_agreed_at` 추가 · **기본값 → 가입 시 광고성 동의와 동기화**(2-2) |
| 공구 마감 임박 | 없음 | `group_buy_ending_push_agree` · `_agreed_at` |

- `NotificationSetting` 임베더블에 열 3 + 시각 3 을 더하고, `agreed_at` 은 **켤 때만** 갱신(끄면 이력에만 철회가 남고 화면 「수신 동의」 줄은 숨김).

- 응답 `NotificationSettingResponse` → 토글 배열 `[{key, enabled, agreedAt}]` + 고정 문구는 FE. 요청은 `Boolean` 4개 부분 갱신(기존 모양).

### 2-2. 기본값 · 기존 사용자

네 토글은 전부 **광고성**이다(시안 「위 알림은 광고성 정보예요. 켜면 수신에 동의한 것으로 처리」). 그런데 지금 `follow_post_push_agree` 는 **동의 없이 기본 true** 다 — 광고성 정보를 미동의자에게 보내는 상태라 그대로 둘 수 없다.

- 가입: 네 토글 = 가입 [선택] 광고성 동의 값으로 초기화 · `agreed_at = 가입 시각`(동의한 경우).
- 기존 행 백필(V206): `follow_post_push_agree = MARKETING_AGREE` · 새 열 3 = `MARKETING_AGREE` · `agreed_at = MARKETING_AGREE_CHANGED_AT`(없으면 `CREATED_AT`). 동의하지 않은 사용자의 게시물 알림이 **꺼진다** — 운영 데이터 영향(12절 Q).

### 2-3. 「처리 결과를 알림으로」

토글을 켜거나 끄면 `MARKETING_CONSENT_CHANGED` 알림함 행 1건(거래 알림 · 즉시 · 「{토글명} 수신에 동의/철회했어요 · 2026.10.16 14:20」) — 정보통신망법 §50 ④ 처리 결과 통지. 네 토글을 한 번에 바꾸면 1건으로 묶는다.

### 2-4. 야간 · 묶음 · D-1

1-6 의 outbox · 스케줄러가 든다. 추가 설정: `notification.quiet-hours.start=21 · end=8` · `notification.digest-hour=20` · `notification.ending-notice-hour=10` · `notification.retention-days.user=90 · member=30`.

## 4. 파트너센터 홈(16)

### 4-0. 먼저 정한 것

1. **홈은 집계를 다시 만들지 않는다** — 메뉴별 `/summary` 가 쓰는 리포지토리 메서드를 그대로 부른다. 숫자가 홈과 메뉴에서 어긋나면 안 된다(시안 「GNB 배지 = 처리 대기 합」). 없는 숫자 4개(발송 기한 경과 · 검수 지연 · 조정 「내 응답」 · 공구별 오늘)만 리포지토리에 더한다.
2. **API 는 셋** — 홈 1회 조립(`GET /home`) · 실시간 카드 1분 폴링(`GET /home/live`) · 달력 월 이동(`GET /home/calendar`). 처리 대기 갱신은 **진입 시**(시안 [근거 대기] → 가정값 · 폴링은 live 만).
3. **「오늘」 = KST 00:00 기준**(시안 [근거 대기] 「00시 / 공구 오픈 시각」 → 가정값 00시 — 어드민 지표의 「오늘」과 같아야 한다).
4. **재고는 상품 재고다** — 공구 전용 재고가 없다(`ProductVariant.stock` 만). 「최소 준비 물량 300개 중」의 300 은 계약 항목 합(`ContractItem.getMinQuantity()`). 품절 예상 문구는 시안이 뺐다.
5. **가이드 판정은 서버**(「시스템이 자동 판정 · 체크를 사람이 누르지 않는다」) · 숨김만 저장(`market.home_guide_hidden_at`).

## 5. 쇼룸 스튜디오 홈(14)

### 5-0. 먼저 정한 것

1. **할 일 한 건 = 카드 한 장 · 버튼 하나** — 서버가 `todos[]` 를 기한순으로 정렬해 내린다(세금계산서 「지급 대기」 맨 위 · 기한 없는 연결 요청 맨 아래). 정렬 규칙을 FE 에 두면 H1 · H4 · H5 가 각자 정렬한다.
2. **정지 중에도 할 일을 숨기지 않는다** — 막히는 카드만 `blocked{reason}`(연결 수락 · 게시물 작성 · 재등록). 계약 서명 · 연장 응답은 그대로(진행 중 공구를 지키는 일).
3. 가이드(H3)는 **첫 연결 요청이 오면 사라진다** · 숨기기 버튼 없음 → 저장 열 없음.
4. 실시간 띠 값은 **공구 관리(09) 잠정 실적과 같다**(취소 · 반품 제외 · `OrderGroupBuySalesReader`) — 파트너 live 의 「결제 기준 취소 전 포함」과 **정의가 다르다**. 시안 둘이 그렇게 적었다 — 각각 자기 메뉴 값을 쓴다.

## 6. 어드민 홈(00 rev.4)

### 6-0. 먼저 정한 것

1. **홈 전용 숫자를 만들지 않는다** — 모든 행은 모듈 `/summary` 가 쓰는 리포지토리 메서드다. 「합계 = 사이드바 배지 합」을 서버가 보장하도록 **사이드바 배지 API 를 같은 서비스가 낸다**(`GET /v1/admin/badges`).
2. **급한 정도 = 상태 배지 + 정렬** — 서버가 `urgency` 로 `FAILED(1) · OVERDUE(2) · EXECUTION_PENDING(3) · DUE_SOON(4) · WAITING(5)` 를 매겨 정렬해 내린다. 한 큐가 D-1 과 대기로 갈리면 **행이 둘**(「브랜드 입점 심사 D-1 1 / 대기 3」).
3. **기한 임박 = 다음 영업일 마감**(ⓓ 가정값 · `BusinessCalendar`) · 금요일이면 월요일.
4. **오늘 처리 완료 = 운영팀 전체**(ⓒ 가정값) · 처리 시각 열이 있는 큐만 합산 — 없는 큐(배송 예외 · 차감 미회수)는 뺀다고 응답 `note` 에 적는다.
5. **1:1 문의 SLA 는 24시간으로 맞춘다** — 코드 `AdminInquiryService.SLA_DAYS = 3` 을 설정값 `admin.inquiry-sla-hours = 24` 로 바꾸고 `isSlaExceeded` · 홈 · 지표(7절)가 같은 값을 읽는다. 시안 00 · 21 모두 24시간이다.
6. **연동 상태는 3종 고정** — PG(`PaymentHealthService` 결과 노출) · 배송 추적(신규 레지스트리) · 전자서명(**연동 없음 → `NOT_INTEGRATED` · 수동**). 모두싸인 API 가 없다는 사실을 배지가 그대로 보인다.

## 7. 어드민 운영 지표(21 rev.2)

### 7-0. 먼저 정한 것

1. **집계 전용 · 저장 없음** — MVP 데이터 규모(공구 수십 · 주문 수백)에서 원표 집계가 충분하다. 6개월 월별만 무거워질 수 있어 **응답 캐시 10분**(`@Cacheable("adminMetrics")` · key = preset+from+to+tab). 집계 테이블은 두지 않는다.
2. **기간 규칙은 서버가 확정**해 응답에 적는다(`period · compare · unit`) — 「한 달 = 1일 ~ 어제 · 전월 같은 기간」 · 비교는 언제나 **직전 같은 길이** · 기준 시각 오늘 00:00.
3. **증감 방향의 의미(좋아짐 · 나빠짐 · 무의미)는 지표 enum 이 든다**(`betterWhen: UP|DOWN|NONE`) — 탭 배지(「나빠진 지표 수」)를 서버가 센다.
4. **공구당 지표는 중앙값**(ⓒ 가정값) · 재공구 · 재계약 판정 **60일**(ⓐ 가정값 · `admin.metrics.regroupbuy-window-days`) · 목표값 열 없음(ⓓ).
5. **거래액 = 결제 시점 · 취소 포함**(홈과 같음) · 반품 · 교환율 = **배송완료 기준**(분모 = 기간 중 `delivered_at` 하위주문) · 활성 = 기간 중 판매일 존재 · 운영 = 처리 완료 시각.

### 8-4. 서명 기한 정지 — `contract` 컬럼 2(V207)

```sql
ALTER TABLE `contract`
  ADD COLUMN `sanction_hold_since` DATETIME(6) NULL COMMENT '당사자 정지로 보류 시작 — SIGNING 서명 기한이 멈춘 시각',
  ADD COLUMN `sanction_hold_party` VARCHAR(16) NULL COMMENT 'BRAND · CREATOR · BOTH';
```

- **정지 시**(`BrandSanctionService#suspend` · `CreatorSanctionService#suspend` → 신규 `ContractSanctionHoldService.hold(party, id, now)`): 그 당사자의 `REVIEW_PENDING · SIGNING · CONCLUSION_PENDING` 계약에 `hold_since IS NULL` 이면 `now` · `party`. 이미 상대 정지로 보류 중이면 `party = BOTH`.
- **해제 시**(`#release` → `resume(party, id, now)`): `party` 에서 해제된 쪽을 빼고, 남은 당사자가 없으면 `SIGNING` 계약의 `signature_deadline_at += (now − hold_since)` · 두 열 NULL · 이력 `SIGN_DEADLINE_RESUMED`(「남은 기한부터 다시 센다」). `BOTH` 였으면 다른 쪽만 남긴다.
- 표시(`ContractDetailAssembler` · `CreatorContractDetailAssembler` · 목록 DTO): `hold { kind: MINE | COUNTERPARTY, label }` — 내 정지면 「검토 보류 · 계정 정지」(REVIEW_PENDING) / 「체결 보류 · 계정 정지」(SIGNING · CONCLUSION_PENDING)(경고), 상대 정지면 「체결 보류 · 상대 계정」(브랜드) / 「체결 보류 · 상대 브랜드 사정」(스튜디오)(중립) · 상세 안내 문구는 FE. **상대의 정지 사실 · 사유는 내리지 않는다** — `kind` 만. 작성중 · 검토 반려 초안의 「편집 불가」(S4 · 중립)는 `account-status.suspended` 로 FE 가 판정한다.
- 상세의 `signatureDeadlineAt` 옆 `deadlinePaused: true`(「정지 중 멈춤 · 해제 후 남은 기한부터」 / 「보류 중 멈춤 · 재개 후 남은 기한부터」). 서명 안내 재발송 버튼 비활성은 FE(가드 8-1 · 8-2 가 409 로 받친다).
- **어드민** 계약 목록 · 상세(`AdminContractQueryService` DTO)에도 같은 `hold { party: BRAND|CREATOR|BOTH, label }` — 운영자가 「검토 보류 · 계정 정지」를 보고 검토 · 체결을 진행하지 않는다(8-3 의 409 가 받친다). 어드민 공구 목록 · 상세도 8-5 와 같은 `hold`.
- 기한 D-1 스케줄러(1-4 · `ContractDeadlineScheduler` 매일 10:00)는 `hold_since IS NULL` 만 본다. 만료는 여전히 운영자 수동(`expire` 전제조건은 **이동된** `signature_deadline_at`).

### 8-5. 공구 보류 표시 — 저장 없음 · 조립 시 파생
