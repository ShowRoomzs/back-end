## 0. 먼저 정한 10가지

### 0-1. 도메인은 어드민 설계서가 정본이다 — 이 설계서는 「어느 열을 어떻게 내리는가」만 적는다

정산 = 공구 1건 = `settlement` 1행(어드민 설계서 0-1). 생성 · 산식 · 상태 전이 · 3자 분배 · 증빙 · 차감 · 스케줄러는 **전부 그쪽**이고 파트너 13 은 같은 행을 읽는 세 창 중 하나다. 이 설계서에 테이블 정의 · 산식이 **없는 것은 의도**다 — 두 설계서에 같은 식이 있으면 한쪽만 고쳐진다. 공구는 두 사건만 통보받는다 — `recordSalesFinalized`(정산 생성) · `markSettled`(지급 완료 → `SETTLED`) — 둘 다 `GroupBuyCommandService` 에 이미 있다.

### 0-2. 생성은 배치가 찾는다 — 즉시 훅은 없다

어드민 설계서 0-2 · 2-1. `SettlementGenerationScheduler`(10분)가 `group_buy.status = ENDED ∧ settlement 없음` 인 공구를 돌며 `GroupBuyCommandService.isSettlementReady`(ENDED ∧ 미종결 0 · 포트가 비면 false)를 묻는다. 최대 10분 지연은 「3영업일 확인 기간」 앞에서 의미가 없다. `GroupBuyFulfillmentCheck`(이행 확인)는 게이트에서 **이미 빠져 있다**(1009 수정계획 6절).

### 0-3. 금액은 생성 시 **스냅샷**이다 — 명세까지 복사된다

정산은 「돈의 사실」(§41-4)이다. 생성 뒤 원천(주문 · 클레임 · 계약)이 바뀌어도 정산 금액은 움직이지 않고, 뒤늦은 환불은 **차감**(0-8)이라는 별도 사건으로만 들어온다. 파트너 12 성과 관리의 「수취 예정액」(정산 전)은 `SettlementCalculator` 를 **같이 호출**하고, 정산이 생긴 공구는 `SettlementReader.findByGroupBuy` 로 저장값을 그대로 쓴다(어드민 설계서 8-5).

### 0-4. 상태 5종은 enum 하나 · 파트너는 4종만 본다

`SettlementStatus { REVIEWING(정산 확인 중 · 정보) · ADJUSTING(조정 협의 · 경고) · PAYOUT_SCHEDULED(지급 예정 · 중립) · PAID(지급 완료 · 성공) · PAYOUT_FAILED(분배 실패 · 위험 · 어드민 전용) }`. 파트너 응답은 `PAYOUT_FAILED` 를 **`PAID` 로 접어서** 내린다(`toPartnerStatus`) — 「수취자 화면은 그대로 지급 완료」(§41-5 · §46 A-4 미결). 수취자별 실제 지급 상태는 `payouts[].status` 가 따로 말한다(브랜드 몫만 실패했으면 브랜드 행이 `FAILED`). 폐기된 「정산 대기 · 확정 대기 · 정산 확정 · 정산 보류 · 이체 완료」는 enum · 라벨 · 이력에 **없다**(§41-2).

### 0-5. 확정 · 지급 예정일 · 기한은 **전부 서버 계산 · 저장값**이다 — 어드민 설계서 0-10

| 값 | 규칙 |
| --- | --- |
| 확인 마감 `review_due_at` | 생성 다음 영업일부터 **3영업일째 23:59:59**(`BusinessDayCalculator.dueAt`) |
| 자동 확정 `confirmed_at` | 마감 **다음 날 00:00:00**(규칙값) · 합의 = 동의 시각 · 만료 = 기한 다음 날 00:00:00 |
| 지급 예정일 `payout_due_date` | 확정일 + **3영업일** — 10.06(화) 확정 → 10.07 · 10.08 · (10.09 한글날 제외) · **10.12** |
| 세금계산서 발행 기한 | 확정일이 속한 달의 **다음 달 10일** |
| 합의 기한 | 조정 요청 + 10영업일 23:59:59 · 연장 없음 |

영업일 수(3 · 3 · 10)는 `settlement.*` 설정값이다. 기한은 발급 시점에 계산해 저장하므로 뒤에 공휴일이 추가돼도 이미 적힌 기한은 움직이지 않는다.

### 0-6. 조정 요청 · 응답 3종의 API 는 **이슈 스레드 설계서 3절**이다

`POST /v1/seller/settlements/{id}/adjustment`(요청) · `GET …/adjustment/preview`(미리보기) · `GET /v1/seller/threads/{threadId}/adjustment` · `POST /v1/seller/settlement-adjustments/{id}/proposals[/{pid}/accept|reject]` — 컨트롤러 `SellerSettlementAdjustmentController`(같은 패키지 · 별도 클래스). 이 설계서의 상세 응답은 **버튼 노출 판정과 조정 내역 블록**만 든다(4-3). 스레드는 **새 `ThreadKind.SETTLEMENT_ADJUSTMENT`** 라 구 `GroupBuyIssue` 1건 제약과 무관하다 — 초안의 미결 S-4(다른 유형 이슈가 열려 있으면 409)는 **해소**됐다.

### 0-7. 지급은 **포트 뒤**다 — `SIMULATED` 모드로 개발하고 `PG` 는 런칭 게이트

어드민 설계서 0-5. `SettlementPayoutGateway` · `settlement.payout.mode = SIMULATED | PG`. 운영 프로필은 `PG` 강제라 **PG 지급대행 연동 전 운영 배포 불가**(12절 S-1). 「지급 실행」 · 「앞당기기」 버튼은 어느 서피스에도 없다(§41-5).

### 0-8. 차감(클로백)은 환불 집행이 만든다 — 몫별로 따로 간다

어드민 설계서 0-8 · 6절. 이미 **생성된 정산**(상태 무관)의 항목이 운영자 사유 · 반품 통과 환불로 집행되면 `SettlementClawbackHook` 이 브랜드 행 · 인플루언서 행 2개를 만들고, 브랜드 몫은 **같은 마켓의 다음 정산**에서 회수된다(측별 · §46 A-3). 회수분은 플랫폼 몫이다. 차감이 반영된 정산에는 플랫폼 → 브랜드 **마이너스 수정세금계산서** 행(`BRAND_TAX_INVOICE_CREDIT`)이 함께 생긴다.

### 0-9. 세무 증빙은 **읽고 내려받기만** 한다

`settlement_tax_document` 의 `BRAND_TAX_INVOICE`(정산당 1행 · 확정 시 `PENDING_ISSUE`) · `BRAND_TAX_INVOICE_CREDIT`(차감 건마다) 를 읽는다. 발행본 등록(M5)은 어드민이고, 파트너는 `status = ISSUED ∧ file_key` 일 때만 `[다운로드]`. 공급가 = **리워드**(§41-6 · §46 B-7 미결 — 초안의 「리워드 + 플랫폼 수수료」는 버렸다 · 베타 0% 라 지금은 같다). 인플루언서 축 증빙은 파트너 응답에 `influencerTax { businessType, withholdingType }` **표시값**만 있다(「브랜드가 챙길 인플루언서 증빙은 없습니다」).

### 0-10. 조회 전용 — 목록에 체크박스 · 관리 열 · 일괄 액션이 없다

§41-8 공통. 브랜드가 정산에 할 수 있는 일은 **정산 조정 요청 · 응답 3종**(이슈 스레드 설계서) · 명세 · 세금계산서 **다운로드**뿐이다. 버튼 노출은 서버 `actions {}` 가 정한다(37 설계서 0-3 과 같은 방식). 계좌 마스킹은 `SettlementAccountMasker`(뒤 6자리 노출 · 기본정보와 같은 형식 — `global.utils` 로 옮겨 스튜디오와 공유) · 시안의 `123-****-**89` 는 쓰지 않는다(공통 결정 #14).

## 1. 파트너가 읽는 열 — 도메인 ↔ 응답 매핑

어드민 설계서 1절의 테이블에서 파트너 13 이 읽는 열만 적는다. 열 이름은 **그쪽이 정본**이다.

| 응답 | 원천 | 비고 |
| --- | --- | --- |

### 1-1. 「반품 · 교환 배송비」 블록 — 분해 밖 · 표시 전용 · 파트너만

파트너 13 만 있는 블록(§41-8). 이 공구의 `order_claim_collection` 을 `fee_bearer` 로 가른다 — `CONSUMER`(단순 변심 · 기타) = 소비자 부담 · `return_deduction` 합 → 「브랜드 수취」 / `SELLER`(파손 · 오배송) = 브랜드 부담 · `market.return_fee / exchange_fee` × 건수 → 「정산 대상 아님」. 정산 생성 시점에 검수 전인 클레임은 없다(미종결 0 이 생성 조건이라 「판정 대기」 행은 **생기지 않는다** — 시안 D2 의 「판정 대기 3건」은 11절 #3). 금액 산정(왕복 vs 편도)은 `[미정]` 그대로 — 지금은 **차감액 · 요금표 값 그대로** 싣는다. 정산 행에 저장하지 않고 **조회 시 계산**한다(분해 · 검산과 무관).

```
  confirmedSalesAmount, feeAmount(= pg + platform), rewardAmount, rewardVatAmount, brandPayoutAmount,
  status, statusLabel, statusTone,
  schedule { kind: REVIEW_DUE | PAYOUT_DUE | PAID | NONE, date } }   ← 「지급(예정)일」 열: 09.28까지 확인 · 10.12 예정 · 07.24 · —
```

열은 계산 순서 그대로(L1) — 서버는 합치지 않고 `feeAmount` 만 두 수수료의 합이다(시안 「수수료」 한 열). `schedule.date` 는 **브랜드 행**(`settlement_payout.payee = BRAND`)의 `due_date` · `paid_at` 이다 — 사업자 인플루언서 건은 인플루언서 행과 날짜가 다르지만 브랜드는 자기 행만 본다.

### 2-3. 요약 — `GET /v1/seller/settlements/summary`

```
{ paidTotal, paidCount,                                   ← 누적 지급(brand_payout_amount 합 · PAID + PAYOUT_FAILED 중 브랜드 행 PAID)
  scheduledTotal, scheduledCount, nextPayoutDate, scheduledHasClawback,   ← 지급 예정(브랜드 행 SCHEDULED · 가장 가까운 due_date)
  reviewingCount, reviewingDueAt,                         ← 정산 확인 중(가장 임박한 마감)
  adjustingCount,
  statusCounts { REVIEWING, ADJUSTING, PAYOUT_SCHEDULED, PAID },
  attentionCount }                                        ← GNB 배지 = 요청 가능 창이 열린 REVIEWING 건수
```

- 전부 **마켓 전체** 기준이다 — 검색어 · 상태 칩과 무관(KPI 는 필터를 따라가지 않는다).
- 빈 상태(L2)는 `count = 0 · amount = null`(0 이 아니다 — 「0원은 실적처럼 읽힌다」) · FE 가 「—」.
- `attentionCount` 는 **정산 확인 중(요청 가능 창 열림)** 만 센다. 조정 협의의 「내 응답 필요」는 연결·소통 GNB(스레드 안 읽음)가 센다 — 같은 조치를 두 배지에 세지 않는다(공통 결정 #19 · 초안의 `REVIEWING + ADJUSTING` 은 버렸다).

## 3. 조정 협의 — 파트너가 보는 것(API 는 이슈 스레드 설계서)

- 요청 입력은 `rewardAmount` · `reason`(1,000자) **둘뿐**(근거 첨부 없음 · 2026.10.07). 상한 · 미리보기(인플루언서 실지급 · 브랜드 수취액)는 `GET …/adjustment/preview` 가 **서버 계산**으로 내린다 — 초안의 `adjustmentPreviewBasis`(FE 계산용 기준값)는 버렸다. 시안 C1 검산: 504,000 → 브랜드 수취액 6,300,000 − 189,000 − 504,000 − 50,400 = 5,556,600 · 상한 (6,300,000 − 189,000) ÷ 1.1 → **5,555,450**(10원 절사).
- 동의 시 **금액 변경 + 보류 해제 + 종결**이 한 트랜잭션이고(이슈 스레드 설계서 2-3) 정산은 즉시 `PAYOUT_SCHEDULED`(확정일 = 동의일 · 지급 예정일 = +3영업일). 반대 뒤에는 **양쪽 다** 새 제안을 낼 수 있다(§46 A-9 잠정).
- 합의 기한 만료는 원래 금액 확정 · 「아무도 동의하지 않은 결과」(배지 중립) · 지급 예정일 = 만료 확정일 + 3영업일.
- 카드 버튼 상태는 스냅샷이 아니라 제안 행에서 읽는다(`MessageCardResponse.Action.respondable`). 종결 후 입력창 잠금은 `SETTLEMENT_ADJUSTMENT_CLOSED`(이슈 스레드 설계서 3-7). 운영자는 열람만.
