## 0. 먼저 정한 6가지

### 0-1. 공구는 파트너센터의 것이 아니라 **3서피스가 공유하는 하나의 객체**다

§29-0이 "컴포넌트를 3서피스 동일 마크업으로 재사용한다"로 시작하고, 상태 7종·게시물 8종이 전부 **3서피스 공통**이다. 계약 설계(26 · 0-1)와 같은 판단을 한다 — **테이블은 처음부터 어드민 판정(직권 중단·소명·숨김·정산 확인)과 스튜디오 액션(게시물·연장 응답·이행 확인)까지 수용하도록 판다.** 파트너 API만 먼저 열더라도 컬럼은 다 만든다.

- 도메인: `showroomz.domain.groupbuy.{entity, repository, type, service}` — **한 벌**
- API: `showroomz.api.seller.groupbuy.*`(이번 범위) / `showroomz.api.creator.groupbuy.*` / `showroomz.api.admin.groupbuy.*`(다음)
- 스케줄러: `showroomz.global.scheduler.GroupBuyLifecycleScheduler`

### 0-2. 공구는 **체결 트랜잭션 안에서** 생긴다 — 버튼이 아니다

§29-1: "**계약 체결 시에만** 생성된다" · "생성 진입점은 **세 서피스 어디에도 없다**". 어드민 계약 기획(§28 C4)도 "누르는 순간 계약이 성립하고 **공구가 생성**된다"고 적었다.

그런데 **파트너 계약 시안 B5에 `[공구 생성]` 버튼이 남아 있고**(§26 B5), 공구 시안 A2 빈 상태 문구도 "계약 상세에서 생성할 수 있습니다"라고 한다. 둘은 양립할 수 없다.

**체결 트랜잭션 안에서 자동 생성으로 확정한다.** 이유 둘:

1. 28 설계서 8-3이 이미 경고한 상태 — **「체결완료인데 공구가 없는 계약」** — 을 구조적으로 없앤다. 버튼 방식이면 브랜드가 누르지 않는 한 그 상태가 무기한 남는다.
2. 체결은 **유일한 불가역 조치**다. 공구 생성이 실패하면 체결도 롤백되어야 불가역 조치의 결과가 반쪽이 되지 않는다. 같은 트랜잭션이어야 이게 된다.

→ 계약 쪽 수정이 따라온다(2-4). 계약 시안 B5의 `[공구 생성]`과 공구 시안 A2 문구는 **시안 정정 대상**이다(7-1 #1).

### 0-3. 계약 조건은 **복사하지 않고 참조**한다 — 공구가 소유하는 값은 **기간** 하나다

계약 설계(26 · 0-5)는 계약이 상품 마스터를 **스냅샷**했다. 공구는 다르다 — 참조 대상인 계약이 **`CONCLUDED` 이후 불변**이기 때문이다(26 · 3-1 "`CONCLUDED` 이후로 나가는 전이가 없다", 계약 편집 잠금은 서버 권한).

| 값 | 어디서 읽나 | 이유 |
| --- | --- | --- |
| 공구명 · 상대 · 상품 항목(정가·공구가·리워드율·최소 물량) · 고정 지급비 · 콘텐츠 의무 | **`contract` · `contract_item`** | 불변 원본이 이미 있다. 복사하면 **같은 확정값이 두 곳**에 생긴다 |
| 시작 일시 | `group_buy.start_at` | 불변이지만 **스케줄러·정렬 인덱스**가 필요해 둔다 |
| **현재 종료 예정** | `group_buy.end_at` | **연장이 바꾸는 유일한 값**(§29-1 "유일한 예외") |
| 원래 종료 예정 | `contract.group_buy_end_at` | B4d "8일 → 15일" · B5d "종료 예정일 / 실제 종료" 병기의 원본 |
| 실제 종결 시각 | `group_buy.ended_at` | 조기 마감·중단은 `end_at`보다 이르다 |

`group_buy_item` 테이블을 **만들지 않는다.** 공구 상품 = 계약 상품 전부이고(§31-2 "상품·가격 계약 확정값 · 수정 불가"), 하위 집합을 고르는 기획이 없다.

### 0-4. 상태는 7종 하나 — **요청·통지·게시물·이행은 상태가 아니라 사실 테이블**이다

§29-6 "**요청은 상태가 아니다**" · §29-10 "**이슈는 상태가 아니다**" · §29-3 "게시물은 공구와 **별 축**". 그러므로:

| 축 | 저장 위치 | 공구 상태에 미치는 영향 |
| --- | --- | --- |
| 공구 수명주기 | `group_buy.status` (7종) | — |
| 기간 연장 | `group_buy_extension_request` | 수락 시 `end_at`만 바뀐다 |
| 중단·조기 마감 요청 | `group_buy_change_request` | **승인 하나만** 상태를 바꾼다 |
| 직권 중단 통지·소명 | `group_buy_admin_suspension` | 통지 = `SUSPENSION_SCHEDULED`, 집행 = `SUSPENDED` |
| 공구 게시물 | `group_buy_post` | 오픈 승인이 게이트 ③ |
| 이행 확인 · 이슈 | `group_buy_fulfillment_check` · `group_buy_issue` | **없음** — 정산 보류만 |

B4a~B4h 11종 화면은 **전부 `IN_PROGRESS`** 이고, 화면 분기는 사실 테이블 조합으로 FE가 고른다. 서버가 `IN_PROGRESS_EXTENSION_PENDING` 같은 값을 만들면 요청 3종 × 결과 3종이 상태값으로 폭발한다(계약 설계 1-2와 같은 판단).

### 0-5. **시간이 여는 전이는 스케줄러가 한다** — 계약과 반대 결정이다

계약 설계는 "스케줄러를 만들지 않는다"(26 · 0-2)였다. 만료가 **자동 판정이 아니라고 기획이 못박았기** 때문이다. 공구는 반대다.

| 기획 근거 | 결론 |
| --- | --- |
| §29-4 "**시작 버튼이 없다** — 시작 시각이 되면 **시스템이 자동으로 연다**" | 준비완료 → 진행중은 스케줄러 |
| 시안 이력 "공구 시작 · 게시물 노출 시작 · **시스템**" / "공구 종료 · **시스템**" | 행위자 `SYSTEM`이 기획에 있다 |
| §29-6 연장 "**무응답 = 변경 없이 종결** · 별도 만료 처리가 없다" | 종료 전이가 대기 중인 연장을 함께 닫는다 |

반대로 **사람이 판단하는 전이는 스케줄러에 넣지 않는다** — 직권 중단 집행은 소명 기한이 지나도 **운영자가 누른다**(§32-3 B2c "기한이 차면 버튼이 저절로 열린다"). 기한 도달 = 버튼 활성이지 자동 집행이 아니다.

### 0-6. 아직 없는 모듈에 기대는 자리는 **포트**로 둔다 — 그리고 **없는 값은 `null`이지 0이 아니다**

공구 화면이 읽는 숫자 중 셋은 **이 저장소에 아직 출처가 없다.**

| 필요한 값 | 출처 모듈 | 현재 상태 |
| --- | --- | --- |
| 판매 KPI(주문·수량·금액) · 미종결 주문 건수 | 판매 관리 | `domain/order`에 **공구 귀속 컬럼이 없고**, `OrderProductStatus`는 `PENDING/PURCHASE_CONFIRMED/CANCELLED` 3종뿐이며 **주문 생성 경로 자체가 없다** |
| 정산완료 전이 · 확정 실적 | 정산 관리 | 모듈 없음 · `[보류-정산구조]` |
| 이슈 스레드 · 3자 스레드 | 연결·소통 | `MessageThread`가 **`connection_id` UNIQUE로 연결 1:1**이라 같은 쌍에 두 번째 스레드를 만들 수 없다 |

공구 도메인은 **인터페이스만 정의하고 의존한다**(5절). 구현이 없는 동안 판매 포트는 `Optional.empty()`를 돌려주고 응답은 `null`이 된다.

**`0`으로 내리지 않는 이유** — 미종결 주문 `0`은 **"정산해도 된다"**는 뜻이다(§29-11 "미종결 0 아니면 정산 확인 버튼 비활성"). 판매 모듈이 없어서 0이 나오면 정산 게이트가 **거짓으로 열린다.** 계약 설계의 `pgFeeRate: null`과 같은 규칙이다.

> ⚠️ **종료의 색이 기획 안에서 갈린다** — §29-2 상태표는 「정보」, 같은 절 종결 3종 표는 「중립」. 시안·§30-4는 정보다. **정보로 집행**하고 7-1 #6에 올린다.

**기존 `ProductGroupBuyStatus`(`PREPARING/READY/IN_PROGRESS/NOT_CONNECTED`)를 재사용하지 않는다.** 시안 머리말이 명시한다 — "연결 없음은 상품 기준 파생값이고 종료·정산완료·중단은 공구에만 있다. **두 축을 한 열에 섞지 않는다**". 두 enum의 관계는 1-11의 동기화가 맡는다.

**「검토 중 추가 요청 불가」(§29-6)를 생성 컬럼 UNIQUE로 막는다.** MySQL은 NULL을 여러 개 허용하므로 `PENDING`인 행만 공구당 1개로 제한된다. 브랜드의 중단 요청과 인플루언서의 중단 요청이 **동시에** 들어와도 하나는 DB에서 떨어진다 — 서비스의 선검사만으로는 이 경합을 막지 못한다. 시안 B4a·B4f·B4g가 "액션 없음"인 것이 이 규칙의 화면 표현이다.

**`LAPSED`** — 검토 중 요청이 있는 상태로 `end_at`이 지나 공구가 끝나면, 판정 대상이 사라진다. 스케줄러가 종료 전이와 같은 트랜잭션에서 `LAPSED`로 닫는다. 그러지 않으면 **어드민 조치 큐(§32-1)에 이미 끝난 공구가 남아 0이 되지 않는다.**

**사유 코드**

| 요청 | 코드 |
| --- | --- |
| 중단 · 브랜드(C2·C4) | `QUALITY_ISSUE`(상품 품질 이슈) · `PRICE_TERMS_ERROR`(가격·조건 오기) · `NEGOTIATION_BROKEN`(인플루언서와 협의 결렬) · `ETC` |

`QUALITY_ISSUE` 옆에 재고 소진이 **없는 것이 맞다** — §29-2 "재고 소진은 중단이 아니라 조기 마감이다". enum을 요청 유형별로 **분리**해 두면 `SUSPEND + STOCK_OUT` 조합이 컴파일 단계에서 불가능해진다.

```java
if (post == null)                         return NOT_WRITTEN;     // 미작성
if (groupBuy.status().isTerminal())       return CLOSED;          // 종료 — 종료·조기 마감·중단 공통
return switch (post.reviewStatus()) {
    case DRAFT    -> WRITING;                                     // 작성중
    case PENDING  -> PENDING_APPROVAL;                            // 승인대기
    case REJECTED -> REJECTED;                                    // 반려
    case APPROVED -> post.isHidden()          ? HIDDEN            // 숨김
                   : groupBuy.isSelling()     ? EXPOSED           // 노출중 (IN_PROGRESS · SUSPENSION_SCHEDULED)
                   :                            SCHEDULED;        // 예약
};
```

§29-3과 시안 머리말이 "게시물은 **공구를 따라가는 값**이지 공구를 움직이는 값이 아니다"라고 했다. 따라가는 값을 따로 저장하면 **스케줄러가 공구를 열고 게시물 갱신을 빠뜨린 순간** 두 열이 어긋난다. 게시물이 **스스로 가진 사실**(작성·제출·심사·숨김)만 저장하고 나머지는 공구 상태에서 읽는다.

**`post.status`의 `SUSPENDED`를 숨김에 재사용하지 않는다 — 치명적이다.** 일반 게시물의 `SUSPENDED`는 이의 신청 기한이 걸린 상태이고, `PostAppealDeadlineScheduler`가 기한이 지나면 **영구 삭제로 넘긴다**(`PostLifecycleService.expireOverdueSuspensions`). 공구 게시물 숨김을 `SUSPENDED`로 표현하면 **7일 뒤 게시물 원문이 사라진다** — §29-8은 숨김이 "되돌릴 수 있는 조치"이고, 종결 후에도 "원문은 **분쟁 근거로 보관**"이다. 공구 게시물의 `post.status`는 `DRAFT` / `PUBLISHED` / `DELETED`만 쓴다(쓰기 규칙은 스튜디오 설계 소관).

### 1-9. 이행 확인 · 이슈 — `group_buy_fulfillment_check` · `group_buy_issue`

**`group_buy_fulfillment_check`** — §29-10 "계약 전체에 **1회** · 이행/미이행 **2지** · **불가역**".

| 컬럼 | 비고 |
| --- | --- |
| `fulfillment_check_id` PK / `group_buy_id` FK | |
| `checker_side` VARCHAR(16) | `SELLER` / `CREATOR` — **`UNIQUE(group_buy_id, checker_side)`** = 측별 1회 · 불가역 |
| `result` VARCHAR(16) | `FULFILLED` / `UNFULFILLED` |
| `reason` VARCHAR(2000) NULL | `UNFULFILLED`면 **필수** — 3자 스레드의 첫 글(제20조②③) |
| `auto_confirmed` BOOLEAN | **무응답 자동 이행** 여부 — 어드민 B5b "실제로 확인한 것과 기한이 지나 자동 처리된 것은 뜻이 다르다" |
| `checked_at` · `checked_by` | |
| `thread_id` BIGINT NULL | 미이행 시 열린 3자 스레드 |

- 행이 **없음** = 확인 전. 체크박스 방식의 `false`와 구분된다(§29-10 "체크 안 함과 미이행은 뜻이 다르다") — 행의 부재가 곧 "안 함"이다.

**`fulfillment_due_at`와 무응답 처리** — 시안은 "기한까지 답하지 않으면 **이행으로 처리**"로 그렸지만 §29-10 ⚠️ · §33-3 **D-1이 "약관 근거 없음"**으로 막아 두었다.

| 항목 | 처리 |
| --- | --- |
| 기한 | 종료 전이 시 `ended_at + groupbuy.fulfillment.due-days`로 **확정·저장** — 값 자체가 미정(§33-1 #5)이라 설정값 |

| 꺼진 동안 | 기한이 지나도 확인은 **계속 받는다.** 기한은 **표시값**이다 |

구현은 해두고 **스위치로 막는다.** 근거가 확정되면 설정만 바꾸고, 반대로 결정되면 코드를 걷어내지 않아도 된다. "인플루언서에게 불리한 간주 조항"(D-1)을 근거 없이 켜는 것이 가장 나쁜 선택이다.

**`group_buy_issue`** — §29-10 "이슈 스레드는 **정산과 무관한 이견**을 여는 창구".

| 컬럼 | 비고 |

### 1-10. 공구번호 — `GB-YYYYMMDD-NNN`

- **날짜 = 공구 생성일**(= 체결일). 시안 "GB-20260806-018 · 2026.08.06 생성".
- 생성 방식은 계약번호(`ContractNumberGenerator`)와 **같은 upsert 시퀀스**: `group_buy_number_sequence(seq_date DATE PK, last_seq INT)` + `INSERT … ON DUPLICATE KEY UPDATE`. `Propagation.MANDATORY` — 생성 트랜잭션 밖에서 번호를 태우지 않는다.
- `contract_number_sequence`에 접두어 컬럼을 추가해 공용화하지 **않는다** — 계약 테이블의 PK를 바꾸는 마이그레이션이 되고, 얻는 것은 테이블 1개 절약뿐이다.

> ⚠️ 28 설계서 8-3은 **`GRB-…`**로 적었다. 최신 시안(rev.4)이 `GB-`이므로 **`GB-`로 확정**한다(7-1 #8).

### 1-11. 상품의 공구 상태 동기화 — `Product.groupBuyStatus`

`product.group_buy_status`(V89)는 **지금 아무도 쓰지 않는다** — 기본값 `NOT_CONNECTED`로만 들어간다. 그런데 **읽는 곳은 이미 있다**:

| 읽는 곳 | 쓰는 방식 |
| --- | --- |
| `CartService.unavailableReason()` | `isConnected()`(= `NOT_CONNECTED` 아님)이고 진열이면 **구매 가능** |
| 앱 상품 상세(C7) | 연결된 상품만 진입 |
| `AdminProductService` | 공구 상태 필터·카운트 |

공구 모듈이 이 값을 **처음으로 쓰게 된다.** 규칙:

```
product.groupBuyStatus = 이 상품을 담은 활성 공구 중 가장 앞선 단계
  IN_PROGRESS  ← 공구가 IN_PROGRESS 또는 SUSPENSION_SCHEDULED(아직 팔린다)
  READY        ← READY
  PREPARING    ← PREPARING
  NOT_CONNECTED← 활성 공구 없음(종결 3종뿐이거나 없음)
```

- `ProductGroupBuyStatusSynchronizer.resync(productIds)`를 **모든 상태 전이와 같은 트랜잭션**에서 호출한다. 대상 상품은 `contract_item.product_id`.
- **단일 값이 아니라 재계산인 이유** — 계약 검증에 "같은 상품이 기간이 겹치는 다른 계약에 들어가 있는가"가 **없다.** 한 상품이 두 공구에 걸릴 수 있으므로, 한 공구가 끝날 때 무조건 `NOT_CONNECTED`로 내리면 **다른 공구가 진행 중인 상품이 판매 불가**가 된다.

> 🚨 **P3 배포 전 필수 선행 — 장바구니가 준비중 상품을 판다.** `CartService`는 `isConnected()`로 구매 가능을 판정하는데, `ProductGroupBuyStatus.isConnected()`는 **`PREPARING`·`READY`도 참**이다(상세 진입용 의미). 지금까지는 아무 상품도 이 값을 갖지 않아 드러나지 않았다. 공구 모듈이 동기화를 시작하는 순간 **시작 전 공구 상품이 장바구니에서 결제 가능**해진다. 구매 판정은 `== IN_PROGRESS`여야 한다 — 앱 쪽 수정이 이 설계의 **P3 선행 조건**이다(6절).

> ⚠️ **겹치는 공구의 가격** — 한 상품이 동시에 두 공구에서 `IN_PROGRESS`면 소비자가 어느 공구가로 사는지 정할 수 없다. **계약 검토 요청 시 "같은 상품 · 기간 겹침"을 하드 검증으로 막을지** 기획 확정이 필요하다(7-2 #4). 확정 전까지는 동기화만 올바르게 한다.

## 2. 공구 생성 — 체결과 같은 트랜잭션

### 2-1. 흐름

`AdminContractCommandService.conclude()` 안에서, 현재 주석 "공구 모듈이 assignGroupBuy 조건부 게이트로 연결한다"가 있는 자리에 한 줄을 넣는다.

```
[기존] 상태·서명·문서 판정 → CONCLUDED 전이 → 이력 CONCLUDED
[추가] → groupBuyFactory.createFromConcludedContract(contract, now)
           ├ 번호 발급(GB-…)
           ├ group_buy INSERT  (status = PREPARING, start_at·end_at 계약 복사)
           ├ contractRepository.assignGroupBuy(contractId, groupBuyId)  ← 26 · 1-8 게이트
           │     rowsAffected = 0 → CONTRACT_GROUP_BUY_ALREADY_CREATED (롤백)
           ├ group_buy_history CREATED (SYSTEM)
           ├ contract_history GROUP_BUY_CREATED
           └ product groupBuyStatus resync(PREPARING)
[기존] → 양측 통지
```

- `GroupBuyFactory`는 **도메인 서비스**(`domain/groupbuy/service`)다. 어드민 계약 서비스가 도메인 서비스를 부르는 방향이라 `domain/contract` → `domain/groupbuy` 의존이 생기지 않는다.
- 게이트를 이미 만들어 둔 26 설계가 그대로 쓰인다 — **조건부 UPDATE가 중복 생성의 최종 방어선**이고, `group_buy.contract_id` UNIQUE가 반대편 방어선이다.
- 생성 실패 = 체결 실패. 0-2의 결정 그대로다.

### 2-2. 상속 — 무엇이 어디로

| 계약 값 | 공구에서 | 비고 |
| --- | --- | --- |
| `market` · `creator` | `group_buy.market_id` · `creator_id` 복사 | 비정규화(1-1) |
| `group_buy_start_at` / `group_buy_end_at` | `start_at` / `end_at` 복사 | `end_at`만 이후 변한다 |
| `title` · `items[]` · `fixed_fee_*` · `content_*` | **복사하지 않음** — 조회 시 조인 | 0-3 |
| `connection` | 조회 시 조인 | 「스레드 열기」 딥링크의 출처 |

### 2-3. 이미 체결된 계약 — 백필

계약 모듈이 먼저 배포되어 **`CONCLUDED`인데 `group_buy_id IS NULL`인 계약**이 이미 있을 수 있다(28 설계 리스크 "체결완료인데 공구가 없는 계약이 쌓인다").

- **일회성 러너** `GroupBuyBackfillRunner` — `groupbuy.backfill.enabled=true`일 때만 기동 시 1회 실행. SQL 마이그레이션이 아닌 이유: 번호 발급·이력·상품 동기화를 **생성 경로와 같은 코드**로 태워야 한다.
- **멱등** — 26 게이트(`assignGroupBuy`)가 이미 생성된 계약을 0행으로 떨군다. 두 번 돌아도 안전하다.
- 백필된 공구의 **시작 일시가 이미 지났을 수 있다** — 7-2 #2(시작 시각 경과 준비중)의 규칙을 그대로 따른다.

### 2-4. 계약 쪽에 따라오는 수정

| 대상 | 현재 | 수정 |
| --- | --- | --- |
| `ContractDetailResponse.permissions.canCreateGroupBuy` | `CONCLUDED && groupBuyId == null` | **제거** — 생성 진입점이 없다 |
| `ContractDetailResponse.GroupBuy` | `{groupBuyId, 생성 가능 여부}` | `{groupBuyId, groupBuyNumber}` — B5a·B5b `[공구 관리에서 보기 ↗]`의 목적지 |

| 계약 시안 B5 `[공구 생성]` · 공구 시안 A2 문구 | | **시안 정정 요청**(7-1 #1) |

## 3. 상태 전이

### 3-1. 전이표 — 누가, 어디서, 어디로

| # | 전이 | 주체 | 트리거 | 이번 범위 |
| --- | --- | --- | --- | --- |
| 1 | — → `PREPARING` | 시스템 | 계약 체결 트랜잭션 | ✅ |
| 2 | `PREPARING` → `READY` | **게이트를 마지막으로 채운 행위자** | 게이트 ① 브랜드 확인 / ③ 운영자 승인 | ✅ ①쪽 |
| 3 | `READY` → `IN_PROGRESS` | 시스템 | `start_at` 도달 | ✅ 스케줄러 |
| 4 | `IN_PROGRESS` → `ENDED` (`COMPLETED`) | 시스템 | `end_at` 도달 | ✅ 스케줄러 |
| 5 | `IN_PROGRESS` → `ENDED` (`EARLY_CLOSED`) | 운영자 | 조기 마감 요청 승인 | admin |
| 6 | `READY`·`IN_PROGRESS` → `SUSPENDED` | 운영자 | 중단 요청 승인 | admin |
| 7 | `IN_PROGRESS` → `SUSPENSION_SCHEDULED` | 운영자 | 직권 중단 사전 통지(M6) | admin |
| 8 | `SUSPENSION_SCHEDULED` → `IN_PROGRESS` | 운영자 | 철회(M7) | admin |
| 9 | `SUSPENSION_SCHEDULED` → `SUSPENDED` | 운영자 | 집행 — **소명 기한 경과 후에만** | admin |
| 10 | `IN_PROGRESS`·`SUSPENSION_SCHEDULED` → `SUSPENDED` | 운영자 | **긴급** 직권 중단(M4) | admin |
| 11 | `SUSPENSION_SCHEDULED` → `ENDED` | 시스템 | 집행 전에 `end_at` 도달 — 통지는 `LAPSED` | ✅ 스케줄러 · 7-2 #3 |
| 12 | `ENDED` → `SETTLED` | 정산 모듈 | 이체 완료 통보 | 포트만 |

**`SUSPENDED` · `SETTLED`에서 나가는 전이가 없다.** §29-6 "재개 불가" · 제16조③. `ENDED`에서 나가는 것은 `SETTLED` 하나다 — 시안 B5 "공구를 다시 열 수는 없습니다".

**`PREPARING`에서 `SUSPENDED`로 가는 전이가 없다** — B1·B2에 중단 요청 버튼이 없다. 시작도 안 한, 게이트도 안 채운 공구는 판매가 없으므로 "소비자 주문을 끊는 일"(§29-6 중단의 근거)이 성립하지 않는다. 이 구간의 철회 수단은 기획에 없다(7-2 #1).

### 3-2. 게이트 판정 — `PREPARING` → `READY`

```java
boolean gatesSatisfied =
        groupBuy.getStockConfirmedAt() != null                      // ① 브랜드
     && post != null && post.getSubmittedAt() != null               // ② 인플루언서
     && post.getReviewStatus() == APPROVED;                         // ③ 운영자
```

- 판정은 **게이트를 바꾸는 트랜잭션마다** 한다 — 브랜드 확인(①), 오픈 승인(③). ②(제출)는 그 자체로 ③을 만족시킬 수 없으므로 판정하지 않아도 된다.
- **어느 쪽이 마지막이든 같은 메서드**(`GroupBuyReadiness.promoteIfSatisfied`)를 부른다. 브랜드가 마지막이면 `READY` 전이의 이력 행위자는 브랜드, 운영자가 마지막이면 운영자다 — 시안 B3 이력은 운영자가 마지막인 경우("운영자 오픈 승인 · 준비완료")를 그렸다.
- **동시성** — 브랜드 확인과 운영자 승인이 동시에 들어오면 둘 다 "상대가 아직"으로 읽고 아무도 전이하지 않을 수 있다. **판정 전에 `group_buy` 행을 `PESSIMISTIC_WRITE`로 잠근다.** 게이트 두 개를 잇는 판정은 조건부 UPDATE 한 줄로 표현할 수 없다(게시물 심사 상태가 다른 테이블에 있다).

### 3-3. 스케줄러 — `GroupBuyLifecycleScheduler`

```java
@Scheduled(cron = "0 * * * * *", zone = "Asia/Seoul")   // 매분 0초
public void tick() { open(); end(); autoConfirmFulfillment(); }
```

**1분 주기인 이유** — 기존 `PostAppealDeadlineScheduler`는 1시간이다(기한이 일 단위). 공구는 **"08.14 10:00 시작"을 소비자에게 공지한 시각**이 있다. 1시간 주기면 10:59에 열리는 공구가 생긴다.

| 작업 | 대상 | 한 트랜잭션에서 하는 일 |
| --- | --- | --- |
| `open` | `status = READY AND start_at <= now` | `IN_PROGRESS` · `opened_at = now` · 이력 `OPENED` · 상품 resync · 양측 통지 |
| `end` | `status IN (IN_PROGRESS, SUSPENSION_SCHEDULED) AND end_at <= now` | `ENDED` · **`ended_at = end_at`** · `close_type = COMPLETED` · 대기 연장 → `EXPIRED` · 검토 중 요청·통지 → `LAPSED` · `fulfillment_due_at` 확정 · 이력 `ENDED`(+`EXTENSION_EXPIRED`) · 상품 resync |
| `autoConfirmFulfillment` | 스위치 켜짐 AND `ENDED` AND `fulfillment_due_at <= now` AND 측 행 없음 | `auto_confirmed = true` 행 생성 — **기본 꺼짐**(1-9) |

- **`ended_at = end_at`이지 `now`가 아니다.** 스케줄러가 23:56:00에 돌아도 공구는 23:55에 끝난 것이다. 시안 B5 이력 "2026.08.21 23:55 · 시스템"이 이 값이다. 조기 마감·중단은 판정 시각(`now`)을 쓴다.
- 기존 스케줄러와 같은 전제 — **단일 인스턴스**, 분산 락 없음, `MAX_PER_RUN = 200`, **행마다 별도 트랜잭션**(한 건 실패가 나머지를 막지 않게), 예외는 로그 후 삼킨다.
- **읽기 쪽 보정** — 스케줄러 사이 최대 1분 동안 `status = IN_PROGRESS`인데 `end_at`이 지난 공구가 있다. 구매 판정(앱)은 `status`만 보지 말고 **`end_at > now`도 함께 본다.** 공구 상세 응답의 `timeline`도 `now` 기준으로 계산한다.

### 3-4. 모든 전이는 조건부 UPDATE — 위험한 경합 4쌍

```java
int changed = groupBuyRepository.transition(id, FROM_SET, TO, now);
if (changed == 0) throw new BusinessException(GROUP_BUY_STATUS_CONFLICT);
```

| 경합 | 막는 조건 |
| --- | --- |
| **연장 수락** vs 스케줄러 종료 | 수락 UPDATE에 `AND status = 'IN_PROGRESS' AND end_at = :beforeEndAt AND end_at > :now` — §29-6 "수락 기한 = **현재 종료 시각**. 그 뒤에는 누를 수 없다". 23:54:59 수락과 23:55:00 종료가 겹치면 **하나만** 통과한다 |
| 조기 마감 승인 vs 스케줄러 종료 | `AND status = 'IN_PROGRESS'` — 이미 종료됐으면 요청은 `LAPSED`로 닫혀 있다 |
| 중단 요청 승인 vs 직권 중단 통지 | 둘 다 `IN_PROGRESS`에서 출발 — 한쪽은 0행 |
| 오픈 vs 중단 요청 승인(준비완료) | `READY`에서 둘 다 출발 — 10:00:00에 승인 버튼을 누르면 하나만 이긴다. 오픈이 이기면 승인은 409 → 운영자는 **진행중 공구의 중단**으로 다시 판단한다 |

**연장 수락은 `end_at = :beforeEndAt`까지 본다** — 요청 행이 가진 `before_end_at`과 현재 `end_at`이 다르면(있을 수 없어야 하지만) 연장이 이중 적용된다. 불가능해야 하는 조건에 기대지 않는다.

### 3-5. 이력은 전이와 **같은 트랜잭션**에서 쓴다

`GroupBuyHistoryRecorder`를 서비스에서 직접 호출하고 이벤트 리스너로 분리하지 않는다 — 26 · 3-5와 같다. 특히 **최소 물량 확인 기록은 제25조 제재 판정의 증거**(§29-4)라 이력이 비는 순간 증거가 사라진다.

### 4-3. `summary` — 탭 카운트 + GNB 배지

목록과 분리하는 이유는 계약(26 · 4-4)과 같다 — GNB 배지는 다른 화면에서도 폴링된다.

**`actionRequiredCount` — 브랜드가 지금 조치해야 하는 건수**

| 포함 | 조건 | 화면 |
| --- | --- | --- |

**넣지 않는 것** — B2a(게시물 반려)와 B4j(게시물 숨김)는 경고색이지만 **고칠 권한이 인플루언서·운영자에게 있다**(§29-3 "고칠 권한은 인플루언서"). 배지에 넣으면 브랜드가 **끌 수 없는 배지**가 켜진다. 계약 설계의 배지 정의(26 · 4-4 "공이 상대에게 있는 정상 대기는 넣지 않는다")와 같은 기준이다. 요청 대기(B4a·B4c·B4f·B4g)도 같은 이유로 제외.

### 4-4. 상세 — `GET /v1/seller/group-buys/{id}`

B1~B7a 22종이 **같은 응답 하나**를 쓴다. 화면 분기는 FE가 값으로 고른다.

**`items[].expectedUnitReward`는 `RewardCalculator.calcUnitReward()`로 계산한다** — 계약 응답·정산·계약서 PDF가 쓰는 **같은 메서드**(26 · 1-5). 시안 "리워드율 12% · 예상 리워드 3,264원" = 27,200 × 12% 절사.

**`fixedFee.displayText`를 서버가 만든다** — §29-9 "표준 표기 — **3서피스 문자 단위 동일**":

```
고정 지급비 300,000원 · 지급 시점: 공구 게시물 등록 후 · 브랜드 직접 지급
```

FE 3개가 각자 조립하면 반드시 한 곳의 가운뎃점·띄어쓰기가 어긋난다. 이 문자열 하나는 예외적으로 서버가 짓는다 — "문자 단위 동일"이 규칙 자체이기 때문이다. **`paidAt`은 싣지 않는다** — 계약 응답에는 있지만(자기 신고) 공구 화면은 "「지급 완료」·「미지급」 배지를 두지 않는다"(§29-9).

**`sales` — 상태별로 서버가 내려주지 않는다**

| 상태 | `sales` | 이유 |
| --- | --- | --- |
| `PREPARING` · `READY` | `null` | 체크리스트 자리 |
| `IN_PROGRESS` · `SUSPENSION_SCHEDULED` | **실시간 KPI** · `basis = LIVE` | §30-3 "체크리스트가 KPI로 교체" |
| **`ENDED`** | **`null`** | §30-4 "**종료 화면에 KPI를 두지 않는다** — 잠정치가 지급액으로 오해된다" |
| `SETTLED` | 정산 모듈의 **확정 실적** · `basis = SETTLED` | B6 |
| `SUSPENDED` | 중단 시점 실적 · `basis = AT_SUSPENSION` | B7 "확정 시 변동" |

**FE가 감추는 게 아니라 서버가 안 내려준다.** 종료 KPI 금지는 "같은 숫자가 두 상태에서 뜻하는 바가 다르다"는 **의미 규칙**이고, 응답에 값이 있으면 3서피스 중 어느 한 곳은 결국 그린다. `rewardAmount`는 항목별 수량 × `calcUnitReward`의 합이다.

**`orderClosure`** — `IN_PROGRESS`(레일 "미종결 주문 12건 처리하기 ↗") · `ENDED`(B5 "18건 / 전체 312건") · `SUSPENDED`에서 채운다. **포트가 비어 있으면 `null`**(0-6). 경로별 내역은 싣지 않는다 — §29-11 "공구 화면은 **남은 건수만** 센다".

**`timeline`** — "시작까지 8일" · "진행 3일차 · 종료까지 5일" · "기간 진행 3일 / 8일". 일수는 `Contract.periodDays()`와 **같은 양끝 포함 일자 계산**을 쓰고, 서버 `now`(Asia/Seoul) 기준이다. FE 시계를 믿지 않는다.

**`extension.maxDays`** — C1 "연장 일수를 넣으면 새 종료일과 총 기간이 **즉시 계산**돼 30일 상한에 걸리는지 그 자리에서 보인다". 상한을 FE가 알아야 즉시 계산할 수 있다. `maxDays = 30 − totalDays`(4-6).

**`history[]` 호칭** — 운영자 주체는 `actorType = ADMIN`만 내리고 표시 문구는 FE가 고른다(26 · 1-6). §29-13은 파트너센터 호칭을 「어드민」으로, 시안 rev.4는 「운영자」로 적었다 — 서버 영향이 없도록 문구를 내리지 않는 것이 이 어긋남의 해법이다(7-1 #9).

### 4-5. `permissions` — 서버가 판정한다

| 필드 | 조건 |
| --- | --- |
| `canConfirmStock` | `PREPARING` · `stock_confirmed_at IS NULL` |
| `canRequestExtension` | `IN_PROGRESS` · 연장 행 **없음** · `now < end_at − 12h` · **요청 차단 조건 없음** |
| `canRequestEarlyClose` | `IN_PROGRESS` · 요청 차단 조건 없음 |
| `canRequestSuspension` | `READY` 또는 `IN_PROGRESS` · 요청 차단 조건 없음 |
| `canSubmitAppeal` | `SUSPENSION_SCHEDULED` · `NOTICED` 통지 · 미제출 · `now <= appeal_deadline_at` |
| `canOpenIssue` | (`ENDED` 또는 **브랜드가 요청하지 않은** `SUSPENDED`) · 열린 이슈 없음 |
| `canCheckFulfillment` | `ENDED` · 내 측 행 없음 |
| `canOpenPairThread` | 계약에 `connection`이 있음 |

**요청 차단 조건** — 셋 중 하나라도 있으면 연장·조기 마감·중단 요청이 **모두** 막힌다.

| 차단 | 근거 |
| --- | --- |
| 검토 중(`PENDING`) 중단·조기 마감 요청이 있음(요청자 무관) | §29-6 "검토 중 추가 요청 불가" · B4a·B4f·B4g 액션 없음 |
| `SUSPENSION_SCHEDULED` | B4i 액션은 소명뿐 |
| 게시물 숨김 중 | B4j "기간 연장·조기 마감·중단 요청은 **숨김이 풀린 뒤에** 하세요" |

**대기 중인 연장은 차단 조건이 아니다** — B4c "중단 요청만" 가능.

> ⚠️ **이 규칙은 시안의 버튼 조합보다 넓다.** 시안은 결과 화면마다 버튼을 손으로 골랐고, 원칙으로 환원하면 네 칸이 다르다 — 원칙은 아래 칸에서 **버튼을 하나 더 보여준다.**
>
> | 화면 | 시안 | 원칙 | 차이 |
> | --- | --- | --- | --- |
> | B4c 연장 대기 | 중단 | 중단 · **조기 마감** | 조기 마감 |
> | B4d 연장 수락 | 중단 | 중단 · **조기 마감** | 조기 마감 |
> | B4e 연장 거절 | 중단 | 중단 · **조기 마감** | 조기 마감 |
> | B4b 중단 반려 | 연장 · 중단 재요청 | 연장 · 중단 · **조기 마감** | 조기 마감 |
> | B4h 조기 마감 반려 | 연장 · 조기 마감 재요청 | 연장 · 조기 마감 · **중단** | 중단 |
>
> 시안처럼 좁힐 **규칙상 근거가 기획에 없다** — 예컨대 연장을 거절당한 브랜드가 재고 소진으로 조기 마감을 못 할 이유가 없다. **원칙으로 집행하고 기획에 확인을 요청한다**(7-1 #2). 좁히기로 확정되면 `permissions` 판정만 바꾸면 되고 스키마·API는 그대로다.

`permissions`를 FE가 복제하지 않게 하는 이유는 계약과 같다 — 조건이 상태 × 요청 × 통지 × 게시물 × 시각으로 갈린다. **실행 API는 같은 판정 메서드(`GroupBuyPermissionPolicy`)를 다시 호출해** 409로 막는다. 버튼 판정과 집행 판정이 한 메서드라 어긋날 수 없다.

### 4-6. 실행 API

#### `POST /{id}/stock-confirmation` — B1 `[확보 완료]`

바디 없음.

- 조건부 UPDATE: `SET stock_confirmed_at = :now, stock_confirmed_by = :sellerId WHERE id = :id AND status = 'PREPARING' AND stock_confirmed_at IS NULL` → 0행이면 409 `GROUP_BUY_STOCK_ALREADY_CONFIRMED` 또는 `STATUS_CONFLICT`.
- 이력 `STOCK_CONFIRMED` · detail에 **최소 물량 스냅샷**("크림 300개 · 세럼 200개") — 제재 판정 때 "무엇을 확인했는지"가 이력만으로 읽혀야 한다.
- 이어서 게이트 판정(3-2) — 운영자 승인이 이미 끝났으면 **이 요청이 `READY`를 만든다.**
- **되돌리는 API가 없다** — `[미정: 효력·해제]`(§33-1 #10). 해제를 열면 제25조 증거가 지워질 수 있다. 확정 전까지 만들지 않는다.
- **서버는 재고를 판정하지 않는다** — `product_variant.stock`과 최소 물량을 비교하지 않는다. 시안 머리말 "시스템이 재고를 판정할 수 없으므로 **브랜드의 자기 확인**". 재고 필드는 판매 가능 수량이지 공구용 확보 물량이 아니다.

#### `POST /{id}/extension-request` — C1

```json
{ "extensionDays": 7, "reason": "수요가 예상보다 많음" }
```

| 검증 | 실패 |
| --- | --- |
| `canRequestExtension`(4-5) | 409 |
| 연장 행 존재(동시 요청은 UNIQUE 위반 번역) | 409 `GROUP_BUY_EXTENSION_ALREADY_USED` |
| `now >= end_at − 12h` | 409 `GROUP_BUY_EXTENSION_WINDOW_CLOSED` — C1 "공구 종료 **12시간 전까지만**" |
| `extensionDays < 1` | 400 |
| 연장 후 총 일수 > **30** | 400 `GROUP_BUY_EXTENSION_EXCEEDS_LIMIT` |
| `reason` 300자 초과 | 400 |

- **새 종료 = `end_at + extensionDays일`** — 시각은 그대로(23:55). C1 "시작일은 변경할 수 없습니다".
- **총 30일의 기준은 `start_at` 일자부터 새 종료 일자까지(양끝 포함)** — 계약 H4와 같은 계산(`Contract.periodDays`)이다. 시안의 "1~22일"은 8일 공구에서 파생된 **예시값**이지 고정 상한이 아니다(§33-1 #6 "상한 22일 · 총 30일" — 22는 30 − 8).
- 요청만으로 `end_at`은 **바뀌지 않는다.** 수락(스튜디오 API)이 3-4의 조건부 UPDATE로 바꾼다.
- 상한 30 · 컷오프 12시간은 `GroupBuyProperties`의 설정값 — 둘 다 `[근거 대기]`다.

#### `POST /{id}/early-close-request` — C3

```json
{ "reasonCode": "STOCK_OUT", "memo": "크림 잔여 재고가 40개 미만…" }
```

- `canRequestEarlyClose` · `reasonCode ∈ {STOCK_OUT, TARGET_REACHED, ETC}` · `ETC`면 `memo` 필수(400 `GROUP_BUY_REASON_MEMO_REQUIRED`) · 메모 1,000자.
- INSERT `status = PENDING` · `status_at_request` · 판매 스냅샷(포트가 있으면) — **생성 컬럼 UNIQUE 위반 = 409 `GROUP_BUY_REQUEST_ALREADY_PENDING`**.
- 공구 상태는 **그대로** `IN_PROGRESS`. 이력 `EARLY_CLOSE_REQUESTED` · 어드민 통지.
- **반려 후 재요청을 막지 않는다** — B4h `[조기 마감 재요청]`. 횟수 제한은 §33-1 #4(남용 방지) 확정 후.

#### `POST /{id}/suspension-request` — C2 · C4

```json
{ "reasonCode": "QUALITY_ISSUE", "memo": "입고분에서 용기 불량…" }
```

- 조기 마감과 같은 검증 · `reasonCode ∈ {QUALITY_ISSUE, PRICE_TERMS_ERROR, NEGOTIATION_BROKEN, ETC}`.
- **`READY`에서도 받는다(C4).** §29-6 표는 "가능 시점: 진행중"이지만 §30-5가 C4를 "준비완료 · 시작 전" 모달로 명시하고 시안 B3에 버튼이 있다 — 브랜드 명세가 더 구체적이라 따른다(7-1 #3).
- `status_at_request`를 저장하는 이유 — C2와 C4는 "같은 상태값으로 귀결되고 **문구만 분기**"한다(§30-5). 어드민 승인 모달(M2)도 "주문 환불·배송 의무" 고지가 이 값에 따라 달라진다.
- 요청만으로 판매는 **멈추지 않는다**(제16조②) — 상태 불변. 응답·상세 배너의 "배송을 멈추지 마세요"는 FE 문구지만, **이 사실(요청 ≠ 집행)을 서버가 상태로 보장한다.**

#### `POST /{id}/appeal/attachments` → `POST /{id}/appeal` — C9

```json
// 1) presign
{ "fileName": "시험성적서.pdf", "contentType": "application/pdf", "sizeBytes": 812345 }
// → { "attachmentId": 31, "uploadUrl": "https://…", "expiresAt": "…" }

// 2) 제출
{ "content": "해당 표현은 …", "attachmentIds": [31] }
```

- 첨부: `content_type ∈ {image/png, image/jpeg, application/pdf}` · 10MB · 제출 시 **HeadObject로 실재·크기 재검증** — 연결·소통 첨부와 같은 흐름.
- 제출 조건부 UPDATE: `WHERE admin_suspension_id = :sid AND status = 'NOTICED' AND appeal_submitted_at IS NULL AND appeal_deadline_at >= :now` → 0행이면 `APPEAL_ALREADY_SUBMITTED` / `APPEAL_DEADLINE_PASSED` / `APPEAL_NOT_OPEN`을 구분해 409.
- **제출 후 수정 API가 없다** — C9 "제출 후에는 수정할 수 없습니다". 소명은 운영자가 **판단 근거로 읽은 글**이라 바뀌면 판정의 근거가 흔들린다.
- 상태는 **그대로** `SUSPENSION_SCHEDULED`. 이력 `APPEAL_SUBMITTED` · 어드민 통지(조치 큐 「소명 검토」 §32-1).
- `content` 필수(2,000자) · 첨부는 선택.

#### `POST /{id}/issues` — C5

```json
{ "issueType": "CONTENT_FULFILLMENT", "content": "계약상 스토리 3건인데…" }
```

- `canOpenIssue` · 유형 4종 · 내용 필수(2,000자) · 열린 이슈 있으면 409 `GROUP_BUY_ISSUE_ALREADY_OPEN`(생성 컬럼 UNIQUE).
- 스레드 포트로 3자 스레드를 열고(5-3) `thread_id`를 저장한다. **포트 호출과 INSERT가 같은 트랜잭션** — 스레드만 생기고 이슈 행이 없거나 그 반대가 되면 B5e의 "중복 개설 방지"가 깨진다.
- 공구 상태 **불변**(§29-10 "이슈는 상태가 아니다"). 정산 보류도 **하지 않는다** — B5e "이슈가 열려 있어도 정산도 예정대로 진행된다".
- 응답: `{ issueId, threadId }` — FE가 `스레드로 이동 ↗`에 쓴다.

#### `POST /{id}/fulfillment-check` — C6 · C7

```json
{ "result": "UNFULFILLED", "reason": "계약상 스토리 3건인데 2건만…" }
```

- `canCheckFulfillment` · `result ∈ {FULFILLED, UNFULFILLED}` · `UNFULFILLED`면 `reason` 필수(400 `GROUP_BUY_FULFILLMENT_REASON_REQUIRED`).
- INSERT — `UNIQUE(group_buy_id, checker_side)` 위반 = 409 `GROUP_BUY_FULFILLMENT_ALREADY_CHECKED`. **불가역**(제20조②) — 수정·삭제 API 없음.
- `UNFULFILLED`면 **같은 트랜잭션에서** 3자 스레드 개설(첫 글 = `reason`) → `thread_id` 저장 → 정산 보류(파생). 이력 `FULFILLMENT_DISPUTED`.
- **확인 대상은 상대의 의무다** — 브랜드 요청은 항상 `checker_side = SELLER`로 저장되고, 뜻은 "**인플루언서의 콘텐츠 의무**를 확인했다"이다(§29-10). 응답·상세의 `mine`/`theirs` 라벨이 이 방향을 담는다.
- 기한이 지나도 받는다 — 자동 이행 스위치가 꺼져 있는 동안 기한은 표시값이다(1-9).

## 5. 다른 모듈과의 연계 — 포트

| 방향 | 대상 | 포트 / 호출 | 이번 범위 |
| --- | --- | --- | --- |
| 입력 | 계약 관리 | `AdminContractCommandService.conclude()` → `GroupBuyFactory` | ✅ 2절 |
| 입력 | 계약 관리 | `contract` · `contract_item` 조회(불변 원본) | ✅ |
| 입력 | 상품 관리 | 상품명 링크(새 탭) · `groupBuyStatus` 동기화 | ✅ 1-11 |
| 입력 | 쇼룸 게시물 | `group_buy_post` 읽기 | ✅ 읽기 · 쓰기는 스튜디오 설계 |
| 출력 | 판매 관리 | `GroupBuySalesReader` | 포트 + 빈 구현 |
| 출력 | 정산 관리 | `GroupBuySettlementGateway` | 포트 + 빈 구현 |
| 양방향 | 연결·소통 | `GroupBuyThreadGateway` | 포트 · **선행 변경 필요** |

**기획 제외 패키지(CLAUDE.md)를 건드리지 않는다** — 마켓 해석은 `MarketRepository`로 하고(`api.seller.market.service.MarketService` 미사용), 쿠폰·리뷰·필터와 접점이 없다.

### 5-1. 판매 — `GroupBuySalesReader`

```java
public interface GroupBuySalesReader {
    /** 취소·반품 반영 판매 실적. 판매 모듈이 없으면 empty — 0이 아니다(0-6). */
    Optional<GroupBuySales> readSales(Long groupBuyId);
    /** 전체·종결·미종결 주문 건수. §29-11 종결 경로 5종의 판정은 판매 모듈이 한다. */
    Optional<GroupBuyOrderClosure> readClosure(Long groupBuyId);
}
```

판매 모듈이 이 포트를 구현하려면 **주문에 공구 귀속이 필요하다** — `order_product`에 `group_buy_id`(+ 결제 당시 공구가) 컬럼이 있어야 "이 공구의 주문"을 셀 수 있다. 지금 `OrderProduct`에는 없다. **판매 관리 설계의 선행 요구사항으로 넘긴다.**

§29-11의 **"거절 확정 = 즉시 구매확정"**과 **종결 경로 5종**도 판매 모듈의 판정 규칙이다. 공구는 결과 건수만 받는다 — "같은 표를 다시 그리면 두 화면의 숫자가 어긋난다".

### 5-2. 정산 — `GroupBuySettlementGateway`

| 방향 | 메서드 | 의미 |
| --- | --- | --- |
| 정산 → 공구 | `GroupBuyCommandService.markSettled(groupBuyId, transferredAt)` | `ENDED` → `SETTLED` · 이력 `SETTLED` |
| 정산 → 공구 | `recordSalesFinalized(groupBuyId, finalizedAt)` | 이력 `SALES_FINALIZED`(B6 "전 주문 종결 · 실적 확정") |
| 공구 → 정산 | `isSettlementReady(groupBuyId)` | `ENDED` ∧ 미종결 0 ∧ 양측 이행 확인 ∧ 보류 아님 |

**정산 상태머신(정산대기 → 운영자 확인 → 이체완료)은 공구에 두지 않는다** — §32-6 "정산 상태머신은 **어드민에만** 있다 · 양측에는 받았는지 아직인지만 의미가 있다". 공구가 아는 것은 `SETTLED` 하나다.

**정산 명세(수수료·PG·원천징수)를 공구에서 계산하지 않는다**(§29-11). 상세 `sales`의 `SETTLED` 값도 정산 모듈이 확정한 숫자를 **그대로** 받는다.

### 5-3. 스레드 — `GroupBuyThreadGateway` 🚧 선행 변경 필요

| 용도 | 필요한 것 | 현재 |
| --- | --- | --- |
| 「스레드 열기」(B1~B7) | 브랜드-인플루언서 **PAIR 스레드 id** | ✅ `contract.connection` → `message_thread`(1:1)로 해석 가능 |
| 이슈 스레드(C5) · 미이행 3자 스레드(C7) | **같은 쌍의 두 번째 스레드** + 운영자 참여 | ❌ `message_thread.connection_id` **UNIQUE** — 쌍당 스레드 1개 |

`MessageThread` 주석이 명시한다 — "CONNECTION에 1:1로 종속된다 · 스레드의 정체성은 전부 CONNECTION에서 파생". 이슈 스레드는 **정체성이 공구·이슈에서 오는 스레드**라 이 모델에 들어가지 않는다.

**권장안** — 연결·소통 설계에서 `message_thread`에 `thread_kind`(`CONNECTION` / `GROUP_BUY_ISSUE` / `GROUP_BUY_FULFILLMENT`)와 `subject_id`를 더하고, `connection_id` UNIQUE를 `kind = CONNECTION`에 한정한다. 참여자는 기존 `thread_participant`(`ParticipantType.ADMIN`이 이미 있다)로 3자가 된다.

**기각한 대안** — PAIR 스레드에 운영자를 참여자로 추가하고 첫 글만 쓰는 방식. 테이블 변경이 없지만 ① 운영자가 **그 쌍의 모든 대화**를 영구히 보게 되고 ② B5e의 "답변 대기 · 콘텐츠 이행 문제" 같은 **이슈 단위 상태**를 담을 곳이 없고 ③ 제20조⑤ "양측 동의로 종결"의 종결 대상이 스레드 전체가 된다.

→ **이 결정은 연결·소통 소관이다.** 공구는 포트에만 의존하고, 포트 구현이 없으면 `POST /issues` · 미이행 제출(P7)을 **배포하지 않는다**(6절).

**종결 통보** — 연결·소통이 스레드 종결(양측 동의)을 `GroupBuyCommandService.resolveFulfillmentDispute(…)` / `closeIssue(…)`로 알려준다. 공구 모듈이 스레드를 폴링하지 않는다.
