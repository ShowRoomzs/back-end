### 공통 확인 방법

1. 화면 표시, API 원값, DB 변화를 함께 기록한다. 버튼 노출의 기준은 서버 플래그다 — 06a `groups[].actions`, 06b `canAcceptDispute` · `canRefundUnanswered`, 06c `executable`. `false`면 **숨김**이다(비활성 아님 · §37-4).
2. 쓰기 성공 후 영향받는 화면을 모두 다시 조회한다 — 06a 상세 · 06b 상세 · 06c 목록/상세 · 06d 목록/요약, 파트너센터 주문/클레임, 소비자 앱 주문 내역.
3. 실패 요청은 HTTP 상태와 응답 `code`를 확인하고, 큐 행 · 이력 · 결제 취소 · 재고 · 클레임 상태에 부수 효과가 없는지 본다. **주의** — `INVALID_INPUT_VALUE` · `ORDER_PAGE_SIZE_INVALID` · `ORDER_SEARCH_RANGE_INVALID`는 응답 `code`가 모두 `INVALID_INPUT`이다. enum 이름이 아니라 메시지로 구분한다.
4. 돈이 움직이는 케이스는 매번 **PG 호출 횟수 · `payment.cancelled_amount` · `payment_cancel` 행 · `order_refund_task.status/attempt/executed_by`** 넷을 같이 확인한다.
5. 운영자 조치의 이력은 `actor_type = ADMIN`이어야 하고, 환불 이력 `detail`은 `RFD-{id} · `로 시작해야 한다(06c 상세 `history[]`가 이 접두로 고른다).
6. 시안 · 명세와 코드가 충돌하면 9절에 기록하고 어느 한쪽으로 임의 통과시키지 않는다.
