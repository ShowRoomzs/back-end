## 0. 통신 방식 결정 — 폴링(CRUD), SSE 불필요

기획 §13-1에 **"게시판형이며 실시간이 아니다(거래플로우 §3). 알림은 안 읽은 수 배지만 표시하고, 새 메시지 도착 시 팝업·토스트를 띄우지 않는다"** 가 명시돼 있다. §14-4의 연결 요청 도착도 **"즉시 팝업 없이 배지로만 누적"** 이다.

→ **전 구간 REST CRUD로 구현하고 SSE/WebSocket은 넣지 않는다.** 화면 갱신은 스레드 진입/탭 전환 시 재조회 + GNB 배지용 카운트 폴링(권장 30~60초)으로 충분하다. 실시간 채널을 붙이면 기획이 명시적으로 배제한 도착 알림 UX를 전제하게 되고, 운영 비용만 늘어난다.

- 배지 전용 경량 엔드포인트를 따로 두어 폴링 비용을 낮춘다(§3의 `/summary`).

## 1. 도메인 모델

신규 패키지: `showroomz.domain.connection`, `showroomz.domain.message`

### 1-1. `CONNECTION` — [2026.08 결정 반영] 브랜드↔인플루언서만이 아니라 운영자↔브랜드 · 운영자↔인플루언서도 동일 객체로 취급

**결정 사항** — 운영자 고정 채널(§13-3·§14-6, 미결 #7)을 브랜드-인플루언서 쌍과 **별도 객체로 특수 취급하지 않는다.** "운영자와 브랜드", "운영자와 쇼룸(인플루언서)"도 브랜드-인플루언서 쌍과 **완전히 같은 연결·스레드 모델을 그대로 재사용**하고, 운영자를 그 연결의 한쪽 당사자(counterparty)로 놓는다. `TYPE` 한 컬럼만 추가해서 세 가지 쌍을 구분한다.


| TYPE               | 당사자         | 요청·수락 절차                        |
| ------------------ | ----------- | ------------------------------- |
| `PAIR`             | 브랜드 + 인플루언서 | 있음 (§13-6)                      |
| `OPERATOR_MARKET`  | 운영자 + 브랜드   | **없음** — 입점 승인 시 자동 `CONNECTED` |
| `OPERATOR_CREATOR` | 운영자 + 인플루언서 | **없음** — 등록 승인 시 자동 `CONNECTED` |


**쌍(또는 운영자-당사자)당 1행으로 유지하고 status만 전이시킨다.** 기획 §13-4(스레드는 쌍당 1개, 재연결 시 동일 스레드로 이어짐) + §13-6(같은 쌍의 동시 유효 연결 1개만)을 이제 `PAIR`/`OPERATOR_MARKET`/`OPERATOR_CREATOR` 세 타입 모두에 **동일한 DB 제약 하나로** 보장한다.


| 컬럼                           | 타입                        | 비고                                                        |
| ---------------------------- | ------------------------- | --------------------------------------------------------- |
| `CONNECTION_ID`              | BIGINT PK                 |                                                           |
| `TYPE`                       | VARCHAR(20)               | `PAIR` / `OPERATOR_MARKET` / `OPERATOR_CREATOR`           |
| `MARKET_ID`                  | BIGINT FK → MARKET, NULL  | `PAIR`·`OPERATOR_MARKET`에서만 값 존재                          |
| `CREATOR_ID`                 | BIGINT FK → CREATOR, NULL | `PAIR`·`OPERATOR_CREATOR`에서만 값 존재                         |
| `STATUS`                     | VARCHAR(20)               | `REQUESTED` / `CONNECTED` / `REJECTED` / `DISCONNECTED`   |
| `REQUESTED_AT`               | DATETIME                  | 마지막 요청 시각 (요청함 "2일 전" 표기용) — OPERATOR_* 는 생성 시각과 동일값으로 채움 |
| `RESPONDED_AT`               | DATETIME                  | 수락/거절 시각                                                  |
| `DISCONNECTED_AT`            | DATETIME                  | 해제 시각                                                     |
| `created_at` / `modified_at` |                           | `BaseTimeEntity`                                          |


- `**UNIQUE` 제약의 함정**: `UNIQUE(TYPE, MARKET_ID, CREATOR_ID)`를 그대로 걸면 안 된다 — MySQL/InnoDB는 **NULL을 서로 다른 값으로 취급**해서 유니크 검사를 통과시키므로, `CREATOR_ID`가 항상 NULL인 `OPERATOR_MARKET` 행은 같은 `MARKET_ID`로 몇 개든 중복 생성될 수 있다. 그래서 `MARKET_ID_KEY = COALESCE(MARKET_ID, 0)` / `CREATOR_ID_KEY = COALESCE(CREATOR_ID, 0)` **생성 컬럼(generated column)을 만들어 `UNIQUE(TYPE, MARKET_ID_KEY, CREATOR_ID_KEY)`로 건다.** 이 한 방으로 §13-6 "동시 유효 연결 1개"가 세 타입 모두에서 성립한다.
- 상태 전이 이력이 필요하면 `CONNECTION_HISTORY`를 별도 append-only 테이블로 분리(§13/§14에 이력 화면 요구는 없음 → **Phase 5 선택 항목**).
- `**PAIR` 전이표**: `REQUESTED → CONNECTED`(수락) / `REQUESTED → REJECTED`(거절) / `CONNECTED → DISCONNECTED`(해제) / `REJECTED·DISCONNECTED → REQUESTED`(재요청). **자동 수락 없음**(§14-4) — 요청은 반드시 인플루언서의 명시적 수락을 거친다.
- `**OPERATOR_MARKET`/`OPERATOR_CREATOR` 전이표 — [2026.08 확정]**: **상태 전이가 아예 없다.** 승인 즉시 `CONNECTED`로 생성되고, **탈퇴 전까지 계속 `CONNECTED`로 유지**된다(휴면 없음 — §13-4의 "연결 해제 시 휴면" 규칙은 `PAIR`에만 적용되고 `OPERATOR_`*에는 적용하지 않기로 결정). 즉 이 타입에는 `REQUESTED`/`REJECTED`/`DISCONNECTED`가 실질적으로 쓰이지 않는다.
  - 탈퇴 시점에 이 연결에 별도 훅을 걸 필요도 없다 — 탈퇴 회원은 **이미 기존 인증 로직에서 API 호출 자체가 막힌다**(`Market.status=WITHDRAWN` / `Creator.getUser().getStatus()=UserStatus.WITHDRAWN`, `AuthService`·`UserService`의 기존 탈퇴 가드). 스레드 상태를 따로 `DORMANT`로 바꾸지 않아도 쓰기가 자연히 차단되므로, 이 기능을 위해 탈퇴 이벤트에 새로 개입할 필요가 없다.
  - 어드민이 탈퇴한 브랜드·인플루언서의 과거 운영자 채널을 기록 조회용으로 열람하는 것 자체는 막을 이유가 없다(항상 `OPEN` 상태이므로 읽기는 그대로 된다).
- **가짜 Market/Creator 로우를 만들지 않는다** — "운영자"를 표현하려고 `MARKET`/`CREATOR` 테이블에 SHOWROOMZ용 더미 행을 넣는 방식은 채택하지 않는다. 실제 브랜드·인플루언서 목록 조회 등 기존 쿼리에 가짜 데이터가 섞여 들어가는 부작용이 크다. 대신 `MARKET_ID`/`CREATOR_ID`를 둘 다 NULL 허용으로 열어두고, 운영자 쪽 당사자는 애플리케이션 레벨에서 `SENDER_TYPE=ADMIN`(1-5 참고)로만 식별한다.

### 1-2. 연결코드 — `CREATOR.CONNECTION_CODE`

§13-6: **쇼룸별 고정(영구)**, 인플루언서가 재발급 가능. 별도 테이블 없이 `CREATOR`에 컬럼 추가가 적절하다.


| 컬럼                                   | 비고                        |
| ------------------------------------ | ------------------------- |
| `CONNECTION_CODE` VARCHAR(16) UNIQUE | 대문자+숫자, 혼동 문자(0/O/1/I) 제외 |
| `CONNECTION_CODE_ISSUED_AT` DATETIME | 재발급 시각                    |


- 생성 시점: 크리에이터 등록 완료(`completeRegistration`) 시. 기존 크리에이터는 마이그레이션에서 백필.
- 재발급 API는 BE에서 먼저 만들어 둔다 — **스튜디오 시안에 코드 표시·재발급 UI가 아직 없음(§13-12 미결 1·§14-8)**. FE 나오기 전이라도 BE는 막히지 않는다.
- 코드 조회는 **인증된 브랜드만**, 그리고 **레이트 리밋 필수** — 코드 대입으로 인플루언서를 열거할 수 있는 표면이다.

### 1-3. `MESSAGE_THREAD` — [재설계] `CONNECTION`에 1:1로 종속

1-1의 결정에 따라 스레드도 더 이상 별도의 `TYPE`/`MARKET_ID`/`CREATOR_ID`를 들고 있지 않는다 — **스레드의 정체성(누구와 누구의 대화인지)은 전부 `CONNECTION`에서 파생**되므로, 스레드는 그냥 `CONNECTION_ID`를 참조하기만 하면 된다. `PAIR`든 `OPERATOR_MARKET`이든 `OPERATOR_CREATOR`든 스레드 쪽 로직은 완전히 동일하다.


| 컬럼                                  | 비고                                                         |
| ----------------------------------- | ---------------------------------------------------------- |
| `THREAD_ID` BIGINT PK               |                                                            |
| `CONNECTION_ID` BIGINT FK, UNIQUE   | `CONNECTION` 1:1 — 스레드 종류는 이 FK를 통해 `CONNECTION.TYPE`으로 판정 |
| `STATUS` VARCHAR(20)                | `OPEN` / `DORMANT`(휴면)                                     |
| `LAST_MESSAGE_AT` DATETIME          | 목록 정렬용                                                     |
| `LAST_MESSAGE_PREVIEW` VARCHAR(255) | 목록 1줄 미리보기 (역정규화)                                          |


- 스레드 생성 시점: `**CONNECTION.STATUS`가 처음 `CONNECTED`가 되는 순간**. `PAIR`는 수락 시, `OPERATOR_MARKET`/`OPERATOR_CREATOR`는 승인 즉시(요청 단계가 없으므로 생성과 동시에 `CONNECTED`) — 결국 셋 다 "같은 훅"(연결이 `CONNECTED`로 바뀌는 이벤트)에서 스레드를 만들면 된다. 별도의 "운영자 채널 생성 로직"을 딴 데 만들 필요가 없다.
- 기존 브랜드·크리에이터는 마이그레이션에서 `OPERATOR_MARKET`/`OPERATOR_CREATOR` `CONNECTION` + `MESSAGE_THREAD`를 함께 백필한다(1-7 V94).
- 휴면(§13-4): `CONNECTION`이 `DISCONNECTED`되면 `DORMANT`, 다시 `CONNECTED`되면 `OPEN`. **열람 가능·작성 불가.** 이 전이는 `**PAIR`에만 해당** — `OPERATOR_MARKET`/`OPERATOR_CREATOR`는 1-1에서 확정한 대로 상태 전이가 아예 없으므로 휴면에 빠지지 않는다.

### 1-4. `THREAD_PARTICIPANT` — 읽음 상태


| 컬럼                                                                              | 비고                     |
| ------------------------------------------------------------------------------- | ---------------------- |
| `THREAD_ID` / `PARTICIPANT_TYPE`(`SELLER`/`CREATOR`/`ADMIN`) / `PARTICIPANT_ID` | 복합 UNIQUE              |
| `LAST_READ_MESSAGE_ID` BIGINT                                                   | 안 읽은 수 = 이 id 초과 메시지 수 |
| `LAST_READ_AT` DATETIME                                                         |                        |


- `**PAIR` 스레드**의 운영자 열람(§13-4)은 **모니터링 열람**이므로 ADMIN 참가자 행을 두지 않거나(또는 두더라도) 읽음 계산에서 제외한다 — 운영자는 이 스레드의 당사자가 아니다.
- `**OPERATOR_MARKET`/`OPERATOR_CREATOR` 스레드**는 다르다 — 여기서 ADMIN은 §13-4 표의 "운영자 열람"이 아니라 **연결의 실제 당사자**(브랜드·인플루언서와 대칭)이므로, `SELLER`/`CREATOR`와 동일하게 정상적으로 안 읽은 수를 추적한다.

### 1-5. `MESSAGE`


| 컬럼                              | 비고                                                |
| ------------------------------- | ------------------------------------------------- |
| `MESSAGE_ID` BIGINT PK          |                                                   |
| `THREAD_ID` FK                  |                                                   |
| `SENDER_TYPE` / `SENDER_ID`     | `SELLER` / `CREATOR` / `ADMIN`                    |
| `CONTENT` TEXT NULL             | 첨부만 전송 시 null (§13-11)                            |
| `CLIENT_MESSAGE_ID` VARCHAR(64) | **멱등키** — `UNIQUE (THREAD_ID, CLIENT_MESSAGE_ID)` |
| `created_at`                    | 타임스탬프                                             |


- **재전송 멱등(§13-10)**: FE가 메시지 생성 시 UUID를 발급해 보내고, 재전송은 **같은 키로 재요청**한다. 서버는 유니크 충돌 시 신규 저장 대신 **기존 메시지를 200으로 반환**한다. "재전송해도 중복 생성되지 않는다"는 기획 확정 요구를 이 한 가지 규칙으로 만족시킨다.
- `CONTENT`와 첨부가 **둘 다 비면 400**.

### 1-6. `MESSAGE_ATTACHMENT`

| ------------------------------- | ---------------------------------------------------------------------------------------- |

| `FILE_URL` VARCHAR(1024)        | CloudFront URL                                                                           |
| `ORIGINAL_NAME` VARCHAR(255)    | 화면 표기용 원본 파일명                                                                            |
| `EXTENSION` VARCHAR(16)         | FE의 확장자→아이콘 매핑 키 (§13-8)                                                                 |
| `CONTENT_TYPE` VARCHAR(128)     |                                                                                          |
| `SIZE_BYTES` BIGINT             | **HeadObject 실측값** — 500MB 합산 검증은 이 값 기준                                                 |
| `DURATION_SECONDS` INT NULL     | 영상 재생시간 표기(§13-8) — **FE가 `loadedmetadata`로 읽어 `complete` 시 전달하는 참고값**(4-4)              |
| `SORT_ORDER` INT                | 그리드 순서 — presign이 아니라 **전송 시 `attachmentIds` 배열 index로 채움**(4-5)                         |
| `created_at` / `modified_at`    | `BaseTimeEntity` — 고아 파일 정리 스케줄러가 `PENDING` 방치 시간 판정에 사용(4-6)                            |


- 인덱스: `INDEX (MESSAGE_ID, SORT_ORDER)` — 메시지 조회 시 첨부를 순서대로 끌어오는 주 경로. 고아 정리용으로 `INDEX (STATUS, created_at)`도 함께 건다.

## 2. 서버 검증 규칙 (§13-7 · §0-2 원칙)

클라이언트 검증은 우회 가능하므로 **전송 API에서 서버가 다시 판정**한다.


| 검증           | 내용                                                                                        | 위반 시               |
| ------------ | ----------------------------------------------------------------------------------------- | ------------------ |
| 첨부 개수        | 메시지 1건당 **최대 20개**                                                                        | 400 + 전용 ErrorCode |
| 첨부 총 용량      | 메시지 1건당 합계 **500MB**                                                                      | 400 + 전용 ErrorCode |
| 확장자          | **허용 목록 방식**(2-1 참고) — 통상 업무 파일은 폭넓게 허용, 실행·스크립트 계열만 차단                                   | 400                |
| 참가자          | 요청자가 해당 스레드 참가자인지                                                                         | 403                |
| **첨부 소유·귀속** | 첨부가 **요청자 본인이 올린 것**이고 **같은 스레드에 속하며** 아직 다른 메시지에 안 붙었는지 (4-5)                            | 403 / 409          |
| 스레드 상태       | `DORMANT`면 작성 불가 — **목록엔 애초에 안 뜨므로(3-1 참고) UI로는 도달 불가, 캐시된 threadId로 직접 호출하는 경우를 막는 방어용** | 409                |
| 중복 연결        | 이미 `CONNECTED`/`REQUESTED`면 재요청 차단                                                        | 409                |


**두 축은 독립이다** — 개수 통과 + 용량 초과도 전송 불가. 검증 순서를 개수 → 용량으로 고정해 오류 문구가 화면과 일치하게 한다.

신규 ErrorCode(안):
`CONNECTION_ALREADY_EXISTS`, `CONNECTION_NOT_FOUND`, `CONNECTION_CODE_NOT_FOUND`, `CONNECTION_INVALID_STATUS`, `THREAD_NOT_FOUND`, `THREAD_DORMANT`, `THREAD_ACCESS_DENIED`, `ATTACHMENT_COUNT_EXCEEDED`, `ATTACHMENT_SIZE_EXCEEDED`, `ATTACHMENT_EXTENSION_NOT_ALLOWED`, `MESSAGE_EMPTY`

### 2-1. 첨부 확장자 정책 — [2026.08 확정, §13-12 #3 해소]

기획 §13-7의 원안(거래플로우 §3 = 이미지·영상까지만)보다 넓은 확장이었으나, **통상적으로 업무에서 쓰는 파일 형식은 폭넓게 허용하고 실행형·스크립트 계열만 차단**하는 쪽으로 확정한다.

구현은 여전히 **허용 목록(default-deny) 방식**을 쓴다 — 차단 목록만 두면 아직 알려지지 않은 위험 확장자가 나올 때마다 뚫린 채로 남으므로, "웬만한 파일은 다 허용"이라는 요구는 **허용 목록을 넉넉하게 채우는 방식**으로 만족시키고 판정 로직 자체는 안전한 기본값(목록에 없으면 거부)을 유지한다.


| 분류  | 허용 확장자                                                                      |
| --- | --------------------------------------------------------------------------- |
| 이미지 | `jpg` `jpeg` `png` `gif` `webp` `bmp` `svg` `heic` `heif`                   |
| 영상  | `mp4` `mov` `avi` `wmv` `mkv` `webm` `m4v`                                  |
| 문서  | `pdf` `doc` `docx` `hwp` `hwpx` `xls` `xlsx` `ppt` `pptx` `txt` `csv` `rtf` |
| 압축  | `zip` `rar` `7z`                                                            |


**명시적으로 차단**(허용 목록에 없어도 이중 방어 차원에서 별도 확인): `exe` `bat` `cmd` `com` `scr` `msi` `cpl` `jar` `js` `jse` `vbs` `vbe` `ws` `wsf` `ps1` `psm1` `sh` `apk` `app` `dmg` `deb` `rpm` `dll` `sys` `bin` `lnk` `reg` `iso` `html` `htm` `php` `jsp` `asp` `aspx`

- 판정은 **파일명 확장자 + `Content-Type` 헤더를 함께 검사**한다 — 확장자만 보면 `.jpg`로 이름 붙인 실행 파일을 못 막는다(매직바이트 검사는 여력 되면 Phase 5에서 추가).
- `MESSAGE_ATTACHMENT.ATTACHMENT_TYPE`(`IMAGE`/`VIDEO`/`DOCUMENT`)은 이 표의 분류를 그대로 따른다. 압축 파일은 `DOCUMENT`로 취급해 file-chip UI(§13-8)로 노출한다.
- 허용 목록은 `ImageType`류와 동급의 상수 클래스(`AllowedAttachmentExtensions`)로 분리해두고, 이후 목록 조정이 코드 변경 한 줄로 끝나게 한다.

## 4. 첨부 업로드 — S3 Presigned URL 직접 업로드로 확정

기존 `ImageService`는 20MB·이미지 전용에 **서버를 경유하는 멀티파트 업로드**라 500MB 파일에는 애초에 못 쓴다. 서버 경유 방식은 타임아웃·메모리·대역폭 리스크가 확정적으로 크므로, 장기 권장이 아니라 **처음부터 Presigned URL 직접 업로드로 간다.** 클라이언트가 파일 바이트를 서버에 보내지 않고 **S3로 바로 PUT**하고, 서버는 업로드 권한(서명된 URL) 발급과 사후 검증만 담당한다.

신규 컴포넌트: `showroomz.api.common.attachment.service.MessageAttachmentService` (Presigned URL 발급 + 완료 검증), `S3Presigner` 빈 추가(`S3Config`에 `software.amazon.awssdk.services.s3.presigner.S3Presigner` 등록 — 기존 `S3Client`와 별개).

### 4-1. 업로드 3단계


| 단계           | 주체      | 내용                                                                                                                                                                                                                                        |
| ------------ | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① Presign 발급 | FE → BE | `POST /v1/{seller,creator}/threads/{threadId}/attachments/presign` `{ fileName, contentType, sizeBytes }` — 서버가 **확장자(2-1)·개별 파일 크기**를 먼저 검증하고, `MESSAGE_ATTACHMENT`를 `status=PENDING`·`message_id=NULL`로 선(先)생성, S3 presigned PUT URL 발급 |
| ② 직접 업로드     | FE → S3 | 발급받은 URL로 파일을 **S3에 직접 PUT**. 서버를 거치지 않으므로 대역폭·타임아웃 부담이 없다. FE가 XHR/`fetch` 업로드 진행 이벤트로 A7의 진행률 바를 그대로 구현                                                                                                                                 |
| ③ 완료 통지      | FE → BE | `PATCH /attachments/{attachmentId}/complete` `{ durationSeconds? }` — 서버가 **S3 HeadObject로 실제 업로드 크기·Content-Type을 재확인**하고 `status=UPLOADED`로 전환. 선언 값과 실측이 어긋나면 `status=REJECTED` + 객체 삭제                                                |


메시지 전송(`POST .../messages`)은 `attachmentIds` **배열**을 받는다(순서가 곧 표시 순서 — 4-5). 검증·연결 규칙은 4-5에 따로 정리한다.

### 4-2. 보안 트레이드오프 — 서버가 실제 바이트를 못 본다

직접 업로드의 대가로 **서버가 파일 내용을 검사할 기회 자체가 없어진다**. presign 시점의 확장자·`Content-Type`은 클라이언트가 "주장"한 값일 뿐이다. 대응:

- Presigned POST(단순 PUT이 아니라 policy 기반)를 쓰면 `content-length-range`, `Content-Type` 조건을 **S3가 업로드 시점에 강제**하게 만들 수 있다 — 선언과 다른 크기·타입으로는 업로드 자체가 S3에서 거부된다.
- ③ 완료 통지에서 **HeadObject 재확인**은 사후 방어선이다 — 위조된 채로 이미 올라간 객체를 잡아 삭제한다. 불일치 시 행을 **물리 삭제하지 않고 `status=REJECTED`로 남긴다**(S3 객체만 삭제) — 반복적으로 위조를 시도하는 계정을 추적할 근거가 남고, 디버깅 시 "왜 첨부가 사라졌는지"를 설명할 수 있다. `REJECTED` 행은 고아 정리 스케줄러가 일정 보존 기간 후 함께 삭제한다.
- **매직바이트(실제 파일 시그니처) 검사는 요청 경로에서 불가능하다** — 관통 업로드가 아니므로. 필요하면 S3 `ObjectCreated` 이벤트 → Lambda(또는 서버 훅)로 **업로드 후 비동기 스캔**해 이상 객체를 격리·삭제하는 구조가 되어야 한다. 이번 스코프에서는 확장자+Content-Type 이중 검증까지만 하고, 바이트 수준 스캔은 **Phase 5 이후 검토 항목**으로 남긴다(악성코드 검사 필요 여부는 보안 정책 확인 필요).

### 4-3. 인프라 확인 필요

- **S3 버킷 CORS 설정** — 브라우저가 S3로 직접 PUT하려면 버킷에 프론트 도메인 Origin + `PUT` 메서드를 허용하는 CORS 정책이 있어야 한다. 현재 `S3Config`/`S3Properties`에는 CORS 설정이 없으므로 **인프라 작업으로 별도 필요**.
- **IAM 권한 분리** — presign 서명에 쓰는 자격 증명은 대상 프리픽스(`uploads/message/`**)에 대한 `PutObject`만 허용하고 버킷 전체 권한을 주지 않는다.
- **Presigned URL 만료 시간** — 대용량 업로드 소요 시간을 고려해 넉넉히 설정(예: 15분).

### 4-4. 영상 재생시간(`DURATION_SECONDS`)은 어디서 오나

§13-8의 영상 file-chip은 `0:58 · 31.2MB`처럼 **재생시간을 표기**한다. 그런데 직접 업로드 설계에서는 **서버가 파일 바이트를 열어볼 수 없으므로 서버가 이 값을 스스로 구할 방법이 없다.** 선택지는 둘뿐이다:


| 방식        | 내용                                                                   | 판단                                      |
| --------- | -------------------------------------------------------------------- | --------------------------------------- |
| **FE 추출** | `<video>`의 `loadedmetadata` 이벤트로 브라우저가 읽은 `duration`을 ③ 완료 통지에 실어 보냄 | **채택** — 추가 인프라 0, 즉시 표기 가능             |
| 서버 후처리    | S3 `ObjectCreated` → Lambda(ffprobe)로 메타 추출 후 DB 갱신                  | 과함 — 이 값 하나 때문에 비동기 파이프라인을 새로 만들 이유가 없다 |


- **이 값은 "표시용 참고값"이며 신뢰 경계 밖이다** — 확장자·Content-Type과 마찬가지로 클라이언트가 주장하는 값이다. 다만 **재생시간은 위조돼도 피해가 없다**(용량 제한 판정처럼 정책 결정에 쓰이지 않고, 화면에 잘못된 숫자가 보일 뿐). 반면 `SIZE_BYTES`는 500MB 정책 판정에 쓰이므로 반드시 HeadObject 실측값을 써야 한다 — **두 값의 신뢰 등급이 다르다는 점을 구현 시 혼동하지 말 것.**
- 값이 없으면(브라우저가 못 읽는 코덱 등) `NULL`로 두고 FE는 용량만 표기한다 — 첨부 자체를 거부하지 않는다.

### 4-5. 메시지 전송 시 첨부 연결 규칙

`POST .../threads/{threadId}/messages`가 `attachmentIds` 배열을 받았을 때 서버가 수행하는 검증·연결이다. **§2의 "서버가 다시 검증한다" 원칙이 적용되는 실제 지점.**

**검증 항목** (하나라도 실패하면 전체 전송 실패 — 부분 연결 금지)


| #   | 검증                                        | 실패 시 |
| --- | ----------------------------------------- | ---- |
| 1   | 모든 attachment가 **존재**하고 `STATUS=UPLOADED` | 400  |
| 2   | `UPLOADER_TYPE`/`UPLOADER_ID`가 **요청자 본인** | 403  |
| 3   | `**THREAD_ID`가 요청 경로의 `threadId`와 일치**    | 403  |
| 4   | `MESSAGE_ID IS NULL` (아직 다른 메시지에 안 붙음)    | 409  |
| 5   | 개수 ≤ 20 · `SIZE_BYTES` 합계 ≤ 500MB (§2)    | 400  |


3번이 **핵심 방어선**이다 — 이게 없으면 A 스레드에서 올린 파일의 id를 알아내 B 스레드 메시지에 붙이는 것이 가능해진다. `THREAD_ID` 컬럼을 둔 이유가 정확히 이 검증이다.

**연결 방식** — 검증 통과 후 `message_id`를 채울 때 **조건부 UPDATE**를 쓴다:

```sql
UPDATE MESSAGE_ATTACHMENT
   SET MESSAGE_ID = :messageId, SORT_ORDER = :index
 WHERE ATTACHMENT_ID = :id
   AND MESSAGE_ID IS NULL          -- 낙관적 잠금 역할
   AND STATUS = 'UPLOADED'
   AND THREAD_ID = :threadId
   AND UPLOADER_ID = :requesterId
```

- **영향받은 행 수가 요청 개수와 다르면 롤백**한다. 조건 없는 `UPDATE ... WHERE id IN (...)`으로 하면, 네트워크 재시도 등으로 같은 첨부가 두 전송 요청에 동시에 걸렸을 때 **조용히 뒤쪽 메시지로 소유권이 넘어간다** — 검증(4번)만으로는 검증~UPDATE 사이의 경합을 막지 못하므로 UPDATE 자체에 조건을 걸어야 한다.
- `**SORT_ORDER`는 이 시점에 `attachmentIds` 배열의 index로 채운다.** presign은 파일당 개별 호출이라 그 시점엔 "이 메시지에서 몇 번째인지"를 알 수 없고, 병렬 업로드면 도착 순서도 신뢰할 수 없다. **배열 순서가 곧 사용자가 의도한 표시 순서**이므로 이것만이 유일한 정답이다.
- **멱등 재전송(1-5)과의 상호작용**: `CLIENT_MESSAGE_ID` 충돌로 기존 메시지를 그대로 반환하는 경우, 첨부 연결은 **다시 시도하지 않는다**(이미 첫 요청에서 붙었으므로). 그대로 재시도하면 4번 조건에 걸려 409가 나면서, 성공했어야 할 재전송이 실패한다.

### 4-6. 기타

- S3 키: `uploads/message/{threadId}/{uuid}.{ext}` — 첨부는 이미 열려 있는 스레드 안에서만 이뤄지므로 presign 요청 시점에 `threadId`가 항상 확보된다.
- **영상 스트리밍(§13-8 · 미결 #4)**: CloudFront/S3의 **HTTP Range Request**가 켜져 있어야 `<video>` 부분 로드가 성립한다. 배포 설정에서 확인 필요 — 꺼져 있으면 "재생"이 사실상 전체 다운로드가 되어 재생/다운로드 분리 설계가 무너진다.
- **고아 파일 정리** (Phase 5, 기존 `global/scheduler` 관례): 아래 세 부류를 대상으로 한다.
  - `PENDING`인데 생성 후 일정 시간(예: 24h) 내 `complete` 통지가 없는 행 → S3 객체 + 행 삭제
  - `UPLOADED`인데 `MESSAGE_ID IS NULL`로 방치된 행(첨부만 해두고 전송 안 한 경우) → 동일 처리
  - `REJECTED` 행 → 보존 기간 경과 후 삭제
  - 판정 기준은 `created_at`(1-6)이며, `S3_KEY`로 실제 객체를 지운다.

## 7. 리스크

1. **Presigned 직접 업로드의 검증 공백(§4-2)** — 서버가 실제 파일 바이트를 못 보므로 확장자·Content-Type 위조 가능성이 원천적으로 남는다. Presigned POST 정책 조건 + 업로드 후 HeadObject 재검증까지는 이번 스코프에서 처리하되, 매직바이트 수준 스캔이 필요한지는 보안 정책 확인 필요(Phase 5 후보).
2. **S3 CORS 미설정** — 현재 버킷에 브라우저 직접 PUT을 허용하는 CORS 정책이 없다. P3 착수 전 인프라 작업으로 선행되어야 FE 연동이 가능하다.
3. **연결코드 열거** — 코드 확인 API에 레이트 리밋이 없으면 브루트포스로 쇼룸을 열거할 수 있다. 코드 길이(≥10자)와 시도 제한을 함께 설계.
4. `ddl-auto: validate` — 엔티티/DDL 불일치 시 부팅 실패. 마이그레이션 → 엔티티 순서를 지킬 것
