## 1. 직권 취소 요청자 · 요청 시각

### 1-1. 현재

- `POST /v1/admin/contracts/{id}/cancel`의 본문은 `signatureRequestWithdrawn` · `reasonCode` · `memo`뿐이다(`AdminContractDto.CancelRequest`).
- 계약에 남는 것은 `close_actor_type = ADMIN` · 사유·메모, 이력은 `CANCELED`(actor = 처리 운영자)다. **누가 언제 요청했는지는 어디에도 없다.**
- 상세의 `closure`는 파트너·스튜디오와 같은 `ContractDetailResponse.Closure`를 쓴다.

### 1-2. 스레드에서 요청을 찾지 않는 이유

브랜드의 계약 취소 기능은 삭제됐다(10-A · 커밋 `798c72a0`). 지금 취소 요청은 **정해진 형식이 없는 메시지**로 들어온다. PAIR 스레드일 수도 있고, 운영자 스레드나 전화·메일일 수도 있다. 서버가 "이 메시지가 취소 요청이다"를 판정할 근거가 없다. 운영자가 메시지를 고르게 하는 방식(`requestMessageId`)은 정확하지만, FE에 메시지 선택 UI가 필요하고 스레드 밖에서 온 요청은 담지 못한다. 그래서 **FE가 제안한 대안을 채택한다** — 운영자가 취소 모달에서 요청자를 고른다.

### 1-3. API — `CancelRequest`에 3필드 추가

```json
{
  "signatureRequestWithdrawn": true,
  "reasonCode": "NEGOTIATION_STOPPED",
  "memo": "브랜드 요청으로 취소합니다.",
  "requesterType": "SELLER",
  "requestChannel": "THREAD",
  "requestedAt": "2026-08-14T10:05:00"
}
```

| 필드 | 값 | 규칙 |
| --- | --- | --- |
| `requesterType` | `SELLER` · `CREATOR` · `ADMIN` | `ADMIN` = 운영자 직권(요청자 없음). `ContractActorType` 재사용, `SYSTEM`은 400 |
| `requestChannel` | `THREAD`(소통 스레드) · `PHONE` · `EMAIL` · `ETC` | 신규 enum `ContractCancelRequestChannel`. 요청자가 브랜드·인플루언서면 필수, `ADMIN`이면 null이어야 한다 |
| `requestedAt` | 일시 | 요청자가 브랜드·인플루언서면 필수 · `≤ now` · `≥ 계약 생성 시각`. `ADMIN`이면 null이어야 한다 |

- 위반은 신규 `CONTRACT_CANCEL_REQUESTER_INVALID`(400) 하나로 묶는다. 어느 필드가 문제인지는 메시지로 알린다.
- **구현** — `requesterType` 누락도 `@NotNull`(→ `INVALID_INPUT`)이 아니라 서비스 검증(`AdminContractCommandService#requireRequester`)이 같은 코드로 거절한다. FE가 요청자 오류를 코드 하나로 처리할 수 있게 하기 위해서다.
- **배포 순서로 필수화한다.** Jackson 기본 설정이 모르는 필드를 무시하므로 FE가 먼저 세 필드를 보내도 깨지지 않는다. ① FE 배포(필드 전송 시작) → ② BE 배포. BE가 먼저 나가면 기존 취소 모달이 400이 되므로 순서를 지킨다. 필수화를 미루려면 `requireRequester`에서 `null`을 `ADMIN`으로 보면 된다(미결 ②).

### 1-4. 저장 — `contract` 컬럼 3개 (`V137`)

```sql
ALTER TABLE contract
    ADD COLUMN cancel_requester_type  VARCHAR(16) NULL,
    ADD COLUMN cancel_request_channel VARCHAR(16) NULL,
    ADD COLUMN cancel_requested_at    DATETIME(6) NULL;
```

**구현** — 시각 컬럼은 기존 마이그레이션(V136)과 같이 `DATETIME(6)`으로 했다. 세 값은 값 객체 `ContractCancelRequester`(`byAdmin()` = 직권)로 묶어 `applyCanceledByAdmin(reasonCode, memo, requester, now)`에 넘긴다.

- `Contract.applyCanceledByAdmin(...)`이 세 값을 함께 받는다. 종결 사유(`close_reason_*`)와 같은 자리에 두는 이유는 취소 한 번에 한 벌만 생기기 때문이다 — 별도 테이블은 과하다.
- 기존 취소 건은 null로 남는다(소급 없음). FE는 null이면 지금처럼 일반 안내 문구를 쓴다.
- **이름은 저장하지 않는다.** 응답 시점에 `SELLER` → 마켓명, `CREATOR` → 쇼룸명으로 채운다. `contract.brand.name` · `contract.creator.name`과 같은 값이라 한 화면 안에서 이름이 어긋나지 않는다. 대신 이후 브랜드명이 바뀌면 바뀐 이름이 보인다(미결 ③).

### 1-5. 응답 — 어드민 상세에 `cancelRequest` 블록

`AdminContractDto.Detail`에 추가한다. 운영자 취소(`status = CANCELED ∧ close_actor_type = ADMIN`)가 아니면 null이다.

```json
"cancelRequest": {
  "requesterType": "SELLER",
  "requesterName": "부트코스스테틱",
  "requestChannel": "THREAD",
  "requestChannelLabel": "소통 스레드",
  "requestedAt": "2026-08-14T10:05:00",
  "processedAt": "2026-08-14T11:20:00",
  "processedByName": "김윤영"
}
```

- `processedAt` · `processedByName`은 `closure.closedAt`과 `CANCELED` 이력의 `actorDisplayName`이다. 새로 저장하지 않고, 우측 레일의 '요청 · 처리' 행을 이 블록 하나로 그릴 수 있게 모았다.
- 기존 취소 건은 `requesterType` 등 요청 필드가 null이고 처리 필드만 채워진다.
- **공유 `Closure`에는 넣지 않는다.** `Closure`는 파트너·스튜디오 상세도 쓴다. 넣으면 "상대가 취소를 요청했다"가 양측에 보이는데, 이것은 기획이 정할 일이다(미결 ①).

## 2. 체결 문서 용량

### 2-1. 현재

- `contract_document.size_bytes`는 **이미 저장된다.** 업로드 등록(`AdminContractDocumentService`)은 요청의 `sizeBytes`를, 자동 생성본(`ContractDraftGenerator`)은 `bytes.length`를 넣는다.
- 상세의 `AdminContractDto.Document`만 이 값을 싣지 않는다. `GET /documents/{type}`(`DownloadResponse`)에는 `sizeBytes`가 있어서, FE가 용량 하나를 얻으려고 문서마다 추가 호출을 한다.
- 참고로 상세 `documents[].downloadUrl`은 이미 있다. 추가 호출에서 FE가 얻는 새 정보는 용량뿐이었다.

### 2-2. 변경

```java
public record Document(ContractDocumentType type, boolean exists, String fileName, String downloadUrl,
                       Long sizeBytes, LocalDateTime uploadedAt, LocalDateTime sourceReviewRequestedAt) {}
```

- `AdminContractQueryService`(88–89행)에서 `d.getSizeBytes()`를 넣는다. 문서가 없으면 null이다.
- 컬럼이 nullable이라 이론상 null일 수 있다. 스키마에 `nullable = true`를 표시하고 FE는 null이면 용량을 생략한다.
- 표시 단위("1.2MB")는 FE가 계산한다. 서버는 바이트만 내린다 — `DownloadResponse.sizeBytes`와 같은 계약이다.
- 레코드 인자 순서가 바뀌므로 생성 지점 2곳(88·89행)을 함께 고친다. JSON은 필드명으로 나가서 FE 계약에는 영향이 없다.
- 파트너·스튜디오 상세의 `Document`에도 용량이 없지만, 요청 범위가 아니고 시안에도 용량 표시가 없어 이번에는 손대지 않는다.

### 2-3. 테스트

- `AdminContractIntegrationTest`의 상세 문서 검증에 `sizeBytes`를 추가한다 — 업로드본은 등록 요청값, 생성본은 생성된 PDF 크기, 미업로드는 null.

## 3. 스레드 읽음 처리 동시성 — `MessageThreadService.markRead`

### 3-1. 현재와 실제 증상

```java
ThreadParticipant participant = repository.findBy...(thread, type, id)
        .orElseGet(() -> ThreadParticipant.create(thread, type, id));
participant.markRead(latestId);
repository.save(participant);
```

`thread_participant`에는 `uk_thread_participant(thread_id, participant_type, participant_id)` 유니크 키가 있다(V92 · 엔티티 둘 다). 그래서 **행이 중복 생성되지는 않는다.** 실제 증상은 두 가지다.

| # | 상황 | 결과 |
| --- | --- | --- |
| ① | 참여자 행이 없는 스레드를 두 창(또는 앱 재시도)에서 동시에 연다 | 둘 다 없다고 보고 INSERT → 늦은 쪽이 `DataIntegrityViolationException` → **읽음 API 500** |
| ② | 행이 있는 상태에서 요청 A가 최신 id 10을, B가 11을 읽는다. B가 먼저 커밋하고 A가 나중에 커밋한다 | `last_read_message_id`가 11 → **10으로 되돌아가** 안 읽은 배지가 다시 뜬다 |

FE 보고는 ①이다. ②는 같은 원인(읽고 쓰는 사이의 경합)에서 나오는 문제라 함께 고친다.

### 3-2. 변경 — 단일 upsert

`ThreadParticipantRepository`에 네이티브 upsert를 둔다. 한 문장이라 경합 구간이 없고, `GREATEST`로 읽음 위치가 앞으로만 간다.

```sql
INSERT INTO thread_participant
    (thread_id, participant_type, participant_id, last_read_message_id, last_read_at, created_at, modified_at)
VALUES (:threadId, :type, :participantId, :messageId, :now, :now, :now)
ON DUPLICATE KEY UPDATE
    last_read_at = CASE WHEN COALESCE(last_read_message_id, 0) <= VALUES(last_read_message_id)
                        THEN VALUES(last_read_at) ELSE last_read_at END,
    last_read_message_id = GREATEST(COALESCE(last_read_message_id, 0), VALUES(last_read_message_id)),
    modified_at = VALUES(modified_at)
```

- **대입 순서가 중요하다** — MySQL은 `ON DUPLICATE KEY UPDATE`의 대입을 왼쪽부터 적용하므로, `last_read_at`이 옛 `last_read_message_id`와 비교하도록 먼저 둔다.
- `VALUES()`는 MySQL 8.0.20부터 deprecated 경고가 나지만 동작한다. H2 테스트(MySQL 모드)와의 호환 때문에 행 별칭(`AS new`) 문법 대신 이것을 쓴다. 구현할 때 H2와 실 MySQL(`ShowroomzApplicationTests`) 양쪽에서 확인한다.
- `markRead`는 `@Modifying` 쿼리 한 줄이 된다. 엔티티의 `ThreadParticipant.markRead`는 다른 호출처가 없으면 제거한다.
- **구현** — 호출처가 없어진 `ThreadParticipant.create` · `markRead`를 모두 제거했다. 참여자 행을 만드는 경로는 이제 upsert 하나다.
- 호출처는 `SellerThreadService:130` · `CreatorThreadService:159` 두 곳이고, 시그니처가 같아 호출처는 고치지 않는다.

**검토했지만 쓰지 않는 안**

| 안 | 버린 이유 |
| --- | --- |
| 예외를 잡고 재조회 | `markRead`가 호출자 트랜잭션에 참여하므로 flush 예외가 트랜잭션을 rollback-only로 만든다. `REQUIRES_NEW`로 떼어내야 해서 upsert보다 복잡하고 ②는 못 막는다 |
| 스레드 행 비관적 잠금 | 읽음 처리는 가장 잦은 호출이라 스레드 단위 직렬화가 과하다. 행이 없을 때의 INSERT 경합도 남는다 |
| 스레드 생성 시 참여자 행 미리 생성 | 스레드 생성 경로가 여러 개라 누락되기 쉽고 ②는 못 막는다 |

### 3-3. 테스트

- 참여자 행이 없는 스레드에 읽음 API를 두 스레드에서 동시에 호출해도 둘 다 204이고, 행은 1개, `last_read_message_id`는 최신 메시지다(`CountDownLatch` 패턴 — `CreatorGroupBuyScenarioIntegrationTest.concurrentFirstSubmissionCannotOverwriteReview` 참고).
- 리포지토리 단위: 11로 upsert한 뒤 10으로 upsert해도 11이 유지되고 `last_read_at`도 바뀌지 않는다.
- 기존 안 읽은 수 집계(`countUnreadByThreadIds`) 테스트가 그대로 통과한다.
- **구현** — `ThreadReadPositionIntegrationTest`(동시 최초 열람 8건 · 후퇴 방지 + 안 읽은 수) · `MessageThreadServiceTest`(upsert 호출 검증). 수정 전 로직으로 되돌려 돌리면 동시 열람 테스트가 `uk_thread_participant` 위반으로 실패하는 것을 확인했다.
