## 28. 어드민 계약 관리 — [v0.33 신설]

대상 화면: `ui-admin-01-contracts.html` (**rev.1**), 상태 17종(목록 2 · 상세 상단 5 · 상세 하단 5 · 모달 5). 셸은 `ui-admin-17-groupbuys`, **스타일시트는 `ui-partner-08-contracts`(rev.7)에서 문자 그대로 이식.**

### 28-0. 이 화면이 왜 생겼나

모두싸인 API를 쓰지 않으므로 파트너·스튜디오에 보이는 서명 현황은 전부 **운영자가 모두싸인에서 눈으로 확인해 입력한 값**이고, 양쪽 화면에 「확인한 시점 기준 · N 기준」이 박혀 있다. **그 값을 입력하는 화면이 어디에도 없었다.** 이 파일이 그 자리다.

**상류 두 화면이 요구하는 입력값 10종 — 전부 이 파일에서 나온다**

| # | 입력값 | 위치 |
| --- | --- | --- |
| ① | 검토 통과 / 반려 | B1 |
| ② | **반려 사유 2단**(제목 + 상세) | C2 |
| ③ | 검토 통과 일시 | C1 |
| ④ | **서명 요청 발송 일시 · 서명 기한** | C1 |
| ⑤ | 브랜드 서명 완료 일시 | B3 |
| ⑥ | 인플루언서 서명 완료 일시 | B3 |
| ⑦ | **기준 시각**(B3 저장 시각 = 양쪽 `.s-asof`) | B3 |
| ⑧ | 체결 완료 처리 | C4 |
| ⑨ | 서명 PDF · 감사추적인증서 업로드 | B4 |
| ⑩ | 만료 처리 | C5 |

**지침에 없던 5번째 작업 — 서명 안내 재발송** — 파트너 rev.7과 스튜디오 모두 `[서명 안내 다시 받기]` 버튼을 두고 "운영자에게 재발송 요청"이라 적었는데 **그 요청이 도착할 화면이 정의돼 있지 않았다.** **조치 큐 4번째 항목**과 **B3 안내 블록 + `[재발송 처리 기록]`**으로 받는다. 재발송 자체는 모두싸인에서 하고 **이 화면은 기록만** 한다.

### 28-1. 목록 — `FE`·`BE`

**조치 큐 4개를 탭보다 위에 둔다** — 운영자는 **처리할 것을 찾으러** 온다.

| 큐 | 설명 |
| --- | --- |
| 검토 대기 | 브랜드 제출 · 승인 또는 반려 |
| 체결 처리 대기 | 양측 서명 완료 · PDF 업로드 |
| 만료 확인 | 서명 기한 경과 · 수동 종결 |
| **재발송 요청** | 서명 안내 다시 받기 |

**조치 큐는 검색과 무관하게 그대로 있다** — 검색 결과가 비어도 처리할 건은 남아 있다.

**탭 6종** — 전체 / 검토 대기 / 서명 진행중 / 체결 처리 대기 / 체결완료 / 종료

**탭에 없는 두 상태** — **작성중**은 검토 요청 전이라 운영자에게 도착하지 않고(스튜디오가 같은 이유로 작성중 탭을 없앴다), **검토 반려**는 반려하는 순간 **공이 브랜드로 넘어가 운영자 조치 대상이 아니다** — 전체 탭에 배지로만 남는다.

**컬럼 7종** — 공구명 / **브랜드** / **인플루언서** / 상품 수 / 공구 기간 / 검토 요청 / 상태

파트너는 「계약 상대」 1열, 스튜디오는 「브랜드」 1열이지만 **운영자는 양측이 다 보여야 누구의 계약인지 안다.**

| 항목 | 규칙 |
| --- | --- |
| **목록은 조회 전용** | 관리 열 · 체크박스 · 일괄 처리가 없고 **행 클릭 진입**이다. 승인·반려·체결은 **근거를 읽고 누르는 판단**이라 **목록에서 누르면 검토가 형식이 된다** |
| 정렬 | **검토 요청 오래된순**(기본 · 방치 건이 먼저) · 최근 생성순 · 공구 시작일순 |
| 주 CTA | **없다** — 운영자는 계약을 만들지 않는다 |
| 빈 상태 | §8 규격(패딩 72px) · **검색어는 지우지 않는다** |

### 28-2. 검토 — 체크리스트를 두지 않는다 — `FE`

**MVP에는 금액·기간 임계값이 없다**(리워드율 40% · 고정 지급비 100만원 · 할인율 70% 등). **임계값이 없으면 판정할 것도 없고, 없는 기준으로 만든 판정표는 있지도 않은 규칙이 있는 것처럼 보이게 한다** — 없는 데이터를 UI에 올리지 않는다는 기존 원칙 그대로다.

**그러면 운영자 검토는 무엇을 하나 — 대조다.**

| 대조 대상 | 확인 내용 |
| --- | --- |
| 스레드 | 계약 조건이 **양측 합의 내용**과 같은지 |
| 상품 정보 | 상품 항목이 **상품 마스터**와 맞는지 |
| 콘텐츠 의무 | **이행 판정 가능한 형태**인지 |
| 당사자 | 계정이 **정상**인지 |

전부 **원문을 읽어야 아는 것이고 자동화할 수 없어 판정 UI를 만들지 않았다.** 그래서 검토 진행 다음에 **계약 조건 카드가 바로 온다.**

**반려 사유 5종 — 같은 축으로 다시 썼다** (임계값 문구를 뺐다)

`합의 불일치` · `정보 불일치` · `이행 판정 불가` · `오기·누락` · `계정 상태`

**상세를 상단·하단 2장으로 내는 이유** — 좌측 카드가 최대 5장이라 1024px 프레임 하나에 들어가지 않는다. **실제 화면은 한 페이지를 스크롤**하는 것이며 **라우팅이 갈리지 않는다.** sticky 레일은 양쪽에 반복한다(스크롤해도 승인·반려·체결을 누를 수 있어야 한다). **B1이 가장 중요한 이유** — 상단에서 짚은 항목의 원문이 **하단 상품 항목**에 있어, 운영자는 **상단에서 짚고 하단에서 대조**한다.

### 28-3. 검토 승인 — `[승인 ≠ 발송]` — `FE`·`BE`

**API가 없으므로 이 화면은 서명 요청을 보내지 못한다.** 운영자가 모두싸인에 계약 내용을 **직접 입력해 보낸 뒤** 승인을 누르고, **승인은 「보냈다」는 기록**이다. 그래서 C1이 단순 확인 모달이 아니라 **모두싸인 입력 체크리스트 + 발송 일시 입력**이다 — **발송 전에 승인하면 양측이 오지 않은 메일을 기다린다.**

| 입력 | 성격 |
| --- | --- |
| 체크리스트 4개 | **기록이 아니라 확인용** — 모두싸인에 실제로 넣었는지 **우리 시스템이 검증할 방법이 없어 눈 대조가 유일한 방어선**이다 |
| **발송 일시** | 모두싸인에서 정해진 값을 옮겨 적는다 |
| **서명 기한** | 위와 같다. **나중에 만료 판단의 기준**이 되므로 발송 시점에 받아 둔다 — **확인 체크로 받으면 「설정했다」는 사실만 남고 며칠인지가 우리 쪽에 남지 않는다** |

**승인 즉시 양측 상태가 서명 진행중으로 바뀐다.**

### 28-4. 검토 반려 — `FE`

| 항목 | 규칙 |
| --- | --- |
| **사유 2단 필수** | **제목**(정형 사유 선택) + **상세**(무엇을 어떻게 고치라는 문장) **둘 다 필수.** 사유만 있고 고칠 방법이 없으면 **브랜드가 같은 내용으로 재요청한다** |
| 파트너와의 정합 | 파트너 B3d가 **2단 구조로 받으므로** 단일 텍스트로 받으면 브랜드 화면이 **한 줄만 얻는다** |
| **노출 고지** | **브랜드 화면에 그대로 노출됨**을 모달에서 고지한다 — **내부 메모처럼 쓰면 사고가 난다** |
| 실행 버튼 | **흰 배경 + 위험색 글자** — 반려는 **파괴적 조치가 아니라 되돌림**이다 |
| **반려 후 액션 없음** | 공이 브랜드로 넘어가 운영자가 할 일이 없다. **반려 취소 버튼도 두지 않았다** — 브랜드 화면이 이미 열렸고 사유가 노출됐으므로 **되돌리면 두 화면이 어긋난다.** 잘못 반려했으면 스레드로 알리고 재요청을 받는다 |

### 28-5. 서명 현황 갱신 — `FE`·`BE`

| 항목 | 규칙 |
| --- | --- |
| 컴포넌트 | 서명 카드는 양측과 **완전 동일한 `.signs/.sbox`**이고 **체크 + 일시 입력만 더했다**(`.sbox.edit`) — 같은 컴포넌트를 쓰되 **운영자만 쓰기 권한**을 갖는다 |
| **체크 해제 가능** | 오입력 정정 경로가 없으면 **잘못 찍은 서명 완료가 양측 화면에 박혀 되돌릴 수 없다.** 다만 **체결 완료는 불가역이라 거기서 잠긴다** |
| **기준 시각 경고** | 이 화면의 **핵심 문구**다 — **대시보드를 보지 않고 저장하면 시각만 새로워지고 양측은 확인된 값이라 읽는다.** B3 경고 배너와 C3 모달 **양쪽에** 박았다 |
| C3 모달 | **변경 내역을 before → after로** 보여준다. **무엇이 바뀌는지 보지 않고 누르면 오입력이 그대로 나간다** |
| 되돌림 명시 | **체결 완료 전까지 체크는 해제 가능**함을 모달에 적는다 |
| 확인 버튼 | **주 액션** — 파괴적이지 않고 자주 하는 일이라 위험색을 쓰지 않는다 |

### 28-6. 체결 처리 — 유일한 불가역 — `FE`·`BE`

**체결 문서 카드가 이 상태에만 있다** — API를 쓰지 않아 PDF·감사추적인증서가 자동 수신되지 않으므로 **운영자가 내려받아 올린다.**

| 항목 | 규칙 |
| --- | --- |
| **두 파일이 다 올라와야 버튼이 열린다** | 필수 미입력이라 **에러 문구 없이 버튼만 비활성**(절대 규칙). 대신 **우측 메타에 「감사추적인증서 미업로드」를 경고색**으로 띄워 **왜 비활성인지를 화면에서 읽히게** 했다 |
| **C4가 유일한 불가역 조치** | 누르는 순간 **계약이 성립하고 공구가 생성**된다. 모달이 **서명 기록 · 업로드 문서 · 생성될 공구를 다시 나열**한다 — 서명 일시가 틀렸으면 **지금이 마지막 정정 기회**이고, **무엇이 만들어지는지 모르고 누르는 불가역 버튼은 없어야** 한다 |
| 실행 버튼 | **주 액션** — **파괴가 아니라 성립**이라 위험색을 쓰지 않는다(파트너의 체결완료=성공색과 같은 판단) |
| **체결 후** | 액션이 없다. **생성된 공구 번호와 이동 링크**를 둔다 — 파트너·스튜디오와 다른 점이며, **체결의 결과물이 공구이고 운영자가 다음으로 갈 곳이 거기**다 |
| **체결 문서 잠금** | **교체·삭제 불가** — **서명 원본이 바뀌면 계약의 증거가 사라진다** |

### 28-7. 만료 처리 — `FE`

**만료는 자동 판정이 아니다** — 기한이 지나도 시스템이 닫지 못해 운영자가 확인해 종결시킨다.

모달은 **「정말 서명이 없었는지」를 되묻는다** — **모두싸인에는 서명이 들어왔는데 우리 화면에 반영되지 않았을 수 있고, 그 상태로 만료시키면 성립한 계약을 닫는다.** 그래서 **대시보드 재확인 체크를 필수**로 두고 **기한 경과일을 병기**한다.

결과 상태는 **만료 = 중립**이다(원칙 ② · 부정 결과 확정이 아니라 시간으로 닫힌 건).

### 28-8. 확정 필요 · 미결 — `[대표 확정]`

#### A. MVP 규칙 유무 — 파트너와 어드민의 전제가 어긋난다

| 문서 | 전제 |
| --- | --- |
| 파트너 rev.7 | **경고 6종**(리워드율 40% · 고정 지급비 100만원 · 할인율 70% 등)이 존재하고, 통과된 경고는 **어드민에게 플래그로 전달**된다 |
| 어드민 rev.1 | **MVP에 금액·기간 임계값이 없다**는 전제로 **검토 체크리스트를 두지 않았다** |

**둘 중 하나를 정리해야 한다.** 경고를 유지한다면 어드민 검토 화면에 **경고 플래그 표시 영역**이 필요하고, 임계값이 없다면 파트너의 W1~W6을 걷어내야 한다.

**부수 정정** — 파트너 규칙 박스는 여전히 "통과된 경고는 어드민 **공구 오픈 승인 화면**에 플래그로 전달된다(**계약 단계에 운영자 승인이 없어** 유일한 사후 실마리)"로 기술한다. **rev.5부터 계약 단계에 운영자 검토가 생겨 전제가 무너졌다.**

#### B. 리드타임 7일 재검토 + 기준일 재정의

| rev.2~4 | rev.7 |
| --- | --- |
| 인플루언서 서명 → 게시물 등록 → 오픈 승인(3영업일) | **운영자 검토** → 양측 서명 → **운영자 체결 처리** → 게시물 등록 → 오픈 승인(3영업일) |

**단계가 2개 늘었는데 리드타임은 7일 그대로다.** 기준일은 rev.7에서 「발송일」 → **「검토 요청일」**로 바뀌었으나, **검토 소요가 며칠인지(SLA)가 미정**이라 7일이 실제로 충분한지 판단할 수 없다.
