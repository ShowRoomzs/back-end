## 0. 먼저 정한 7가지

### 0-1. 어드민은 유일한 쓰기 권한자이지만 **조건은 한 글자도 못 고친다**

§25-4 — "운영자도 고칠 수 없다. 어드민 화면에 수정 필드가 한 곳도 없다."

그래서 어드민이 쓰는 값은 **계약 내용이 아니라 절차값**뿐이다.

| 어드민이 쓰는 것 | 어드민이 못 쓰는 것 |
| --- | --- |
| 검토 승인/반려 · 반려 사유 2단 | 공구명 · 기간 · 상품 항목 · 공구가 · 리워드율 |
| 발송 일시 · 서명 기한 | 고정 지급비 · 지급 시점 |
| 브랜드/인플루언서 서명 일시 · 기준 시각 | 콘텐츠 의무 전부 |
| 체결 완료 · 만료 처리 | 계약 상대 |
| 체결 문서 2종 업로드 · 재발송 기록 | — |

**조건 필드를 받는 엔드포인트를 만들지 않는다.** "운영자 권한이니 언젠가 필요할 것"이라며 수정 API를 열어두면, 그 API가 존재한다는 사실만으로 **양측이 서명한 대상이 바뀔 수 있는 시스템**이 된다. 문제가 있으면 반려한다.

### 0-2. 「승인 ≠ 발송」은 서버 관점에서 **승인 API가 기록 API라는 뜻**이다

§25-1 · §28-3 — 우리 시스템은 서명 요청을 보내지 못한다. 운영자가 모두싸인에서 보낸 뒤 승인을 누른다.

| 이 설계에 없는 것 | 대신 있는 것 |
| --- | --- |
| 모두싸인 발송 API 호출 | **`signatureRequestedAt` 필수 입력** |
| 서명 기한 계산 로직 | **`signatureDeadlineAt` 필수 입력** |
| 웹훅 수신 엔드포인트 | 서명 일시 **수동 입력**(7절) |

**서버가 기한을 계산하는 코드를 한 줄도 두지 않는다.** §25-3이 "우리 화면이 「공구 시작 −3일」 같은 값을 계산해 보여주면 있지도 않은 규칙이 생기고 모두싸인의 실제 값과 어긋난다"고 못박았다. 기본값 제안조차 하지 않는다 — 제안값을 그대로 누르는 운영자가 반드시 생기고, 그 순간 모두싸인의 실제 마감과 우리의 만료 기준이 갈린다.

### 0-3. **계약서 PDF 생성이 이 설계서의 두 번째 축**이다

`SHOWROOMZ_계약서_생성규격_v0.1.md`가 나오면서 **파트너·스튜디오 설계서에 없던 책임**이 생겼다 — 플랫폼이 브랜드 입력값 + 표준 조항으로 **A4 6면 PDF를 자동 생성**하고, 운영자가 B1에서 내려받아 모두싸인에 그대로 올린다.

이것이 단순한 부가 기능이 아닌 이유는 규격 §6-2에 있다. **모두싸인 입력란을 5개(사인 2 · 날짜 2 · 체크박스 1)로 줄인 근거가 "협의 조건이 전부 PDF에 인쇄되어 있다"**는 것이다. PDF 생성이 없으면 운영자가 모두싸인에서 조건을 손으로 옮겨 적어야 하고, **검토를 통과한 내용과 서명한 내용이 달라지는 경로**가 열린다.

→ 12절에서 별도로 다룬다. 치환 변수 49종 · 조건부 분기 6종 · 생성 시점 · 렌더링 스택.

### 0-4. **불가역은 체결 하나뿐이고, 나머지의 가역성은 DB가 보장한다**

§25-4 · §28-5 — 서명 현황 체크는 체결 전까지 해제 가능하다.

| 조치 | 가역 | 보장 방법 |
| --- | --- | --- |
| 검토 승인 | ❌ (상태가 이미 양측에 나갔다) | — |
| 검토 반려 | ❌ (**반려 취소 API를 만들지 않는다** — §28-4) | — |
| 서명 현황 갱신 | ✅ **해제 가능** | `NULL` 저장 허용 + 상태 역전이 |
| 체결 완료 | ❌ **유일한 불가역** | `CONCLUDED`를 벗어나는 전이 없음 |
| 만료 처리 | ❌ | 종결 |

**"가역"을 `deleted_at` 같은 소프트 삭제로 흉내 내지 않는다.** 서명 일시는 `NULL`로 되돌리는 것이 정확한 표현이다 — 운영자가 잘못 체크했다는 것은 **그 서명이 없었다**는 뜻이지, 있었는데 취소됐다는 뜻이 아니다. 무슨 일이 있었는지는 이력이 가지고 있다.

### 0-5. 조치 큐는 목록이 아니라 **카운트 4개 + 정렬**이다

§28-1 — "조치 큐는 검색과 무관하게 그대로 있다. 검색 결과가 비어도 처리할 건은 남아 있다."

→ **큐 카운트는 목록 API가 아니라 `summary`가 내린다**(3절). 목록에 얹으면 검색어가 걸린 카운트가 나가고, 시안이 명시한 "검색과 무관"이 깨진다.

**큐를 누르면 목록 필터가 걸릴 뿐 별도 엔드포인트가 아니다.** 큐 4개는 전부 `tab` + `sort` 조합으로 표현된다(2-3).

### 0-6. 모든 처리에 **처리자 실명**이 남는다 — 기존 패턴을 그대로 쓴다

§25-9 — "어드민 이력 주체는 「김운영」(실명)" · "모든 수동 처리에 처리자·시각이 남는다."

어드민 운영자는 **`Seller` 계정으로 로그인**한다(`AdminAuthController` → `sellerService.loginAdmin`). 처리자 이름 해석도 이미 같은 패턴이 있다:

```java
// AdminChangeRequestService.java:322
private String resolveAdminName(Long processorId) {
    return sellerRepository.findById(processorId).map(Seller::getName).orElse("운영자");
}
```

→ 계약도 같은 방식을 쓴다. `UserPrincipal.getUserId()`를 `requireOperatorId()`로 꺼내 `contract_history.actor_id`에 넣고, `actor_display_name`에 **그 시점의 실명을 스냅샷**한다.

**계약 본체에 `concluded_by` 같은 처리자 컬럼을 따로 두지 않는다.** 이력이 append-only 단일 소스이고(파트너 설계 1-6), 본체에 복사하면 두 곳이 어긋날 자리가 생긴다. B5 상태 카드의 「처리자 김운영」은 `CONCLUDED` 이력 행에서 읽는다.

### 0-7. 어드민은 **경고 W1~W6을 판정하지 않는다**

§28-2 · §28-8 A — 어드민 rev.1은 "MVP에 금액·기간 임계값이 없다"는 전제로 검토 체크리스트를 두지 않았고, 파트너 rev.7은 경고 6종이 "어드민에게 전달된다"고 적었다. **두 문서의 전제가 어긋나 있다.**

서버의 처리는 파트너 설계 2-3에서 이미 정해졌다 — **`warning_flags`에 저장은 하고 노출은 보류.** 어드민 설계에서 더할 것은 하나다: **어드민 응답에 `warningFlags`를 싣지 않는다.** 확정 전에 내려주면 FE가 "일단 보여주자"로 화면에 붙이고, §28-2가 없애려 한 **"있지도 않은 규칙이 있는 것처럼 보이는 판정표"**가 생긴다. 확정되면 응답에 한 줄 추가하면 되고, 데이터는 그때 이미 쌓여 있다.

## 1. 모델 보강 — 파트너 설계 대비 **추가 4건**

테이블 6개는 파트너 설계 1절에서 확정됐다. 어드민 시안·계약서 규격을 반영해 **네 곳을 보강**한다.

### 1-1. `contract_history.event_type` 2종 추가

| 추가 | 왜 |
| --- | --- |
| `RESEND_HANDLED` | B4 이력에 「서명 안내 재발송 · 08.14 08:55 · 김운영」이 있다. 기존 `RESEND_REQUESTED`는 **양측이 요청한 사실**이고 이것은 **운영자가 처리한 사실**이다. 요청 없이 운영자가 자발적으로 재발송하는 경우도 있어 요청 행의 `handled_at`만으로는 표현되지 않는다 |
| `CONTRACT_PDF_GENERATED` | 계약서 생성본이 **어느 제출본 기준으로 만들어졌는지**가 분쟁의 근거가 된다(규격 §7 "반려 후 재요청 건은 계약서를 다시 받아야 한다") |

### 1-2. `contract_document` — **체결 전 교체를 허용**한다 (파트너 설계 정정)

파트너 설계 1-6은 "교체·삭제 API를 만들지 않는다"고 적었다. **어드민 시안 B4에는 업로드된 PDF 옆에 `[교체]` 버튼이 있다.**

둘 다 맞다 — **잠기는 시점이 다를 뿐이다.**

| 상태 | 업로드 | 교체 | 삭제 |
| --- | --- | --- | --- |
| `CONCLUSION_PENDING` | ✅ | ✅ | ✅ |
| `CONCLUDED` | ❌ | ❌ | ❌ **영구 잠금** |

§28-6의 "교체·삭제 불가"는 **B5(체결완료) 카드의 캡션**이다. 체결 전에 잘못 올린 파일을 못 바꾸면 **틀린 증거를 안고 불가역 버튼을 눌러야** 한다.

→ `UNIQUE(contract_id, document_type)`는 유지하고, 교체는 **같은 행의 S3 키를 갈아 끼운다**(옛 객체는 삭제). 상태 판정을 서비스가 먼저 한다.

### 1-3. `contract_document.document_type`에 `GENERATED_DRAFT` 추가

계약서 생성본(규격 §7 ②)을 보관할 자리다.

| type | 생성 주체 | 교체 |
| --- | --- | --- |
| `GENERATED_DRAFT` | **플랫폼 자동 생성** | 재요청 시 **덮어쓴다** |
| `SIGNED_PDF` | 운영자 업로드 | 체결 전까지 |
| `AUDIT_TRAIL` | 운영자 업로드 | 체결 전까지 |

**생성본을 버전별로 쌓지 않고 덮어쓰는 이유** — 반려 후 재요청되면 조건이 바뀌었고, **옛 조건의 계약서는 서명 대상이 된 적이 없다.** 보관할 법적 가치가 없는 파일을 위해 `revision` 컬럼과 유니크 제약 변경을 끌어들이지 않는다. 언제 어느 제출본으로 생성됐는지는 `CONTRACT_PDF_GENERATED` 이력이 갖고 있다.

### 1-4. 만료 재확인 체크는 **저장하지 않는다**

C5의 「모두싸인 대시보드를 다시 확인했습니다」 체크는 §28-3의 C1 체크리스트와 성격이 같다 — **"기록이 아니라 확인용"**이다.

→ 요청 바디에서 `true`를 **필수로 요구**하되(아니면 400) 컬럼을 만들지 않는다. 저장하면 "운영자가 확인했다고 체크한 기록"이 남는데, **그 기록은 실제로 확인했는지를 아무것도 증명하지 못한다.** 검증할 수 없는 자기 신고를 DB에 쌓으면 나중에 그것을 근거처럼 쓰게 된다.

### 1-5. 마이그레이션

스튜디오 설계가 `V122`를 쓰므로 **`V123`부터**.

| 파일 | 내용 |
| --- | --- |
| `V123__alter_contract_document_add_generated_draft.sql` | `document_type` enum 값 추가(문자열 컬럼이면 주석만) · 체크 제약 조정 |
| `V124__add_contract_admin_queue_index.sql` | `(status, signature_deadline_at)` 보강 · `contract_resend_request(handled_at, requested_at)` 확인 |

`(status, review_requested_at)`(검토 대기 큐)와 `(status, signature_deadline_at)`(만료 확인 큐)는 **파트너 설계 1-1에 이미 있다.** V124는 실제로 빠진 것만 담는다 — 마이그레이션 파일을 채우려고 중복 인덱스를 만들지 않는다.

## 2. 목록 — `GET /v1/admin/contracts`

### 2-1. 어드민만의 가시성

```sql
status <> 'DRAFT'
```

**한 줄이다.** §28-1 — "작성중은 도착하지 않는다. 검토 요청 전이라 운영자에게 올 이유가 없다."

스튜디오와 달리 **`REVIEW_REJECTED`는 보인다**(탭은 없고 전체 탭에 배지로). 운영자가 반려한 건이므로 자기가 처리한 결과를 볼 수 있어야 한다.

### 2-2. 파라미터

| 이름 | 값 | 기본 |
| --- | --- | --- |
| `tab` | `ALL` · `REVIEW_PENDING` · `SIGNING` · `CONCLUSION_PENDING` · `CONCLUDED` · `CLOSED` | `ALL` |
| `queue` | `REVIEW` · `CONCLUSION` · `EXPIRY` · `RESEND` | — |
| `keyword` | **공구명 · 브랜드명 · 쇼룸명 · 계약번호** (A2 빈 상태 문구가 네 가지를 명시) | — |
| `sort` | `REVIEW_REQUESTED_ASC` · `CREATED_DESC` · `START_AT_ASC` | `REVIEW_REQUESTED_ASC` |
| `PagingRequest` | 20 / 50 | 20 |

**기본 정렬이 「검토 요청 오래된순」인 것이 세 서피스 중 유일하게 오름차순**이다 — §28-1 "방치 건이 먼저". 파트너는 최근 생성순, 스튜디오는 받은 순(둘 다 내림차순)인데, 운영자만 **오래 기다린 건이 위로 와야** 한다.

`REVIEW_REQUESTED_ASC`에서 **`review_requested_at`이 NULL인 행은 없다** — `DRAFT`를 제외했고 나머지 8종은 전부 검토 요청을 거쳤다.

### 2-3. 조치 큐 = 탭 + 정렬의 조합 (별도 엔드포인트 아님)

| 큐 | 필터 | 정렬 |
| --- | --- | --- |
| 검토 대기 | `status = REVIEW_PENDING` | `review_requested_at ASC` |
| 체결 처리 대기 | `status = CONCLUSION_PENDING` | `signature_as_of ASC` |
| 만료 확인 | `status = SIGNING` AND `signature_deadline_at < now` | `signature_deadline_at ASC` |
| **재발송 요청** | 미처리 `contract_resend_request` 존재 | `requested_at ASC` |

**「만료 확인」은 상태값이 아니라 조건**이다. `EXPIRED`는 운영자가 처리한 **결과**이고, 큐에 있는 것은 아직 `SIGNING`이다. 이 구분이 흐려지면 "만료 탭"을 만들게 되고 §25-2의 9종이 10종이 된다.

**「재발송 요청」만 조인이 필요하다** — `EXISTS (SELECT 1 FROM contract_resend_request r WHERE r.contract_id = c.contract_id AND r.handled_at IS NULL)`. 큐 카운트는 `summary`가 내리므로 목록 쿼리에는 `queue=RESEND`일 때만 붙는다.

### 2-4. 목록 항목 — **양측이 다 보인다**

```
contractId · contractNumber · title
brandName · creatorName          ← 어드민만 2열
itemCount · startAt · endAt
reviewRequestedAt                ← 「검토 요청」 열
status · statusLabel · statusTone
```

§28-1 — "파트너는 「계약 상대」 1열, 스튜디오는 「브랜드」 1열이지만 운영자는 양측이 다 보여야 누구의 계약인지 안다."

- 「검토 요청」 열은 `review_requested_at` **원시값**이다. 스튜디오의 `deadline.type`처럼 여섯 갈래로 갈리지 않으므로 판정 필드를 만들지 않는다.
- `entryMode` 없음 — 운영자는 계약을 편집하지 않는다.
- **관리 열·체크박스를 내리지 않는다.** §28-1 "승인·반려·체결은 근거를 읽고 누르는 판단이라 목록에서 누르면 검토가 형식이 된다." → **목록 응답에 `permissions`를 싣지 않는다.** 버튼이 없으므로 권한도 필요 없고, 내려주면 FE가 목록에 버튼을 달 수 있게 된다.

## 3. 요약 — `GET /v1/admin/contracts/summary`

```json
{ "queues": { "REVIEW": 2, "CONCLUSION": 1, "EXPIRY": 1, "RESEND": 1 },
  "tabCounts": { "ALL": 10, "REVIEW_PENDING": 2, "SIGNING": 3,
                 "CONCLUSION_PENDING": 1, "CONCLUDED": 1, "CLOSED": 2 },
  "actionRequiredCount": 5 }
```

- `actionRequiredCount` = **큐 4개의 합**(시안 A1: 2+1+1+1 = 5, 헤더 「조치 필요 5건」, GNB 「5 계약 관리 5」). 세 서피스 중 **유일하게 여러 사유의 합**이다.
- 탭 카운트 합이 `ALL`과 다르다 — 시안 A1에서 2+3+1+1+2 = 9인데 전체는 10이다. **빠진 1건이 `REVIEW_REJECTED`**이고, 탭이 없어 전체에만 잡힌다(§28-1). 이 불일치는 **버그가 아니라 사양**이므로 테스트에 그대로 박아 둔다.
- **`queue`와 `tabCounts`를 한 응답에 싣되 계산은 분리한다** — 큐는 검색어를 타지 않고(0-5) 탭 카운트도 마찬가지다. `summary`는 **파라미터를 받지 않는다.**

## 4. 상태 전이 — 어드민 소관 6종

파트너 설계 3-1의 전이표 12종 중 **어드민이 주체인 것은 6종**이다.

| # | 전이 | 화면 | 가역 | 부수 효과 |
| --- | --- | --- | --- | --- |
| 4 | `REVIEW_PENDING` → `SIGNING` | C1 | ❌ | 발송 일시 · 서명 기한 기록 · **양측 통지** |
| 5 | `REVIEW_PENDING` → `REVIEW_REJECTED` | C2 | ❌ | 사유 2단 · **브랜드 편집 재개** |
| 7 | `SIGNING` → `CONCLUSION_PENDING` | B3/C3 | ✅ | 양측 서명 완료의 **결과**(직접 전이가 아니다) |
| 8 | `CONCLUSION_PENDING` → `SIGNING` | B3/C3 | ✅ | 체크 해제의 **결과** |
| 9 | `CONCLUSION_PENDING` → `CONCLUDED` | C4 | ❌ **유일한 불가역** | 문서 2종 필수 · 공구 게이트 |
| 11 | `SIGNING` → `EXPIRED` | C5 | ❌ | 기한 경과 확인 |

**7·8번은 「전이 API」가 아니다.** 운영자가 누르는 것은 `[서명 현황 저장]` 하나이고, 상태는 **두 서명 값의 조합에서 파생**된다(7절). 별도 `POST /conclusion-pending` 같은 엔드포인트를 만들면 **서명 값과 상태가 어긋나는 조합**이 생긴다.

**모든 전이는 조건부 UPDATE로 쓴다**(파트너 설계 3-3). 특히 위험한 조합:

- **브랜드 `[요청 취소]` vs 운영자 `[검토 승인]`** — 둘 다 통과하면 **작성중인데 서명 요청이 나간 계약**이 생긴다
- **운영자 A의 `[계약 취소]` vs 운영자 B의 `[체결 완료]`** — 공구가 생기면서 동시에 종결된다
- **운영자 A의 `[체결 완료]` vs 운영자 B의 `[체크 해제]`** — 어드민은 다중 사용자다

## 5. 검토 승인 — `POST /v1/admin/contracts/{id}/review/approve`

```json
{ "recipientsRegistered": true,
  "documentUploaded": true,
  "requestSent": true,
  "signatureRequestedAt": "2026-08-13T16:40:00",
  "signatureDeadlineAt": "2026-08-20T23:59:00" }
```

**전이**: `REVIEW_PENDING` → `SIGNING`

### 5-1. 체크리스트 3종은 **받되 저장하지 않는다**

C1의 3항목(수신자 2명 등록 · 계약서 PDF 업로드 · 발송 완료)은 §28-3이 "기록이 아니라 확인용"이라고 명시했다.

| | 처리 |
| --- | --- |
| 받는다 | 셋 다 `true`가 아니면 **400** |
| 저장한다 | ❌ — 1-4와 같은 이유 |
| 이력에 남긴다 | ❌ |

**셋 다 `true`를 요구하는 것이 무의미해 보이지만 그렇지 않다** — FE가 체크박스 없이 승인을 호출하는 경로(자동화 스크립트, 테스트 코드, 잘못 만든 화면)를 막는다. 우리가 검증할 수 없는 사실이라도 **"확인했다고 말한 요청만 받는다"**는 계약은 지킬 수 있다.

### 5-2. 두 시각은 **필수**이고 서버가 정합성을 본다

| 검증 | 이유 |
| --- | --- |
| `signatureRequestedAt` 필수 | 양측 화면의 「서명 요청 발송」이 이 값이다 |
| `signatureDeadlineAt` 필수 | **만료 판단의 유일한 기준**(§25-3) |
| `review_requested_at ≤ signatureRequestedAt` | 발송이 제출보다 앞설 수 없다 |
| `signatureRequestedAt < signatureDeadlineAt` | 기한이 발송보다 앞서면 즉시 만료 대상이 된다 |
| `signatureRequestedAt ≤ now` | **미래 발송을 받지 않는다** — 「보낸 뒤 누르세요」(§28-3)가 절차인데 미래 시각이 들어오면 아직 안 보냈다는 뜻이다 |

**`signatureDeadlineAt`의 상한을 두지 않는다.** 모두싸인에서 정해지는 값이므로 우리가 "너무 길다"고 판정할 근거가 없다(§25-3). 파트너 시안의 경고 W1~W6과 같은 이유로 **임계값을 발명하지 않는다.**

> ⚠️ **시각 역전이 실제로 들어온다.** 파트너 설계 리스크 표가 지적한 시안의 모순(통과가 요청보다 빠름)이 그 증거다. 사람이 옮겨 적는 값이므로 **입력 시점에 막는 것이 유일한 방어선**이다 — 나중에 이력 화면에서 시간순이 뒤집힌 줄을 보게 된다.

### 5-3. 한 트랜잭션이 하는 일

상태 판정 → 체크 3종 검증 → 시각 정합성 검증 → `review_approved_at = now` · 발송 일시 · 기한 기록 → 상태 전이(조건부 UPDATE) → 이력 `REVIEW_APPROVED` + `SIGNATURE_SENT` append → **양측 통지**.

**이력 두 줄을 남긴다.** 시안 B3 이력에 「운영자 검토 통과 15:20」과 「양측에 전자서명 요청 발송 16:40」이 **각각 있고 시각이 다르다.** 한 API 호출이지만 **서로 다른 시각의 두 사실**이므로 한 줄로 합치면 스텝퍼의 두 칸을 채울 수 없다.

### 5-4. 승인에 **되돌림이 없다**

`SIGNING`에서 `REVIEW_PENDING`으로 가는 전이는 전이표에 없다. 승인하는 순간 **양측 화면이 바뀌고 모두싸인에는 이미 문서가 나가 있다.** 잘못 승인했으면 **운영자가 `[계약 취소]`**한다(10-A) — 발송 이후에는 브랜드가 취소할 수 없다.

## 6. 검토 반려 — `POST /v1/admin/contracts/{id}/review/reject`

```json
{ "reasonCode": "AGREEMENT_MISMATCH", "reasonDetail": "2차 활용 기간이 ..." }
```

**전이**: `REVIEW_PENDING` → `REVIEW_REJECTED` · **브랜드 편집 재개**

### 6-1. 사유 5종 + 기타 (`ContractReviewRejectReason`)

| enum | 화면 문구 |
| --- | --- |
| `AGREEMENT_MISMATCH` | 계약 조건이 인플루언서 합의 내용과 다릅니다 |
| `INFO_MISMATCH` | 계약 조건과 상품 정보가 일치하지 않습니다 |
| `OBLIGATION_UNVERIFIABLE` | 콘텐츠 의무가 이행 판정 가능한 형태가 아닙니다 |
| `TYPO_OR_OMISSION` | 계약 내용에 오기·누락이 있습니다 |
| `ACCOUNT_STATUS` | 당사자 계정 상태 문제 |
| `ETC` | 기타(직접 입력) |

§28-2가 "같은 축으로 다시 썼다 — 임계값 문구를 뺐다"고 한 5종에 시안 C2의 `기타(직접 입력)`을 더한 6값이다.

### 6-2. `reasonDetail`이 **무조건 필수**다

§28-4 — "사유만 있고 고칠 방법이 없으면 브랜드가 같은 내용으로 재요청한다."

거절(스튜디오)·취소(파트너)의 메모가 선택이거나 `ETC`일 때만 필수인 것과 **다르다.** 반려는 **브랜드가 고쳐서 다시 올려야 끝나는 유일한 상태**(§25-2 "검토 반려만 경고색")이고, 무엇을 고칠지 모르면 그 루프가 닫히지 않는다.

`reasonCode`가 `ETC`든 아니든 `reasonDetail`은 필수다. 길이는 1000자(`reject_reason_detail` 컬럼).

### 6-3. 반려 취소 API를 **만들지 않는다**

§28-4 — "반려를 되돌리는 기능은 없습니다. 잘못 반려했으면 스레드로 알리고 재요청을 받으세요."

되돌리면 **브랜드 화면이 이미 반려 사유를 노출한 뒤**라 두 화면이 어긋난다. 브랜드가 수정을 시작했을 수도 있다.

### 6-4. 사유는 **브랜드에게 그대로 나간다**

C2가 "내부 메모를 적지 마세요"를 고지한다. 서버는 가공하지 않고, **반려 사유를 어드민 전용 메모 필드로 오해할 수 있는 별도 컬럼을 두지 않는다.** 필드가 하나뿐이면 오용할 자리가 없다.

## 7. 서명 현황 갱신 — `PUT /v1/admin/contracts/{id}/signatures`

**이 화면이 어드민 계약 관리가 존재하는 이유다**(§28-0). 파트너·스튜디오의 「확인한 시점 기준 · N 기준」을 실제로 입력하는 곳이 여기뿐이다.

```json
{ "brandSignedAt": "2026-08-14T09:12:00",
  "creatorSignedAt": null,
  "version": 7 }
```

### 7-1. **기준 시각은 클라이언트가 보내지 않는다**

`signature_as_of = now` — **서버 시각으로 고정한다.**

§28-5가 이 화면의 핵심 문구로 꼽은 것이 기준 시각 경고다 — "대시보드를 보지 않고 저장하면 **시각만 새로워지고** 양측은 확인된 값이라 읽는다." 즉 **기준 시각의 의미는 "운영자가 저장 버튼을 누른 때"**이지 운영자가 입력하는 값이 아니다.

클라이언트가 보낼 수 있게 하면 **과거 시각을 적어 넣어 "그때 확인했다"는 기록을 만들 수 있다.** 그 값이 양측 화면에 「운영자가 확인한 시점」으로 나간다.

### 7-2. 상태는 **두 값의 조합에서 파생**된다 (같은 트랜잭션)

| `brandSignedAt` | `creatorSignedAt` | 결과 상태 |
| --- | --- | --- |
| NULL | NULL | `SIGNING` |
| 값 | NULL | `SIGNING` |
| NULL | 값 | `SIGNING` |
| **값** | **값** | **`CONCLUSION_PENDING`** |

- 둘 다 차면 **같은 트랜잭션에서** `CONCLUSION_PENDING`으로 올린다. 스튜디오 설계 4-1이 지적한 「둘 다 서명했는데 상태는 `SIGNING`」 조합을 여기서 없앤다.
- 하나라도 `NULL`로 되돌리면 **`SIGNING`으로 내린다**(전이 8). 이것이 §28-5의 "체크 해제 가능"이다.
- **허용 진입 상태는 `SIGNING` · `CONCLUSION_PENDING` 둘뿐.** `CONCLUDED`에서 호출하면 409 — 체결 후 잠긴다.

### 7-3. 값이 안 바뀌어도 **저장을 허용한다**

C3 모달이 「브랜드: 서명 완료 · 08.14 09:12 **(변경 없음)**」을 보여준다. 즉 **기준 시각만 갱신하는 저장이 정상 동작**이다 — 운영자가 대시보드를 확인했지만 새 서명이 없었던 경우이고, 그 사실 자체가 양측에 전달할 정보다.

→ "변경 없음"을 400으로 막지 않는다. 다만 이력 `detail`에 **무엇이 바뀌었는지**를 적는다(「인플루언서 서명 완료 확인」 / 「변경 없음 · 기준 시각만 갱신」).

### 7-4. before → after는 **FE가 만든다**

C3 모달이 변경 내역을 before → after로 보여주지만, **서버가 미리보기 API를 만들지 않는다.** FE는 상세 조회로 현재 값을 이미 갖고 있고, after는 사용자가 방금 입력한 값이다. 서버가 낄 자리가 없다.

서버가 보장해야 하는 것은 **그 사이에 값이 안 바뀌는 것**이고, 그건 `version`(낙관적 락)이 한다 — 어드민은 다중 사용자이고 **운영자 둘이 같은 계약을 여는 일이 실제로 있다.**

### 7-5. 미래 시각과 순서

| 검증 | |
| --- | --- |
| `signedAt ≤ now` | 미래에 서명할 수 없다 |
| `signatureRequestedAt ≤ signedAt` | 발송 전에 서명할 수 없다 |
| 두 서명 간 순서 | **검증하지 않는다** — §25-1 "서명에 순서가 없다" |
| `signedAt > signatureDeadlineAt` | **막지 않는다** — 실제로 늦게 서명한 건을 운영자가 그대로 옮겨 적을 수 있어야 한다. 기한 초과 서명을 어떻게 처리할지는 운영 판단이고, **입력을 막으면 사실을 기록할 방법이 사라진다** |

## 8. 체결 처리 — `POST /v1/admin/contracts/{id}/conclude`

**이 시스템에서 유일한 불가역 조치**(§28-6 · §25-4).

**전이**: `CONCLUSION_PENDING` → `CONCLUDED`

### 8-1. 진입 조건 4개를 **전부 서버가 다시 본다**

| 조건 | 실패 시 |
| --- | --- |
| `status = CONCLUSION_PENDING` | 409 |
| `brand_signed_at IS NOT NULL` AND `creator_signed_at IS NOT NULL` | 409 |
| `SIGNED_PDF` 존재 | 409 `CONTRACT_DOCUMENT_REQUIRED` |
| `AUDIT_TRAIL` 존재 | 409 `CONTRACT_DOCUMENT_REQUIRED` |

두 번째는 상태에서 파생되므로 중복처럼 보이지만, **7-2의 파생 로직에 버그가 있으면 상태만 맞고 값이 비는 계약이 생긴다.** 불가역 조치의 진입 조건은 중복해서 본다.

**문서 2종은 「버튼 비활성」이 FE의 표현**이고(§28-6 · 절대 규칙: 필수 미입력은 에러 문구 없이 비활성), 서버는 409로 막는다. 이 경우만 `kind: REQUIRED`로 내려 FE가 문구를 띄우지 않게 한다.

### 8-2. 트랜잭션

상태·서명·문서 판정 → `concluded_at = now` → 조건부 UPDATE → 이력 `CONCLUDED` append(처리자 실명) → **공구 생성 게이트 호출** → 양측 통지.

### 8-3. 공구 생성은 **계약이 하지 않는다**

파트너 설계 1-8 그대로 — 계약은 게이트만 연다.

```sql
UPDATE contract SET group_buy_id = :id
 WHERE contract_id = :cid AND status = 'CONCLUDED' AND group_buy_id IS NULL
```

**공구 도메인이 아직 없다.** 현재 범위에서는 `CONCLUDED` 전이까지만 하고, `group_buy_id`는 공구 모듈이 붙을 때 이 게이트로 채운다. C4 모달의 「생성될 공구」 미리보기는 **계약 값(공구명·기간)을 그대로 보여주는 것**이라 공구 모듈 없이도 그릴 수 있다.

> ⚠️ **공구 모듈 도착 전에 체결을 열면 「체결완료인데 공구가 없는 계약」이 쌓인다.** C4 모달이 "공구가 생성됩니다"라고 약속하고 B5가 「생성된 공구 GRB-…」를 보여주므로 **화면이 거짓말을 한다.** 순서 의존이 있는 유일한 지점이다 — 15절 리스크 참조.

### 8-4. 체결 후 **전이가 없다**

§25-2의 [결정 필요] 그대로. `CONCLUDED`를 벗어나는 전이를 만들지 않고, 공구 진행 중 중단은 공구 관리의 「중단」이다.

## 9. 만료 처리 — `POST /v1/admin/contracts/{id}/expire`

```json
{ "dashboardRechecked": true }
```

**전이**: `SIGNING` → `EXPIRED` · `close_actor_type = ADMIN`

### 9-1. **배치를 만들지 않는다**

§25-3 — "만료가 자동 판정이 아니다. 운영자가 확인해 만료 처리한다." §25-9 — "모든 수동 처리에 처리자·시각이 남는다."

스케줄러가 상태를 닫으면 **처리자가 「시스템」이 되어** 파트너 rev.7이 주체를 「시스템」에서 「운영자」로 바꾼 개정이 되돌아간다. 큐 카운트(2-3)만 조건으로 뽑고 **닫는 것은 사람이 한다.**

### 9-2. 서버 검증

| 검증 | 이유 |
| --- | --- |
| `status = SIGNING` | `CONCLUSION_PENDING`은 **양측이 서명한 건**이라 만료 대상이 아니다 — 상태 조건만으로 §28-7의 "성립한 계약을 닫는" 사고가 구조적으로 막힌다 |
| `signature_deadline_at < now` | **기한 전 만료 불가.** 시안이 버튼을 비활성하지만 서버가 본다 |
| `dashboardRechecked = true` | 1-4 — 받되 저장하지 않는다 |

**한쪽만 서명한 건은 만료된다.** 시안 C5의 예시가 그렇다(브랜드 완료 · 인플루언서 없음). 「서명이 하나라도 있으면 막는다」는 규칙을 넣지 않는다 — 그게 정확히 만료의 정의다.

### 9-3. 사유가 없다

`close_reason_code = NULL`. §27-6 — "만료: 사유 카드 없음 · 아무도 거절하지 않았으므로 중립색." 만료 API는 사유 필드를 **받지 않는다.**

### 9-4. 일괄 처리를 만들지 않는다

§28-8 D #8이 미정이지만, 시안이 건별로만 둔 이유가 명확하다 — **서명 반영 누락 위험.** 일괄 처리는 C5의 재확인 체크를 한 번으로 줄이는 것이고, 그건 확인하지 않는 것과 같다. 확정 전까지 **엔드포인트를 만들지 않는다**(미결 #5).

## 10-A. 계약 취소 — `POST /v1/admin/contracts/{id}/cancel`

**계약 취소는 운영자만 한다.** 브랜드에게는 계약 취소가 없다 — 발송 전의 되돌림은 `[요청 취소]`(검토 대기 → 작성중)뿐이다. 발송 이후는 모두싸인에 양측 서명 요청이 나가 있어, 우리 상태만 종결하면 양측이 여전히 서명 링크를 들고 있으므로 요청을 거둘 수 있는 사람만 취소한다.

| | 처리 |
| --- | --- |
| 허용 상태 | `SIGNING` · `CONCLUSION_PENDING` → `CANCELED` (`CONCLUDED`는 체결 후 해지 값이 없어 제외 — 미결) |
| 체크리스트 | `signatureRequestWithdrawn = true` 필수 — 모두싸인에서 서명 요청을 회수했다는 확인(API 미도입) · 없으면 400 `CONTRACT_CHECKLIST_REQUIRED` |
| 사유 | 브랜드 취소와 같은 5종(`ContractCloseReasonCode`) 필수 · `ETC`면 메모 필수 · 메모 1,000자 |
| 종결 필드 | `close_actor_type = ADMIN` · 사유·메모 저장 |
| 이력 | `CANCELED` append (actor `ADMIN`, detail = 사유 라벨) |
| 통지 | 양측 |
| 권한 | 상세 `permissions.canCancel` |

스튜디오 입장에서 도착한 계약의 `CANCELED`는 이제 **항상 운영자 취소**다. 만료(`EXPIRED`)도 주체가 `ADMIN`이라 FE는 `status`로 둘을 가른다.

## 10. 재발송 처리 기록 — `POST /v1/admin/contracts/{id}/resend/handle`

§28-0 — "재발송 자체는 모두싸인에서 하고 **이 화면은 기록만** 한다."

| | 처리 |
| --- | --- |
| 상태 | **불변**(`SIGNING`) |
| 미처리 요청이 있으면 | 전부 `handled_at = now` · `handled_by = operator`로 닫는다 |
| **미처리 요청이 없어도** | **허용한다** — 운영자가 자발적으로 재발송할 수 있다(B4 이력에 요청 없는 재발송이 있다) |
| 이력 | `RESEND_HANDLED` append |

**요청 여러 건을 한 번에 닫는다** — 스튜디오 설계 5-2와 파트너 설계 3-6이 중복 억제를 걸었지만, 브랜드와 인플루언서가 **각각** 요청하면 미처리 행이 2개다. 한 번의 재발송이 둘 다 해소한다.

**`handled_at`을 채우는 것 외에 상태를 바꾸지 않는다.** 재발송은 서명 기한을 늘리지도, 발송 일시를 갱신하지도 않는다 — 모두싸인에서 기한이 바뀌었다면 운영자가 그 사실을 옮겨 적어야 하는데, **그 경로가 지금 없다**(미결 #6).

## 11. 체결 문서 — 업로드 · 다운로드

### 11-1. 기존 presign 패턴을 그대로 쓴다

`MessageAttachmentService`(`src/main/java/showroomz/api/common/attachment/service/MessageAttachmentService.java`)가 이미 S3 presigned PUT/GET을 하고 있다 — 업로드 15분 · 다운로드 5분 만료.

| Method | Path | |
| --- | --- | --- |
| `POST` | `/{id}/documents/presign` | `documentType` · `contentType` · `fileName` → 업로드 URL |
| `POST` | `/{id}/documents` | 업로드 완료 등록 (`s3Key` · 크기 · 원본명) |
| `DELETE` | `/{id}/documents/{type}` | **`CONCLUSION_PENDING`에서만** |
| `GET` | `/{id}/documents/{type}` | 다운로드 URL |

**`fileUrl`을 그대로 쓰지 않고 매번 새로 서명한다** — 기존 서비스의 주석이 적어둔 이유 그대로다(S3 키가 UUID라 파일명이 깨진다).

### 11-2. 업로드 시 상태 판정

| 상태 | 업로드 |
| --- | --- |
| `CONCLUSION_PENDING` | ✅ (교체·삭제 포함) |
| `CONCLUDED` | ❌ **영구 잠금** — `CONTRACT_DOCUMENT_LOCKED` |
| 그 외 | ❌ |

§28-6 — "서명 원본이 바뀌면 계약의 증거가 사라진다."

### 11-3. 세 서피스가 같은 파일을 읽는다

B5 캡션 — "이 화면은 **그 파일의 단일 원본**이다. 브랜드·인플루언서도 각자 화면에서 내려받는다(서명 후에만)."

→ `contract_document` 한 행을 **세 서피스의 다운로드 API가 각자의 권한 판정을 거쳐** 읽는다. 파일을 복사하지 않는다. 스튜디오는 `status = CONCLUDED`에서만(스튜디오 설계 4-6), 파트너도 같다.

## 12. 계약서 PDF 자동 생성

`SHOWROOMZ_계약서_생성규격_v0.1.md` 전량이 여기에 대응한다. **파트너·스튜디오 설계서에 없던 책임**이다.

### 12-1. 생성 시점 — **요청 시 생성(lazy) + 캐시**

규격 §7은 ①브랜드 검토 요청 → ②**플랫폼 PDF 자동 생성** → ③운영자 다운로드 순으로 적었다. 그대로 읽으면 검토 요청 트랜잭션 안에서 PDF를 만들게 되는데, **그렇게 만들지 않는다.**

| 안 | 문제 |
| --- | --- |
| 검토 요청 트랜잭션 안에서 동기 생성 | 렌더링(헤드리스 브라우저)이 느리거나 죽으면 **브랜드의 검토 요청이 실패한다.** 계약 제출이 PDF 엔진의 가용성에 묶인다 |
| 검토 요청 후 비동기 생성 | 어드민 B1이 파일을 못 받는 구간이 생기고, **실패를 알아차릴 사람이 없다** |
| **다운로드 요청 시 생성 + 캐시** ← 채택 | 실패해도 **운영자가 즉시 알고 다시 누른다.** 반려된 계약의 PDF를 만들지 않아 낭비도 없다 |

**캐시 키는 `review_requested_at`**이다 — 파일명에 「제출본 기준 시각」을 박는 이유(규격 §7)가 그대로 무효화 조건이 된다. 재요청되면 `review_requested_at`이 갱신되고 캐시가 자동으로 무효가 된다.

```
GET /v1/admin/contracts/{id}/document-draft
  → GENERATED_DRAFT가 있고 생성 시점 == review_requested_at 이면 그 URL
  → 아니면 렌더링 → S3 업로드 → contract_document 덮어쓰기 → 이력 append → URL
```

**어드민만 이 엔드포인트를 갖는다.** 서명 전 계약서를 브랜드·인플루언서에게 주는 문제는 규격 미결 ⓘ(§28-8 D-12)로 열려 있다 — 확정 전까지 파트너·스튜디오에 경로를 열지 않는다.

### 12-2. 렌더링 스택

현재 `build.gradle`에 **PDF 라이브러리가 하나도 없다.** Thymeleaf는 있다.

| 단계 | 도구 |
| --- | --- |
| 치환 | **Thymeleaf** — `SHOWROOMZ_계약서_양식_v0.2.html`을 템플릿으로 이식 |
| HTML → PDF | **헤드리스 크로미움 `print-to-pdf`**(규격 §8) |
| 저장 | S3 (`contract_document`) |

**규격이 크로미움을 고른 근거는 타당하다** — 양식이 이미 `@page` · `@media print` · `page-break-after`를 갖추고 있어 변환 레이어가 필요 없다. 다만 **운영 비용이 있다**: 서버에 크로미움 바이너리(또는 별도 컨테이너)가 필요하고 현재 배포 구성에 없다.

> **대안(openhtmltopdf 등 JVM 내장)을 굳이 검토한다면** 양식의 `display:flex` 2곳이 걸린다 — 표 기반으로 바꾸면 JVM 안에서 끝나 배포가 단순해진다. 다만 **양식이 SoT이고 인쇄 결과가 곧 법적 문서**라 레이아웃을 우리 편의로 고치는 판단은 기획·법무가 할 일이다. 이 설계서는 **규격대로 크로미움을 전제**하고, 배포 구성 추가를 미결로 남긴다(미결 #1).

| `원천징수_문구` | `Creator.businessType` 분기 |
| **`관할법원`** | ⚠️ **「브랜드 주소지 관할」 — 매핑이 없다** |

> ⚠️ **`관할법원`이 파생으로 적혀 있지만 파생 규칙이 없다.** 주소 문자열에서 관할 법원을 뽑으려면 **행정구역 → 법원 매핑표**가 필요하고, 그건 코드가 아니라 데이터다. 잘못 뽑으면 **분쟁 시 관할 조항이 틀린 계약서**가 된다. 매핑표가 확정되기 전까지는 **「갑의 주소지를 관할하는 법원」이라는 문장 그대로 인쇄**하는 것이 안전하다(법률 문언으로 성립하고, 값을 틀리게 채우는 것보다 낫다). 미결 #3.

**`개당리워드`의 「원 단위 절사」는 파트너 설계 1-5와 일치한다** — 예상 리워드는 **1원 단위 · 소수점 버림(`RoundingMode.DOWN`)**으로 확정됐다. 계약서 렌더러는 **자체 계산을 두지 않고 같은 공유 유틸을 호출**한다. 계약서에 인쇄된 값과 화면·정산이 갈리면 §25-5-4의 분쟁 해결 경로(계약서가 근거)가 무너진다.

**`서명기한`** — 12-5에서 따로 다룬다.

### 12-4. 양식 템플릿의 이식 과제 3건

템플릿을 Thymeleaf로 옮길 때 **양식 파일을 그대로 쓸 수 없는 지점**이 셋 있다.

| # | 양식의 현재 상태 | 이식 시 |
| --- | --- | --- |
| 1 | **푸터가 `data-foot="… 1 / 6"`로 하드코딩** | 규격 §2가 "면 수가 변한다"(상품 3종 이상 · 비고 장문 · 지급비 0원)고 명시했는데 **6이 박혀 있다.** `n / N`을 **렌더링 시 계산**해야 한다 — 크로미움 `print-to-pdf`의 `headerTemplate`/`footerTemplate`이 페이지 번호를 넣어주므로 그쪽으로 옮긴다 |
| 2 | **상품 행이 `[1]` `[2]` 2행 고정** | 계약 상품은 1건 이상 N건이다. `th:each` 반복으로 바꾼다 |
| 3 | `data-k="인플루언서_사업자등록번호\|비사업자면 …"` — **같은 변수가 두 키로 존재** | 파이프 뒤는 작성자 주석이다. 이식 시 키를 하나로 정리한다 |

**서명면 강제 분리**(규격 §2 · §8)는 양식의 `page-break-after`가 이미 갖고 있어 그대로 쓴다. **이 규칙이 깨지면 모두싸인 입력란 좌표가 어긋나 5개 입력란이 엉뚱한 곳에 얹힌다** — 렌더링 테스트에서 가장 먼저 확인할 항목이다.

### 12-5. `서명기한`이 생성 시점에 **비어 있다** — 3안 중 ①을 권고

규격 미결 ⓙ. 계약서 제3조 제2항이 서명 기한을 인쇄해야 하는데, 그 값은 **운영자가 C1에서 입력**한다(§28-3). 즉 **PDF를 만드는 시점에는 아직 존재하지 않는다.**

규격이 제시한 3안을 절차 순서에 대보면 하나만 남는다.

| 안 | 판정 |
| --- | --- |
| ① 생성본에는 비우고 **모두싸인 유효기간으로만 관리** | ✅ **권고** |
| ② 검토 승인 시 **계약서 재생성** | ❌ **치명적** — 운영자는 ④단계에서 **이미 업로드하고 발송**했다(규격 §7). 승인 시점에 재생성하면 **우리가 보관한 계약서와 양측이 서명한 문서가 다른 파일**이 된다 |
| ③ 운영자가 발송 전에 기한을 먼저 정하고 생성 | △ 가능하지만 **입력 화면이 없다.** C1은 승인 모달이고 그 전에 기한을 받는 화면을 새로 만들어야 한다 |

①을 택할 때 제3조 제2항은 **「본 계약의 서명 기한은 전자서명 솔루션에 설정된 기한에 따른다」** 같은 문장이 된다. 기한이 **계약서에 숫자로 박히지 않는 것**이 법률적으로 문제가 없는지는 자문 대상이다 — 하지만 **②는 시스템이 두 개의 서로 다른 계약서를 갖게 되므로** 그쪽이 훨씬 위험하다. 미결 #7.

## 13. 상세 응답 · 권한

### 13-1. 응답 구조 — 어드민만의 것

```
contract     번호 · 공구명 · 상태(3필드) · 기간 · 일수
             brand{ marketId, name, link } · creator{ creatorId, name, link }
             threadId
stepper      4단 — reviewApprovedAt(+actor) · signatureRequestedAt
             · signedCount · concludedAt(+actor)
review       requestedAt · waitingElapsed · approvedAt
             · rejectedAt · rejectReason{code, detail}     ← 어드민만 전량
signature    requestedAt · deadlineAt · brandSignedAt · creatorSignedAt
             · asOf · asOfActorName · deadlinePassedDays
items[] · content · fixedFee · settlement · closure         ← 읽기 전용
documents[]  GENERATED_DRAFT · SIGNED_PDF · AUDIT_TRAIL (각 존재 여부 + URL)
resend       pendingCount · lastRequestedAt · lastRequesterType
groupBuy     groupBuyId · groupBuyNumber · status
permissions  canApprove · canReject · canUpdateSignature
             · canConclude · canExpire · canHandleResend
             · canUploadDocument
history[]    **전량** · actorType · actorId · actorDisplayName · detail
version      낙관적 락(7-4)
```

| 어드민에만 있는 것 | 근거 |
| --- | --- |
| `review` 블록 전량 | 스튜디오는 통째로 뺐고(스튜디오 설계 4-2) 파트너는 자기 계약의 반려 사유만 본다 |
| `waitingElapsed`(대기 경과) | B1 상태 카드 「1일 2시간」 — §28-8 D #5(검토 SLA 미정)라 **표시만 하고 판정하지 않는다** |
| `asOfActorName` | 「2026.08.14 09:30 · 김운영」 — 실명(0-6) |
| `deadlinePassedDays` | C5 「23일 경과」 |
| `history[]` 전량 | 스튜디오는 7종 화이트리스트, 어드민은 16종 전부 |
| 양측 딥링크 | 브랜드 상세 · 인플루언서 상세 · 스레드 |

| 어드민에 **없는** 것 | 근거 |
| --- | --- |
| `warningFlags` | 0-7 |
| `payout` | 스튜디오 전용 관점 |
| 수정 가능한 조건 필드 | 0-1 |

### 13-2. `permissions` — 7종

| 키 | 조건 |
| --- | --- |
| `canApprove` / `canReject` | `REVIEW_PENDING` |
| `canUpdateSignature` | `SIGNING` · `CONCLUSION_PENDING` |
| `canConclude` | `CONCLUSION_PENDING` AND 서명 2종 AND 문서 2종 |
| `canExpire` | `SIGNING` AND `signature_deadline_at < now` |
| `canHandleResend` | `SIGNING` |
| `canUploadDocument` | `CONCLUSION_PENDING` |

**`canConclude`가 문서 존재까지 보는 것이 §28-6의 「두 파일이 다 올라와야 버튼이 열린다」**이다. FE가 문서 배열을 세어 판정하게 두지 않는다 — 판정 로직이 둘이면 갈린다.

### 13-3. 권한 분리는 **자리만 만들어 둔다**

§28-8 D #3 — "체결 완료·만료는 불가역이라 최고관리자 한정이 타당해 보이나 시안은 구분하지 않음" (⬜ 대표 확정).

→ 지금은 **운영자 전원 허용**(시안대로)하되, `conclude` · `expire` 두 메서드에만 **권한 체크 지점을 명시적으로 남긴다**. 확정되면 그 두 줄에 역할 검사를 넣으면 되고, 나머지 API는 손대지 않는다. 미결 #8.

### 14-1. 신규 `ErrorCode` — 8종

### 14-2. 구현 단계 (PR 분할)

**전제: 파트너 P1(V116~V121 + 엔티티)이 먼저.**

| 단계 | 내용 | 산출물 |
| --- | --- | --- |
| **R1** | `V123`~`V124` + 어드민 가시성 + 큐 조건 + `summary` | A1 · A2 |
| **R2** | 상세 조회(이력 전량 · `permissions`) | B1 · B1-b · B2 · B5 읽기 |
| **R3** | 검토 승인 · 반려 | C1 · C2 · B2 |
| **R4** | 서명 현황 갱신(낙관적 락 · 상태 파생) · 재발송 기록 | B3 · C3 |
| **R5** | 문서 업로드/다운로드 · 체결 처리 · 만료 처리 | B4 · C4 · C5 |
| **R6** | **계약서 PDF 생성**(템플릿 이식 · 렌더링 · 캐시) | B1 계약서 카드 |

**R3이 파트너 P5(검토 요청)와 짝이다** — 어느 쪽이 먼저 배포되든 반대편이 없으면 계약이 한 상태에 갇힌다. **둘을 같은 릴리스로 묶는다.**

**R6을 마지막에 두는 이유** — 렌더링 스택(크로미움 배포 구성)과 문안 확정(`[자문대기-법률]` 3개 조)이 둘 다 외부 의존이라 **가장 늦게 준비된다.** R1~R5는 PDF 없이 전부 동작하고, 그동안 운영자는 조건 카드를 읽고 모두싸인에 수기로 입력한다 — **이것이 규격이 없애려는 상태**이므로 R6은 **미루되 빼지 않는다.**
