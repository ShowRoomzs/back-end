[이 화면이 왜 생겼나] 모두싸인 API를 도입하지 않기로 확정되면서(rev.7 · 요금제만 사용) 우리 시스템은 서명 링크도, 서명 완료 통지도, PDF·감사추적인증서도 자동으로 받지 못한다. 그래서 파트너센터·쇼룸 스튜디오에 보이는 서명 현황은 전부 운영자가 모두싸인에서 눈으로 확인해 입력한 값이고, 양쪽 화면에 「확인한 시점 기준 · YYYY.MM.DD HH:MM 기준」이 박혀 있다. 그 값을 입력하는 화면이 어디에도 없었다 — 이 파일이 그 자리다.
[상류 두 화면이 요구하는 입력값 10종 — 전부 이 파일에서 나온다] ① 검토 통과/반려(B1) ② 반려 사유 2단(제목 + 상세 · C2) ③ 검토 통과 일시(C1) ④ 서명 요청 발송 일시 · 서명 기한(C1 — 둘 다 모두싸인에서 정해진 값을 옮겨 적는다) ⑤ 브랜드 서명 완료 일시(B3) ⑥ 인플루언서 서명 완료 일시(B3) ⑦ 기준 시각(B3 저장 시각 = 양쪽 .s-asof) ⑧ 체결 완료 처리(C4) ⑨ 서명 PDF·감사추적인증서 업로드(B4) ⑩ 만료 처리(C5).
[지침에 없던 5번째 작업 — 서명 안내 재발송] 파트너 rev.7과 스튜디오 모두 [서명 안내 다시 받기] 버튼을 두고 설명을 “운영자에게 재발송 요청”이라 적었는데, 그 요청이 도착할 화면이 정의돼 있지 않았다. 이 파일뿐이므로 조치 큐 4번째 항목과 B3의 안내 블록 + [재발송 처리 기록]으로 받는다. 재발송 자체는 모두싸인에서 하고 이 화면은 기록만 한다(발송 권한이 우리에게 없다는 rev.7 제약 그대로).
[계약서는 우리가 만들고, 운영자가 올린다] 계약서 파일을 플랫폼이 생성한다 — 브랜드가 입력한 조건 + 표준 조항으로 만들어진 PDF이고, 운영자는 그것을 내려받아 모두싸인에 업로드한다. 이 사실이 C1의 성격을 바꿨다: 원래는 조건을 모두싸인 화면에 다시 입력하는 작업이라 「제출본 그대로 옮겼습니까」를 확인해야 했지만, 파일을 올리는 방식이면 전사 오류가 원천적으로 생기지 않는다 — 체크리스트가 4항목에서 3항목(수신자 · 업로드 · 발송)으로 줄었다.
[운영자는 문안을 고칠 수 없다] 다운로드는 생성된 파일을 받는 것이고 편집 경로가 아니다 — 조건이 잘못됐으면 반려해서 브랜드가 고치게 한다(조건 카드를 읽기 전용으로 둔 것과 같은 이유). 파일명에 계약번호와 생성 기준 시각을 박아 어느 제출본으로 만든 파일인지 남긴다 — 브랜드가 반려 후 재요청하면 조건이 바뀌므로 새로 받아야 한다.
[체결본은 양측이 각자 내려받는다] 체결 완료 후 서명 PDF·감사추적인증서는 파트너센터·쇼룸 스튜디오에서 각 당사자가 직접 내려받는다 — 운영자가 메일로 보내주는 일을 만들지 않기 위함이다. 이 화면은 그 파일의 단일 원본이고 교체·삭제가 불가한 이유가 여기에도 있다: 운영자가 파일을 바꾸면 양측이 서로 다른 계약서를 받게 된다. 서명 전에는 열지 않았다 — 미서명 문서가 돌아다니면 어느 것이 합의된 내용인지 흐려진다(확인 필요 ⓘ).
[서명 기한도 우리가 정하지 않는다] 모두싸인에 계약을 운영자가 직접 입력하므로 서명 기한도 거기서 정해진다 — 우리 화면이 「공구 시작 −3일」 같은 값을 계산해 보여 주면 있지도 않은 규칙이 생기고, 모두싸인에 실제로 들어간 값과 어긋날 수 있다. 그래서 C1에서 발송 일시와 나란히 입력받는다. 이 값이 B3·C5의 「서명 기한」이 되고 만료 판단의 유일한 기준이다 — 확인 체크로 받으면 “설정했다”는 사실만 남고 며칠인지가 우리 쪽에 남지 않는다.
[운영자는 계약을 작성하지 않는다] 공구명·기간·상품 항목·리워드율·고정 지급비·콘텐츠 의무 — 전부 읽기 전용이고 수정 필드가 한 곳도 없다. 양측이 서명할 대상이 바뀌면 안 되기 때문이며, 문제가 있으면 반려한다. 계약 조건 카드는 파트너 B3c·B4b의 읽기 전용 카드를 문자 단위로 가져왔고 브랜드·인플루언서 2행만 더했다(파트너는 「계약 상대」 1행, 스튜디오는 「브랜드」 1행 — 운영자는 양측이 다 보여야 한다).
[검토 체크리스트를 두지 않는다 — MVP에는 규칙 위반이 없다] 금액·기간 임계값(리워드율 40% · 고정 지급비 100만원 · 할인율 70% 등)이 MVP 범위에 없다. 임계값이 없으면 판정할 것도 없고, 없는 기준으로 만든 판정표는 있지도 않은 규칙이 있는 것처럼 보이게 한다 — 없는 데이터를 UI에 올리지 않는다는 기존 원칙 그대로다(게시물 신고 행을 그리지 않은 것과 같은 판단). 그래서 검토 진행 다음에 계약 조건 카드가 바로 온다.
[그러면 운영자 검토는 무엇을 하나] 대조다 — 계약 조건이 스레드의 합의 내용과 같은지, 상품 항목이 상품 정보와 맞는지, 콘텐츠 의무가 이행 판정 가능한 형태인지, 당사자 계정이 정상인지. 전부 원문을 읽어야 아는 것이고 자동화할 수 없어 판정 UI를 만들지 않았다. 반려 사유 목록도 같은 축으로 다시 썼다 — 임계값 문구를 빼고 합의 불일치 · 정보 불일치 · 이행 판정 불가 · 오기·누락 · 계정 상태 5종이다.
[승인 ≠ 발송] API가 없으므로 이 화면은 서명 요청을 보내지 못한다. 운영자가 모두싸인에 계약 내용을 직접 입력해 보낸 뒤 승인을 누르고, 승인은 “보냈다”는 기록이다. 그래서 C1이 단순 확인 모달이 아니라 모두싸인 입력 체크리스트 + 발송 일시 입력이다 — 발송 전에 승인하면 양측이 오지 않은 메일을 기다린다. 체크는 우리 시스템이 검증할 방법이 없어 눈 대조가 유일한 방어선이다.
[서명 현황 체크는 되돌릴 수 있고, 체결은 불가역이다] .sbox는 양측과 완전 동일 마크업이고 .sbox.edit로 체크 + 일시 입력만 더했다 — 오입력한 서명 완료가 양측 화면에 박히면 되돌릴 경로가 있어야 한다. 체결 완료를 누른 순간부터 잠긴다(공구가 생성되기 때문). 이 화면에서 불가역한 조치는 체결 완료 하나이며 확인 모달(C4)이 서명 기록·업로드 문서·생성될 공구를 다시 나열한다.
[기준 시각이 이 화면의 가장 위험한 값] 저장 시각이 양쪽 .s-asof에 그대로 나가고, 양측은 그것을 운영자가 모두싸인을 확인한 때로 읽는다. 대시보드를 보지 않고 저장하면 시각만 새로워지고 값은 그대로인 화면이 나간다 — B3 경고 배너와 C3 모달 양쪽에 이 문장을 박았다. C3은 변경 내역을 before → after로 보여준다.
[N건 대기를 맨 위에] 운영자는 처리할 것을 찾으러 오므로 조치 큐 4개(검토 대기 · 체결 처리 대기 · 만료 확인 · 재발송 요청)를 탭보다 위에 둔다. 상태 배지 색은 바꾸지 않았다 — 「검토 대기」가 운영자에게는 조치 필요 상태지만 파트너·스튜디오에서 정보색이고 같은 계약이 세 화면에서 다른 색이면 안 된다(원칙 ③). 앞세우는 수단은 큐 카운트 + 정렬(검토 요청 오래된순 기본)이다.
[상태 색 — 세 화면 동일] 작성중=중립 · 검토 대기·서명 진행중·체결 처리 대기=정보 · 검토 반려=경고 · 체결완료=성공 · 거절=위험 · 만료·취소=중립(원칙 ②). 종결 스텝 칩도 배지와 같은 축이다(.stop 거절 · .halt 만료·취소).
[탭에 없는 두 상태 — 작성중 · 검토 반려] 작성중은 검토 요청 전이라 운영자에게 도착하지 않는다(스튜디오가 같은 이유로 작성중 탭을 없앴다). 검토 반려는 반려하는 순간 공이 브랜드로 넘어가 운영자 조치 대상이 아니다 — 전체 탭에 배지로만 남는다. 탭 6종: 전체 10 · 검토 대기 2 · 서명 진행중 3 · 체결 처리 대기 1 · 체결완료 1 · 종료 2(+ 검토 반려 1 = 10).
[목록은 조회 · 액션 없음] 관리 열·체크박스·일괄 처리가 없고 행 클릭 진입이다(v1.3 목록 상호작용 규칙 + 어드민 공통). 승인·반려·체결은 근거를 읽고 누르는 판단이라 목록에서 누르면 검토가 형식이 된다. 운영자 화면이라 주 CTA도 없다(파트너의 [+ 계약 작성]을 가져오지 않는다 — 운영자는 계약을 만들지 않는다).
[모든 수동 처리에 처리자·시각이 남는다] 이력 항목의 주체를 「김운영」으로 적고(파트너·스튜디오 쪽 이력은 「어드민」·「운영자」로 익명), 만료·체결·서명 갱신·재발송 전부 기록된다. 파트너 B7의 주체가 rev.7에서 「시스템」 → 「어드민」으로 바뀐 것이 이 규칙의 출발점이다.
[필수 미입력 = 버튼 비활성만] C1의 체크 4개, C5의 재확인 체크, B4의 문서 2종 — 전부 에러 문구 없이 버튼만 비활성이다(프로젝트 절대 규칙). B4는 우측 메타에 「감사추적인증서 미업로드」를 경고색으로 띄워 왜 비활성인지를 화면에서 읽히게 했다.
[GNB — 제안 · 확정 필요] 기존 어드민 셸(20개 파일 확정)에 계약 관리가 없었다. 「5 계약 관리」를 공구 관리 앞에 넣고 이하 번호를 +1 했다(6 공구 · 7 거래 · 8 정산 · 9 CS·콘텐츠 · 10 게시물·소통 · 11 설정) — 계약 체결이 공구 생성의 입구라 흐름 순서와 맞고, 하위 메뉴 없는 1단 항목이다. 기존 20개 파일에는 아직 반영하지 않았다 — 확정되면 일괄 반영이 필요하다.
[호칭 — 「운영자」로 통일 · 확정 필요] 지침은 “어드민 화면 문구는 「어드민」”이었으나 기존 어드민 20개 파일이 전부 「운영자」이고 탑바가 “김운영 운영자”다. 이 파일만 「어드민」이면 한 화면에 두 이름이 생긴다. 파트너센터는 「어드민」, 스튜디오는 「운영자」로 쓰는 것은 그대로 두고 운영자 자신의 화면만 「운영자」로 맞췄다 — 되돌리려면 치환 한 번이다.
[원본 시각 모순 1건 수정] 파트너 B3c는 검토 요청을 08.13 16:40으로, B4b는 검토 통과를 08.13 15:20 · 서명 요청 발송을 16:40으로 적어 통과가 요청보다 빠르다. 이 파일은 요청 14:50 → 통과 15:20 → 발송 16:40으로 잡았다 — 파트너 파일도 같은 값으로 맞춰야 세 화면이 일치한다.
[상세는 상단·하단 2장으로 낸다] 좌측 카드가 최대 5장(서명 진행 · 체크리스트/체결 문서 · 계약 조건 · 상품 항목 · 콘텐츠 의무)이라 1024px 프레임 하나에 들어가지 않는다 — ui-admin-07b-settlement-detail·ui-admin-18-influencer-detail이 쓴 방식 그대로 상단/하단 스냅샷 2장으로 쪼갰고 sticky 레일은 양쪽에 반복한다(스크롤해도 승인·반려·체결을 누를 수 있어야 한다). 실제 화면은 한 페이지를 스크롤하는 것이며 라우팅이 갈리지 않는다. B1이 가장 중요한 이유 — 체크리스트가 짚은 「리워드율 45%」의 원문이 하단 상품 항목에 있어, 운영자는 상단에서 짚고 하단에서 대조한다.
