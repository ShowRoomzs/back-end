# 전체 플로우 통합 테스트 시나리오 — 계약 → 공구 → 게시물 → 구매 → 주문관리

## 1. 범위와 판정 기준

- 대상: **연결 → 계약 체결 → 공구 생성·준비·오픈 → 공구 게시물 → 소비자 구매(결제) → 파트너센터 주문관리 → 구매확정 → 공구 종료·이행 확인 → 정산 게이트**까지 한 거래가 끝까지 흐르는지를 서피스 4개(파트너센터·쇼룸 스튜디오·어드민·소비자 앱)에 걸쳐 검증한다.
- 기준 자료(설계 정본):

| 구간 | 설계서 | 주요 API |
| --- | --- | --- |
| 계약 | `dev/브랜드 계약관리/26_…` · `dev/어드민 계약관리/28_…` | `/v1/seller/contracts` · `/v1/admin/contracts` · `/v1/creator/contracts` |
| 공구 | `dev/브랜드 공구관리/30_…` · `dev/쇼룸 공구관리/31_…` · `dev/어드민 공구관리/32_…` | `/v1/seller/group-buys` · `/v1/creator/group-buys` · `/v1/admin/group-buys` |
| 구매·결제 | `dev/결제 기능 구현 계획서.md` | `/v1/user/orders` · `/v1/user/payments` · `/v1/webhooks/portone` |
| 주문관리 | `dev/브랜드 주문관리/34_파트너센터_주문관리_BE_설계서.md` | `/v1/seller/orders` |

- 단일 기능의 세부 케이스는 각 기능테스트 문서(`브랜드_공구관리_기능테스트_상세.md` 등)가 담당한다. 이 문서는 **구간 사이의 이음새** — 한 구간의 출력이 다음 구간의 입력으로 올바로 넘어가는지 — 를 본다.
- 아래 케이스는 **테스트 명세**이며 통과 표시가 아니다. 7절 「현행 제약」에 적은 의존 기능은 실제 연결 후 목표 동작을 판정하고, 스텁의 `null`·미동작을 통과로 기록하지 않는다.
- 날짜·시각은 서버 `Asia/Seoul` 기준. 자동 전이는 스케줄러를 직접 실행하거나 기준 시각 컬럼을 조정해 재현한다(5절).

### 1-1. 등장인물·계정

| 역할 | 계정 | 비고 |
| --- | --- | --- |
| 브랜드 A | 파트너센터 셀러 | 마켓 1개 · `shipping_lead_days = 2` 로 설정해 발송기한 검증에 쓴다 |
| 브랜드 B | 파트너센터 셀러 | 격리 검증용 — 자기 공구·주문 1건 이상 보유 |
| 인플루언서 A | 쇼룸 스튜디오 | 브랜드 A와 연결·계약 상대 |
| 운영자 | 어드민 | 계약 체결·오픈 승인·거래 관리 권한 |
| 소비자 C1·C2 | 앱 유저 | C1 기본 배송지 보유 · C2는 취소 요청 플로우용 |

### 1-2. 기준 fixture (계약 조건)

- 상품 2개: 크림(정가 34,000 · 공구가 27,200) · 세럼(정가 30,000 · 공구가 24,000), 옵션 각 1개 이상, 재고 10.
- 배송비 3,000 · 무료배송 문턱 50,000 · 공구 기간 8일 · 리워드율 12% · 최소 물량 300 · 고정 지급비 300,000.
- 결제: 스테이징은 포트원 테스트 채널(카드·간편결제), 로컬 통합 테스트는 `portone.enabled=false`(FakePaymentGateway).

### 1-3. 공통 확인 방법

1. 매 단계에서 **행위자 화면의 상태와 상대 서피스의 상태를 함께** 조회한다(예: 브랜드가 준비 시작하면 소비자 앱의 취소 버튼이 바뀌어야 한다).
2. 성공 요청 후 목록·상세·요약(탭 카운트)·이력을 다시 조회해 같은 트랜잭션의 값이 함께 바뀌었는지 확인한다.
3. 실패 요청은 HTTP 상태·`code`를 확인하고, DB에 부수 효과(이력·환불 큐·재고 변화)가 남지 않았는지 확인한다.
4. 돈의 시점·방향에 닿는 값(발송기한 · 배송완료 출처 · 구매확정일 · 환불 예정액)은 **DB 원값까지** 기록한다.

## 2. 메인 해피패스 (E2E-0) — 한 거래의 일생

한 번의 연속 실행으로 끝까지 간다. 각 단계의 기대 결과가 다음 단계의 전제다.

| # | 단계 | 행위자 | 절차 | 기대 결과 (이음새 판정) |
| --- | --- | --- | --- | --- |
| 0-1 | 연결 | 브랜드 A → 인플루언서 A | `POST /v1/seller/connections` → `POST /v1/creator/connections/{id}/accept` | 연결 성립 · PAIR 스레드 생성. 계약 작성 진입 가능 |
| 0-2 | 계약 작성·검토 요청 | 브랜드 A | `POST /v1/seller/contracts` → 조건 입력(1-2 fixture) → `/{id}/validate` → `/{id}/review-request` | 하드 검증 통과 · 검토 중 상태 · 운영자 검토 큐 도착. **인플루언서에게는 아직 도착하지 않은 계약**(404 `CONTRACT_NOT_RECEIVED`) — 승인(서명 요청 발송) 후 `SIGNING`으로 도착 |
| 0-3 | 승인·서명·체결 | 운영자 | `/review/approve` → `PUT /{id}/signatures`(양측) → `POST /{id}/conclude` | **체결과 같은 트랜잭션에서 공구 1건 자동 생성** — `PREPARING` · `GB-YYYYMMDD-NNN` · 계약에 `groupBuyId` · 상품 `group_buy_status=PREPARING` · 이력 `CREATED(SYSTEM)` |
| 0-4 | 준비 게이트 ① | 브랜드 A | `POST /v1/seller/group-buys/{id}/stock-confirmation` | 게이트 1/3 · 이력 `STOCK_CONFIRMED` |
| 0-5 | 준비 게이트 ②③ | 인플루언서 A → 운영자 | `PUT /v1/creator/group-buys/{id}/post/draft` → `POST …/post/submission` → `POST /v1/admin/group-buys/{id}/open-review/approve` | 마지막 게이트 충족 순간 1회만 `PREPARING → READY` · 게시물 `SCHEDULED` |
| 0-6 | 자동 오픈 | 시스템 | `startAt` 도달 + 수명주기 배치(1분) | `IN_PROGRESS` · 게시물 `EXPOSED` · 상품 구매 가능. **시작 버튼은 어디에도 없다** |
| 0-7 | 게시물 노출 확인 | 소비자 C1 | 앱 피드·상품 상세 진입 | 공구 게시물 노출 · 대가관계 표시 자동 삽입 · 상품 상세에서 공구가 27,200 표시 |
| 0-8 | 주문서·주문 생성 | 소비자 C1 | 크림 1개 장바구니 → `POST /v1/user/orders/checkout` → `POST /v1/user/orders` | 금액은 서버 계산(27,200 + 배송비 3,000) · 주문 `PAYMENT_PENDING` · 재고 10→9(예약) |
| 0-9 | 결제 확정 | 소비자 C1 | `POST /v1/user/payments/{paymentId}/complete` (또는 웹훅) | 주문 `PAID` · **하위주문 활성화**: `order_delivery_group.fulfillment_status=NEW` · `sub_order_number={주문번호}-01` · `ship_due_at = paid_at + 2일` · 이력 `PAID` · 장바구니 행 삭제 |
| 0-10 | 신규 탭 확인 | 브랜드 A | `GET /v1/seller/orders?tab=NEW` · `GET /summary` | 행 1건(소비자 실명 전체 표기 · 발송기한 표시 · 오래된순) · `actionBar.prepareStart=1` · `tabCounts.NEW=1`. **타 브랜드(B) 화면에는 없음** |
| 0-11 | 발주서 + 준비 시작 | 브랜드 A | `POST /v1/seller/orders/purchase-order` (기본 8컬럼 — 다운로드 = 준비 시작 · 2026-10-05부터 옵션 없음) | xlsx 수신(항목 단위 행 · 수취인 실명·연락처·주소 포함) · 그룹 `PREPARING` · `purchase_order_download_log` 1행 · 이력 `PREPARE_STARTED`(소비자 취소권 종료 병기). **소비자 앱의 「주문 취소」가 「취소 요청」으로 바뀜** |
| 0-12 | 송장 등록 | 브랜드 A | `POST /v1/seller/orders/shipments` — CJ · `1234-5678-9012` | 그룹 `SHIPPING` · 송장은 숫자만 저장(`123456789012`) · `shipped_at` 확정(발송기한 판정값) · 발송기한 열 「—」. 소비자 앱 송장 노출은 목표 케이스(7절) |
| 0-13 | 배송완료 | 시스템(추적) | 추적 배치가 완료 감지 — **스텁 기간은 5-2 방법으로 재현** | `DELIVERED` · `delivered_source=TRACKER`(「자동 확인」 병기) · 배송완료 탭에 `구매확정 예정 D-7`. **브랜드 배송완료 버튼·요청 창구가 어디에도 없음을 함께 확인** |
| 0-14 | 구매확정 | 시스템 | D+7 경과 + 구매확정 배치(매시 05분) | 그룹 `CONFIRMED` · 항목 `PURCHASE_CONFIRMED` · 이력 `PURCHASE_CONFIRMED(시스템)` · 구매확정 탭에 결제금액 30,200 · `settlementLabel=null`(0 아님) |
| 0-15 | 공구 종료 | 시스템 | `endAt` 도달 + 수명주기 배치 | 공구 `ENDED` · 게시물 종료 · 상품 구매 불가. 진행 중이던 주문관리 데이터는 그대로 처리 가능 |
| 0-16 | 이행 확인 | 브랜드 A · 인플루언서 A | 각각 `POST …/fulfillment-check` `FULFILLED` | 측별 1회 · 불가역 |
| 0-17 | 정산 게이트 | 운영자 | `GET /v1/admin/group-buys/{id}` | `afterEnd.orderClosure.unclosedCount=0`(0-14의 구매확정이 미종결을 닫았다) · `settlement.blockers=[]`. **0-14 전에 조회하면 `UNCLOSED_ORDERS`로 닫혀 있어야 한다**. `canConfirmSettlement`는 정산 포트가 비어 있어 아직 `false`(7절) |

> **이음새 핵심 3곳** — ① 0-3 체결↔공구 생성이 원자적인가(실패 시 둘 다 롤백) ② 0-9 결제↔하위주문 활성화가 같은 트랜잭션인가(PAID인데 NEW가 아닌 그룹이 존재하면 결함) ③ 0-14 구매확정↔정산 게이트(미종결 집계가 실값인가).
>
> **실행 순서 메모** — 자동 테스트는 ③을 한 흐름에서 보려고 0-15(공구 종료)·0-16(이행 확인)을 0-14(구매확정)보다 **먼저** 실행한다. 공구가 끝난 뒤에도 주문 처리가 이어지는 실제 순서이기도 하다.

## 3. 취소 3경로 분기 (E2E-A·B·C)

각 경로는 E2E-0을 0-9(결제 완료)까지 실행한 뒤 분기한다.

### E2E-A. 소비자 취소 — 준비 시작 전

| ID | 절차 | 기대 결과 |
| --- | --- | --- |
| A-01 | 0-9 직후 소비자가 `POST /v1/user/orders/{id}/cancel` | PG 자동 취소(브랜드·운영자 개입 없음) · 주문 `CANCELLED` · 그룹 `CANCELLED(cancel_type=CONSUMER)` · 재고 9→10 원복 · **환불 큐에 쌓이지 않음**(PG가 직접 환불) |
| A-02 | 브랜드 A 취소 탭 조회 | 취소 사유 열 「소비자 취소 · 준비 시작 전」 · 관리 열 없음 · 신규 탭·요약 바에서 제외 |
| A-03 | 0-11(준비 시작) 후 같은 취소 호출 | **409 `ORDER_CANCEL_WINDOW_CLOSED`** · 주문·그룹·재고 불변. 앱은 취소 요청 경로 안내 |

### E2E-B. 취소 요청 → 승인 / 거부 — 준비 시작 후

전제: 0-11까지 실행(상품준비중). 소비자 C2가 크림+세럼 2항목 주문으로 시작하면 부분 승인 검증이 된다.

| ID | 절차 | 기대 결과 |
| --- | --- | --- |
| B-01 | 소비자가 취소 요청 생성(앱 C10 — 미구현 구간은 `order_cancel_request` 직접 적재) · 사유 4택 중 「단순 변심」 · 대상 크림 1항목 | 하위주문이 **취소 요청 탭으로 이동**(상품준비중 탭에서 사라짐 — 이행 상태는 `PREPARING` 그대로) · 목록에 「2건 중 1건 요청 · 남은 1건 발송 대기」 · 경과 열 |
| B-02 | 요청 걸린 상태에서 준비 시작 재시도·송장 등록·직권 취소 | 전부 `skipped[].code=CANCEL_REQUEST_PENDING_EXISTS` — 선처리 요구. 상태 불변 |
| B-03 | 취소 요청 탭에서 일괄 처리 수단 확인 | 체크박스·일괄 바 없음 · 관리 `요청 확인` 하나 — 승인은 상세에서만 |
| B-04 | `POST /v1/seller/orders/cancel-requests/{id}/approve` | **요청 항목(크림)만** `CANCELLED(REQUEST_APPROVED)` · 크림 재고 원복 · 세럼은 발송 대기 유지 · 그룹은 `PREPARING` **복귀**(상품준비중 탭 재등장) · `order_refund_task` 1행(27,200 · 배송비 미포함 — 부분 취소 재계산 없음) |
| B-05 | 같은 요청 재승인 | 409 `CANCEL_REQUEST_ALREADY_DECIDED` · 환불 큐·이력 중복 없음 |
| B-06 | (별건) 전 항목 요청을 승인 | 그룹 `CANCELLED` — 전 항목 승인일 때만 취소 탭 · 환불 예정액 = 항목 합 + **배송비 전액** |
| B-07 | (별건) `…/reject` — 사유 입력 | 사유 필수(빈 값 400) · 그룹 원래 탭 복귀 · 이력에 거부 사유(소비자 전달용) · 이후 송장 등록 정상 진행 |

### E2E-C. 브랜드 직권 취소

| ID | 절차 | 기대 결과 |
| --- | --- | --- |
| C-01 | 신규 탭에서 `POST /v1/seller/orders/cancel` — `SOLD_OUT` + 소비자 설명 | 그룹 `CANCELLED(SELLER_DIRECT)` · `status_at_cancel=NEW` 기록(§34-13 #1 확정 대비) · 전 항목 취소·재고 원복 · 환불 큐 1행(전액+배송비) · 이력에 사유+설명 |

## 4. 송장·배송 이상·반송 분기 (E2E-D·E)

### E2E-D. 엑셀 일괄 + 배송 이상 + 송장 수정

전제: 상품준비중 주문 3건 이상(그중 1건은 신규 유지).

| ID | 절차 | 기대 결과 |
| --- | --- | --- |
| D-01 | `GET /shipments/template` → 3행 작성(정상 2 · 신규 주문 1) → `POST /shipments/parse` | **상태 불변**(파싱만) · 정상 2행 valid · 신규 행 `NEW_NOT_ALLOWED`(「준비 시작 전이라 송장을 등록할 수 없습니다」) |

## 5. 자동 전이 재현 방법

### 5-1. 스케줄러

| 배치 | 주기 | 테스트 실행 |
| --- | --- | --- |
| 공구 수명주기(오픈·종료) | 1분 | 대기하거나 `GroupBuyLifecycleService`를 직접 호출 |
| 구매확정 | 매시 05분 | `OrderFulfillmentService.confirmPurchase(id, now, threshold)` 직접 호출 또는 cron 대기 |
| 배송 추적 | 30분(`delivery.tracker.poll-interval-ms`) | **`delivery.tracker.enabled=true` + 연동 구현 전에는 미기동**(7절) |

### 5-2. 추적 스텁 기간의 배송 구간 재현

연동 업체 연결 전에는 추적 이벤트가 없으므로, 판정 로직을 직접 태운다(판정·전이 코드는 운영과 동일 경로).

- 배송완료: `OrderFulfillmentService.applyTracking(대상, TrackSnapshot(lastEventAt, deliveredAt, false, false), now, 24, 7)` 호출 → `DELIVERED/TRACKER` 전이.
- 집화 미확인: `shipped_at`을 25시간 전으로 UPDATE 후 `applyTracking(…, Optional.empty(), …)`.
- 추적 정지: `TrackSnapshot(lastEventAt = 8일 전, …)` 주입.
- 반송·입고: `returnDetected=true` → `returnCompleted=true` 순서로 주입.
- 구매확정 기한: `delivered_at`을 8일 전으로 UPDATE 후 배치 실행.

> SQL로 상태 컬럼을 직접 바꾸는 방식은 이력·부수 효과가 빠지므로 **금지** — 반드시 서비스 메서드를 태운다.
