## 0. 먼저 물어본 두 가지에 대한 판단

### Q1. 기존 "위치" 기능 — 삭제인가, 응답에서만 제외인가

**답: 삭제하지 않는다. 이번 작업에서 아예 건드리지 않는다.**

먼저 사실 확인. "위치" 기능의 실체는 회원관리가 아니라 **로그인 이력** 쪽이다.

| 구성요소 | 위치 |
| --- | --- |
| `LoginHistory.country / city` | `domain/history/entity/LoginHistory.java` |
| GeoIP 조회 | `global/service/GeoLocationService.java` |
| 국가/도시 한글 변환 | `global/utils/LocationNameMapper.java` |
| 필터 API | `GET /v1/admin/history/login/filters/locations` |
| 검색 조건 | `LoginHistorySearchCondition.country / city` |
| GeoIP DB | `src/main/resources/GeoLite2-City.mmdb` (**63MB**) |

**현재 회원관리 API(`AdminUserService`)는 위치를 반환한 적이 없다.** 즉 "응답에서 제외"할 대상 자체가 없다. 새 소비자 상세의 `최근 로그인`은 `2026.08.14 09:41 · iOS 앱` — 일시 + 디바이스이고 위치는 없다. 새 DTO에 안 넣으면 그걸로 끝이다.

그래서 질문은 사실 "이 참에 로그인 이력의 위치 기능을 지울까"인데, 지우지 않는 이유:

1. **범위가 다르다.** `api/admin/history`는 별도 모듈이고 별도 화면이다. §25는 이 모듈을 언급하지 않는다. 회원관리 PR에 무관한 모듈 삭제를 섞으면 리뷰가 어려워지고 롤백 단위가 뭉개진다.
2. **접근 기록은 함부로 지우지 않는다.** 이 화면의 골격 자체가 "누가 무엇을 언제 봤는가"다(§25 성격). 로그인 이력은 그와 같은 계열의 기록이고, 기획서 ⓒ **개인정보 열람 로그 보존 기간**이 아직 법률 자문 대기다. 보존 기간이 정해지기 전에 컬럼을 DROP하면 되돌릴 수 없다.
3. **오히려 이번에 쓴다.** 새 상세의 `최근 로그인 · 디바이스`는 `Users.lastLoginAt` + `LoginHistory.userAgent → DeviceType`로 **실데이터로 채울 수 있다**. 위치 컬럼만 안 읽으면 된다.

**다만 따로 처리할 것 하나** — `GeoLite2-City.mmdb` 63MB가 jar/이미지에 그대로 들어간다. 빌드·배포 용량 문제이고 GeoLite2 라이선스는 주기적 갱신을 전제로 한다. 이건 **별도 이슈**로 빼서 (a) 리소스 외부화 또는 (b) 로그인 이력 화면이 새 어드민 IA(GNB)에 없다는 점을 근거로 기능 전체 폐기 — 둘 중 하나를 결정한다. 회원관리 PR에 넣지 않는다.

### Q2. 현재 없는 기능 — 임시데이터 vs 추후 추가

**답: 임시데이터는 넣지 않는다. 다만 전부 "추후"로 미루는 것도 아니다. 3분류로 나눈다.**

기획서가 이미 답을 갖고 있다. 두 문장이 결정적이다.

> 신고 관련 행은 `[자문대기-법률 · 쟁점 J]`라 **행 자체를 그리지 않았다** — **없는 데이터를 UI에 올리지 않는다** (§25-4)

> `— 파기됨`은 값이 있었다가 지워졌다는 뜻이다. **애초에 수집하지 않은 항목에는 쓰지 않는다** (§25-5)

기획자가 "데이터가 없으면 화면에 올리지 않는다"를 명시적 원칙으로 세웠다. 임시데이터는 이 원칙을 정면으로 어긴다.

그리고 지금 코드가 정확히 그 상태다 — `AdminUserDto`에 `1234567`, `"서울특별시 강남구 테헤란로 123, 101호"`, `dummyTotalOrderCount = 15`가 DTO 안에 하드코딩돼 있다. 이건 정리 대상이지 확장 대상이 아니다.

**결정적 논거 하나 더** — 이 화면은 **계정 정지 권한**을 가진 화면이고, 반품률은 기획서가 대놓고 "정지 판단의 근거"라고 못박은 숫자다. 가짜 `14.3%`를 보고 실제 계정을 정지시키면 실제 피해가 발생한다. 거래 지표만큼은 임시데이터가 절대 안 된다.

그래서 3분류:

| 분류 | 처리 | 해당 항목 |
| --- | --- | --- |
| **A. 실데이터로 지금 구현** | 데이터가 있거나 유도 가능 | 회원번호·닉네임·이름·휴대폰·가입수단·가입일·상태·최근로그인+디바이스·생년월일·성별·최초인증·배송지·팔로우 쇼룸 수·작성 문의 수·가입 후 경과·누적 주문 건수 |
| **B. 이번에 스키마·기능을 새로 만든다** | 이게 화면의 골격이라 미루면 화면이 성립 안 함 | 관리자 메모 누적 · 처리 이력 · 개인정보 열람 로그 · 정지/해제 사유 코드+처리자+상세사유 · 서버 마스킹 · 약관 동의 내역 |
| **C. 응답에서 빼고 FE가 안 그린다** | 소스 도메인 자체가 없음 | 최근 주문 5건 · 누적 구매액 · 반품·교환 건수/비율 · 좋아요 수 · 배송지 최근 사용 주문일 · 약관 버전 · 정지/해제 알림 발송 |

**B를 "추후"로 미루면 안 되는 이유**: 메모·이력·열람 로그·약관 동의는 *기록*이다. 기록은 소급이 안 된다. 지금 안 만들면 그 기간의 판단과 동의는 영원히 없다. 반대로 C는 나중에 주문 도메인이 완성되면 **과거 데이터까지 소급 계산된다**. 그래서 B는 지금, C는 나중이다.

**C의 UI 처리** — 카드를 지우지 말고 "연동 전" 빈 상태로 둔다. `— 파기됨`은 쓰지 않는다(수집한 적 없는 값이므로, §25-5 규칙 그대로). 응답에서는 필드를 아예 내리거나 `null`로 내려 FE가 행을 그리지 않게 한다.

**본인확인 3개 필드(내외국인·통신사·최근 갱신)만 예외적으로 B에 가깝게 처리** — PASS 미연동이라 값은 없지만, 이 프로젝트엔 이미 `IdentityVerificationService`라는 **스텁 경계**가 있다(임시 인증 데이터를 이 클래스 한 곳에 가둬 두고 TODO를 남기는 패턴). 값을 DTO에 흩뿌리지 말고 **컬럼을 만들고 스텁이 `null`을 채우게** 한다. 기획서 §25-5도 *"CI/DI는 DB 스키마 확정 전에 결론이 나야 한다"*고 스키마 결정을 급한 일로 본다.

## 2. 데이터 모델 변경

> Flyway 다음 버전은 **V108**. (주의: 현재 `V105`·`V106`이 각각 중복 존재 — 머지 사고로 보임. 별도 확인 필요.)

### V108 — 회원관리 개편

**1) `user_admin_memo` 신설 (누적 메모)**

```
user_admin_memo_id  BIGINT PK
user_id             BIGINT NOT NULL  FK→USERS
author_id           BIGINT NOT NULL  -- 작성 운영자(seller_id)
content             VARCHAR(300) NOT NULL
created_at          DATETIME NOT NULL
modified_at         DATETIME NULL    -- 값이 있으면 '수정됨' 표기
deleted_at          DATETIME NULL    -- soft delete
INDEX (user_id, created_at DESC)
```

- 300자는 **서버에서 검증**(기획: "서버에서 검증한다").
- 수정·삭제 권한: `author_id == 요청자` **AND** `now - created_at <= 24h`. **서버가 판정**하고, 응답에 `editable` 불리언을 실어 FE가 버튼 노출을 결정한다.
- soft delete인 이유: 기획 ⓖ *"삭제된 메모 본문을 감사 목적으로 보관할지 미정"*. **하드 삭제하면 나중에 보관 결정이 나도 소급 불가**하므로 일단 남긴다. 응답에서는 제외.
- `USERS.ADMIN_MEMO`는 **이번에 제거하지 않는다.** V108에서 기존 값을 `user_admin_memo`로 백필하고, 컬럼은 다음 릴리스에서 DROP(2단계 마이그레이션).

**2) `user_admin_history` 신설 (처리 이력)**

```
user_admin_history_id BIGINT PK
user_id               BIGINT NOT NULL FK→USERS
event_type            VARCHAR(32) NOT NULL
actor_type            VARCHAR(16) NOT NULL  -- OPERATOR / CONSUMER / SYSTEM
actor_id              BIGINT NULL           -- OPERATOR일 때 seller_id (이벤트 시점 고정)
detail                VARCHAR(500) NULL     -- "(사유: 반품 남용)" 같은 부가 문구
created_at            DATETIME NOT NULL
INDEX (user_id, created_at DESC)
```

`event_type`: `SIGNED_UP` · `STATUS_CHANGED` · `MEMO_CREATED` · `MEMO_UPDATED` · `MEMO_DELETED` · `PRIVACY_UNMASKED` · `WITHDRAWN`

`ProductInquiryHistory`의 `actor_id` 설계(이벤트 시점의 행위자를 고정해 두 번째 운영자가 처리해도 과거 이력이 안 바뀌게 한다)를 그대로 따른다.

**3) `user_privacy_access_log` 신설 (개인정보 열람 로그)**

```
user_privacy_access_log_id BIGINT PK
user_id                    BIGINT NOT NULL FK→USERS  -- 열람 대상 소비자
operator_id                BIGINT NOT NULL           -- 열람한 운영자(seller_id)
reason                     VARCHAR(32) NOT NULL      -- CS_RESPONSE / DELIVERY_INCIDENT / PAYMENT_RETURN_DISPUTE / INVESTIGATION_COOPERATION
fields                     VARCHAR(255) NOT NULL     -- 'NAME,BIRTHDAY,PHONE'
accessed_at                DATETIME NOT NULL
expires_at                 DATETIME NOT NULL         -- accessed_at + 10분
locked_at                  DATETIME NULL             -- 수동/자동 잠금 시각
INDEX (user_id, accessed_at DESC), INDEX (operator_id, accessed_at DESC)
```

- **`기타` 사유는 만들지 않는다** (§25-2: 4종을 벗어나는 열람이 정당한 경우가 없다).
- **상세 사유 텍스트 컬럼도 만들지 않는다** (§25-2: 사유 축은 통계로 집계돼야 한다). 나중에 사유별 통계 쿼리가 바로 돌아간다.
- 보존 기간 정책은 법률 자문 대기 → **삭제 배치는 만들지 않는다.**

**4) `user_terms_agreement` 신설 (약관 동의 내역)**

```
user_terms_agreement_id BIGINT PK
user_id                 BIGINT NOT NULL FK→USERS
terms_type              VARCHAR(32) NOT NULL  -- SERVICE / PRIVACY / UNIQUE_ID / CARRIER / MARKETING
version                 VARCHAR(16) NULL      -- 소급 불가한 기존 회원은 NULL
agreed_at               DATETIME NOT NULL
INDEX (user_id)
```

- **지금 만드는 이유**: 동의 기록은 소급이 안 된다. 가입 시점에 안 남기면 영원히 없다. 기획 §25-5도 *"약관 동의 내역은 파기 대상이 아니다(보존)"*로 못박았다.
- 기존 회원 백필: `Users`의 boolean 4개 → `agreed_at = USERS.CREATED_AT`, `version = NULL`. 버전은 모르므로 **NULL로 두고 FE는 버전 칩을 안 그린다** (가짜 `v1.0`을 넣지 않는다).
- 항목 구성 5종은 기획 ⓐ 법률 자문 대기 → 타입 enum만 잡고 확정 시 추가.

**5) `USERS` 컬럼 추가 (본인확인)**

```
NATIONALITY_TYPE     VARCHAR(16) NULL  -- DOMESTIC / FOREIGN, PASS 연동 전 NULL
CARRIER              VARCHAR(16) NULL  -- SKT / KT / LGU / MVNO, PASS 연동 전 NULL
IDENTITY_RENEWED_AT  DATETIME NULL     -- 최근 갱신
```

`IdentityVerificationService.IdentityVerification`에 `nationalityType` / `carrier` 필드를 추가하고 **`null`을 반환**한다(현 임시 데이터와 동일한 스텁 경계). PASS 연동 시 이 클래스 한 곳만 교체하면 된다.

**6) `user_status_history` 확장 (정지/해제)**

```
ALTER TABLE user_status_history
  ADD actor_id          BIGINT NULL       -- 처리 운영자(seller_id)
  ADD reason_type       VARCHAR(32) NULL  -- 정지 6종 / 해제 3종
  ADD reason_detail     VARCHAR(500) NULL -- '기타(직접 입력)'일 때만 필수
  ADD appeal_inquiry_id BIGINT NULL       -- 소명 1:1 문의
```

기존 `reason` 컬럼은 백필 후 다음 릴리스에서 DROP.

**7) `DELIVERY_ADDRESS`** — **변경 없음.** 별칭 컬럼을 추가하지 않는다(C13과 충돌, 위 1-2 참고).

## 3. API 설계

기존 `/v1/admin/users`를 유지하되 스펙에 맞춰 재작성한다.

### 목록

```
GET /v1/admin/users
  ?tab=ALL|ACTIVE|SUSPENDED|WITHDRAWN     (기본 ALL)
  &keyword=                               (회원번호 / 닉네임 / 휴대폰 뒤4자리 — 서버가 형태로 축 판별)
  &providerType=KAKAO|NAVER|APPLE|GOOGLE
  &sort=RECENT_JOINED|ORDER_COUNT_DESC|MEMBER_NO
  &page&size
```

응답 `content[]`: `memberNo("CST-88231")` `nickname` `maskedName` `maskedPhone` `providerType` `joinedAt` `orderCount` `status`
응답 `summary`: 탭별 요약 — `ALL` → `{total, active, suspended, withdrawn}`, `SUSPENDED` → `{suspended, newSuspendedIn30Days}`

**이름·휴대폰은 서버가 마스킹해서 내려보낸다.** 원본을 내리고 FE가 가리는 방식은 통제가 아니다 — 응답 페이로드에 이미 전체 값이 들어 있으면 열람 통제가 무의미하다. 목록은 **해제 경로가 없으므로**(§25-1) 원본을 아예 안 보낸다.

`keyword` 축 판별: `CST-`로 시작 → 회원번호, 숫자 4자리 → 휴대폰 뒤 4자리, 그 외 → 닉네임 부분일치.

### 상세

```
GET /v1/admin/users/{userId}
```

마스킹 상태를 **서버가 판정**한다 — 유효한 열람 세션(`user_privacy_access_log` 중 `expires_at > now`, `locked_at IS NULL`, `operator_id = 요청자`)이 있으면 원본, 없으면 마스킹 값을 내려보낸다. 응답에 `unmask: {unmasked, operatorName, unmaskedAt, remainingSeconds}`를 실어 카운트다운 칩을 그리게 한다.

배송지의 `상세주소·수령인·연락처`도 같은 판정을 받는다(§25-1: 주소는 본인확인 정보와 같은 급). 마스킹 중에는 **시·군·구까지만** 잘라서 내려보낸다.

**C 분류 필드는 응답에 넣지 않는다** — `recentOrders` 빈 배열, `totalPurchaseAmount`/`returnCount`/`returnRate`/`likeCount` 미포함.

### 조치

```
POST   /v1/admin/users/{userId}/privacy-unmask   { reason }              → 열람 로그 + 이력 + 원본 반환
POST   /v1/admin/users/{userId}/privacy-lock                             → 즉시 재마스킹(지금 잠금)
POST   /v1/admin/users/{userId}/suspend          { reasonType, reasonDetail? }
POST   /v1/admin/users/{userId}/activate         { reasonType }
GET    /v1/admin/users/{userId}/memos
POST   /v1/admin/users/{userId}/memos            { content }             (≤300자)
PATCH  /v1/admin/users/{userId}/memos/{memoId}   { content }             (본인·24h)
DELETE /v1/admin/users/{userId}/memos/{memoId}                           (본인·24h)
GET    /v1/admin/users/{userId}/histories
```

- `PATCH /{userId}/status` (기존)는 **제거**한다 — "변경할 상태 셀렉트를 두지 않는다"는 §25-4 규칙이 API에도 그대로 적용된다. 목적지가 하나인 조치는 목적지별 엔드포인트로 나눈다.
- `PATCH /{userId}/memo` (기존 덮어쓰기)도 **제거**한다.
- 재마스킹 트리거 4종 중 ①②(다른 소비자 이동 · 새로고침)는 세션이 `user_id + operator_id`에 묶이고 페이지 재진입 시 새 요청이므로 **서버 상태만으로 자동 성립**한다. ③(무조작 10분)은 `expires_at`, ④(지금 잠금)는 `privacy-lock`이 담당한다.
- ③의 사유 프리필은 직전 로그의 `reason`을 상세 응답에 `lastUnmaskReason`으로 실어 주면 된다.
- **탈퇴에는 어떤 조치 엔드포인트도 만들지 않는다** — 셀프서비스이므로 운영자 액션이 없다(§25-5). 승인/반려 API를 만들면 기획 의도를 깬다.

### 권한

- 전 엔드포인트: `RoleType.ADMIN`.
- `privacy-unmask`는 기획상 **최고관리자 한정**이지만 등급 모델이 없다. 지금은 `AdminPermission.canUnmaskPrivacy(principal)` 한 지점으로 뽑아 두고 **`ADMIN`이면 통과 + TODO**. 등급이 생기면 그 메서드 하나만 고친다. 등급 모델은 `설정 > 운영자 계정` 화면 작업에서 정의한다.
- 기획 ⓓ(최고관리자 한정 여부)가 법률 자문 대기이므로 지금 등급을 발명하지 않는다.

## 6. 확인 필요

1. **`DORMANT`(휴면)** — 새 목록 탭은 3종(활성/정지/탈퇴)뿐이다. `UserStatus.DORMANT`는 유저 쪽에서 세팅되는 곳이 없다(휴면 전환 배치 없음). enum에서 뺄지, 남기고 `전체` 탭에만 보일지 결정 필요.
2. **배송지 별칭 충돌** — 어드민 시안은 `집/회사`를 그렸으나 앱 `C13`은 별칭을 없앴다. 어느 쪽이 최신인지 기획 확인.
3. **누적 주문 정의** — 기획 ⓐ 취소·환불 포함 여부 미정. 잠정: `CANCELLED` 제외.
4. **소명 문의 연결 방식** — 정지 후 들어온 1:1 문의를 자동으로 잡을지, 운영자가 수동 지정할지.
5. **Flyway V105·V106 중복** — 머지 사고로 보인다. V108 작성 전 정리 필요.
6. **`USERS.ADMIN_MEMO` DROP 시점** — 2단계 마이그레이션의 2단계를 언제 칠지.
