## 1. 범위와 판정 기준

- **대상**: `/v1/admin` 일반 게시물 모니터링 엔드포인트 **15개**(목록 · 요약 · 상세 · 사유 목록 · 근거 규정 목록 · 노출 중지 · 신고 종결 · 조치 취소 · 신고 지목 켜기/끄기 · 신고 대기열 · 신고 1건 반려 · 이의 신청 목록 · 승인 · 반려)와, 이 화면의 값을 만드는 **연계 경로** — 스튜디오 이의 신청 · 본인 삭제 · 원본 내려받기(`GET /v1/creator/posts/{id}/originals` 기록 적재) · 스튜디오 인사이트(숫자 일치) · 앱 신고 접수 · 기한 만료 배치 · 파기 배치 · V192 재매핑.
- **범위 밖**:
  - 공구 게시물 모니터링(별도 화면 · 아직 없다 — A-54). 여기서는 **공구 게시물이 섞이지 않는지 · 조치가 막히는지**만 본다(20-1절).
  - FE 표현 — 카드 배치 순서, 「+N장 더 보기」 접기, D-n 계산, 색, 빈 상태 문구, 버튼 활성. 서버는 재료만 내린다(설계 3-3 · 4-3). 재료가 맞는지만 본다.
  - 댓글(§54-7 ⓑ) · 인플루언서 계정 단위 제재(§53 · §51) · 소비자 신고 화면 C18 자체.
- **아래 케이스는 테스트 명세이고 통과 기록이 아니다.** 실행할 때 TC마다 `PASS / FAIL / BLOCKED / NOT RUN`과 실행 환경, 빌드, 일시, 증빙(응답 JSON · DB 행)을 남긴다.
- 「신고 접수」는 **저장하지 않는 파생 상태**다(설계 0-2). 같은 게시물이 목록 · 요약 · 상세에서 같은 `monitoringStatus`인지가 모든 케이스의 기본 확인이다(1-3 ①).
- 시각은 서버 `Asia/Seoul`. 서버는 절대 시각만 내리고 D-n은 FE가 센다. 기한 비교는 같은 트랜잭션의 `now`로 계산되므로 **초 단위 일치**를 기대한다(마이크로초는 비교하지 않는다).
- 배치는 `application-test` 프로필에서 꺼져 있다. `PostLifecycleService.expireOverdueSuspensions(now, limit)` · `PostPurgeService`를 **직접 호출**하고, 기한 · 유예 · 보관 만료는 SQL로 과거 시각을 넣어 재현한다.
- 알림 발송은 FCM 미설정이 기본이라 이력만 쌓이고 `delivered = false`다. 「알림이 갔다」는 **`post_notification_log` 행**으로 판정한다.

### 1-3. 공통 확인 방법

1. **상태 세 곳 일치** — 같은 게시물의 목록 행 `monitoringStatus · monitoringStatusLabel`, 요약의 해당 칸, 상세 `monitoringStatus`가 같아야 한다. 쓰기 직후 세 곳을 다시 읽는다.
2. **원천 행 확인** — 쓰기 케이스는 응답만 보지 않는다. `post` · `post_suspension` · `post_report` · `post_appeal` · `post_notification_log` · `post_original_download`를 직접 읽는다.
3. **알림 이력 증감** — 쓰기 전후 `post_notification_log` 행 수를 센다. 노출 중지 · 조치 취소 · 승인 · 반려 · 기한 만료는 **+1**, 신고 종결 · 신고 1건 반려 · 신고 지목은 **0**이다.
4. **신고자 실명 비노출** — 어드민 응답 본문 전체에서 실명 문자열(`한지준` 등)을 검색해 0건이어야 한다. 스튜디오 · 앱 응답에는 마스킹 이름 · `reporterUserId`도 없어야 한다.
5. **운영자 표기** — 어드민 응답은 운영자 이름(`김운영`)을 싣는다. 스튜디오 · 앱 응답에는 운영자 이름 · id가 없다.
6. **오류 응답** — HTTP 상태와 `code`를 함께 본다. 실패한 쓰기는 원천 행이 하나도 바뀌지 않아야 한다(롤백).
