## 0. 먼저 정한 8가지

### 0-1. 새 테이블은 1개, 나머지는 **이미 있는 구조 위에 응답을 다시 조립**하는 일이다

24 설계가 §24-5 · §24-6을 구현하면서 운영자 조치의 저장 구조를 끝내 놓았다. 코드로 확인한 현재 상태:

### 0-2. 「신고 접수」는 **저장하지 않는 파생 상태**다

§54-1의 상태 5종 중 「신고 접수」는 어드민에만 있고 스튜디오 상태 3종과 충돌하지 않는다고 했다. 저장된 `PostStatus`(5종 · `DRAFT / PUBLISHED / SUSPENDED / UNDER_REVIEW / DELETED`)를 늘리지 않고, 어드민 응답에서만 계산한다.

```
monitoringStatus =
  DELETED                       → CLOSED        (영구 삭제 · 중립)
  UNDER_REVIEW                  → UNDER_REVIEW  (이의 신청 심사 중 · 경고)
  SUSPENDED                     → SUSPENDED     (노출 중지 · 위험)
  PUBLISHED & 대기 신고 > 0      → REPORTED      (신고 접수 · 경고)
  PUBLISHED & 대기 신고 = 0      → PUBLISHED     (게시중 · 성공)
  DRAFT                         → 목록에서 제외 (노출된 적이 없다 · §54-0)
```

저장 상태로 두면 신고가 들어올 때마다 `post.status`를 건드려야 하고, 그 순간 스튜디오 목록(상태 3종 탭)이 어드민 사정으로 흔들린다. 신고 종결(§54-5)이 "게시중으로 되돌린다"는 것도 실제로는 **대기 신고가 0이 되는 것**이지 상태 전이가 아니다 — 그래서 "신고 이력은 남고 신고 수는 0으로 리셋"이 추가 저장 없이 그대로 성립한다.

### 0-3. 사유 축은 **소비자 신고 6종 + 운영자 전용 1종**으로 바꾼다 — 기존 8종을 재매핑한다

현재 `PostSuspensionReason` 8종(`MEDICAL_CLAIM · AD_DISCLOSURE · COPYRIGHT · MISLEADING_AD · SEXUAL_CONTENT · VIOLENCE_HATE · PERSONAL_INFO · OTHER`)과 `PostReportReason`은 1:1이다. 코드 주석이 "목록은 잠정 — 신고 사유 선택 화면 미확정"이라고 적어 두었고, rev.3이 그 화면(C18)을 6종으로 확정했다. 그대로 따른다(2-4).

- 「의료적 효능 표현」은 사유가 아니라 **허위 · 과장 정보의 근거 규정(3조 4항)**이다 → `MEDICAL_CLAIM` 폐기.
- 「대가관계 미표시」는 커머스 특화 사유를 두지 않는다(ⓖ) → 숨은 협찬 신고는 허위 · 과장 정보로 받는다 → `AD_DISCLOSURE` 폐기.
- 「저작권 침해」는 6종에 없다 → `OTHER` + 상세로 흡수.
- 「개인정보 노출」은 **운영자 전용**이다 — 소비자 신고 사유에서 빠지고 조치 사유에만 남는다. 1:1 대응이 **6 ⊂ 7 포함 관계**로 바뀐다. `PostReportReason.toSuspensionReason()`은 그대로 쓴다.

알림 이력(`post_notification_log.payload`)에 굳어 있는 옛 코드 문자열은 **고치지 않는다** — "그때 그 통지"다.

### 0-4. 근거 규정은 **코드로 받고 문구를 스냅샷**한다

§54-5가 근거 규정을 필수로 못박았다(이의 · 반려 심사의 판단 기준). 현재는 `policy_ref VARCHAR(200)` 자유 문구이고 선택이다. 조항 5개는 운영정책 문서가 없어 **가정값**(X-23 · A-59)이므로, 코드(`PostPolicyClause`)로 받아 `policy_clause_code`에 저장하고 그 시점의 조항 문구를 기존 `policy_ref`에 함께 굳힌다. 문서가 확정되어 조항 번호가 바뀌어도 과거 조치의 근거 문구는 그대로 남는다.

사유 ↔ 조항 조합은 **제한하지 않는다**. 시안의 사유 7종과 조항 5개는 다대다이고(허위 · 과장 → 3조 2항 또는 3조 4항), 운영자 판단 영역이다. FE 기본 선택용 추천 매핑만 `policy-clauses` 응답에 싣는다(4-4).

### 0-5. 반려 시점이 **어드민 기준 삭제 확정 시각**이다 — 상태를 더 만들지 않는다

C7 · C8이 「유예 7일 뒤 영구 삭제」라고 쓰지만, 시안 C8의 처리 레일은 **삭제 확정 = 반려 시각**(2026.08.09 11:30 둘 다)이고 목록도 곧바로 `영구 삭제 · 보관 ~2027.02` 행이다. 현재 구현(반려 즉시 `DELETED` · `grace_until` = 반려 + 유예일 · `purge_at` = 반려 + 보관 개월)이 어드민 화면과 정확히 맞는다.

유예가 뜻하는 것은 **작성자의 원본 내려받기 가능 기간**(`PostAppeal.graceUntil` · `GET /v1/creator/posts/{id}/originals` 가 이미 이 기간을 판정한다)이다. 바꾸는 것은 기본값만이다 — `post.download-grace-days` **30 → 7**(스튜디오 · 어드민 시안 모두 7일 · 가정값). 유예 중 스튜디오 목록에 남기는 문제는 스튜디오 소관으로 8절에 적는다.

### 0-6. 「작성자 조치 이력」은 **알림 이력에서 센다**

§54-3 레일의 「노출 중지 N회 · 삭제 N회」는 사실 기록이고 판단 지표로 가공하지 않는다. `post_suspension`에서 세면 보관 만료로 게시물이 **파기될 때 행이 같이 사라져** 횟수가 줄어든다. `post_notification_log`는 FK가 없고 영구 보존이며 `creator_id` · `event_type`을 가진다 — 여기서 센다.

```
노출 중지 N회 = count(SUSPENDED) − count(SUSPENSION_CANCELED)     -- 운영자가 거둔 조치는 작성자 이력이 아니다
삭제 N회     = count(APPEAL_REJECTED) + count(DELETED_BY_EXPIRE)  -- 제재로 끝난 삭제만 · 작성자 삭제(DELETED_BY_SELF)는 세지 않는다
```

「작성자 삭제」를 삭제 횟수에서 빼는 이유 — C10이 "다투지 않는 출구"라고 정의했고, 제재 결과가 아니라 본인 선택이다. 포함할지는 11-2 #4.

### 0-7. 운영자 식별 · 처리자 표기는 기존 관례 그대로

컨트롤러가 `@AuthenticationPrincipal UserPrincipal`의 `userId`를 넘기고(`requireOperatorId` — 이미 있다), 이름은 `AdminOperatorResolver.namesOf`로 **페이지 단위 일괄 조회**한다(36 설계 0-4 · 3-5). 저장은 id만, 이름은 어드민 직렬화 때 붙인다. 스튜디오 · 앱 응답에는 운영자 이름 · id가 나가지 않는다 — 현재 `PostDto`가 그렇고, 이 설계도 그 쪽을 건드리지 않는다.

### 0-8. 동시 조치는 **행 잠금**으로 막는다

운영자 둘이 같은 게시물에 「노출 중지」를 동시에 누르면 둘 다 `PUBLISHED`를 읽고 둘 다 `post_suspension`을 넣는다 — 열린 조치가 두 행이 되고 기한 만료 배치가 둘을 집는다. MySQL은 부분 유니크(`resolution IS NULL`)를 걸 수 없으므로, 조치 5종(4-5~4-9)은 `PostRepository.findByIdForUpdate`(`@Lock(PESSIMISTIC_WRITE)`)로 게시물 행을 잠근 뒤 상태를 판정한다. 조회 경로는 잠그지 않는다.

## 2. 모델 보강

### 2-1. `post_image` — 2개 (신고 지목)

| 컬럼 | 타입 | 비고 |
| --- | --- | --- |
| `report_flagged_at` | DATETIME(6) NULL | 운영자가 「신고 지목」을 켠 시각. NULL이면 지목 없음 |
| `report_flagged_by` | BIGINT NULL | 켠 운영자 id |

운영자 **수동 표시**다(§54-3 — C18에 사진 지정 칸이 없다 · ⓗ). 지목은 사진 단위 조치가 아니라 **읽기 보조 표식**이고, 노출 중지는 게시물 단위다(C11). ⓗ가 확정되어 소비자가 사진을 지정하게 되면 `post_report.target_sort_order INT NULL`을 더하고 접수 시 이 두 컬럼을 자동으로 채운다 — 테이블 구조는 그때도 바뀌지 않는다.

### 2-2. `post_suspension` — 1개 (근거 규정 코드)

| 컬럼 | 타입 | 비고 |
| --- | --- | --- |
| `policy_clause_code` | VARCHAR(40) NULL | `PostPolicyClause` 코드. 기존 `policy_ref`에는 선택 시점의 **조항 문구**를 함께 굳힌다(0-4). 기존 행은 NULL — 재매핑 2-6에서 `MEDICAL_CLAIM`이던 건만 `ARTICLE_3_4`로 채운다 |

### 2-3. `post_original_download` — 신규 (유예 중 원본 내려받기 기록)

```sql
CREATE TABLE `post_original_download` (
  `download_id`   BIGINT NOT NULL AUTO_INCREMENT,
  `post_id`       BIGINT NOT NULL COMMENT 'FK 없음 — 파기 뒤에도 경위는 남는다(알림 이력과 같은 규칙)',
  `creator_id`    BIGINT NOT NULL,
  `appeal_id`     BIGINT NULL COMMENT '어느 반려의 유예 중 내려받았는지',
  `image_count`   INT NOT NULL,
  `downloaded_at` DATETIME(6) NOT NULL,
  PRIMARY KEY (`download_id`),
  KEY `idx_post_original_download_post` (`post_id`, `downloaded_at`)
) COMMENT='반려 유예 중 작성자의 사진 원본 내려받기 기록 — C8 「작성자 내려받기 1회(08.10 21:14)」';
```

- 적재 지점은 스튜디오 `ShowroomPostService.getOriginalImages` — **삭제된 게시물에 대한 유예 중 호출**일 때만 1행(8-1). 살아 있는 게시물의 원본 조회는 상세 화면의 일부라 기록하지 않는다.
- URL 발급이 곧 내려받기인지는 알 수 없다(S3 URL을 받고 안 받을 수 있다). "원본을 **받아 갈 수 있게 해 준** 기록"이고, 「내 사진을 돌려 달라」 문의에 "N월 N일에 내려받기 경로를 열어 드렸다"가 답이다. 문구는 FE · 기획 확인(11-2 #5).
- 파기 배치(`PostPurgeService`)는 이 테이블을 건드리지 않는다.

## 3. 접근 · 범위 · 상태 판정

### 3-1. 대상 게시물

| 조건 | 규칙 |
| --- | --- |
| `post_type = GENERAL` | 공구 게시물은 어느 응답에도 섞이지 않는다 — 기존 `findAdminPosts` 조건 유지. 조치 API는 `post.isGeneral()` 아니면 409(기존) |
| `status <> DRAFT` | 작성중은 노출된 적이 없어 모니터링 대상이 아니다(§54-0). **상세도 404가 아니라 409 `POST_NOT_EDITABLE`**로 막지 않고 — 상세는 조회 전용이니 그냥 보여 준다. 목록 · 요약에서만 뺀다 |
| `status = DELETED` | **보인다**(§54-6 운영자 콘솔 전용 조회). `purge_at`이 지나 파기되면 404 |

신고 대기열(`GET /post-reports`)은 **공구 게시물 신고도 보인다**(기존 · `postType` 표기). 공구 게시물 모니터링 화면이 없는 동안 운영자가 어드민 공구관리의 숨김으로 가도록 안내하는 창구다 — 바꾸지 않는다.

### 3-2. 조치별 선행 상태

| 조치 | 허용 상태 | 그 외 |
| --- | --- | --- |
| 노출 중지 | `PUBLISHED`(대기 신고 유무 무관) | 409 `POST_NOT_EDITABLE` |
| 신고 종결 | `PUBLISHED` **AND** 대기 신고 ≥ 1 | 409 `POST_REPORT_NOTHING_TO_CLOSE` |
| 조치 취소 · 재게시 | `SUSPENDED`(열린 조치 1건 · 이의 신청 없음) | 409 `POST_SUSPENSION_NOT_CANCELABLE` — `UNDER_REVIEW`면 「이의 승인」이 그 자리다 |
| 이의 승인 · 반려 | 신청 `PENDING` (게시물은 `UNDER_REVIEW`) | 409 `POST_APPEAL_ALREADY_REVIEWED`(기존) |
| 신고 지목 토글 | `DRAFT` 외 전부 — `DELETED`도 허용(보관 중 자료에 표식을 남길 수 있다) | — |

### 3-3. 기한 3종 — 서버가 **절대 시각**을 내리고 D-n은 FE가 센다

| 상태 | 필드 | 출처 |
| --- | --- | --- |
| 노출 중지 | `appealDeadline` | 열린 `post_suspension.appeal_deadline` |
| 이의 신청 심사 중 | `reviewDueAt` | `post_appeal.submitted_at` + `appeal-review-business-days` **영업일**(5-4) |
| 영구 삭제 | `purgeAt` · `graceUntil` | `post.purge_at` · `post_appeal.grace_until`(반려 삭제만) |

D-n을 서버가 계산하면 응답을 캐시한 화면이 날을 넘길 때 틀린다. 36 설계 3-1의 `subLabel` 재료 방식과 같은 이유로 **재료만** 내린다.

### 4-1. 목록 — `GET /v1/admin/posts`

| 파라미터 | 값 |
| --- | --- |
| `tab` | `ALL`(기본) · `REPORTED` · `SUSPENDED` · `UNDER_REVIEW` · `CLOSED` — 0-2의 파생 상태로 거른다 |
| `sort` | `ACTION_FIRST`(기본) · `LATEST` · `MOST_REPORTED` |
| `keyword` | 쇼룸명 · 본문 `LIKE %kw%`(OR). 전문 검색은 두지 않는다 — 어드민 볼륨에서 LIKE로 충분하다 |
| `showroomId` | 인플루언서 상세 → 「일반 게시물 N건」 딥링크용. 기존 파라미터 유지 |
| `page` · `size` | 기존 `PagingRequest`(20 · 50) |

기존 `status` 파라미터는 **없앤다** — 저장 상태 필터는 파생 상태와 어긋난다(`PUBLISHED`에 신고 접수가 섞인다).

**정렬 `ACTION_FIRST`** — 조치 필요 우선:

```
rank = CASE
  WHEN status = UNDER_REVIEW                          THEN 0
  WHEN status = PUBLISHED AND pending_reports > 0     THEN 0
  WHEN status = SUSPENDED                             THEN 1
  WHEN status = PUBLISHED                             THEN 2
  WHEN status = DELETED                               THEN 3
END
ORDER BY rank ASC,
         (rank 0) 가장 오래 기다린 신호 ASC  -- 이의: submitted_at · 신고: 최초 대기 신고 reported_at
         (rank 1) appeal_deadline ASC        -- 기한 급한 것부터
         (rank 2) published_at DESC
         (rank 3) deleted_at DESC,
         post_id DESC
```

경고 2종(신고 접수 · 심사 중)이 같은 rank인 것은 §54-1 "둘 다 운영자가 지금 판단할 상태"를 그대로 옮긴 것이다. `MOST_REPORTED`는 `pending_reports DESC, published_at DESC` · `LATEST`는 `published_at DESC`.

**구현** — `PostRepositoryImpl.findAdminPosts`를 `findMonitoringPosts(AdminPostSearchCondition, Pageable)`로 교체. 대기 신고 수는 `post_report`를 `(post_id, status=PENDING)`로 집계한 **서브쿼리 조인**(`idx_post_report_post(post_id, status)`가 이미 있다)으로 붙여 WHERE(탭) · ORDER BY(정렬) · SELECT(응답)에 한 번에 쓴다. 열린 조치 기한 · 이의 신청은 페이지의 `postId` 집합으로 **별도 2쿼리**(`findOpenByPostIds` 기존 · `findByPost_IdIn` 신설) — 정렬 키로 쓰는 `appeal_deadline` · `submitted_at`은 서브쿼리로 함께 붙인다. 카운트 쿼리는 같은 WHERE를 쓴다.

### 4-2. 요약 — `GET /v1/admin/posts/summary`

```json
{
  "all": 6, "reported": 2, "suspended": 1, "underReview": 1, "closed": 1,
  "actionRequired": 3
}
```

- 탭 숫자 5개는 **한 쿼리**(`CASE … COUNT`)로 뽑는다 — 탭 하나씩 부르면 요청이 5배고 탭 전환마다 숫자가 흔들린다(스튜디오 `countByCreatorGroupedByStatus`와 같은 이유).
- `actionRequired = reported + underReview` — GNB 「9 게시물 · 소통 모니터링 › 일반 게시물」 배지. 신고 접수 탭이 비어도 심사 1건이 남으면 1이다(C9). GNB 상위 묶음(공구 게시물 · 소통 스레드 합산)은 FE가 각 요약을 더한다 — 이 API는 일반 게시물 몫만 안다.
- `showroomId` · `keyword`는 받지 않는다 — 요약은 전체 기준이다.

### 4-5. 노출 중지 — `POST /posts/{postId}/suspend`

```json
{ "reasonCode": "MISLEADING_INFO", "policyClause": "ARTICLE_3_2",
  "reasonDetail": "효과를 단정하고 환불을 보장하는 표현이 있어 노출을 중지합니다. 이의가 있으면 7일 안에 신청해 주세요." }
```

| 필드 | 규칙 |
| --- | --- |
| `reasonCode` | 필수 · 7종 |
| `policyClause` | **필수** — 없으면 400 `POST_POLICY_CLAUSE_REQUIRED`. 서버가 `policy_clause_code` + `policy_ref`(라벨 스냅샷) 저장 |
| `reasonDetail` | 「작성자에게 전달할 설명」 — 선택. `OTHER`면 필수(기존 `POST_SUSPENSION_DETAIL_REQUIRED`). 500자 |

흐름은 기존 `AdminPostService.suspend` 그대로 — 행 잠금(0-8) → `PUBLISHED` 검사 → `post_suspension` 저장 → `post.suspend()` → 대기 신고 전부 `ACCEPTED`(기존 `acceptPendingReports`) → 알림 이력 `SUSPENDED`(payload에 `policyClauseCode` 추가). 응답은 기존 `AdminPostActionResponse` + `monitoringStatus`.

조치 기록 5항목(사유 · 근거 규정 · 조치 시각 · 처리자 · 기한)이 `post_suspension` 1행과 알림 payload에 동시에 남는다 — 게시물이 파기돼도 payload는 남는다(§54-5 "조용히 사라지는 경우는 없다").

### 4-6. 신고 종결 — `POST /posts/{postId}/reports/close`

```json
{ "note": "효능 단정 표현이 아니라 개인 사용감으로 판단" }
```

- 행 잠금 → `PUBLISHED` · 대기 신고 ≥ 1 검사 → 대기 신고 **전부** `report.dismiss(operatorId, now)` → 응답 `{ postId, monitoringStatus: "PUBLISHED", closedReportCount }`.
- `note`는 선택 · 200자 · **저장하지 않는다**(저장할 곳이 `post_report`에 없고, 종결은 게시물에 아무 일도 일으키지 않는 결정이다). 기록이 필요해지면 `post_report.handle_note`를 더한다 — 11-2 #6.
- 작성자 · 신고자 **누구에게도 알리지 않는다**(기존 `dismiss` 규칙 — 신고자에게 결과를 돌려주면 게시물 상태를 캐는 창구가 된다).
- 종결 뒤 같은 사람이 같은 게시물을 다시 신고하면 `uk_post_report(post_id, user_id)`에 걸려 409다(기존). 「종결된 신고는 다시 못 넣는다」가 현재 규칙이고, ⓔ(중복 신고 셈법)와 함께 11-1에 둔다.

### 4-7. 조치 취소 · 재게시 — `POST /posts/{postId}/suspension/cancel`

```json
{ "note": "근거 규정 적용 오류 — 개인 사용감 표현으로 재검토" }
```

- 행 잠금 → `SUSPENDED` 검사(열린 조치 1건 · `post_appeal` 없음) → `suspension.resolve(CANCELED_BY_ADMIN, now)` → `post.republish()` → 알림 이력 `SUSPENSION_CANCELED`(payload: `suspensionId` · `canceledAt` · `canceledBy` · `note`).
- `note`는 선택이지만 **payload에는 굳힌다** — 작성자가 "왜 다시 올라왔나"를 알 수 있어야 한다.
- 좋아요 · 인사이트는 중지 중에도 깎지 않았으므로 복원 로직이 없다(승인 재게시와 같다).
- `ACCEPTED`로 닫혔던 신고는 **그대로 둔다** — 그 시점에 조치로 이어진 것은 사실이다. 취소 뒤 대기 신고는 0이라 파생 상태는 `PUBLISHED`다.
- 응답 `{ postId, monitoringStatus: "PUBLISHED" }`.

### 4-8. 이의 승인 — `POST /post-appeals/{appealId}/approve`

기존 그대로(`comment` 선택). 응답에 `monitoringStatus` 추가.

### 4-9. 이의 반려 — `POST /post-appeals/{appealId}/reject`

- `comment` **필수**(비면 400 `POST_APPEAL_REJECT_REASON_REQUIRED`) · 500자. 작성자에게 그대로 전달되고 알림 payload에 굳는다(C7 "알림 이력에 영구 보존").
- 나머지 기존 그대로 — `graceUntil = now + download-grace-days(7)` · `softDelete(APPEAL_REJECTED, now, now + retention-months)` · 알림 `APPEAL_REJECTED`.

- `PUT` → `report_flagged_at = now` · `report_flagged_by = operatorId`(이미 켜져 있으면 덧쓰지 않고 200). `DELETE` → 둘 다 NULL. 204.

## 5. 조치 규칙 상세

### 5-1. 상태 기계 (변경 지점만 굵게)

```
PUBLISHED ──노출 중지──> SUSPENDED ──이의 신청(스튜디오)──> UNDER_REVIEW ──승인──> PUBLISHED
    ^                      │  │                                │
    │                      │  └──기한 경과(배치)──> DELETED      └──반려──> DELETED (grace_until · purge_at)
    │                      └──본인 삭제(스튜디오)──> DELETED
    └──────**조치 취소 · 재게시**───────┘            (SUSPENDED에서만 · 이의 없을 때)

PUBLISHED(대기 신고 ≥1) ──**신고 종결**──> PUBLISHED(대기 신고 0)   -- 상태 전이 아님 · 신고 행만 닫힌다
```

### 5-2. 신고자 노출 — 결정 변경

현재 코드는 신고자를 어드민 응답에 **싣지 않기로** 했다(`AdminPostReportDto` 주석 — "어드민 화면의 값은 분쟁 과정에서 인플루언서 쪽으로 옮겨 갈 수 있다"). rev.3은 **마스킹한 이름 + 회원 상세 연결**을 요구한다(§54-3 — ⓕ 허위 신고 누적 제재에 신고자 식별이 필요하다).

| | 응답 |
| --- | --- |
| 어드민(이 설계) | `reporterMaskedName`(`한*준`) · `reporterUserId` |
| 스튜디오 · 앱 | **여전히 없음** — 조치 통지 payload에도 신고자 정보는 넣지 않는다 |

마스킹은 **가운데 글자**를 가린다(시안 `한*준`). 기존 `MaskingUtils.maskName`은 C15-2 회원정보용으로 **끝 글자**를 가리므로(`김수민 → 김수*`) 그대로 쓸 수 없다 — `MaskingUtils.maskNameMiddle`을 신설한다: 2자 `한*` · 3자 `한*준` · 4자 이상은 첫 · 끝만 남기고 `*`(`박다은이 → 박**이`) · 1자 `*` · 없으면 `null`. 실명(`Users.name` — 본인인증 결과)이 없는 소비자는 닉네임을 `NicknameMasker.mask`로 가린다. 운영자가 마스킹을 벗기는 경로는 회원 상세(별도 권한)지 이 화면이 아니다.

### 5-3. 알림 — 작성자에게 가는 것과 가지 않는 것

| 조치 | 작성자 알림 | 신고자 알림 |
| --- | --- | --- |
| 노출 중지 | `SUSPENDED` — 사유 · 근거 · 시각 · 처리자 id · 기한 · 설명 | ✕ |
| 신고 종결 | ✕ (아무 일도 일어나지 않았다) | ✕ |
| 조치 취소 · 재게시 | **`SUSPENSION_CANCELED`** | ✕ |
| 이의 승인 | `APPEAL_APPROVED`(기존) | ✕ |
| 이의 반려 | `APPEAL_REJECTED` + 반려 사유 + 유예(기존) | ✕ |
| 기한 미신청 삭제(배치) | `DELETED_BY_EXPIRE`(기존) | ✕ |

발송은 기존 `PostNotificationDispatcher`(커밋 후 · FCM 미설정이면 이력만 · `delivered = false`)를 그대로 탄다. 이력이 먼저고 발송이 뒤다 — 바뀌지 않는다.

### 5-4. 심사 기한 — 3영업일

`reviewDueAt = submitted_at + appeal-review-business-days` — 토 · 일을 건너뛴 **영업일** 계산(`BusinessDays.plus(LocalDateTime, int)` · `global.utils`). 공휴일 캘린더는 **두지 않는다**(프로젝트에 휴일 데이터가 없다 · 11-1 ⓒ와 묶음). 설정값은 기존 `PostProperties.appealReviewBusinessDays`(3)를 쓴다 — 지금은 "표시용 · 로직에 쓰지 않는다"고 주석됐는데, 이 설계가 **표시 재료 계산**에 쓴다. 기한 초과 시 자동 처리는 없다(ⓒ 미결) — 넘긴 건은 `reviewDueAt < now`로 FE가 강조만 한다.

### 5-5. 작성자 삭제(C10)의 재료

| 응답 필드 | 출처 |
| --- | --- |
| `deletion.type = SELF` · `deletedBySelf = true` | `post.delete_reason = SELF` |
| 「노출 중지 중 · 이의 미신청」 | 직전 `post_suspension.resolution = DELETED_BY_SELF`(스튜디오 `deletePost`가 열린 조치를 이 값으로 닫는다 — 기존) · `post_appeal` 없음 |
| `daysAfterSuspension` | `deleted_at − suspended_at`(일) |
| `appealDeadlineAtDeletion` | 그 조치의 `appeal_deadline` — FE가 삭제 시각 기준 D-n |
| 유예 · 내려받기 | **없음**(운영자 조치가 아니다) — `graceFrom/Until = null` · `originalDownloads = []` |

게시중 상태에서 본인이 지운 게시물도 `SELF`로 들어온다(열린 조치가 없다). 이 경우 `originSuspensionId = null`이고 FE는 「작성자 삭제」만 적는다 — 모니터링 화면에는 「종결」 탭에서 보인다. 이 행을 목록에서 뺄지는 11-2 #7.

## 6. 집계 — 지표 · 처리 이력 · 작성자 이력

### 6-1. 지표 — `PostMetricsService`(도메인) 신설

현재 `api.creator.post.service.PostInsightService.getInsights`가 노출 · 좋아요 · 쇼룸 방문 · 팔로우를 원천 로그에서 세고, 열린 조치가 있으면 상한을 `suspended_at`으로 자른다. 어드민도 **같은 숫자**를 보여야 하므로(§54-3 "스튜디오 인사이트와 같은 집계") 집계 코어를 `domain.post.service.PostMetricsService.measure(postId, LocalDateTime to)`로 내리고 둘이 함께 쓴다.

| 상태 | `to`(상한) | 시안 문구 |
| --- | --- | --- |
| 게시중 | `now` | 「조치 판단 참고 · 스튜디오 인사이트와 같은 집계」 |
| 노출 중지 · 심사 중 | 열린 조치 `suspended_at` | 「중지 시 유지되며 재게시 승인 시 그대로 복원」 |
| 영구 삭제 | `deleted_at` | 「삭제 시점 기준 동결」 |

- 기간은 **전체**(`from = null`) — 어드민은 기간 탭이 없다. 리포지토리의 기간 메서드(`countByPostIdInPeriod` 등)에 `from` nullable을 허용하거나 `LocalDateTime.MIN` 대신 `post.created_at`을 하한으로 넘긴다.
- `likeRate = likes ÷ impressions × 100`(소수 1자리 · 노출 0이면 `null`) — `PostInsightService.rateOf`와 같은 함수.
- 연령 · 성별 분포는 내리지 않는다 — 조치 판단 재료가 아니고 표본 최소치 규칙이 따로 있다.
- 카운터(`impression_count` · `like_count`)는 **쓰지 않는다** — 삭제 시점 동결이 카운터로는 안 된다(소프트 삭제 후에도 피드에서 빠지므로 늘지는 않지만, "같은 집계"가 아니다).

### 6-2. 처리 이력 — `timeline[]`

서버가 7개 원천을 시간순(DESC)으로 합쳐 내린다. 저장 테이블을 새로 만들지 않는다 — 전부 이미 기록되어 있다.

| `type` | 원천 | `actorType` · 표기 | 비고 |
| --- | --- | --- | --- |
| `PUBLISHED` | `post.published_at` | `CREATOR` · 인플루언서(쇼룸명) | 「게시물 등록」 |
| `EDITED` | `post.edited_at` | `CREATOR` | 「게시물 수정」 — **마지막 1건만**(수정 이력 테이블이 없다 · 11-2 #8) |
| `REPORTED` | `post_report` 각 행 | `USER` · 소비자(마스킹) | 「신고 접수 (N건째)」 — `ordinal`은 접수 시각 순번 · `reasonLabel` |
| `REPORTS_CLOSED` | `post_report` 중 `DISMISSED` 묶음(같은 `handled_at`) | `ADMIN` · 운영자(이름) | 「신고 종결 (N건)」 |
| `SUSPENDED` | `post_suspension` | `ADMIN` | 「노출 중지 · {사유}」 |
| `SUSPENSION_CANCELED` / `REPUBLISHED` / `DELETED_BY_*` | `post_suspension.resolution` + `resolved_at` | `ADMIN` / `SYSTEM` / `CREATOR` | 종결값별 라벨 |
| `NOTIFIED` | `post_notification_log` 각 행 | `SYSTEM` | 「작성자 알림 발송 · {이벤트}」 · `delivered` |
| `APPEAL_SUBMITTED` / `APPEAL_APPROVED` / `APPEAL_REJECTED` | `post_appeal` | `CREATOR` / `ADMIN` | — |
| `ORIGINAL_DOWNLOADED` | `post_original_download` | `CREATOR` | 「원본 내려받기 (N장)」 |
| `DELETED` | `post.deleted_at` + `delete_reason` | `CREATOR` / `ADMIN` / `SYSTEM` | 「영구 삭제 · 비공개 보관 전환」 |

```json
{ "type": "REPORTED", "at": "2026-08-12T10:26:00", "actorType": "USER", "actorName": "임*현",
  "label": "신고 접수 (3건째)", "detail": "기타", "refId": 19 }
```

`label`은 서버가 조립한 한국어 문구다 — 이 화면 전용이고 FE가 `type`으로 색(`h-warning` 등)을 고른다. 주체 표기 규칙은 §54-3 그대로: 「운영자(김운영)」 · 「인플루언서(김소연)」 · 「소비자(한*준)」 · 「시스템」.

### 6-3. 작성자 조치 이력

```sql
SELECT event_type, COUNT(*) FROM post_notification_log
WHERE creator_id = :creatorId
  AND event_type IN ('SUSPENDED','SUSPENSION_CANCELED','APPEAL_REJECTED','DELETED_BY_EXPIRE')
GROUP BY event_type
```

0-6의 식으로 `suspensionCount` · `sanctionDeleteCount`를 만든다. 인덱스는 기존 `idx_post_notification_creator(creator_id, sent_at)`로 충분하다(creator 선두). 어드민 인플루언서 상세의 「게시물 검토 N회」와 **같은 쿼리**를 쓰도록 `PostNotificationLogRepository.countSanctionEventsByCreator`를 도메인에 둔다 — 두 화면이 다른 숫자를 내면 안 된다.
