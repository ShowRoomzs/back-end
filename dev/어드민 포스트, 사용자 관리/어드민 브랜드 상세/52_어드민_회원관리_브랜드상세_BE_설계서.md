## 0. 먼저 정한 14가지

### 0-1. 「브랜드」= `Market` 이고 식별자는 `market_id` 다 — 회원번호 `BRD-{market_id}`

코드의 브랜드는 두 행이다 — 계정 `Seller`(로그인 · 담당자 · 사업자 · 정산 계좌)와 `Market`(브랜드명 · 상태 · 배송 정책). 정산(`settlement.market_id`) · 연결(`connection.market_id`) · 계약 · 공구 · 변경 요청이 전부 `market_id` 로 브랜드를 가리키므로 회원 관리도 **`market_id`** 를 쓴다. 회원번호는 소비자와 같은 방식(`AdminMemberNumber` — 컬럼을 만들지 않고 id 를 포맷)으로 **`BRD-{market_id}`** 다 — `AdminBrandNumber`. 가입 순서가 곧 번호라는 성질도 같다.

- 회원 관리 대상은 **입점이 끝난 브랜드**(`Seller.status = APPROVED` ∧ `Market` 존재)뿐이다. `PENDING · REJECTED` 는 입점 관리(`/v1/admin/sellers/applications`)의 일이고 이 화면에 나오지 않는다.
- 운영자 계정(`Seller` · `RoleType.ADMIN`)도 `Seller` 행이지만 `Market` 이 없어 자연히 빠진다.

### 0-2. 회원 상태 축 = `MarketStatus` — 바꾸지 않고 `DORMANT` 만 쓰지 않는다

§51-0 「회원 상세 배지 = 목록 상태 열」. `MarketStatus { ACTIVE · SUSPENDED · DORMANT · WITHDRAWN }` 가 이미 있고 소통 스레드(`AdminChannelMemberStatus`) · 정산 차감(`MARKET_WITHDRAWN`)이 이 값을 읽는다. 새 상태 열을 만들지 않는다. **`DORMANT` 는 어느 코드도 세팅하지 않는다**(셀러 휴면 전환 배치 없음) — 응답 enum `BrandMemberStatus { ACTIVE · SUSPENDED · WITHDRAWN }` 로 접고, DB 에 `DORMANT` 가 있으면 `ACTIVE` 로 내리며 로그를 남긴다. 값 자체는 지우지 않는다(스레드 매핑이 참조한다).

탈퇴 **신청**은 상태가 아니다(§51-0 축 분리) — `brand_withdrawal_request.status = PENDING` 행의 유무이며, 응답에 `withdrawalReview` 카드로 따로 내린다. 승인된 순간에만 `MarketStatus.WITHDRAWN` 이 된다.

### 0-3. 정지는 **행**이다 — `brand_sanction`(정지 1건 = 1행 · 해제까지)

시안 A3 「같은 카드에 사유 · 처리자 · 일시 · 상세 사유 전문 · 지급 여부」 · 처리 이력 「지난달에 이미 정지 한 번 했나」. `Market` 에 사유 컬럼을 더하면 두 번째 정지가 첫 번째를 덮는다. 정지는 `brand_sanction` 행이고, **열린 정지 = `released_at IS NULL`** 행이다(마켓당 최대 1건 — 생성 컬럼 UNIQUE · 1-3). `market.status = SUSPENDED` 는 이 행에서 **파생해 저장**한다(목록 · 스레드 · 정산이 열 하나로 읽어야 한다).

- 사유 6종 `BrandSuspensionReason`(§51-2) · 「기타」만 상세 사유 필수.
- **지급 정지 여부는 사유가 정한다**(`holdsPayout`) — 운영자 스위치가 아니다(§51-1). 정지 행에 `payout_held` 를 **스냅샷**한다 — 뒤에 사유별 규칙이 바뀌어도 이미 내린 정지의 효과는 그대로다.
- 정지 기간은 없다(ⓧ 미정) — 수동 해제뿐. 기한제가 확정되면 `expires_at` 컬럼 하나와 배치 하나다.

### 0-4. 지급 정지 = 정산 수취자 행의 `BLOCKED` 다 — 새 상태 · 새 버튼을 만들지 않는다

§51-3 「정산은 생성 · 확인 · 확정까지 그대로 · 브랜드 몫 지급 요청만 보내지 않는다 · 해제 다음 영업일 지급 · 07b 는 표시만」. 44 설계서의 수취자 행(`settlement_payout`)에 이미 **`PayoutStatus.BLOCKED` + `fail_code`(= `PayoutBlockReason`)** 가 있고, 지급 배치 앞단(`SettlementPayoutTransitions.claim`)이 재판정한다. 그 틀에 사유 하나를 더한다 — **`PayoutBlockReason.BRAND_SUSPENDED`**.

| 시점 | 처리 |
| --- | --- |
| 정지(지급 정지 사유) | 그 마켓의 `BRAND` 행 중 `SCHEDULED` → `BLOCKED(BRAND_SUSPENDED)` (`blockScheduled` · 이력 `PAYOUT_BLOCKED`). `REQUESTED`(이미 PG 에 지시) 는 건드리지 않는다 — 돌이킬 수 없다 |
| 정지 중 확정 | 확정 시 `BRAND` 행을 `SCHEDULED` 가 아니라 `BLOCKED(BRAND_SUSPENDED)` 로 만든다(`SettlementConfirmService` 가 `BrandPayoutHoldReader` 를 본다) |
| 정지 중 지급 배치 | `claim` 앞단이 `BrandPayoutHoldReader.isHeld(marketId)` 면 `BLOCKED` 로 돌린다 — 틈새(정지 직후 확정 · 배치 경합)를 이 재판정이 닫는다 |
| 해제 | `BLOCKED(BRAND_SUSPENDED)` 행을 `SCHEDULED` · `due_date = 해제일의 다음 영업일` 로 (`BusinessCalendar.addBusinessDays(today, 1)`) — 「해제 다음 영업일에 지급」 |

「예약분은 요청 취소」(§51-3)는 토스 지급대행이 **예정일 당일 지시**라 취소할 예약이 없다 — `SCHEDULED → BLOCKED` 가 그것이다. 인플루언서 · 플랫폼 몫은 손대지 않는다. 포트 방향은 44 공통 결정 #9 와 같다 — 정산이 회원을 **읽는다**(`domain.settlement.port.BrandPayoutHoldReader` · 구현은 `domain.member.brand`), 회원은 정산 **서비스를 호출**한다(`SettlementSanctionHook.holdBrandPayouts / releaseBrandPayouts`).

### 0-5. 탈퇴는 **신청 → 승인**이고 승인이 파기를 집행한다 — `brand_withdrawal_request`

§51-5 「셀프 즉시 탈퇴 없음 · 조건은 신청 화면에서 잠근다 · 어드민은 사유와 경과를 보고 승인 · 반려」. 신청 1건 = 1행(`PENDING · APPROVED · REJECTED · CANCELED`) · 마켓당 열린 신청 1건(생성 컬럼 UNIQUE). 반려 뒤 재신청은 **새 행**이다(이력 보존 · 변경 요청과 같은 관례).

- 조건 4종(공구 · 체결 전 계약 · 미종결 주문 · 진행 중 정산)의 판정식은 **`BrandWithdrawalEligibility` 하나**다(4-1). 파트너 신청 화면의 체크리스트와 어드민 **승인 시 재검증**이 같은 식을 쓴다 — 신청 이후 상황이 바뀐 건(새 주문 · 조정 요청)을 승인 직전에 잡는다. 어드민 응답에는 체크리스트를 내리지 않는다(§52 「늘 ✓만 뜨는 블록은 정보가 아니다」) — 승인 모달의 「미배송 0건 · 진행중 공구 0건 · 미정산액 0원」은 **승인 API 의 재검증 결과**로 답하고, 미충족이면 409 에 어느 항목이 걸렸는지를 싣는다.
- 승인 효과(4-3)는 한 트랜잭션 — 회원 상태 `WITHDRAWN` · 열린 정지 종결 · **로그인 차단**(이메일 치환 · 비밀번호 폐기 · 리프레시 토큰 삭제) · 사업자 · 정산 · 담당자 정보 **파기**(반려 파기 `purgePersonalDataOnRejection` 과 같은 방식 — 사업자등록번호는 **해시**로 남겨 「같은 사업자등록번호로 재가입 가능 · 이전 데이터 미승계」가 성립한다) · 상품 전건 `HIDDEN` · 남은 PAIR 연결 전건 종료.
- **보존**: 브랜드명 · 회원번호 · 가입일 · 입점 승인일 · 배송 · 반품 정책 전부(반품 수취 주소 포함 — 남은 반품의 비용 기준) · CS 번호 · 주문 · 정산 · 계약 · 이력 · 메모. 쟁점 G(법률) 종속이라 파기 범위는 **`BrandWithdrawalPurger` 한 클래스**에 모은다 — 자문 결과가 바뀌면 그 클래스의 목록 한 줄이다.
- 기존 **`DELETE /v1/seller/auth/withdraw`**(`SellerService.withdraw` — `Seller` · `Market` **하드 삭제**)는 §51-5 와 정면으로 어긋난다. **`RoleType.SELLER` 에 대해 409 `BRAND_WITHDRAWAL_REQUIRES_REQUEST`** 로 막는다(활성 엔드포인트의 동작 변경 — 11절 #3). `CREATOR` 는 인플루언서 설계서가 같은 결정을 내릴 때까지 그대로 둔다.

### 0-6. 처리 이력은 **이 모듈의 사건만 저장**하고 남의 사건은 읽을 때 합친다

시안 처리 이력 = 가입 신청 · 입점 승인 · 정지 · 해제 · 탈퇴 신청 접수 · 승인 · 반려 · 메모 기입 · 정산 계좌 변경 요청 접수 ↗. 가입 · 입점 승인은 `seller.created_at` · `seller_application_history` 에, 변경 요청 접수 · 승인 · 반려는 `brand_change_request` 에 이미 **사실이 있다**. 그것을 다시 쓰면 백필과 이중 기록이 생긴다. 그래서 `brand_admin_history` 에는 **이 모듈이 일으킨 사건**(정지 · 해제 · 탈퇴 신청 · 취소 · 승인 · 반려 · 메모 생성 · 수정 · 삭제)만 쓰고, 조회 시 파생 행 3종(가입 · 입점 승인 · 변경 요청 3상태)을 **읽어서 합쳐** 최신순으로 자른다(5-2). 소비자 개발계획의 「기록은 소급이 안 되므로 지금 만든다」는 이 모듈의 사건에만 해당한다.

### 0-7. 관리자 메모는 **누적**이고 `market.admin_memo` 는 건드리지 않는다

§52-2 「누적 기입 · 300자 · 작성자 본인 24시간 내 수정 · 삭제 · 브랜드 비노출」 — 소비자 개발계획과 같은 규격이라 **같은 구조**(`brand_admin_memo` · soft delete · 서버가 `editable` 판정)로 간다. 기존 `MARKET.admin_memo`(V59 · 덮어쓰기 500자)는 **기획 제외** `MarketAdminController` 가 쓰는 컬럼이다 — CLAUDE.md 규칙 2 · 5 에 따라 **백필도 DROP 도 하지 않는다**. 새 화면은 그 컬럼을 읽지 않는다. 덮어쓰기 500자로 되돌릴지는 §55 B-15 미결이며, 되돌리면 이 테이블 대신 그 컬럼을 쓰면 된다.

### 0-8. 마스킹은 서버가 끝내고 이 화면에 해제가 없다

계좌번호는 **가운데 마스킹**(시안 `110-****-3841`) — `AdminBrandMasker.maskAccountNumber`(앞 3 · 뒤 4 자리만 남긴다 · 구분자 보존). 파트너용 `SettlementAccountMasker`(뒤 6자리)는 그 클래스 주석대로 어드민에 들여오지 않는다 — 규칙이 다르고, 어드민 정산 관리는 전체 노출이다(§52-1 ⚠️ A-39 는 미결 그대로). 목록 · 상세 어디에도 해제 버튼이 없으므로(§52-1) 원본은 응답에 싣지 않는다. 담당자 연락처 · 이메일 · 사업자등록번호는 시안대로 **그대로** 내린다 — 법인 식별 정보이지 본인확인 정보가 아니다(인플루언서 상세의 M4 마스킹 해제와 다른 점).

### 0-9. 「최근 문의」 카드는 **내리지 않는다** · 「열린 1:1 문의」 칩은 운영팀 스레드로 읽는다

§52-2 ⚠️ 「파트너센터 1:1 문의(PIQ-)는 정의된 적이 없다」(§55 A-5). 코드에도 없다 — `OneToOneInquiry` 는 소비자(`Users`)의 것이다. 소비자 개발계획 Q2 「없는 데이터를 UI에 올리지 않는다」를 그대로 따라 **`recentInquiries` 필드를 만들지 않는다**. 대신 그 카드의 실제 역할(「운영자 채널 열기」)만 `operatorThread { threadId · unreadByOperator · lastMessageAt }` 로 내린다 — 브랜드의 소명 · 문의 경로가 운영팀 스레드이기 때문이다(§51-4). 진행 중 칩의 「열린 1:1 문의」도 같은 이유로 **운영팀 채널의 운영팀 미확인 메시지 수**(`countUnreadForOperatorTeam`)로 센다 — 키는 `OPERATOR_THREAD_UNREAD` · 라벨 「운영팀 스레드 미확인」. 파트너센터 1:1 문의가 기획되면 칩 하나를 더하면 된다(13절 #4).

### 0-10. 진행 중 칩 8종은 전부 **기존 리더**로 센다 — 새 집계 테이블 없음

「이 브랜드 밀린 거 있어?」는 다른 화면들이 이미 세고 있는 숫자다. 파트너 주문 관리 요약 바(`SellerOrderQueryService.getSummary`)의 식을 그대로 가져오고, 없는 것(발송 기한 경과 · 상품 문의 미답변 · 세금계산서 발행 대기)만 카운트 쿼리를 더한다(2-5). 칩은 **1건 이상만** 응답에 싣고 각 칩에 이동 경로를 붙인다.

### 0-11. 차단 범위는 **서버 가드**로 집행한다 — 다섯 지점

§51-1 「숨기지 않고 비활성 + 안내」는 화면의 일이고, 서버는 그 행위를 **409 `BRAND_SUSPENDED`** 로 거부한다(7절). 차단 지점 다섯 — 상품 등록 · 새 계약 등록(작성 · 검토 요청) · 인플루언서 연결 요청 · **공구 오픈**(`READY → IN_PROGRESS` 게이트) · 그리고 「공구 개설 신청」은 존재하지 않으므로(§51-1 ⚠️) 지점이 없다. **오픈 승인 자체는 막지 않는다** — 승인 · 준비완료까지는 진행되고 시작 시각이 와도 열리지 않으며, 해제하면 다음 스케줄러 틱이 연다(「해제 시 이어 간다」). 그 밖(주문 처리 · 상품 문의 답변 · 기존 상품 수정 · 품절 · 기본정보 · 계좌 변경 요청 · 스레드 · 정산 조회 · 조정 요청)은 가드가 없다. 로그인도 그대로다.

기존 **기획 제외** `AdminMarketService.updateMarketStatus`(정지 시 상품 전건 `HIDDEN`)와 원칙이 다르다(11절 #1) — 이 설계는 **상품을 숨기지 않는다**(진행 중 공구의 판매 유지).

### 0-12. 시스템 카드 2종은 회원 유형에 중립이다 — `ACCOUNT_SUSPENDED` · `ACCOUNT_SUSPENSION_RELEASED`

§51-4 「정지 순간 운영팀 스레드에 「계정 정지 · 사유 · 일시」 카드 자동 등록 · 해제 시 「정지 해제」 카드」. 계약 취소 카드(`MessageContractChannelGateway.postAdminCanceledCard`)와 같은 틀이다 — `MessageCardType` 2종 · `MessageCardPayload.sanction(...)` · 게이트웨이 `MessageSanctionChannelGateway`(8절). 인플루언서 정지가 그대로 쓰도록 카드 이름에 브랜드를 박지 않는다. 운영자 이름은 payload 에 넣지 않는다(36 설계 0-4 — id 만).

### 0-13. 운영자 조치 4종은 전부 **조건부 UPDATE + 이력 + 카드/알림 훅**

정지 · 해제 · 승인 · 반려. 거래 · 정산과 같은 관례 — `WHERE status = …` 0행이면 409 `BRAND_STATE_CHANGED`. 운영자 id 는 `UserPrincipal` 에서, 이름 스냅샷은 `AdminOperatorResolver.operatorName`. 알림 발송 인프라가 없으므로(소비자 개발계획 C) `BrandMemberNotifier` 는 로그 스텁이고 호출 지점만 둔다.

### 0-14. 발송 기한 변경 보조줄은 **작은 이력 테이블** 하나로 — 다른 배송 정책 값은 이력을 두지 않는다

§52-1 「발송 기한 보조줄 = 주문별 기한이 다른 이유」. 발송 기한 N 은 주문 생성 때 하위주문에 스냅샷되므로(`ShipDuePolicy`) 변경 이력이 없으면 「왜 이 주문은 2영업일인가」를 설명할 수 없다. `market_ship_lead_history`(마켓 · 이전 · 이후 · 시각) 를 두고 `SellerBasicInfoService.updateDeliveryPolicy` 가 값이 바뀔 때만 1행 쓴다. 배송비 · 반품비는 기획이 이력을 요구하지 않는다 — 두지 않는다.

## 2. 상세 조회 — `GET /v1/admin/brands/{marketId}` 조립

`AdminBrandQueryService.getDetail(marketId)` 가 한 응답에 좌측 7카드 · 레일 4카드를 담는다. 카드 하나가 비어도 응답은 성립한다 — 집계 리더가 하나 실패하면 그 카드만 `null` 이 아니라 **예외**다(숫자가 틀리게 나가는 것이 비는 것보다 나쁘다).

### 2-1. 헤더 · 기본 정보 · 사업자 정보

| `memberStatus` | `BrandMemberStatus.of(market.status)` | 0-2 |

## 3. 정지 · 정지 해제 — `AdminBrandCommandService`

### 3-1. 정지 `POST /v1/admin/brands/{marketId}/suspend` — M1

입력 `{ reason: BrandSuspensionReason, reasonDetail?: ≤500 }`.

1. 마켓 · 셀러 조회 — `APPROVED` 셀러의 마켓이 아니면 404 `MARKET_NOT_FOUND`.
2. `memberStatus == WITHDRAWN` → 409 `BRAND_WITHDRAWN`(해지된 계정은 제재 대상이 아니다). 열린 정지가 있으면 409 `BRAND_ALREADY_SUSPENDED`.
3. `reason == OTHER ∧ detail 공백` → 400 `BRAND_SUSPEND_DETAIL_REQUIRED`.
4. `brand_sanction` INSERT(`payout_held = reason.holdsPayout()` · 처리자 id · 이름 스냅샷) — UNIQUE 충돌이면 409 `BRAND_ALREADY_SUSPENDED`(경합).
5. `MarketRepository.transitionStatus(marketId, {ACTIVE}, SUSPENDED)` — 0행이면 409 `BRAND_STATE_CHANGED`.
6. `payout_held` 면 `SettlementSanctionHook.holdBrandPayouts(marketId, now)`(6-1).
7. 이력 `SUSPENDED`(`detail = 사유 라벨` · `ref = sanction`).
8. `afterCommit` — `MessageSanctionChannelGateway.postSuspendedCard(market, sanction)`(8-1 · 카드 id 를 행에 저장) · `BrandMemberNotifier.suspended(marketId, reason)`(스텁).

탈퇴 심사 중이어도 막지 않는다(ⓨ · §51-0). 응답은 갱신된 **현재 상태 카드**(`rail.currentStatus`)다 — 상세 전체를 다시 부르지 않게.

### 3-2. 정지 해제 `POST /v1/admin/brands/{marketId}/release`

입력 `{ reason?: SanctionReleaseReason(기본 RESOLVED), note?: ≤500 }`.

1. 열린 정지 행이 없으면 409 `BRAND_NOT_SUSPENDED`.
2. 행 UPDATE `released_* ` — `WHERE released_at IS NULL` 0행이면 409 `BRAND_STATE_CHANGED`.
3. `transitionStatus(marketId, {SUSPENDED}, ACTIVE)`.
4. `payout_held` 였으면 `SettlementSanctionHook.releaseBrandPayouts(marketId, today)`(6-2).
5. 이력 `SUSPENSION_RELEASED`(detail = 해제 사유 라벨 + note).
6. `afterCommit` — 「정지 해제」 카드 · 알림 스텁.

해제는 **이 화면에서만** 한다(§51-4) — 파트너 · 스레드 어디에도 해제 경로를 만들지 않는다. 해제 뒤 정지 브랜드의 `READY` 공구는 다음 `GroupBuyLifecycleScheduler` 틱에 열린다(7절) — 별도 호출 없음.

## 4. 탈퇴 심사 — 신청 조건 · 승인 · 반려

### 4-1. 조건 판정식 — `BrandWithdrawalEligibility.evaluate(marketId) → Result { unmet: Map<BrandWithdrawalCondition, long> }`

파트너 체크리스트(건수 + 링크)와 어드민 승인 재검증이 **같은 메서드**를 쓴다. 전부 0 이면 적격.

| 조건 | 판정 | 원천 |
| --- | --- | --- |
| `ACTIVE_GROUP_BUYS` | `GroupBuyStatus.ACTIVE`(준비중 · 준비완료 · 진행중 · 중단 예정) 건수 — **종료 후 주문 종결 대기**는 ③ 에서 걸린다 | `GroupBuyRepository.countByStatus(marketId)` |
| `CONTRACTS_BEFORE_CONCLUSION` | `ContractStatus.BEFORE_CONCLUSION − {DRAFT}`(검토 대기 · 반려 · 서명 진행중 · 체결 처리 대기) ∧ `deleted_at IS NULL` — 작성중은 조건이 아니고 승인 시 함께 삭제(§51-5) | `ContractRepository.countByStatus(marketId)` |
| `UNCLOSED_ORDERS` | `order_delivery_group` · `market_id` · `order.paid_at IS NOT NULL` · `FulfillmentStatus.isSettlementOpen`(미종결 — 공구 정산 게이트와 같은 정의) 건수 | `OrderDeliveryGroupRepository.countUnclosedByMarket(marketId)` 신규 — `countByStatusForGroupBuy` 의 마켓판 |
| `UNSETTLED` | 지급 완료 전 정산 또는 회수 대기 차감 | `SettlementReader.hasUnsettledForMarket`(기존 — 그 클래스 주석 「호출처는 탈퇴 API 가 생길 때 붙는다」) → 건수가 필요하므로 `countUnsettledForMarket` 로 확장 |

차감(클로백) 대기 금액(`[자문대기-법률 J]`)은 이미 `hasUnsettledForMarket` 에 들어 있다 — 자문 결과가 「막지 않는다」면 그 조건식 한 줄이다.

### 4-2. 신청 · 취소(파트너 — 짝 설계 · 여기서는 도메인 서비스만)

`BrandWithdrawalService.request(market, reason, message, requesterName)` — 적격 아니면 409 `BRAND_WITHDRAWAL_CONDITION_UNMET`(`unmet` 포함) · 열린 신청 있으면 409 `BRAND_WITHDRAWAL_ALREADY_PENDING` · 행 INSERT · 이력 `WITHDRAWAL_REQUESTED(actor BRAND · detail = 사유 라벨)`. `cancel(requestId)` — `PENDING → CANCELED` · 이력 `WITHDRAWAL_CANCELED`. 대기 중 잠기는 것(새 공구 시작 · 비밀번호 · 로그인 이메일 · 재신청 — 파트너 4-I)은 **열린 신청 행의 유무**로 파트너 측 가드가 판정한다 — 반려 · 취소가 되면 자동으로 풀린다(§51-5 ⚠️ 「활성으로 되돌아가고」 문구 문제가 BE 에는 없다 — 회원 상태는 내내 `ACTIVE` 다).

### 4-3. 승인 `POST /v1/admin/brands/{marketId}/withdrawal-requests/{requestId}/approve` — M2

입력 없음(승인은 조건 충족의 확인 — 사유를 받지 않는다). 한 트랜잭션 · 순서 고정:

1. 신청 행 조회 — 마켓 불일치 404 · `status ≠ PENDING` → 409 `BRAND_WITHDRAWAL_NOT_PENDING`.
2. **재검증** `BrandWithdrawalEligibility.evaluate` — 미충족이면 409 `BRAND_WITHDRAWAL_CONDITION_UNMET` + `unmet { condition: count }`. 운영자는 그 축으로 반려한다(M3 사유 = 조건 축).
3. 신청 `PENDING → APPROVED`(처리자 · 시각 · 이름) — 조건부 UPDATE 0행 409 `BRAND_STATE_CHANGED`.
4. 열린 정지 행이 있으면 `released(SYSTEM · WITHDRAWN)` 로 종결(이력 `SUSPENSION_RELEASED` · detail 「탈퇴 승인으로 종결」). 지급 정지 중이면 조건 ④ 가 걸려 2 에서 이미 막혔다 — 여기 도달했다면 미정산이 없다.
5. `transitionStatus(marketId, {ACTIVE, SUSPENDED}, WITHDRAWN)`.
6. **파기 · 차단** `BrandWithdrawalPurger.purge(seller, market)` — 1-6 의 목록 · `SellerRefreshTokenRepository` 삭제(이메일 키) · 사업자등록번호 해시(`BusinessRegistrationNumberHasher` — 반려 파기와 같은 해시).
7. `DRAFT` 계약 삭제(soft — `deleted_at`) · 상품 전건 `HIDDEN` · PAIR `CONNECTED` 연결 전건 `DISCONNECTED` + 그 스레드 `dormant`(운영팀 채널은 그대로 — `THREAD_READ_ONLY` 가 쓰기를 막는다).
8. 이력 `WITHDRAWAL_APPROVED`(중립 톤 · `detail = 신청 사유 라벨`).
9. `afterCommit` — `BrandMemberNotifier.withdrawalApproved`(수신처가 파기된 뒤라 **파기 전에 읽은 이메일**을 넘긴다 — 스텁이라 지금은 로그).

되돌릴 수 없다 — 복구 API 를 만들지 않는다(§51-5 「재입점은 신규 가입으로만」).

### 4-4. 반려 `POST …/withdrawal-requests/{requestId}/reject` — M3

입력 `{ reason: BrandWithdrawalRejectReason, note?: ≤500 }` · `OTHER` 면 note 필수(400 `BRAND_WITHDRAWAL_REJECT_DETAIL_REQUIRED`). `PENDING → REJECTED` · 이력 `WITHDRAWAL_REJECTED(detail = 사유 라벨 + note)` · 알림 스텁(사유 · 안내가 브랜드에 간다). 회원 상태는 건드리지 않는다. 브랜드는 즉시 재신청할 수 있다(새 행).

| `GET …/memos?page&size` | 최신순 · `deleted_at IS NULL` · 각 행 `editable` |
| `POST …/memos { content }` | 300자 서버 검증(공백 제거 후 1 ~ 300 · 400 `INVALID_INPUT_VALUE`) · 탈퇴 계정 409 `BRAND_WITHDRAWN` · 이력 `MEMO_CREATED` |
| `PATCH …/memos/{memoId} { content }` | 작성자 본인(403 `BRAND_MEMO_NOT_AUTHOR`) ∧ 24h 이내(403 `BRAND_MEMO_EDIT_WINDOW_CLOSED`) · `modified_at` 갱신 · 이력 `MEMO_UPDATED` |
| `DELETE …/memos/{memoId}` | 같은 조건 · `deleted_at` · 이력 `MEMO_DELETED` |

고지 문구(「정산 · 분쟁 시 증빙으로 인용될 수 있음」)는 FE 고정 문구다.

### 5-2. 처리 이력 — `GET …/histories?page&size`

`BrandAdminHistoryReader.read(marketId)` 가 세 원천을 합쳐 `created_at DESC` 로 자른다.

| 원천 | 행 |
| --- | --- |
| `brand_admin_history` | 저장된 9종 그대로 |
| `seller` · `seller_application_history` | `SIGNED_UP(seller.created_at · actor BRAND)` · `ONBOARDING_APPROVED(APPROVED 행 created_at · actor ADMIN · processed_by 이름은 `AdminOperatorResolver.namesOf`)` |
| `brand_change_request` | `CHANGE_REQUEST_RECEIVED(requested_at · actor BRAND · detail = 유형 라벨 · ref = request → ↗ 변경 요청)` · `…_APPROVED / …_REJECTED(processed_at · actor ADMIN)` — `CANCELED` 는 내리지 않는다(브랜드가 철회한 건은 운영자 조치의 근거가 아니다) |

페이지는 **메모리 병합**이다 — 한 브랜드의 사건은 많아야 수백 건이고(변경 요청 · 메모 · 정지), 세 원천을 각각 페이지하면 순서가 어긋난다. 상세 응답의 「최신 3건」도 같은 리더에서 `limit` 만 다르다.

## 6. 지급 정지 연동 — `domain.settlement`

### 6-1. `SettlementSanctionHook.holdBrandPayouts(marketId, now)`

그 마켓 정산의 `BRAND` 수취자 행 중 `status = SCHEDULED` 를 `SettlementPayoutTransitions.blockScheduled(settlementId, payoutId, BRAND, "BRAND_SUSPENDED", "계정 정지 · 지급 정지", …)` 로 돌린다(이력 `PAYOUT_BLOCKED`). `WAITING · HELD`(확정 전)는 건드리지 않는다 — 확정 때 6-3 이 판정한다. `REQUESTED · PAID · FAILED` 도 건드리지 않는다. `derive` 로 정산 상태를 다시 계산하지 않는다 — `BLOCKED` 는 `PAYOUT_SCHEDULED` 안의 수취자 상태다(인플루언서 증빙 대기와 같다).

### 6-2. `releaseBrandPayouts(marketId, today)`

`BLOCKED ∧ fail_code = BRAND_SUSPENDED` 인 `BRAND` 행을 `SCHEDULED` · `due_date = BusinessCalendar.addBusinessDays(today, 1)` 로 — `releaseIfUnblocked` 와 같은 조건부 UPDATE 경로(`updateStatusWhere … EnumSet.of(BLOCKED) → SCHEDULED`). 지급 배치는 예정일 당일 10:00 에 집는다 — 「해제 다음 영업일에 지급」.

### 6-3. 재판정 두 지점 — `BrandPayoutHoldReader`(포트 · `domain.settlement.port`)

`boolean isHeld(Long marketId)` — 구현은 `domain.member.brand.service.BrandSanctionReader`(열린 정지 ∧ `payout_held`).

- `SettlementConfirmService` 가 수취자 행을 `SCHEDULED` 로 올리는 자리에서 `payee == BRAND ∧ isHeld` 면 `BLOCKED(BRAND_SUSPENDED)` 로.
- `SettlementPayoutTransitions.claim` 앞단에서 `BRAND` 행에 같은 검사 — 정지 직후 배치가 돌거나 6-1 과 확정이 경합해도 지시가 나가지 않는다.

어드민 07b · 파트너 13 은 수취자 행의 `status · failCode` 를 이미 라벨로 내린다 — `PayoutBlockReason.BRAND_SUSPENDED` 의 라벨 · `dueNoteFormat` 이 그대로 보인다. **추가 작업 없음**(§51-3 「07b 는 표시만」).

## 7. 브랜드 측 차단 가드 — `BrandSanctionGuard`

`domain.member.brand.service.BrandSanctionGuard.requireNotSuspended(Market market, BrandBlockedAction action)` — `market.status == SUSPENDED` 면 409 `BRAND_SUSPENDED`(메시지에 행위 라벨 — 「계정 정지 중에는 상품을 등록할 수 없습니다」). `market.status` 만 보고 정지 행을 읽지 않는다 — 가드는 뜨거운 경로다.

| 지점 | 메서드 | 행위 |
| --- | --- | --- |
| 상품 등록 | `ProductService.createProduct` 첫 줄 | `PRODUCT_CREATE` — 수정 · 삭제 · 품절은 막지 않는다 |
| 새 계약 | `SellerContractCommandService.create` · `requestReview` | `CONTRACT_CREATE` · `CONTRACT_REVIEW_REQUEST` — 작성중 계약의 수정 · 삭제 · 검토 요청 취소는 허용 |

| 공구 오픈 | `GroupBuyLifecycleService`(`READY → IN_PROGRESS` · 스케줄러 경로) — 예외가 아니라 **건너뛴다**(배치가 멈추면 안 된다) · 로그 1줄 | `GROUP_BUY_OPEN` — 해제 후 다음 틱이 연다 |

공구 상세의 `blockers` 에 `BRAND_SUSPENDED` 를 더해 「왜 안 열리나」를 공구 관리가 보이게 하는 것은 공구 설계서의 연계 항목이다(13절 #8). 파트너센터 기본정보 `GET /v1/seller/basicinfo/business` 의 `brandStatus` 는 이미 `market.status` 를 내린다 — 여기에 `sanction { reason · reasonLabel · suspendedAt · payoutHeld }` 를 덧붙여 파트너 화면(미작성)이 배너를 그릴 재료를 준다. 그 이상의 파트너 정지 화면은 범위 밖이다.
