## 1. 범위와 판정 기준

- 대상: 어드민 `/v1/admin/brands/**` **13개** 엔드포인트(목록 · 사유 목록 · 상세 · 정지 · 해제 · 탈퇴 승인 · 반려 · 이력 · 메모 4 · 연결 인플루언서) + 연계 지점 — 지급 보류(`PayoutHoldTransitions` · 확정 `SettlementConfirmService` · 지급 지시 앞단 `SettlementPayoutTransitions` · 포트 구현 `MemberPayoutHoldReader`) · 차단 가드 `BrandSanctionGuard` 5지점 · 운영팀 스레드 카드 `MessageSanctionChannelGateway` · 파트너 탈퇴 신청 · 취소(`/v1/seller/basic-info/withdrawal-requests`) · 파트너 기본정보 `GET /v1/seller/basic-info/business` 의 `sanction` · 즉시 탈퇴 차단(`DELETE /v1/seller/auth/withdraw`) · 발송 기한 이력(`PUT /v1/seller/basic-info/delivery-policy`) · V199.

- 아래 케이스는 **테스트 명세**다. 자동 테스트로 옮긴 범위와 실행 결과는 16-1, 옮기지 못한 것은 16-2 · 16-3 이다. 17절의 판정 보류 항목은 코드를 바꾸지 않고 **현재 동작을 테스트로 고정**했다 — 판정이 나면 기대값이 바뀐다.

### 1-3. 공통 확인 방법

1. 쓰기 한 번마다 **DB 행 · 처리 이력 · 레일 응답**을 같이 본다 — `market.status` · `brand_sanction` · `brand_withdrawal_request` · `brand_admin_history` · `brand_admin_memo` · `settlement_payout`(브랜드 · 인플루언서 · 플랫폼 3행의 `status · fail_code · due_date`) · `settlement_history`(`PAYOUT_BLOCKED · PAYOUT_HOLD_RELEASED`) · 운영팀 채널 메시지 `card_type` · `seller` · `seller_refresh_token`.
2. 실패 요청은 HTTP + 응답 `code` 를 보고 **부수 효과가 없는지**(행 · 이력 · 카드 · 지급 행 · 상태 불변) 본다. 응답 `code` 가 enum 이름과 다른 것: `INVALID_INPUT_VALUE → INVALID_INPUT` · `UNAUTHORIZED_ACCESS → UNAUTHORIZED`. `@Valid` 실패 · enum 역직렬화 실패도 400 이다.
3. 조치 응답은 **커밋 뒤 다시 읽은 레일**이다 — 같은 시점의 `GET /{marketId}` 의 `rail` 과 값이 같아야 한다.
4. 계좌번호 원본(`110123456789`)은 응답 본문 **문자열 검색**으로 없어야 한다(마스킹 필드만 보는 것으로는 부족하다).
5. 운영팀 카드 · 지급 보류 · 이력은 조치와 **같은 트랜잭션**이다(15 #2) — 조치가 실패 · 롤백되면 셋 다 없어야 한다. 알림 스텁만 커밋 뒤(`AfterCommit`)다.
6. 브랜드 몫만 움직여야 하는 케이스에서 인플루언서 · 플랫폼 행이나 다른 마켓 행이 움직이면 실패다.
7. 시안 · 설계서 · 코드가 충돌하면 17절에 적고 어느 쪽으로도 임의 통과시키지 않는다.
