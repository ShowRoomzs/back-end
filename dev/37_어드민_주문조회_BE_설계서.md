## 0. 먼저 정한 8가지

### 0-1. 행 = 주문(결제 1건) — 하위주문 테이블을 **주문 id로 묶어** 만든다

파트너센터(34 설계서)는 `order_delivery_group`(하위주문)이 행이고, 어드민은 `orders`(결제 1건)가 행이다. CS에 들어오는 말은 「주문 하나 했는데요」다(§37-0). 그래도 **조회의 원천은 하위주문 테이블 하나**다 — 탭 · 상태 · 배송 이상 · 취소 요청이 전부 하위주문에 붙어 있기 때문이다.

- `OrderDeliveryGroupRepositoryImpl.searchOrderIdsForAdmin` — 하위주문을 조건으로 거른 뒤 `GROUP BY o.id` 로 **주문 id 페이지**를 뽑고, 서비스가 그 주문의 하위주문 전부를 다시 읽어 행 확장(A2)까지 한 번에 내린다.
- 「하위주문 하나라도 조건에 맞으면 그 주문이 나온다」가 규칙이다. 상태 셀렉트 「배송중」을 고르면 배송중 하위주문이 있는 혼합 주문도 나온다.
- 새 테이블 · 새 뷰는 없다. 주문 단위 집계(`totalAmount` · `paidAt` · 수취인)는 `orders` 가 이미 가진 값이다.

### 0-2. 조회 조건은 **파트너 조건과 다른 레코드**다 — `AdminOrderSearchCondition`

파트너 조회(`SellerOrderSearchCondition`)를 「마켓 조건 없이」 재사용하지 않는다. 축이 다르다 — 파트너는 탭 7 · 날짜 기준 5종 · 검색 유형 4종, 어드민은 탭 3 · 결제일 하나 · 통합 키워드다. 조건을 억지로 합치면 파트너 쪽 `pendingCancelFilter` 같은 탭 의미가 어드민에 새어 들어온다. `adminWhere` 는 `OrderDeliveryGroupRepositoryImpl` 안에 **따로** 있다.

### 0-3. 운영자 조치는 5종이고, **버튼 노출은 서버가 결정**한다 — `actions`

§37-4 「레일 액션은 조건 미충족이면 숨긴다(비활성 아님)」. 상세 응답의 하위주문마다 `actions { canCorrectDeliveredAt, canRegisterShipment, canCancel, canEnqueueRefund, canOpenDefectClaim }` 를 내리고 FE는 `true` 인 버튼만 그린다. 판정식은 `AdminOrderQueryService.actions` 한 곳에 있고, 커맨드 서비스는 **같은 판정을 다시 검사**한다(조회 뒤 상태가 바뀌었을 수 있다).

### 0-4. 「대행 가능」은 **상태가 아니라 조건**이다 — 저장하지 않는다

시안 B4 「대행 가능은 상태가 아니라 조건이다 — 배지를 쓰지 않는다」. 발송 기한 경과 ∧ 자동 알림 N회(기본 3 · `order.act-on-behalf-notice-threshold`) 무응답 — 둘 다 이미 저장된 사실(`ship_due_at` · `overdue_notice_count`)에서 계산된다. `canActOnBehalf(group, now)` 가 조회 · 대행 송장 · 직권 취소에서 같은 식으로 쓰인다.

### 0-5. 돈 — **편입과 집행을 나눈다**

| 경로 | 이 화면에서 | 집행 주체 |
| --- | --- | --- |
| 대행 직권 취소(미발송분) | 큐 적재(`origin = PG_AUTO`) | **시스템** — 커밋 직후 `RefundExecutor`(1009 수정계획 2-4) |
| 운영자 사유 환불(발송분) | 큐 적재(`origin = OPERATOR` · `PENDING`) **까지만** | **운영자** — 06c 집행 대기 탭의 재확인 다이얼로그 |
| 반송 완료 · 취소 요청 자동 승인 · 반품 검수 통과 | 조회만 | 시스템(PG 자동) |

운영자가 이 화면에서 누르는 버튼으로 돈이 **즉시** 나가는 경우는 직권 취소 하나이고, 그것도 브랜드 직권 취소와 같은 경로(PG 자동)다. 「[환불 집행으로] 버튼은 없앴다」(시안 rev.4)가 그대로다.

### 0-6. 반품 대신 열기는 **클레임 도메인의 공용 경로**를 탄다

`OrderClaimService.openDefectClaimByOperator` — 소비자 반품 신청과 같은 `OrderClaimCollection` + `OrderClaim` 을 만들되 `opened_by = OPERATOR` · `opened_by_admin_id` · `open_reason` 을 남긴다. 그 뒤는 일반 반품과 같다(회수 송장은 소비자 · 검수는 브랜드 · 통과 시 PG 자동 환불). 어드민 전용 클레임 테이블이나 상태는 없다 — 파트너 11 목록에 「운영자 개설」로 보이기만 한다.

### 0-7. 이 화면은 상류 5건의 **결과를 읽는 창**이다

1009 수정계획 8절 순서대로 **1(발송 기한) → 2(PG 자동 환불) → 3(취소 요청 자동 승인) → 4(타이머) → 5(클레임)** 가 먼저 끝났고, 06a 는 그 결과 컬럼(`ship_due_business_days` · `origin` · `respond_due_at` · `auto_approved` · `confirm_paused_at` · `overdue_notice_count`)을 조립해 보여준다. 이 설계서가 새로 판 컬럼은 `order_claim.opened_by` 계열(V174) 뿐이다.

### 0-8. 패키지는 `api.admin.transaction` 하나

수정계획 8절은 `admin.order · admin.claim · admin.refund · admin.exception` 네 패키지를 적었으나 **거래 관리 메뉴 하나 = 패키지 하나**로 묶었다. 네 컨트롤러가 같은 DTO(`AdminTransactionDto` 공용 조각)와 같은 판정(`canActOnBehalf`)을 나눠 쓰고, 06d 「열기」 → 06a 상세 · 06a B5 → 06c 집행 대기처럼 서로를 가리키는 링크가 많아서다.

## 2. 조회 — `GET /v1/admin/orders`

권한 `ADMIN`(`SecurityConfig` `/v1/admin/**`). 읽기 전용 트랜잭션. 응답은 `PageResponse<AdminOrderListItem>`.

### 2-1. 파라미터

| 파라미터 | 타입 | 시안 | 규칙 |
| --- | --- | --- | --- |
| `tab` | `AdminOrderTab` | A1 탭 3 | 기본 `ALL` |
| `status` | `FulfillmentStatus` | 상태 셀렉트 | 하위주문 하나라도 같으면 그 주문. 배송 이상 탭의 「이상 유형 셀렉트」는 **파라미터가 따로 없다**(8절 #1) |
| `marketId` | Long | 상세 조건 「브랜드」 · 브랜드 상세 「이 브랜드 진행 주문 보기」 | 하위주문 `market_id` |
| `keyword` | String | 검색어 | 주문번호 · 하위주문번호 · 수취인 · 브랜드명 OR 매치. 숫자가 섞여 있으면 송장번호(숫자만)도 OR. 검색 대상 셀렉트는 **없다**(8절 #1) |
| `from` · `to` | `yyyy-MM-dd` | 결제일 프리셋 · 직접 입력 | `orders.paid_at` 기준 · `to` 는 그날 23:59:59. 기본 기간(1개월)은 FE 가 채운다 |
| `page` · `size` | `PagingRequest` | 20 · 50 · 100 | `size` 1 ~ `order.list-page-size-max`(100), 넘으면 `ORDER_PAGE_SIZE_INVALID` |

정렬은 **결제일시 최신순 고정**(`o.paidAt DESC, o.id DESC`). 시안의 「결제금액 높은순」 · 배송 이상 탭 「이상 지속 오래된순」은 8절 #2.

### 2-2. 탭 ↔ 조회 조건 — 서버가 소유한다

| 탭 | WHERE(하위주문 기준) | 비고 |
| --- | --- | --- |
| `ALL` | `o.paid_at IS NOT NULL` | 결제 전 주문은 어떤 탭에도 없다 |
| `DELIVERY_ISSUE` | `g.tracking_alert IS NOT NULL OR g.fulfillment_status = RETURNING` | 집화 확인 필요 · 추적 정지 · 반송 중. **반송중은 어드민에서 배송 이상 열**이다(§37-8 A-3 — 도메인은 이행 상태값, 화면은 열) |
| `CANCEL` | `g.fulfillment_status = CANCELLED OR EXISTS(pending cancel_request)` | 취소된 하위주문 + 검토 중 취소 요청 |

### 2-3. 응답 — 행 + 행 확장을 한 번에

```
AdminOrderListItem {
  orderId, orderNumber, paidAt, recipientName, totalAmount,
  groups[]: AdminOrderGroupSummary {            ← A2 행 확장 · 하위주문 1단에서 끊는다
    deliveryGroupId, subOrderNumber, brandName,
    status, statusLabel, statusTone,            ← 상태 축
    trackingAlert, trackingAlertLabel,          ← 배송 이상 축(별도)
    shipDueAt, shipOverdue, cancelRequested
  },
  attentionCount                                ← 배송 이상 ∨ 발송 기한 경과 ∨ 검토 중 취소 요청 ∨ 반송중 인 하위주문 수
}
```

- 시안 열 「브랜드」(여럿이면 `N개 브랜드`) · 「상태」(갈리면 `혼합` + 조합 부기) · 「배송 이상」은 **FE 가 `groups[]` 에서 만든다**. 서버는 하위주문을 전부 내리고 합치지 않는다 — 합치면 열 의미가 행마다 바뀐다(§37-3).
- `shipOverdue` = `status ∈ {NEW, PREPARING} ∧ ship_due_at < now`. 파생값이라 저장하지 않는다(34 설계서 0-5).
- 항목(SKU)은 목록에 없다 — 상세 ②블록의 일이다.

### 2-4. 요약 — `GET /v1/admin/orders/summary`

같은 `marketId · keyword · from · to` 로 탭 셋을 각각 `COUNT(DISTINCT o.id)` 한다. 상태 셀렉트는 무시한다(탭 숫자는 셀렉트와 무관하게 고정). 응답 `{ tabCounts: { ALL, DELIVERY_ISSUE, CANCEL } }`.

툴바 좌측 「처리 지연 N건」은 **이 응답에 없다** — 06d `GET /v1/admin/order-exceptions/summary` 가 소유한다(8절 #3).

### 2-5. 상세 — `GET /v1/admin/orders/{orderId}`

`paid_at` 이 없는 주문은 `ORDER_NOT_FOUND`(결제 전 주문은 화면 밖). 시안 좌 5블록 + 우 레일을 하위주문 배열로 내린다.

| 시안 블록 | 응답 |
| --- | --- |
| ① 결제 정보 | `payment { paymentId, status, methodLabel, amount, cancelledAmount, paidAt }` — 취소 가능 잔액 = `amount − cancelledAmount` 는 FE 계산. 교환 재발송비(추가 결제)는 **클레임 결제**라 06b 상세의 몫(8절 #5) |
| ② 하위주문 · 항목 | `groups[].items[] { orderProductId, productName, optionName, quantity, returnedQuantity, price, status, cancelTypeLabel }` · `groupBuyNumber` · `brandName` |
| ③ 배송 | `groups[].shipping { shipDueAt, shipDueBusinessDays, shipOverdue, overdueNoticeCount, prepareStartedAt, shippedAt, carrier(+Label), trackingNumber, trackingAlert(+Label), lastTrackingAt, returnDetectedAt, returnCompletedAt, deliveredAt, deliveredSourceLabel }` |
| ④ 정산 반영 | `groups[].purchaseConfirm { paused, remainingDays, dueAt, confirmedAt }` — 정산 편입 · 확정일 · 클로백은 **정산 모듈 전이라 없다**(`null` 이 아니라 필드 자체가 없다 · 8절 #4) |
| ⑤ 이력 | `groups[].history[] { eventType, label, actorType, detail, occurredAt }` — 오래된순. 준비 시작 사유(발주서 다운로드 / 개별 / 일괄)는 `PREPARE_STARTED.detail` |
| 취소 요청(B7) | `groups[].cancelRequest { cancelRequestId, reasonLabel, reasonDetail, requestedAt, respondDueAt, orderProductIds }` — PENDING 일 때만 |
| 환불 | `groups[].refunds[] { refundTaskId, source, origin, originLabel, amount, status, lastError, executedAt, createdAt }` |
| 우 레일 | `groups[].actions` — 2-6 |
| 헤더 | `consumer { userId, name, email }` · `recipient { name, phone, zipCode, address, detailAddress, memo }` — **마스킹하지 않는다**(§37-8 A-7 미결 — 9절) |

### 2-6. `actions` 판정 — `AdminOrderQueryService.actions`

| 필드 | 시안 | 판정식 |
| --- | --- | --- |
| `canCorrectDeliveredAt` | B3 | `status == DELIVERED` |
| `canRegisterShipment` | B4 | `status == PREPARING ∧ canActOnBehalf ∧ ¬cancelRequested` |

## 3. 운영자 조치 5종 — 전부 조건부 UPDATE · 이력 `ADMIN`

모든 조치는 성공 시 **갱신된 상세(2-5)** 를 돌려준다(B6 만 생성 id). 운영자 id 는 `UserPrincipal.userId`(없으면 `UNAUTHORIZED_ACCESS`). 권한 등급(운영자 vs 최고관리자 · §37-8 B-8)은 미결이라 `ADMIN` 단일이다.

### 3-1. B3 배송완료일 정정 — `PATCH /groups/{deliveryGroupId}/delivered-at`

요청 `{ deliveredAt(필수), reason(필수 · 300자) }`. 「직권 배송완료」는 **없다** — 추적이 원래 없는 건이 생기지 않는다(rev.4).

| 순서 | 검사 · 처리 | 실패 |
| --- | --- | --- |
| 1 | `status == DELIVERED ∧ delivered_at IS NOT NULL` | 409 `ORDER_STATE_CHANGED` |
| 2 | `shipped_at ≤ deliveredAt ≤ now` | 400 `INVALID_INPUT_VALUE` |
| 3 | `UPDATE … SET delivered_at, delivered_source = ADMIN, delivered_by WHERE status = DELIVERED` | 1행 아니면 409 |
| 4 | `confirm_restart_at` 이 있으면(교환 재발송 뒤) **같은 차이만큼** 민다. 없으면 기산점(`confirmBaseAt`)이 `delivered_at` 이라 저절로 따라간다 | — |
| 5 | 이력 `DELIVERED_AT_CORRECTED` · `ADMIN` · detail `「구 날짜 → 신 날짜 · 사유」` | — |

- 구매확정 예정일과 반품·교환 가능 기간(클레임 `invoiceDueAt` 계산의 기산점)이 **함께 움직인다** — 시안 B3 경고 문구의 근거다. 브랜드 · 소비자 통지는 알림 모듈(이벤트 없음 · 8절 #8).
- 정정 횟수 · 방향 제한(§37-8 B-11 「앞으로만」)은 없다 — 확정되면 `shipped_at ≤ deliveredAt` 검사 옆에 `before < deliveredAt` 한 줄.

### 3-2. B4 운영자 대행 송장 등록 — `POST /groups/{deliveryGroupId}/shipment`

요청 `{ carrier(필수), trackingNumber(필수), note(대행 사유 · 300자) }`. 브랜드 송장 등록(34 설계서 3-2)과 **같은 전이**를 마켓 조건 없이 탄다.

| 순서 | 검사 · 처리 | 실패 |
| --- | --- | --- |
| 1 | `canActOnBehalf` — 발송 기한 경과 ∧ 자동 알림 3회 | 409 `ORDER_ACT_ON_BEHALF_NOT_ALLOWED` |
| 2 | 택배사 `isSelectable`(쿠팡택배 제외) · 숫자만 남긴 송장이 비지 않음 · `DeliveryTrackerPort.validateInvoice ≠ INVALID` | 400 `INVOICE_FORMAT_INVALID` |
| 3 | 전역 중복 — `INVOICE_ACTIVE` 상태의 다른 하위주문에 같은 택배사 · 송장 | 409 `INVOICE_DUPLICATE` |
| 4 | `UPDATE … SET SHIPPING, carrier, tracking_number, shipped_at = now WHERE status = PREPARING ∧ NOT EXISTS(pending cancel_request) ∧ NOT EXISTS(payment CANCEL_REQUESTED)` | 1행 아니면 — 검토 중 요청이 있으면 409 `CANCEL_REQUEST_PENDING_EXISTS`, 아니면 `ORDER_STATE_CHANGED` |
| 5 | 이력 `INVOICE_REGISTERED` · `ADMIN` · detail `「운영자 대행 · 택배사 송장 · 사유」` | — |

- 시안의 「대행 사유 필수」는 서버에서 **선택**이다(`note` nullable) — 8절 #9.
- 발송기한 판정값은 송장 등록 시각(지금)이라 이 건은 영원히 「기한 경과」로 남는다. 출처 「운영자 대행」은 이력 detail 에만 있고 하위주문에 열이 없다(파트너 10c 목록 표기는 이력으로 판단).
- `NEW`(준비 대기)는 대상이 아니다 — 시안도 「상품준비중」만 적었다. 준비 시작 없이 발송기한을 넘긴 `NEW` 는 직권 취소(3-3)로만 닫힌다.

### 3-3. B4 · B5 대행 직권 취소(미발송분) — `POST /groups/{deliveryGroupId}/cancel`

요청 `{ reasonCode(SellerCancelReason · 필수), consumerMessage(필수 · 300자 · 소비자에게 그대로) }`. 브랜드 직권 취소(파트너 10d E5)와 같은 전이 · 재고 원복 · **PG 즉시 자동 환불**.

| 순서 | 검사 · 처리 | 실패 |
| --- | --- | --- |
| 1 | `reasonCode == DEFECT` 이거나 `canActOnBehalf` | 409 `ORDER_ACT_ON_BEHALF_NOT_ALLOWED` |
| 2 | `PAID` 항목을 미리 읽는다 | — |
| 3 | `UPDATE … SET status_at_cancel = status, CANCELLED, cancelled_at, cancel_type = SELLER_DIRECT, cancel_reason_code, cancel_reason_detail WHERE status ∈ {NEW, PREPARING} ∧ NOT EXISTS(pending) ∧ NOT EXISTS(payment CANCEL_REQUESTED)` | `CANCEL_REQUEST_PENDING_EXISTS` / `ORDER_STATE_CHANGED` |
| 4 | `OrderFulfillmentService.cancelItemsWithRestock(paidItems, SELLER_DIRECT)` | — |
| 5 | 환불액 = 취소 항목 `price × quantity` 합 + 하위주문 `delivery_fee` → `enqueueRefund(SELLER_DIRECT_CANCEL, PG_AUTO)` → 커밋 뒤 `RefundExecutor` | 실패는 06c 실패 탭 |
| 6 | 이력 `CANCELLED_BY_SELLER` · **`ADMIN`** · detail `「운영자 대행 · 사유 · 소비자 메시지」` | — |

- 위해성 긴급 중단(B5 · 결정 4) — 미발송 하위주문은 여기(`DEFECT`), 발송된 하위주문은 3-4. 다른 브랜드의 하위주문은 운영자가 고르지 않으면 건드리지 않는다.
- `cancel_type` 이 `SELLER_DIRECT` 로 남는다 — 어드민 전용 취소 유형을 만들지 않았다. 주체는 이력 `actor_type = ADMIN` 으로 구분한다. 시안 「직권 취소 폼」은 미제작(§37-9 #9)이라 입력 두 개로 열었다.

### 3-4. B5 운영자 사유 환불 편입 — `POST /groups/{deliveryGroupId}/refund-tasks`

요청 `{ reason(OperatorRefundReason · 필수), amount(≥ 1 · 필수), detail(근거 · 필수 · 500자) }`. **편입만** — 돈은 06c 재확인 다이얼로그에서 나간다.

| 순서 | 검사 · 처리 | 실패 |
| --- | --- | --- |
| 1 | 하위주문 `SELECT … FOR UPDATE` | 404 `ORDER_GROUP_NOT_FOUND` |
| 2 | `status ∉ {PENDING, NEW, PREPARING, CANCELLED}` — 발송 전은 직권 취소로 | 409 `ORDER_STATE_CHANGED`(「발송 전 주문은 직권 취소로 환불합니다」) |
| 3 | `amount ≤ payment.cancellableAmount − Σ outstanding(PENDING · EXECUTING · FAILED) refund_task(같은 결제)` | 409 `REFUND_AMOUNT_EXCEEDED`(잔액을 메시지에 싣는다) |
| 4 | `enqueueOperatorRefund` → `order_refund_task(OPERATOR_REASON · OPERATOR · PENDING · payment_id · reason_code · reason_detail · requested_by)` | — |
| 5 | 이력 `REFUND_ENQUEUED_BY_OPERATOR` · `ADMIN` · detail `「사유 · N원」` | — |

- 시안의 「대상 항목 체크 + 수량」은 **금액 하나**로 받는다 — 항목 단위 상태 전이(`REFUNDED`)가 집행 시점에 일어나지 않고, 환불액이 결제 잔액 안이기만 하면 된다(8절 #7).
- `sourceId` 는 `null` — 06b B2(반려 이의 인용)는 같은 `enqueueOperatorRefund` 에 클레임 id 를 싣는다.
- 결제 밖 주문(`paid_payment_id IS NULL`)은 잔액 검사를 건너뛴다 — 운영자가 수동 기록한다.

### 3-5. B6 구매확정 후 하자 · 반품 대신 열기 — `POST /groups/{deliveryGroupId}/defect-claims`

요청 `{ items[]{ orderProductId, quantity ≥ 1 }, reasonCode(ClaimReason), detail(필수 · 1000자), evidenceImageUrls[](1장 이상) }`. 응답 `{ requestId(collection) , claimIds[] }`.

`OrderClaimService.openDefectClaimByOperator` 의 검사 순서:

| 순서 | 검사 | 실패 |
| --- | --- | --- |
| 1 | 항목 1개 이상 · 중복 없음 | 400 `INVALID_INPUT_VALUE` |
| 2 | `reasonCode.feeBearer == SELLER` — 파손·불량 · 오배송만. **단순 변심 · 기타 불가** | 400 `INVALID_INPUT_VALUE` |
| 3 | `detail` · 증빙 1장 이상 | 400 `CLAIM_REASON_DETAIL_REQUIRED` |
| 4 | 하위주문 잠금 · `status ∈ {CONFIRMED, DELIVERED}` | 409 `CLAIM_NOT_ELIGIBLE` |
| 5 | `delivered_at + 3개월 ≥ now`(전자상거래법 제17조③ 공급일 기준) | 409 `CLAIM_NOT_ELIGIBLE`(「3개월이 지나 열 수 없습니다」) |
| 6 | 항목이 이 하위주문 소속 · `PURCHASE_CONFIRMED` 또는 `PAID` · 잔여 수량(`quantity − returned − 점유 중 클레임`) 안 | 404 `ORDER_PRODUCT_NOT_FOUND` / 409 `CLAIM_NOT_ELIGIBLE` / 409 `CLAIM_QUANTITY_EXCEEDED` |
| 7 | `OrderClaimCollection(RETURN · feeBearer = SELLER · invoiceDueAt = now + N일)` + 항목별 `OrderClaim(opened_by = OPERATOR, opened_by_admin_id, open_reason)` | — |

- 「안 날부터 30일」은 **서버가 검사하지 않는다**(수정계획 Q6 · 운영자 판단) — 시안의 「하자 인지일」 입력은 받지 않는다(8절 #10).
- 귀책 **브랜드**(착불 · 차감 없음)로 열린다. 검수에서 브랜드가 소비자 귀책으로 바꿀 수 있고(§37-8 B-16 해소 · V174 `fault_changed_to_seller` 의 역방향은 06b 설계), 소비자 이의는 06b 경로다.
- `open_reason` 은 고정 문자열 「구매확정 후 하자」다(`OrderClaim.markOpenedByOperator`).
- 소비자 반품 접수와 달리 이 경로는 **구매확정 타이머를 정지시키지 않는다**(`pauseConfirmTimer` 호출 없음). 대상이 `CONFIRMED` 면 상관없지만 `DELIVERED` 상태에서 열면 D+7 배치가 열린 클레임 `NOT EXISTS` 안전망으로만 보류된다 — 8절 #14.
- 정산 확정 항목의 클로백(「다음 정산에서 차감」)은 정산 모듈 전이라 **표시도 계산도 없다**(8절 #4).

## 4. 조치가 없는 상태 — 조회로만 표현한다

| 시안 | 서버 표현 | 레일 문구의 근거 |
| --- | --- | --- |

반송 사유 · 분실 판정은 어디에도 없다 — 플랫폼이 단정하지 않는다(§37-4).

| 대상 | 방향 | 내용 |
