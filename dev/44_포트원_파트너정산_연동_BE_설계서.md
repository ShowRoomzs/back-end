## 0. 먼저 정한 것 — 조사에서 확인된 사실과 그로부터 나온 결정

### 0-1. 포트원 Platform 은 「3자 분배」가 아니라 「정산 뒤 지급대행」이다 — §41-5 전제의 수정

§41-5 는 「소비자 결제금이 PG 에서 브랜드 · 인플루언서 · 플랫폼에게 **각각 직접** 지급된다 — 플랫폼이 대금을 보관했다 나눠주는 구조가 아니다」라고 썼다. 포트원 파트너 정산은 그 구조가 아니다. 결제 대금은 PG 가 **우리(플랫폼) 가맹점 계정**으로 정산하고, 포트원은 그 뒤 우리가 올린 정산건을 모아 **우리 지급 계좌에서 파트너 계좌로 송금을 대행**한다(`PlatformPayoutMethod.AGENCY` · 「송금 대행을 통해 일어난 이체 내역」). 즉 **플랫폼이 대금을 한 번 받는다.**

- 코드에는 영향이 없다 — 정산 모듈은 처음부터 「지급은 포트 뒤」였고, 금액 분해 · 3자 분배 행 · 검산은 그대로다.
- 기획 · 법무에는 영향이 있다 — 「돈이 안 들어왔다」 문의의 응답 주체가 PG 에서 **우리**로 바뀌고, 대금 보관에 따르는 등록 의무(전자금융거래법 · 결제대금예치) 검토가 필요하다. **13절 미결 L-1** 로 올린다. 이 설계서는 법무 판단과 무관하게 연동 자체를 설계한다.

### 0-2. 산식은 우리가 소유하고 포트원은 **지급만** 맡는다 — 수기 정산건(`manual transfer`) 방식

포트원에는 계약(수수료율 · 정산 주기) · 할인 분담 · 추가 수수료로 **정산액을 계산해 주는 엔진**(주문 정산건 `POST /platform/transfers/order`)이 있다. 쓰지 않는다. 이유 — ① 리워드(항목별 율 · 계약서 PDF 와 같은 1원 절사) · 원천징수(소득세 · 지방소득세 각각 절사) · 조정 합의 · 차감 이월 · 소비자 배송비 가산은 포트원 계약 모델로 표현되지 않는다 ② 「세 화면이 같은 숫자를 보는 근거는 `SettlementCalculator` 하나」(44 어드민 0-6)를 지킨다 ③ 포트원 금액과 우리 금액이 1원이라도 다르면 수취자에게 설명해야 하는 쪽은 우리다.

그래서 **수취자 행 1개 = 포트원 수기 정산건 1개**(`POST /platform/transfers/manual` · `settlementAmount` 명시 · 계약 없음)이고, 포트원은 그 금액을 **그대로** 지급한다.

### 0-3. 지급 **실행** API 가 없다 — 지급은 포트원 콘솔에서 사람이 누른다(Q1 전까지)

REST V2 · SDK 0.24.0 의 Platform API 를 전부 확인한 결과, 지급 쪽에는 `GET /platform/payouts` · `GET /platform/bulk-payouts`(조회)와 `POST /platform/partner-settlements/complete-payout`(**우리가 직접 송금한 뒤** 「지급 완료」로 표시 — `DIRECT`)만 있다. **일괄 지급을 요청(실행)하는 POST 는 없다.** 포트원 안내도 「재무 담당자가 콘솔에서 지급 실행을 요청하면 각 파트너 계좌로 자동 이체」다.

따라서 지급 흐름은 **「우리 배치가 정산건을 올린다 → 운영자가 포트원 콘솔에서 일괄 지급을 실행한다 → 우리 배치가 결과를 조회해 닫는다」** 가 된다. 우리 서피스에 지급 버튼이 없다는 §41-8 은 그대로이고, 사람의 손은 **포트원 콘솔**에 한 번 들어간다(9절 런북). 포트원에 실행 API(비공개 · unstable) 또는 정산일 자동 지급 옵션이 있는지가 **Q1** 이다 — 있으면 5-3 의 한 단계가 사라질 뿐 나머지 설계는 같다.

### 0-4. 원천징수는 우리가 계산하고 포트원은 **떼지 않는다**(`deductWht = false`) — Q2 전까지

포트원은 파트너 유형 「원천징수 대상자(`whtPayer`)」에 대해 지급 시 소득세 · 지방소득세를 스스로 계산해 뗄 수 있다(`PlatformSetting.deductWht` · `PlatformPayout.incomeTaxAmount · localIncomeTaxAmount`). 우리는 이미 `creator_payout_amount`(세후)를 계산하고 원천징수영수증 · 신고 자료를 만든다(44 어드민 5절). 둘이 겹치면 **이중 공제**다.

결정 — 플랫폼 설정 `deductWht = false` 로 두고, 수기 정산건에는 **세후 실지급액**을 올린다. 파트너 유형은 사실대로 등록한다(사업자 `business` / 비사업자 `whtPayer` — 비대상자 `nonWhtPayer` 는 쓰지 않는다). `whtPayer` 파트너에 `deductWht = false` 가 허용되는지, 포트원 원천세 신고 대행이 있다면 우리 신고 자료와 어떻게 나눌지가 **Q2** 다. 답에 따라 7절이 바뀔 수 있고, 그래도 우리 산식(세후액)은 바뀌지 않는다.

### 0-5. 테스트 모드는 포트원이 제공한다 — 전 호출에 `test` 플래그

SDK 의 모든 Platform 메서드는 첫 인자 `Boolean test` 를 받고, 정산건 · 조회 필터에는 `isForTest` 가 있다. **테스트 데이터는 운영 데이터와 분리**되어 같은 상점 · 같은 API Secret 으로 돈 없이 끝까지 돈다. 그래서 `settlement.payout.mode` 는 셋이 된다 — `SIMULATED`(지금 · 포트원 호출 없음) · `PG_TEST`(포트원 테스트 모드 · 개발 서버) · `PG`(운영). 운영 프로필 기동 검증은 `PG` 만 통과시킨다(6-4).

### 0-6. 파트너 등록은 **정산 확정 시점**에 보장하고, 계좌 변경은 즉시 반영한다

포트원 파트너(`/platform/partners`)는 계좌 예금주 검증을 거쳐 `APPROVED` 가 되어야 정산건을 받을 수 있다. 가입 때마다 등록하면 정산이 한 번도 없을 브랜드 · 인플루언서가 포트원에 쌓이고, 지시 순간에 등록하면 검증 실패가 지급일에 터진다. 그래서 **확정(`SettlementConfirmService.confirm`) 때** 두 수취자의 파트너를 보장(없으면 생성 · 계좌가 다르면 갱신)하고, 실패하면 확정은 그대로 두고 수취자 행만 `BLOCKED(PARTNER_NOT_READY)`로 둔다(4-3). 정산계좌 변경 요청 승인(`ChangeRequestApplier`) · 인플루언서 계좌 수정은 **즉시 PATCH** 한다(4-4) — 확정 회차의 계좌 고정(공통 결정 #14)과 충돌하지 않는다: 포트원 정산건은 파트너의 **현재** 계좌로 지급되므로, 확정 때 고정한 계좌와 다르면 지시 직전에 파트너 계좌를 그 스냅샷으로 맞춘다(5-2 ③).

### 0-7. 멱등 키는 우리가 정한다 — 파트너 id · 정산건 id

포트원은 파트너 id · 정산건 id 를 **호출자가 지정**할 수 있다(`CreatePlatformPartnerBody.id` · `CreatePlatformManualTransferBody.id`). 재시도 · 중복 호출은 `PlatformPartnerIdAlreadyExistsError` · `PlatformTransferAlreadyExistsError` 로 돌아오고, 그것은 **성공으로 취급**한다(이미 있음 → 조회). 키 규칙은 3-3.

### 0-8. 포트원 결제 연동과 **같은 켤레**로 만든다

`PortOneV2Gateway`(결제)와 같은 방식 — SDK 클라이언트 보유 · 생성자에서 `requireText` 기동 검증 · `CompletableFuture` 를 설정의 읽기 타임아웃으로 끊기 · 4xx(`PortOneException`)는 「결과 확정 실패」, 통신 · 5xx · 해석 불가는 「결과 모름」으로 가르기 · API Secret 로그 금지. 상점 · Secret · base URL 은 **결제와 같은 값**(`portone.*`)을 쓰고 Platform 전용 값만 `portone.platform.*` 에 둔다(6-3).

## 2. 전제 · 자격

### 2-1. 활성화 — 착수 게이트

Platform API 는 상점에 기능이 켜져 있지 않으면 전부 `PlatformNotEnabledError` 다. 결제 테스트 키가 있어도 자동으로 열리지 않는다. **포트원에 「테스트 상점 Platform(파트너 정산) 활성화」를 요청**하는 것이 이 설계서의 첫 단계다(10절 단계 0). 켜졌는지는 `GET /platform/partners?test=true` 한 번으로 확인한다(`PlatformNotEnabledError` 가 아니면 켜진 것).

### 2-2. 키 · 상점

결제와 같은 `portone.store-id` · `portone.api-secret` 을 쓴다(SDK `PlatformClient(apiSecret, baseUrl, storeId)` — `PaymentClient` 와 같은 생성자). Platform 전용 Secret 을 따로 발급받을 필요는 없다 — 다만 운영은 **지급 권한이 있는 Secret** 이라 결제용과 분리하고 싶으면 `portone.platform.api-secret` 로 덮어쓸 수 있게 둔다(6-3).

### 2-3. 콘솔에서 1회 설정할 것(운영 · 테스트 각각)

| 항목 | 값 | 이유 |
| --- | --- | --- |
| 원천징수 공제 `deductWht` | **false** | 0-4 |
| 정산 금액 유형 `settlementAmountType` | 수기 정산건은 금액을 그대로 쓰므로 영향 없음 — 기본값 유지 | — |
| 지급 방식 | `AGENCY`(지급대행) · 지급 계좌(우리 출금 계좌) 등록 · 충전/예치 방식 확인 | 0-1 · Q3 |
| 출금 · 입금 통장 메모 기본값 | `SHOWROOMZ 정산` / `쇼룸즈` | 수취자 통장에 찍히는 문구 — 기획 확인 |

### 2-4. SDK

### 4-4. 계좌 갱신과 「확정 회차는 기존 계좌」(공통 결정 #14)의 양립

포트원 정산건은 **파트너의 현재 계좌**로 지급된다(정산건에 계좌가 없다). 그래서 계좌 변경 승인이 즉시 파트너에 반영되면, 그 사이 확정된 회차가 새 계좌로 나갈 수 있다. 지시 직전(5-2 ③)에 **행의 스냅샷 계좌로 파트너를 맞추고** 지시한 뒤, 다음 지시 때 다시 현재 계좌로 돌아간다. 두 회차가 같은 날 지시되면서 계좌가 다르면 — 같은 파트너의 정산건은 같은 지급으로 묶이므로 한 계좌로만 나간다. 이 경우 뒤 회차를 **다음 영업일로 미룬다**(`claim` 이 같은 파트너 · 다른 계좌 행을 보면 `due_date + 1영업일`). 드문 경우라 로그 · 운영자 알림으로 충분하다.

## 5. 지급 — 지시 · 실행 · 결과

### 5-1. 흐름(예정일 D)

```

   ├ releaseBlocked  … 주민등록번호 · 파트너 재판정

       └ applyResults … REQUESTED 유지 · pg_transfer_id 저장 · 이력 PAYOUT_REQUESTED

```

플랫폼 몫(`PLATFORM` 행)은 지금처럼 어댑터가 즉시 `PAID` 로 돌려준다(내부 계정 · 정산건을 올리지 않는다).

### 5-2. 지시 — `distribute(PayoutCommand)` 의 어댑터 구현

행마다(BRAND · CREATOR):

1. 파트너 id 산출(3-3) · `portone_partner_id` 가 없으면 `FAILED(PARTNER_NOT_READY)`(확정 때 보장했어야 한다 — 여기서 만들지 않는다 · 지급일에 검증 실패를 만들지 않기 위해).
2. 금액 가드 — `amount > 0`(기존). 포트원 수기 정산건은 0 · 음수를 받지 않는다.
3. **계좌 동기화** — `PayoutLine` 의 계좌(행 스냅샷 · 평문)와 파트너의 현재 계좌 지문이 다르면 `updatePlatformPartner(account)`. 실패 → `FAILED(ACCOUNT_SYNC_FAILED)`.
4. `transfer.createPlatformManualTransfer(test, partnerId, memo, amount, settlementTaxFreeAmount = null, settlementDate = today(yyyy-MM-dd), isForTest = test, userDefinedProperties, id = transferId, KRW)`.
   - 성공 · `PlatformTransferAlreadyExistsError` → `LineResult(REQUESTED, pgReference = null)` + `pg_transfer_id`.
   - `PlatformPartnerNotFoundError` → `FAILED(PARTNER_NOT_READY)` · `PlatformCurrencyNotSupportedError` · `InvalidRequestError` → `FAILED(REJECTED_BY_PG)`.
   - 통신 · 5xx · 타임아웃 → 예외를 **던진다**. `SettlementPayoutService.call` 이 전 행을 `REQUESTED` 로 두고(기존 동작), 결과 조회가 `getPlatformTransfer(transferId)` 로 「생겼는가」를 닫는다 — 정산건 id 가 결정적이라 재시도해도 중복이 없다.

`PayoutResult.lines` 는 지시한 행 전부를 돌려준다(기존 계약).

### 5-3. 실행 — 포트원 콘솔(런북 9-1) · Q1

우리가 할 수 있는 것은 **「D 일자 파트너 정산이 포트원에 전부 생겼다」** 를 확인하는 것까지다. 배치 끝에 `partnerSettlement.getPlatformPartnerSettlements(test, page, filter{settlementDates = [D], partnerIds})` 로 건수 · 합계를 대조해 운영자 알림(「D 일자 지급 N건 · 합계 ₩ — 포트원 콘솔에서 일괄 지급을 실행해 주세요」 · `SettlementNotifier.payoutReadyForExecution` 신규 훅)을 보낸다. 대조가 어긋나면(우리 REQUESTED 행 수 ≠ 포트원 정산건 수) 알림 문구에 차이를 적는다.

Q1 의 답이 ① 실행 API 제공 → 이 단계를 어댑터의 `execute(settlementDate)` 호출로 대체 ② 정산일 자동 지급 옵션 → 콘솔 설정 1회로 대체 ③ 둘 다 없음 → 런북 유지(또는 11절 Q1-b `DIRECT` 대안).

### 5-4. 결과 조회 — `SettlementPayoutResultScheduler`(30분 · `PG*` 모드만)

`REQUESTED` 행(`pg_transfer_id` 있음)을 정산 단위로 모아:

1. `transfer.getPlatformTransfer(transferId, test)` → `PlatformManualTransfer.status · payoutId`.
   - `payoutId == null`(아직 지급 전) → 그대로. 다만 **D+1 영업일 10:00 까지도** null 이면 운영자 알림 재발송(「지급 미실행」 · 9-2).
2. `payoutId` 있음 → `payout.getPlatformPayouts(test, …, filter{payoutIds})` → `PlatformPayout.status · failReason · amount`.
3. 매핑:

| 포트원 `PlatformPayout.status` / 파트너 정산 상태 | 우리 `settlement_payout` | 처리 |
| --- | --- | --- |
| 지급 완료(파트너 정산 `PAID_OUT` · 지급 `CONFIRMED`/완료 계열) | `PAID` · `pg_payout_id = pg_reference = payoutId` · `paid_at` | `markPaid` · 이력 `PAYOUT_PAID(PG)` · 재파생(기존 `applyResults` 의 PAID 분기 재사용) |
| 실패(`PAYOUT_FAILED` · 지급 실패 계열) | `FAILED` · `fail_code = classify(failReason)` · `fail_reason = failReason` | `markFailed` · 이력 · 운영자 알림 · 정산 `PAYOUT_FAILED` → M3 |
| 취소(`CANCELLED` — 운영자가 콘솔에서 지급을 취소) | `FAILED(CANCELLED_AT_PG)` | 같은 경로 — 재분배로 다시 올린다 |
| 보류(`PAYOUT_WITHHELD`) | `REQUESTED` 유지 · 이력 `PAYOUT_WITHHELD_AT_PG` 1회 | 운영자 알림 — 포트원 콘솔에서 사유 확인 |
| 진행(`PAYOUT_SCHEDULED · PAYOUT_PREPARED · IN_PAYOUT` · 지급 `PREPARED`) | `REQUESTED` 유지 | — |

`amount` 가 우리 행 금액과 다르면 **PAID 로 닫지 않고** `fail_code = AMOUNT_MISMATCH` 이력 + 운영자 알림(수기 정산건은 금액을 그대로 쓰므로 일어나면 설정 — `deductWht` — 이 틀린 것이다 · 0-4).

지급 상태 문자열의 전체 목록은 문서에 `CONFIRMED · PREPARED · CANCELLED · …` 까지만 공개돼 있다. 어댑터는 **알려진 값만 매핑**하고 모르는 값은 `REQUESTED` 유지 + `WARN` 로그 — 테스트 모드에서 실제 값을 받아 표를 채운다(10절 단계 2).

### 5-5. 실패 코드 분류 — `fail_code`

| `fail_code` | 뜻 | 재분배(M3) 계좌 출처 권고 |
| --- | --- | --- |
| `ACCOUNT_MISSING` | 등록 계좌 없음(기존) | 회원 정보 등록 뒤 `CURRENT_PROFILE` |
| `ACCOUNT_HOLDER_MISMATCH` | 예금주 불일치(파트너 등록 · 포트원 `failReason` 「예금주」 포함) | `CURRENT_PROFILE`(계좌 변경 뒤) |
| `PARTNER_NOT_READY` | 파트너 미등록 · 심사 중 · 거절 | 운영자가 포트원 콘솔 확인 |
| `ACCOUNT_SYNC_FAILED` | 지시 직전 계좌 갱신 실패 | `PREVIOUS` 재시도 |
| `COMPANY_NOT_IN_BUSINESS` | 사업자 휴 · 폐업 | 브랜드 기본정보 확인 |
| `UNSUPPORTED_BANK` | 포트원 미지원 은행 | 계좌 변경 |
| `REJECTED_BY_PG` | 포트원 4xx(그 밖) | 원문 확인 |
| `CANCELLED_AT_PG` | 콘솔에서 지급 취소 | 재지시 |
| `AMOUNT_MISMATCH` | 지급액 ≠ 행 금액 | 설정 확인(0-4) — 재분배 금지 |
| `BANK_REJECTED` | 은행 거절(계좌 해지 · 한도 등 — `failReason` 분류) | 계좌 변경 |

### 5-6. 재분배(M3)와의 연결

`AdminSettlementCommandService.redistribute` 는 `attempt + 1` · 계좌 재스냅샷 · `SCHEDULED(오늘)` 뒤 즉시 `distribute` 를 부른다(기존). 어댑터에서는 **새 정산건 id**(`…-{attempt}`)가 되고, 계좌 출처가 `CURRENT_PROFILE` 이면 5-2 ③ 이 파트너 계좌를 갱신한 뒤 올린다. 포트원 쪽의 실패한 지급 · 정산건은 그대로 남는다(콘솔 이력) — 우리가 지우지 않는다.

재분배 상한(3회) 초과 뒤 「수동 이체 절차」(44 어드민 13절 A-7)는 이 연동으로도 자동화되지 않는다 — Q1-b 의 `DIRECT`(직접 송금 뒤 `complete-payout`) 경로가 그 자리를 채울 수 있어 함께 확인한다.

## 6. 어댑터 · 설정 · 기동 검증

### 6-1. 포트 확장 — `SettlementPayoutGateway`

```java
public interface SettlementPayoutGateway {
    PayoutResult distribute(PayoutCommand command);                       // 기존
    /** REQUESTED 행의 결과 — PG 가 비동기인 모드만 구현. SIMULATED 는 빈 결과. */
    default List<LineResult> lookup(List<PayoutLookup> lookups) { return List.of(); }
    record PayoutLookup(Long payoutId, String pgTransferId, long amount) {}
    // PayoutCommand · PayoutLine · PayoutResult · LineResult · Outcome 그대로
}
```

`PayoutLine` 에 **수취자 식별**이 없다(계좌 · 금액만). 파트너 id 산출에 `marketId · creatorId` 가 필요하므로 `PayoutLine` 에 `Long payeeRefId`(BRAND = marketId · CREATOR = creatorId · PLATFORM = null) 를 **추가**한다 — 기존 호출처는 `SettlementPayoutTransitions.claim` 한 곳.

### 6-2. 구현 — `global.payment.settlement.portone`

| 클래스 | 역할 |
| --- | --- |
| `PortOneSettlementPayoutGateway implements SettlementPayoutGateway` | 5-2 · 5-4. `PlatformClient` 보유. `@PreDestroy close()` |
| `PortOnePlatformClientFactory` | `PlatformClient(apiSecret, baseUrl, storeId)` 1개 — 결제 `PaymentClient` 와 **별 인스턴스**(SDK 가 클라이언트별 커넥션) |
| `PortOnePartnerRegistrar` | 4-2(파트너 생성 · 갱신 · 계좌 · 사업자 검증). `SettlementPartnerSyncService`(도메인)가 이 **포트 `SettlementPartnerGateway`** 를 통해 부른다 — 도메인이 SDK 를 모르게 |
| `PortOneBanks` | 4-5 |

### 6-4. 기동 검증 — `SettlementPayoutGatewayConfig` 개정

| 모드 | 빈 | 기동 조건 |
| --- | --- | --- |
| `SIMULATED` | `SimulatedSettlementPayoutGateway` | 런칭 게이트 켜진 `prod` 면 **실패** · 게이트 꺼진 `prod` 는 경고만(9-4) |

## 9. 운영 런북(Q1 결론 전)

### 9-1. 지급일(영업일) 절차 — 운영팀

1. 10:00 배치 뒤 알림 「D 일자 지급 N건 · 합계 ₩ · 포트원 정산건 N건 일치」를 받는다. **불일치면 개발팀 호출**(배치가 못 올린 행 = `REQUESTED` 인데 `pg_transfer_id` 없음).
2. 포트원 콘솔 → 파트너 정산 → 정산일 D 필터 → 전체 선택 → **일괄 지급 실행**(지급대행 · 출금 계좌 잔액 확인 — 부족하면 충전 · Q3).
3. 30분 내 우리 어드민 07a 「분배 실패」 탭 · 07b 레일을 확인한다. 실패 건은 M3 재분배(사유별 계좌 출처 5-5).

### 9-2. 미실행 감지

결과 조회 배치가 D+1 영업일 10:00 에도 `payoutId == null` 인 `REQUESTED` 행을 보면 「지급 미실행」 알림을 다시 보낸다(이후 매 영업일 10:00). 우리 행은 `REQUESTED` 로 남고 수취자 화면은 「지급 예정」이다(44 파트너 설계서 — `REQUESTED` 라벨 = `SCHEDULED`).

### 9-3. 대사

월 1회 — 포트원 `GET /platform/payouts(createdAt 범위)` 합계 vs 우리 `settlement_payout(PAID · paid_at 범위)` 합계. 어긋나면 건별 `pg_payout_id` 로 좁힌다. `GET /platform/account-transfers` 로 출금 계좌 흐름을 교차 확인한다.

### 9-4. 런칭 게이트 — 개발 단계 `prod` 와 실제 운영의 구분(2026-10-11 결정)

지금 `prod` 프로필로 도는 배포 서버는 **개발 단계**다(결제도 테스트 PG). 그래서 「`prod` = 실제 돈」 가정의 기동 검증 둘(사업자 정보 · `PG` 모드 강제)을 **`settlement.launch-gate-enabled`(기본 false)** 뒤로 옮겼다. 게이트를 끈 `prod` 는 더미 사업자 정보 · `SIMULATED`/`PG_TEST` 로 뜨고 기동 로그에 경고를 남긴다.

| 서버 | 환경변수 | 동작 |
| --- | --- | --- |
| 지금 배포 서버(개발 단계 `prod`) | 없음 | `SIMULATED` — 지급 완료는 기록만, 돈은 안 나감. 기동 경고 2줄 |
| 포트원 테스트 상점 활성화 뒤 | `SETTLEMENT_PAYOUT_MODE=PG_TEST` | 포트원 테스트 모드 연동(8-2 T1 ~ T8) |
| **실제 운영 서버** | `SETTLEMENT_LAUNCH_GATE_ENABLED=true` · `SETTLEMENT_PLATFORM_*`(실제 사업자 정보) · `SETTLEMENT_PAYOUT_MODE=PG` · `PORTONE_*` 운영 키 | 셋 중 하나라도 빠지면 **기동 실패** — 가짜 지급이 운영에 새지 않는다 |

**오픈 체크리스트(운영 서버에만)**: ① `SETTLEMENT_LAUNCH_GATE_ENABLED=true` ② 사업자 정보 5종 ③ `SETTLEMENT_PAYOUT_MODE=PG` ④ 콘솔 `deductWht=false`(2-3) ⑤ 기동 로그에 「정산 런칭 게이트 꺼짐」 경고가 **없는지** 확인.
