## 0. 이 계획의 전제 — 필드 권한 3분류가 곧 API 경계다

브랜드의 사업자·정산·담당자 정보는 지금 가입 시점에 `SELLER`/`MARKET`에 한 번 적재된 뒤 **읽는 API조차 없다.** GNB #9 화면을 붙이려면 조회·수정 API 묶음이 통째로 필요하고, 그중 신원정보·정산 계좌는 브랜드가 직접 못 고치므로 **`brand_change_request` 레코드와 어드민 심사 플로우가 함께** 있어야 한다.

§15-1의 3분류를 그대로 백엔드 권한 규칙으로 옮긴다. 분류가 다르면 엔드포인트가 다르다.

| 분류 | 처리 | 백엔드 |
| --- | --- | --- |
| ① 직접 수정 | 브랜드가 고쳐 `[저장]` | `PATCH`/`PUT /v1/seller/basic-info/*` — 즉시 반영 |
| ② 변경 요청 | 운영자 검토 후 반영 | `POST /v1/seller/change-requests` → 어드민 승인 시에만 원본 갱신 |
| ③ 변경 불가 | 어떤 경로로도 변경 없음 | **enum에 존재하지 않는다** — 요청 자체가 400 |

③을 "검증으로 막는다"가 아니라 "타입에 존재하지 않게 한다"로 구현하는 것이 핵심이다. 사업자등록번호는 `ChangeRequestField` enum에 없으므로 어떤 경로로도 요청 레코드에 실리지 않는다.

### 착수 전 확정 사항

| # | 항목 | 결정 |
| --- | --- | --- |
| 1 | 로그인 이메일 월 1회 기준(§15-9 미결 3) | **1개월 롤링** — `emailChangedAt.plusMonths(1)`. 시안 `08.03 → 09.03` 표기와 일치 |
| 2 | 변경 요청 취소 시 어드민 목록(§15-9 미결 6) | **`CANCELED` 상태로 행 보존** — '전체' 탭에서만 노출. §15-3 감사 기록 요건 충족 |
| 3 | SLA 초과 배지 기준 | **48시간** |
| 4 | 증빙 파일 업로드 | **기존 multipart 업로드 재사용** — `ImageService`에 `CHANGE_REQUEST_DOCUMENT` 타입 추가 |

### 1-1. `brand_change_request` — M1·M2 공통 레코드

§15-6 "레코드는 `{항목, 현재값, 요청값}` 배열 1개로 두 유형 모두 담는다"를 그대로 구현한다. **유형별 테이블을 나누지 않는다** — 어드민 목록·상세·승인·반려가 두 유형에서 완전히 같은 코드로 돌아간다.

| 컬럼 | 타입 | 비고 |
| --- | --- | --- |
| `request_id` | BIGINT PK | |
| `request_code` | VARCHAR(20) UNIQUE | `CHG-YYYY-NNNN` — 연도별 채번(§16-2 표시용) |
| `market_id` | BIGINT FK → MARKET | 브랜드 식별. `Seller`는 `market.getSeller()`로 파생 |
| `type` | VARCHAR(20) | `BUSINESS_INFO` / `SETTLEMENT_ACCOUNT` |
| `status` | VARCHAR(20) | `PENDING` / `APPROVED` / `REJECTED` / `CANCELED` |
| `pending_key` | BIGINT GENERATED STORED | `IF(status='PENDING', 1, NULL)` — 아래 유니크 제약용 |
| `reason` | VARCHAR(500) NULL | 브랜드 작성 변경 사유. M1 필수 / M2 선택 |
| `requester_name` | VARCHAR(64) | 요청 시점 `Seller.name` **스냅샷** |
| `evidence_file_url` | VARCHAR(1024) | 증빙 1개 필수(두 유형 모두) |
| `evidence_file_name` | VARCHAR(255) | 어드민 파일칩 표시용 |
| `evidence_file_size` | BIGINT | 〃 (`· 1.2MB`) |
| `requested_at` | DATETIME | 경과·정렬 기준 |
| `processed_at` | DATETIME NULL | 승인·반려·취소 시각 |
| `processed_by` | BIGINT NULL | 운영자 `SELLER_ID` — **감사 기록**(§15-3) |
| `reject_reason` | VARCHAR(64) NULL | 정형 사유 enum name |
| `reject_reason_detail` | VARCHAR(500) NULL | 상세 사유(자유 입력) |
| `result_acknowledged_at` | DATETIME NULL | 브랜드가 배너 `[확인]`을 누른 시각 |
| `created_at` / `modified_at` | | `BaseTimeEntity` |

- **중복 요청 차단(§15-7)을 DB 제약 하나로 보장한다** — `UNIQUE (market_id, type, pending_key)`. MySQL/InnoDB는 유니크 인덱스에서 NULL을 서로 다른 값으로 취급하므로, `status != 'PENDING'`인 행은 `pending_key`가 NULL이 되어 몇 건이든 쌓이고 `PENDING`인 행만 (브랜드, 유형)당 1건으로 묶인다. `V90__create_connection.sql`이 `COALESCE` 생성 컬럼으로 같은 함정을 우회한 것과 동일한 기법이다.
- **재요청은 신규 행이다**(§16-6). 입점 심사(`SellerApplicationHistory`)처럼 한 행에 이력을 누적하지 않는다 — 요청 시점마다 값이 달라서 누적하면 증빙↔요청값 대응이 끊긴다.
- **처리 이력 테이블을 만들지 않는다.** §16-2 타임라인은 접수(`requested_at`) → 승인/반려/취소(`processed_at`, `processed_by`) 최대 2이벤트뿐이라 요청 행 자체에서 파생된다.

### 1-2. `brand_change_request_item` — {항목, 현재값, 요청값}

| 컬럼 | 타입 | 비고 |
| --- | --- | --- |
| `item_id` | BIGINT PK | |
| `request_id` | BIGINT FK | |

**`ChangeRequestRejectReason`** — §15-8·§16-5 목록. `Set<ChangeRequestType> supports` 필드로 유형별 노출을 가른다(`OTHER`만 양쪽 지원).

| 유형 | enum |
| --- | --- |
| BUSINESS_INFO (6종) | `EVIDENCE_MISSING` 증빙 서류 미첨부 · `EVIDENCE_VALUE_MISMATCH` 증빙 서류와 요청 값이 일치하지 않음 · `EVIDENCE_UNREADABLE` 서류 판독 불가(흐림·잘림) · `EVIDENCE_EXPIRED` 서류 유효기간 경과 · `REASON_INSUFFICIENT` 변경 사유 불충분 · `OTHER` 기타 |

## 2. 파트너센터 API — `/v1/seller/basic-info`

패키지 `showroomz.api.seller.basicinfo`. 인증은 `SecurityConfig`의 `/v1/seller/**`(SELLER·CREATOR) 규칙이 이미 적용되고, 현재 사용자는 `SellerThreadController.getCurrentSellerEmail()`과 동일하게 `UserPrincipal`에서 이메일을 꺼내 쓴다.

| # | 메서드 · 경로 | 내용 |
| --- | --- | --- |
| 1 | `GET /business` | 사업자 정보 탭 — 조회 전용 8필드 + tax 이메일 + 사이트 링크 + 심사 첨부 3종 URL + 현재 변경 요청 배너 |
| 2 | `PATCH /business` | 직접 수정 2필드 `{ taxEmail, brandSiteUrl }` |
| 3 | `GET /settlement` | 은행명 · **마스킹 계좌번호(뒤 6자리)** · 예금주 + 배너 |
| 4 | `GET /manager` | 담당자·CS 3필드 + 반품 수취 주소 4필드 |
| 5 | `PUT /manager` | 7필드 일괄 저장 |
| 6 | `GET /account` | 로그인 이메일 · `emailChangeable` · `nextEmailChangeableAt` |
| 7 | `PATCH /account/password` | `{ currentPassword, newPassword, newPasswordConfirm }` |
| 8 | `PATCH /account/email` | `{ currentPassword, newEmail }` |

> **응답 스키마는 부록 A에 필드 단위로 확정돼 있다.** 시안에 렌더링되는 값 하나하나를 어느 필드가 채우는지 대응시켰으므로, 구현 시 부록 A를 계약으로 삼는다.

### 필드 → 엔티티 매핑

| 화면 필드 | 저장 위치 |
| --- | --- |
| 판매 담당자 이름 / 연락처 | `Seller.name` / `Seller.phoneNumber` |
| 고객센터 전화번호 | `Market.csNumber` |
| 반품 수취 주소 4필드 | `Market.shippingRecipientName` / `shippingContact` / `shippingAddress` / `shippingDetailAddress` |
| tax 확인용 이메일 | `Seller.taxEmail` |
| 브랜드 사이트 링크 | `Market.brandSiteUrl` (신설) |
| 심사 첨부 3종 | `Seller.businessLicenseImageUrl` / `mailOrderRegImageUrl` / `bankbookImageUrl` — **조회만**(§15-1 ③) |

### 마스킹 — 패키지 위치로 규칙을 강제한다

`SettlementAccountMasker`를 `showroomz.api.seller.basicinfo` 패키지 **안에** 둔다. `global/utils`에 두지 않는 것이 요점이다: §16-7이 "두 화면의 마스킹을 공용 유틸로 묶지 않는다"를 명시했고, 패키지 위치로 그 규칙을 물리적으로 강제한다. **어드민 쪽에는 마스킹 코드가 아예 존재하지 않는다.**

### 검증 규칙 (§4·§6과 문자 단위 동일 — 신규 문구를 만들지 않는다)

| 필드 | 규칙 |
| --- | --- |
| tax 이메일 | 이메일 형식, 필수 |
| 브랜드 사이트 링크 | `http(s)://` 전체 주소, **null 허용**(미입력 시 소비자 앱이 버튼 비노출) |
| 판매 담당자 연락처 | `^010-\d{4}-\d{4}$` — **010 11자리 고정**(내부 관리용) |
| 수취인 연락처 | `^01(?:0\|1\|[6-9])-\d{3,4}-\d{4}$` — 10~11자리(구 통신사 번호 허용). 담당자 연락처와 **의도적으로 다른 규칙**(§15-4, 외부 노출용) |
| 고객센터 전화번호 | `'-'` 포함 8~12자리 |
| 비밀번호 | 기존 `SellerSignUpRequest`의 `^(?=.*[A-Za-z])(?=.*\d)(?=.*[@$!%*#?&])[A-Za-z\d@$!%*#?&]{8,16}$` 재사용 |
| 조회 전용(`disabled`) 필드 | **검증 대상이 아니다** — 요청 바디에 들어와도 무시 |

### 로그인 이메일 변경 (§15-5)

1. `currentPassword`를 `passwordEncoder.matches`로 검증 (실패 → `LOGIN_PASSWORD_MISMATCH`)
2. `emailChangedAt`이 있고 `now < emailChangedAt.plusMonths(1)`이면 `EMAIL_CHANGE_LIMIT_EXCEEDED` + `nextChangeableAt` 반환
3. 중복 검사는 **기존 `SellerRepository.existsByEmailAndStatusNotRejected`를 그대로 재사용** — §2-3 조회 범위(활성·심사대기만, 반려 제외)가 이미 그 쿼리에 들어 있다
4. `Seller.email` 갱신 + `emailChangedAt = now`
5. **구 이메일로 변경 통지 발송** — `MailService.sendLoginEmailChangedNotice(oldEmail, newEmail, changedAt)`. UI 없음, 계정 탈취 시 원 소유자가 인지하게 하는 BE 전용 안전장치
6. 이메일이 refresh token 키(`SellerRefreshToken.adminEmail`)이므로 **기존 리프레시 토큰을 삭제**한다 — 안 하면 구 이메일 키로 남아 토큰 갱신이 조용히 깨진다

## 3. 변경 요청 API (브랜드) — `/v1/seller/change-requests`

| # | 메서드 · 경로 | 내용 |
| --- | --- | --- |
| 1 | `POST /` | M1·M2 공통 생성 |
| 2 | `GET /latest?type=` | 배너 상태(검토 중 / 승인 / 반려 + 사유) |
| 3 | `POST /{id}/cancel` | 검토 중 철회 → `CANCELED` |
| 4 | `POST /{id}/acknowledge` | 배너 `[확인]` → `result_acknowledged_at` |
| 5 | `GET /fields?type=` | **M1·M2 모달 진입용** — `[{fieldKey, label, currentValue}]` |

5번을 두는 이유 — 시안 M1은 체크박스를 켤 때마다 `현재 · 홍길동`을 그 자리에 그린다. 항목 목록·라벨·현재값의 SoT는 서버 `ChangeRequestField` enum이므로, FE가 6종 라벨과 필드 순서를 하드코딩하면 enum이 바뀔 때 조용히 어긋난다. 모달이 필요한 것만 한 번에 내려준다.

**생성 요청 바디**

```
{ type, items: [{ fieldKey, requestedValue }], reason,
  evidenceFileUrl, evidenceFileName, evidenceFileSize }
```

**생성 시 서버 검증**

- 동일 (브랜드, 유형)에 `PENDING` 존재 → `CHANGE_REQUEST_ALREADY_PENDING` (DB 유니크 위반도 같은 코드로 매핑)
- `fieldKey`가 요청 유형에 속하지 않으면 400. 사업자등록번호는 enum에 없으므로 자동 400
- `items` 최소 1개. M2는 은행·계좌번호·예금주 **3개 고정**
- `reason` — M1 필수, M2 선택, 최대 500자
- 증빙 파일 3필드 **필수**(두 유형 모두, §15-6)
- 계좌번호 `^\d{10,16}$` — **하이픈 없이 숫자만**(§15-3 / 포트원 계좌실명조회 요건). 가입 화면의 `^[0-9-]+$`보다 **의도적으로 엄격하다**
- `current_value` 스냅샷 후 **요청값이 현재값과 같은 항목은 400** — 대조표에 "변경 없음"으로 나올 행을 레코드에 실을 이유가 없다(§15-6 "체크 해제 시 입력해둔 값도 함께 폐기"의 서버 측 대응)
- `request_code` 채번 — `CHG-{YYYY}-{4자리 연내 순번}`

**증빙 업로드** — `ImageType`에 `CHANGE_REQUEST_DOCUMENT` 추가, `SELLER_ALLOWED_TYPES`에 포함, `ImageService.getAllowedExtensions`의 문서 분기(`SIGNUP_DOCUMENT`/`CREATOR_DOCUMENT`)에 합류시킨다. 브랜드는 기존 `POST /v1/seller/images`로 올리고 반환된 URL을 생성 요청에 싣는다.

**배너 상태 판정 (§15-7)** — 브랜드에 보여줄 "현재 요청"은 (브랜드, 유형)별 최신 1건 중 `status = PENDING` 이거나, `status ∈ {APPROVED, REJECTED}` **AND** `result_acknowledged_at IS NULL`인 것. `[확인]`을 누르면 배너가 사라지고 상태가 `none`으로 복귀하며 `[변경 요청]` 버튼이 다시 열린다. **별도 `[다시 요청]` 경로도, 재요청 대기기간도 없다.**

## 4. 어드민 API — `/v1/admin/change-requests`

패키지 `showroomz.api.admin.changerequest`. `SecurityConfig`의 `/v1/admin/**` → `ADMIN` 규칙이 그대로 적용된다.

| # | 메서드 · 경로 | 내용 |
| --- | --- | --- |
| 1 | `GET /?status=&keyword=&page=&size=` | 목록 + 탭별 건수 |
| 2 | `GET /summary` | GNB 배지용 검토 대기 건수(§16-0 상위 '입점 관리' 합산에 사용) |
| 3 | `GET /{id}?status=` | 상세 — 대조표·증빙·메타·이력·이전/다음 |
| 4 | `POST /{id}/approve` | 승인 |
| 5 | `POST /{id}/reject` | 반려 `{ reasonType, reasonDetail }` |
| 6 | `GET /reject-reasons?type=` | 반려 모달 드롭다운 — `[{code, label, detailRequired}]` |

6번을 두는 이유 — 정형 사유 목록이 유형별로 6종/5종이고 "기타일 때만 상세 사유 필수"라는 조건부 규칙이 붙는다(§16-5). `detailRequired`를 서버가 내려주면 FE가 `code === 'OTHER'`를 하드코딩하지 않아도 되고, 사유 문구가 **가공 없이 브랜드에게 전달되는 값**이라 문구의 SoT도 서버 enum 한 곳으로 모인다.

### 목록 — 사용자 정렬 셀렉트를 두지 않는다(§16-1)

시안 C1의 행 순서를 그대로 재현하는 고정 정렬이다.

```sql
ORDER BY (status = 'PENDING') DESC,
         CASE WHEN status = 'PENDING' THEN requested_at END ASC,
         requested_at DESC
```

검토 대기가 항상 위, 그 안에서 경과 내림차순(= 요청일시 오름차순)이라 SLA 초과 건이 최상단에 온다. 처리 완료 건은 경과가 `—`이므로 최신순으로 내려간다.

- `status` 탭 = `PENDING` / `APPROVED` / `REJECTED` / `ALL`. **`CANCELED`는 `ALL`에서만 보인다**(확정 2)
- 탭 배지 건수는 `AdminService.buildApplicationStatusCounts` 패턴(group-by count 1회)을 따른다 — 탭 수만큼 count 쿼리를 날리지 않는다
- 행 응답: `brandName`(= `Market.marketName`) · `type` · `requestedAt` · `processedAt` · `elapsedText` · `status` · `slaExceeded`
- 경과 표기는 `RelativeTimeFormatter`가 아니라 **`2일 3h` / `18h` 형태 전용 포매터**가 필요하다(시안 표기). `slaExceeded = PENDING && 경과 > 48h`
- 빈 상태(§16-1)는 `content: []` + `pageInfo.totalElements: 0`으로 프런트가 판단
- **의도적으로 만들지 않는 것**: 변경 항목 컬럼 · 증빙 컬럼 · CSV 내보내기 · 요청 유형 필터 · 표시 건수 셀렉트

### 상세 (§16-2)

- 대조표는 **변경 없는 행까지 전부** 내려준다. 유형별 전체 항목을 순서대로 만들고 `items`에 있는 것만 `changed: true` + `requestedValue`를 채운다
- **사업자등록번호 행은 항상 포함**하되 `locked: true`로 내려 프런트가 "변경 요청 불가" 상수를 표시한다(§16-2). 번호가 바뀐 경우는 **신규 입점 심사** 대상이다
- **계좌번호는 전체 노출**(§16-7) — 마스킹하지 않는다. 목적은 통장 사본 대조 하나다
- 정산 계좌 요청은 `holderMismatch` 플래그를 함께 계산한다 — 요청 예금주 vs `Seller.companyName`. 시안 C4의 "오지급 위험" 경고와 §16-3 미리보기 대조 패널이 이 값을 쓴다
- 이전/다음은 **현재 탭의 목록 순서**를 따른다(§16-2) → `status` 파라미터를 상세에서도 받아 같은 정렬로 앞뒤 id를 계산한다
- 요청자는 `requester_name` 스냅샷을 쓴다 — 담당자 이름은 직접 수정 가능 필드라 실시간 조회하면 과거 요청의 요청자가 바뀌어 보인다

### 승인 (§16-4)

1. `PENDING`이 아니면 `CHANGE_REQUEST_NOT_PENDING`
2. `ChangeRequestApplier`가 `field_key`별로 `Seller`/`Market`에 값을 반영 — **전체 승인 또는 전체 반려뿐, 부분 승인은 없다**
3. `MARKET_NAME`은 승인 시점에 **중복을 재검사**한다(`marketRepository.existsByMarketNameAndSellerStatusNotRejected`). 접수와 승인 사이에 다른 브랜드가 같은 이름을 선점할 수 있고, 그때 조용히 덮어쓰면 유니크 제약에서 터진다 → `DUPLICATE_MARKET_NAME`으로 운영자에게 되돌린다
4. `BANK_CODE`는 `bankRepository.findById` → `Bank.getName()`을 저장(가입 로직과 동일 경로)
5. `status=APPROVED`, `processed_at`, `processed_by`(운영자 `SELLER_ID`) 기록 — 감사 기록
6. `MailService.sendChangeRequestApprovedEmail` 발송. 수신은 **로그인 이메일**(`Seller.email`), tax 이메일이 아니다

### 반려 (§16-5)

- `reasonType` 필수 + 요청 유형과 맞는지 검증(`supports(type)`)
- `reasonType == OTHER`일 때만 `reasonDetail` 필수 — 그 외엔 선택, 최대 500자
- 선택 문구 + 상세 사유가 **가공 없이** 브랜드 배너와 통지 메일에 실린다
- `MailService.sendChangeRequestRejectedEmail` 발송

### 메일

`MailService`에 3개 메서드를 추가한다. 기존 `sendApprovalEmail`/`sendRejectionEmail`(입점 심사)과 같은 스타일·서명(`OPS_TEAM`, `SELLER_MAIL_DATETIME`)을 쓰되 **별도 메서드로 둔다**: 변경 요청 승인 / 변경 요청 반려 / 로그인 이메일 변경 통지.

# 부록 A. 응답 스키마 — 시안 기준 확정

시안(`ui-partner-06-basic-info.html` rev.8 · `ui-admin-05-change-requests.html` rev.6)에 실제로 그려지는 값을 기준으로 확정한 계약이다. 각 필드 옆의 `←`는 그 값을 렌더링하는 시안 위치다.

## A-0. 공통 규약

| 항목 | 규약 |
| --- | --- |
| 날짜·시각 | ISO-8601 `2026-08-06T14:20:00` 으로 내린다. 시안의 `2026.08.06 14:20` / `2026.09.03` 표기 변환은 FE 책임 |
| enum | **코드로 내린다**(`BUSINESS_INFO`, `PENDING`). 라벨은 FE가 매핑 |
| 예외 — 서버가 문자열로 내리는 것 | ① **반려 정형 사유**(§16-5 "가공 없이 그대로 전달") ② **변경 항목 라벨**(목록의 SoT가 서버 enum) — 이 둘만 서버가 완성된 한글 문구를 내린다 |

- `brandName`·`brandStatus` ← 상단 브랜드 칩 `○○ 브랜드 [활성]`. `Market.marketName` / `Market.status`
- **`businessAddress`는 `Seller.businessAddress` + `detailAddress`를 결합한 단일 문자열이다** ← 1-A가 `서울특별시 강남구 테헤란로 123, 4층 401호` 한 줄로 그린다. M1 모달의 사업장 주소도 **자유 입력 단일 필드**(카카오 주소 API가 아니다 — 시안 M1은 `<input type="text" placeholder="변경할 값을 입력하세요">`)이므로 요청·대조·승인 전 구간에서 단일 문자열로 다룬다. **승인 시 요청값 전체를 `businessAddress`에 넣고 `detailAddress`는 `null`로 정규화한다** — 결합 규칙이 그대로라 표시 결과는 동일하다
- `reviewDocuments`의 `label`은 **서류 종류 상수**다 ← 1-A 뱃지 `사업자등록증.jpg`. `Seller.*ImageUrl`은 `ImageService.generateFileName`이 만든 UUID 파일명이라 **원본 파일명이 남아 있지 않다.** FE는 `label + '.' + extension`으로 뱃지를 조립한다. (변경 요청 증빙은 이와 달리 원본 파일명을 컬럼에 저장하므로 어드민 파일칩에 그대로 쓴다)
- `changeRequest`는 A-5. `null`이면 배너 없음 + `[변경 요청]` 활성

## A-7. `GET /v1/admin/change-requests` ← C1·C2

```json
{
  "content": [
    {
      "requestId": 81,
      "requestCode": "CHG-2026-0081",
      "brandName": "○○코스메틱",
      "type": "BUSINESS_INFO",

```

- 상태 배지는 `status` + `slaExceeded` 조합으로 FE가 그린다 — `PENDING && slaExceeded` → `SLA 초과`(경고색), `PENDING` → `검토 대기`(정보색), 나머지는 상태 그대로 ← C1 4개 행이 이 규칙을 다 보여준다

- 빈 상태(C2)는 `content: []` + `totalElements: 0` — 안내 문구는 FE 상수
