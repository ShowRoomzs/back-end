## 15. 파트너센터 기본정보 관리 — [v0.23 신설]

대상 화면: `ui-partner-06-basic-info.html` (**rev.8**). 근거 와이어프레임 `wf-partner-08-기본정보관리`. GNB #9. 컴포넌트 출처는 §4(가입 — 폼 검증·업로드·비밀번호) · §6(온보딩 — 반품 수취 주소) · §11(카드·행) · §13(모달 셸).

**성격** — 조회 중심 화면이다. 브랜드가 스스로 바꿀 수 있는 값과 운영자 검토를 거쳐야 하는 값이 섞여 있고, **그 경계가 이 섹션의 핵심**이다. §16(어드민 변경 요청)과 한 쌍으로 동작한다.

**스코프 한정** — 서브탭 6종 중 **4종만** 제작. `배송·반품 정책`·`택배 연동`은 법률 검토 이후 제작하며 서브탭 위치만 확보하고 "준비중" 비활성으로 둔다. **브랜드 탈퇴는 카드 자체를 넣지 않는다**(법률 검토 후 별도 화면 신설).

### 15-1. 필드 수정 권한 3분류 — `FE`·`BE`

이 화면의 모든 필드는 아래 3가지 중 하나에 속한다. **분류가 곧 백엔드 권한 규칙**이다.

| 분류 | 처리 | 대상 필드 |
| --- | --- | --- |
| ① 직접 수정 | 브랜드가 고쳐 `[저장]` — 즉시 반영 | tax 확인용 이메일 · 브랜드 사이트 링크 · 담당자·CS 3필드 · 반품 수취 주소 4필드 · 비밀번호 · 로그인 이메일 |
| ② 변경 요청 | `[변경 요청]` → 운영자 검토(§16) → 승인 시 반영 | 사업자 유형 · 브랜드명 · 대표자명 · 사업자등록증 상호 · 업태 · 사업장 주소 · 통신판매업 신고번호 · **정산 계좌 3필드** |
| ③ 변경 불가 | 어떤 경로로도 변경되지 않음 | **사업자등록번호** · 심사 첨부 파일 3종(조회만) |

**사업자등록번호를 ③으로 둔 이유 — 재논의 금지**
번호가 바뀌면 법적으로 다른 사업자이므로, 정보 변경이 아니라 **신규 입점 신청** 대상이다(§3 반려·폐기 구조와 동일한 판단). 변경 항목 체크박스에 남겨두면 브랜드가 체크할 수 있고 운영자는 매번 반려해야 한다. 체크박스 목록 7종 → **6종**으로 확정.

**검사 시점** — §4-1 원칙 그대로. blur 이후 → 이후 입력 변경 시 즉시 재검사. **조회 전용(`disabled`) 필드는 검증 대상이 아니다.** 플레이스홀더·검증 규칙·오류 문구는 §4(가입)·§6(온보딩)과 **문자 단위로 동일**하게 맞춘다 — 같은 필드가 3개 화면에 등장하므로 문구를 따로 관리하지 않는다.

### 15-4. 담당자·CS — `FE`·`BE`

담당자·CS 3필드는 직접 수정 후 `[저장]`. 반품 수취 주소 4필드(수취인 이름 · 수취인 연락처 · 주소 · 상세 주소)는 **§6-2 컴포넌트·플레이스홀더·오류 문구를 그대로 재사용**한다.

| 항목 | 규칙 |
| --- | --- |
| 수취인 연락처 | `'-'` 포함 **10~11자리**(구 통신사 번호 허용) — §6-3 근거 그대로 |
| 판매 담당자 연락처 | **010 11자리 고정** — 수취인 연락처와 **의도적으로 다른 규칙**. 전자는 택배기사 등 외부 노출용, 후자는 내부 관리용 |
| 주소 입력창 | **카카오 주소 API** 연동. `readonly`로 직접 입력 불가, 클릭 시 검색창 오픈 |
| 상세 주소 | **주소 검색 여부와 무관하게 항상 입력 가능** — rev.2~3의 "검색 완료 전 비활성" 규칙은 **폐기** |

### 15-5. 계정 — 비밀번호 · 로그인 이메일 — `FE`·`BE`

| 항목 | 규칙 |
| --- | --- |
| 비밀번호 변경 | 현재 · 새 · **재입력 3필드**. 규칙·플레이스홀더·오류 문구·표시 토글은 §4-3 Step1과 동일. 재입력 필드는 오타로 인한 로그인 불가를 막기 위한 것 |
| 로그인 이메일 변경 | **계정 탭에서 브랜드가 직접 변경**한다. 방식 = **현재 비밀번호 확인 → 즉시 변경 확정**. 인증 링크 방식은 rev.3에서 검토했으나 **폐기** |
| 변경 횟수 제한 | **월 1회.** 소진 시 `[변경]` 비활성 + 다음 변경 가능일 안내 |
| 구 이메일 통지 | 변경 완료 시 구 이메일로 변경 통지 발송 — **BE 처리, UI 없음**. 계정 탈취 시 원 소유자가 인지할 수 있게 하는 안전장치 |
| 중복 검사 | 새 이메일은 §2-2 이메일 중복 확인 대상. 조회 범위(활성·심사대기만, 반려·폐기 제외)도 §2-3 동일 |
| 브랜드 탈퇴 | **이번 범위 제외** — 카드 자체를 넣지 않는다 |

**"변경 불가·운영자 문의"를 폐기한 이유** — 담당자 퇴사나 회사 도메인 변경 시 브랜드가 자기 계정 통제권을 잃는다. 운영자 문의 경로만 남기면 그 자체가 CS 부하이자 계정 탈취 리스크가 된다. 대신 월 1회 제한 + 구 이메일 통지로 남용을 막는다.

### 15-6. 변경 요청 — 데이터 모델 · 모달 구조 — `FE`·`BE`

M1(사업자 정보)·M2(정산 계좌) 두 유형이며, **백엔드 레코드는 하나의 구조를 공유**한다.

| 항목 | 내용 |
| --- | --- |
| 레코드 | `brand_change_request` — `{항목, 현재값, 요청값}` **배열 1개**로 두 유형 모두 담는다 |
| M1 입력 | 변경 항목 체크(6종) → **체크한 항목마다 현재 값 표시 + 바꿀 값 입력칸 동적 생성** → 변경 사유(필수) → **증빙 파일(필수)** |
| M2 입력 | 은행 · 계좌번호 · 예금주 → **통장 사본(필수)** |
| 공통 완료 모달 | M3 — 제출 후 공통 노출. 확인 시 해당 카드가 검토 중 상태로 전환 |
| 체크 해제 시 | 입력해둔 "바꿀 값"도 함께 폐기한다(잔류 값이 요청 레코드에 실리지 않게) |

**M1을 "새 값 입력형"으로 바꾼 이유 (rev.7)**
이전 M1은 변경 항목 + 사유만 받아 **운영자가 대조할 "요청 값"이 존재하지 않았다** — §16 대조표의 데이터 소스 부재. 운영자가 서류를 보고 직접 타이핑하는 방식은 **오타와 책임 소재** 문제를 만든다. 브랜드가 요청한 값이 레코드에 남으면 분쟁 시 책임이 명확하다.

**증빙 첨부를 선택 → 필수로 바꾼 이유** — 증빙 없는 신원정보 변경은 승인 근거가 없다. M2 통장 사본과 규칙을 통일했다.

### 15-7. 변경 요청 결과 — 배너 3단계 — `FE`·`BE`

| 상태 | 색 | 브랜드 화면 | 재요청 버튼 |
| --- | --- | --- | --- |
| 검토 중 | **정보색** | 접수 안내 + 요청 취소 가능 | 비활성 |
| 승인 | **성공색** | 값이 이미 반영된 상태 | (배너 닫은 뒤) 활성 |
| 반려 | **위험색** | 반려 사유 노출 | (배너 닫은 뒤) 활성 |

**§9 상태색 4원칙 매핑** — 검토 중을 **경고색이 아니라 정보색**으로 둔 것이 핵심이다. 브랜드 조치가 필요 없는 정상 대기이므로 원칙 ①(운영자/당사자 조치가 필요한 상태만 경고·위험색)에 따른다. 반려는 브랜드가 서류를 고쳐 다시 요청해야 하므로 **조치 필요 = 위험색**이다.

| 항목 | 규칙 |
| --- | --- |
| 배너 소멸 | 승인·반려 모두 `[확인]`으로 사라지는 **1회성 알림**. 상태는 `none`으로 복귀 |
| 재요청 경로 | **별도 `[다시 요청]` 버튼 없음** — 배너를 닫은 뒤 원래의 `[변경 요청]` 버튼을 다시 쓴다 |
| 재요청 대기기간 | **없음** — 브랜드 재등록 즉시 허용(§3) 규칙과 동일. 인플루언서 14일 쿨다운(§7-3·§9-5)과는 다르다 |
| 중복 요청 차단 | 검토 중에는 동일 카드의 재요청 버튼 비활성 |

## 16. 어드민 변경 요청 (사업자 정보 · 정산 계좌) — [v0.23 신설]

대상 화면: `ui-admin-05-change-requests.html` (**rev.6**). **[v0.24] 파일명 재번호** — 구 `ui-admin-04-change-requests.html`. §12(`ui-admin-04-product-management.html`)와 번호가 겹쳐 `05`로 변경했다(화면 내용·rev 변경 없음). §15와 **한 쌍**이며, 같은 요청 레코드를 처리하는 쪽 화면이다. 셸·테이블·모달·토스트는 §5(`ui-admin-02-onboarding-brand.html`) 컴포넌트를 그대로 재사용하고 도메인만 교체했다.

**성격** — 입점 심사(§5·§9)와 **행위가 동일**하다: 서류 대조 → 승인/반려. 다른 점은 대상이 신규 계정이 아니라 **이미 활성인 브랜드의 특정 필드**라는 것뿐이다.

### 16-0. GNB 배치 — 최상위 메뉴 신설하지 않음 — `FE`

`2. 입점 관리` 하위 드롭다운 **맨 아래**에 `변경 요청`을 추가한다.

| 하위 항목 | 배지 |
| --- | --- |
| 브랜드 | 심사 대기 건수 |
| 인플루언서 | 심사 대기 건수 |
| **변경 요청** | **검토 대기 건수** |

상위 `입점 관리` 배지는 3개 하위 항목의 **합산**이다(기존 7 → 9). 입점 심사와 판단 행위가 같으므로 최상위 메뉴를 새로 만들지 않는다.

> **[정합 경고]** `ui-admin-02-onboarding-brand.html` · `ui-admin-03-onboarding-influencer.html` 두 파일의 GNB에는 `변경 요청` 항목이 **없다**. 현재 어드민 3개 시안 간 GNB가 어긋난 상태이며, 두 파일에 1행씩 추가하는 패치가 필요하다(16-8 미결 1번).
>

### 16-2. 상세 — 변경 대조표 — `FE`·`BE`

| 영역 | 내용 |
| --- | --- |
| 제목 줄 | 브랜드명 + `[브랜드 상세 ↗]` 칩 링크 · 요청 유형 · 요청 번호(`CHG-YYYY-NNNN`) |
| 우상단 | `[목록]` · `[‹ 이전]` · `[다음 ›]` |
| 변경 대조 | **항목 / 현재 값 / 변경 요청 값** 3열. 변경 행만 강조, 나머지는 "변경 없음" |
| 대조 확인 항목 | 어떤 값을 서류와 맞춰봐야 하는지 운영자에게 명시 |
| 브랜드 작성 변경 사유 | 원문 그대로 |
| 첨부 증빙 | 파일칩 + `[미리보기]` |
| 우측 패널 | 상태 · 요청 번호 · 요청 유형 · 요청일시 · 요청자 · 경과 → `[✕ 반려]` `[✓ 승인]` |
| 처리 이력 | 접수 → 승인/반려 타임라인 |

| 항목 | 규칙 |
| --- | --- |
| 요청 값의 출처 | **브랜드가 §15 M1·M2에서 직접 입력한 값**이다. 운영자가 서류를 보고 타이핑하는 값이 아니다 |
| 사업자등록번호 행 | 행은 존재하되 요청 값 칸에 **"변경 요청 불가"가 상수로** 표시된다(§15-1 ③ 분류). 번호가 바뀐 경우는 **신규 입점 심사** 대상 |
| 이전/다음 이동 순서 | **현재 탭의 목록 순서**를 따른다(전체 목록 순서가 아니다). 여러 건 연속 처리 시 목록으로 되돌아가지 않아도 된다 |

**`[브랜드 상세 ↗]`만 위치가 다른 이유** — 우상단 버튼군은 **이 목록 안에서의 이동**이고, 브랜드 상세는 **다른 메뉴(회원 관리)로 나가는 동작**이라 성격이 다르다. 제목 옆 칩 링크로 두면 "이 브랜드를 더 보기"라는 뜻이 위치만으로 읽히고, 이동 버튼군과 섞이지 않는다.

### 16-3. 증빙 미리보기 — 대조 패널 병기 — `FE`

`[미리보기]`는 이미지만 띄우는 라이트박스가 아니다. **좌: 서류 이미지(회전·확대·원본) + 우: 요청 값 대조 패널** 2분할이다.

| 패널 구성 | 내용 |
| --- | --- |
| 변경 대상 항목 | 항목별 **현재 값(취소선) → 요청 값(강조)** |
| 참고 항목 병기 | 변경 대상이 **아닌** 값(사업자등록번호·상호 등)도 같은 패널에 표시 |

**참고 항목을 병기하는 이유** — 운영자가 확인해야 하는 것은 요청 값만이 아니다. **동일 사업자인지**, **예금주가 사업자 명의와 맞는지**를 함께 봐야 한다. rev.3 이전에는 서류 이미지와 대조표가 다른 화면에 있어 모달을 여닫아야 했다. 통장 사본 대조(정산 계좌)에서는 예금주 대조 기준(사업자등록증 상호)을 같은 패널에 병기하고 **불일치 시 경고를 노출**한다.

### 16-4. 승인 처리 — `FE`·`BE`

| 항목 | 내용 |
| --- | --- |
| 확인 모달 | **되돌릴 수 없는 집행 액션**이므로 확인 모달 필수. 단축 경로를 만들지 않는다 |
| 승인 시 | 변경 값이 브랜드 계정에 **즉시 반영** → 파트너센터에 승인 배너(§15-7) + 이메일 통지 |
| 정산 계좌 승인 | 모달에 **정산 회차 영향**까지 명시(확정 회차는 기존 계좌로 지급) |
| 처리 완료 | 목록 복귀 + 성공 토스트. 해당 건은 **승인 탭으로 이동** |
| 부분 승인 | **미지원** — 한 요청에 묶인 변경 항목은 **전체 승인 또는 전체 반려**로만 처리한다 |

**부분 승인을 두지 않는 이유** — 한 건의 요청은 하나의 증빙 서류에 근거한다. 서류 일부만 인정하는 판단은 근거가 애매하고, 브랜드 화면의 배너 상태(§15-7)도 3단계로 확정되어 부분 상태를 표현할 자리가 없다.

### 16-5. 반려 처리 — `FE`·`BE`

| 항목 | 규칙 |
| --- | --- |
| 정형 사유 | 드롭다운 **필수 선택**. 목록은 §15-8과 동일(요청 유형별 6종 / 5종) |
| 상세 사유 | 자유 입력 **선택**, 최대 500자 |
| 조건부 필수 | 정형 사유 = **"기타"일 때만** 상세 사유 필수로 전환. 미입력 시 `[반려 처리]` 비활성 |
| 노출 범위 | 선택 문구 + 상세 사유가 **브랜드 파트너센터 배너와 통지 이메일에 그대로** 실린다 |
| 작성 원칙 | 운영자용 축약어를 쓰지 않고 **문장형으로 유지**한다(가공 없이 브랜드에게 전달되므로) |

> §9-4(인플루언서 입점 반려)와 **정반대 정책**이다. 그쪽은 사유가 내부 전용이고, 여기는 브랜드에게 그대로 보인다. 근거는 §15-8 비교표.
> 

### 16-6. 재요청 처리 — 신규 행 생성 — `FE`·`BE`

| 구분 | 처리 |
| --- | --- |
| 입점 심사(§5·§9) | 동일 건에 **이력 누적** |
| **변경 요청(§16)** | **신규 행 생성** — 별건으로 취급 |

**분기 이유** — 변경 요청은 **요청 시점마다 값이 다르다**. 같은 행에 누적하면 어떤 증빙이 어떤 요청 값에 대응하는지 추적이 끊긴다. 반려 건은 브랜드가 **대기기간 없이 즉시** 재요청할 수 있고(§15-7), 그때마다 새 행이 목록에 들어온다.

### 16-7. 계좌번호 노출 범위 — 화면별 분기 — `FE`·`BE`

| 화면 | 노출 |
| --- | --- |
| 파트너센터 정산 계좌 조회(§15-3) | **뒤 6자리만**(마스킹 유지) |
| 어드민 변경 요청 상세(§16) | **전체 노출** |

어드민에서 전체를 보여주는 목적은 **통장 사본 대조** 하나다. 브랜드용 화면의 마스킹은 계속 유지하며, 두 화면의 마스킹 처리를 **공용 유틸로 묶지 않는다**. 예금주 명의 불일치 시 경고를 함께 노출한다.
