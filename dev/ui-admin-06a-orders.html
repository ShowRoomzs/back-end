[rev.4 · 거래 관리 결정 12건 반영 · 2026.10.05] ① 환불 자동화 — 반품 검수 승인·반송 완료까지 PG 자동, 운영자는 사유 환불만(B2 · B5) ② 구매확정 후 하자 = 운영자가 반품을 대신 연다(B6 신규) ③ 직권 배송완료 삭제 → 배송완료일 정정(B3) ④ 위해성 중단 시 발송분 = 사유 환불 · 미발송분 = 직권 취소(B5) ⑤ 사이드바 거래 관리 = 주문 조회 · 반품·교환 · 환불 관리 · 예외 관리(배송 예외 + 처리 지연 합본).
[rev.4 · 파트너 2026.10.05 반영] ① 발송 기한 = 공구 마감 시각 + 브랜드가 정한 N영업일(기본 3 · 1~7) — N은 주문 시점 값으로 고정되므로 상세 배송 블록에 그 주문에 적용된 N과 계산된 기한을 함께 적는다(B4 · B7). 공구 진행 중 주문은 마감 전까지 기한이 없다(B1). 경과 판정은 송장 등록 시각. 「출고 소요일(결제 + N일)」 폐기 ② 취소 요청 응답 1영업일 · 넘기면 자동 승인 — 응답 마감과 자동 승인 여부를 보여주고 운영자 조치는 없다(B7). 요청 중 항목은 브랜드 송장 등록 잠김 ③ 준비 시작 사유(발주서 다운로드 / 개별 준비 시작 / 일괄)를 이력에 구분해 남긴다 ④ 집화 확인 필요 = 등록 후 24시간(72시간 단계 폐기) · 추적 정지 = 집화 후 7일 — 목록 예시 값을 이 기준에 맞췄다(A3) ⑤ 택배사는 추적 연동 목록 하나로 출고·회수·재발송 공통 ⑥ 발송 기한 경과 독촉은 시스템 자동 알림이고 운영자 독촉 버튼은 없다(B4 이력).
[영업일 정의] 영업일 = 주말·공휴일 제외. 발송 기한 · 취소 요청 응답 기한 · 이행 확인 기한이 모두 같은 기준이다.
[rev.3 — 디자인시스템 재대조] rev.2에서 DS를 벗어난 곳 6개를 되돌렸다. ① 상태 분포 줄(.dist)은 DS에 없는 발명품이고 그 CSS가 <style> 바깥으로 새어 적용조차 되지 않았다 → DS는 요약 건수를 .tbar-l에 둔다(“총 4건 · 처리 필요 2건” 패턴). ② 관리 [상세] 버튼 열 → DS §8 “행 클릭으로 상세 이동 · 별도 상세 버튼을 두지 않는다”, QA “행 클릭 외 중복 상세 버튼이 없는가”. ③ .qform 자체 필터 박스 → DS .filter > .tabs + .search. ④ .segbar 세그먼트 → 같은 자리의 셀렉트. ⑤ .empty 패딩·타이포를 DS 규격(72px · 아이콘 28px · .empty-t 13px/600)으로 복원하고 빈 상태를 두 프레임으로 분리. ⑥ 모달 레일 268 → 320px(DS §9 1fr 320px). KPI 카드 CSS 잔여물도 제거했다.
[상태 6종을 탭이 아니라 셀렉트로] DS §6이 명시한다 — “탭은 4~5개까지. 상태 수가 그보다 많으면 묶음 탭 + 상태 셀렉트로 분리한다.” 그래서 탭은 전체 · 배송 이상 · 취소 3개(운영자가 여는 축 · 반품 환불은 반품·교환, 환불 실패는 환불 관리 소관이라 「취소」만 남는다)이고 결제완료·상품준비중·배송중·배송완료·구매확정은 상태 셀렉트에 건수와 함께 들어간다. 탭이 축을 바꾸면 그 셀렉트도 이상 유형으로 따라 바뀐다(A3).
[단위 = 주문(결제 1건)] 파트너센터는 하위주문이 행이지만 어드민은 결제가 행이다 — CS에 들어오는 말은 “주문 하나 했는데요”다. 확장은 하위주문 1단에서 끊는다: 항목(SKU) 트리는 상세 모달 ②블록의 일이고, 3단을 같은 열 골격에 얹으면 열 의미가 행마다 바뀐다.
[조회 화면이다 — 목록에서 처리하지 않는다] 액션 버튼도 체크박스·일괄 처리도 없다. 송장 대행 · 배송완료일 정정 · 직권 취소 · 운영자 사유 환불 · 반품 대신 열기는 남의 거래에 개입하는 일이라 상세에서 근거를 읽고 눌러야 한다.
[rev.4 · 환불은 자동이 기본] 결제완료 취소 · 취소 요청 승인 · 브랜드 직권 취소 · 반품 검수 승인 · 반송 완료는 모두 PG 자동 환불이고 이력에 「PG 자동 환불」로만 남는다. 운영자가 실행하는 환불은 운영자 사유 환불(반려 이의 인용 · 위해성 리콜 · 기타) 하나이며, 이 화면에서는 환불 대기 편입까지만 하고 집행은 환불 관리의 재확인 다이얼로그에서 한다. 자동 환불이 실패하면 환불 관리 · 실패 탭으로 올라온다. [환불 집행으로] 버튼은 없앴다.
[상태 열과 배송 이상 열은 다른 축] 상태는 진행 단계, 배송 이상은 그 단계에서 벌어진 사고다 — “배송중인데 반송 중”이 실제 조합이라 합치면 단순해 보이고 읽기는 어려워진다. 하위주문 상태가 갈리면 상태 열에 혼합 + 조합을 부기한다.
[rev.4 · 직권 배송완료 삭제] 택배사가 추적 연동 목록 하나로 묶이고 수기 송장·자유 입력이 없어져 추적이 원래 없는 건이 생기지 않는다. 추적 정지는 플랫폼 미개입(관찰 표시만)이고, 운영자가 날짜에 손대는 경우는 소비자 수령일 이의를 받아들인 배송완료일 정정(B3) 하나다. 분실 신고·판정 요소는 없다.
[배송완료 출처 3종] (자동 확인) / (운영자 정정) / 송장 출처 (운영자 대행) — 배송완료일이 구매확정 D+7과 반품·교환 기간의 기산점이라, 누가 언제 무슨 근거로 찍었는지가 이의의 쟁점이 된다. 정정 전 값은 이력에 남는다.
[상태 색 매핑] 조치 필요(발송기한 초과·집화 확인 필요)=경고 / 반송 중·추적 정지=위험 / 정상 진행=정보 / 배송완료·구매확정=성공 / 취소·환불=중립(원칙 ②) · 직권 취소는 흰 배경 + 중립 테두리 + 위험색 글자.
[필수 미입력 = 버튼 비활성만] 에러 문구는 형식 오류·중복 송장에만 뜬다. 비활성 버튼에 인라인 opacity를 덧씌우지 않는다 — DS .btn:disabled가 이미 대비를 정해 놨다.
[정렬 설명문은 UI가 아니다] DS §8 — .tbar-r에는 컨트롤만 두고 “경과 오래된순 고정” 같은 설명은 .rule·.state-spec에만 쓴다. 조치 탭에서는 정렬 기본값과 선택지가 바뀌는 것으로 대신한다.
[DS에 없어 확장한 것 — 4개만] .filter.two/.fline(기간 축이 탭·검색과 한 줄에 안 들어간다) · .qmore(상세 조건 접힘) · .fchip(적용됨 칩 — 숨긴 조건을 밖으로 내보내는 장치) · 모달 내부 블록(.modal.wide/.mbk/.sc/.rl/.ifm — DS §10 모달은 520px 확인 모달만 정의한다). 그 외는 전부 DS 컴포넌트를 그대로 쓴다.
