## 13. 파트너센터 연결·소통 — [v0.22 신설]

대상 화면: `ui-partner-05-connections.html` (**rev.2**). 근거 와이어프레임 `wf-partner-03-연결소통계약` F1(연결 목록)·F2(소통 스레드). 정합 기준: `SHOWROOMZ_거래플로우_상태정의서_v1.2` §2(연결)·§3(소통 스레드). GNB #3.

**스코프 한정** — 이번 범위는 **연결 + 1:1 소통**까지다. 계약 관리(GNB #4)는 별도 화면이며 본 섹션은 `[계약 작성]` 버튼의 **활성 조건**만 다룬다. 이슈 스레드(브랜드+인플루언서+운영자 3자 채널)도 범위 밖이다.

### 13-1. 화면 구조 — `FE`

좌우 2패널 고정 구조다. 좌측은 대화 상대 목록, 우측은 선택된 상대와의 스레드. 상단에 스레드 헤더(상대 정보 · 연결 상태 · `[계약 작성]`), 그 아래 **운영자 열람 고지 문구 고정**, 본문은 메시지 영역, 하단은 입력창(텍스트 + 첨부).

게시판형이며 **실시간이 아니다**(거래플로우 §3). 알림은 안 읽은 수 배지만 표시하고, 새 메시지 도착 시 팝업·토스트를 띄우지 않는다.

### 13-2. 좌측 목록 규칙 — `FE`·`BE`

| 항목 | 규칙 |
| --- | --- |
| 정렬·구성 | 운영자 채널 **최상단 고정** → 그 아래 연결된 인플루언서를 최근 메시지순 |
| 노출 대상 | **연결됨 상태만** — `연결요청`(수락 대기중) 상태의 상대는 목록에 나타나지 않는다 |
| 항목 표시 | 프로필 · 쇼룸명 · 최근 메시지 시각 · 최근 메시지 1줄 미리보기 · 안 읽은 수 배지 |
| 상태 표시 | **색상칩·상태 배지를 쓰지 않는다** — 목록에 뜬다는 것 자체가 연결됨이므로 중복 |
| 연결 요청 버튼 | `[+ 연결 요청]`은 **목록 하단**에 배치(상단 아님) |

> **왜 요청중이 목록에 없는가** — 스레드는 연결됨 시점에 활성화된다(거래플로우 §2 전이표). 수락 전에는 주고받을 스레드가 없으므로 목록에 둘 근거가 없다. 다만 이 때문에 **브랜드가 자기가 보낸 요청의 현재 상태를 확인할 화면이 없다** — 현재는 연결 요청 모달에서 같은 상대를 다시 검색해야 `요청중` 배지를 볼 수 있다(13-12 미결 1번).
> 

### 13-3. 운영자 고정 채널 — `[신규제안]` — `FE`·`BE`

목록 최상단에 **SHOWROOMZ 운영팀 채널**이 항상 고정된다. 인플루언서 연결이 하나도 없는 빈 상태(A2)에서도 이 채널만은 노출된다.

| 항목 | 내용 |
| --- | --- |
| 성격 | 브랜드 ↔ 운영자 1:1 채널 |
| 존재 조건 | **없음** — 입점 승인 시점부터 항상 존재 |
| 용도 | 정산 안내, 운영 공지, **미진열(요청) 상품의 진열 복귀 요청**(§11-11) 등 |

> **[신규제안 · 도메인 확인 필요]** ②거래플로우 §3은 소통 스레드의 참여자를 **브랜드·인플루언서(작성) / 운영자(모니터링 열람)**로 정의한다. 즉 **운영자가 작성 주체인 스레드는 문서상 정의되어 있지 않다.** 운영자 고정 채널은 브랜드+인플루언서 쌍 스레드와 **다른 객체**로 취급해야 하며(쌍 키가 성립하지 않는다), 도메인모델·거래플로우 양쪽에 신규 정의가 필요하다. **§11-11의 진열 복귀 경로가 이 채널에 의존**하므로 미확정으로 둘 수 없는 항목이다.
> 

### 13-4. 스레드 도메인 규칙 — `FE`·`BE`

| 항목 | 규칙 | 근거 |
| --- | --- | --- |
| 단위 | **브랜드+인플루언서 쌍당 1개** — 연결이 끊겼다 재생성돼도 같은 쌍이면 동일 스레드로 이어짐(대화 기록 보존) | 거래플로우 §3 |
| 휴면 | 연결 해제 시 스레드는 **휴면** — 열람만 가능, 작성 불가. 재연결 시 다시 열림 | 거래플로우 §3 |
| 운영자 열람 | 분쟁 대응을 위해 운영자가 열람할 수 있으며, **이 사실을 화면에 상시 고지**해야 한다 | 거래플로우 §3 · `[자문대기-법률]` |
| 동시 연결 | 같은 쌍의 동시 유효 연결은 **1개만** 허용 | 거래플로우 §2 |

고지 문구는 스레드 상단에 고정 배치한다. 스크롤로 사라지면 "상시 고지" 요건을 만족하지 못한다 — 고지 없는 열람은 분쟁 리스크이므로 구현 시 sticky 처리가 필수다. **문구 자체는 변호사 패키지 회신 대상**(`[자문대기-법률]`)이며, 시안 문구는 잠정안이다.

> **[미설계]** 휴면 상태의 화면(입력창 비활성 + 사유 안내)은 이번 시안에 없다(13-12 미결 2번).
> 

### 13-5. 계약 작성 버튼 게이트 — `FE`·`BE`

`[계약 작성]`은 스레드 헤더 우측에 놓이며, 연결 상태가 **연결됨일 때만 활성**이다. `연결요청`(수락 대기중)에서는 비활성. 계약 관리 화면 자체는 GNB #4의 별도 화면이므로 이 버튼은 **진입점 역할만** 한다.

### 13-6. 연결 요청 — 2가지 방식 — `FE`·`BE`

**탐색·추천·매칭 시스템은 제공하지 않는다**(거래플로우 §2 핵심 규칙). 상대는 아래 2가지로만 지정한다 — 외부에서 이미 합의가 이뤄진 상태를 전제한다.

| 방식 | 입력 | 판정 |
| --- | --- | --- |
| 쇼룸명 검색 | 쇼룸명 텍스트 | 부분 일치 검색, 결과 목록에서 개별 `[요청]` |
| 연결코드 입력 | 연결코드 | `[확인]`으로 일치 여부 판정 후 `[요청 보내기]` 활성 |

**연결코드 규칙**

| 항목 | 내용 |
| --- | --- |
| 발급 단위 | **쇼룸별 고정(영구)** |
| 확인 위치 | 인플루언서가 쇼룸 스튜디오에서 확인해 브랜드에 직접 전달 |
| 재발급 | **인플루언서가 원하면 재발급 가능** (시안 안내 문구 기준) |

> **[정합 경고]** 재발급 기능은 파트너센터 시안의 **안내 문구에만 존재**하고, 쇼룸 스튜디오 시안(§14)에는 연결코드 표시·재발급 UI가 **아직 없다**. 브랜드 화면이 "인플루언서가 재발급할 수 있다"고 안내하는데 인플루언서 화면에 그 기능이 없으면 문의가 발생한다 — 코드 표시·복사·재발급 UI를 스튜디오에 추가해야 한다(14-8 미결 1번).
> 

**중복 요청 차단** — 같은 상대에게 이미 `연결됨` 또는 `요청중`이면 검색 결과에서 `[요청]` 버튼 대신 **현재 상태 배지**를 표시한다(버튼을 눌렀다가 실패시키지 않고 애초에 막는 방식).

**모달 상태 6종**

| 상태 | 내용 |
| --- | --- |
| 쇼룸명 검색 · 결과 있음 | 결과 목록 + 상태별 버튼/배지 |
| 쇼룸명 검색 · 결과 없음 | 빈 상태 안내 |
| 쇼룸명 검색 · 결과 많음 | 결과 영역 **최대 높이 고정 + 스크롤**, 총 건수 표기("N건 — 스크롤해서 더 볼 수 있습니다") |
| 연결코드 입력 · 초기 | `[요청 보내기]` 비활성 |
| 연결코드 확인 · 존재함 | 일치 쇼룸 정보 카드 노출 + `[요청 보내기]` 활성 |
| 연결코드 확인 · 없음 | 오류 문구만 노출, `[요청 보내기]` 비활성 유지 |

### 13-7. 첨부 정책 — 개수·용량 2축 — `FE`·`BE`

**두 제한은 서로 독립적인 축이며, 둘 다 통과해야 전송된다.** 개수는 통과했는데 용량이 초과인 경우(대용량 영상 2개 등)도 전송 불가다.

| 축 | 제한 | 초과 시 |
| --- | --- | --- |
| 개수 | 메시지 1건당 **최대 20개** | 오류 문구 + 전송 버튼 비활성 |
| 용량 | 메시지 1건당 첨부 **총합 500MB** | 오류 문구 + 전송 버튼 비활성 |

> **[신규제안 · 도메인 범위 확인 필요]** ②거래플로우 §3은 첨부를 **"이미지·영상"까지만** 허용한다고 명시한다. 시안은 여기에 **문서 파일(PDF·DOCX·HWP·XLSX·PPTX·ZIP 등)**을 추가했다 — 문서상 정의 범위를 벗어나는 확장이므로 허용 여부를 확정해야 한다. 확정 시 **허용 확장자 화이트리스트**와 **차단 확장자(exe 등 실행 파일)**를 함께 정해야 한다(13-12 미결 3번). 500MB 용량 제한도 거래플로우에 없던 신규 정책이다.
> 
> 
> **[BE]** 개수·용량 판정은 **서버에서 다시 검증**한다(§0-2 1번과 동일 원칙 — 클라이언트 검증은 우회 가능).
> 

### 13-8. 첨부 종류별 표시·클릭 동작 — `FE`

브라우저는 앱과 달리 파일 시스템에 직접 접근할 수 없어 "이미 받은 파일이면 열어주기"가 불가능하다. 그래서 **종류별로 클릭 동작이 다르다.**

| 종류 | 표시 | 클릭 | 저장 |
| --- | --- | --- | --- |
| 이미지 | 썸네일 그리드 | **라이트박스 미리보기**(다운로드 아님) | 별도 다운로드 아이콘 |
| 영상 | **문서와 동일한 file-chip**(mp4 아이콘, 재생시간·용량 표기) | 재생 | file-chip의 다운로드 버튼 |
| 문서 | file-chip(확장자 아이콘 + 파일명 + 용량) | **매번 새로 다운로드** | 클릭이 곧 다운로드 |

**문서 파일은 예외 없이 전부 다운로드**로 통일한다(2026.08 확정 — 초기엔 PDF만 새 탭 미리보기로 여는 예외를 뒀으나 규칙 단순화를 위해 폐기). file-chip의 "다운로드 완료" 체크 표시는 **"과거에 최소 한 번 받은 적 있다"는 이력 표시**일 뿐, "다시 안 받아도 된다"는 뜻이 아니다.

**이미지 그리드 규칙**

| 장수 | 표시 |
| --- | --- |
| 2~4장 | 전부 노출 |
| 5장 이상 | **3×2(6칸) 고정 그리드** |
| 7장 이상 | 마지막 칸에 `+N` 오버레이로 나머지 개수 표시(최대 20장 기준) |

**이미지 미리보기 창(라이트박스)** — 상단에 보낸 사람 · 닫기 · 다운로드. 여러 장이면 좌우 이동 + 장수 표시. 여기서도 다운로드 가능하며, 클릭할 때마다 새로 받아진다.

> **[구현 방식 — FE]** 파일 아이콘은 화면마다 하드코딩하지 않고 **확장자 → {라벨, 색상} 매핑 테이블**로 자동 처리한다. 테이블에 없는 확장자는 **회색 기본 아이콘 + 확장자 텍스트 그대로**를 보여주는 기본값으로 처리 — 새 확장자가 나와도 화면이 깨지지 않는다.
> 
> 
> **[BE 확인 필요 · 영상 스트리밍]** 영상 재생은 `<video>` 태그의 **스트리밍 재생**을 전제로 설계됐다(전체 파일을 미리 받지 않고 필요한 만큼만 로드). 이게 성립하려면 스토리지가 **HTTP Range Request(부분 요청)를 지원**해야 한다. S3·CloudFront 등은 기본 지원되나 구현 시 꺼져 있으면 "재생"이 사실상 "전체 다운로드 후 재생"이 되어 재생/다운로드를 분리한 설계 의도가 무너진다 — 김화창 확인 필요(13-12 미결 4번).
> 

### 13-9. 전체 다운로드 · 다운로드 진행 UI — `FE`

한 메시지에 첨부가 **2개 이상**이면 첨부 영역 바로 아래에 `[전체 다운로드]` 버튼을 노출한다. 클릭 시 첨부된 **모든 파일이 개별 다운로드**된다(압축 없음 — 브라우저가 순차 저장 처리).

버튼 라벨의 장수는 **화면에 보이는 장수가 아니라 실제 첨부된 전체 개수** 기준이다(`+N` 오버레이로 가려진 사진 포함).

> **[다운로드 진행 UI는 만들지 않는다 — 확정]** 진행률·퍼센트는 브라우저 자체 다운로드 트레이가 이미 보여주는 정보다. 채팅 UI 안에 별도 구현하면 단순 다운로드 링크가 아니라 스트리밍 처리가 필요해져 불필요하게 복잡해지고, 대부분 파일은 체감상 즉시 끝나 볼 일도 거의 없다. **버튼은 다운로드 아이콘 하나로 충분하다.** 나머지는 브라우저에 맡긴다.
> 

### 13-10. 전송 실패 처리 — [rev.2 신규] — `FE`·`BE`

| 항목 | 내용 |
| --- | --- |
| 표시 위치 | 말풍선의 **타임스탬프 자리**에 빨간 느낌표 아이콘 |
| 액션 | 말풍선 아래에 `[재전송]` · `[취소]` 노출 |
| 재전송 | 같은 내용으로 재시도 — 성공 시 정상 타임스탬프로 복귀 |
| 취소 | 실패한 메시지를 스레드에서 제거 |

> **[BE]** 실패한 메시지가 **서버에 저장됐는지 여부**를 프론트가 알 수 있어야 재전송이 중복 저장을 일으키지 않는다. 멱등 처리 방식은 김화창 영역이나, "재전송해도 중복 생성되지 않는다"는 **요구 자체는 확정 사항**이다.
> 

### 13-11. 텍스트 없는 첨부 전송 — `FE`

텍스트 없이 파일(사진·영상·문서)만 보내는 경우 말풍선이 없어 전송 시각을 표시할 자리가 없다. 이 경우 **첨부된 항목 중 가장 하단(마지막) 항목에 전송 시각을 표시**한다.

## 14. 쇼룸 스튜디오 연결·소통 — [v0.22 신설]

**메인 셸 신규 구축** — 쇼룸 스튜디오 로그인 이후의 메인 셸(GNB + 탑바)을 이 화면에서 처음 만들었다. 지금까지 스튜디오는 로그인·신청·온보딩(Auth 셸)만 있었다(§7·§8·§10). 파트너센터 선례와 동일하게 **셸 패턴을 그대로 재사용하고 GNB 라벨만 스튜디오 기준으로 교체**했다.

**스코프 한정** — 연결·소통만(1:1 스레드 2패널 + 연결 요청함). **이슈 스레드(브랜드+인플루언서+운영자 3자 채널, `wf-studio-02` F6)와 계약 관리는 별도 작업으로 분리**(2026.08 확정).

### 14-2. 파트너센터와의 구조 차이 — 수신 측 — `FE`·`BE`

연결은 **항상 브랜드가 발신**하고 인플루언서는 수락/거절만 한다(거래플로우 §2 전이표). 이 비대칭이 화면 구조의 차이를 만든다.

| 항목 | 파트너센터 (§13) | 쇼룸 스튜디오 (§14) |
| --- | --- | --- |
| 연결 요청 발신 | `[+ 연결 요청]` 버튼 있음 | **버튼 없음** |
| 좌측 목록 | 단일 목록 | **2탭 — 연결됨 / 요청함** |
| 계약 버튼 | `[계약 작성]` — 연결됨이면 활성 | `[계약 확인]` — **계약이 있을 때만 노출** |
| 운영자 채널 | 최상단 고정 | 최상단 고정 (동일) |

> **버튼 게이트 방식이 다르다** — 파트너센터는 계약을 **만드는** 쪽이라 조건 충족 시 활성/비활성으로 갈리지만, 스튜디오는 계약을 **확인하는** 쪽이라 없으면 볼 것이 없으므로 **버튼 자체를 숨긴다**. 같은 원칙(계약 유무 게이트)의 방향만 반대다.
> 

### 14-3. 좌측 2탭 구조 — `FE`

### 14-5. 컴포넌트 재사용 범위 — `FE`

첨부·메시징 컴포넌트(이미지 그리드 · 라이트박스 · 영상 file-chip · 문서 file-chip · 업로드 진행 · 입력창)는 파트너센터와 **완전 동일 마크업을 재사용**한다. 프론트 리프트 시 **공유 컴포넌트로 만들고 별도 재설계하지 않는다.**

도메인 규칙도 동일하게 적용된다 — **§13-7(개수 20개·용량 500MB 2축)·§13-8(종류별 클릭 동작)·§13-9(전체 다운로드)·§13-10(전송 실패)·§13-11(첨부만 전송 시 타임스탬프)은 §14에서 재기술하지 않는다.** 스튜디오 상태 S3~S11이 파트너센터 A3~A11과 1:1 대응한다.

### 14-6. 운영자 고정 채널 — 대칭 적용 — `FE`·`BE`
