ui-partner-03-connections — 파트너센터 연결·소통

근거: wf-partner-03-연결소통계약(F1·F2) · SHOWROOMZ_거래플로우_상태정의서_v1.2 §2(연결)·§3(소통 스레드) · GNB #3(계약 관리는 #4, 별도 화면)

[도메인 규칙] 스레드는 브랜드+인플루언서 쌍 기준 유일 — 연결이 끊겼다 재생성돼도 같은 쌍이면 동일 스레드로 이어짐(대화 기록 보존). 연결 해제 시 스레드는 휴면(열람만 가능, 작성 불가) 상태가 되고 재연결 시 다시 열림.
[도메인 규칙] [계약 작성] 버튼은 진열 상태 "연결됨"일 때만 활성 — "연결요청"(수락 대기중) 상태에서는 비활성. 계약 관리(GNB #4)는 별도 화면이라 이 문서 범위 밖.
[도메인 규칙] 같은 쌍의 동시 유효 연결은 1개만 허용 — 이미 연결됨/연결요청 상태인 인플루언서는 연결 요청 모달 검색 결과에서 "요청" 버튼 대신 현재 상태 배지로 표시.
[법적 고지 — 실제 UI] 운영자는 분쟁 대응을 위해 스레드를 열람할 수 있으며, 이 사실은 화면에 상시 고지되어야 한다(②거래플로우 §3) — 스레드 상단에 고정 안내 문구로 반영.
[제약] 탐색·매칭 시스템 없음 — 상대는 쇼룸명 검색 또는 연결코드로만 지정(외부 합의 전제). 메시지 첨부는 1건당 최대 20개(이미지·영상).
[신규제안 · 도메인 범위 확인 필요] ②거래플로우_상태정의서 §3은 "이미지·영상 첨부"까지만 허용한다고 명시되어 있음. 이번에 문서 파일(PDF·DOCX·HWP·XLSX·PPTX·ZIP 등) 첨부를 추가로 디자인했는데, 이는 문서상 정의 범위를 벗어나는 확장이라 실제 허용할지 김화창님·소 대표님 확인 필요. 실제 허용 확장자 전체 목록·차단 확장자(exe 등 실행파일)는 별도 확정 필요.
[구현 방식 — FE] 파일 아이콘은 화면마다 하드코딩하지 않고, 확장자 → {라벨, 색상} 매핑 테이블로 자동 처리합니다. 파일명에서 확장자를 추출해 테이블에서 찾고, 테이블에 없는 확장자는 회색 기본 아이콘 + 확장자 텍스트 그대로를 보여주는 기본값(default)으로 처리 — 새 확장자가 나와도 화면이 깨지지 않고, 디자이너가 매번 새 아이콘을 그릴 필요도 없습니다(A7 참고).
[정책 · 신규] 메시지 1건 전송 시 첨부 총 용량 500MB 제한. 초과 시 전송 버튼 비활성화 + 오류 문구 노출(A9 참고). 개별 파일 개수 제한(최대 20개, 위 [제약] 참고)과는 별개의 축이라 두 조건 다 확인해야 함(개수 OK + 용량 초과인 경우도 전송 불가).
[중요 · 클릭 동작은 파일 종류마다 다릅니다] 브라우저는 앱(카톡)과 달리 파일 시스템에 직접 접근할 수 없어 "이미 받은 파일이면 열어주기"가 불가능합니다. 그래서 종류별로 클릭 동작이 다르게 설계됩니다 — 사진·영상: 클릭 시 화면 안에서 미리보기/재생만(다운로드 아님), 저장하려면 별도의 작은 다운로드 아이콘을 눌러야 함(A4·A5·A6 참고). 모든 문서 파일(PDF·DOCX·HWP·XLSX·PPTX·ZIP 등): 예외 없이 클릭할 때마다 매번 새로 다운로드됨(2026.08 확정 — 초기엔 PDF만 새 탭 미리보기로 열리는 예외를 뒀으나, 규칙을 단순화하기 위해 문서 파일은 전부 동일하게 다운로드로 통일). A6의 "다운로드 완료" 체크 표시는 "다시 안 받아도 된다"는 뜻이 아니라 "과거에 최소 한 번 받은 적 있다"는 이력 표시일 뿐입니다.
[신규 · 2026.08 추가] 한 메시지에 사진·영상·문서 첨부가 2개 이상이면 첨부 영역 바로 아래 [전체 다운로드] 버튼을 노출한다(A4·A6 참고). 여러 개를 한 번에 받아야 하는 경우 하나씩 누르는 번거로움을 줄이기 위함 — 클릭 시 첨부된 모든 파일이 개별 다운로드된다(브라우저가 순차적으로 여러 파일 저장을 처리, 압축 없음). 사진 그리드는 화면에 보이는 장수가 아니라 실제 첨부된 전체 개수 기준으로 버튼 라벨이 표기된다("+N" 오버레이로 가려진 사진 포함).
[신규 · 2026.08 추가] 영상 첨부도 문서 첨부와 동일한 file-chip UI로 다운로드를 제공한다(A5 참고) — 기존에는 썸네일 위 작은 원형 아이콘으로만 저장이 가능해 다운로드 동작이 눈에 잘 띄지 않았음. 재생(썸네일 클릭)과 다운로드(file-chip의 다운로드 버튼)는 여전히 완전히 분리된 동작이다.
[다운로드 진행 UI는 별도로 만들지 않음] 다운로드 진행 상태(퍼센트·진행바)는 브라우저(크롬)가 자체 다운로드 트레이로 이미 보여주는 정보라 채팅창 안에 따로 구현하지 않는다. 실시간 진행률을 채팅 UI에 표시하려면 단순 다운로드 링크가 아니라 별도 스트리밍 처리가 필요해 불필요하게 복잡해지고, 대부분 파일(수백 KB~수 MB)은 체감상 즉시 끝나 커스텀 UI를 볼 일도 거의 없음. 버튼은 다운로드 아이콘 하나면 충분 — 나머지는 브라우저에 맡긴다.
[BE 확인 필요 · 영상 재생은 다운로드 없이 스트리밍] 영상 재생(▶)은 <video> 태그의 스트리밍 재생을 전제로 설계됨 — 전체 파일을 미리 받지 않고 재생에 필요한 만큼만 그때그때 불러온다(유튜브와 동일 원리). 단 이게 되려면 영상을 서빙하는 스토리지가 HTTP Range Request(부분 요청)를 지원해야 함 — S3·CloudFront 등 일반적인 스토리지는 기본 지원되나, 구현 시 꺼져있으면 "재생"이 사실상 "전체 다운로드 후 재생"이 되어버려 재생과 다운로드를 분리한 설계 의도(A5·A9)가 무너짐. 김화창님 확인 필요.
[신규 규칙] 텍스트 없이 파일(사진·영상·문서)만 전송하는 경우, 말풍선이 없어 전송 시각을 표시할 자리가 없으므로 첨부된 항목 중 가장 하단(마지막) 항목에 전송 시각을 표시한다(A4·A5·A6·A8 참고).
A1연결·소통 · 기본 좌: 운영자(최상단 고정) + 연결된 인플루언서만 노출(요청중은 목록에 없음, 색상칩 없이 안읽음 수만) · 연결 요청 버튼은 목록 하단 · 말풍선은 글 길이에 맞춤(2줄 예시 포함) · 전송 실패 시 타임스탬프 자리에 빨간 느낌표 + 말풍선 아래 [재전송]/[취소] 노출
