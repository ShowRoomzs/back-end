## 1. 발송 기한 = 공구 마감 + 브랜드 N영업일

### 1-1. 현재

- `Market.shipping_lead_days`(가입 시 입력 · 1 이상 · 상한 없음) — 「출고 소요일」. 결제 후 N**일**(달력일).
- `OrderFulfillmentService.activate`(PAID 전이) — `ship_due_at = paid_at + N days` 스냅샷. `OrderDeliveryGroup.ship_due_at` 주석도 그렇게 적혀 있다.
- 파트너 목록 `shipOverdue`(판정 = 송장 등록 시각) · `SHIP_DUE_ASC` 정렬 · 앱 `shipDueAt`(NOT_SHIPPED 일 때) · 상품 상세 `shippingLeadDays`(숫자만).

### 1-2. 바뀌는 규칙(어드민 전달 프롬프트 §1)

| 규칙 | 구현 |
| --- | --- |
| 기한 = **공구 마감 시각 + N영업일** · 영업일 = 주말·공휴일 제외 | `BusinessCalendar.addBusinessDays(endAt.toLocalDate(), N)` 의 **그 날 23:59:59**(`BusinessDayCalculator.dueAt`와 같은 규칙 — 기산일 불산입) |
| N = 브랜드 설정 · 기본 3 · **1~7** | `Market.shipping_lead_days` 그대로 쓰되 의미를 「발송 기한(영업일)」로 바꾸고 `@Min(1) @Max(7)` · 기본 3 |
| **주문 시점의 N으로 고정** — 뒤에 바꿔도 접수된 주문은 그대로 | `order_delivery_group.ship_due_business_days TINYINT NOT NULL` 스냅샷(PAID 전이 때). 어드민 상세 B4·B7이 「이 주문에 적용된 N」을 보여준다 |
| **공구 진행 중 결제 건은 마감 전까지 기한이 없다** | `ship_due_at`은 **공구가 종료되는 순간**에 채운다. PAID 전이에서는 `ship_due_at = NULL` · N만 스냅샷. 그 공구가 이미 종료된 뒤 결제된 주문(종료 후 결제 가능 여부와 무관하게 방어)은 PAID 전이에서 바로 계산 |
| 조기 마감 · 연장 · 중단으로 **마감 시각이 바뀐다** | 기한을 PAID 때 계산해 두면 조기 마감(`endedAt = end_at`가 아닌 승인 시각) · 연장 승인에서 틀어진다. 그래서 **종료 사건 하나에서 일괄 계산**한다 — `GroupBuyTerminator.terminate/tryTerminate` 끝에 `OrderFulfillmentService.assignShipDue(groupBuyId, endedAt)` → `UPDATE order_delivery_group SET ship_due_at = f(endedAt, ship_due_business_days) WHERE group_buy_id = ? AND ship_due_at IS NULL AND fulfillment_status IN (NEW, PREPARING)`. 영업일 계산은 N값별로 한 번씩(최대 7종) |
| 경과 판정 = 송장 등록 시각(기존과 같음) | 변경 없음. `ship_due_at IS NULL`이면 「마감 전」이라 경과도 없다 — `SellerOrderAssembler` 의 `shipOverdue` 는 이미 null-safe 인지 확인 |

- `order_delivery_group`에 `group_buy_id`가 있는지 확인 — 없으면 `order_product → group_buy` 조인으로 대상 그룹을 찾는다(한 하위주문의 항목은 같은 공구다 — 장바구니가 공구 단위로 묶인다 · V142).
- 중단(SUSPENDED)도 종료 사건이다 — 중단 시 미발송분 처리(직권 취소 · 환불)는 8절 어드민 B5 범위지만, **기한 계산은 같은 훅**에서 한다(발송해야 할 주문이 남을 수 있다).

## 2. 환불 — PG 즉시 자동 · 운영자 집행은 「운영자 사유」만

### 2-1. 현재

- `OrderFulfillmentService.enqueueRefund` 가 네 경로 전부를 `order_refund_task(PENDING)` 로 쌓는다: `CANCEL_REQUEST_APPROVED` · `SELLER_DIRECT_CANCEL` · `RETURN_COMPLETED`(반송 완료) · `CLAIM_RETURN_PASSED`(반품 통과 — 요청 단위 `finalize`).
- 집행(`markExecuted` · 클레임 `completeRefund`)을 부르는 어드민 API가 **없다** — 지금은 환불이 영원히 PENDING 이다.
- `PortOnePaymentGateway.cancel(paymentId, amount, reason)` — 시그니처에 금액이 있지만 Javadoc·`PaymentTransitions.completeCancel`은 **전액 취소 전제**(PAID → CANCELLED). `PaymentCancel` 엔티티는 부분 취소를 막지 않는다고 적혀 있다.
- 준비 시작 전 소비자 취소(`OrderCommandService`) · 교환 재발송비 결제 취소(`ClaimPaymentService`)는 이미 PG 자동(전액)이다.

### 2-2. 바뀌는 규칙(결정 1 · 06c)

| 경로 | 처리 |
| --- | --- |
| 결제완료 소비자 취소 · 취소 요청 승인(자동 승인 포함) · 브랜드 직권 취소 · 반품 검수 통과 · 반송 완료 | **PG 즉시 자동** — 큐에 쌓고 **커밋 직후 집행**한다 |
| 운영자 사유 환불(반려 이의 인용 · 구매확정 후 하자 · 위해성 리콜) | 큐에 쌓고 **어드민 06c에서 재확인 후 집행**(8절) |
| 자동 환불 실패 | 06c 「실패」 탭 — 자동 재시도 1회(간격은 Q3) 뒤 운영자 재시도 |

한 결제에 하위주문(브랜드) 여럿 · 항목 여럿이라 **부분 취소가 기본**이다. 전액이 되는 경우는 주문 전체 취소뿐이다.

### 2-4. 집행기 — `RefundExecutor`

```
enqueueRefund(group, source, sourceId, amount, origin = PG_AUTO)       ← 도메인 트랜잭션 안
  → afterCommit: RefundExecutor.execute(taskId)                          ← 트랜잭션 밖(PaymentCancelExecutor 와 같은 규칙)
       1. task PENDING → EXECUTING 조건부 UPDATE(선점 · attempt++)
       2. payment PAID|CANCEL_REQUESTED → CANCEL_REQUESTED 선점(결제 단위 락 — 실패면 task 를 RETRY_WAIT · 다음 회차)
       3. gateway.cancel(paymentId, amount, reason)
          CANCELLED → payment.completeCancel(부분) · task DONE(executed_at · payment_cancel_id) · 도메인 훅
          REJECTED  → task FAILED(last_error) · payment 복귀 · 06c 실패 탭
          UNKNOWN   → task EXECUTING 유지 · 수렴 배치(기존 cancel-retry)가 포트원을 재조회해 닫는다
```

- **도메인 훅**(DONE 시) — 경로별로 지금 「어드민이 집행하면 할 일」로 설계된 것을 그대로 부른다: `CLAIM_RETURN_PASSED` → `OrderClaimService.completeRefund(collectionId)`(REFUND_PENDING → COMPLETED(REFUNDED) 일괄 · 35 설계서) / 취소 계열 → 항목 `REFUNDED` 전이가 이미 승인 시점에 끝났는지 확인하고, 아니면 여기서.
- `order_refund_task` 컬럼: `origin VARCHAR(16)`(PG_AUTO / OPERATOR) · `attempt INT` · `last_error VARCHAR(500)` · `payment_id VARCHAR(64)`(어느 결제를 취소하는가 — 원 결제 / 재발송비 결제). 상태 `PENDING · EXECUTING · DONE · FAILED · VOID`.
- 재시도 스케줄러 `RefundRetryScheduler` — `FAILED` 이고 `attempt < 2` 인 PG_AUTO 를 한 번 더(Q3). 그 뒤는 06c 운영자 [재시도].
- `OrderRefundTask` 주석(「환불은 브랜드가 절대 실행하지 않는다」)은 그대로 참이다 — 브랜드 액션은 여전히 큐만 쌓는다. 바뀐 것은 **큐를 비우는 주체가 어드민에서 시스템으로** 옮긴 것뿐이다.

### 2-5. 금액

- 지금 적재되는 예정액(`activeItemsAmount + deliveryFee` · 클레임 `refund_amount`)을 그대로 집행액으로 쓴다. 반송 완료의 「왕복 배송비 차감(약관 근거 대기)」은 여전히 전액이다 — 결정 사항에 없다.
- 운영자 사유 환불은 운영자가 입력한 금액(8절).

## 4. 구매확정 타이머 — 정지 · 재개

### 4-1. 현재

- 배송완료 + 7일(`purchaseConfirmDays`) 배치 확정. `confirmPurchase` WHERE 에 `NOT EXISTS (열린 클레임 — rejectedAt IS NULL)` 가 있어 **보류**된다. 교환 재발송 도착은 `confirm_restart_at` 으로 7일을 새로 센다.

| 변경 | 내용 |

## 9. 계약 상세 「정산 방식」 블록(선택)

`CreatorContractDetailResponse.settlementMethod { payer: "SHOWROOMZ", withholding: WithholdingType, expectedNetPreview: { gross: 100000, net: 96700 } }` — `WithholdingType.from(creator.businessType)` · 비사업자 3.3% · 사업자는 `gross + VAT 10%` 가 아니라 **공급가 = 리워드**이므로 `net = gross`(부가세는 세금계산서로 별도). 표시 전용이고 정산 모듈이 생기면 그쪽 값이 정본이다. 「리워드 지급자: SHOWROOMZ」 · 「고정 지급비는 브랜드 직접 지급 · 정산 미포함」은 FE 고정 문구.
