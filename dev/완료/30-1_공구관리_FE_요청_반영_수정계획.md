# 30-1 공구관리 FE 요청 반영 — 수정 계획

Oct 4, 2026 · @hc

FE가 시안 기준으로 올린 백엔드 요청 13건(「시안 우선 기준」 8건 + 「공구 관리 · 시안 기준」 5건)의 판단과 수정 계획이다. 대상 설계서는 30(파트너) · 31(스튜디오) · 32(어드민) 공구관리와 연결·소통이다.

**결론 — 6건을 고치고, 7건은 고치지 않는다.** 고치지 않는 7건은 백엔드 누락이 아니라 **값을 만들 모듈이나 기획이 없는 것**이다. 없는 값을 지어내 내리지 않는다는 기존 규칙(30 설계 0-6)을 그대로 따른다.

**구현 완료(2026-10-04)** — 6건 모두 7절의 기본값으로 구현했고 30 · 31 · 32 설계서와 연결·소통 개발계획(13-14)에 반영했다(8절). 계획과 달라진 점은 각 절에 「구현」으로 적었다.

## 1. 이슈 · 미이행 스레드 개설 (A1 · A8)

### 1-1. 현재

- `PairOnlyGroupBuyThreadGateway`가 `openIssueThread` · `openAdminIssueThread` · `openFulfillmentDisputeThread` 셋 모두 `GROUP_BUY_THREAD_UNAVAILABLE`(503)로 거절한다.
- 원인은 `message_thread.connection_id`가 UNIQUE라는 점이다(V92 `uk_message_thread_connection`). 브랜드-인플루언서 쌍당 스레드가 1개뿐이라 이슈 · 미이행용 두 번째 스레드를 만들 수 없다.
- 30 설계 5-3이 이 변경을 「연결·소통 소관」으로 넘기고 멈춘 상태다. 그 사이 API는 배포돼 FE가 503을 받는다.

### 1-2. DB — `V154__alter_message_thread_add_kind.sql`

```sql
ALTER TABLE `message_thread`
    ADD COLUMN `thread_kind` VARCHAR(32) NOT NULL DEFAULT 'CONNECTION'
        COMMENT 'CONNECTION, GROUP_BUY_ISSUE, GROUP_BUY_FULFILLMENT' AFTER `connection_id`,
    ADD COLUMN `subject_id` BIGINT NULL COMMENT '공구 id — CONNECTION이면 NULL' AFTER `thread_kind`,
    ADD COLUMN `connection_thread_key` BIGINT
        GENERATED ALWAYS AS (IF(`thread_kind` = 'CONNECTION', `connection_id`, NULL)) STORED,
    ADD KEY `idx_message_thread_connection` (`connection_id`),
    DROP INDEX `uk_message_thread_connection`,
    ADD CONSTRAINT `uk_message_thread_connection_kind` UNIQUE (`connection_thread_key`);
```

- **쌍당 일반 스레드 1개 제약은 그대로다.** 생성 컬럼 UNIQUE로 `CONNECTION` 종류에만 건다. `group_buy_issue.open_group_buy_id`(V130)와 같은 방식이다.
- `connection_id`는 이슈 · 미이행 스레드에도 **그 쌍의 PAIR 연결**을 넣는다. 접근 판정과 목록 쿼리가 전부 연결 기준이라 그대로 동작한다(1-5).
- `subject_id`는 공구 id다. 이슈 id가 아닌 이유는 스레드가 이슈 행보다 먼저 만들어지기 때문이다(같은 트랜잭션 · 30 설계 4-6). 이슈 → 스레드 방향은 `group_buy_issue.thread_id`가 이미 갖고 있다.
- 기존 행은 기본값으로 전부 `CONNECTION`이 된다. 백필이 필요 없다.
- FK가 쓰던 UNIQUE 인덱스를 지우므로 일반 인덱스를 **같은 ALTER에서 먼저** 더한다.

> **구현** — ALTER를 네 문장으로 나눴다(컬럼 추가 → 생성 컬럼 · UNIQUE → 일반 인덱스 → 기존 UNIQUE 삭제). 생성 컬럼이 같은 문장에서 추가된 컬럼을 참조하는 것과, FK 인덱스 교체를 한 문장에 몰아넣는 것을 피했다. 미이행 스레드 조회용 `idx_message_thread_kind_subject(thread_kind, subject_id)`도 더했다.

### 1-3. 엔티티 · 리포지토리

| 대상 | 변경 |
| --- | --- |
| `MessageThread` | `@OneToOne` → `@ManyToOne`, `unique = true` 제거 · `kind`(`ThreadKind`) · `subjectId` 추가 · 팩토리 `openForGroupBuy(connection, kind, groupBuyId)` |
| `domain/message/type/ThreadKind` | 신규 enum — `CONNECTION` · `GROUP_BUY_ISSUE` · `GROUP_BUY_FULFILLMENT` |
| `MessageThreadRepository.findByConnection` | `findByConnectionAndKind`로 바꾼다. 결과가 여러 건이 될 수 있어 그대로 두면 예외가 난다 |
| 호출부 4곳 | `MessageThreadService.activateThread` · `AdminContractQueryService:81` · `CreatorContractDetailAssembler:368` · 게이트웨이의 `findPairThreadId` — 전부 `kind = CONNECTION`으로 고정 |

### 1-4. 게이트웨이 실구현

`PairOnlyGroupBuyThreadGateway`를 지우고 **메시지 도메인**에 `MessageGroupBuyThreadGateway`를 둔다. 판매 포트를 주문 도메인이 구현한 것(`OrderGroupBuySalesReader`)과 같은 배치다.

| 메서드 | 동작 |
| --- | --- |
| `findPairThreadId` | 지금과 같다 |
| `openIssueThread` · `openAdminIssueThread` | PAIR 연결을 해석 → `GROUP_BUY_ISSUE` 스레드 생성 → 첫 글 = 이슈 내용 |
| `openFulfillmentDisputeThread` | 그 공구의 `GROUP_BUY_FULFILLMENT` 스레드가 있으면 재사용, 없으면 생성 → 첫 글 = 미이행 사유 |

- **PAIR 연결 해석**은 `findPairThreadId`와 같은 규칙이다 — `contract.connection`, 없으면 현재 `CONNECTED`인 쌍. 둘 다 없으면 스레드를 열 곳이 없으므로 `GROUP_BUY_THREAD_UNAVAILABLE`을 유지한다. 503은 이 경우에만 남는다.
- **미이행 스레드는 공구당 1개다.** 양측이 모두 미이행을 내면 두 번째 사유는 같은 스레드의 글로 붙는다. 어드민 상세의 `fulfillment.threadId`가 단일 값인 것과 맞춘다. 호출자가 공구를 `PESSIMISTIC_WRITE`로 잠그고 들어오므로 조회 후 생성이 경합하지 않는다.
- **첫 글의 보낸 사람** — 브랜드는 `SELLER` / 마켓 id, 인플루언서는 `CREATOR` / 크리에이터 id, 운영자는 `ADMIN` / 운영자 id. 기존 메시지 전송(`MessageThreadService.sendMessage`)을 그대로 쓴다.
- **멱등 키** — 이슈 `group-buy-issue-open`, 미이행 `group-buy-fulfillment-{side}`. `UNIQUE(thread_id, client_message_id)`가 재시도 중복을 막는다.
- 스레드 생성 · 첫 글 · 이슈(또는 이행 확인) INSERT가 **한 트랜잭션**이라는 기존 약속은 그대로다.

> **구현** — 포트 시그니처가 하나 바뀌었다. `openAdminIssueThread(groupBuy, operatorId, issueType, content)` — 기존 시그니처에는 운영자 id가 없어 첫 글의 보낸 사람을 정할 수 없었다. `GroupBuyIssueService`가 이미 받던 `openerId`를 넘긴다.

### 1-5. 연결·소통 목록 노출 (A8)

이슈 · 미이행 스레드는 PAIR 연결을 `connection_id`로 갖는다. 그래서 `findOpenThreadsForMarket` · `findOpenThreadsForCreator`가 **쿼리 변경 없이** 함께 돌려준다. 안 읽은 수 집계 · 메시지 조회 · 전송 · 접근 판정(`getMyThread`)도 전부 스레드 id와 연결 기준이라 그대로 동작한다.

고칠 것은 목록 항목뿐이다. 같은 상대 이름의 줄이 2~3개 생기므로 구분 값을 내린다.

```json
{
  "threadId": 5521,
  "counterpartName": "뷰티_소연",
  "kind": "GROUP_BUY_ISSUE",
  "groupBuyId": 88,
  "groupBuyTitle": "수분크림 8월 공구"
}
```

- `kind`는 항상 내린다. 일반 스레드는 `CONNECTION`이고 `groupBuyId` · `groupBuyTitle`은 `null`이다.
- 파트너(`seller/thread`) · 스튜디오(`creator/thread`)의 `ThreadListItem` 둘 다 같은 3필드를 더한다.
- 스튜디오의 `hasContract`(계약 확인 버튼 게이트)는 일반 스레드에만 의미가 있다. 이슈 · 미이행 스레드는 `false`로 내린다.

### 1-6. 테스트

아래 3개 통합 테스트가 지금 503을 기대한다. 성공 케이스로 바꾸고 「스레드가 생기고 첫 글이 등록된다 · 목록에 나온다」를 검증한다.

- `SellerGroupBuyCommandIntegrationTest` (미이행 :346 · 이슈 :375)
- `CreatorGroupBuyCommandIntegrationTest` (미이행 :386)
- `AdminGroupBuyCommandIntegrationTest` (이슈 :467)

추가 케이스 — 쌍당 일반 스레드 중복 생성이 여전히 막히는가 · 연결이 끊긴 쌍은 503인가 · 양측 미이행이 한 스레드로 모이는가.

> **구현** — 「쌍당 일반 스레드 중복」은 통합 테스트로 검증하지 못한다. 테스트 DB(H2 · `create-drop`)는 엔티티에서 스키마를 만들어 생성 컬럼 UNIQUE가 없다 — `open_group_buy_id`와 같은 사정이다. 대신 「같은 연결에 3자 스레드가 붙어도 `pairThreadId`가 연결 쌍의 스레드를 가리킨다」를 검증했다.

### 1-7. 이번에 하지 않는 것

| 항목 | 이유 |
| --- | --- |
| **운영자의 스레드 열람 · 답장 API** | 어드민에는 스레드 API가 아예 없다(`api/admin`에 thread 패키지 없음). 「게시물·소통 모니터링」 화면 소관이다. 그 전까지 운영자는 3자 스레드의 글을 볼 수 없다 |

두 번째가 결정이 필요한 지점이다(7절 #1).

## 2. 열린 이슈의 「답변 대기」 배지 (A3)

### 2-1. 현재

`group_buy_issue.status`는 `OPEN` · `CLOSED` 둘뿐이고, `openIssue`는 열린 건만 내려가므로 상태 값을 더해도 항상 `OPEN`이다. 「답변 대기」는 이슈의 상태가 아니라 **스레드에서 상대가 아직 답하지 않았다**는 사실이다.

### 2-2. 변경

파트너 `GroupBuyDetailResponse.OpenIssue`와 어드민 `AdminGroupBuyDetailResponse.OpenIssue`에 더한다.

| 필드 | 값 |
| --- | --- |
| `openerType` | `SELLER` · `CREATOR` · `ADMIN` — 어드민에는 이미 있다. 파트너에만 추가 |
| `awaitingReply` | 스레드의 **마지막 글을 쓴 쪽이 개설자와 같으면** `true` |

- 판정은 `MessageRepository.findTopByThreadOrderByIdDesc`(이미 있다) 1회 조회다. 컬럼을 더하지 않는다.
  - **구현** — 공구 조립기가 메시지 리포지토리를 직접 부르지 않도록 포트에 `findLastSpeaker(threadId)`를 더했다. 판정(마지막 글 = 개설 측)은 조립기가 한다.
- 개설자가 운영자인 이슈는 `ADMIN` 글이 마지막이면 `true`다.
- FE는 `awaitingReply = true`면 「답변 대기」, `false`면 「답변 있음」 계열 배지를 그린다. 문구는 FE 상수다.

스튜디오 상세는 `afterEnd`에 `openIssue` 자체가 없다. 이번 요청에 없으므로 건드리지 않는다.

## 3. 스튜디오 상세에 구매확정 · 환불 건수 (B1)

### 3-1. 현재

`CreatorGroupBuyDetailResponse.Sales`에는 `orderCount` · `ordersSinceHidden`만 있다. 스튜디오의 `orderClosure`는 종결 경로별 건수를 싣지 않고, 정산완료(`SETTLED`)에서는 블록 자체가 `null`이라 B8에 쓸 수 없다.

### 3-2. 변경 — `Sales`에 2필드

```json
"sales": {
  "basis": "SETTLED",
  "orderCount": 312,
  "purchaseConfirmedCount": 308,
  "refundedCount": 4
}
```

- 출처는 파트너 · 어드민의 `orderClosure.purchaseConfirmedCount` · `refundedCount`와 **같은 포트 호출**(`GroupBuySalesReader.readClosure`)이다. 세 화면의 숫자가 어긋나지 않는다.
- 둘 다 nullable이다. 포트가 비면 `null`이지 0이 아니다.
- `CreatorGroupBuyDetailAssembler`가 `orderClosure()`에서 이미 `readClosure`를 부른다. 한 번 읽어 두 곳에서 쓰도록 정리한다.
  - **구현** — `readSales`처럼 상태와 무관하게 한 번 읽는다. `orderClosure` 블록의 상태 조건(판매중 · 종료 · 중단)은 그대로다.

## 4. 실적 확정 이력의 상세 문구 (B2)

`GroupBuyCommandService.recordSalesFinalized`가 `SALES_FINALIZED` 이력의 `detail`에 `null`을 넣는다. 기록 시점에 `readClosure`를 읽어 **`"구매확정 308건"`** 을 넣는다. 건수를 모르면 `null`로 둔다.

이 메서드는 정산 모듈이 부르는 통보 지점이라 **지금은 호출하는 곳이 없다.** 고쳐도 정산 모듈이 생기기 전에는 이 이력 줄이 화면에 나오지 않는다.

## 5. 자동 이행 이력의 라벨 (B4)

### 5-1. 변경

`GroupBuyLifecycleService.autoConfirmFulfillment`가 `detail`에 `side.name()`을 넣는다. 라벨로 바꾼다.

| `side` (답하지 않은 쪽) | `detail` |
| --- | --- |
| `SELLER` | `브랜드 무응답으로 자동 이행` |
| `CREATOR` | `인플루언서 무응답으로 자동 이행` |

- 어드민 FE가 이미 쓰는 문구와 같게 맞춘다. FE의 치환 처리는 지워도 된다.
- `ref_id`에 생성된 이행 확인 id를 함께 넣는다. 수동 확인 이력(`FULFILLMENT_CONFIRMED`)과 같은 규칙이다.
- `actor`를 나누지 않는 이유 — 이 이력의 행위자는 `SYSTEM`이 맞다. 답하지 않은 쪽은 행위자가 아니라 사건의 내용이다.
- **구현** — 라벨은 `FulfillmentSide`에 둔다(`SELLER("브랜드")` · `CREATOR("인플루언서")`).

### 5-2. 기존 행 보정 — `V155__fix_fulfillment_auto_confirmed_detail.sql`

```sql
UPDATE `group_buy_history`
SET `detail` = CASE `detail`
        WHEN 'SELLER'  THEN '브랜드 무응답으로 자동 이행'
        WHEN 'CREATOR' THEN '인플루언서 무응답으로 자동 이행'
    END
WHERE `event_type` = 'FULFILLMENT_AUTO_CONFIRMED'
  AND `detail` IN ('SELLER', 'CREATOR');
```

자동 이행 스위치는 기본이 꺼짐이라 운영 DB에는 대상 행이 없을 가능성이 높다. 다시 실행해도 결과가 같다.

## 6. 고치지 않는 것과 이유

### 6-1. 「계약 체결완료」 이력 줄 (B3)

- **이력에 넣지 않는다.** 공구 이력은 공구 생성부터다. 계약 이력을 공구 이력에 합성하지 않는다는 결정(31 설계 6-2 · 10-1 #14)을 유지한다. 같은 사건이 계약 이력과 공구 이력 두 곳에 쌓이면 한쪽만 고쳐진다.
- **일시는 이미 내려간다.** 세 앱 상세 모두 `contract.concludedAt`이 있다. FE가 이력 목록 맨 아래에 고정 줄로 그리면 된다.
- **서명자는 내릴 값이 없다.** 계약에는 서명 시각(`brand_signed_at` · `creator_signed_at`)만 있고 서명자 이름이 없다. 체결 처리는 운영자의 행위다(30 설계 2-1). 시안의 「뷰티_소연」은 행위자 오기다. 서명자 자리는 비우거나 「운영자」로 쓴다.

### 6-2. 정산 확인 · 인플루언서 정산 API (A2 · B5)

- 정산 도메인이 없다(`domain/settlement` 없음). `EmptyGroupBuySettlementGateway`는 버그가 아니라 **의도한 빈 구현**이다 — 32 설계 8-2 「정산 모듈이 없으면 이 API를 배포하지 않는다」.
- 정산은 자금 흐름 A/B가 미확정이라 착수 게이트에 걸려 있다(§33-4 #1). 결제 계획서 #9의 PG업 등록 문제와 같은 결정이다.
- 게이트웨이만 채워서 버튼을 여는 방법은 없다. 정산 상태머신을 공구에 두지 않기로 했기 때문이다(30 설계 5-2).
- FE 처리 — [정산 확인]은 비활성 유지, 스튜디오의 [정산 관리 열기] · [정산 명세 보기]는 「준비 중」 유지.

정산 모듈 설계서를 따로 써야 풀린다. 이 문서의 범위가 아니다.

### 6-3. 종결 내역의 거절 확정 · 교환 완료 (A4)

- 반품·교환 모듈(`11-claims`)이 없다. 하위주문 상태(`FulfillmentStatus`)에 반품 거절 · 교환 완료에 해당하는 값이 없어 **셀 대상이 존재하지 않는다.**
- 지금 내려가는 `purchaseConfirmedCount` · `refundedCount`는 사실 그대로다. 반품 거절 확정은 즉시 구매확정이라, 모듈이 생기면 구매확정 건수에 포함된 채로 내역 필드가 추가된다(32 설계 4-8).
- 항상 `null`인 필드를 미리 더하지 않는다. FE는 시안의 괄호 내역 「(거절 확정 2 · 교환 완료 4 포함)」을 빼고 두 값만 그린다.

### 6-4. 콘텐츠 의무 진척도 · 게시 현황 (A5 · A6)

- 31 설계 10-1 #16에서 이미 결론을 냈다 — **데이터 출처가 없다.** 인스타그램 피드 · 릴스 · 스토리의 게시 여부를 추적하는 기능이 기획 어디에도 없다.
- 시안의 분모도 계약과 맞지 않는다(「2 / 4」인데 계약 의무는 피드 1 · 릴스 1 · 스토리 3 = 5).
- 서버가 아는 것은 계약의 의무 건수뿐이고, 이미 `fulfillment.myTarget` · `theirTarget`의 `counts`로 내려간다. FE는 「확인됨 N건」 없이 의무 건수만 그린다.
- 풀려면 「인플루언서가 게시한 콘텐츠를 어떻게 확인하는가」(자기 신고 URL 등록 · 브랜드 건별 확인 등)가 **기획으로 먼저** 정해져야 한다. 신규 기능이다.

### 6-5. CS 문의의 하자 분류 (A7)

- 상품 문의 유형(`ProductInquiryType` 5종)에도 1:1 문의 유형(`CsCategory` 5종)에도 하자 분류가 없다. 32 설계 4-5가 `defectRelated = null`로 확정한 그대로다.
- 본문 키워드로 세지 않는다. 운영자가 그 숫자를 하자 주장의 근거로 읽기 때문이다.
- `CsCategory`는 FAQ와 1:1 문의가 공유하는 고정 5종이다(§17-2-1). 분류 추가는 소비자 앱 · FAQ · 어드민 탭이 함께 바뀌는 기획 변경이다.
- 대안 지표가 하나 있다 — 브랜드 직권 취소 사유의 `DEFECT`(상품 하자). 「요청 후 하자 사유 취소 N건」은 지금 데이터로 셀 수 있다. 다만 시안의 「CS 문의」와 다른 지표라 기획 확인 후 별도 필드로 더한다(7절 #2).
