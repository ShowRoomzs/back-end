# 결제 기능 구현 전 선행 수정 계획서

Sep 27, 2026 · @hc

「결제 기능 구현 계획서 — 포트원 V2」(이하 결제 계획서)는 09-27 14:23에 작성됐고, 그 뒤 18:09 커밋 「공구가로 통일」이 옵션 계획서(A·B·C·E)와 가격 계획서(PR 1~3)를 한 번에 구현했다. 결제 계획서는 그 구현을 **전제**로 쓰였지만 실제 코드와 대조하면 이미 끝난 일을 다시 하라고 적은 곳, 마이그레이션 번호가 겹치는 곳, 가격 계획서가 "재검토 필요"로 되돌려 보낸 설계가 남아 있는 곳이 있다. 이 문서는 결제 PR 1을 열기 전에 **① 결제 계획서에서 고칠 문장**, **② 코드에서 먼저 고칠 것**, **③ 결제 구현 중 건드리면 안 되는 접점**을 정리한다.

## 3. 코드 선행 수정

### 3-1. `iamport-rest-client-java` 제거 — 선행 PR 0

`build.gradle:41` 한 줄 삭제. `repositories { maven { url 'https://jitpack.io' } }`는 이 의존성 하나 때문에 있었는지 확인하고, 다른 의존성이 jitpack을 안 쓰면 같이 지운다. 빌드·전체 테스트 통과가 검증이다.

### 3-2. `OrderPricingCalculator` 추출 — 결제 PR 3 앞부분

`CartService`에서 아래를 `api/app/order/service/OrderPricingCalculator`(또는 `domain/order/service`)로 옮기고 `CartService`는 호출만 한다. **규칙·숫자는 한 줄도 바꾸지 않는다.**

| 옮길 것 | 지금 위치 | 비고 |
| --- | --- | --- |
| `priceOf(carts)` → `CartPricing` | `CartService` | 입력을 `Cart`가 아니라 **`(groupBuyId, variantId, quantity)` 줄 목록**으로 일반화한다. 장바구니 줄·바로 구매 한 줄·주문 상품 줄이 같은 형태로 들어간다 |
| `unavailableReason(cart, pricing)` · `unavailableReason(variant)` · `requirePurchasable` | 〃 | 판정 순서 「공구 → 계약 옵션 → 상품 → 재고」 유지. 주문 생성은 여기서 `CART_ITEM_NOT_PURCHASABLE`을 던진다 |
| `calculateSummary` · `buildGroupShipping` · `lineSaleTotal` · `GroupKey` · `MarketShippingAccumulator` | 〃 | 그룹 키는 공구다. 귀속 없는 옛 줄(`GroupKey(null, marketId)`)은 선택될 수 없으므로 주문 경로에서는 오지 않는다 — 계산기는 `groupBuyId` non-null을 전제해도 된다. `MarketShippingAccumulator`의 max/min은 그룹 안에 마켓이 하나뿐이라 사실상 단순 대입이다 — 옮기면서 단순화해도 결과가 같다(테스트로 고정) |
| `CartDto.MAX_QUANTITY` 상한 | 〃 | 주문 생성도 같은 상수 |

`CartServiceTest`는 그대로 통과해야 한다. 주문서 케이스는 결제 PR 3이 더한다.

### 3-3. `InquiryOrderSummary.formatOrderNumber` 교체 — 결제 PR 1

`orders.order_number`가 생기면 `order.getOrderNumber()`로 바꾸고 파생식(`yyyyMMdd-%04d`)을 지운다. 결제 계획서 7-3에 이미 있다. `InquiryControllerDocs`의 예시 `"20260803-1147"`도 `"20260803-000123"` 형식으로. `orderDate`는 그대로 둔다(`order_product.order_date`) — 주문 생성이 `orders.created_at`과 같은 값을 넣는다.

### 3-4. 어드민 회원 목록 「누적 주문」·탈퇴 차단 — 결제 PR 1

| 코드 | 지금 | 결제 뒤 문제 | 수정 |
| --- | --- | --- | --- |
| `AdminUserQueryRepository.search` · `orderCount()` (`:78-80`) | `order_product.status != CANCELLED`인 주문을 센다 | 결제 대기 30분 안의 주문, 사전 등록만 되고 결제 안 된 주문이 "누적 주문"에 든다 | `leftJoin(order).on(order.user.id.eq(user.id).and(order.status.in(PAID 이후)))`로 **주문 상태**를 조건에 더한다. `order_product` 조인 조건은 유지 |
| `UserService` 탈퇴 차단 (`FINISHED_ORDER_STATUSES`) | `PURCHASE_CONFIRMED`·`CANCELLED` 제외가 진행 중 | `PENDING`(결제 대기)도 진행 중으로 잡혀 30분 안에는 탈퇴가 막힌다 | **바꾸지 않는다.** 만료 스케줄러가 `order_product.status = CANCELLED`로 내리므로 30분 뒤 풀린다. 결제 대기 중 탈퇴를 허용하면 웹훅이 도착한 주문의 사용자가 없다 — 막는 쪽이 맞다. 주석만 보강 |

### 3-5. 테스트 픽스처 — 결제 PR 1

`orders`에 NOT NULL 컬럼(`order_number`·`status`·금액 4종)이 생기면 `Order.builder().user(user).build()`로 만드는 기존 픽스처가 깨진다.

- 사용처: `src/test/java/showroomz/api/admin/user/AdminConsumerListIntegrationTest.java:252-253` 1곳(운영 코드에는 `Order` 생성이 없다).
- `src/test/java/showroomz/support/OrderFixture`(가칭)를 두고 "결제 완료 주문 1건 + 상품 N줄"을 만드는 헬퍼로 바꾼다. 리뷰·문의 테스트가 주문을 만들 때도 이것을 쓴다.
- `Order` 엔티티는 빌더에 필수 인자를 늘리는 대신 **정적 팩토리** `Order.create(user, orderNumber, snapshot…)`로 바꾸는 편이 "빈 주문"이 생기는 경로를 막는다.

### 3-6. `@IntegrationTest` 프로퍼티 — 결제 PR 4·5·7

`src/test/java/showroomz/support/IntegrationTest.java`의 `properties`에 결제 설정을 더한다. yml이 아니라 여기 적는 이유는 파일 상단 주석대로다(환경변수보다 우선).


### 3-7. `SecurityConfig` 화이트리스트 — 결제 PR 5

`AUTH_WHITELIST`에 `"/v1/webhooks/portone"` 추가. `anyRequest().authenticated()`라 빠뜨리면 포트원 웹훅이 401이다. `TokenAuthenticationFilter`는 토큰 없는 요청을 통과시키므로 별도 처리 없음. `/v1/user/**` 규칙에 `USER`·`CREATOR`가 있으므로 주문·결제 API는 크리에이터 계정으로도 열린다 — 장바구니와 같다.

### 3-8. 셀러 재고 수정과 예약 수량 — 결제 PR 4와 같은 릴리스

`api/seller/product/service/ProductService.java:998`의 `existing.setStock(variantRequest.getStock())`(재고만 수정)과 상품 등록·옵션 재생성 경로의 `stock` 저장이 **절대값**이다. 결제 4-3이 주문 생성 시 `stock`을 직접 깎으므로 두 경로가 충돌한다.

```
예약 3건(100 → 97) 사이에 셀러가 "100" 저장 → 100
만료 복원 +3                                 → 103   ← 실물보다 3 많다
```

**수정** — 스키마를 바꾸지 않고 셀러 경로만 고친다.

| 지점 | 변경 |
| --- | --- |
| 셀러 재고 **저장** | `stock = 입력값 − reserved(variantId)`. `reserved` = `SUM(order_product.quantity)` where `orders.status = PAYMENT_PENDING AND orders.stock_released_at IS NULL AND variant_id = :id`. 음수면 0으로 자르고 경고 로그 |
| 셀러 재고 **조회**(상품 상세·목록의 `stock`) | `stock + reserved`를 보여 준다 — 셀러가 보는 값은 실물 재고, DB 값은 가용 재고 |
| 옵션 구조 재생성 경로 | 이미 `requireOptionStructureUnlocked`(진행 중 계약·공구가 있으면 400)가 막는다. 예약이 있을 수 있는 상품은 항상 진행 중 공구가 있으므로 여기서 걸린다 — 추가 조치 없음 |
| `OrderProductRepository.sumReservedQuantityByVariantIds(...)` | 결제 PR 4의 리포지토리에 함께 둔다 |

`reserved` 조회는 결제 PR 4의 `orders.status`·`stock_released_at`이 있어야 한다. 그래서 PR 4와 같은 릴리스다 — PR 4가 먼저 나가고 이 수정이 늦으면 그 사이 셀러 재고 수정이 예약을 지운다.

`reserved_quantity` 컬럼을 두는 대안(가용 = stock − reserved)은 C7·장바구니·`countInStockVariantsByProductIds`·`sumStockByProductIds` 등 읽는 곳 전부를 고쳐야 해서 이번에는 택하지 않는다. 셀러 재고 수정 빈도가 늘어 위 계산이 경합을 일으키면 그때 옮긴다(7절 미결 ②).

### 3-9. 1:1 문의의 주문 소유 검증 — 완료 (2차 검토에서 추가)

`api/app/inquiry/service/InquiryService.registerInquiry`는 요청의 `orderId`를 **검증 없이** 저장한다. 지금은 모든 주문이 리뷰용 시드라 드러나지 않지만, 실주문이 생기면 다른 사용자의 주문 ID를 실어 보내 그 주문의 상품명·썸네일·주문번호가 내 문의 카드(`InquiryOrderSummary`)에 그려진다 — 주문 정보 노출이다.

- `OrderRepository.existsByIdAndUser_Id(orderId, userId)`(`OrderProductRepository.existsByIdAndOrder_User_Id`와 같은 형태)를 두고, 등록·수정 모두 `orderId`가 있으면 검증한다. 실패는 `ORDER_ACCESS_DENIED`(403, 결제 계획서 5-8의 코드를 앞당겨 만들었다). 없는 주문도 같은 코드다 — 404로 나누면 남의 주문 ID가 있는지를 흘린다.
- 결제 대기·만료 주문도 문의는 붙일 수 있게 둔다(「결제가 안 돼요」가 문의 유형 `ORDER_PAYMENT`다). 상태는 검사하지 않는다.
- `market_inquiry_view`(V47)는 Java 코드가 읽지 않는 SQL 뷰라 이 검증과 무관하다.

## 7. 미결

1. **기존 `orders`·`order_product` 운영 데이터 건수.** V36으로 만든 리뷰 선행 테이블이라 운영에 시드가 남아 있을 수 있다. 결제 PR 1 배포 전에 `SELECT COUNT(*) FROM orders`를 보고, 0이면 백필 SQL(`status='PAID'`·`order_number`·마켓별 `order_delivery_group`)을 단순화한다. 0이 아니면 결제 계획서 3-3의 백필을 그대로 쓴다.
2. **재고 예약의 자리(3-8).** 이번은 셀러 경로 보정으로 막는다. 셀러 재고 수정이 잦아지거나 어드민 강제 재고 조정이 생기면 `reserved_quantity` 컬럼으로 옮기고 읽는 곳(C7·장바구니·집계 쿼리)을 `stock − reserved`로 바꾼다.
3. **`/v1/user/**` 권한에 `CREATOR` 포함.** 크리에이터 계정이 소비자로 주문하는 것을 허용할지는 기획 확인 사항이다. 장바구니가 이미 허용하므로 결제도 같은 규칙으로 두되, 막아야 한다면 `SecurityConfig`가 아니라 서비스 계층(`RoleType`)에서 건다 — 장바구니·주문 두 곳.
4. **`market_inquiry_view`(C1)를 `order_delivery_group.market_id`로 옮길지.** 지금 뷰는 상품의 현재 마켓으로 문의를 분류한다. 주문 시점 마켓 스냅샷이 생기면 그쪽이 정확하지만, 상품이 마켓을 옮기는 경로가 없어 실익이 작다. 셀러 「판매 관리」 때 함께 본다.
5. **결제 계획서 9-1 ②·④·⑤·⑦·⑧·⑨·⑪·⑫·⑬**은 이 문서 범위 밖이며 그대로 남는다.
