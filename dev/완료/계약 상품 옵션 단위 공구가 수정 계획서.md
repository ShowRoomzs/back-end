# 계약 상품 옵션 단위 공구가 수정 계획서

Sep 27, 2026 · @hc

## 0. 결정 요약

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 계약서의 옵션 입력 | **옵션 행은 최소 물량(재고 확보 수량)만 받는다.** 공구가·리워드율은 지금처럼 **상품 단위** 하나다 | 시안(계약 상품 항목)이 옵션 행에 수량 칸만 두고 상품 행에 공구가·리워드율을 둔다. 「공구가·리워드율의 출생지 · 상품별 차등 가능」 문구 그대로다 |
| 상품 단위 최소 물량 | **옵션 합계의 파생값**. `contract_item.min_quantity` 컬럼은 **제거**하고 `ContractItem.getMinQuantity()`가 옵션 행을 합산한다 | 시안의 「최소 물량 · 옵션 합계」. 두 곳에 저장하면 어긋난다(26 설계 1-4 「예상 리워드는 저장하지 않는다」와 같은 원칙) |
| 옵션 행의 집합 | **상품의 현재 옵션 조합(`product_variant`) 전량**. 빼는 조작은 없다 — 수량 0은 「확보 약속 없음」이지 「판매 안 함」이 아니다 | 시안에 옵션 제외 UI가 없다. 옵션 없는 상품도 variant 1행이 있어 같은 구조로 다룬다 |
| 옵션가 정의 | **옵션가 = 옵션 정가(`product_variant.regular_price`) − 상품 정가(`product.regular_price`)**. 계약 시점에 옵션 정가를 **스냅샷**으로 복사하고 옵션가는 계산한다 | 셀러 상품 등록의 `VariantRequest.regularPrice`가 「판매가(옵션가 포함)」이고 C7·장바구니가 이미 이 값을 옵션 단가로 쓴다. `product_option.price`(옵션별 추가 가격)는 조합 단가와 대조되지 않아 원천으로 쓰지 않는다(9절 미결 ①) |
| 소비자 판매가 | **옵션 판매가 = 계약 공구가 + 옵션가**. 원천은 **계약 스냅샷**이지 `product_variant.sale_price`가 아니다 | `sale_price`는 옵션 생성 시 정가를 복사한 값이라 공구가가 반영되는 경로가 없다(결제 계획서 9-1 ①). 공구 중 셀러가 옵션 정가를 바꿔도 소비자 가격은 계약대로 고정된다 |
| 가격 해석기 | **`GroupBuyPriceResolver(groupBuyId, variantId)`** 하나가 C7 상세·옵션 시트·장바구니·주문 단가를 낸다. 계약에 옵션 행이 없으면 **empty = 이 공구에서 살 수 없는 옵션** | 결제 계획서 0절 「주문 단가」·7-1 `OrderPricingCalculator`가 이 해석기를 전제한다. 값이 없을 때 0이나 정가로 물러서면 공구가 없는 가격으로 결제된다 |
| 리워드 기준 | **공구가 × 리워드율(옵션가 제외)**. 지금과 같다 | 계약서 PDF의 「개당리워드」가 이 식이고 정산은 계약서를 근거로 한다(26 설계 1-5). 옵션가를 포함할지는 기획 확인 사항(9절 미결 ②) |
| 상품 관리 보호 | **계약에 묶인 상품은 옵션 구조를 바꿀 수 없다** — 셀러 상품 수정의 `optionGroups + variants` 전달(variant 전량 재생성)을 400으로 막는다. 재고만 수정은 허용 | 옵션 구조 수정은 `product.getVariants().clear()`로 variant를 지우고 다시 만든다. 계약 옵션 행이 가리키던 variant가 사라지면 해석기가 empty를 돌려줘 공구 중 상품이 통째로 구매 불가가 된다 |
| 공구 게시물 카드 | **변경 없음**. 카드의 정가·공구가는 상품 단위 그대로 | 카드는 옵션을 고르기 전 화면이다. 옵션가는 C7 옵션 시트에서 처음 보인다 |
| 배포 단위 | 계약 임시저장 PUT의 항목 스키마가 바뀐다(`items[].minQuantity` → `items[].options[]`). **파트너센터 FE와 같이 배포** | 전체 교체 시맨틱이라 옛 요청이 오면 옵션 행이 전부 비어 저장된다 |

## 1. 개요 · 범위

이 계획은 두 가지를 한다.

1. **계약 작성 화면(시안 「계약 상품 항목」)** — 상품 행 아래 옵션 행이 펼쳐지고, 옵션마다 최소 물량을 받는다. 상품 행의 최소 물량은 합계 표시다.
2. **실제 판매 가격** — 공구 게시물 → C7 → 장바구니 → 주문으로 이어지는 경로에서 옵션 가격을 **계약 공구가 + 옵션가**로 낸다. 결제 계획서가 비워 둔 `GroupBuyPriceResolver`를 만든다.

| 화면 · 접점 | 이번에 할 일 | 현재 상태 |
| --- | --- | --- |
| 파트너센터 계약 작성(B1·B2) | 폼 선택지에 옵션 동봉, 임시저장 `items[].options[]`, 검토 요청 검증 | 상품 단위 공구가·리워드율·최소 물량. 옵션 없음 |
| 계약 상세(파트너·스튜디오·어드민)·계약서 PDF | 옵션별 최소 물량·옵션가·옵션 판매가를 내린다 | 상품 단위 |
| 공구 상세(3서피스)·[확보 완료] 이력 | 옵션별 최소 물량 표시, 이력 문구에 옵션 내역 | 상품 단위 합계 |
| C7 상품 상세 · 옵션 재고 조회 | `groupBuyId`가 오면 옵션 판매가를 해석기로 낸다 | `product_variant.sale_price`(정가) |
| 장바구니·주문서·주문 단가 | 해석기를 쓴다 — **결제 계획서 7-1이 집행**한다 | 결제 계획서 PR 2·3 |
| 셀러 상품 수정 | 계약에 묶인 상품의 옵션 구조 변경 차단 | 무방비 — variant 재생성 |

**범위 밖** — 옵션별 공구가·리워드율(시안에 없다), 옵션별 판매 실적(판매 포트 `ItemQuantity`는 상품 단위 유지), 정산 규칙 변경, 장바구니·주문의 실제 코드 변경(결제 계획서 소관 — 이 문서는 해석기 인터페이스만 확정한다), 앱·파트너센터 FE.

## 2. 도메인 모델

### 2-1. 전체 그림

```
contract ──1:N── contract_item ──1:N── contract_item_option ──N:1── product_variant
                 (상품 · 공구가 ·        (옵션 · 최소 물량 ·                 (현재 재고 · 현재 정가)
                  리워드율 · 정가 스냅샷)   옵션 정가 스냅샷)
                       │
                       └── N:1 product
group_buy ──1:1── contract                      ← GroupBuyPriceResolver는 이 경로로 읽는다
```

- `contract_item`은 그대로 **상품 단위**다. 공구가·리워드율·정가 스냅샷의 자리는 바뀌지 않는다.
- `contract_item_option`이 새로 생긴다. **한 상품 행에 그 상품의 옵션 조합 전량**이 매달린다.
- 옵션 판매가는 저장하지 않는다 — `contract_item.group_buy_price + (contract_item_option.regular_price − contract_item.regular_price)`의 파생값이다.

### 2-2. `contract_item_option` — 계약 상품 옵션 항목

| 컬럼 | 타입 | 비고 |
| --- | --- | --- |
| `contract_item_option_id` | BIGINT PK | |
| `contract_item_id` | BIGINT FK → contract_item | `ON DELETE CASCADE` — 항목이 통째 교체될 때 함께 사라진다 |
| `variant_id` | BIGINT FK → product_variant, **NULL** | `ON DELETE SET NULL`. 종결 계약은 variant가 사라져도 스냅샷으로 남는다(아래) |
| `variant_name` | VARCHAR(255) NULL | **스냅샷** — 「단품」·「2개 세트」. 옵션 없는 상품은 NULL |
| `regular_price` | INT NULL | **스냅샷** — 계약 시점의 옵션 정가. 옵션가 = 이 값 − `contract_item.regular_price` |
| `min_quantity` | INT NULL | 최소 물량. 작성중은 NULL 허용, 검토 요청 시 필수 |
| `sort_order` | INT NOT NULL | 옵션 행 순서 — 상품의 variant 순서(`variant_id` 오름차순)를 복사 |

- `UNIQUE (contract_item_id, variant_id)` — 같은 옵션이 두 행이면 합계가 두 번 더해진다. `variant_id`가 NULL이면 MySQL 유니크는 통과하므로 NULL 행 중복은 서비스가 막는다(SET NULL은 삭제 결과라 새로 생기지 않는다).
- `CHECK (min_quantity IS NULL OR min_quantity >= 0)`, `CHECK (regular_price IS NULL OR regular_price >= 0)`.
- **옵션 판매가·옵션가는 저장하지 않는다.** 저장하면 정가 스냅샷을 갱신할 때(검토 요청·복제) 둘을 같이 고쳐야 하고, 하나를 빠뜨리는 날이 온다.

**`variant_id`가 NULL이 되는 경우** — 종결된 계약(DECLINED·EXPIRED·CANCELED, 또는 공구가 끝난 CONCLUDED)의 상품에서 셀러가 옵션 구조를 바꾸면 옛 variant가 지워진다. 계약서에는 스냅샷이 남고, 해석기는 NULL 행을 보지 않는다(살 수 없는 공구다). 진행 중 계약에서는 6-1의 가드가 먼저 막으므로 NULL이 생기지 않는다.

### 2-3. `contract_item` 변경

| 변경 | 내용 |
| --- | --- |
| `min_quantity` 컬럼 **삭제** | 백필(2-4) 뒤 제거. `ContractItem.getMinQuantity()`는 남기되 **옵션 합계를 돌려주는 파생 메서드**로 바꾼다 — 옵션 행이 없거나 하나라도 NULL이면 NULL. 호출처 8곳(공구 상세 3서피스·PDF·확보 완료 이력·조기 마감 근거·복제)은 시그니처가 같아 그대로 동작한다 |
| `options` 연관 추가 | `@OneToMany(mappedBy = "contractItem", cascade = ALL, orphanRemoval = true) @OrderBy("sortOrder")`. `replaceOptions(List)`로 통째 교체 |
| `resetNegotiatedValues()` | 상품이 바뀐 행은 옵션 행도 비운다 — 다른 상품의 variant가 남으면 안 된다 |
| `refreshSnapshot()` | 상품명·정가와 함께 **옵션 행의 `variant_name`·`regular_price`도 현재 값으로** 갱신한다. 정가만 갱신하고 옵션 정가를 옛 값으로 두면 옵션가가 어긋난다 |

### 2-4. 마이그레이션

| 파일 | 내용 |
| --- | --- |
| `V139__create_contract_item_option.sql` | 2-2 테이블 |
| `V140__backfill_contract_item_option.sql` | 기존 `contract_item` 행마다 상품의 현재 variant 전량을 옵션 행으로 넣는다(아래 규칙) |
| `V141__drop_contract_item_min_quantity.sql` | 백필이 끝난 뒤 컬럼 제거 |

번호는 잠정이다 — 결제 계획서 PR 1도 V139~V143을 잡아 두었다. **먼저 머지되는 쪽이 번호를 가져가고 뒤쪽이 밀린다.** 결제 계획서 9-1 ①의 순서(옵션 PR A → 결제 PR 2·3)상 이 문서가 앞설 가능성이 높다.

**백필 규칙** — 상품 하나의 옛 최소 물량을 옵션 여럿에 나눌 근거가 없다.

| 조건 | `min_quantity` |
| --- | --- |
| 상품에 variant가 1개 | 옛 `contract_item.min_quantity`를 그대로 |
| variant가 여럿 · 계약이 **편집 가능**(DRAFT·REVIEW_REJECTED) | NULL — 브랜드가 다시 입력한다. 검토 요청 시 3-3이 잡는다 |
| variant가 여럿 · 그 외 상태 | 대표 옵션(`is_representative`)에 옛 값 전부, 나머지 0. 대표가 없으면 `variant_id` 최솟값 행 |
| `product_id`가 NULL(미선택 행) | 옵션 행 없음 |

`variant_name`·`regular_price`는 백필 시점의 현재 variant 값이다. 체결된 계약의 「계약 시점 옵션 정가」는 복원할 수 없다 — 현재 값으로 대신하고 이력에 남기지 않는다. 운영 데이터에 체결 계약이 있으면 백필 전에 건수를 확인한다(9절 미결 ③).

## 3. 계약 작성 · 검증

### 3-1. 폼 선택지 — `GET /v1/seller/contracts/form-sources`

`products[]`에 옵션을 동봉한다. 옵션 행을 그리려면 상품 선택 즉시 옵션 목록이 필요하고, 드롭다운은 「진열 상품 전량 + 옵션 전량」을 한 번에 받는 구조다(`ContractFormSourcesResponse` 주석).

```jsonc
"products": [{
  "productId": 87, "productName": "수분진정 세럼 30ml", "regularPrice": 32000, "thumbnailUrl": "…",
  "options": [
    { "variantId": 301, "variantName": "단품",     "regularPrice": 32000, "stock": 420, "isRepresentative": true },
    { "variantId": 302, "variantName": "2개 세트", "regularPrice": 60000, "stock": 180, "isRepresentative": false }
  ]
}]
```

- `stock`은 **참고값**이다 — 시안 문구 「재고 선택」의 힌트로 쓰고 서버는 최소 물량 ≤ 재고를 판정하지 않는다. 최소 물량은 「확보를 약속하는 수량」이지 현재 재고가 아니다(계약 요구사항 「최소 물량」 행). 확보 여부는 공구 관리의 [확보 완료]가 브랜드의 자기 확인으로 다룬다.
- `optionExtraPrice`(옵션가)는 내리지 않는다 — 폼은 공구가를 입력받기 전이라 판매가를 그릴 수 없고, 상세 응답(3-4)이 낸다. FE가 미리 보여주려면 `regularPrice − 상품 regularPrice`로 계산한다.
- 조회: `ProductVariantRepository.findByProductIdInWithOptions(productIds)` 신설 — 진열 상품 N건에 N번 쿼리하지 않는다.

### 3-2. 임시저장 — `PUT /v1/seller/contracts/{id}` `items[]`

```jsonc
{ "contractItemId": 42, "productId": 87, "groupBuyPrice": 22000, "rewardRate": 15.0,
  "options": [
    { "contractItemOptionId": 7, "variantId": 301, "minQuantity": 200 },
    { "contractItemOptionId": 8, "variantId": 302, "minQuantity": 100 }
  ] }
```

| 규칙 | 집행 |
| --- | --- |
| `items[].minQuantity` **제거** | 스프링 기본은 모르는 필드를 조용히 버린다. 그러면 옛 FE가 저장한 계약의 물량이 전부 사라지므로, 레코드에 `@Deprecated Integer minQuantity`를 한 배포 주기 남겨 두고 값이 오면 400 `CONTRACT_ITEM_MIN_QUANTITY_MOVED`로 거부한다. 다음 배포에서 필드를 지운다 |
| `options[].variantId`는 `productId`의 variant여야 한다 | 아니면 400 `CONTRACT_ITEM_OPTION_NOT_OF_PRODUCT`. 남의 상품 variant를 붙이면 그 옵션의 정가가 이 계약에 스냅샷으로 들어온다(`resolveProduct`의 소유 검사와 같은 이유) |
| 같은 `variantId` 두 번 | 400 `CONTRACT_ITEM_OPTION_DUPLICATED` |
| 옵션 누락·상품 미선택 | **막지 않는다** — 임시저장은 형식만 본다(26 설계 0-3). 검토 요청 시 3-3이 본다 |
| 상품이 바뀐 행(`contractItemId`는 같은데 `productId`가 다름) | 공구가·리워드율과 함께 **옵션 행도 버린다**. 요청의 `options`는 무시하고 빈 목록으로 저장 — 다른 상품의 variant를 검사할 필요가 없다 |
| `minQuantity` | `@Min(0) @Max(1_000_000)`. NULL 허용 |
| 스냅샷 | `variant_name`·`regular_price`를 지금 variant 값으로 복사. 검토 요청 때 다시 맞춘다 |

`buildItems`는 요청 `options`를 `variantId` 순으로 정렬해 `sort_order`를 채운다 — 화면 순서가 아니라 variant 순서다. 옵션 행은 FE가 고르는 목록이 아니라 상품이 정하는 목록이라 순서를 FE에 맡기지 않는다.

### 3-3. 검토 요청 검증 — `ContractValidator.validateItems` 확장

| 코드 | 종류 | 판정 | 문구 |
| --- | --- | --- | --- |
| `ITEM_OPTIONS_MISMATCH` | RULE | 옵션 행의 `variant_id` 집합 ≠ 상품의 현재 variant 집합(누락·삭제·NULL) | 「옵션 구성이 바뀌었습니다. 상품을 다시 선택해 주세요.」 |
| `ITEM_OPTION_MIN_QUANTITY_REQUIRED` | REQUIRED | 옵션 행의 `min_quantity`가 NULL | 「옵션별 최소 물량을 입력해 주세요.」 |
| `ITEM_OPTION_SALE_PRICE_NEGATIVE` | RULE | 공구가 + 옵션가 < 0 | 「옵션 판매가가 0원 미만입니다.」 |

- 필드 경로: `items[i].options[j].minQuantity`. 상품 단위 항목(`ITEM_GROUP_BUY_PRICE_REQUIRED` 등)은 그대로다.
- 기존 검증에 **최소 물량 필수가 없었다**(요구사항 표는 「필수」인데 `ContractValidator`에 코드가 없다). 이번에 옵션 단위로 집행한다.
- `ITEM_OPTIONS_MISMATCH`가 잡힐 때 서버가 자동으로 옵션 행을 다시 만들지 않는다 — 브랜드가 입력한 수량을 서버가 임의 배분할 수 없다. 화면은 상품을 다시 선택하게 한다(상품 재선택 = 초기화, §25-5-3).
- `ITEM_OPTION_SALE_PRICE_NEGATIVE`는 옵션 정가가 상품 정가보다 낮고 그 차가 공구가보다 큰 극단에서만 걸린다. H1(공구가 ≤ 정가)이 있으므로 옵션 판매가 ≤ 옵션 정가는 자동으로 성립한다.
- 경고 W1(할인율 70% 초과)은 **상품 단위**로 유지 — 옵션가는 할인 대상이 아니다.
- `requestReview`의 `refreshItemSnapshots`가 옵션 스냅샷도 갱신한 뒤 검증한다. variant가 지워진 행은 `variant_id` NULL → `ITEM_OPTIONS_MISMATCH`.

### 3-4. 상세 응답 — `ContractDetailResponse.Item`

```jsonc
{ "contractItemId": 42, "productId": 87, "productName": "…", "regularPrice": 32000,
  "groupBuyPrice": 22000, "rewardRate": 15.0, "unitReward": 3300,
  "minQuantity": 300,                                   // 파생 — 옵션 합계. 옵션에 NULL이 있으면 null
  "options": [
    { "contractItemOptionId": 7, "variantId": 301, "variantName": "단품",     "regularPrice": 32000,
      "optionExtraPrice": 0,     "salePrice": 22000, "minQuantity": 200 },
    { "contractItemOptionId": 8, "variantId": 302, "variantName": "2개 세트", "regularPrice": 60000,
      "optionExtraPrice": 28000, "salePrice": 50000, "minQuantity": 100 }
  ] }
```

- `salePrice`는 `groupBuyPrice`가 NULL이면 null. `optionExtraPrice`는 두 정가 스냅샷이 있으면 항상 낸다.
- 스튜디오(`CreatorContractDetailResponse.Item`)·어드민(파트너 응답 재사용)도 같은 `options[]`를 받는다. 스튜디오의 `brandSupplyQuantity`는 합계로 유지.
- 계산은 `ContractItemOption.optionExtraPrice()`·`salePrice()` 도메인 메서드 한 곳이 한다 — 상세 3서피스·PDF·해석기가 같은 식을 부른다(`RewardCalculator`와 같은 이유).

## 5. 판매 가격 — `GroupBuyPriceResolver`

> 이 절은 **인터페이스와 규칙**을 정한다. 구현과 C7·장바구니·주문 적용은 「계약 가격 기준 판매·장바구니 가격 수정 계획서」가 든다(2026-09-27 이관). 5-2·5-3은 그 문서 4·5·6절이 대체한다.

### 5-1. 인터페이스

`domain/groupbuy/service/GroupBuyPriceResolver` — 공구 도메인이 소유한다. 계약을 직접 조인하는 곳은 여기 하나다.

```java
public interface GroupBuyPriceResolver {
    /** 이 공구에서 이 옵션을 살 때의 가격. 계약에 옵션 행이 없으면 empty — 살 수 없는 옵션이다. */
    Optional<GroupBuyPrice> resolve(Long groupBuyId, Long variantId);
    /** 상품의 옵션 전량 — C7 옵션 시트·주문서가 한 번에 받는다. 없는 variant는 맵에 없다. */
    Map<Long, GroupBuyPrice> resolveByProduct(Long groupBuyId, Long productId);

    record GroupBuyPrice(Long contractItemId, Long variantId,
                         int regularPrice,      // 옵션 정가 스냅샷 — C7 취소선
                         int groupBuyPrice,     // 상품 공구가
                         int optionExtraPrice,  // 옵션가
                         int salePrice) {       // 공구가 + 옵션가 — 주문 단가
    }
}
```

| 규칙 | 근거 |
| --- | --- |
| **공구 상태를 판정하지 않는다** | 판정 시점은 호출자마다 다르다 — C7은 `isOngoing(now)`, 주문 생성은 결제 계획서 4-6, 결제 확정은 「주문 뒤 30분」을 인정한다. 해석기가 상태로 empty를 돌려주면 마감 직전 주문의 결제 확정이 가격을 잃는다 |
| **`variant_id`가 NULL인 행은 보지 않는다** | 사라진 옵션이다 |
| **empty는 0이 아니다** | 0으로 물러서면 0원 결제, 정가로 물러서면 공구가 없는 결제다. 호출자는 empty를 「구매 불가」로 다룬다 |
| 캐시 없음 | 계약은 CONCLUDED 이후 불변이라 캐시할 이유가 있지만, 결제 경로에 캐시 무효화 버그를 들일 이유는 없다. 쿼리 하나다 |

구현 `ContractGroupBuyPriceResolver` — `ContractItemOptionRepository.findByGroupBuyIdAndVariantIdIn(groupBuyId, variantIds)`: `contract_item_option ⋈ contract_item ⋈ contract ⋈ group_buy(contract_id)`. `group_buy.contract_id`가 유니크라 공구 하나에 계약 하나다.

### 5-2. C7 상품 상세 · 옵션 재고 조회

결제 계획서 7-3이 `GET /v1/user/products/{id}?groupBuyId=`를 예고했다. 이 문서가 **가격**을 붙인다.

| 응답 | `groupBuyId` 없음 | `groupBuyId` 있음 · 계약에 상품 있음 | `groupBuyId` 있음 · 없음 |
| --- | --- | --- | --- |
| `salePrice`·`discountRate`(상품) | 지금과 같음(`product.sale_price`) | 대표 옵션의 `salePrice`, 할인율은 `DiscountRate.of(옵션 정가 스냅샷, salePrice)` | 지금과 같음, `groupBuyId: null`(결제 계획서 7-3) |

| `GET /products/{id}/variants/stocks` | 지금과 같음 | `groupBuyId`를 받아 같은 규칙 | 지금과 같음 |

### 6-1. 셀러 상품 수정 가드 — 옵션 구조 변경 차단

`ProductService.updateProduct`의 `hasOptionStructureUpdate`(`optionGroups + variants` 동시 전달) 분기 앞에서 판정한다.

```
차단 ⇔ ∃ contract_item_option o ⋈ contract_item i ⋈ contract c :
        i.product_id = :productId
        ∧ ( c.status ∈ {DRAFT, REVIEW_PENDING, REVIEW_REJECTED, SIGNING, CONCLUSION_PENDING}
          ∨ ( c.status = CONCLUDED ∧ group_buy.status ∉ {ENDED, SUSPENDED, SETTLED} ) )
```

- 400 `PRODUCT_OPTION_LOCKED_BY_CONTRACT` — 「진행 중인 계약·공구에 포함된 상품은 옵션 구성을 변경할 수 없습니다. 재고만 수정할 수 있습니다.」
- 재고만 수정(`hasStockOnlyUpdate`)은 허용 — variant를 지우지 않는다.
- 상품 정가 수정(`request.regularPrice`)은 막지 않는다 — 계약은 스냅샷을 쓰고, 검토 요청 시 H1이 현재 정가로 다시 본다(기존 규칙).
- **지금도** `cart.variant_id`·`order_product.variant_id` FK가 RESTRICT라 담긴 적 있는 상품의 옵션 구조 수정은 500으로 실패한다. 이 가드는 그 앞에서 계약 사유만 400으로 바꾼다. 장바구니·주문 사유는 상품 관리 소관(9절 미결 ⑤).

## 9. 미결 사항 · 작업 순서

### 9-1. 미결

1. **옵션가의 원천.** `product_variant.regular_price − product.regular_price`로 잡았다. `product_option.price`(옵션별 추가 가격)는 셀러 등록 화면이 받지만 조합 단가(`VariantRequest.regularPrice` 「판매가(옵션가 포함)」)와 대조하지 않아 둘이 어긋날 수 있다. 상품 관리가 둘 중 하나를 파생값으로 정리하면 이 문서의 정의도 그에 맞춘다. 옵션가가 10원 단위가 아닐 수 있다(옵션 정가 제약 없음) — H2는 공구가의 제약이라 옵션 판매가에는 걸지 않는다.
2. **리워드 기준에 옵션가를 포함할지.** 계약서 「개당리워드」는 공구가 × 리워드율이고 정산이 계약서를 근거로 한다. 2개 세트(판매가 50,000)와 단품(22,000)의 리워드가 같은 3,300원인 것이 기획 의도인지 확인. 포함한다면 계약서 규격·`RewardCalculator` 호출처 5곳·판매 포트 `ItemQuantity`가 옵션 단위가 돼야 한다.
3. **백필 대상 운영 데이터.** 체결 계약의 「계약 시점 옵션 정가」는 복원할 수 없어 현재 값을 쓴다. 백필 전 `SELECT COUNT(*) FROM contract_item WHERE min_quantity IS NOT NULL AND product_id IN (variant 2개 이상)`로 재분배 대상 건수를 본다.
4. **계약서 생성 규격 v0.1 개정** — 옵션 내역 행. 개정 전에는 합계만 인쇄한다(3-5).
5. **상품 관리의 옵션 구조 수정 자체.** `cart`·`order_product` FK RESTRICT 때문에 담긴 적 있는 상품은 이미 옵션 구조를 못 바꾼다(500). variant 재생성 대신 diff 갱신으로 바꾸는 것이 근본 해결이고 상품 관리 소관이다. 그때 6-1 가드는 「진행 중 계약의 옵션 삭제」만 막는 것으로 좁힌다.
6. **옵션별 판매 실적.** `GroupBuySalesReader.ItemQuantity`가 상품 단위라 「단품 200개 중 몇 개 팔렸나」는 못 본다. 공구 상세가 옵션별 소진율을 요구하면 포트를 옵션 단위로 넓힌다 — 결제 계획서 7-2 `OrderGroupBuySalesReader` 이후.
7. **최소 물량 상한.** `@Max(1_000_000)`은 임의값이다. 기획 상한이 있으면 맞춘다.

**PR A의 과도기 규칙** — A가 나가고 B(파트너센터 FE 동시 배포)가 늦어지는 사이에도 새 계약에 옵션 행이 있어야 한다. 옵션 행이 없는 계약으로 만든 공구는 해석기가 empty를 돌려 **판매 불가**가 된다.

> **구현 메모(2026-09-27)** — 배포 전 단계라 A·B·C·E를 한 번에 구현했고, 아래 과도기 규칙은 **만들지 않았다**. 옛 `items[].minQuantity` 필드는 받지 않고(모르는 필드는 무시된다) `items[].options[]`만 받는다. A와 B를 나눠 배포하게 되면 그때 이 규칙을 구현한다.

| 지점 | A에서의 동작(B가 대체할 때까지) |
| --- | --- |
| `PUT items[].minQuantity` | 계속 받는다. 서버가 상품의 현재 variant 전량으로 옵션 행을 만들고, 수량은 백필 규칙(2-4)과 같이 배분한다 — variant 1개면 그 값, 여럿이면 대표 옵션에 전부·나머지 0 |
