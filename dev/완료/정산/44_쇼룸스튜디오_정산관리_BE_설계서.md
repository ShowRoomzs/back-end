## 0. 먼저 정한 10가지

### 0-1. 도메인은 어드민 설계서가 정본이다 — 구현 순서가 스튜디오 먼저여도 **같은 행**을 읽는다

지금 코드에 정산은 포트 2개와 빈 구현뿐이다(`GroupBuySettlementGateway` · `GroupBuySettlementReader` · `Empty…`) — 공구 `SETTLED` 로 가는 `GroupBuyCommandService.markSettled` 를 아무도 부르지 않는다. 기획은 「기준은 어드민 07a · 07b」(§41-0)이고, 도메인(`domain.settlement`)의 테이블 · 산식 · 상태머신 · 스케줄러는 **어드민 설계서 1절 ~ 6절**이 정본이다. 구현 순서는 어드민 설계서 11-1 의 S1 ~ S3(테이블 · 생성 · 확정 · 지급)이 먼저이고 이 설계서의 API 는 그 위에 선다 — 어드민 **API**(S4)보다 스튜디오 조회가 먼저 들어가도 된다. 세 서피스가 같은 행을 읽어야 「두 화면 숫자가 다르다」는 문의에 한 행으로 답할 수 있다.

### 0-2. 정산 1건 = 공구 1건 — 생성 사건은 「마지막 하위주문 종결」이고 배치가 찾는다

§41-1 #7 · §41-3. `SettlementGenerationScheduler`(10분)가 `ENDED ∧ 정산 없음` 공구를 `GroupBuyCommandService.isSettlementReady` 로 판정해 만든다(어드민 설계서 2-1 · 공통 결정 #7 — 초안의 종결 전이 afterCommit 훅은 버렸다). 생성 시점에 분해 행 전부를 **스냅샷**한다 — 정산이 생긴 뒤의 주문 변화(운영자 사유 환불)는 **차감**(0-9)으로 다음 정산에 들어가는 것이지 이번 정산 금액을 바꾸지 않는다. 판매 0건 공구는 정산을 **만들지 않는다**(공통 결정 #16).

### 0-3. 상태 5종 — 스튜디오는 4종만 보고 **분배 실패는 지급 완료로 보인다**

`SettlementStatus { REVIEWING(정산 확인 중) · ADJUSTING(조정 협의) · PAYOUT_SCHEDULED(지급 예정) · PAID(지급 완료) · PAYOUT_FAILED(분배 실패) }`. 분배 실패는 어드민 전용이고(§41-2) 수취자 화면은 「지급 완료」다 — §46 A-4 미결을 그대로 따른다. 스튜디오 응답에는 `PAYOUT_FAILED` 가 **나가지 않는다**(`toCreatorStatus` 가 `PAID` 로 접는다). 「예정」 금액은 존재하지 않으므로 어느 상태에도 회색 · 예정 플래그가 없다.

### 0-4. 사업자 세금계산서는 정산 상태와 **다른 축**이다 — 발행 축이 인플루언서 몫 지급을 막는다

D5 ~ D5c 는 전부 정산 상태 「지급 예정」이고 세금계산서 카드만 4상태(발행 필요 · 확인 중 · 반려 · 확인 완료)로 갈린다. 둘을 한 enum 에 섞지 않고, `settlement_tax_document(type = CREATOR_TAX_INVOICE)` 한 행의 `status`(`PENDING_INPUT · SUBMITTED · REJECTED · VERIFIED`)가 카드 상태다(어드민 설계서 1-6 · 5-1). 반려 후 재제출은 **같은 행** `REJECTED → SUBMITTED`(초안의 「제출 1회 = 1행 · seq」는 버렸다 — 이전 반려 사유는 정산 이력에 남는다). 정산은 `creator_business_type`(생성 시점 스냅샷)만 든다 — 생성 뒤 온보딩 정보가 바뀌어도 이미 생긴 정산의 세무 처리는 바뀌지 않는다. 인플루언서 몫의 분배 조건은 「비사업자 ∨ `VERIFIED`」(어드민 설계서 5-4).

### 0-5. 조정 요청 · 응답 3종의 API 는 **이슈 스레드 설계서 3절**이다

`POST /v1/creator/settlements/{id}/adjustment`(요청) · `GET …/adjustment/preview`(미리보기) · `GET /v1/creator/threads/{threadId}/adjustment` · `POST /v1/creator/settlement-adjustments/{id}/proposals[/{pid}/accept|reject]` — 컨트롤러 `CreatorSettlementAdjustmentController`(같은 패키지 · 별도 클래스). 스레드는 **새 `ThreadKind.SETTLEMENT_ADJUSTMENT`** 이고 구 `GroupBuyIssue` · `GroupBuyIssueService.open` 은 쓰지 않는다 — 초안 11-3 #1 · #2(다른 유형 이슈가 열려 있으면 409)는 **해소**됐다. 이 설계서의 상세 응답은 **버튼 노출 판정 · 조정 내역 블록 · `threadId` 링크**만 든다(4-4). 요청 모달의 자동 계산(원천징수 · 실지급 · 원래 대비)은 FE 계산이 아니라 **서버 미리보기**(`GET …/adjustment/preview`)다 — 절사 규칙을 FE 가 들면 정산 화면과 1원이 어긋난다.

### 0-6. 돈은 **PG 3자 분배**로 나가고 코드에는 **포트**만 둔다 — `SIMULATED` 로 개발 · `PG` 는 런칭 게이트

어드민 설계서 0-5. `SettlementPayoutGateway` · `settlement.payout.mode = SIMULATED | PG`. `SIMULATED` 는 개발 · QA 전용이고 참조번호를 `SIM-` 으로 찍는다 — 운영 프로필은 `PG` 강제라 연동 전 운영 배포 불가(11-2 #1). 어느 서피스에도 「지급 실행」 버튼이 없다.

### 0-7. 세율 · 요율 · 기간은 **설정값이고 정산 행에 스냅샷**된다 · 원 단위는 전부 절사

`SettlementProperties(settlement.*)` — 3.3%(소득세 3% + 지방소득세 0.3% · **각각 절사**) · 부가세 10% · PG 3.0% · 플랫폼 0% · 확인 3영업일 · 지급 +3영업일 · 합의 10영업일. 생성 시점 값을 `withholding_income_rate` 등에 **저장**한다. 원 단위는 PG · 부가세 · 원천징수 **전부 절사(DOWN)**(공통 결정 #5 — 초안의 「PG · 부가세 반올림」은 버렸다 · 시안 D1 수치 30,294 · 91,800 은 나누어떨어져 같다). 플랫폼 수수료 0% 는 **행을 지우지 않는다** — `platform_fee_amount = 0` 으로 저장된다(스튜디오 응답에는 안 내린다).

### 0-8. 조회 전용이다 — 스튜디오의 쓰기는 **정산 조정 요청 · 응답(이슈 스레드 설계서) · 세금계산서 제출** 뿐이다

시안 「조회 전용 — 나도 돈을 만지지 않는다」. 금액 수정 · 지급 요청 · 앞당기기 · 승인 엔드포인트를 만들지 않는다. 목록에 체크박스 · 일괄 액션이 없으므로 다건 요청 API 도 없다. 「이슈 스레드 열기」는 상세 응답의 `adjustment.threadId` 로 **스튜디오 11 화면으로 이동**하는 링크이지 이 모듈의 API 가 아니다.

### 0-9. 차감(클로백)은 **플랫폼이 선집행한 환불의 회수**다 — 측별로 다음 정산에서 빼고 플랫폼 몫에 잡는다

어드민 설계서 0-8 · 6절. 운영자 사유 환불(`OperatorRefundReason` 4종 — 구매확정 후 하자 · 위해성 리콜 · 반려 이의 인용 · 검수 무응답) · 운영자 개설 반품 통과 환불은 PG 가맹점인 **플랫폼의 결제 잔고**에서 소비자에게 나간다. 이미 분배된 리워드는 **같은 인플루언서의 다음 정산**에서 회수되고(측별 · §46 A-3), 회수분은 그 정산의 플랫폼 몫에 더해진다. 시안 D3 「이전 회차 차감분의 브랜드 귀속 [확인 필요]」의 답 — 귀속 주체는 **환불을 선집행한 플랫폼**이다. `[자문대기-법률 J]` 근거 조항은 그대로 남는다. 차감이 리워드보다 크면 0 까지만 빼고 나머지는 이월된다(어드민 설계서 6-2).

### 0-10. 패키지 — API `api.creator.settlement` 하나 · 계좌 마스킹은 기존 규칙

도메인은 `domain.settlement`(어드민 설계서) · `domain.settlement.adjustment`(이슈 스레드 설계서). 입금 계좌는 **뒤 6자리 노출** 규칙(`SettlementAccountMasker` — `api.seller.basicinfo` 에서 `global.utils` 로 옮겨 두 서피스가 같이 쓴다 · 어드민은 쓰지 않는다)이고 시안의 `123-****-**89` 는 쓰지 않는다(공통 결정 #14 · 11-1 #13). 계좌가 비어 있으면(온보딩 미완료) 블록을 null 로.

## 2. 조회 API

권한 `CREATOR`(`SecurityConfig` `/v1/creator/**`). 인플루언서 식별은 공구 컨트롤러와 같이 `getCurrentUserEmail() → Creator`. **가시성은 `settlement.creator_id = 나`** 하나 — 남의 정산은 **404**(`SETTLEMENT_NOT_FOUND` · 31 설계 0-4 와 같은 이유로 403 을 쓰지 않는다 · 파트너 · 이슈 스레드 설계서와 같은 규칙).

### 2-2. 목록 — `GET /v1/creator/settlements`

| 파라미터 | 규칙 |

### 2-3. 요약 — `GET /v1/creator/settlements/summary`

```
{ totalPaid:        { amount, count },                 ← 내 행 PAID · Σ creator_payout_amount(세후) · 「누적 수령 1,127,522원 · 지급 완료 2건」
  payoutScheduled:  { amount, count, nearestDate },    ← 내 행 SCHEDULED · 가장 가까운 due_date(BLOCKED 는 count 에 들고 nearestDate 에서 제외)
  reviewing:        { count, nearestDueAt },           ← REVIEWING · 가장 빠른 review_due_at(「09.24 23:59까지」)
  adjusting:        { count },
  statusCounts:     { REVIEWING, ADJUSTING, PAYOUT_SCHEDULED, PAID },   ← 상태 칩 숫자
  attentionCount }                                     ← GNB 배지
```

- 전부 **인플루언서 전체** 기준이다 — 검색어 · 상태 칩과 무관(KPI 는 필터를 따라가지 않는다).
- 빈 상태(L2)는 `count = 0 · amount = null` 로 내린다 — 「0원이 아니라 —」(시안 L2).
- `attentionCount`(GNB 「정산 관리 1」) = **요청 가능 창이 열린 정산 확인 중** + **세금계산서 `PENDING_INPUT · REJECTED`**. 조정 협의의 「내 응답 필요」는 연결·소통 GNB(스레드 안 읽음)가 센다 — 같은 조치를 두 배지에 세지 않는다(공통 결정 #19 · 11-1 #6).

- `timeline.payoutDueDate` 는 **내 행** 기준이다. 사업자 발행 전은 `null` + `payoutDueNote = "발행 확인 후 + 3영업일"`(D5) · 확인 중은 `"확인 후 + 3영업일"`(D5a) · 반려는 `"재제출 확인 후 + 3영업일"`(D5b) — 서버가 문장을 내린다. 자동 확정 · 비사업자는 `"자동 확정 {MM.DD} + 3영업일"` · 합의 · 만료 확정은 `"합의 확정 {MM.DD} + 3영업일"` / `"기한 만료 확정 {MM.DD} + 3영업일"`.
- `review` 는 `status == REVIEWING` 에서만 — `canRequestAdjustment = now ≤ review_due_at ∧ adjustment == null`(어드민 설계서 3-1 식) · `maxRewardAmount` 는 포트 `find()` 값(어드민 설계서 4-1 · 10원 절사 · D1 예 5,396,720). 시안 C1 힌트 「0원 ~ 4,926,600원(브랜드 수취액)」은 상한 산식 확정 전 문구라 FE 가 서버 값을 그대로 찍는다(11-1 #3).
- `payouts.rows` 의 상태 문구: `WAITING`(확정 전) → 「확인 기간 후 지급」 · `HELD`(조정 협의) → 「보류 중」 · `BLOCKED`(사업자 발행 전) → 「발행 필요」/「확인 중」/「반려 · 재제출 필요」 · `SCHEDULED` → 「{MM.DD} 지급 예정」 · `PAID` → 「{MM.DD} 지급 완료」 · `FAILED` → **내 행**은 `status = FAILED` · 「지급 확인 중」(「실패」라는 말은 쓰지 않는다) · **브랜드 행**은 「지급 예정」으로 접는다(어드민 설계서 0-4 · §46 A-4 — 정산 라벨만 `PAID` 로 접는 것과 구분) · `NOT_APPLICABLE` → 「—」. 플랫폼 행은 항상 「플랫폼 신고 · 납부」/「부가세는 인플루언서에게 지급」. 금액은 생성 시 채워지므로(어드민 설계서 2-7) `shownAfterConfirm = true` 에서도 금액은 보인다.
- `adjustment.turn` — 이슈 스레드 설계서 1-5 · `MY_TURN`(「내 응답 필요」 경고) · `THEIR_TURN` · `OPEN_FLOOR` · `CLOSED`. `remainingBusinessDays = businessDaysBetween(today, deadline.date)`(「D-7」).
- `withholding.receiptAvailable = status == PAID ∧ WITHHOLDING_RECEIPT.status == GENERATED` — 그 전에는 「다운로드」 비활성(D1 ~ D3).
- `taxInvoice` 는 `creatorBusinessType == BUSINESS ∧ status ∈ {PAYOUT_SCHEDULED, PAYOUT_FAILED, PAID}` 에서만 — **확정 직후에 나타나는 카드**(시안 「왜 이 시점」 · 어드민 설계서 3-2 #3). `REVIEWING · ADJUSTING` 에서는 null. `rejectReason` 은 `TaxInvoiceRejectReason` enum(어드민 M4 3종) · 라벨은 서버.
- `payment.accountNumberMasked` 는 뒤 6자리 노출 규칙(0-10). 지시 후에는 내 행 스냅샷, 지시 전에는 `Creator` 현재 계좌 · `accountHolder = Creator.realName`. 계좌가 비어 있으면 블록 null(지급 시 `FAILED(ACCOUNT_MISSING)` → 어드민 재분배 · 어드민 설계서 13절 A-5).
- `items.preview` 는 `settlement_item` 주문번호 내림차순 5건 · `downloadAvailable = status ∉ {REVIEWING, ADJUSTING}`(공통 결정 #15).

### 2-5. 명세 — `GET /{id}/items`

`PageResponse<CreatorSettlementItem>` — `{ orderNumber, productName, optionName, quantity, settledQuantity, paidAmount, status, statusLabel, settledAmount, rewardRate, rewardAmount }`. 정렬 주문번호 내림차순. 페이지 조회는 상태 무관하게 열린다(정산이 생겼으면 금액은 확정값이다). `consumer_*` 는 **DTO 에 없다**.

## 3. 쓰기 API — 세금계산서 승인번호 제출

### 3-1. `POST /{id}/tax-invoice`(multipart)

```
approvalNumber: "20260829-41000012-38475920"
attachment: (PDF · 선택 · 10MB)
→ 200 { settlementId, taxInvoice: { cardStatus: "SUBMITTED", approvalNumber, submittedAt, attachmentName } }
```

실행은 어드민 설계서 5-2 `SettlementTaxDocumentService.submitCreatorInvoice` — 이 설계서의 커맨드 서비스는 소유 검사(404) · 첨부 검증 · S3 업로드(`settlements/{id}/tax-invoice/{documentId}.pdf` · private · `GroupBuyAppealAttachmentStorage` 와 같은 방식)만 하고 도메인 서비스를 부른다.

| 검증 | 결과 |
| --- | --- |
| 내 정산 아님 | 404 `SETTLEMENT_NOT_FOUND` |
| `creatorBusinessType ≠ BUSINESS` | 409 `SETTLEMENT_TAX_INVOICE_NOT_REQUIRED` |
| `status ∉ {PAYOUT_SCHEDULED, PAYOUT_FAILED}` 또는 문서 행 없음 | 409 `SETTLEMENT_TAX_INVOICE_NOT_OPEN` — 확정 전에는 카드가 없다 |
| 문서 `status ∈ {SUBMITTED, VERIFIED}` | 409 같은 코드 — 「확인 중에 독촉 버튼이 없다」 · 확인 완료 후 입력은 닫힌다(D5c) |
| 형식 `^\d{8}-\d{8}-\d{8}$` 불일치 · 빈 값 | 400 `SETTLEMENT_TAX_INVOICE_NUMBER_INVALID` — **형식 오류만 에러 문구**(D5b) · 빈 값은 FE 비활성 + 같은 400 |
| 같은 승인번호가 **다른 정산**에 `VERIFIED` | 400 같은 코드(중복) |
| 첨부가 PDF 아님 · 10MB 초과 | 400 `INVALID_INPUT_VALUE` |

결과: 문서 행 `PENDING_INPUT | REJECTED → SUBMITTED(approval_number · file_key · file_name · submitted_at · submitted_by)` · 이력 `TAX_INVOICE_SUBMITTED(CREATOR)` · afterCommit 운영자 알림 「대조 대기」. 반려 · 확인은 어드민 M4 — 확인 시 내 행 `BLOCKED → SCHEDULED(due = 확인일 + 3영업일)`. 재제출 시 이전 첨부는 새 키로 덮어쓴다(같은 행).

「발행 정보 복사」는 FE 클립보드다 — 상세의 `taxInvoice.supplier` · 금액 3종을 조립한다. 서버 API 가 없다.

## 4. 다운로드

### 4-1. 전체 명세 — `GET /{id}/items/download`(xlsx)

`status ∈ {REVIEWING, ADJUSTING}` 이면 409 `SETTLEMENT_STATEMENT_NOT_READY`(세 서피스 공통 · 공통 결정 #15). `ClaimReshipExcel` 과 같은 POI 경로. 열 = 주문번호 · 상품 · 옵션 · 수량 · 반영 수량 · 결제금액 · 상태 · 정산 반영액 · 리워드율 · 내 리워드 + 마지막 합계 행(확정 거래액 · 항목 리워드 합계 · 합의 후 리워드). 소비자 열 **없음**. 파일명 `정산명세_{settlementNumber}.xlsx`. 컬럼 구성은 §46 ③ 미결 — 어드민 설계서의 `SettlementStatementColumn` enum 을 같이 쓰되 소비자 열을 뺀다.

### 4-2. 원천징수영수증 — `GET /{id}/withholding-receipt`(PDF)

- `WITHHOLDING_RECEIPT` 행이 없거나 `status ≠ GENERATED` → 409 `SETTLEMENT_RECEIPT_NOT_READY`.
- 생성은 **어드민 설계서 5-3**(인플루언서 몫 `PAID` 전이에서 비동기 · `ContractPdfRenderer` · 실패 시 `PENDING_ISSUE` 유지 · 매시 40분 재시도). 내용: 발행 SHOWROOMZ(설정) · 수령자 실명 · 주민등록번호 · 지급일 · 지급액(차감 후 리워드) · 소득세 3% · 지방소득세 0.3% · 실지급액.
- 응답은 S3 presigned URL **리다이렉트**가 아니라 바이트 스트림이다(계약서 다운로드와 같이 — 링크가 밖으로 새지 않게).
- 영수증의 법정 서식 · 지급명세서 제출은 `[확인 필요-세무]`(어드민 설계서 C-8).

### 4-3. 연간 지급 내역 — `GET /annual-statement?year=`(xlsx)

`year` 의 **내 행 `paid_at`** 기준 지급 완료 정산 전부 — 행 = 정산번호 · 공구명 · 브랜드 · 지급일 · 판매 리워드 · 차감 · 원천징수(소득세 · 지방소득세) · 실지급액 + 합계. 비사업자 **종합소득세 신고용**이고 사업자는 세금계산서가 증빙이라 사업자에게는 부가세 열 · 승인번호 열이 대신 들어간다. `year` 생략 시 올해. 데이터 없음은 **빈 파일**이 아니라 404 `SETTLEMENT_NOT_FOUND` — 빈 엑셀은 「올해 소득 0」으로 읽힌다.

### 4-4. 제출한 세금계산서 PDF — `GET /{id}/tax-invoice/attachment`

`CREATOR_TAX_INVOICE.file_key` 스트림. 없으면 404. D5c 의 「세금계산서 PDF 다운로드」 — 첨부가 없었으면 버튼이 없다(`taxInvoice.attachmentName = null`).

## 5. 차감 · 알림 · 연계 — 스튜디오가 받는 것

### 5-1. 차감(어드민 설계서 6절)

`CREATOR` 행은 **같은 인플루언서의 다음 정산**에 들어가고 `APPLIED` 가 된다 — 상세 `clawbacks[]` 는 그 반영된 정산에서 보인다. 차감 발생 시점에 「다음 정산에서 {amount}원이 차감됩니다」 알림(§41-7 「사전 고지」). 탈퇴로 다음 정산이 생길 수 없는 행은 `UNRECOVERABLE`(표시는 어드민만). 스튜디오 06 탈퇴 반려 「정산이 끝나지 않았습니다」는 `SettlementReader.hasUnsettled(creatorId)`(어드민 설계서 8-5) — 호출처는 탈퇴 API 가 생길 때.

### 5-2. 알림 — `SettlementNotifier`(스텁 · 어드민 설계서)

인플루언서가 받는 것 — 생성(「{MM.DD} 23:59까지 확인 · 조정 요청 가능」) · 조정 요청 · D-1 · 확정(지급 예정일) · 세금계산서 발행 요청 · 확인 · 반려 · 지급 완료 · 차감 발생. 채널은 미정.

### 5-3. 연계

| 대상 | 내용 |
| --- | --- |
| 스튜디오 10 성과 관리 | 「판매 리워드 실지급」 줄은 `SettlementReader.findByGroupBuy` — 따로 계산하지 않는다 |
| 스튜디오 공구 상세(31 설계 4-5) | `settlement` 블록은 `settlementId` · `confirmedReward` 만 — `fixedFeeAmount · totalBeforeDeduction` 은 비운다(어드민 설계서 8-7 · 공구 설계서 후속) |
| 스튜디오 06 기본정보 | 주민등록번호 미등록 → 내 행 `BLOCKED(RESIDENT_NUMBER_MISSING)` · 등록 시 자동 해제(어드민 설계서 5-4) · 계좌 변경은 지시 전까지 반영 |

### 8-3. 다른 모듈 영향 — 이 설계서가 손대지 않고 **확인을 요청**하는 것

1. **파트너 C5 · 어드민 B5 「이슈 직접 개설」** — 이슈 스레드 설계서 7절이 `@Hidden` + 409 로 끈다. 새 스레드 종류가 따로 있어 열린 이슈 1건 제약과 무관하다.
2. **`GroupBuyIssueType` 4종** — 보존만(이슈 스레드 설계서 7절).
3. **`GroupBuy.fulfillment_*` 컬럼 · `isSettlementOnHold`** — 이행 확인 폐기(1009 6절)로 죽은 코드다. 정산은 읽지 않는다.
4. **스튜디오 공구 상세 `settlement` 블록**(31 설계 4-5) — 5-3.
5. **스튜디오 10 성과 관리** — `SettlementReader`(5-3).

### 8-4. 리스크

- **사업자 건의 지급 예정일 혼동** — 정산의 `payout_due_date` 는 브랜드 · 플랫폼 몫의 날짜다. 스튜디오는 **항상 내 행**을 읽는다 — 조회 서비스가 `settlement.payout_due_date` 를 직접 내리는 경로를 두지 않는다(C-01 · C-06 이 고정).
- **분배 실패 접기** — 정산 라벨은 `PAID` 로 접히고 내 행만 「지급 확인 중」이라, 상세를 열지 않으면 인플루언서는 입금이 없는데 목록은 완료로 보인다. §46 A-4 가 확정되기 전까지는 어드민 재분배 속도가 유일한 완화다.
- **PDF 생성 지연** — 영수증은 비동기 + 재시도라 지급 완료 직후 몇 분간 `receiptAvailable = false` 일 수 있다. FE 는 409 를 「준비 중」으로 그린다.
