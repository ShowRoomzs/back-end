## 0. 한눈에 — 무엇이 바뀌고 무엇이 그대로인가

| | 포트원 파트너 정산(지금) | 토스 지급대행(이후) | 영향 |
| --- | --- | --- | --- |
| 지급 실행 | **API 없음** — 운영자가 포트원 콘솔에서 일괄 지급(0-3 · 5-3 · 9-1) | `POST /v2/payouts` — **우리 배치가 실행** | 콘솔 단계 · 「지급 미실행」 알림 · 런북 9-1 **삭제**. §41-8 「지급 버튼 없음」이 사람 개입 없이 성립 |
| 지급 시점 | 콘솔 실행 시 | `EXPRESS`(당일 · 영업일 08:00 ~ 15:00 요청) / `SCHEDULED`(익일 ~ 1년 내 영업일) | 10:00 배치는 `EXPRESS`. 창 밖 지시(재분배)는 `SCHEDULED` 다음 영업일(D-2) |
| 원천징수 | 포트원이 뗄 수 있어 `deductWht=false` 강제 · Q2 | 토스에 세금 공제 기능 **없음** | 기동 검증 `deductWht` · `AMOUNT_MISMATCH` 분기 · 7절 Q2 **소멸**. 세후액 그대로 |
| 수취자 등록 | 파트너 — id 를 **우리가** 정함 · 예금주 조회 → 사업자 상태 조회 → 생성 | 셀러 — id 는 **토스가 발급**(≤35자) · `refSellerId`(7 ~ 20자) 는 우리 것 · 계좌 · 사업자 검증은 **등록 호출 안에서** 토스가 함 | 토스 `id` 저장 열 추가(V184). 예금주 · 사업자 조회 2단계 삭제 |
| 수취자 승인 | `PENDING → APPROVED`(포트원 심사) | 개인 · 개인사업자: `APPROVAL_REQUIRED`(**본인인증 SMS**) → `PARTIALLY_APPROVED`(주 1천만 원) → `KYC_REQUIRED` → `APPROVED`. 법인: 등록 즉시 `PARTIALLY_APPROVED` | 보류 사유 2종 추가 · 수취자 본인이 해야 하는 단계가 생김(L-2′) · 주당 한도 선검사 |
| 은행 | SDK enum ↔ 표준 코드 매핑표(`PortOneBanks`) | **금융결제원 3자리 코드 그대로**(`bank.bank_code`) | `PortOneBanks` 삭제. 미지원은 HSBC(054) 만 |
| 전송 보안 | SDK · API Secret | Basic 인증 + **JWE(alg `dir` · enc `A256GCM`)** 로 본문 암호화 · 응답도 암호화 | HTTP 클라이언트 · JWE 계층 신규(`nimbus-jose-jwt` — 이미 전이 의존성) |
| 결과 수신 | 폴링만(웹훅 없음) | 웹훅 `payout.changed` · `seller.changed`(HMAC-SHA256 서명) + 조회 API | 웹훅 수신 컨트롤러 신규 · 30분 폴링은 백스톱으로 유지 |
| 자금 | 지급대행(`AGENCY`) 출금 계좌 · 충전(Q3) | **잔액**(`GET /v2/balances` · `pendingAmount → availableAmount` 정산 주기) | 배치 앞단 잔액 선검사(D-9). 잔액이 결제 매출 정산금인지가 **최대 미결(Q1)** |

## 1. 토스페이먼츠 지급대행 API — 조사 결과(사실)

### 1-1. 엔드포인트

| 기능 | 메서드 · 경로 | 본문 암호화 |
| --- | --- | --- |
| 잔액 조회 | `GET /v2/balances` | — |
| 셀러 등록 | `POST /v2/sellers` | **JWE** |
| 셀러 수정 | `POST /v2/sellers/{id}` | **JWE** |
| 셀러 삭제 | `DELETE /v2/sellers/{id}` | — |
| 셀러 단건 · 목록 | `GET /v2/sellers/{id}` · `GET /v2/sellers?limit&startingAfter` | — |
| 지급 요청 | `POST /v2/payouts` | **JWE** |
| 지급 요청 취소 | `POST /v2/payouts/{id}/cancel` | — (본문 없음) |
| 지급 단건 · 목록 | `GET /v2/payouts/{id}` · `GET /v2/payouts?limit&startingAfter&payoutDateGte&payoutDateLte` | — |

- 부가 API 라 **별도 계약**이 필요하다. base URL `https://api.tosspayments.com`.
- 목록 응답은 커서(`hasMore · nextCursor · items`) · `limit` 기본 10 · 최대 10000. **`refSellerId` · `refPayoutId` 로 조회하는 필터는 없다**(id 분실 시 목록 스캔 — Q7).

### 1-2. 헤더 · 인증 · 암호화

| 항목 | 값 |
| --- | --- |
| 인증 | `Authorization: Basic base64("{secretKey}:")` — 콜론 필수 · `test_sk_` / `live_sk_` 접두로 환경 구분 |
| 암호화 모드 | `TossPayments-api-security-mode: ENCRYPTION` — 본문 있는 POST 3종에 필수. **응답(성공 · 실패)도 JWE** 라 같은 키로 복호화 |
| JWE | `alg = dir` · `enc = A256GCM` · 커스텀 헤더 `iat`(`yyyy-MM-dd'T'HH:mm:ss±hh:mm`) · `nonce`(UUID). 키 = 개발자센터 「API 개별 키 > 보안 키」 **64자 hex → 32바이트** |
| 멱등 | `Idempotency-Key`(≤300자 · **15일** 유효 · POST 만) — 같은 키 · URL · 메서드면 첫 응답을 돌려준다. `409 IDEMPOTENT_REQUEST_PROCESSING` 은 처리 중 |
| 기타 | 라이브에서 과다 요청 시 `429`. API 키 **허용 IP** 정책을 걸 수 있다 |

### 1-3. 셀러(Seller)

- 요청: `refSellerId`(필수 · **7 ~ 20자** · 등록 후 수정 불가) · `businessType ∈ {INDIVIDUAL, INDIVIDUAL_BUSINESS, CORPORATE}` · `company{name · representativeName · businessRegistrationNumber(하이픈 없는 10자리) · email · phone(하이픈 없는 8자 이상)}`(사업자 2종 필수) · `individual{name · email · phone}`(개인 필수) · `account{bankCode · accountNumber(하이픈 없이 ≤14자) · holderName(≤50자)}` · `metadata`(≤5쌍 · 키 ≤40자 · 값 ≤2000자).
- 응답: `id`(토스 발급 · ≤35자 · 불변 · 삭제돼도 재발급 안 됨) · `status` · 등록 정보.
- 수정: 바꿀 필드만 보냄 · `company.name/representativeName/email/phone` · `individual.email/phone` · `account` · `metadata` 만 가능. **사업자번호 · businessType 은 수정 불가**(폐업 → 삭제 후 재등록). **미완료 지급이 있으면 수정 · 삭제 불가**(`FORBIDDEN_SELLER_MODIFY · FORBIDDEN_SELLER_DELETE`).
- 상태:

| `status` | 뜻 | 지급 |
| --- | --- | --- |
| `APPROVAL_REQUIRED` | 개인 · 개인사업자 등록 직후. `phone` 으로 **본인인증 문자** 발송 | ❌ |
| `PARTIALLY_APPROVED` | 본인인증 완료 / 법인은 등록 직후 | ✅ **주당 1천만 원 미만** |
| `KYC_REQUIRED` | 주당 1천만 원 이상 지급 요청 시 전이(요청은 취소됨) · 이메일로 KYC 안내 · 사전 요청 불가 | ❌ |
| `APPROVED` | KYC 통과. **1년 또는 3년**마다 재심사(다시 `KYC_REQUIRED`) | ✅ 한도 없음 |

### 1-4. 지급(Payout)

- 요청: `refPayoutId`(필수 · ≤50자) · `destination`(셀러 `id`) · `scheduleType ∈ {EXPRESS, SCHEDULED}` · `payoutDate`(`SCHEDULED` 필수 · `yyyy-MM-dd` · **익일 09:00 부터 1년 이내 영업일** · 과거 · 휴일은 오류) · `amount` · `transactionDescription`(이체 적요 · **≤7자**) · `metadata`.
- 제약: 건당 **10억 원 미만** · 한 요청에 ≤100건이지만 **하나라도 실패하면 전체 실패**(첫 실패의 에러 반환). `EXPRESS` 는 **영업일 08:00 ~ 15:00** 에만 요청 가능 · 취소 불가. 취소는 `SCHEDULED` · `REQUESTED` 상태만.
- 응답: `id`(토스 발급 · ≤35자) · `refPayoutId` · `destination` · `scheduleType` · `payoutDate` · `amount{currency, value}` · `transactionDescription` · `requestedAt` · `status` · `error{code, message}` · `metadata`.
- 상태: `REQUESTED`(처리 전 · 취소 가능) → `IN_PROGRESS` → `COMPLETED` / `FAILED`(사유 `error`) · `CANCELED` · `REJECTED`(반려 · 웹훅은 `FAILED` 로) · `DELETED`(웹훅 없음).
- 「지급된 정산금은 회수가 어렵고 토스는 지급에 책임지지 않는다」 · **라이브에서 테스트하면 수수료 부과**.

### 1-5. 잔액(Balance)

`pendingAmount`(아직 지급 불가 — **매출은 정산 주기 2일 전에 여기 반영**) · `availableAmount`(지급 가능) · `KRW` 만. 정산 주기가 지나면 pending → available. 정산 주기 변경은 고객센터. 테스트 환경 응답에는 `availableAmount` 만. **충전 · 입금 방식은 문서에 없다**(Q1).

### 1-6. 웹훅

- 이벤트: `payout.changed`(`COMPLETED · FAILED` 로 바뀔 때 · `REJECTED` 는 `FAILED` 로 · `DELETED` 는 미발송) · `seller.changed`(4 상태로 바뀔 때 · 등록 직후 `APPROVAL_REQUIRED` 진입은 미발송).
- 페이로드: `eventType · createdAt · version · eventId · entityType · entityBody(Payout | Seller 객체)`.
- 서명(이 두 이벤트만): 헤더 `tosspayments-webhook-signature`(`v1:` + base64 · 쉼표로 여러 개) · `tosspayments-webhook-transmission-time` · `tosspayments-webhook-transmission-retried-count`. 검증 = `HMAC-SHA256(보안 키, "{payload}:{transmission-time}")` 과 서명 중 하나 일치.
- 재전송: **10초 내 200** 아니면 최대 **7회**(1 · 4 · 16 · 64 · 256 · 1024 · 4096분 뒤 — 마지막은 3일 19시간 뒤). 상점아이디(MID)별 등록 · 로컬 포트 URL 불가.

### 1-7. 에러 코드(지급대행)

| 영역 | 코드 → 우리 분류(5-5) |
| --- | --- |
| 공통 | `INVALID_REQUEST`(400) · `INVALID_ENCRYPTION`(400 · JWE 잘못) · `UNAUTHORIZED_KEY`(401) · `FORBIDDEN_REQUEST`(403 · **계약 없음 포함**) · `NOT_FOUND`(404) · `COMMON_ERROR`(500 · 일시) |
| 셀러 등록 · 수정 | `DUPLICATE_SELLER`(이미 있음 → 성공 취급 · id 복구) · `INVALID_BUSINESS_NUMBER` → `COMPANY_NOT_IN_BUSINESS` · `INVALID_ACCOUNT_INFO`(예금주 ≠ 계좌) · `NOT_SELLER_ACCOUNT`(본인 계좌 아님) → `ACCOUNT_HOLDER_MISMATCH` · `BANK_ACCOUNT_VERIFICATION_FAIL` → `BANK_REJECTED`(재시도) · `BUSINESS_REGISTRATION_LOOKUP_FAILED`(500 · 재시도) · `FORBIDDEN_SELLER_MODIFY` → `ACCOUNT_SYNC_FAILED` |
| 지급 요청 | `INVALID_PAYOUT_DATE` · `EXCEEDED_PAYOUT_DATE` · `INCORRECT_PAYOUT_DATE_FORMAT` → `REJECTED_BY_PG`(우리 날짜 계산 버그) · `EXCEEDED_PAYOUT_BALANCE_AMOUNT` → **`INSUFFICIENT_BALANCE`(신규 · 다음 영업일)** · `DUPLICATE_PAYOUT_REQUEST` → 성공 취급(조회) · `INVALID_SELLER_INFO` · `NOT_FOUND_SELLER` → `PARTNER_NOT_READY` · `FORBIDDEN_SELLER_PAYOUT`(본인인증 · KYC 필요) → `IDENTITY_VERIFICATION_REQUIRED` / `KYC_REQUIRED`(셀러 상태로 가름) · `FORBIDDEN_OVERDUE_PAYOUT_FEE`(이용료 미납) · `FORBIDDEN_ACCOUNT_SUSPENDED` → `PAYOUT_CONTRACT_BLOCKED`(신규 · 운영자) · `PREVIOUS_REQUEST_IN_PROGRESS` · `EXCEED_MAXIMUM_REQUESTS` → 결과 모름 취급(REQUESTED 유지 · 다음 폴링) |
| 취소 | `FORBIDDEN_PAYOUT_CANCEL_REQUEST`(REQUESTED 만 취소 가능) |
| 계좌 검증 | `NOT_AVAILABLE_BANK_ACCOUNT_VERIFICATION` — 은행 점검(23:30 ~ 00:30) · 재시도 권장 |

### 1-8. 테스트 환경

- 테스트 키로 **법인(`CORPORATE`) 셀러만** 유효한 사업자번호로 등록 가능. `KYC_REQUIRED` 까지는 가지만 테스트 KYC 가 없어 `APPROVED` 불가. 테스트 셀러에 주 1천만 원 이상 지급을 시도하면 그 셀러로 다시 지급할 수 없다.
- 실패 유도 계좌: `77701777777`(우리종합금융 295) · `3025353430761`(농협 011) · `02004240994312`(산업은행 002).
- 지급이 테스트에서 `COMPLETED` 까지 가는지 · 웹훅이 오는지는 문서에 없다(Q4).

### 1-9. 은행 코드

금융결제원 공식 3자리(`004 국민 · 088 신한 · 020 우리 · 081 하나 · 011 농협 · 090 카카오 · 092 토스 · 089 케이 · 003 기업 · 023 SC · 071 우체국 · 045 새마을 · 048 신협 · 007 수협 · 027 씨티 · 064 산림 · 050 저축은행 · 031 iM(대구) · 032 부산 · 039 경남 · 034 광주 · 037 전북 · 035 제주 · 002 산업 · 012 단위농협 · 030 수협중앙회` + 증권 `261 · 267 · 287 · 238 · 290 · 240 · 291 · 278 · 209 · 280 · 288 · 264 · 271 · 294 · 270 · 262 · 243 · 269 · 263 · 279 · 218 · 227 · 292 · 247 · 266`) — 우리 `bank.bank_code` 와 **같은 체계**. 지급대행은 **HSBC(054) 제외** 전 은행 지원.

## 2. 설계 결정(D) — 포트원 설계서의 「0절 먼저 정한 것」을 갈아 끼운다

| # | 결정 | 포트원 설계서의 어디를 대체하는가 |

| **D-1** | **지급은 우리 배치가 `POST /v2/payouts` 로 실행한다.** 사람의 손이 들어가는 단계가 없다 | 0-3 · 5-3 · 9-1 · 9-2 · Q1 **폐기**. `SettlementNotifier.payoutReadyForExecution` → `payoutRequestedSummary`(대사 요약으로 의미 변경) · `payoutExecutionOverdue` → `payoutStale`(「IN_PROGRESS 가 N영업일」) |

            → 웹훅 payout.changed  → TossPayoutWebhookController → SettlementPayoutWebhookService → applyLookupResults  (D-8 · 1차)
*/30 분    SettlementPayoutResultScheduler.tick → pollResults → gateway.lookup  (백스톱 · 웹훅과 같은 전이 · 멱등)

- 플랫폼 몫(`PLATFORM` 행)은 그대로 어댑터가 즉시 `PAID`(내부 계정).
- 확정 뒤 `SettlementPartnerSyncService.ensureForSettlement` 는 골격 유지. 개인 수취자는 등록 직후 `APPROVAL_REQUIRED` 가 **정상**이라 `BLOCKED(IDENTITY_VERIFICATION_REQUIRED)` + 수취자 알림 `partnerVerificationRequired`(신규 — 「토스페이먼츠 본인인증 문자를 확인해 주세요」). 지급 예정일(확정 + 3영업일)이 본인인증 기간이 된다.
- 계좌 변경(4-4): 토스도 셀러의 **현재 계좌**로 지급한다 — 지시 직전 스냅샷 계좌로 맞추는 5-2 ③ 그대로. 단 그 셀러에 `REQUESTED/IN_PROGRESS` 지급이 있으면 수정이 거절(`FORBIDDEN_SELLER_MODIFY`)되므로 **같은 날 두 회차 · 다른 계좌**(포트원 4-4 의 「다음 영업일로」)는 토스에서는 자연히 `ACCOUNT_SYNC_FAILED → 다음 영업일 재시도` 로 귀결 — `claim` 의 특수 처리 삭제.
