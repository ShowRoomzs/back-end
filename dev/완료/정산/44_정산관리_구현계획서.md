### 0-3. 왜 이 순서인가

1. **산식 → 생성 → 확정 · 지급 → 조회** 순. `SettlementCalculator` 는 단위 테스트로 더미 수치 3건(어드민 설계서 2-4)을 먼저 고정한다 — 세 화면이 같은 숫자를 보는 근거가 이 클래스 하나다.
2. **조회 ①(단계 4)을 조정 협의(단계 5)보다 먼저** — 조정 · 증빙 · 차감 블록은 전부 `null` · `[]` 로 시작해도 FE 가 기본 화면을 그릴 수 있다(설계서가 「서버가 안 내린다」 규칙을 이미 정했다). 조정 협의는 이슈 스레드 설계서 한 편 분량이라 따로 간다.
3. **조정 협의는 V179 머지 뒤 병행 가능** — 가짜 포트(`FakeSettlementAdjustmentPort`)로 단계 5-1 · 5-3 · 5-4 를 돌릴 수 있다(이슈 스레드 설계서 0-2). 포트 어댑터(5-2)만 단계 3 이 끝나야 한다.
4. **어드민 조회(단계 6)가 조정 협의 뒤** — 07a `ADJUSTING` 탭 · 07b 「조정 내역」 · `by-thread` 가 `SettlementAdjustmentReader` 를 읽는다.
5. **증빙(단계 7) · 차감(단계 8)은 각자 마이그레이션 1개** — 단계 3 의 확정 · 지급 흐름에 훅(`onConfirmed` · `onCreatorPaid` · `onRefundExecuted`)으로 붙는다. 앞 단계는 훅 자리만 두고 비워 둔다.
6. **마이그레이션은 4개 · 순서 고정** — V179(본체) → V180(조정) → V181(증빙) → V182(차감). 머지 순서가 바뀌면 번호만 민다(어드민 설계서 10절).
