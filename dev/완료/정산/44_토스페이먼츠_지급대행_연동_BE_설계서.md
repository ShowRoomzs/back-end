## 0. 먼저 정한 것 — 토스 지급대행의 사실과 그로부터 나온 결정

### 0-1. 토스 지급대행은 「우리 잔액에서 셀러 계좌로」다 — 플랫폼이 대금을 받는다(포트원 0-1 유효)

잔액(`GET /v2/balances`)은 `pendingAmount`(정산 전 · 「매출은 정산 주기 2일 전에 반영」)와 `availableAmount`(지급 가능)로 나뉘고, 지급 요청은 `availableAmount` 안에서만 된다. 즉 결제 대금은 **우리 상점**에 정산되고 토스는 그 잔액에서 셀러에게 송금한다. 포트원 설계서 0-1 의 기획 · 법무 영향(「돈이 안 들어왔다」의 응답 주체 = 우리 · 전자금융거래법 검토 · **L-1**)은 그대로다. 잔액이 **어느 MID 의 매출**인지(우리 결제는 포트원 허브형) · 충전이 가능한지는 **Q1** — 이 설계서는 어느 답이든 어댑터가 같도록 「잔액은 바깥에서 들어오고 우리는 선검사만 한다」로 잡는다(5-1).

### 0-2. 산식은 우리가 소유하고 토스는 **지급만** 한다 — 세후 실지급액을 그대로 올린다

토스 지급대행에는 수수료 · 세금을 계산하는 기능이 **없다**(요청 필드가 `amount` 하나). 원천징수(소득세 · 지방소득세 각각 절사)는 `SettlementCalculator` 가 계산한 `creator_payout_amount`(세후)를 그대로 보낸다. 포트원의 `deductWht` 기동 검증 · 이중 공제 걱정 · `AMOUNT_MISMATCH` 분기는 **없다**. 응답 `amount.value` 는 방어적으로 비교해 다르면 `WARN` 로그만(5-4).

### 0-3. 지급 실행은 **우리 배치**가 한다 — 사람의 손이 들어가는 단계가 없다

`POST /v2/payouts` 가 지급을 **실행**한다. 운영자가 PG 콘솔에 들어가는 단계(포트원 0-3 · 5-3 · 9-1 · 9-2)는 없다. §41-8 「지급 버튼은 어느 서피스에도 없다」가 사람 개입 없이 성립한다. 운영자가 보는 것은 **대사 요약 알림**(지시 N건 · 합계 · 토스 조회 건수 일치 여부 · 5-3)과 **실패 · 보류 · 연기** 알림이다.

### 0-4. 지급 유형은 **지시 시각**이 정한다 — `EXPRESS`(당일) · `SCHEDULED`(다음 영업일)

`EXPRESS` 는 **영업일 08:00 ~ 15:00** 에만 요청할 수 있고 당일 지급 · 취소 불가. `SCHEDULED` 는 `payoutDate`(**익일 09:00 부터 1년 이내 영업일** · 과거 · 휴일은 오류) 에 지급 · `REQUESTED` 동안 취소 가능. 10:00 지급 배치는 항상 `EXPRESS`, 어드민 재분배(M3 · 즉시 지시)와 배치 지연은 창 밖이면 `SCHEDULED(payoutDate = 다음 영업일)`. 판정은 어댑터가 `PayoutCommand.requestedAt` 과 우리 `BusinessCalendar` 로 한다(5-2 ②). 영업일 기준이 토스와 같은지는 **Q3**.

### 0-5. 셀러 id 는 **토스가 발급**한다 — 우리 참조 id 와 둘 다 저장한다

포트원은 파트너 id 를 우리가 정했지만 토스는 `id`(≤35자 · 불변 · 삭제돼도 재발급 안 됨)를 발급하고 우리는 `refSellerId`(**7 ~ 20자** · 등록 후 수정 불가)를 붙인다. 조회는 `id` 로만 된다(`refSellerId` 필터 없음). 그래서 **`id` 를 잃으면 안 된다** — 등록 응답 즉시 `seller.pg_partner_id` / `creator.pg_partner_id` 에 적고, `DUPLICATE_SELLER`(우리 DB 에 없는데 토스에 있다 — 이전 시도의 커밋 실패)는 `GET /v2/sellers` 목록을 커서로 훑어 `refSellerId` 가 같은 것을 찾아 복구한다(4-2 ⑤ · Q7). 지급 `id` 도 같다 — 요청 응답에 바로 오므로 `REQUESTED` 전이에서 `pg_payout_id` 를 함께 적는다(3-2).

### 0-6. 멱등은 `Idempotency-Key` 가 맡는다 — 키는 우리 참조 id 에서 결정적으로

`POST` 는 `Idempotency-Key`(≤300자 · **15일** 유효 · 같은 키 · URL · 메서드면 첫 응답을 돌려줌)를 받는다. 지급 요청 키 = `UUID.nameUUIDFromBytes(refPayoutId)`, 셀러 등록 키 = `UUID.nameUUIDFromBytes(refSellerId)`. 통신 실패 · 타임아웃 뒤 재시도(다음 배치 · 폴링)가 15일 안이면 **같은 응답(같은 `id`)** 을 받아 이중 지급이 없다. 15일이 지난 재시도는 `DUPLICATE_PAYOUT_REQUEST` 로 거절되고 — 그때는 `payoutDate` 범위 목록 조회에서 `refPayoutId` 일치로 `id` 를 찾는다(5-4 ②). 「에러 뒤 멱등키를 바꿔 재시도하는 것은 위험」(토스 가이드) — 우리는 키를 **바꾸지 않는다**(같은 행 = 같은 refPayoutId = 같은 키). 재분배는 `attempt + 1` 로 **새 refPayoutId** 다.

### 0-7. 계좌 · 사업자 검증은 토스가 등록 호출 안에서 한다 — 우리는 프로필 완전성만 본다

예금주 조회 · 사업자 상태 조회 API 가 따로 없다. `POST /v2/sellers` 가 계좌(`INVALID_ACCOUNT_INFO` · `NOT_SELLER_ACCOUNT` · `BANK_ACCOUNT_VERIFICATION_FAIL`)와 사업자번호(`INVALID_BUSINESS_NUMBER` · `BUSINESS_REGISTRATION_LOOKUP_FAILED`)를 검증해 코드로 거절한다. 우리 사전 검사는 길이 · 형식(4-2 ①)만 — PG 를 부르기 전에 우리가 아는 사유로 거절하는 원칙은 같다.

### 0-8. 셀러 승인에 **수취자 본인**이 끼어든다 — 본인인증 · 주당 한도 · KYC

개인 · 개인사업자 셀러는 등록 직후 `APPROVAL_REQUIRED` 이고 토스가 `phone` 으로 **본인인증 문자**를 보낸다. 본인이 끝내면 `PARTIALLY_APPROVED`(**주당 1천만 원 미만** 지급 가능). 법인은 등록 즉시 `PARTIALLY_APPROVED`. 주당 1천만 원 이상 지급을 요청하면 **그 요청은 취소되고** 셀러가 `KYC_REQUIRED`(지급 전면 불가 · 이메일로 KYC 안내 · 사전 요청 불가)로 넘어가며, KYC 를 통과하면 `APPROVED`(한도 없음 · 1 년 또는 3 년마다 재심사 → 다시 `KYC_REQUIRED`).

결정 — ① `PARTIALLY_APPROVED` · `APPROVED` 를 **지급 가능**으로 본다 ② `APPROVAL_REQUIRED` → `BLOCKED(IDENTITY_VERIFICATION_REQUIRED)` · `KYC_REQUIRED` → `BLOCKED(KYC_REQUIRED)` 로 두고 **수취자에게** 안내한다(알림 훅 신규 · 화면 문구는 기획 L-2′) ③ `PARTIALLY_APPROVED` 수취자는 **주당 한도를 우리가 먼저 센다**(5-2 ① — 토스에 그대로 던지면 그 요청만 취소되는 게 아니라 셀러가 `KYC_REQUIRED` 로 넘어가 **다른 회차까지 막힌다**) ④ `seller.changed` 웹훅이 오면 배치를 기다리지 않고 즉시 보류를 푼다(4-3).

### 0-9. 결과는 웹훅이 1차, 폴링이 백스톱 — 둘은 같은 전이를 탄다

`payout.changed`(`COMPLETED · FAILED` 로 바뀔 때 · `REJECTED` 는 `FAILED` 로 · `DELETED` 는 미발송)와 `seller.changed` 가 **HMAC-SHA256 서명**으로 온다. 10초 내 200 을 주지 않으면 최대 7회 재전송(3일 19시간). 웹훅은 DB 전이만 하고 외부 호출을 하지 않는다. 30분 폴링(`SettlementPayoutResultScheduler`)은 그대로 두어 웹훅 유실 · 서명 실패 · `IN_PROGRESS` 장기화를 잡는다. 두 경로는 `SettlementPayoutTransitions.applyLookupResults` 하나로 닫히고 **멱등**이다(이미 `PAID` 면 무시).

### 0-10. 테스트 모드는 **테스트 키**다 — 법인 셀러만 등록된다

`test_sk_` 키의 데이터는 라이브와 분리된다. 테스트 환경은 **유효한 사업자번호의 법인(`CORPORATE`) 셀러만** 등록되고 `APPROVED` 까지 못 가며(테스트 KYC 없음), 실패 유도 계좌 3개를 준다. 그래서 `settlement.payout.mode` 는 그대로 셋 — `SIMULATED`(토스 호출 없음) · `PG_TEST`(`test_sk_` · 비법인 수취자는 `toss.payouts.test.corporate-override-brn` 으로 대체 등록) · `PG`(`live_sk_`). `PG` 에서 대체 사업자번호가 차 있으면 **기동 실패**(6-4).

### 0-11. 결제 연동과 **같은 켤레**로 만든다 — SDK 가 없을 뿐

토스 공식 Java SDK 는 없다. Spring `RestClient`(Boot 3.5.7) + `nimbus-jose-jwt`(JWE · 이미 `oauth2-client` 전이 의존성 — 명시 선언) 로 만들고, 실패 분류(4xx 코드 = 결과 확정 실패 `PaymentGatewayRejectedException` / 통신 · 5xx · `429` · 복호화 실패 = 결과 모름 `PaymentGatewayException`) · 타임아웃 · 시크릿 로그 금지 · 웹훅 원문 바이트 검증은 `PortOneV2Gateway` · `PortOneWebhookController` 와 같은 방식이다.

## 2. 전제 · 자격

### 2-1. 계약 · 키 — 착수 게이트

지급대행은 **부가 API · 별도 계약**이다. 계약이 없으면 전 호출이 `403 FORBIDDEN_REQUEST`. 받아야 할 것 — ① 테스트 · 라이브 **시크릿 키**(`test_sk_…` / `live_sk_…` · Basic 인증) ② **보안 키**(개발자센터 「API 개별 키 > 보안 키」 · 64자 hex · JWE 와 웹훅 서명 둘 다) ③ 웹훅 URL 등록(MID 별 · 테스트 · 라이브 각각 · 로컬 포트 URL 불가) ④ 라이브는 **API 키 허용 IP**(Q10). 켜졌는지는 `GET /v2/balances` 한 번으로 확인한다.

### 2-2. 결제(포트원)와의 관계

결제는 포트원 허브형으로 토스에 들어가고, 지급대행은 토스 **직접** API 다. 키 · base URL 을 공유하지 않는다 — 설정 네임스페이스가 `toss.payouts.*` 로 따로 있다(6-3). 잔액이 결제 매출 정산금인지(같은 MID 인지)는 **Q1**.

### 2-3. 토스 콘솔(개발자센터)에서 1회 할 것

| 항목 | 값 | 이유 |
| --- | --- | --- |
| 웹훅 등록 | `https://{host}/v1/webhooks/toss/payouts` · 이벤트 `payout.changed` · `seller.changed` | 5-4 · 4-3 |
| 허용 IP(라이브) | 운영 서버 egress IP | 2-1 ④ |
| 정산 주기 확인 | `pendingAmount → availableAmount` 전환 주기 | 지급 예정일(확정 + 3영업일 · `payout-business-days`)이 매출 정산보다 **빨라** 잔액이 비는지 — Q1 · 9-2 |

### 2-4. 라이브러리

`com.nimbusds:nimbus-jose-jwt`(Spring Boot BOM 관리 · `oauth2-client` 가 이미 끌어옴 — `build.gradle` 에 **명시**) · `org.springframework.web.client.RestClient`(spring-web · 추가 의존성 없음). `io.portone:server-sdk` 는 결제가 쓰므로 유지.

### 4-2. 절차 — `ensure(settlementId, payee)` (확정 트랜잭션 **밖** · 4-3)

1. **프로필 완전성**(우리가 아는 사유로 먼저 거절 — PG 호출 없음) — 계좌 비면 `ACCOUNT_MISSING` · 은행 코드 없음/`054` → `UNSUPPORTED_BANK` · 계좌번호 >14자 · 예금주 >50자 → `ACCOUNT_INVALID`(신규) · 사업자번호 ≠ 10자 · 전화 <8자 · 이메일 없음 · 대표자명 없음 → `PARTNER_NOT_READY`(사유 문구).
2. **최신인가** — `pg_partner_id` 있고 · `pg_partner_env` = 현재 모드 · 계좌 지문 같고 · `pg_partner_status ∈ {PARTIALLY_APPROVED, APPROVED}` 면 **끝**(호출 없음).
3. **연결 없음**(`id` 없음 · env 불일치) → `POST /v2/sellers`(JWE · `Idempotency-Key = UUIDv3(refSellerId)`).
   - 성공 → `id · status` 저장.
   - `DUPLICATE_SELLER` → **id 복구**: `GET /v2/sellers?limit=10000` 을 `startingAfter` 커서로 훑어 `refSellerId` 일치 항목의 `id`(Q7 — 응답에 id 가 오면 스캔 생략). 못 찾으면 `PARTNER_NOT_READY("중복 셀러 · id 복구 실패")` + 운영자 알림.
   - `INVALID_BUSINESS_NUMBER` → `businessType` 을 반대(법인 ↔ 개인사업자)로 **1회 재시도** · 그래도 실패면 `COMPANY_NOT_IN_BUSINESS`.
   - 그 밖 4xx → 5-5 분류 · 5xx `COMMON_ERROR` · `BUSINESS_REGISTRATION_LOOKUP_FAILED` · `NOT_AVAILABLE_BANK_ACCOUNT_VERIFICATION`(은행 점검 23:30 ~ 00:30) · 통신 → 예외(결과 모름 → 호출자가 `PARTNER_NOT_READY("PG 호출 실패")` 로 보류 · 배치 앞단이 재시도).
4. **연결 있음 · 지문 다름**(계좌 · 연락처 변경) → `POST /v2/sellers/{id}`(바꿀 필드만 · JWE). `FORBIDDEN_SELLER_MODIFY`(미완료 지급 있음) → `ACCOUNT_SYNC_FAILED` — 다음 기회(배치 앞단 · 지시 직전)에 다시. `NOT_FOUND`(토스에서 삭제됨) → 연결을 지우고 ③ 으로.
5. **연결 있음 · 지문 같음 · 상태만 미승인** → `GET /v2/sellers/{id}` 로 상태 재조회(본인인증을 끝냈는데 웹훅을 놓친 경우).
6. 응답 `status` 를 `pg_partner_status` 에 원시값으로 · `pg_partner_ref · env · synced_at · account_hash`(승인 상태일 때만 지문 저장). `PartnerResult` 매핑 — `PARTIALLY_APPROVED | APPROVED → APPROVED` · `APPROVAL_REQUIRED → PENDING(IDENTITY_VERIFICATION_REQUIRED)` · `KYC_REQUIRED → PENDING(KYC_REQUIRED)`.

| 시점 | 호출 | 실패하면 |

| **지급 배치 앞단** `releaseBlocked` | `BLOCKED` 행 중 파트너 사유 코드(`PARTNER_CODES`)를 다시 `ensure`(4-2 ⑤ 로 상태 재조회) | 성공하면 `SCHEDULED(due = max(예정일, 오늘))` |
| **지시 직전** `claim` 안(5-2 ③) | 확정 때 고정한 계좌 ≠ 셀러 현재 계좌면 `POST /v2/sellers/{id}`(계좌만) | `FORBIDDEN_SELLER_MODIFY` · 그 밖 실패 → 그 행 `FAILED(ACCOUNT_SYNC_FAILED)` · 재분배로 |

### 4-4. 계좌 갱신과 「확정 회차는 기존 계좌」(공통 결정 #14)의 양립

토스 지급도 **셀러의 현재 계좌**로 간다(`destination = 셀러 id` · 요청에 계좌 없음). 그래서 지시 직전(5-2 ③)에 행의 스냅샷 계좌로 셀러를 맞추고 지시한다 — 포트원 4-4 와 같다. 다른 점 하나: 그 셀러에 `REQUESTED · IN_PROGRESS` 지급이 있으면 토스가 수정을 **거절**(`FORBIDDEN_SELLER_MODIFY`)하므로, 같은 날 두 회차 · 다른 계좌는 뒤 회차가 `FAILED(ACCOUNT_SYNC_FAILED)` → 다음 영업일 재분배로 **자연히** 귀결된다. 포트원 설계서의 `claim` 특수 처리(「같은 파트너 · 다른 계좌 행이면 `due + 1영업일`」)는 **삭제**한다 — 토스가 이미 그 규칙을 강제한다.

### 4-5. 은행 코드

`bank.bank_code`(금융결제원 3자리)를 **그대로** `bankCode` 로 보낸다. 매핑표(`PortOneBanks`)는 없다. 미지원 = `054`(HSBC) 만 — `TossSellerRegistrar` 의 상수 집합 `UNSUPPORTED_BANK_CODES = {"054"}`. 토스가 그 밖의 코드를 거절하면 `INVALID_REQUEST → REJECTED_BY_PG` 원문으로 남는다(새 코드가 나오면 집합에 추가).

### 5-1. 흐름(예정일 D)

플랫폼 몫(`PLATFORM` 행)은 어댑터가 즉시 `PAID`(내부 계정 · 요청하지 않는다 · 참조 `PLATFORM-{정산번호}`).

**① 잔액 선검사(`SettlementPayoutService.distributeDue`)** — `availableBalance()` 가 비면(SIMULATED) 건너뛴다. `available < ourTotal` 이면 예정 정산을 **수취자 행 합계 내림차순**으로 정렬해 누적이 `available` 을 넘지 않는 것까지만 `distribute` 하고, 나머지 정산의 `SCHEDULED` 행은 `deferForBalance(payoutId, nextBusinessDay)` — `due_date = 다음 영업일` · `attempt` 불변 · 이력 `PAYOUT_DEFERRED("잔액 부족 · {D+1} 로 연기")` · 운영자 알림 `payoutBalanceInsufficient(D, available, ourTotal, deferredCount)`. 동기 거절 `EXCEEDED_PAYOUT_BALANCE_AMOUNT`(선검사와 실제 사이에 잔액이 줄었다)도 같은 처리 — `LineResult(DEFERRED)` 신규 Outcome → `applyResults` 가 `REQUESTED` 를 `SCHEDULED(+1영업일)` 로 되돌린다(`requested_at` 비움).

### 5-2. 지시 — `distribute(PayoutCommand)` 의 어댑터 구현

행마다(BRAND · CREATOR) — **1행 = 1요청**(토스는 ≤100건 묶음을 받지만 하나라도 실패하면 전체가 실패하므로 묶지 않는다):

1. **주당 한도**(어댑터가 아니라 `claim` 안 · 도메인) — 수취자의 `pg_partner_status == PARTIALLY_APPROVED` 면 `sumRequestedOrPaidSince(payee, refId, now − 7일)` + 이 행 금액 ≥ `settlement.payout.weekly-limit-amount`(1천만) → 이 행은 지시하지 않고 `BLOCKED(KYC_REQUIRED, "주당 한도 초과 예상 — KYC 완료 후 지급")` · 운영자 알림 `payoutCheckRequired`. `APPROVED` 면 검사 없음. `pg_partner_id` 없음 → `FAILED(PARTNER_NOT_READY)`(확정 때 보장했어야 한다 — 여기서 만들지 않는다).
2. **유형 판정** — `requestedAt` 이 영업일 `[08:00, 15:00)` 안이면 `EXPRESS`(payoutDate 없음) · 아니면 `SCHEDULED` · `payoutDate = businessCalendar.addBusinessDays(requestedAt.toLocalDate(), 1)`. 창 경계는 설정 `toss.payouts.express-window-start/end`(기본 08:00 / 15:00 · Q3 로 보정) — 15:00 정각은 창 밖으로 본다(토스가 거절하는 쪽보다 하루 늦는 쪽이 낫다).
3. **계좌 동기화** — `GET /v2/sellers/{id}` → `account.bankCode · accountNumber` 가 행 스냅샷(`bankCode · 숫자만 비교`)과 다르면 `POST /v2/sellers/{id}`(계좌만). 실패 → `FAILED(ACCOUNT_SYNC_FAILED)` · 다음 행으로.
4. `POST /v2/payouts` — 본문 `{ refPayoutId, destination: sellerId, scheduleType, payoutDate?, amount, transactionDescription, metadata }` · JWE · `Idempotency-Key = UUIDv3(refPayoutId)`.
   - 2xx → `LineResult(REQUESTED, pgReference = id, …, pgTransferId = refPayoutId, scheduleType, payoutDate)`. 응답 `status` 가 이미 `FAILED/REJECTED`(즉시 반려)면 `FAILED(classify(error))`.
   - `DUPLICATE_PAYOUT_REQUEST`(멱등 키 15일 만료 뒤 재시도) → **성공 취급** · `id` 는 5-4 ② 경로로 복구 → `REQUESTED(pgReference = null)`.
   - `EXCEEDED_PAYOUT_BALANCE_AMOUNT` → `DEFERRED`(5-1 ①).
   - `FORBIDDEN_SELLER_PAYOUT`(본인인증 · KYC 필요) → 셀러 상태 재조회 → `BLOCKED` 경로가 아니라 **이미 `REQUESTED` 로 옮긴 뒤**라 `FAILED(IDENTITY_VERIFICATION_REQUIRED | KYC_REQUIRED)` — `applyResults` 가 이 두 코드는 `FAILED` 대신 **`BLOCKED` 로 되돌린다**(attempt 불변 · 재분배 아님 · 수취자가 인증하면 풀린다).
   - `NOT_FOUND_SELLER` · `INVALID_SELLER_INFO` → `FAILED(PARTNER_NOT_READY)` · `INVALID_PAYOUT_DATE` · `EXCEEDED_PAYOUT_DATE` · `INCORRECT_PAYOUT_DATE_FORMAT` → `FAILED(REJECTED_BY_PG)`(우리 날짜 계산 버그 — `ERROR` 로그) · `FORBIDDEN_OVERDUE_PAYOUT_FEE` · `FORBIDDEN_ACCOUNT_SUSPENDED` · `FORBIDDEN_REQUEST` → `FAILED(PAYOUT_CONTRACT_BLOCKED)` + 운영자 알림(전 행 같은 사유일 것) · `INVALID_ENCRYPTION` → `FAILED(REJECTED_BY_PG)` + `ERROR`(보안 키 틀림 — 기동 검증이 잡아야 한다).
   - `PREVIOUS_REQUEST_IN_PROGRESS` · `EXCEED_MAXIMUM_REQUESTS` · `429` · `409 IDEMPOTENT_REQUEST_PROCESSING` · 5xx `COMMON_ERROR` · 타임아웃 · 복호화 실패 → **예외를 던진다**(결과 모름). `SettlementPayoutService.call` 이 전 행을 `REQUESTED(pgReference = null)` 로 두고, 폴링이 5-4 ② 로 닫는다 — 멱등 키가 같아 재시도해도 중복이 없다.

`PayoutResult.lines` 는 지시한 행 전부를 돌려준다(기존 계약). `Outcome` 에 `DEFERRED` 추가.

### 5-3. 대사 알림 — `reconcileRequested(D)`(포트원 5-3 의 「콘솔 실행 요청」을 대체)

배치 끝에 `GET /v2/payouts?payoutDateGte=D&payoutDateLte=D`(커서 전부)로 건수 · 합계를 우리 `countRequestedBetween(D)` 와 대조해 `payoutRequestedSummary(D, ourCount, ourAmount, pgCount, pgAmount)` 를 보낸다. 사람이 할 일은 없고 **어긋날 때만** 본다(`REQUESTED` 인데 `pg_payout_id` 없는 행 = 결과 모름 상태 · 폴링이 닫는다). `SCHEDULED` 로 올린 행은 `payoutDate = D+1` 이라 그날 대사에 들어간다.

### 5-4. 결과 — 웹훅(1차) · 폴링(백스톱)

**웹훅 `payout.changed`** — `TossPayoutWebhookController`(`/v1/webhooks/toss/payouts` · `@Hidden` · `SecurityConfig` 화이트리스트): 원문 바이트로 서명 검증(6-2 `TossPayoutsWebhookVerifier`) 실패 → 401 · 본문 미해석. 통과 → `SettlementPayoutWebhookService.handle(headers, body, now)`: ① `eventId` 가 `settlement_payout_webhook_event` 에 있으면 200(멱등) ② `entityBody.id` 로 `settlement_payout.pg_payout_id` 조회 — 없으면 `refPayoutId`(`entityBody.refPayoutId`) 로 재조회(5-2 ④ 결과 모름 행) — 그래도 없으면 `IGNORED` 기록 · 200(우리 행이 아닌 지급 — 콘솔 수동 지급 등) ③ `gateway.fromWebhook(entityBody, lookup)` → `LineResult` → `transitions.applyLookupResults(settlementId, [result], now)` ④ `APPLIED` 기록 · 200. 외부 호출 없음 · 10초 안에 끝난다. 예외 → `FAILED` 기록 · 500(토스가 재전송).

**폴링 `pollResults`(30분 · `PG*` 모드만)** — `REQUESTED` 행을 정산 단위로 모아 `gateway.lookup`:

1. `pg_payout_id` 있음 → `GET /v2/payouts/{id}`.
2. 없음(결과 모름) → `GET /v2/payouts?payoutDateGte={requested_at 날짜}&payoutDateLte={+1영업일}` 에서 `refPayoutId` 일치 → 있으면 `id` 기록 + 상태 매핑 / **없고** `requested_at` 이 `result-stale-business-days`(1) 를 넘었으면 `FAILED(TRANSFER_NOT_FOUND, "PG 지급 미생성")` → M3 가 새 ref 로 올린다(멱등 키가 같은 ref 라 **15일 안에 뒤늦게 토스에 생기면** 그것은 폴링 ① 이 다음에 보고 PAID 로 닫는다 — 재분배 행과 **이중 지급 위험** → 재분배 전 「원 ref 를 `cancel` 시도(`SCHEDULED` 일 때만 가능)」 · `EXPRESS` 면 재분배를 **다음 영업일**로 미루고 하루 더 조회한다. 9-5).
3. 매핑:

| 토스 `Payout.status` | 우리 `settlement_payout` | 처리 |
| --- | --- | --- |
| `COMPLETED` | `PAID` · `pg_reference = pg_payout_id = id` · `paid_at` | `markPaid` · 이력 `PAYOUT_PAID(PG)` · 재파생 · 공구 `SETTLED` · 영수증(기존 `applyResults` PAID 분기 재사용). `amount.value ≠ 행 금액` 이면 `WARN` 만(0-2) |
| `FAILED` · `REJECTED` | `FAILED` · `fail_code = classify(error.code)` · `fail_reason = "{code}: {message}"` | `markFailed` · 이력 · 운영자 알림 · 정산 `PAYOUT_FAILED` → M3 |
| `CANCELED` | `FAILED(CANCELLED_AT_PG)` | 같은 경로 — 재분배 |
| `DELETED` | `FAILED(TRANSFER_NOT_FOUND)` | 재분배(새 ref) |
| `REQUESTED` · `IN_PROGRESS` | `REQUESTED` 유지 | `requested_at`(또는 `pg_payout_date`) 기준 `stale-in-progress-business-days`(1) 넘으면 `markStale` — 이력 `PAYOUT_CHECK_REQUIRED("PG 처리 지연")` 1회 · 운영자 알림 `payoutStale`(Q3 로 기준 보정) |
| 모르는 값 | `REQUESTED` 유지 | `WARN` — 테스트에서 실제 값을 받아 표를 채운다 |

**웹훅 `seller.changed`** — 4-3 둘째 줄. `entityBody.id` 로 `seller.pg_partner_id` → `creator.pg_partner_id` 순으로 찾는다.

`PayoutBlockReason.PARTNER_CODES` = `{PARTNER_NOT_READY, ACCOUNT_HOLDER_MISMATCH, COMPANY_NOT_IN_BUSINESS, ACCOUNT_MISSING, ACCOUNT_INVALID, UNSUPPORTED_BANK, PAYOUT_CONTRACT_BLOCKED, IDENTITY_VERIFICATION_REQUIRED, KYC_REQUIRED}` — 배치 앞단이 다시 등록 · 상태 조회를 시도하는 코드. 삭제: `AMOUNT_MISMATCH` · `PLATFORM_NOT_ENABLED`.

### 5-6. 재분배(M3)와의 연결

`AdminSettlementCommandService.redistribute` 는 `attempt + 1` · 계좌 재스냅샷 · `SCHEDULED(오늘)` 뒤 즉시 `distribute`(기존). 어댑터에서는 **새 refPayoutId · 새 멱등 키**가 되고, 15:00 뒤면 `SCHEDULED(다음 영업일)` 로 올라가 행은 `REQUESTED` · `pg_payout_date = D+1`(07b 레일 · 스튜디오 · 파트너 화면에 「{D+1} 지급 예정」). 계좌 출처 `CURRENT_PROFILE` 이면 5-2 ③ 이 셀러 계좌를 먼저 갱신한다. 토스 쪽 실패 지급은 그대로 남는다(콘솔 이력) — 지우지 않는다.

`TRANSFER_NOT_FOUND` 재분배는 9-5 의 이중 지급 방지 절차를 **먼저** 거친다. 재분배 상한(3회) 초과 뒤 「수동 이체」(44 어드민 13절 A-7)는 이 연동으로도 자동화되지 않는다.

## 6. 어댑터 · 설정 · 기동 검증

### 6-1. 포트 확장

```java
public interface SettlementPayoutGateway {
    PayoutResult distribute(PayoutCommand command);                                   // 기존
    default List<LineResult> lookup(List<PayoutLookup> lookups) { return List.of(); }   // 기존
    default Optional<Reconciliation> reconcile(LocalDate payoutDate) { return Optional.empty(); } // 기존 · 뜻만 「대사」
    /** 지급 가능 잔액 — 지원하지 않는 모드는 empty(5-1 ①). */
    default Optional<Long> availableBalance() { return Optional.empty(); }
    /** 검증 끝난 웹훅 entityBody(Payout JSON) → 결과. 폴링과 같은 전이를 탄다(5-4). */
    default Optional<LineResult> fromWebhook(String payoutJson, PayoutLookup lookup) { return Optional.empty(); }

    record PayoutCommand(Long settlementId, String settlementNumber, List<PayoutLine> lines, LocalDateTime requestedAt) {}
    record PayoutLine(Long payoutId, SettlementPayee payee, long amount, String bankName, String accountNumber,
                      String holder, Long payeeRefId, int attempt, String bankCode, String partnerExternalId /* 토스 셀러 id */) {}
```

## 9. 운영 런북

### 9-1. 지급일(영업일) — 운영팀

사람이 할 일은 없다. 10:00 배치 뒤 알림 「D 일자 지급 N건 · 합계 ₩ · 토스 조회 N건 일치」를 받고, **불일치 · 연기 · 실패** 알림이 있을 때만 어드민 07a 「분배 실패」 탭 · 07b 레일을 본다. 실패 건은 M3 재분배(사유별 계좌 출처 5-5). `IDENTITY_VERIFICATION_REQUIRED` · `KYC_REQUIRED` 는 재분배 대상이 아니다 — 수취자에게 안내(스튜디오 · 파트너 화면 문구 · L-2′).

### 9-2. 잔액

`payoutBalanceInsufficient` 알림이 오면 연기된 행은 다음 영업일 배치가 다시 본다. 잔액이 매출 정산 주기에 달려 있으면(Q1) 지급 예정일(`payout-business-days` = 3)이 정산 주기보다 빠른 구조적 부족일 수 있다 — 그때는 `payout-business-days` 를 늘리거나(44 어드민 9-1 설정값) 충전(가능하면)으로 푼다. 연기가 2영업일 연속이면 개발팀 호출.

### 9-3. 대사

월 1회 — `GET /v2/payouts?payoutDateGte&Lte`(월 범위 · 커서 전부) 합계 vs 우리 `settlement_payout(PAID · paid_at 범위)` 합계. 어긋나면 건별 `pg_payout_id` 로 좁힌다. 웹훅 실패 내역은 토스가 **이메일**로 보내므로 수신함을 운영 메일로.

### 9-4. 런칭 게이트(포트원 9-4 승계 · 값만 갱신)

| 서버 | 환경변수 | 동작 |

| 지금 배포 서버(개발 단계 `prod`) | 없음 | `SIMULATED` — 기동 경고 2줄 |
| 토스 테스트 키 수령 뒤 | `SETTLEMENT_PAYOUT_MODE=PG_TEST` · `TOSS_PAYOUTS_SECRET_KEY=test_sk_…` · `TOSS_PAYOUTS_SECURITY_KEY` · `TOSS_PAYOUTS_TEST_BRN` | 8-2 T1 ~ T9 |
| **실제 운영 서버** | `SETTLEMENT_LAUNCH_GATE_ENABLED=true` · `SETTLEMENT_PLATFORM_*` · `SETTLEMENT_PAYOUT_MODE=PG` · `TOSS_PAYOUTS_SECRET_KEY=live_sk_…` · `TOSS_PAYOUTS_SECURITY_KEY` · `TOSS_PAYOUTS_TEST_BRN` **비움** | 하나라도 빠지면 기동 실패 |

### 9-5. 결과 모름 행의 재분배 — 이중 지급 방지

`TRANSFER_NOT_FOUND` 로 `FAILED` 가 된 행(지시가 토스에 닿았는지 모른다)을 M3 로 다시 올리기 전에: ① 토스 콘솔(또는 `GET /v2/payouts` 범위 조회)에서 원 `refPayoutId` 가 **정말 없는지** 확인 ② 있고 `SCHEDULED · REQUESTED` 면 `POST /v2/payouts/{id}/cancel` 뒤 재분배 ③ 있고 `IN_PROGRESS · COMPLETED` 면 재분배하지 **않고** `pg_payout_id` 를 수기로 채워 폴링이 닫게 한다. 어댑터는 ①을 자동으로 하지만(5-4 ②) 멱등 키 15일 창 안에서 늦게 생기는 경우가 있어 사람이 한 번 본다.

### 9-6. 키 교체

보안 키 · 시크릿 키를 바꾸면 **웹훅 서명 · JWE 가 동시에** 바뀐다. 교체 창에는 폴링만으로 닫히게 두고(웹훅 401 은 토스가 재전송 — 7회 · 3일 19시간) 환경변수 반영 뒤 재기동. `Idempotency-Key` 는 API 키별이라 **키 교체 뒤 같은 ref 재시도는 중복 지급이 될 수 있다** — 교체 전 `REQUESTED(pg_payout_id 없음)` 행이 0 인지 확인.
