## 0. 먼저 정한 6가지

### 0-1. 새로 만드는 것은 **어드민 API와 「카드」**뿐이다 — 채널은 이미 있다

13-14 설계가 운영팀 채널의 저장 구조를 끝내 놓았다. 이 설계는 그 위에 선다.

| 이미 있는 것 (코드 확인) | 이 설계가 더하는 것 |
| --- | --- |
| `connection.type = OPERATOR_MARKET / OPERATOR_CREATOR` — 회원당 1행, 승인·등록 완료 시 자동 생성(`OperatorChannelService`) | 어드민 컨트롤러 · 서비스(`api.admin.thread`) |
| `message_thread` · `message` · `message_attachment` · 멱등 전송 · presign 첨부 | `message`에 **메시지 타입 · 카드** 컬럼 6개 |
| 파트너센터 · 스튜디오 쪽 운영팀 채널 노출(목록 최상단 고정) | 운영팀 **공용 읽음 위치** · 팀 기준 안 읽은 수 |
| `contract_resend_request` · 계약 취소 요청자 기록 | 그 둘을 **채널에 잇는** 포트 1개 |

**신규 테이블은 0개다.** 「새 대화」 API도 없다 — 채널이 미리 있고 찾기는 검색이다(§36-0).

### 0-2. 통신은 폴링이다 — SSE를 붙이지 않는다

13-14 설계 0절의 결정(게시판형 · 배지만)을 그대로 따른다. 스레드 진입 · 탭 전환 시 재조회 + `summary` 폴링(30~60초). 운영팀 메시지의 외부 알림(§36-9 B-13)이 확정되면 그때 알림 훅을 붙인다.

### 0-3. 카드는 **메시지의 한 종류**다 — 별도 테이블이 아니다

§36-3 "절차의 기록은 카드로, 사람의 대화는 말풍선으로". 카드도 대화의 시간순 흐름 안에 놓이고, 안 읽은 수 · 미리보기 · 커서 페이징을 그대로 타야 한다. 그래서 `message` 행으로 저장하고 `message_type`으로 가른다.

- 카드에 **박히는 사실**(계약번호 · 공구명 · 요청자 · 사유)은 생성 시점 스냅샷(`card_payload`)이다 — 나중에 원본이 바뀌어도 "그때 그 안내"가 그대로 남아야 분쟁 때 쓸 수 있다.
- 카드의 **액션 상태**(재발송 알림 전/후)는 스냅샷이 아니라 **참조 객체에서 읽는다** — 상태가 두 군데 있으면 어긋난다.

### 0-4. 운영자 개인 식별자는 **직렬화 단계에서 서피스별로 갈린다**

§36-4 "화면에서 가리는 것으로는 부족하다". 현재 파트너 · 스튜디오 `MessageItem`은 `senderId`를 내리지 않는다(확인함) — 이 성질을 규칙으로 못박는다.

| | 어드민 응답 | 파트너센터 · 스튜디오 응답 |
| --- | --- | --- |
| 운영자 말풍선 | `operatorName: "김운영"` · `autoNotice` | `senderType: ADMIN`뿐 — **이름 · id · `autoNotice` 없음** |
| 카드의 처리자 | `doneByName` · `processedByName` | **필드 자체가 없다** |
| 저장 | `message.sender_id` = 운영자 `Seller.id`(내부 감사용) | — |

카드 스냅샷에는 운영자 **id만** 넣고 이름은 어드민 직렬화 때 붙인다. 카드의 대체 텍스트(`content`)에도 운영자 이름을 쓰지 않는다 — 구 FE가 `content`를 그대로 그리기 때문이다(0-6).

### 0-5. 운영팀의 읽음 위치는 **팀 공용 1행**이다

운영자 여럿이 같은 채널을 본다. 운영자별로 읽음을 따로 세면 A가 답한 채널이 B에게 계속 "안 읽음"으로 남는다. `thread_participant`에 `(thread, ADMIN, 0)` 한 행을 운영팀의 읽음 위치로 쓴다(`0` = `OperatorChannelService.SYSTEM_OPERATOR_ID`).

담당자 지정(§36-9 B-8)이 확정돼 개인별 읽음이 필요해지면 `participant_id`에 실제 운영자 id 행을 추가하면 된다 — 구조 변경이 아니다.

### 0-6. 파트너센터 · 스튜디오는 **깨지지 않게만** 손댄다

상대편 화면의 카드 표시는 미정이다(§36-9 C-18). 이 설계는 두 서피스의 `MessageItem`에 `messageType` · `card`를 **추가만** 하고, 카드 행의 `content`에 카드 제목을 넣어 둔다. 카드 렌더를 아직 안 만든 FE는 일반 말풍선으로 제목이 보이고, 만든 FE는 `messageType`으로 가른다.

## 1. 모델 보강 — 컬럼 11개

### 1-1. `message` — 6개

| 컬럼 | 타입 | 비고 |
| --- | --- | --- |
| `message_type` | VARCHAR(16) NOT NULL DEFAULT `'TEXT'` | `TEXT`(말풍선) / `SYSTEM`(카드) |
| `card_type` | VARCHAR(40) NULL | `CONTRACT_RESEND_REQUEST` / `CONTRACT_ADMIN_CANCELED` — `SYSTEM`일 때만 |
| `ref_type` · `ref_id` | VARCHAR(32) · BIGINT NULL | 참조 객체. 재발송 = `CONTRACT_RESEND_REQUEST` + 요청 id · 취소 = `CONTRACT` + 계약 id |
| `card_payload` | TEXT NULL | 생성 시점 스냅샷(4절) — JSON 문자열(`MessageCardPayload`) |
| `auto_notice` | BIT(1) NOT NULL DEFAULT 0 | 정해진 문구의 자동 전송 말풍선(§36-5). **어드민 응답에만** 내린다 |

- 카드의 `sender_type` / `sender_id`는 **그 카드를 생기게 한 주체**다 — 재발송 요청 카드는 요청자(브랜드 = 마켓 id · 인플루언서 = 크리에이터 id), 취소 결과 카드는 처리 운영자. 기존 안 읽은 수 쿼리가 "본인이 보낸 것 제외"라서, 이렇게 두면 **요청 카드는 요청자의 배지를 올리지 않고 운영팀 배지만 올리며**, 결과 카드는 그 반대가 된다. 쿼리를 고치지 않아도 맞는다.
- `client_message_id`는 카드도 필수다(기존 UNIQUE). 고정 규칙으로 채워 **멱등키로 쓴다** — `resend-card-{requestId}` · `resend-notice-{requestId}` · `contract-cancel-{contractId}`.
- 카드는 `content`에 카드 제목을 넣는다(0-6). 첨부는 없다.

### 1-2. `message_thread` — 1개

| 컬럼 | 비고 |
| --- | --- |
| `last_message_sender_type` VARCHAR(20) NULL | 목록 미리보기의 「운영팀: 」 접두 판정(§36-1). `recordLastMessage`가 함께 쓴다. 기존 행은 마지막 메시지에서 백필 |

미리보기 문자열에 접두를 박지 않는다 — 같은 스레드를 파트너센터 · 스튜디오도 읽는다. 접두는 어드민 FE가 `lastMessageByOperator`를 보고 붙인다. 카드가 마지막이면 미리보기는 카드 제목이 된다(`content` = 제목이라 기존 로직 그대로).

### 1-3. `contract_resend_request` — 3개

| 컬럼 | 비고 |
| --- | --- |
| `thread_id` BIGINT NULL | 카드가 등록된 운영팀 채널 |
| `card_message_id` BIGINT NULL | 요청 카드 |
| `notice_message_id` BIGINT NULL | 자동 안내 말풍선 — 알림 전송 후 채워진다 |

기획의 `resendRequest` 필드와의 대응:

| 기획 필드 | 컬럼 |
| --- | --- |
| `requestedBy` · `requestedAt` | 기존 `requester_type` · `requester_id` · `requested_at` |
| `notifiedBy` · `notifiedAt` | **기존 `handled_by` · `handled_at`을 그대로 쓴다** |
| `threadId` · `cardMessageId` · `noticeMessageId` | 신규 3개 |

`handled_*`를 `notified_*`로 개명하지 않는다. "처리 = 카드 버튼"이 되었으므로 뜻이 같고, 계약 관리의 재발송 큐(`handled_at IS NULL`)가 **아무것도 고치지 않아도** 기획이 말한 "카운트 = `notifiedAt == null` 카드 수"가 된다(§36-9 A-1 ①).

### 1-4. `contract` — 1개

| 컬럼 | 비고 |
| --- | --- |
| `cancel_request_thread_id` BIGINT NULL | 직권 취소 결과 카드가 등록된 채널(§36-6 `cancel.requestThreadId`). 요청 경로가 스레드가 아니면 NULL |

### 1-5. `thread_participant` — 컬럼 추가 없음

`(thread_id, 'ADMIN', 0)` 행을 운영팀 읽음 위치로 쓴다(0-5). 기존 `upsertReadPosition`을 그대로 호출한다.

### 1-6. enum

| 위치 | 값 |
| --- | --- |
| `domain.message.type.MessageType` | `TEXT` · `SYSTEM` |
| `domain.message.type.MessageCardType` | `CONTRACT_RESEND_REQUEST("요청 · 서명 안내 다시 받기")` · `CONTRACT_ADMIN_CANCELED("계약 직권 취소 처리됨")` |
| `domain.message.type.MessageRefType` | `CONTRACT_RESEND_REQUEST` · `CONTRACT` |

## 2. 접근 · 가시성

### 2-1. 어드민이 여는 스레드는 **운영팀 채널뿐**이다 (이 설계 범위)

| 스레드 | 이 API에서 |
| --- | --- |
| `OPERATOR_MARKET` · `OPERATOR_CREATOR` 의 `CONNECTION` 스레드 | 읽기 · 쓰기 |
| `PAIR` 연결의 일반 스레드 | **403 `THREAD_ACCESS_DENIED`** — 열람 화면의 행방이 미결이다(§36-9 A-2) |
| `GROUP_BUY_ISSUE` · `GROUP_BUY_FULFILLMENT` | **403** — 이슈 스레드 소관(추후 기획 예정) |

판정은 서비스 한 곳(`AdminThreadAccess.requireOperatorChannel(threadId)`)에 둔다. A-2 · 이슈 스레드 기획이 확정되면 이 메서드 옆에 판정을 추가한다 — 엔드포인트는 그대로 쓴다.

### 2-2. 운영자 식별

기존 어드민 관례 그대로 — 컨트롤러가 `@AuthenticationPrincipal UserPrincipal`의 `userId`를 넘기고, `AdminOperatorResolver.operatorName`이 ADMIN 여부 검사와 이름 조회를 겸한다. 경로 권한은 `SecurityConfig`의 `/v1/admin/**`가 이미 건다.

### 2-3. 탈퇴 · 정지 회원의 채널 — **잠정**(§36-9 B-9 미결)

| 회원 상태 | 목록 | 읽기 | 쓰기 |
| --- | --- | --- | --- |
| 활성 · 휴면 · **정지** | 노출 | ○ | ○ — 정지 사유를 이 채널에서 설명해야 할 수 있다 |
| **탈퇴** | 노출(상태 배지) | ○ | ✕ `409 THREAD_READ_ONLY` — 받을 사람이 로그인할 수 없다 |

응답의 `writable`로 FE가 입력창을 가른다. 운영팀 채널은 휴면(`DORMANT`)에 빠지지 않는다는 13-14 설계 1-1의 결정은 그대로다 — 스레드 상태가 아니라 **회원 상태**로 판정한다. 보존 기간은 확정 전까지 삭제 로직을 만들지 않는다.

### 2-4. 기획 제외 패키지(CLAUDE.md)

브랜드 정보는 `domain.market` · `domain.member.seller` 리포지토리로만 읽는다. `api.admin.market`(기획 제외)의 서비스 · DTO를 쓰지 않는다. 이 설계가 건드리는 제외 대상 파일은 없다.

패키지: `showroomz.api.admin.thread.{controller, docs, dto, service}` — `AdminThreadController implements AdminThreadControllerDocs`.

경로는 파트너센터 · 스튜디오와 같은 모양으로 맞춘다(13-14 설계 3-3의 초안 경로 `/connections/threads/{id}/messages`는 이 표로 대체한다).

| Method | Path | 설명 | 시안 |

| POST | `/v1/admin/threads/{threadId}/cards/{messageId}/resend-notice` | **재발송 완료 알림 보내기** | A6-0 → A6 |

### 3-1. 목록 — `GET /v1/admin/connections/threads`

| 파라미터 | 값 |
| --- | --- |
| `tab` | `BRAND`(= `OPERATOR_MARKET`) · `INFLUENCER`(= `OPERATOR_CREATOR`) — 필수. `ISSUE`는 이슈 스레드 기획 후 추가 |
| `keyword` | 브랜드 탭: 브랜드명 · 회원번호 · 담당자 / 인플루언서 탭: 쇼룸명 · 회원번호 |
| `page` · `size` | 기존 `PagingRequest` |

- 정렬: `last_message_at DESC NULLS LAST`, 동률은 `thread_id DESC`. **메시지 0건 채널도 나온다** — 채널은 항상 존재한다(§36-0). 맨 아래에 깔린다.
- 검색어가 회원번호 접두(`BRD-` · `INF-`)로 시작하면 번호 축으로만 본다. 숫자가 아니면 **결과 0건**이다(전체 목록으로 떨어지지 않는다 — `AdminMemberNumber.parseOrNull`과 같은 규칙).
- 안 읽은 수는 페이지 전체를 한 쿼리로 집계한다(3-3의 팀 기준 쿼리).

```json
{
  "threadId": 55,
  "tab": "BRAND",
  "name": "무드코스메틱",
  "imageUrl": "https://…/market/17.jpg",
  "memberNo": "BRD-1017",
  "memberId": 1017,
  "subLabel": "담당 이현",
  "memberStatus": "ACTIVE",
  "lastMessagePreview": "여름 수분 세럼 계약 취소 요청드립니다.",
  "lastMessageByOperator": false,
  "lastMessageAt": "2026-08-14T10:05:00",
  "unreadCount": 1,
  "writable": true
}
```

| 필드 | 브랜드 | 인플루언서 |
| --- | --- | --- |
| `name` | `Market.marketName` | `Creator.showroomName` |
| `imageUrl` | `Market.marketImageUrl` | `Users.profileImageUrl` |
| `memberNo` | `BRD-{marketId}` | `INF-{creatorId}` — **잠정**(11-2 #1) |
| `subLabel` 재료 | `managerName` (판매 담당자 = `Seller.name`) | `businessType` (`BUSINESS` → 사업자 / `INDIVIDUAL` → 개인) |

`subLabel`은 완성 문자열이 아니라 재료 필드(`managerName` · `businessType`)로 내리고 「담당 {이름}」 조립은 FE가 한다.

### 3-2. 요약 — `GET /v1/admin/connections/summary`

```json
{
  "brand":      { "unreadCount": 3, "pendingCardCount": 0 },
  "influencer": { "unreadCount": 2, "pendingCardCount": 1 },
  "issue": null
}
```

탭 숫자 배지의 뜻이 미정이다(§36-9 B-7). **안 읽은 메시지 수와 미처리 카드 수를 둘 다 내리고** FE가 확정값을 고른다. 「미답 채널 수」는 SLA 정의가 있어야 계산할 수 있어 만들지 않는다. `issue`는 이슈 스레드 기획 전까지 `null`.

- `unreadCount` — 그 탭 전 채널의 팀 기준 안 읽은 수 합.
- `pendingCardCount` — 그 탭 채널에 등록된 재발송 요청 중 `handled_at IS NULL`이고 계약이 `SIGNING`인 건수.

### 3-3. 팀 기준 안 읽은 수

기존 `countUnreadByThreadIds`는 "보낸 사람 = 나"만 제외한다. 운영팀으로 호출하면 다른 운영자가 보낸 말풍선이 팀의 안 읽은 수로 잡힌다. 어드민용 쿼리를 따로 둔다.

```
안 읽은 수(운영팀) = 그 스레드에서 sender_type <> 'ADMIN'
                   AND message_id > (ADMIN, 0)의 last_read_message_id 인 메시지 수
```

요약용은 `connection.type`으로 묶어 한 쿼리로 합친다. `idx_message_thread_id_desc(thread_id, message_id)`가 이미 있다.

### 3-4. 헤더 + 정보 바 — `GET /v1/admin/threads/{threadId}/info`

접힌 상태에서도 요약 줄이 보이므로 스레드 진입 시 1회 부른다. 계약 관리 등에서 딥링크로 들어온 경우 목록 없이 헤더를 그리는 데도 쓴다.

```json
{
  "threadId": 55,
  "tab": "BRAND",
  "name": "무드코스메틱",
  "memberNo": "BRD-1017",
  "memberId": 1017,
  "memberStatus": "ACTIVE",
  "writable": true,
  "profile": {
    "managerName": "이현", "managerContact": "010-4827-2231",
    "businessType": null, "taxType": null, "businessEmail": null,
    "instagramUrl": null,
    "joinedAt": "2026-03-04T11:20:00"
  },
  "progress": {
    "contractSigning": 1, "contractConcluded": 2,
    "groupBuyOngoing": 1, "groupBuyEnded": null,
    "unsettledCount": null,
    "connectedBrandCount": null
  },
  "openIssueThreads": []
}
```

| 값 | 출처 | 비고 |
| --- | --- | --- |
| `managerName` · `managerContact` | `Seller.name` · `Seller.phoneNumber` (기본정보 관리 담당자·CS 탭 저장값) | 브랜드만 |
| `businessType` · `businessEmail` · `instagramUrl` | `Creator` | 인플루언서만 |
| `taxType`(과세 유형) | **저장 값이 없다** — `null` | 11-2 #2 |
| `joinedAt` | 브랜드 = `Seller.createdAt` · 인플루언서 = `Creator` 생성 시각 | 승인일인지 가입일인지 11-2 #3 |
| `contractSigning` | 계약 수 `status IN (SIGNING, CONCLUSION_PENDING)` | 시안 A5에서 취소 대상이 이 구간이다. `CONCLUSION_PENDING`을 따로 셀지는 11-2 #4 |
| `contractConcluded` | `status = CONCLUDED` | |
| `groupBuyOngoing` · `groupBuyEnded` | 공구 모듈 집계 | `Ended`는 인플루언서만 |
| `unsettledCount` | **정산 모듈이 없다** — `null` | 브랜드만 · `[집계 대기]` |
| `connectedBrandCount` | `PAIR` 연결 `CONNECTED` 수 | 인플루언서만 |
| `openIssueThreads[]` | 그 회원이 당사자인 공구 3자 스레드 중 열린 것 `{ threadId, kind, groupBuyId, groupBuyTitle }` | 이슈 스레드 기획 전까지는 링크만 — 클릭 대상 화면이 없다 |

**이 화면에서 계산하지 않는다**(§36-2). 각 수치는 그 도메인의 리포지토리 count 쿼리 한 줄을 부르는 reader(`AdminChannelInfoReader`)로 모으고, 모듈이 없으면 **0이 아니라 `null`**이다 — 0은 "없음"이라는 사실이고 `null`은 "모름"이다(32 설계 0-7과 같은 규칙). FE는 `null`인 행을 그리지 않는다.

### 3-5. 메시지 조회 — `GET /v1/admin/threads/{threadId}/messages?cursor=&size=`

기존과 같은 최신순 커서 페이징(`size + 1` 조회로 `hasNext`). 응답 항목은 어드민 전용 DTO다.

```json
{
  "messageId": 9013,
  "messageType": "TEXT",
  "senderType": "ADMIN",
  "mine": true,
  "operatorName": "김운영",
  "autoNotice": true,
  "content": "모두싸인에서 서명 안내를 다시 보내드렸습니다. 메일함(스팸함 포함)을 확인해 주세요.",
  "attachments": [],
  "card": null,
  "createdAt": "2026-08-14T08:55:00"
}
```

| 필드 | 규칙 |
| --- | --- |
| `mine` | `senderType == ADMIN` — **운영자 개인이 아니라 운영팀 기준**이다. 다른 운영자의 말풍선도 오른쪽에 온다 |
| `operatorName` | `sender_id`의 운영자 이름. `sender_id = 0`(가입 안내 등 시스템 발신)이면 `null` — FE는 「운영팀」만 표기 |
| `autoNotice` | `message.auto_notice` 또는 `sender_id = 0` |
| `senderName` | 상대 말풍선의 이름(브랜드명 · 쇼룸명) — 역할 태그는 `senderType`으로 FE가 붙인다 |
| `card` | `messageType = SYSTEM`일 때만(4절) |

운영자 이름은 페이지의 `sender_id` 집합을 한 번에 조회한다(메시지당 조회 금지). 이름은 **현재 값**이다 — 스냅샷하지 않는다. 계약 이력처럼 "그때의 실명"이 필요한지는 감사 범위(C-17)와 함께 정한다.

### 3-6. 전송 — `POST /v1/admin/threads/{threadId}/messages`

```json
{ "clientMessageId": "f3b1…", "content": "확인했습니다.", "attachmentIds": [] }
```

- `MessageThreadService.sendMessage(thread, ADMIN, operatorId, …)`를 그대로 부른다. 멱등(같은 `clientMessageId` → 기존 메시지 200) · 본문/첨부 둘 다 비면 400 · 첨부 검증(20개 · 500MB · 본인 업로드 · 같은 스레드)이 전부 기존 규칙이다.
- 신규 저장 201 · 멱등 재전송 200(기존 컨트롤러 관례).
- **운영자가 카드를 직접 만드는 요청은 없다.** `messageType` · `autoNotice`를 요청으로 받지 않는다 — 카드는 서버의 다른 흐름에서만 생긴다(§36-0 "같은 조치를 두 화면에서 만들지 않는다").
- 전송은 읽음 처리를 하지 않는다(기존과 동일). FE가 진입 시 `/read`를 부른다.

### 3-7. 읽음 — `POST /v1/admin/threads/{threadId}/read`

`markRead(thread, ADMIN, 0)` — 누가 열든 운영팀의 읽음 위치가 앞으로 간다(0-5). 204.

### 3-8. 첨부

`MessageAttachmentService`를 `ParticipantType.ADMIN` · 업로더 id = 운영자 id로 호출한다. 서비스는 이미 ADMIN 업로더를 받도록 만들어져 있다(13-14 설계 1-6). 규칙은 (1) §13-7~§13-11 그대로이고 여기서 다시 적지 않는다. 다운로드 권한은 "첨부가 속한 스레드가 운영팀 채널인가"로 판정한다(2-1).

## 4. 시스템 카드

### 4-1. 카드 응답 — 공통 골격

```json
"card": {
  "cardType": "CONTRACT_RESEND_REQUEST",
  "title": "요청 · 서명 안내 다시 받기",
  "tone": "WARNING",
  "contractId": 41,
  "contractNumber": "CTR-20260813-041",
  "groupBuyTitle": "겨울 리페어 크림 공구",
  "detail": { … 카드 종류별 … },
  "action": { … 있으면 … }
}
```

- `tone`은 **서버가 내린다** — 운영자 조치가 남은 요청 = `WARNING`, 조치가 끝났거나 결과 카드 = `NEUTRAL`(원칙 ①②). 시안 A6이 처리 후에도 경고 배경인 것(§36-10 #5)은 이 값으로 정리된다.
- `contractId`는 `계약 상세 ↗` 딥링크용이다. 링크 대상 화면은 FE 소관(C-15).
- 스냅샷(`card_payload`)에는 `title` · 계약번호 · 공구명 · `detail`의 사실값이 들어간다. `tone` · `action`은 조회 때 계산한다.

### 4-2. 카드 ① 재발송 요청 — `CONTRACT_RESEND_REQUEST`

```json
"detail": { "requesterType": "CREATOR", "requesterName": "뷰티_소연", "requestedAt": "2026-08-14T08:50:00" },
"action": {
  "type": "RESEND_NOTICE",
  "state": "PENDING",
  "canExecute": true,
  "doneAt": null,
  "doneByName": null,
  "noticeMessageId": null
}
```

| `state` | 조건 | `tone` | 화면 |
| --- | --- | --- | --- |
| `PENDING` | `handled_at IS NULL` · 계약 `SIGNING` | `WARNING` | 버튼 `재발송 완료 알림 보내기` |
| `DONE` | `handled_at IS NOT NULL` | `NEUTRAL` | 「✓ 재발송 완료 알림 전송됨 · 시각 · 처리자」 |
| `CLOSED` | `handled_at IS NULL` · 계약이 `SIGNING`을 벗어남(서명 완료 · 만료 · 취소) | `NEUTRAL` | 버튼 없음 — 다시 보낼 안내가 없다 |

`CLOSED`는 시안에 없는 상태다. 요청 뒤 알림 전에 계약이 끝나는 경우가 반드시 생기고, 그때 버튼이 남아 있으면 운영자가 "다시 보냈다"는 거짓 안내를 보내게 된다. 문구는 FE · 기획 확인(11-2 #5).

액션 상태는 페이지에 있는 카드들의 `ref_id`로 `contract_resend_request` + 계약 상태를 **한 번에** 읽는다.

파트너센터 · 스튜디오 응답의 `action`은 `{ type, state, doneAt }`뿐이다 — `doneByName` · `canExecute` 없음(0-4).

### 4-3. 카드 ② 직권 취소 결과 — `CONTRACT_ADMIN_CANCELED`

```json
"detail": {
  "reasonLabel": "당사자 요청 — 조건 재협의",
  "processedAt": "2026-08-14T10:40:00",
  "processedByName": "김운영",
  "notifiedBothParties": true
}
```

- `tone = NEUTRAL` — 취소는 종결이다. `action` 없음.
- `reasonLabel`은 `ContractCloseReasonCode` 라벨(+ 메모가 있으면 ` — {메모}`)의 스냅샷이다. **메모는 당사자에게 그대로 공개한다 — 2026.10.05 확정.** 어드민 · 파트너센터 · 스튜디오 응답이 같은 `reasonLabel`을 내린다. 그래서 C6 취소 모달의 메모는 **상대가 읽는 글**이다 — 계약 관리 화면의 메모 입력란에 그 안내가 필요하다(FE · 28 설계서 10-A 반영).
- `processedByName`은 어드민 응답 전용.

## 5. 흐름 ① — 서명 안내 재발송 요청

### 5-1. 요청 → 카드 등록 (파트너센터 · 스튜디오 → 채널)

기존 `SellerContractCommandService.requestResend` · `CreatorContractCommandService.requestResend`에 카드 등록을 더한다. 계약 도메인이 메시지 도메인을 직접 부르지 않도록 포트를 둔다(공구의 `GroupBuyThreadGateway`와 같은 방식).

```java
// domain.contract.service.port
public interface ContractChannelGateway {
    /** 요청자의 운영팀 채널에 요청 카드를 등록하고 (threadId, cardMessageId)를 돌려준다. */
    ChannelCard postResendRequestCard(Contract contract, ContractResendRequest request);
    /** 요청 채널에 직권 취소 결과 카드를 등록한다. */
    ChannelCard postAdminCanceledCard(Contract contract, ContractActorType requesterType, Long operatorId);
}
// 구현: domain.message.service.MessageContractChannelGateway
```

한 트랜잭션이 하는 일:

1. (기존) 상태 · 서명 여부 검증 — `SIGNING`이고 내 서명이 남아 있을 때만.
2. **중복 억제 — 요청자별로 바꾼다.** 지금은 "계약에 미처리 요청이 하나라도 있으면 새 행을 만들지 않는다"라서, 브랜드가 먼저 요청한 계약에서 인플루언서가 누르면 **인플루언서 채널에 카드가 생기지 않는다.** 조회 조건에 `requester_type`을 더해 「같은 요청자의 미처리 요청이 있으면 그 요청을 돌려준다」로 고친다. 반복 요청의 누적/병합(§36-9 B-12)은 이 규칙으로 **병합**이 잠정값이다 — 처리 후 다시 누르면 새 카드가 생긴다.
3. `contract_resend_request` 저장.
4. 요청자의 운영팀 채널을 찾는다 — 브랜드 = `OPERATOR_MARKET` · 인플루언서 = `OPERATOR_CREATOR`. **없으면 그 자리에서 만든다**(`OperatorChannelService.ensure*` — 백필 누락 회원 대비). 채널이 없다는 이유로 요청을 실패시키지 않는다.
5. 카드 메시지 저장 — `message_type = SYSTEM` · sender = 요청자 · `client_message_id = resend-card-{requestId}` · `ref = (CONTRACT_RESEND_REQUEST, requestId)` · 스레드 `last_message_*` 갱신.
6. 요청 행에 `thread_id` · `card_message_id` 기록.
7. (기존) 계약 이력 `RESEND_REQUESTED` · `notifyAdmin` — **그대로 둔다.** 요청 사실을 계약 이력에 남길지는 미결이다(§36-9 A-1 ②). 확정되면 이 한 줄만 뺀다.

`MessageThreadService`에 카드 저장 메서드를 더한다 — `postSystemCard(thread, senderType, senderId, clientMessageId, cardType, refType, refId, payload)`. 멱등 · 미리보기 갱신은 `sendMessage`와 같은 길을 탄다.

**파트너센터의 `POST /v1/seller/contracts/{id}/resend-request`는 지금 `@Hidden`이다** — 주석이 "요청이 가는 어드민 스레드가 아직 없어 숨긴다 — 어드민 스레드 구현 후 제거"다. 이 단계(P3)에서 그 `@Hidden`을 제거한다. (기획 제외 `@Hidden`이 아니다 — `[기획 제외]` 주석이 없는 임시 숨김이다.)

### 5-2. 알림 전송 — `POST /v1/admin/threads/{threadId}/cards/{messageId}/resend-notice`

요청 본문 없음. **전송과 카드 상태 전환이 한 번에 일어난다**(§36-5) — 한 트랜잭션, 순서는 아래로 고정한다.

| # | 처리 | 실패 시 |
| --- | --- | --- |
| 1 | 카드 조회 — 그 스레드의 `SYSTEM` · `CONTRACT_RESEND_REQUEST` 메시지인가 | 404 `MESSAGE_CARD_NOT_FOUND` |
| 2 | 계약이 `SIGNING`인가 | 409 `CONTRACT_STATUS_CONFLICT` |
| 3 | **조건부 UPDATE** `SET handled_at = now, handled_by = :op WHERE id = :requestId AND handled_at IS NULL` | 0행이면 이미 전송됨 → **200 + 현재 카드 상태**(`alreadyNotified: true`) |
| 4 | 자동 안내 말풍선 저장 — sender = `ADMIN` · 운영자 id · `auto_notice = 1` · `client_message_id = resend-notice-{requestId}` | UNIQUE 충돌 = 3번을 통과할 수 없으므로 발생하지 않음(이중 방어) |
| 5 | 요청 행에 `notice_message_id` 기록 | |

- 3번이 **중복 전송 방지의 본체**다. 운영자 둘이 동시에 눌러도 한 명만 1행을 얻는다. 진 쪽은 오류가 아니라 **굳은 카드 상태**(누가 · 언제)를 받는다 — 화면이 같은 결과로 수렴하면 되고 운영자가 할 일이 없기 때문이다.
- 자동 문구는 상수다: 「모두싸인에서 서명 안내를 다시 보내드렸습니다. 메일함(스팸함 포함)을 확인해 주세요.」 문구 확정 · 관리 위치(고정 / 설정에서 수정)는 §36-9 B-11 — 확정 전까지 코드 상수 한 곳(`OperatorNoticeTemplates`)에 둔다.
- **계약 이력에 아무것도 쓰지 않는다** — 2026.09.28 확정(§36-5). `RESEND_HANDLED`를 기록하지 않는다.
- **이 버튼은 운영자의 신고다.** 모두싸인에서 실제로 보냈는지 서버가 검증하지 않는다 — 검증하는 것처럼 보이는 필드 · 문구를 응답에 넣지 않는다.
- 응답: 갱신된 카드 메시지 + 생성된 안내 말풍선.

```json
{ "alreadyNotified": false, "card": { …MessageItem… }, "notice": { …MessageItem… } }
```

### 5-3. 계약 관리 쪽 정리 — `POST /v1/admin/contracts/{id}/resend/handle`

기존 처리 기록 API는 계약의 미처리 요청을 **전부** 닫고 이력 `RESEND_HANDLED`를 쓴다. 새 흐름과 두 가지가 다르다(카드 단위 처리 · 이력 없음).

| 시점 | 처리 |
| --- | --- |
| 이 설계 배포 시 | API는 **남긴다.** 배포 전에 쌓인 카드 없는 미처리 요청(`card_message_id IS NULL`)을 닫을 길이 이것뿐이다 |
| 카드 없는 미처리 요청이 0건이 된 뒤 | 조치 큐 「재발송 요청」 · B3 안내 블록의 존폐 확정(§36-9 A-1 ①)에 맞춰 제거 또는 유지 |

큐를 유지하기로 하면 손댈 것이 없다 — 큐 카운트가 이미 `handled_at IS NULL`이고 카드 버튼이 그 값을 채운다(1-3). 계약 상세 `resend` 블록에 `threadId` · `cardMessageId`를 더해 큐에서 카드로 바로 가는 딥링크를 줄 수 있다 — A-1 확정 후 28 설계서를 고칠 때 함께 넣는다.

## 6. 흐름 ② — 계약 직권 취소 결과 카드

요청은 **일반 대화**로 들어온다. 자동 카드도, 요청을 기록하는 API도 없다. 운영자가 계약 관리 C6에서 취소하면 카드가 붙는다.

`AdminContractCommandService.cancel`에 한 단계를 더한다.

| 조건 | 카드 |
| --- | --- |
| `requesterType = SELLER` 이고 `requestChannel = THREAD` | 그 계약 **브랜드의** 운영팀 채널에 등록 |
| `requesterType = CREATOR` 이고 `requestChannel = THREAD` | 그 계약 **인플루언서의** 운영팀 채널에 등록 |
| 요청 경로가 전화 · 이메일 · 기타 | 없음 — 가리킬 요청 채널이 없다 |
| `requesterType = ADMIN`(직권) | 없음 |

- **`requestThreadId`를 요청으로 받지 않는다.** 요청자가 정해지면 채널은 하나뿐이라(회원당 1개) 서버가 유도한다. 운영자가 스레드 id를 고르게 하면 틀린 채널에 카드가 붙는 경로가 생긴다. 유도한 값을 `contract.cancel_request_thread_id`에 남긴다.
- 취소와 **같은 트랜잭션**이다 — 취소됐는데 카드가 없는 상태를 만들지 않는다. 채널이 없으면 만든다(5-1의 4번과 같다).
- sender = `ADMIN` · 처리 운영자 id → 회원의 배지가 오른다. `client_message_id = contract-cancel-{contractId}` — `CANCELED`는 종료 상태라 계약당 한 번뿐이다.
- **상대방 채널에는 붙이지 않는다** — 미결이다(§36-9 A-5). 통지는 기존 `ContractNotifier.notifyBothParties`가 맡는다. 붙이기로 확정되면 게이트웨이 호출을 한 번 더 하면 된다(멱등키를 `contract-cancel-{contractId}`로 두면 스레드가 달라 충돌하지 않는다).
- 28-1 수정계획의 `requestChannel = THREAD`("소통 스레드")는 이제 **운영팀 채널**을 뜻한다. 쌍 스레드에서 본 요청을 근거로 취소하는 경우에도 `THREAD`를 고르면 요청자의 운영팀 채널에 결과가 붙는다 — 의도한 동작이다(결과를 알릴 곳이 거기다).

### 11-3. 리스크

1. **카드 없는 기존 미처리 요청** — 배포 전에 쌓인 `contract_resend_request`는 카드가 없다. 소급 생성하지 않고 기존 `resend/handle`로 닫는다(5-3). 소급이 필요하면 P3 배포 시 1회성 백필(서명 진행중 계약의 미처리 건에 카드 생성)을 추가한다.
2. **운영팀 채널 누락 회원** — V95 백필 이후 예외 경로로 승인된 회원에 채널이 없을 수 있다. 카드 등록 경로는 그 자리에서 채널을 만들지만(5-1), **목록에는 채널이 있어야 나온다.** P2 배포 전에 「승인된 브랜드 · 등록 완료 인플루언서 수 = 운영팀 채널 수」를 한 번 대조한다.
3. **응답 분리의 회귀** — 운영자 식별자 비노출은 "필드를 안 넣었다"는 사실에만 기대고 있다. 누가 공용 DTO로 합치면 새어 나간다. 어드민 DTO와 회원 DTO를 **합치지 않고**, 9절의 직렬화 테스트로 막는다.
4. **요약 쿼리 비용** — `summary`는 탭의 전 채널을 합산하며 폴링 대상이다. 채널 수가 회원 수와 같아 수천 건까지는 인덱스로 충분하다. 느려지면 스레드에 팀 기준 안 읽은 수를 역정규화한다(지금은 하지 않는다).
5. **`ddl-auto: validate`** — 마이그레이션 → 엔티티 순서. `message` 컬럼 추가는 대상 테이블이 커지면 온라인 DDL 여부를 확인한다.
