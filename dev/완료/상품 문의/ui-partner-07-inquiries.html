ui-partner-07-inquiries — 파트너센터 문의 관리 · rev.4

근거: ui-admin-07-product-qna.html rev.1(상태·용어·컬럼 정본) · wf-partner-07-문의관리 · 디자인시스템 v1.3 · 셸 출처 ui-partner-04-product-management(rev.32) · GNB #8 · 어드민 「상품 문의 모니터링」과 짝

[rev.2 · 어드민 정본에 맞춰 전면 수정] rev.1은 와이어(wf-partner-07)만 보고 그려 어드민과 모델이 어긋나 있었다. ui-admin-07-product-qna 기준으로 아래를 바로잡았다 — ① 상태를 미답변·답변완료·숨김 3종에서 답변대기 · 답변완료 · 삭제 요청 · 삭제 4종으로 교체(숨김 개념 폐기). ② 비공개 → 비밀글. ③ 문의 유형 컬럼 신설(옵션 · 성분·사용법 · 재입고 · 배송 · 기타 — 소비자가 작성 시 필수 선택). ④ 소비자 문의 사양 반영(250자 이내 · 사진 최대 3장) — 상세에 첨부 썸네일 노출. ⑤ 브랜드의 신고를 삭제 요청으로 교체 — 운영자는 삭제 또는 반려로 판단한다. ⑥ 상세 구조를 어드민과 동일한 문의 정보 / 문의 내용 / 브랜드 답변 3카드 + 우측 처리·이력으로 통일(.frow 라벨 140px · 행 9px).
[역할] 문의는 소비자가 작성하고 답변은 브랜드가 작성한다 — 파트너센터가 답변의 유일한 작성 창구다. 운영자에겐 답변 입력란이 없다(모니터링·삭제 판단만). 문의 유형은 옵션 · 성분·사용법 · 재입고 · 배송 · 기타 5종이다. 배송 유형은 상품 자체의 발송 조건(합포장·분리 발송·발송 시점 등)을 묻는 문의이며, 개별 주문의 배송 추적·환불은 여전히 운영자 단일 창구가 처리한다.
[rev.3 · 상태색 3서피스 동일로 확정] rev.2는 「조치 주체 축」을 적용해 답변대기를 파트너센터에서만 경고로 뒀으나, 어드민 정본과 동일한 색으로 통일한다 — 답변대기=정보, 삭제 요청=경고. 같은 상태값이 서피스마다 다른 색으로 보이면 3서피스를 오가는 운영 소통에서 혼선이 생긴다(원칙 ③ 우선). 브랜드의 조치 시급성은 색이 아니라 등록일 아래 경과 시간 표기와 GNB 카운트가 전달한다.
[rev.3 · 상태는 탭으로 분리] 상태는 한 번에 하나만 보는 배타적 축이라 1단 탭으로 올렸다(디자인시스템 v1.3 「탐색 위계 3단」 · 어드민 ui-admin-07과 동일한 구성). 필터 패널에는 겹쳐 걸 수 있는 축(문의 유형 × 공개여부)만 남는다. 탭에는 전체가 있고 필터 패널에는 없다 — 단일선택은 되돌아갈 항목이 필요하지만, 다중선택은 미선택이 곧 전체이고 해제는 초기화 버튼이 맡는다.
[rev.4 · 반려 시 복귀 규칙] 삭제 요청이 반려되면 상태는 요청 직전 상태로 복귀한다 — 답변완료 건은 답변완료로, 답변대기 건은 답변대기로. "항상 답변완료로 복귀"는 틀렸다: 답변하지 않은 문의가 답변완료로 바뀌어 답변 이력이 소실된다. 삭제 요청·삭제는 노출 축이고 답변대기·답변완료는 답변 축이라, 한 열에 표시하는 동안에도 답변 축 값은 내부적으로 보존돼야 한다.
[rev.4 · 반려 결과 인지 경로] 반려는 브랜드가 후속 판단해야 하는 이벤트이므로 처리 이력에 "삭제 요청 반려 · 결과 알림 수신"으로 기록하고 알림을 발송한다. 별도 상태값·배지는 만들지 않는다(상태 축을 늘리지 않는다).
[rev.4 · 답변 수정 허용] 답변은 수정 가능하다 — 공개 콘텐츠라 잘못된 안내를 고칠 경로가 없으면 브랜드가 삭제 요청으로 우회하게 된다. 대신 조용한 수정은 막는다: 답변 카드에 "등록 시각 · 수정 시각" 병기, 처리 이력에 「답변 수정」 기록. [근거 대기] 수정 횟수 제한·소비자 화면의 "수정됨" 노출 여부·어드민에 수정 전 원문을 보여줄지는 미확정.
[rev.4 · 삭제 시 답변 처리] 문의가 삭제되면 브랜드 답변도 함께 소비자 화면에서 내려간다. 질문 없는 답변은 성립하지 않는다. 원문·답변 모두 보관되며 파트너센터·어드민 상세에서만 조회된다.
[상태색 매핑] 답변대기=정보 · 답변완료=중립(성공색 아님, 정상 종결된 일상 상태) · 삭제 요청=경고(운영자 조치 필요) · 삭제=위험(소비자 노출이 실제로 막힌 상태, ui-admin-04 미진열 선례). 전부 어드민 ui-admin-07과 동일하다.
[공개여부는 상태가 아니라 분류] 공개/비밀글은 상태 배지 체계에 넣지 않는다 — 점 없는 중립 배지(.nodot)로 표기한다. 문의 유형도 같은 규칙.
[상세 진입] 행 전체 클릭. 관리 열에 진입 전용 버튼을 두지 않는다(v1.3 「목록 상호작용 규칙」). 와이어의 [답변]·[보기] 열은 삭제했다.
[버튼 비활성 원칙] 답변 미입력 시 [답변 등록]은 에러 문구 없이 비활성(B1). 삭제 요청 모달도 사유 미선택이면 비활성(C1). 답변 글자수는 상한에서 입력이 막히므로(maxlength) 초과 상태 자체가 생기지 않는다 — 이 화면에 에러 문구는 없다(B3). 에러 문구는 형식 오류·중복·파일 형식/용량 오류에만 쓴다.
[권한 3분류] 답변 등록·수정 = ①직접 수정 / 문의 삭제 = ②변경 요청(운영자 검토 경유 — 브랜드는 요청까지, 집행은 운영자) / 공개↔비밀글 전환·문의 내용 수정 = ③변경 불가.
[작성자 표기] 어드민은 실명+회원 상세 링크지만 파트너센터는 닉네임 마스킹만 본다(구****). 회원 상세 링크 없음.
[rev.3 · 답변 SLA 표기 제외] 답변 기한(SLA) 경과·잔여 시간 표기는 넣지 않는다 — 기한 자체가 운영 정책으로 확정되지 않았고, 근거 없는 수치를 화면에 두면 시급성 신호가 먼저 굳어버린다. 목록의 등록일·답변일은 날짜+시:분까지 표기해 실제 소요를 직접 읽게 한다. SLA가 확정되면 상태값을 늘리지 말고 등록일 아래 보조 텍스트로만 얹는다.
[근거 대기] ① 답변 수정 가능 여부·횟수 — 우선 수정 가능 + 수정 이력 표기로 그렸다(B4). ② 답변 글자수 상한 2,000자는 잠정치(소비자 문의 250자는 어드민 확정값) — 값만 미확정이고 초과 입력을 막는 방식은 확정. ③ 삭제 요청 사유 목록 4종 잠정. ④ 답변 후 소비자 알림 발송 여부. ⑤ 상태값 문자열은 기능요구사항 §12·상태정의서 수신 후 최종 대조.
