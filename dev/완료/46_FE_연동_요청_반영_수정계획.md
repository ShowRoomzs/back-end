## 1. 운영자 사유 환불 버튼의 잔액 조건 (B1)

### 1-1. 현재

- `AdminOrderQueryService.actions()`(:229)는 상태(배송중 · 배송완료 · 구매확정)만 본다.
- 편입 API는 상한을 따로 검사한다. `AdminOrderCommandService.checkRefundable`(:238)이 `available = payment.cancellableAmount() − sumOutstandingByPayment(paymentId)`를 계산하고, 금액이 이를 넘으면 409 `REFUND_AMOUNT_EXCEEDED`를 던진다.
- 원인은 버튼 판정과 서버 판정이 서로 다른 식을 쓰는 것이다. 그래서 전액 환불된 주문(20261017-000001)에 버튼이 보이고, 누르면 409가 난다.

### 1-2. 변경

- 잔액 계산을 한 곳으로 모은다. `api/admin/transaction/service/OperatorRefundLimit`(신규 `@Component`)에 `Integer available(Order order)`를 둔다. 결제가 없는 주문은 `null`(상한 없음)을 돌려준다. 지금 `checkRefundable`이 결제 없는 주문에서 바로 반환하는 것과 같다.
- `checkRefundable`은 이 값을 쓴다. 오류 문구는 그대로 둔다.
- `getOrder`가 주문당 한 번 계산해 `actions(group, cancelRequested, available, now)`에 넘긴다.
  `canEnqueueRefund = 상태 조건 ∧ (available == null ∨ available > 0)`
- 요청에 적힌 `amount − cancelledAmount > 0`보다 한 단계 엄격하다. **아직 돈이 나가지 않은 환불(대기 · 집행 중 · 실패)도 뺀다.** 이것을 빼지 않으면, 대기 환불이 잔액을 다 덮은 주문에서 같은 409가 다시 난다.
- 잔액은 결제 단위라서, 한 주문에 속한 하위주문 버튼이 함께 꺼진다.
- `Payment`에 `operatorRefundableAmount`(= `available`)를 더한다. 편입 다이얼로그의 「최대 N원」 안내에 쓴다. 37 설계서의 「취소 가능 잔액 = `amount − cancelledAmount`는 FE 계산」은 화면 표시값으로 남기고, 입력 상한은 이 필드를 쓴다.

> **구현** — `OperatorRefundLimit`은 `available(Order)`(편입 API — 결제 없으면 null)와 `available(Payment)`(상세 — 이미 읽은 결제로) 두 갈래다. 음수는 0으로 깎는다. `operatorRefundableAmount`는 `payment` 블록 안의 `int`다(결제가 없으면 블록 자체가 null).

### 1-3. 테스트

`AdminOrderDetailIntegrationTest`에 다음 3건을 더한다.

- 전액 환불 완료 → `false`
- 대기 환불이 잔액을 전부 덮음 → `false`
- 잔액이 일부 남음 → `true`, `operatorRefundableAmount`가 남은 잔액과 같음

지금 `true`를 기대하는 5곳(`AdminOrderIntegrationTest:219` · `AdminOrderDetailIntegrationTest:213 · 260 · 358` · `Plan1009ScenarioIntegrationTest:315`)은 픽스처에 잔액이 남아 있는지 확인한다.

## 2. 응답 필드 · 파라미터 (B2)

### 2-1. 반품·교환 상세에 `orderId`

- `AdminTransactionDto.ClaimDetail`에 `orderId` · `deliveryGroupId`를 더한다. 값은 `OrderClaim.orderId` 컬럼을 그대로 쓴다.
- 파트너와 같이 쓰는 `SellerClaimDetailResponse`는 건드리지 않는다. 어드민 전용 값은 래퍼에 둔다(브랜드명 · 귀책과 같은 자리).
- FE는 「주문 상세 열기」를 `GET /v1/admin/orders/{orderId}`로 바꾸고, 주문번호 검색 우회를 지운다.

### 2-2. 공구 목록 `marketId`

- `GET /v1/admin/group-buys?marketId=` — 컨트롤러 · docs · `AdminGroupBuyQueryService.getGroupBuys` · `GroupBuyRepositoryCustom.searchForAdmin`을 고친다. 조건은 `adminFilter`(`GroupBuyRepositoryImpl:266`)에 `market.id.eq(marketId)` 한 줄이다.
- 상세의 이웃 계산(`findOrderedIdsForAdmin`)도 같은 파라미터를 받는다. 「목록과 같은 조건 · 같은 정렬」 규칙(`GroupBuyRepositoryCustom:52`)을 지키기 위해서다.
- 요약 · GNB 배지는 바뀌지 않는다. 검색 조건과 무관하게 센다(28 설계 0-5).
- 주문 조회의 공구 셀렉트는 `tab` 없이(전 상태) 부른다. `size`에 상한이 없으니 `size=100`으로 한 번에 받는다.

### 2-3. 인플루언서 선택 목록 — `GET /v1/admin/group-buys/creators?marketId=` (신규)

```json
[
  { "creatorId": 12, "showroomName": "소연_쇼룸" },
  { "creatorId": 31, "showroomName": "하린_뷰티랩" }
]
```

- **공구를 1건 이상 가진 인플루언서만** 내린다(공구 상태는 따지지 않는다). 주문 조회의 `creatorId` 필터는 `g.groupBuy.creator.id`로 거른다(`OrderDeliveryGroupRepositoryImpl:125`). 공구가 없는 인플루언서는 골라도 항상 0건이 나오기 때문이다.
- `marketId`를 주면 그 브랜드와 공구를 연 인플루언서만 내린다. 다만 시안은 인플루언서 셀렉트를 브랜드에 종속시키지 않았다(종속은 공구 셀렉트만). 그래서 FE는 기본으로 `marketId` 없이 부른다.
- 정렬은 `showroomName ASC`, 페이지 없음. 이름은 공구 목록 `creatorName`과 같은 쇼룸명이다.
- 공구 관리 컨트롤러에 둔다. 목록의 출처가 공구이기 때문이다. `/{groupBuyId}`와 경로가 겹치지 않는다(리터럴 경로가 우선 — `/summary`와 같다).
- 회원 관리 > 인플루언서 목록은 다른 화면이라 이번 범위가 아니다.

> **확인 필요 — 브랜드 셀렉트의 출처.** FE가 `/v1/admin/markets`를 쓰고 있다면, 그 API는 기획 제외 대상(`AdminMarketController` · `@Hidden`)이다. 활성 화면이 보류 중인 API에 기대게 된다. 그렇다면 같은 자리에 `GET /v1/admin/group-buys/brands`를 두기를 권한다(8절 #8). 기획 제외 코드는 건드리지 않는다.

## 3. 반품·교환 (06b · B3-1~3)

### 3-1. 목록 「경과」를 영업일로

- 지금 `SellerClaimListItem.elapsedDays`는 단계 진입(`stageEnteredAt`)부터 센 달력일이다(`SellerClaimAssembler:89`). 파트너 11과 같은 값이다.
- 어드민 행(`AdminTransactionDto.ClaimListItem`)에 `elapsedBusinessDays`를 더한다. 계산은 `BusinessCalendar.businessDaysBetween(stageEnteredAt.toLocalDate(), today)`이다. 같은 서비스의 `inspectOverdueBusinessDays`와 같은 함수이고, 기산일은 넣지 않는다.
- 파트너의 `elapsedDays`는 바꾸지 않는다.
- 시안 「입고 3영업일」 · 「통과 1영업일」의 앞말은 단계마다 정해져 있다. FE가 `stage`와 `reshipReason`을 보고 고른다.

### 3-2. 법정 청약철회 기한

시안은 이 블록을 **운영자가 대신 연 클레임(B6)에만** 그린다. 06b 시안에 따르면, 이 클레임이 다른 클레임과 다른 값은 출처 · 근거 문의 · 법정 기한 세 가지다.

| 값 | 출처 | 시안 예시 |
| --- | --- | --- |
| 공급일 | 하위주문 `deliveredAt` | 08.27 |
| 공급 기준 기한 | 공급일 `plusMonths(3)` | 11.27 |
| 하자 인지일 | **저장하는 곳이 없다** | 09.17 |
| 인지 기준 기한 | 인지일 `plusDays(30)` | 10.17 |
| 적용 기한 | 둘 중 이른 날 | 10.17 |

- B6 개설 요청(`AdminOrderDto.DefectClaimRequest`)에 선택 입력 `defectNoticedOn`(`LocalDate`)을 더한다. 공급일 이후이고 오늘 이전이어야 한다.
- 저장: `V184__alter_order_claim_add_defect_noticed_on.sql` — `order_claim.defect_noticed_on DATE NULL`. `opened_by` · `opened_by_admin_id`와 같은 행에 두고, 한 요청에 속한 클레임에 같은 값을 넣는다.
- 응답: `ClaimDetail.legalDeadline { suppliedOn, supplyDeadline, noticedOn, noticeDeadline, appliedDeadline }`. 운영자가 연 클레임이 아니면 `null`이다. 인지일이 없으면 인지 쪽 두 칸이 `null`이고, 적용 기한은 공급 기준 기한이 된다.
- 개설 가능 판정(`canOpenDefectClaim` = 배송완료 후 3개월 안)은 바꾸지 않는다. 30일 기한이 지난 건의 개설을 막을지는 법무가 판단한다(8절 #9).

> **구현** — 인지일이 배송완료일보다 앞이거나 오늘보다 뒤면 400 `INVALID_INPUT`이다(입력 오류라서). 30일이 지난 건은 그대로 연다.

### 3-3. 정산 반영

- 06a ④가 쓰는 포트를 그대로 쓴다 — `OrderSettlementReader.readByDeliveryGroup(deliveryGroupId)`.
- `ClaimDetail.settlement { settlementNumber, statusLabel, confirmedAt, deductOnPass }`를 더한다. 정산이 아직 없으면 `null`이고, FE는 「정산 전 · 생성 시 반영」을 그린다.
- `deductOnPass` = 정산 있음 ∧ 반품 ∧ 검수 판정 전. 차감은 반품 통과 환불(`CLAIM_RETURN_PASSED`)이 집행된 뒤 `SettlementClawbackService.register`가 만든다. 교환과 반려는 환불이 없으므로 차감도 없다.
- 시안의 「브랜드 수취액 · 리워드」는 차감되는 쪽의 이름이라 고정 문구로 둔다.

> **구현** — `ClaimSettlement`에 정산 상태 코드 `status`도 싣는다(06a ④ `settlement`와 같은 값 · 배지 색용).

## 4. 주문 조회 (06a · B3-4~11)

06a의 변경은 모두 `AdminOrderDto` · `AdminOrderQueryService` 안에서 끝나고, DB는 바뀌지 않는다.

### 4-1. 행 확장 — 항목 요약 · 금액 · 송장 (+ 공구명)

`GroupSummary`에 다음을 더한다.

```json
{
  "subOrderNumber": "20260916-000201-02",
  "brandName": "데일리랩",
  "itemSummary": "데일리 선크림 외 1종",
  "itemQuantity": 2,
  "amount": 24400,
  "carrier": null, "carrierLabel": null, "trackingNumber": null,
  "groupBuyTitle": "데일리 선크림 공구"
}
```

- `itemSummary` — 첫 항목의 상품명에 나머지를 「외 N종」으로 붙인다. 항목이 1종이면 옵션명을 붙인다. 시안: 「글로우 크림 50ml」 · 「데일리 선크림 외 1종」.
- `itemQuantity` — 수량 합. 시안의 「· 2건」이 종 수인지 수량 합인지는 FE가 시안으로 확인한다. 기본은 수량 합이다.
- `amount` = `productTotal + deliveryFee`. 행 확장 금액의 합은 주문 `totalAmount`와 같아야 한다(시안: 34,000 + 24,400 = 58,400). 이것을 테스트로 고정한다.
- `groupBuyTitle` — FE 요청 목록에는 없지만, 시안 목록의 「공구명」 열에 쓴다. 4-8과 같은 조회라서 함께 넣는다.
- 조회 방식: 한 페이지의 하위주문 id 전체로 `orderProductRepository.findByDeliveryGroupIds`를 1회 부른다. 공구명도 공구 id로 1회 읽는다. 하위주문마다 따로 조회하지 않는다.

### 4-2. 배송 이상 경과 문구

### 4-3. 상태 · 이상 유형 셀렉트 건수

`SummaryResponse`에 두 가지를 더한다.

## 5. 환불 관리 (06c · B3-12~13)

### 5-1. M1 클로백 금액

**현재**

- `RefundClawback { clawbackNumber, status, statusLabel }`에는 금액이 없다. 측별 2행(브랜드 · 인플루언서) 중 덜 끝난 쪽 하나를 대표로 낸다(`SettlementOrderReader:54`).
- 더 근본적인 문제가 있다. **차감 행은 환불이 집행(DONE)된 뒤에 생긴다**(`SettlementClawbackService.register`). M1은 집행하기 전에 보는 화면이라, 지금 구조로는 M1에서 보여 줄 차감 행이 아예 없다.

**변경**

1. **집행 후** — `RefundClawback`에 `brandAmount` · `creatorAmount`를 더한다. 포트 record `OrderSettlementReader.RefundSettlement`에 측별 행 목록을 싣는다.
2. **집행 전(M1)** — `RefundSettlement.expectedClawback { brandAmount, creatorAmount }`를 더한다. `register`와 **같은 식**으로 계산만 하고 저장하지 않는다.

   ```
   CREATOR = 단위 리워드 × 환불 수량
   BRAND   = 환불 상품 금액분 − CREATOR − floor(CREATOR × 리워드 부가세율)
   ```

   이 식을 `register`에서 순수 메서드로 떼어 내 두 곳이 같이 쓴다. 예정액과 실제 차감액이 어긋나지 않게 하기 위해서다.
   - 조건: 정산 생성 후(`state = SETTLED`) ∧ 차감 대상 출처(`OPERATOR_REASON` · `CLAIM_RETURN_PASSED` — `isClawbackSource`) ∧ 차감 행이 아직 없음. 이 밖에는 `null`이다.
3. 포트 메서드 시그니처는 그대로 두고, record 필드만 더한다.

> **구현** — 예정액은 `SettlementClawbackLedger.preview(refundTaskId)`가 낸다. `SettlementClawbackService`의 계산을 `split(task)`로 떼어 `register`와 `preview`가 같이 쓴다. 대상은 아직 돈이 나가지 않은 환불(대기 · 집행 중 · 실패)뿐이다. 측별 금액은 이월로 행이 나뉘어도 측마다 합친다.

```json
"settlement": {
  "state": "SETTLED",
  "stateLabel": "정산 STL-2610-004 생성 후",
  "settlementNumber": "STL-2610-004",
  "clawback": null,
  "expectedClawback": { "brandAmount": 24208, "creatorAmount": 2720 }
}
```

### 5-2. M2 자동 재시도

- 지금 FE는 `failure.attempts[]`에서 `actorType = SYSTEM`인 행을 세어 추정한다. `attempt`는 운영자 재시도까지 포함한 전체 시도 수라서 그대로 쓸 수 없다.
- `RefundDetail.autoRetry { count, lastAt, exhausted }`를 더한다.
  - `count` = 시스템 실패 이력 수 − 1. 최초 자동 집행은 재시도로 세지 않는다.
  - `lastAt` = 마지막 시스템 실패 시각
  - `exhausted` = 자동 시도가 상한(`refund-auto-max-attempts` — 기본 2, 최초 + 1회)에 닿았는가. 이 건이 실패 탭에 올라온 이유다.
- PG 자동 환불(`origin = PG_AUTO`)에만 내린다. 운영자 사유 환불은 자동 재시도를 하지 않으므로 `null`이다.
- 시안의 「자동 재시도 1회 · 실패 · 09.16 15:31」은 `count = 1`과 `lastAt`으로 그린다.

## 7. 소비자 앱 (A1~A5)

### 7-1. 취소 요청 철회 (A1)

**현재**

- `CancelRequestStatus`는 `PENDING` · `APPROVED` · `REJECTED` · `VOIDED`(시스템이 닫는 값) 넷이고, 철회 API는 없다.
- C10 설계 7-2 C6 「`WITHDRAWN` 추가 여부」가 정해지지 않은 채 남아 있다. 시안에는 [취소 요청 철회] 버튼과 확인 모달이 있고, 안내 박스에도 「확인 전까지는 요청을 철회할 수 있어요」가 적혀 있다.

**변경 (제공으로 정하면)**

- `CancelRequestStatus.WITHDRAWN`을 더한다. `status`가 `VARCHAR(16)`이라 DDL은 필요 없다.
- `POST /v1/user/orders/{orderId}/cancel-requests/{cancelRequestId}/withdraw`를 둔다. 응답은 클레임 철회(`UserClaimDto.WithdrawResponse`)와 같은 모양으로 한다.
- 철회는 **요청 단위**다. 요청에 담긴 항목이 모두 함께 철회된다(클레임 철회는 항목 단위라 다르다).
- 도메인 `OrderCancelRequestService.withdraw`: 하위주문을 `findForUpdate`로 잠근 뒤 `UPDATE … SET status = WITHDRAWN, decided_at = now WHERE id = ? AND status = PENDING AND requested_by = ?`를 실행한다. 0행이면 409 `CANCEL_REQUEST_ALREADY_DECIDED`를 던진다. 브랜드 승인 · 거부와 자동 승인 배치도 같은 행을 `PENDING` 조건으로 갱신하므로, 경합하면 한쪽만 성공한다.
- 철회의 효과
  - 송장 잠금이 풀린다. 잠금은 `PENDING` 행이 있는지로 판정하므로 따로 할 일이 없다.
  - 앱 항목이 원래 상태(상품준비중)로 돌아간다.
  - 파트너 · 어드민 취소 탭에서 빠진다.
  - 이력 `CANCEL_REQUEST_WITHDRAWN("취소 요청 철회")`이 actor `CONSUMER`로 남는다.
- 취소 상세: 검토 중 응답에 `withdrawable: true`를 더하고, 안내 문구에 시안의 철회 문장을 붙인다(7-4). 철회된 요청은 상세 조회에서 `VOIDED`처럼 건너뛴다(`UserCancelService:69`).
- 다시 요청하는 것은 막지 않는다. 검토 중 요청이 없으면 낼 수 있다는 기존 조건 그대로다. 다만 요청과 철회를 반복하면 발송이 계속 잠길 수 있다. 횟수 제한은 기획이 정한다(8절 #2).
- 브랜드 알림은 보내지 않는다. 요청을 만들 때도 보내지 않는다(`OrderCancelRequestService`).
- 테스트: 철회 후 송장 등록 가능 · 철회 후 브랜드 승인 409 · 승인 후 철회 409 · 자동 승인 배치가 철회된 건을 건너뜀 · 철회 후 재요청 가능 · 남의 주문 404.

> **구현** — 남의 주문 · 다른 주문의 요청 · 없는 요청은 모두 404 `ORDER_NOT_FOUND`다. 응답은 `WithdrawResponse { orderId, cancelRequestId, deliveryGroupId, orderProductIds, withdrawnAt }`.

### 7-2. 취소 수량 선택 (A2)

- 서버는 항목 전량 취소만 받는다. 요청 바디에 `orderProductIds`만 있고, `order_cancel_request_item.quantity`에는 항목 수량 전체가 들어간다. 1009 수정계획 3-1은 `items[]{ orderProductId, quantity? }`로 적었지만, C10 설계 7-2 C2(수량 쪼개기)가 정해지지 않아서 전량으로 구현했다.
- 수량 일부 취소를 받으려면 바뀌는 곳이 많다.
  - 항목에 취소 수량 컬럼 추가(반품의 `returned_quantity`가 선례)
  - 승인 경로의 부분 재고 원복 · 부분 환불액
  - 정산 항목 수량
  - 앱 · 파트너 · 어드민의 항목 표시(일부 취소 · 남은 수량)
  - 결제완료 단계 직접 취소(C1)와의 정합
- 규모가 커서 별도 설계서가 필요하다.
- 기본값은 **전량 유지**이고, 시안에서 스테퍼를 뺀다. 항목(옵션) 단위 선택은 이미 되므로, 차이는 한 항목의 수량이 2개 이상일 때만 생긴다.

### 7-3. 재발송비 결제 기한이 지난 경우 (A3)

**현재**

- 목록의 할 일 줄(`UserClaimPresenter.rejectHold`)은 기한이 지나면 날짜를 빼고 「재발송 배송비 결제 필요」만 쓴다.
- 상세의 `reshipFee.dueDate`는 상태가 `PAYABLE`이면 지난 날짜도 그대로 내린다(`UserClaimQueryService:474`). 그래서 앱이 「10.16(금)까지 결제해 주세요」를 그린다. 두 화면의 기준이 다르다.
- 기한이 지나도 결제는 막히지 않는다(`ClaimPaymentService`에 기한 검사가 없다). 기한이 지나면 `reshipFee.storage`(미결제 고지 횟수 · 보관 기한 · 단계)가 함께 내려간다.

**변경**

- `reshipFee.overdue: boolean`을 더한다. `dueDate`는 그대로 둔다(「기한 10.16 지남」 같은 표기에 쓸 수 있게).
- 문구는 기획이 정한다. 기본값으로 다음을 제안한다.

| 상황 | 문구 |
| --- | --- |
| 기한 경과 · 고지 전(`storage.phase = NOTICE_PENDING`) | 「결제 기한(10.16)이 지났어요. 결제하면 반려 상품을 다시 보내드려요」 |
| 기한 경과 · 보관 중(`STORING`) | 위 문장 + 「보관 기한 11.23 · 이후 처리는 고객센터로 안내드려요」(1009 앱 변경 내역의 보관 문구) |
| 보관 기한도 지남(`EXPIRED`) | 「보관 기한이 지났어요. 고객센터로 문의해 주세요」 |

### 7-4. 서버 문구와 시안 문구 (A4)

원칙부터 정한다. 기본값은 **소비자 앱에 보이는 문구는 시안을 따른다**이다. 서버가 앱용 문구만 바꾸고, 파트너 · 어드민 라벨은 그대로 둔다.

서버가 시안(1009 수정본 C10 · C10-3)과 대조해 찾은 차이는 다음과 같다.

| 위치 | 서버 | 시안 | 고칠 곳 |
| --- | --- | --- | --- |
| 취소 상세 상태(검토 중) | 확인 중 | 취소 요청 · 브랜드 확인 중 | `UserCancelService:113` |
| 취소 상세 상태(거부) | 취소 요청 거부 | 취소 반려 | `UserCancelService:114` |
| 취소 상세 안내(검토 중) | 「…자동으로 취소돼요」 | 「…자동으로 취소돼요. 확인 전까지는 요청을 철회할 수 있어요.」 | `NOTICE_AUTO_APPROVE` — A1을 제공할 때만 |
| 반품·교환 사유 `DAMAGED_OR_DEFECTIVE` | 배송 상품 파손 및 불량 | 상품 파손 · 불량 | 앱 전용 라벨 |
| 반품·교환 사유 `WRONG_OR_LATE_DELIVERY` | 오배송 및 배송 지연 | 오배송 (다른 상품이 왔어요) | 앱 전용 라벨 |

- `ClaimReason.label`은 파트너 11 · 어드민 06b · 이력이 함께 쓴다. 앱만 바꾸려면 `ClaimReason`에 `appLabel`을 두고, 앱 조립 두 곳(폼 `FormReason.label` · 상세 `reasonLabel` `UserClaimQueryService:281`)에서만 쓴다.
- **「배송 지연」이 앱 선택지에서 사라진다.** 시안의 반품 사유에는 「오배송 (다른 상품이 왔어요)」만 있다. 늦게 도착해서 반품하려는 소비자는 고를 사유가 없고, 「단순 변심」을 고르면 소비자 귀책이 된다. 기획 확인이 필요하다(8절 #6).
- FE는 반품·교환 사유가 「일부 다르다」고만 적었다. FE가 아는 나머지 차이를 받아 한 번에 반영한다.

> **구현** — `appLabel` 필드 대신 `ClaimReason.getAppLabel()` 메서드로 뒀다(enum 생성자를 바꾸지 않는다). 거부 사유(`CancelRejectReason`) 라벨은 차이가 확인되지 않아 그대로다.

### 7-5. 배송지 변경 시 요청사항 (A5)

- 지금 `CheckoutService.changeDeliveryAddressTx`(:270)는 새 배송지에 저장된 메모를 `orders.delivery_memo`에 복사한다. C10 설계 3-6 「그 배송지의 값을 … `delivery_memo`에 복사한다」 그대로다. 새 배송지에 메모가 없으면 `null`이 되어, 결제할 때 적은 요청사항이 사라진다.
- 설계 의도는 「메모는 배송지를 따라간다」이다. 「경비실에 맡겨 주세요」 같은 장소 지시가 다른 주소로 따라가면 오히려 잘못 배송된다. 시안 C13도 「배송 메모」를 배송지의 속성으로 둔다.

| 선택지 | 동작 | 규모 |
| --- | --- | --- |
| (a) | 현행 유지. 앱이 변경을 확인할 때 「배송 요청사항도 새 배송지의 메모로 바뀌어요」라고 안내한다 | 없음 |
| (b) | 새 배송지에 메모가 없으면 기존 메모를 유지한다 | 소 |
| (c) | 변경 요청에 `memo`(선택)를 더한다. 앱이 새 배송지 메모를 초기값으로 보여 주고, 고친 값을 보낸다. 결제 화면(「저장된 배송 메모 — 요청사항의 초기값」)과 같은 방식이다 | 소 |

- 기본값은 (a)다. (b)는 장소 지시가 다른 주소로 따라가는 문제가 그대로 남아 권하지 않는다.
