## 25. 어드민 회원 관리 — 소비자 — [v0.33 신설]

대상 화면: `ui-admin-12-consumers.html`(**rev.1**, 목록) · `ui-admin-13-consumer-detail.html`(**rev.1**, 상세). 상태 14종(목록 3 · 상세 11). 셸·카드·필드행·모달·배지는 §16 컴포넌트를 재사용했다. GNB **3. 회원 관리 > 소비자**.

**성격 — 개인정보 열람 통제가 화면의 골격이다.** 다른 어드민 화면이 "무엇을 판단하는가"로 짜였다면, 이 화면은 **"누가 무엇을 언제 봤는가"**를 남기는 구조가 먼저다. 목록은 마스킹 상태로만 훑고, 해제는 상세에서 **사유를 남겨야만** 가능하다.

### 25-1. 마스킹 — 기본 규칙 — `FE`·`BE`

| 위치 | 규칙 |
| --- | --- |
| **목록** | 이름 **가운데 1자** · 휴대폰 **가운데 4자리** 마스킹. **해제 경로 없음** |
| **상세** | 기본 마스킹. 해제는 본인확인 카드 헤더 버튼으로만 |

| 항목 | 규칙 |
| --- | --- |
| 해제 대상 | **이름 · 생년월일 · 휴대폰 3개 일괄** |
| **CI/DI** | **카드에 표시하지 않으며 해제 대상도 아니다** |
| 배송지 | **상세주소·수령인·연락처도 마스킹 통제 대상** — 마스킹 중에는 **시·군·구까지만** 노출. 주소는 본인확인 정보와 같은 급이다 |
| 검색 축 | **회원번호 · 닉네임 · 휴대폰 뒤 4자리** 3축 |

**마스킹 상태로도 CS가 가능한 이유** — **휴대폰 뒤 4자리가 남는다.** 검색도 뒤 4자리 기준이라 목록에서 대조가 된다. 전체 값이 필요한 순간은 **CS 대응 1건 단위**이므로 상세에서만 해제한다.

### 25-2. 마스킹 해제 — `FE`·`BE`

| 항목 | 규칙 |
| --- | --- |
| 진입 | 본인확인 카드 헤더 `마스킹 해제` → 사유 모달 |
| **해제 사유** | **정형 4종 단독** — CS 응대 / 배송 사고 / 결제·반품 분쟁 / 수사기관 협조 |
| **`기타` 없음** | **이 4종을 벗어나는 열람이 정당한 경우가 없다.** 해당하지 않으면 열람하지 않는다 |
| **상세 사유 입력란** | **두지 않는다** — 열람 1건마다 서술을 받으면 형식적으로 채워질 뿐이고, **사유 축은 통계로 집계돼야** 한다 |
| 실행 버튼 색 | **인디고**(위험색 아님) — 파괴적 행위가 아니라 **기록되는 조회**다 |
| 범위 | **이 소비자 1건 · 이 세션 한정** |
| 기록 | 열람 사실 + 사유를 **처리 이력에 즉시** 기록. 도트는 **경고색**(열람은 조치와 같은 급의 사건) |
| 해제 후 표시 | 헤더에 **해제됨 · 처리자 · 시각** + **남은 시간 카운트다운(mm:ss)** |
| **권한** | **최고관리자 한정**(`[신규제안]`). 운영자 역할이면 버튼 비활성 + 툴팁 |

**재마스킹 트리거 4종**

| # | 트리거 | 사유 재입력 |
| --- | --- | --- |
| ① | 다른 소비자 상세로 이동 | **필요** |
| ② | 새로고침 · 재진입 | **필요** |
| ③ | **무조작 10분 경과**(자동) | **직전 사유 프리필 → 확인만** |
| ④ | **`지금 잠금`** 수동 버튼 | **필요** |

| 항목 | 규칙 |
| --- | --- |
| ③만 프리필하는 이유 | **같은 업무를 이어가는 중**이다. 사유를 다시 쓰게 하지 않는다 |
| ③의 알림 톤 | **중립** — 정상 만료라 경고할 일이 아니다. 별도 토스트를 띄우지 않는다 |
| **한 자리 통합** | 카운트다운 · 자동 잠김 표시 · `지금 잠금` 버튼이 **모두 해제 칩과 같은 자리**를 쓴다 — **권한의 상태가 한 곳에서만 바뀌게** 해 놓친 알림으로 열린 채 남는 일을 막는다 |
| ④를 둔 이유 | 열람이 끝난 시점을 **운영자가 스스로 닫을** 수단이 필요하다. 10분을 기다려야만 닫힌다면 **자리를 비울 때 화면을 그대로 두게 된다** |

### 25-4. 상세 — 좌우 분업과 조치 — `FE`·`BE`

| 열 | 성격 | 내용 |
| --- | --- | --- |
| **좌측** | **사실 조회** | 계정 정보 · 본인확인 정보 · 최근 주문 5건 · 콘텐츠 활동 · 배송지 · 약관 동의 내역 |
| **우측** | **판단과 조치** | 현재 상태 + 액션 → **판단 메타** → 관리자 메모 → 처리 이력 |

| 항목 | 규칙 |
| --- | --- |
| **거래 지표 위치** | 누적 주문·구매액·반품률을 **좌측이 아니라 액션 버튼과 같은 열**에 둔다 — **그것이 조치의 근거**이기 때문이다. 정지 버튼을 누르는 눈이 근거를 다시 찾아 좌측으로 내려가지 않게 한다 |
| **반품률 병기** | `2건 · 14.3%` — **"2건"만으로는 판단이 서지 않는다.** 주문 3건 중 2건과 40건 중 2건은 다른 신호다. 계정 정지 권한을 가진 화면이다 |
| **소셜 이메일** | **두지 않는다** — **Apple 릴레이 주소는 실제 연락 가능한 주소가 아니어서** 신뢰할 수 없고, 있으면 CS가 그 주소로 연락을 시도한다 |
| 정지 버튼 스타일 | **흰 배경 + 중립 테두리 + 위험색 글자** — 위험은 알리되 화면의 유일한 강조가 되지 않게. **꽉 찬 위험색은 정지 모달의 최종 실행 버튼에만** |
| 배송지 | **조회 전용.** 운영자는 수정·삭제하지 않으며 잘못된 주소는 소비자가 앱에서 고친다. 각 항목에 **최근 사용 주문일**을 붙여 배송 사고 대조에 쓴다 |
| 신고 관련 행 | 게시물 신고가 `[자문대기-법률 · 쟁점 J]`라 **행 자체를 그리지 않았다** — **없는 데이터를 UI에 올리지 않는다** |

**계정 정지**

| 항목 | 규칙 |
| --- | --- |
| 정지 사유 | **6종** — 욕설·비방 / 반품 남용 / 부정 주문 의심 / 결제 도용 의심 / 신고 다수 접수 / 기타(직접 입력) |
| 상세 사유 | **`기타(직접 입력)`일 때만 필수** |
| 모달 구성 | **"변경할 상태" 셀렉트를 두지 않는다** — 버튼이 이미 목적지를 말한다. **한 번에 갈 수 있는 곳이 하나뿐인 선택지는 실수만 만든다** |
| **차단 범위** | **로그인·주문 차단 / 문의 작성은 허용** |
| 알림 | 사유를 알림으로 발송 |
| 진행 중 주문·반품 | **유지**(25-6 미결 9번) |
| 기록 | 사유·처리자·일시를 **처리 이력에 영구 기록** |
| 정지 상태의 좌측 카드 | **전부 조회 가능** — 정지 사유를 재검토하려면 주문·활동을 다시 봐야 한다 |
| 정지 상태의 액션 | `활성으로 변경` 단독 — **정지 버튼을 두지 않는다**(같은 상태로 다시 보낼 일이 없다) |

**문의 작성을 막지 않는 이유** — **소명 창구가 1:1 문의뿐**이다. 그것까지 막으면 이의를 제기할 방법이 사라진다.

**소명 경로 — 1:1 문의 단일 창구**

별도 이의 신청 화면을 만들지 않는다. **창구가 둘이면 어느 쪽이 접수됐는지 소비자도 운영자도 모른다.** 해제 모달에는 그 **소명 문의 번호를 함께 띄우고 클릭 이동**할 수 있게 한다 — 소명이 1:1 문의로만 오므로 **해제 판단의 근거가 그 문의에 있다**.

**정지 해제**

| 항목 | 규칙 |
| --- | --- |
| 해제 사유 | **3종** — 소명 확인 완료 / 오처리 정정 / 제재 기간 종료 |
| 상세 사유란 | **두지 않는다** — 정지 사유(6종)와 **다른 축**이며 무엇을 확인했는지는 사유 코드로 충분하다 |
| 모달 톤 | **정보 톤 + 인디고 실행 버튼** — **되돌리는 조치**라 위험 경고가 아니다 |
| 모달 표시 | 원 정지 사유·처리자·일시 + **소명 문의 번호** |
| 결과 | 로그인·주문 즉시 재개 · 알림 발송 · **정지 이력과 사유는 그대로 보존** |

### 25-5. 탈퇴 — 셀프서비스 — `FE`·`BE`

| 항목 | 규칙 |
| --- | --- |
| **운영자 액션** | **없다** — 승인·반려 버튼을 두지 않고 우측에 안내로 명시해 **"처리해야 하는 화면"으로 오해하지 않게** 한다 |

| 마스킹 해제 | **비활성** |
| 판단 메타 | 값이 사라지고 **가입 후 경과만** 남는다 |

**보존·파기 범위 (시안 기준 — 법률 확정 대기)**

| 구분 | 항목 |

| **보존** | 주문 내역 · **약관 동의 내역**(동의 기록은 파기 대상이 아니다) |

### 25-6. 관리자 메모 — `FE`·`BE`

**메모는 조치하지 않은 판단의 기록이다.** 정지·해제처럼 이력에 남는 조치와 달리, **"기준에 못 미쳐 넘어갔다"는 판단은 어디에도 남지 않아** 다음 담당자가 같은 검토를 반복한다.

| 항목 | 규칙 |
| --- | --- |
| **누적 기입** | 덮어쓰기가 아니다(`[신규제안]`). 항목마다 **작성자·일시**가 붙고 **최신순**으로 쌓인다 — **덮어쓰기면 판단의 시간축이 사라진다** |
| 분량 | 항목당 **300자** |
| **수정·삭제 권한** | **작성자 본인 · 작성 후 24시간 내** — **오타 정정은 열어 두고 사후 편집은 막는다**. 서버에서 검증한다 |
| 수정 UI | **인라인 편집**(모달 아님) — **앞뒤 메모를 보면서 고쳐야** 한다. 저장하면 일시 옆에 `수정됨`이 붙고 새 입력란은 감춘다 |
| 삭제 | **모달 확인** + 대상 본문 표시 · 사유 입력 없음. 삭제해도 **처리 이력의 기입 기록은 남는다** |
| **열람청구 고지** | 입력란 위 **상시 노출** — "소비자에게 노출되지 않지만 **개인정보 열람청구 시 제공 대상**이 될 수 있다" |
| 미입력 처리 | 기입 버튼 **비활성** · 에러 문구 없음 |
| 빈 상태 | 입력란과 고지는 그대로 두고 **메모를 남기는 이유를 한 줄로** 적는다("없음"만 쓰면 왜 있는 칸인지 알 수 없다) |
| **적용 범위** | **브랜드·인플루언서 상세(F4·F5)에도 동일 규칙** |

**고지를 상시 노출하는 이유** — 내부용이라는 이유로 주관적 서술이 들어가는 것을 **입력 시점에 막는 게 사후 검수보다 확실하다.**

### 25-7. 미결 항목 — `FE`·`BE`
