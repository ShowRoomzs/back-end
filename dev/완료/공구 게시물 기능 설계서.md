# 공구 게시물 기능 설계서

Sep 26, 2026 · @hc

## 1. 개요 · 범위

이 설계는 **이미 쓰기가 끝난 공구 게시물을 소비자 앱(C1·C3·C4·C5)에 내보내는 읽기 계층**이다. 작성·심사·숨김은 31·32 설계로 구현돼 있고, 소비자 경로만 `post_type = GENERAL` 필터로 막혀 있다(31 설계 0-6 ④ "소비자 노출 설계가 나올 때까지"). 이 문서가 그 설계이며, 신규 테이블은 없다.

**끝난 공구의 게시물은 종료 후 3일(72시간) 동안 마감 상태로 보여주고, 그 뒤 소비자에게서 내린다(2026-09-26 확정).** 결정 경위는 4-1.

| 화면 | 이번에 할 일 | 현재 상태 |
| --- | --- | --- |
| C5 공구 게시물 상세 | 제목·배지·광고 표시·상품 전체·판매 상태를 응답에 싣는다. 종료 후 3일까지 `공구 마감`으로 열린다 | 상세 API는 있으나 공구 필드가 없고, 종료 즉시 404 |
| C4 쇼룸 | "진행 중인 공구" 고정 섹션 + 아래 피드에 일반 게시물과 종료 3일 이내 공구를 섞는다 | 피드가 일반 게시물만 내린다 |
| C1 홈 | 팔로잉·추천 피드에 진행 중 공구 카드(상품 행 + 더보기)를 섞는다 | C1 완료 — 일반 게시물만 |
| C3 좋아요 | 종료 3일 이내 공구를 목록에 남기고, "공구 게시물 먼저" 정렬을 진행 중 기준으로 고친다 | C3 완료 — 노출 중인 공구 게시물이 제목 없는 일반 카드로 나가고, 종료 즉시 사라진다 |

**범위 밖** — 공구 게시물 쓰기(31 설계), 어드민 심사·숨김(32 설계), C7 상품 상세·구매 가격(8절 미결 ①), C5 시트의 "이 쇼룸의 게시물 그만 보기"(쇼룸 뮤트는 별도 기능), 신고 사유 목록 확정(C5 남은 결정 ③).

## 2. 화면별 요구사항

네 화면이 같은 공구 카드를 쓰고, 다른 것은 **상품을 몇 개 그리는가**와 **마감 게시물을 보여주는가**뿐이다. 서버는 한 가지 공구 블록을 내리고, 화면별 차이는 조회 조건으로만 다룬다.

| 요소 | 디자인 규칙 | 데이터 원천 |
| --- | --- | --- |
| 제목 | 공구만 있음. 카드 16/700, 상세 17/700 | `group_buy_post.title` |
| 본문 | 카드 2줄 말줄임, 상세 전문 | `post.content` |
| 상태 배지 | `공동구매 D-3` · `품절`(전체 소진) · `공구 마감`/`공구 종료`. 일부 품절은 D-day 유지 | `group_buy.status`·`end_at` + 상품 재고 (파생) |
| 유료 광고 포함 | 공구 게시물에 항상 | `GroupBuyPostPolicy.requiresAdDisclosure()` · `GroupBuyDisclosure` |
| 상품 행 | 썸네일 90 · 상품명 · 정가(취소선) · 할인율 · 공구가. 품절·마감 행은 흑백 + 라벨 | `contract_item` + `product` |
| 상품 더보기 | 대표 1개 노출, 나머지는 버튼으로 **인라인 펼침**(추가 호출 없음) | 상품 전체를 한 번에 내린다 |
| 하트 | 마감이면 회색 · 해제만. 품절은 막지 않음 | 기존 `likeLocked` (`canLike`) |
| 아바타 로즈 링 | 쇼룸에 진행 중 공구가 있음 | 기존 `hasOngoingGroupBuy` — 정의 수정(4-5) |

| 화면 | 상품 행 | 마감 게시물(종료 후 3일) | 비로그인 |
| --- | --- | --- | --- |
| C1 홈(팔로잉·추천) | 대표 1 + 더보기 | **내리지 않음** — 마감 카드 시안 없음 | 추천만 |
| C3 좋아요 | 대표 1, 더보기 없음 | 남김 · `공구 종료` 배지 · 상품 블록 접힘 · 본문 50% 딤 | 로그인 유도 |
| C4 쇼룸 | 대표 1 + 더보기 | 아래 피드에 남김 · 글만(상품 행 없음) | 열람 가능 |
| C5 상세 | 전체(대표 1 + 더보기) | 열림 · 상품 행 전부 흑백 + `공구 마감` | 열람 가능 |

C4는 진행 중 공구를 **상단 고정 섹션**으로 따로 그리고, 없으면 섹션 자체를 감춘다(1c). C5는 사진이 없고 하단 구매 CTA도 없다 — 구매는 상품 행 → C7 한 경로다.

시안의 종료 상태(C3 `공구 종료` 카드, C4 종료 게시물, C5 `공구 마감`)는 **종료 후 3일 동안만** 나타난다. 시안은 기한 없이 남기는 것으로 적었으므로, 3일 뒤 사라진다는 점을 디자인·앱에 공유한다(8절 미결 ⑩).

## 3. 도메인 모델

**신규 테이블·컬럼은 없다.** 공구 게시물은 `post`(뿌리) + `group_buy_post`(1:1 확장)로 이미 저장되고, 좋아요·신고·노출은 `post_id` 하나로 두 타입에 걸려 있다. 상품·가격은 게시물에 저장하지 않고 계약에서 읽는다(30 설계 1-8).

```
post (post_type = GROUP_BUY, status, content, like_count, published_at)
 └─ 1:1  group_buy_post (title, review_status, hidden_at …)
            └─ 1:1  group_buy (status, start_at, end_at, ended_at, opened_at, close_type, market_id, creator_id)
                       └─ 1:1  contract ── 1:N  contract_item (product_id, product_name, regular_price, group_buy_price, sort_order)
                                                        └─ N:1  product (thumbnail_url, is_out_of_stock_forced) ── 1:N  product_variant (stock)
```

| 응답 필드 | 읽는 곳 | 비고 |
| --- | --- | --- |
| 제목 | `group_buy_post.title` | 승인 후 수정이 즉시 반영된다(인플 제14조⑤) |
| 본문 | `post.content` |  |
| D-day · 마감 | `group_buy.end_at` · `status` | KST 날짜 차이로 서버가 계산 |
| 마감 노출 기한 | `group_buy.ended_at` + 3일 | 조기 마감·중단은 `end_at`보다 이르다 — 실제로 끝난 시각 기준 |
| 상품 목록 · 순서 | `contract_item` (`sort_order ASC`) | 계약 상품 전부 = 게시물 상품 |
| 상품명 | `contract_item.product_name` | 계약 시점 이름 — 상품명이 바뀌어도 게시물은 계약대로 |
| 정가 · 공구가 | `contract_item.regular_price` · `group_buy_price` | C7·결제도 같은 값으로 맞춘다(8절 미결 ①) |
| 할인율 | 서버 계산 | C7과 같은 반올림 유틸을 쓴다 |
| 썸네일 | `product.thumbnail_url` |  |
| 품절 | `is_out_of_stock_forced` ∨ 모든 variant `stock <= 0` | C7 `status.isOutOfStock`과 같은 식 |
| 광고 표시 문구 | `GroupBuyDisclosure.text(brandName)` | 저장하지 않고 렌더링 시 조립(31 설계 2-8) |

**바뀌는 것은 규칙 하나와 스케줄러 한 단계다** — `GroupBuyPostExposure`의 투영식(4-1)과 `GroupBuyLifecycleScheduler`의 「마감 게시물 내리기」(4-2). 코드는 `domain/post`·`domain/groupbuy`·`global/scheduler`에 있고, 모두 기획 제외 대상이 아니다.

## 4. 상태 규칙

### 4-1. 노출 투영식 변경 — `GroupBuyPostExposure.sync`

```
현재  PUBLISHED ⇔ of(post, gb) == EXPOSED
변경  PUBLISHED ⇔ of(post, gb) == EXPOSED
                 ∨ (of(post, gb) == CLOSED
                    ∧ post.publishedAt != null
                    ∧ !gbp.isHidden()
                    ∧ gb.closeType != SUSPENDED
                    ∧ now < gb.endedAt + CLOSED_POST_RETENTION)
      DRAFT     그 밖의 전부

CLOSED_POST_RETENTION = 3일(72시간)
```

- **`publishedAt != null`** — 한 번이라도 노출된 게시물만 남는다. 승인 전에 종료·중단된 공구의 게시물은 소비자가 본 적이 없다.
- **숨김 상태로 종료** — 숨긴 채로 남는다. 종료가 숨김 해제가 되면 안 된다.
- **직권 중단(`close_type = SUSPENDED`)** — 즉시 내린다. 중단 사유가 게시물 자체일 수 있다. 8절 미결 ②.
- **`endedAt` 기준** — 기간 종료면 `end_at`과 같고, 조기 마감·중단 승인이면 실제로 끝난 시각이다(`GroupBuy.applyTerminated`).
- **이점** — 상세·좋아요 목록·신고·노출 적재가 이미 `post.status == PUBLISHED`로 판정하므로 **소비자 코드 대부분이 손 없이 따라온다**. 3일이 지나 `DRAFT`로 내려가면 같은 판정이 자동으로 걸러 낸다. 대신 "진행 중만" 내려야 하는 곳(C1 피드·C4 고정 섹션·로즈 링)은 공구 상태를 명시적으로 본다.
- **기존 데이터** — 이미 종료돼 `DRAFT`가 된 행은 배포 후 1회 `sync` 백필을 돌린다(`GroupBuyBackfillRunner` 패턴). 같은 식이 `now`로 판정하므로 종료 3일 이내인 것만 `PUBLISHED`로 돌아온다.
- **결정 경위(2026-09-26)** — ① 종료 게시물을 기한 없이 남기는 안 → ② 종료 즉시 내리는 안 → ③ **3일 동안 마감으로 보여준 뒤 내리는 안(확정)**.

### 4-2. 마감 게시물 내리기 — 스케줄러 한 단계

`post.status`는 저장된 값이라 시간이 지나도 스스로 바뀌지 않는다. `GroupBuyLifecycleScheduler.tick()`(1분 주기 · KST)에 네 번째 단계를 더한다.

```
run("마감 게시물 내리기", lifecycleService.findIdsToRetirePost(now, MAX_PER_RUN), now, lifecycleService::retirePost)

findIdsToRetirePost: group_buy.status ∈ TERMINAL
                     ∧ group_buy.ended_at <= now − 3일
                     ∧ post.status = PUBLISHED        (group_buy_post 경유)
retirePost:          잠금 → GroupBuyPostExposure.sync(gb, now) → DRAFT
```

- 기존 단계와 같은 전제다 — 행마다 별도 트랜잭션, 조건부 처리라 중복 실행해도 두 번 내려가지 않는다. `sync`가 식을 다시 계산하므로 별도 전이 메서드를 만들지 않는다.
- 스케줄러 지연(최대 1분)은 보정하지 않는다. 72시간 중 1분이라 읽기 쪽에 기한 조건을 따로 두지 않는다.
- 내려간 뒤에도 `post_like` 행과 `like_count`는 지우지 않는다 — 스튜디오 인사이트가 계속 쓴다.

### 4-3. 판매 상태 — 저장하지 않고 파생한다

`PostStatus` 주석대로 D-3·품절·마감은 게시물 상태가 아니라 파생값이다. `GroupBuySaleState.of(groupBuy, products, now)` 하나가 판정한다.

| `saleState` | 조건(위에서부터) | 배지 | 상품 행 | 하트 |
| --- | --- | --- | --- | --- |
| `CLOSED` | `group_buy.status` 종결 ∨ `end_at <= now` | `공구 마감` 회색 | 전부 `CLOSED` | 잠김(해제만) |
| `SOLD_OUT` | 모든 상품 품절 | `품절` 회색 | 전부 `SOLD_OUT` | 가능 |
| `PARTIALLY_SOLD_OUT` | 일부 품절 | `공동구매 D-n` 로즈 | 해당 행만 `SOLD_OUT` | 가능 |
| `ON_SALE` | 그 외 | `공동구매 D-n` 로즈 | `ON_SALE` | 가능 |

- **`end_at <= now`도 마감으로 본다** — 종료 스케줄러는 1분 주기라 `end_at`이 지났는데 아직 `IN_PROGRESS`인 구간이 최대 1분 있다(30 설계 "읽기 쪽 보정"). 구매와 직결되므로 이쪽은 보정한다.
- C3 시안의 배지 문구는 `공구 종료`, C5는 `공구 마감`이다. 서버는 문구가 아니라 `saleState`만 내리고 라벨은 앱이 정한다. 8절 미결 ③.

### 4-4. D-day · 좋아요

- `dDay = 날짜(end_at, KST) − 오늘(KST)`, 정수. 마감 당일은 0이다. 앱 시계를 믿지 않도록 서버가 계산하고, 시분 단위가 필요하면 `endAt`도 함께 내린다. `CLOSED`면 `null`.
- 좋아요 규칙은 바꾸지 않는다. `GroupBuyPostPolicy.canLike`는 `EXPOSED`일 때만 true이고 품절은 영향이 없다. 마감 3일 동안은 잠기고(해제만), 품절은 열려 있어 C3·C5 규칙과 일치한다. `canLike`에는 4-3의 `end_at > now`만 더한다.

### 4-5. "진행 중인 공구" — 정의 하나를 세 곳이 쓴다

```
쇼룸 X에 진행 중 공구가 있다 ⇔ ∃ GROUP_BUY 게시물 p :
    p.creator = X ∧ p.status = PUBLISHED ∧ group_buy.status ∈ SELLING ∧ group_buy.end_at > now
```

C4 고정 섹션, 아바타 로즈 링(`hasOngoingGroupBuy` — C1·C2·C4·C14), C1 피드의 공구 필터가 이 정의를 쓴다. 지금 링은 `ConnectionRepository.findCreatorIdsWithOngoingGroupBuy`가 브랜드 연결 + `product.group_buy_status`로 추정하는데, 같은 브랜드에 연결된 다른 쇼룸의 링까지 켜고 숨김 게시물도 진행 중으로 본다. 링이 켜졌는데 C4에 고정 섹션이 없는 어긋남을 막기 위해 위 정의로 교체한다. 마감 3일 동안의 게시물은 링을 켜지 않는다.

### 4-6. C7 진입 — 마감 후 상품 행 탭

C5 시안은 마감 후에도 상품 행이 C7로 간다고 적었지만, 현재 C7은 `product.group_buy_status = NOT_CONNECTED`이면 막히고 공구가 끝나면 상품이 그 값으로 돌아간다. 상품 항목에 `detailAvailable`을 실어 탭 가능 여부를 서버가 알리고, C7 완화 여부는 8절 미결 ④로 둔다.

## 5. API 명세

신규 엔드포인트는 C4 고정 섹션용 1개이고, 나머지는 기존 경로의 응답에 `groupBuy` 블록을 더한다. `FeedItemResponse.contentType`이 이미 판별자라 앱 계약은 깨지지 않는다. 신규 `ErrorCode`는 없다.

### 5-1. 엔드포인트

| 메서드 · 경로 | 화면 | 변경 | 비로그인 |
| --- | --- | --- | --- |
| `GET /v1/user/showrooms/{showroomId}/group-buy-posts` | C4 고정 섹션 | **신규** — 진행 중 공구만, 페이징 없음, `opened_at DESC` | 허용(화이트리스트 추가) |

## 6. 피드 조회 로직

모든 소비자 목록은 `post.status = PUBLISHED`에 **공구 범위 조건 하나**를 더해 만든다. `findPublished()`의 `post_type = GENERAL` 고정 필터를 걷고, 그 자리에 `GroupBuyScope` 인자를 받는다.

| 목록 | 조건 (`PUBLISHED` ∧ …) | 정렬 |
| --- | --- | --- |
| C1 팔로잉 · 추천 · 전체 | `GENERAL` ∨ 진행 중 공구 | `published_at DESC, post_id DESC` (기존) |
| C4 고정 섹션 | creator = X ∧ 진행 중 공구 | `opened_at DESC, post_id DESC` |
| C4 아래 피드 | creator = X ∧ (`GENERAL` ∨ 마감 게시물) | `published_at DESC, post_id DESC` |
| C4 `postCount` | creator = X (타입 무관) | — 고정 섹션 + 아래 피드의 합과 같다 |
| C3 좋아요 | 내가 좋아요 (타입·진행 무관) | `LikedPostSort` |

- **진행 중 공구** = `post_type = GROUP_BUY ∧ group_buy.status ∈ SELLING ∧ group_buy.end_at > now`, **마감 게시물** = 그 밖의 `GROUP_BUY`. `PUBLISHED`가 숨김·미승인·종료 3일 경과를 이미 걸렀으므로(4-1) 공구 상태만 보면 된다.
- **조인** — `post LEFT JOIN group_buy_post gbp ON gbp.post_id = post.post_id LEFT JOIN group_buy gb`. 일반 게시물은 확장 행이 없으므로 반드시 LEFT다. 카운트 쿼리도 같은 조건을 쓴다.
- **C1에서 마감 게시물을 빼는 이유** — C1 시안에 마감 카드가 없고("공구 종료 카드도 그려줘"는 다음 제안으로만 남음), 추천 피드에 살 수 없는 공구가 뜨면 발견이 아니다. 시안이 나오면 `GroupBuyScope`만 바꾼다.
- **C4에서 진행 중을 빼는 이유** — 고정 섹션과 아래 피드에 같은 게시물이 두 번 뜨지 않게 한다.

### 6-1. C3 `GROUP_BUY_FIRST` 재정의

지금은 `post_type = GROUP_BUY`이면 모두 앞으로 보낸다. 시안 설명은 "진행 중 공구를 위로 모아서"이므로 랭크를 `진행 중 공구 → 0, 그 외 1`로 바꾼다. 마감 게시물은 일반 게시물과 같은 줄에서 좋아요한 시각으로 섞인다. `LikedPostSort` 주석("지금은 DEFAULT와 같다")도 함께 고친다.

### 6-2. 카드 조립 — 페이지당 추가 쿼리 3개

`UserPostService.toFeed()`가 이미 사진·좋아요·팔로우를 페이지 단위로 모아 읽는다. 같은 방식으로 `GroupBuyPostCardLoader`(domain/groupbuy)를 두고 페이지의 공구 게시물 id로 한 번에 읽는다.

1. `group_buy_post` + `group_buy` + `market`(브랜드명) fetch join
2. `contract_item` + `product` — `contract_id IN (…)`, `sort_order ASC`
3. 품절 집계 — `product_id`별 `stock > 0`인 variant 수. `is_out_of_stock_forced`와 합쳐 품절을 판정한다

페이지 크기와 무관하게 3회다. 상세(C5)는 게시물 1건으로 같은 로더를 쓴다.

### 6-3. `likeLocked`의 N+1 제거

`toFeed()`는 게시물마다 `postPolicies.of(post).canLike(post)`를 부르고, `GroupBuyPostPolicy.canLike`는 매번 `findById`를 한다. 공구가 피드에 들어오면 카드 수만큼 쿼리가 늘어난다. 목록에서는 로더가 이미 읽은 값으로 `likeLocked = (saleState == CLOSED)`를 쓴다. `PUBLISHED`인 공구 게시물은 4-1에 따라 `EXPOSED` 아니면 마감 3일 이내뿐이라 `canLike`와 답이 같다. 쓰기(좋아요 `POST`)는 계속 정책이 판정한다.

### 8-1. 작업 순서 (PR 분할)

**응답이 투영보다 먼저다.** 좋아요 목록은 지금도 타입 필터가 없어 노출 중인 공구 게시물이 제목 없는 일반 카드 모양으로 이미 나간다. 투영을 먼저 바꾸면 마감 게시물까지 그 모양으로 새므로, S1이 S2보다 앞선다.

1. **S1 카드 응답** — `GroupBuySaleState` · `GroupBuyPostCardLoader` · `PostDto.groupBuy` · `toFeed()`/`getPostById()` · `likeLocked`(6-3). 테스트: 판매 상태 4종 · D-day 경계(KST 자정) · `end_at` 경과 직후 `CLOSED` · 페이지당 쿼리 수
2. **S2 노출 투영 · 마감 게시물 내리기** — `GroupBuyPostExposure` · 스케줄러 단계 · 백필. 테스트: 종료·조기 마감 직후 유지 / 72시간 경과 후 `DRAFT` / 숨김 종료·미승인 종료·직권 중단 즉시 비노출 / 마감 중 좋아요 `POST` 거절·`DELETE` 허용 / 스케줄러 중복 실행 시 한 번만 전이 / 백필이 3일 이내만 되살림
3. **S3 C5 상세** — 마감 3일까지 200 · 이후 404, 상품 전체
4. **S4 C4 쇼룸** — 고정 섹션 API · 아래 피드 범위 · `postCount` · 로즈 링 정의 교체(호출처 5곳) · 화이트리스트. 테스트: 링 ⇔ 고정 섹션 일치, 같은 브랜드에 연결된 다른 쇼룸의 링이 켜지지 않음, 마감 게시물은 아래 피드에만
5. **S5 C1 피드** — `GroupBuyScope`로 `GENERAL` 필터 해제. 테스트: 진행 중만 포함, 추천에서 팔로우·본인 쇼룸 제외 유지
6. **S6 C3 정렬** — `GROUP_BUY_FIRST` 진행 중 기준
7. **S7 문서** — Swagger docs 인터페이스 · 31 설계서 0-3·0-6 갱신
