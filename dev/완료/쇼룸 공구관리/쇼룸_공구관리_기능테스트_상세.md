# 쇼룸 스튜디오 공구 관리 기능 테스트 상세

- 대상: `ui-studio-09-groupbuys.html` rev.3의 A1·A2, B1~B13 및 C1~C7 **23개 화면 상태**, `/v1/creator/group-buys` API와 관련 상태 전이
- 기준: `dev/공구관리 공통 기능명세서.txt` §29, `dev/쇼룸 공구관리/공구관리 쇼룸 기능명세서.txt` §31, `dev/쇼룸 공구관리/31_쇼룸스튜디오_공구관리_BE_설계서.md`, 실제 API 계약
- 목적: 화면 표시, 권한, 상태 전이, 데이터 격리, 외부 모듈 연계를 같은 테스트 데이터로 확인한다.
- 판정 기록: 각 TC에 `PASS / FAIL / BLOCKED / NOT RUN`, 실행 환경·빌드·일시·증빙(응답 또는 화면 캡처)·결함 번호를 남긴다. `BLOCKED`는 기대 기능의 의존 모듈이 없어 실행할 수 없을 때만 사용한다.

## 1. 테스트 기준과 실행 순서

시안의 화면 문구는 그대로 복제하지 않는다. 시안과 확정 규칙이 충돌하는 항목은 §8에 적은 기대값으로 검증하고, 시안 수정 여부를 별도 결함으로 기록한다. 문서 안의 작업 지시·미결 표시도 테스트 요청으로 해석하지 않는다.

1. **P0**: 다른 사람 공구 접근, 게시물 심사 잠금, 공구 노출·종결, 연장 마감·동시 처리, 미이행의 원자성.
2. **P1**: 23개 화면 상태, 6개 탭과 조치 카운트, 게시물 쓰기, 중단 요청, 이행 확인, 금액·이력 정보.
3. **P2**: 문구·배지·반응형 모달·빈 상태·경계 길이.

테스트는 `API 단독 → 브랜드·어드민 연계 → 스튜디오 화면 → 소비자·판매·정산 연계` 순서로 진행한다. 단순한 HTTP 200만으로 통과시키지 않고 **응답 필드, 저장 상태, 상대 화면, 반복 호출 후 상태**를 함께 확인한다.

P0 ID는 `Q-11~12`, `P-04~06`, `P-08~09`, `P-11~14`, `P-16`, `L-02`, `L-05~06`, `S-01`, `S-05~06`, `F-01~04`, `X-02~04`, `X-09`로 고정한다. 나머지 상태·금액·권한 TC는 P1, 순수 표현·접근성 TC는 P2다. P0 중 외부 모듈 때문에 `BLOCKED`인 항목은 출시 판정에서 미통과로 남긴다.

## 3. 조회·목록·권한 API 테스트

기본 경로는 `/v1/creator/group-buys`이며 정상 응답은 `200`이다. 상세 요청에 `tab`·`keyword`·`sort`를 넘긴 경우에만 목록 문맥의 이전·다음 ID를 비교한다.

| 메서드 | 경로 (`/v1/creator/group-buys` 뒤) | 입력 예 |
| --- | --- | --- |
| GET | `/` | `?tab=IN_PROGRESS&sort=ACTION_REQUIRED_FIRST&page=1&size=20` |
| GET | `/summary` | 바디 없음 |
| GET | `/{id}` | `?tab=IN_PROGRESS&keyword=세럼&sort=START_AT_ASC` |
| PUT | `/{id}/post/draft` | `{"title":"세럼 공구","content":"본문"}` |
| POST | `/{id}/post/submission` | `{"title":"세럼 공구","content":"본문"}` |
| PATCH | `/{id}/post` | `{"title":"수정 제목","content":"수정 본문"}` |
| POST | `/{id}/extension/acceptance` | 바디 없음 |
| POST | `/{id}/extension/rejection` | `{"reasonCode":"NEXT_SCHEDULE_BOOKED","memo":"다음 일정이 있습니다"}` |
| POST | `/{id}/suspension-request` | `{"reasonCode":"DELIVERY_FAILURE","memo":"배송 지연 주문 18건"}` |
| POST | `/{id}/fulfillment-check` | `{"result":"UNFULFILLED","reason":"배송 미완료"}` |

모든 쓰기 응답은 갱신된 **상세 응답**이다. 요청 실패 시 공구·게시물·요청·이력에 부분 쓰기가 남지 않는지 확인한다.

| TC | 요청·조건 | API 및 화면 기대값 |
| --- | --- | --- |
| Q-01 | A로 전체 목록 조회 | A 소유 공구만 반환. `content`의 행 수, `pageInfo` 총수, 계약 제목·브랜드·상품 개수·기간 정확. `remark` 필드 없음. |
| Q-02 | D0 전체 목록·요약 | `content=[]`, `tabCounts.ALL=0`, `actionRequiredCount=0`. |
| Q-03 | 탭 6종 각각 조회 | `PREPARING`만 준비중, `READY`만 준비완료, `IN_PROGRESS`에 `SUSPENSION_SCHEDULED` 포함, `ENDED`에 `SETTLED` 포함, `SUSPENDED` 별도. 각 카운트 합계=`ALL`. |

## 7. 자동화 확인과 실행 증빙

실행 가능한 백엔드 경로는 다음 통합 테스트로 자동화한다. UI-01~23의 **실제 브라우저 표현·조작**은 정적 HTML만 있는 현재 저장소에서 자동 실행할 수 없고, 같은 상태를 만드는 API 응답과 전이는 아래 테스트가 확인한다. 각 TC를 실행하면서 테스트 메서드 또는 화면 캡처를 연결한다.

| 자동화 클래스 | 검증 범위 |
| --- | --- |
| `CreatorGroupBuyQueryIntegrationTest` | Q-01~06·08~10·13~14, B1·B10·B13·B7의 상세 응답·이력 격리 |
| `CreatorGroupBuyCommandIntegrationTest` | P-01~07·10~12, L-02~05·07, S-01~04, F-01~03·05 |
| `GroupBuyPostGuardIntegrationTest` | P-09·13~14, 소비자 비노출/일반 피드 격리 |
| `CreatorGroupBuyScenarioIntegrationTest` | 실제 3자 API 연결 수명주기, 6개 탭, B1~B9의 주요 분기, 소유·역할 경계, 페이지, 기한 경과, 동시 최초 제출 |
| `CreatorGroupBuyPortIntegrationTest` | 포트가 값을 제공할 때 B5·B5a·B7·B8·B9 금액과 주문 수, C6→B12, 정산 게이트 |

포트 계약 테스트의 Mockito 대역은 **포트가 값을 준 이후 스튜디오 API가 어떻게 응답하는지**만 검증한다. 실제 판매·정산·3자 스레드 서비스와의 종단간 연결 완료 증거로 취급하지 않는다.

```powershell
.\gradlew.bat test --tests 'showroomz.api.creator.groupbuy.*' --tests 'showroomz.domain.groupbuy.service.GroupBuyDisclosureTest'
```

최소 증빙은 **요청/응답 JSON, DB의 공구·게시물·요청·리비전·이력 상태, FE 캡처, 반대편 화면 또는 포트 결과**다. 동시성 TC는 두 요청의 시작·종료 시각과 최종 DB 상태를 남긴다. 금액 TC는 포트 입력 샘플과 손계산 기대값을 함께 보관한다.

## 8. 시안과 구현 규칙의 충돌 — 테스트 기대값

| 주제 | 시안 또는 명세의 충돌 | 테스트 기대값·판정 |
| --- | --- | --- |
| 목록 탭 | A1은 5개 탭에 중단을 종료·정산에 포함 | 공통 §29·현재 API대로 **6개**, 중단은 독립 탭. UI-01에서 5개면 FAIL. |
| 조치 건수 | A1 헤더 3, GNB 2 | 서버 `actionRequiredCount` 하나를 두 곳에 사용. Q-08에서 다르면 FAIL. |
| 등록 마감 예시 | B1의 2026.08.20은 SLA 영업일 3일 역산과 불일치 | 서버 `readiness.registrationDeadline`을 표시. 시작 2026.08.24·주말만 제외할 때 **2026.08.18**. |
| 연장 재요청 | C2는 거절 후 다시 요청 가능하다고 안내 | 공구당 1회. UI-13에서 해당 고지 있으면 FAIL. |
| 무응답 이행 | B7·C5는 기한 지나면 자동 이행이라고 안내 | 설정 `autoConfirmOnTimeout=false`면 자동 간주·해당 고지 모두 금지. |
| 지급 사실 | C5·C6은 지급비 `입금 완료`라고 표시 | 실제 입금 사실은 서버가 모름. 확인 모달에 지급 완료 단정 문구 금지. |
| 중단 명칭 | B10 일부 문구는 승인 후 `취소` | 상태는 `SUSPENDED` **중단**. |
| 미이행 종결 | B12는 운영자에게 종결 권한이 있다고 표시 | 양측 동의로 종결. 운영자는 중재 의견 제시자. |
| 콘텐츠 의무 | §31-7의 `계약이 성립하지 않아 효력 없음` | 공구는 체결된 계약에서 생성됨. 종결 시 `payout`만 숨기고 계약 무효 문구는 쓰지 않음. |
| 구매확정 표현 | B7은 구매확정이 정산 트리거라고 안내 | 종결 건수와 양측 이행 확인을 기준으로 실제 정산 흐름을 표시; 판매 포트가 없으면 숫자를 만들지 않음. |
