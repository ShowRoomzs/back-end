## 0. 먼저 정한 12가지

### 0-1. 환불 건 = `order_refund_task` 행 1개 — 새 테이블은 없다

34 설계서 1-9가 만든 환불 큐가 그대로 환불 건의 단위다. 집행 대기 · 실패 · 완료 세 탭이 전부 이 테이블의 상태(`status`)와 출처(`origin`)로 갈린다. 환불번호 `RFD-0918`은 **저장하지 않고 `RFD-{refund_task_id}`로 포맷**한다(어드민 회원번호 `CST-{userId}`와 같은 규칙 · 포맷터 한 클래스).

### 0-2. 돈이 나가는 길은 하나 — `RefundExecutor.execute`

PG 자동(커밋 직후) · 재시도 배치 · 운영자 [집행] · 운영자 [재시도]가 **같은 메서드**를 탄다. 1009 수정계획 8-2 초안의 `POST …/retry`는 만들지 않고 **`POST …/execute` 하나로 통합한 현 구현을 확정**한다 — 집행과 재시도는 「PENDING에서 시작하느냐 FAILED에서 시작하느냐」만 다르다(`OrderRefundTask.isExecutable()`).

### 0-3. 집행 대기 탭에는 **운영자 사유만** 온다

PG 자동 환불의 PENDING은 커밋 직후 집행되고, 놓친 것도 2분 뒤 배치가 집는다(Q3). 그래서 집행 대기 탭은 `origin = OPERATOR`만 보여 준다(현 구현 그대로). 단, **결제가 없는 주문**(`payment_id IS NULL` — 시드 · 결제 밖 주문)의 PG 자동 PENDING은 영원히 머문다 — 운영에서는 생기지 않지만 보이지도 않는 행이라 **7-2 #3에 확인 요청**으로 올린다.

### 0-4. 완료 탭은 「모든 환불」이어야 하므로 **큐를 거치지 않는 두 경로를 기록 전용 큐 행으로 편입**한다

§39-2 「PG 자동까지 전부 조회 — CS 1순위 「환불 언제 들어와요?」」. 지금 큐를 거치지 않는 PG 환불이 둘 있다.

| 경로 | 지금 | 완료 탭 |
| --- | --- | --- |
| **결제완료 소비자 취소**(준비 시작 전 · 주문 전액) — `UserCancelService` → `PaymentTransitions`(결제 전액 취소 · `payment_cancel` SUCCEEDED) | 큐 없음 | 안 보인다 |
| **교환 재발송비 결제 취소**(교환 철회 · 선결제 충당 등) — `ClaimPaymentService.executeCancel`(`order_claim_payment` CANCELLED) | 큐 없음 | 안 보인다 — 시안 RFD-0914가 이 경우다 |

**결정** — 두 경로의 취소가 확인되는 시점에 `order_refund_task`를 **DONE 상태로 바로 적재**한다(기록 전용 · `source` 2종 추가 · 1-3). 완료 탭 · 검색 · 환불번호가 **한 테이블 · 한 번호 체계**로 유지되고, 집행기는 PENDING이 아닌 행을 건드리지 않으므로(`claim()`이 `isExecutable()` 아닌 행에 null) 돈이 두 번 나갈 길이 없다. 대안(세 테이블 UNION 읽기 모델)은 환불번호가 셋으로 갈라지고 페이징 · 검색이 어려워 버린다. **P3**로 분리한다(6절) — P1 · P2만으로 큐 경로 환불은 전부 보인다.

### 0-5. 검색 · 경로 · 정렬 · 합계는 **쿼리 한 곳**에서 — `OrderRefundTaskRepositoryCustom`

현 `findForAdmin`(JPQL · 상태 · 출처 · 기간)은 §39-2의 검색(환불번호 · 주문번호 · PG 거래번호) · 경로 셀렉트 · 정렬 2종 · 합계 금액을 못 낸다. `OrderClaimRepositoryImpl`과 같은 QueryDSL `Custom/Impl`로 옮긴다. PG 거래번호는 `payment.pg_tx_id`(포트원 거래 id)와 `payment.payment_id`(포트원 paymentId = `{주문번호}-{시도}`) **둘 다** 받는다 — CS가 어느 쪽을 들고 올지 모른다.

### 0-6. 「소비자 대기 N일」의 기산 시각은 **큐 적재 시각**(`created_at`)이다

§39-6 B-9가 미결로 둔 값. 소비자는 환불이 「생긴」 순간부터 기다리므로 실패 시각이 아니라 적재 시각이 맞다. 실패 탭 요약의 N = 실패 건 중 `now − created_at`의 **최댓값**(일 단위 내림). 확정되면 상수 한 줄이다.

### 0-7. 다이얼로그는 **상세 API**를 본다 — 목록 행에 전부 싣지 않는다

M1(재확인)과 M2(재시도)가 요구하는 근거 · PG 거래번호 · 취소 대상 결제 · 추가 결제 · 정산 · 실패 코드 · 자동 재시도 결과는 목록 10열에 없는 값이다. `GET /v1/admin/refunds/{refundTaskId}`를 새로 두고 목록은 10열 + 액션 가능 여부만 내린다. §39-6 B-10 「행 클릭 동작 — 환불 건 상세가 없다」는 기획 미결이지만 **데이터는 이 상세로 준비해 둔다**(화면이 생기면 그대로 쓴다).

### 0-8. 정산 블록은 **자리만** 둔다

정산 모듈이 코드에 없다(`domain`에 settlement 없음). 상세의 `settlement`는 `{ state: "BEFORE_SETTLEMENT", clawback: null }` 고정이다. 정산 확정 건 클로백(§39-6 A-4 `[자문대기-법률 J]`)은 정산 설계에서 이 필드를 채운다 — 응답 모양을 지금 정해 두어 FE가 M1의 「정산」 행을 미리 그릴 수 있게 한다.

### 0-9. 권한은 ADMIN 단일 · **편입자 = 집행자 허용**(잠정)

`SecurityConfig`의 `/v1/admin/**` → `ADMIN`. 집행 권한 등급(§39-6 B-7 ⓒ)과 편입자=집행자 허용 여부는 미결이라 **막지 않는다**. 이력에 편입자(`requested_by`)와 집행자(`executed_by`)가 따로 남으므로 나중에 규칙이 생겨도 감사가 된다. 막게 되면 `AdminRefundService.execute` 앞 한 줄이다.

### 0-10. 중복 방지는 **큐 행 잠금 + EXECUTING**이지 멱등키가 아니다

연타 · 동시 클릭(§39-3 「PG 취소 요청은 1회」):

| 순서 | 첫 클릭 | 둘째 클릭 |
| --- | --- | --- |
| 서비스 사전 검사 | `isExecutable()` 통과 | 첫 클릭이 EXECUTING으로 올린 뒤면 **409 `REFUND_TASK_NOT_EXECUTABLE`** |
| 같은 순간 | `claim()`이 `findForUpdate`(비관적 잠금)로 행을 잠그고 EXECUTING | 잠금 해제 후 읽으면 EXECUTING → `claim()` null → **200 `outcome=SKIPPED`** |

둘 중 어느 쪽이든 PG 호출은 한 번이다. 포트원에는 **지금 취소 가능 잔액**을 함께 보내(`cancelPartial`의 `currentCancellableAmount`) PG 쪽에서도 끼어들기를 막는다.

### 0-11. 자동 재시도 「1회」= Q3의 「자동 시도 상한 2회」다

시안 ⓐ(자동 재시도 1회)와 1009 수정계획 Q3(자동 시도 상한 2회 · 최초 집행 포함)은 **같은 값**이다 — 최초 1 + 재시도 1. `order.refund-auto-max-attempts: 2`. M2의 「자동 재시도 1회 · 실패」 행은 `attempt`와 이력에서 만든다. **운영자 사유 환불은 자동 재시도하지 않는다**(배치가 `origin = PG_AUTO`만 집는다).

### 0-12. 실패 문구는 **운영자 말**로, 코드는 **상세에만**

`last_error`는 이미 운영자 문장이다(「PG 거절 · …」 「환불액이 취소 가능 잔액보다 큽니다」). 포트원 응답 코드를 따로 두기 위해 `last_error_code`를 더하고(1-3) 목록에는 내리지 않는다 — M2에서만 보여 준다.

### 1-2. 상태 · 탭 매핑 — 탭은 서버가 소유한다

```
PENDING ──▶ EXECUTING ──▶ DONE
   ▲            │
   └── FAILED ◀─┘      PENDING · FAILED ──▶ VOID
```

| 탭 | 조건 | 비고 |
| --- | --- | --- |
| `PENDING` 집행 대기 | `status IN (PENDING, EXECUTING) AND origin = OPERATOR` | EXECUTING은 「환불 처리 중」 라벨 · 버튼 비활성(`executable=false`) |
| `FAILED` 실패 | `status = FAILED` | 출처 불문 — 운영자 사유 집행이 PG에 거절돼도 여기 |
| `DONE` 완료 | `status = DONE AND executed_at >= from` | **기간 기준은 `executed_at`**(현 구현의 `created_at`을 고친다 — 시안의 일시 열은 PG 승인 시각) |
| — | `VOID` | 어느 탭에도 없다(상세 · 주문 상세의 환불 목록에서만) |

기록 전용 행의 적재 — `OrderRefundTask.recorded(group, order, source, sourceId, amount, paymentId, paymentKind, paymentCancelId, now)`: `status = DONE · origin = PG_AUTO · executed_at = now · attempt = 1`. `RefundTaskEnqueuedEvent`를 **발행하지 않는다**(집행할 것이 없다).

```sql
-- V176__alter_order_refund_task_for_admin_refunds.sql
ALTER TABLE order_refund_task
    ADD COLUMN payment_kind    VARCHAR(12) NOT NULL DEFAULT 'ORIGINAL' COMMENT 'ORIGINAL, ADDITIONAL — 어드민 06c 결제 열' AFTER payment_id,
    ADD COLUMN partial         BIT(1)      NOT NULL DEFAULT 0 COMMENT '원래 결제의 부분 취소' AFTER payment_kind,
    ADD COLUMN last_error_code VARCHAR(50) NULL COMMENT 'PG 응답 코드 — 재시도 다이얼로그' AFTER last_error,
    MODIFY COLUMN source VARCHAR(30) NOT NULL COMMENT 'CANCEL_REQUEST_APPROVED, SELLER_DIRECT_CANCEL, RETURN_COMPLETED, CLAIM_RETURN_PASSED, OPERATOR_REASON, USER_CANCEL_BEFORE_PREPARE, CLAIM_PAYMENT_CANCELLED',
    ADD KEY idx_order_refund_task_executed (status, executed_at);

-- 기존 행 백필: 부분 여부
UPDATE order_refund_task t JOIN payment p ON p.payment_id = t.payment_id
SET t.partial = (t.refund_amount < p.amount) WHERE t.payment_id IS NOT NULL;
```

현재 최신은 V176이다(반려 이의 연결 · 2026-10-09 — 38 설계서 0-6). **이 마이그레이션은 V177 이후로 잡는다** — 착수 시점에 번호를 다시 확인한다. `ddl-auto: validate`라 마이그레이션 → 엔티티 순서.

## 2. 집행 경로 — 이미 구현된 것 (1009 수정계획 2-4)

새로 만들지 않는다. 06c가 기대는 보장을 적어 둔다.

```
[집행 대기 · 실패] ── POST /execute ──▶ AdminRefundService.execute
                                          ├ findById → 404 REFUND_TASK_NOT_FOUND
                                          ├ !isExecutable() || payment_id == null → 409 REFUND_TASK_NOT_EXECUTABLE
                                          └ RefundExecutor.execute(taskId, adminId)        ← 트랜잭션 밖
                                               ① RefundTransitions.claim   (REQUIRES_NEW · 큐 행 잠금 · 결제 행 잠금 · EXECUTING · attempt++)
                                               ② gateway.cancelPartial(paymentId, amount, cancellableAmount, reason)
                                               ③ 결과
                                                  SUCCEEDED         → complete: DONE · payment_cancel(SUCCEEDED · refund_task_id) ·
                                                                      payment.cancelled_amount += · 전액이면 CANCELLED · 이력 REFUND_EXECUTED ·
                                                                      CLAIM_RETURN_PASSED면 클레임 일괄 종결(applyRefundExecuted)
                                                  ALREADY_CANCELLED → fail(「이미 전액 취소된 결제」)
                                                  Rejected 예외     → fail(「PG 거절 · …」) · 이력 REFUND_FAILED
                                                  결과 모름         → EXECUTING 유지 → RefundRetryScheduler.resolveStale(30분 뒤 포트원 누적 취소액으로 결론)
```

| 보장 | 어디서 |
| --- | --- |
| 한 결제에 부분 취소는 **하나씩** | `claim()` — 결제 행 `findForUpdate` + `existsByPaymentIdAndStatus(EXECUTING)` |
| 결제 상태가 `PAID`가 아니면 | `CANCEL_REQUESTED`(전액 취소 수렴 중)는 **기다린다**(null · SKIPPED) · 그 밖은 FAILED(문장) |
| 환불액 > 취소 가능 잔액 | FAILED(문장) — 편입 시점에도 `checkRefundable`이 막지만 사이에 다른 환불이 나갔을 수 있다 |
| 결과 미확인 재시도가 이중 환불이 되지 않는다 | `cancelPartial`에 **지금 잔액**을 보낸다 — PG 값과 다르면 거절 |
| 운영자 집행의 흔적 | `executed_by = adminId` · `payment_cancel.requested_by = ADMIN` · 이력 actor `ADMIN` |

**이 설계가 집행기에 더하는 것은 하나** — `RefundTransitions.fail(taskId, error, errorCode)`에 코드 인자를 더하고 `RefundExecutor`가 `PaymentGatewayRejectedException`의 코드(있으면)를 넘긴다. 다른 호출자(배치 · 시드 보류)는 null.

- ✅ 2026-10-09 — 요약도 `days`(기본 30 · 1 미만은 1)를 받는다. 목록과 같은 값을 보내야 완료 탭 숫자 = 목록 건수다(`AdminRefundService.doneDays` 공용).

| `outcome` | 뜻 | FE |
| --- | --- | --- |
| `DONE` | PG 취소 확인 · 큐 DONE | 토스트 「27,200원 환불 완료」 · 완료 탭으로 |
| `FAILED` | PG 명시적 거절 | 실패 탭으로 · `refund.lastError` 노출 |
| `UNKNOWN` | 결과 확인 중(EXECUTING 유지 · 30분 내 배치가 결론) | 「PG 응답 확인 중 — 잠시 후 새로고침」 · 버튼 비활성 |
| `SKIPPED` | 같은 결제의 다른 환불이 처리 중 · 결제가 전액 취소 수렴 중 · 동시 클릭의 뒤쪽 | 「잠시 후 다시 시도」 |

| --- | --- | --- |
| 404 | `REFUND_TASK_NOT_FOUND` | 없는 id |
| 409 | `REFUND_TASK_NOT_EXECUTABLE` | `DONE` · `VOID` · `EXECUTING`(이미 처리 중) · `payment_id IS NULL`(결제 없는 주문 — PG로 돌려줄 길이 없다) |
| 401 | `UNAUTHORIZED_ACCESS` | principal 없음 |

집행 뒤 응답의 `refund`는 **새 읽기 트랜잭션**에서 다시 읽는다(현 구현 — 이 메서드는 트랜잭션 밖이고 집행기가 `REQUIRES_NEW`를 여럿 쓴다).

## 4. 편입 경로 — 이미 구현된 것 (06a B5 · 06b B2)

06c는 **받기만** 한다. 어디서 무엇이 들어오는지만 적는다.

| 경로 | API | 도메인 | 편입 시 함께 일어나는 것 |
| --- | --- | --- | --- |
| 06a B5 위해성 리콜 · 구매확정 후 하자(발송분) | `POST /v1/admin/orders/groups/{id}/refund-tasks` `{ reason, amount, detail }` | `AdminOrderCommandService.enqueueRefund` → `OrderFulfillmentService.enqueueOperatorRefund` | 발송 전 하위주문이면 거절(「직권 취소로 환불합니다」) · `checkRefundable`(취소 가능 잔액 − 아직 안 나간 환불) · 이력 `REFUND_ENQUEUED_BY_OPERATOR` |
| 06b B2 반려 이의 인용 | `POST /v1/admin/claims/{claimId}/dispute-acceptance` `{ amount, detail }` | `OrderClaimService.acceptRejectionDispute` | 미결제 반려 재발송비 요청 `VOID`(같은 요청의 다른 반려 보류가 없을 때) · 클레임 `closeRejectedByDispute` · 반품 수량 반영 · 이력 `DISPUTE_ACCEPTED` |

편입 응답(`DisputeAcceptResponse.refundTaskId` · 주문 상세 `refunds[]`)에 `refundNo`를 더해 운영자가 06c로 넘어올 때 검색어로 쓰게 한다(1-4).

**편입 철회**(§39-6 A-1) — ✅ 2026-10-09 `POST /{id}/void` 구현(42 계획 단계 8). 철회 불가 사유는 반려 이의 인용 · **검수 무응답**(둘 다 편입 때 클레임을 환불로 종결 — `OperatorRefundReason.isClaimBound()` · 2026-10-09 확정). `PENDING(OPERATOR) → VOID` + 이력 `REFUND_VOIDED`. 반려 이의 인용은 편입 시 재발송비 요청까지 소멸시켰으므로 철회가 그 요청을 되살리지 못한다는 점을 기획에 돌려준다(7-1).

### 7-1. 기획 미결(§39-6)과 이 설계의 잠정 처리

| A-5 | 운영자 사유 환불의 정산 반영 | 정산 모듈에서 — 큐 행의 `origin = OPERATOR` · `reason_code`로 가를 수 있다 |
| B-6 | ⓐ 자동 재시도 횟수 · 반복 실패 수동 경로 | 자동 상한 2(최초 포함 · 0-11) · 반복 실패는 실패 탭에 **계속 남는다**(상한 없음) — PG 콘솔 수동 처리 후 기록하는 API는 없다(7-2 #4) |

### 7-2. 이 설계에서 새로 나온 확인 사항

| # | 항목 | 내용 |
| --- | --- | --- |
| 1 | **1009 수정계획 8-2의 `/retry`** | 만들지 않는다 — `execute` 공용(0-2). 수정계획 문서는 이 설계서가 대체한다 |
| 2 | **결제된 반려 재발송비 뒤의 이의 인용** | `acceptRejectionDispute`는 **미결제 요청만** `VOID`한다. 소비자가 재발송비를 이미 결제한 뒤 이의가 인용되면 그 결제(`order_claim_payment` PAID)는 살아 있다 — 06b 설계에서 「인용 시 결제된 재발송비도 취소 선점」을 넣어야 한다. 06c는 상세에 「별도 취소 필요」로 드러내기만 한다(3-3). ✅ **2026-10-09 확정 — 인용 트랜잭션에서 자동 취소 · 차감분은 환원**(BE 38 7절 #4 · 41 보고 1번). 06c에는 수동 취소 동선을 만들지 않는다 |
| 3 | **결제 없는 주문의 PG 자동 PENDING** | 어느 탭에도 안 보인다(0-3). 운영 데이터에는 없어야 하지만, 생기면 발견할 길이 06a 주문 상세 `refunds[]`뿐이다. 06d 예외 관리에 「결제 없는 환불 대기」 집계를 둘지 확인 |
| 4 | **PG 콘솔 수동 처리의 기록** | `OrderRefundTask.markExecuted`(PG 없이 완료 기록)는 있으나 부르는 어드민 API가 없다(`completeRefund`는 반품 통과 전용). 반복 실패를 PG 콘솔에서 사람이 돌려줬을 때 06c에서 「수동 완료 기록」이 필요하다 — B-6 `[근거 대기 · PG 계약]`과 함께 결정 |

### 7-3. 리스크

1. **완료 탭 기간 기준 변경** — `created_at` → `executed_at`으로 바꾸면 집행 전 적재된 옛 건이 완료 탭에 새로 나타난다. 숫자가 늘어난 것이지 데이터가 바뀐 것이 아니다 — 배포 공지에 적는다.
2. **P3 기록행의 금액 분할** — 소비자 전액 취소를 하위주문별로 나누면 각 행의 합이 결제액과 같아야 한다(항목합 + 하위주문 배송비). 할인이 주문 단위면 어긋날 수 있다 — `Order.Totals.discountTotal`이 0이 아닌 주문이 생기는 시점에 분배 규칙이 필요하다. 지금 할인은 쿠폰(기획 제외)뿐이라 0이다.
3. **`partial` 백필의 뜻** — V176 백필은 「적재 시점 결제액 대비」가 아니라 「지금 결제액 대비」다. 결제액은 바뀌지 않으므로 같다.
4. **요약 폴링 · 합계 쿼리** — SUM이 추가돼도 GROUP BY 한 번이다. 완료 탭 기간 조건이 들어가므로 `(status, executed_at)` 인덱스를 V176에 함께 둔다.
5. **`ddl-auto: validate`** — H2 통합 테스트는 엔티티로 스키마를 만든다. `BIT(1)` · `VARCHAR` 타입을 기존 마이그레이션 관례대로 맞춘다(36 설계서 12절의 교훈).
