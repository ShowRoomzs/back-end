[역할 · 방향성 · 서명 순서 확정] 파트너센터는 발신 측이다 — 브랜드가 계약을 작성해 올리고 인플루언서(쇼룸 스튜디오)가 받는다. 다만 서명은 양측이 각각 하며 순서가 없다(rev.5 · 전자서명 솔루션 제약):
브랜드 작성 → [검토 요청] → 어드민 검토 → 양측 동시 서명 요청 → 브랜드·인플루언서 각각 서명 → 어드민 체결 완료 → 공구 생성 (└ 검토 반려 / 거절 / 만료 / 취소)
브랜드도 서명해야 한다 — 그래서 브랜드 화면에 「내 서명 차례」가 존재하지만 서명 버튼은 없다(rev.7) — 서명은 메일·문자로 받은 전자서명 링크에서만 하고 그 링크를 우리가 갖지 못한다. 서명 진행중은 양측 서명 대기 한 형태이고 양측이 끝나도 어드민 체결 처리가 남는다.
[그래서 검토 요청 모달이 필수다] 이 버튼은 서명도 결제도 하지 않지만 누르면 편집이 잠기고 어드민 검토로 넘어간다(경고 항목이 어드민에게 그대로 전달된다). 그래서 확인 모달(C3)을 반드시 경유한다. 되돌릴 방법은 검토 중 [요청 취소]와 서명 완료 전 취소다.
[rev.5 · 상태 9종 · 확정] 아래가 유일한 값이며 새 값을 만들지 않는다. rev.2의 6종에서 검토 대기 · 검토 반려 · 체결 처리 대기 셋이 늘었다 — 어드민 검토와 어드민 체결 처리가 절차에 들어왔기 때문이다.

[종류 축은 색이 아니다] 종료(실패) 3종이 같은 분류여도 색은 갈린다 — 거절만 위험이고 만료·취소는 중립이다. 거절은 상대가 명시적으로 기각한 부정 결과 확정이고, 만료·취소는 아무도 손대지 않아 시간·철회로 닫힌 건이라 원칙 ②(취소·종료=중립)에 속한다. 원칙 ④ 기획문서 태그와 UI 상태색은 별개가 이 경우다.
[rev.2 · 회수(작성중 복귀)는 채택하지 않음] 작성 스펙 §11에는 검토 요청 취소 → 작성중 복귀(C7)와 철회 → 취소가 함께 적혀 있었다. 둘은 같은 일(진행 되돌리기)을 다른 결과로 처리하는데 브랜드가 어느 쪽을 눌러야 하는지 판단할 근거가 화면에 없고, 무엇보다 확정 상태표에 취소는 종료(실패)로 못박혀 있어 작성중 복귀는 표현할 상태가 없다. 그래서 서명 진행중의 되돌림 경로는 [계약 취소] 하나로 두고 항상 종결시킨다. 회수가 필요하면 상태값 추가 여부를 먼저 정해야 한다.
[취소 = 계약 철회로 확정] 취소는 서명 요청 발송 후 서명 완료 전에만 가능하다 — 작성중에는 취소할 게 없고(삭제·임시저장 폐기), 체결완료 후에는 취소가 아니다. B4 계열의 [계약 취소]가 이 전이의 입구다. 검토 단계(B3c)에는 [요청 취소]가 따로 있고 이것은 종결이 아니라 작성중 복귀다(C7) — 두 액션을 구분한다. 작성중 화면(B1·B2·B3)에는 취소 버튼을 두지 않는다(취소할 대상이 없다).
[지적 · 체결 후 해지 값이 없다] 9종 어디에도 체결완료 이후를 닫는 값이 없다. 공구가 이미 진행 중인 계약을 중단해야 하는 상황(브랜드 재고 소진·인플루언서 콘텐츠 미이행·분쟁)에서 표현할 상태가 없다. 이 시안은 그리지 않았다 — 값을 임의로 만들지 않는 규칙에 따른다. [결정 필요] 해지 값을 추가할지, 공구 상태(중단)로만 처리할지.
[rev.5 · 서명 진행중을 쪼개지 않는다 — 단계로 보여준다] 브랜드도 서명 대기 구간이 생기지만 상태값을 「내 서명 대기 / 상대 서명 대기」로 쪼개지 않는다 — 한쪽만 서명한 조합이 넷(둘 다 미서명 · 나만 · 상대만 · 둘 다)이라 상태값으로 표현하면 배지가 폭발한다. 상태는 「서명 진행중」 하나(정보)이고 누가 어디까지 했는지는 4스텝 스텝퍼 + 서명 카드 2장이 보여준다. v1.3 배지 사전의 내 서명 대기=경고 분리는 그대로 쓰지 않는다 — 서명은 상대를 기다리는 일이 아니라 외부 전자서명에서 각자 하는 일이라 이 화면의 조치 대기로 잡지 않는다.
[rev.2 · 「이 조건으로 새 계약 작성」 동작 규칙 · 화면 미제작] 종결 3종(거절·만료·취소)의 이 버튼은 새 계약을 하나 더 만든다 — 원 계약은 종결 상태로 그대로 남고(이력 보존), 새 CTR 번호를 가진 작성중 계약이 생성되어 작성 화면(B1)이 열린다. 종결된 계약을 되살리는 것이 아니다.
  · 복사 — 계약 상대, 공구명, 상품 항목(공구가·리워드율·최소 물량), 고정 지급비 금액, 콘텐츠 의무 전부, 비고.
  · 비운 채로 열기 — 공구 기간(시작·종료)과 게시 완료 기한. 과거 날짜를 그대로 복사하면 "시작 일시 ≥ 검토 요청일 + 7일" 하드 규칙에 즉시 걸리고, 게시 완료 기한은 기간에 연동되므로 함께 초기화한다.
  · 다시 받는 값 — 고정 지급비 확인 체크. 지급 시점을 다시 고르므로 이전 동의를 승계하지 않는다.
  · 승계하지 않는 것 — 서명 이력, 서명 기한, 원 계약의 상태.
  · 복사 직후 재검증 — 그 사이 상품이 미진열로 바뀌었거나 정가가 내려가 공구가 > 정가가 됐을 수 있다. 진입 즉시 하드 검증을 돌려 위반 행에 에러 문구를 띄우고 [검토 요청]을 비활성으로 둔다.
  · 화면 표기 — 작성 화면 상단에 출처를 밝힌다(예: "봄 클렌저 공구의 조건을 복사했습니다"). [화면 미제작] 이 상태의 스냅샷은 만들지 않았다 — B1과 값만 다른 같은 레이아웃이라, 필요해지면 B1 변형으로 추가한다.
[rev.2 · 종결 스텝도 배지와 같은 색] 진행 단계의 종결 칩은 상태 배지와 같은 색 체계를 쓴다 — 거절만 위험(.stop), 만료·취소는 중립(.halt). 같은 화면에서 배지는 중립인데 스텝은 위험색이면 어느 쪽이 진짜인지 읽을 수 없다.
[상태색] 작성중=중립(아직 시작 안 함) · 검토 대기·서명 진행중·체결 처리 대기=정보(정상 진행 대기) · 검토 반려=경고(브랜드 조치로만 풀린다) · 체결완료=성공(공구 생성 게이트가 열리는 실질적 성취라 문의의 "답변완료"와 달리 성공색) · 거절=위험(부정 결과 확정) · 만료·취소=중립(원칙 ② 취소·종료).
[상태는 탭 · 종결은 묶는다] 상태는 배타적 축이라 1단 탭. 탭 「종료」는 종료(실패) 3종(거절·만료·취소)이고, 종료(성공)인 체결완료는 별도 탭이다 — 브랜드가 가장 자주 찾는 값이고 공구 생성의 입구라 실패군과 같은 서랍에 넣지 않는다. 목록 배지는 개별 값 그대로 표시한다.
[rev.2→5 · 작성중·검토·서명 진행중은 같은 화면] 라우팅이 바뀌지 않는다 — /contracts/new 한 화면에서 편집 잠금 + 서명 카드 추가로만 변한다. 상태 3단계: 작성중(전 필드 입력 가능 · 하단 [임시저장]/[검토 요청]) → 서명 진행중(전 필드 읽기 전용 + 서명 영역 노출) → 종결(읽기 전용 + 체결 PDF·인증서 또는 종결 사유). rev.1의 "작성 화면과 계약서 화면을 분리" 판정은 폐기한다.
[rev.3 · 정합 검토] 상태 간 데이터가 이어지도록 맞췄다 — ① A1 목록의 검토 대기·검토 반려·서명 진행중·체결 처리 대기·체결완료·작성중 행 값을 각 상세(B4·B5·C3)와 문자 단위 일치 ② 여름 수분 세럼 공구의 고정 지급비를 전 상태 1,200,000원으로 통일(작성중 화면들이 50만원으로 남아 있었다) ③ 검토 요청 확인(C3)은 가을 앰플 신제품 공구 건으로 교체 — 여름 건은 B3에서 8일로 확정돼 17일 경고와 공존할 수 없다. 경고 열거에 고정 지급비 100만원 초과를 추가해 4건.
[rev.3 · 발송 시퀀스 모달은 별 파일] 시퀀스 8종(결제수단 차단 · 계약서 생성 중 · 브랜드 서명 · 서명 미완료 · 선결제 진행 중 · 결제 실패 · 발송 완료 · 발송 실패)은 ui-partner-08b-send-sequence.html에 있다 — 한 파일에 32장이 들어가면 리뷰가 불가능해 발송 구간만 떼어냈다. 두 파일은 같은 셸·토큰·상태색을 쓴다. [rev.5로 폐기 · 재작성 대기] 그 파일의 8장(문서 생성 → 브랜드 서명 → 선결제 → 발송 완료/실패)은 기안자 선서명 전제라 현재 절차와 맞지 않는다. 새 절차(어드민 검토 → 양측 서명 요청, 결제 단계 없음)로 다시 그려야 하며 그때까지 참조하지 말 것.
[rev.3→5 · 발송 시퀀스는 폐기됐다] rev.3의 하드 검증 → 발송 모달 → 문서 생성 → 브랜드 서명은 기안자 선서명을 전제로 한 순서였고, 전자서명 솔루션이 이를 지원하지 않아 rev.5에서 폐기했다. 확정 순서는 하드 검증 → 검토 요청 모달 → 어드민 검토 → 양측 서명 요청 → 양측 서명 → 어드민 체결 처리다 — 브랜드 서명이 발송 단계에서 빠지고 어드민 검토가 그 자리에 들어왔다.
[rev.3→6 · 선결제 내역 카드는 폐기했다] 카드·결제수단 상태(구 B3a·B3b)·선결제 이력을 전부 삭제했다 — MVP에서 플랫폼이 고정 지급비 결제를 중개하지 않는다. 남은 것은 금액 + 지급 시점이고 계약서에 기재되는 값일 뿐이다.
[rev.3 · 브랜드 사전 검수] 「사전 검수」를 「브랜드 사전 검수」로 바꿨다 — 운영자가 하는 공구 게시물 문구 점검과 이름이 겹쳐 혼동된다.
[rev.7 · 모두싸인 API 미도입 — 수동 갱신 MVP] API 요금제 비용 때문에 웹훅·문서조회 API를 쓰지 않는다(요금제만 사용). 절차는 rev.5 그대로이고 화면에 남는 제약만 셋이다.
  · 서명 링크를 우리가 갖지 못한다 — 모두싸인이 참여자에게 직접 보낸다. 그래서 [내 서명하기]를 없앴다: 누를 대상이 없는 버튼은 누르고 나서 아무 일도 일어나지 않는 것이 최악이다. 대신 [서명 안내 다시 받기](어드민에 재발송 요청)를 두고, 대기 문구에 「메일·문자로 받은 전자서명 링크에서 서명합니다」를 명시한다.
  · 서명 완료를 실시간으로 받지 못한다 — 웹훅이 없어 어드민이 모두싸인에서 확인한 값이 화면에 온다. 그래서 서명 카드 하단에 「어드민이 확인한 시점 기준 · N 기준」을 적는다. 참여자별 3분기(B4·B4a·B4c)는 그대로 유지한다 — 값이 늦을 뿐 틀리지 않고, 늦는다는 사실을 화면이 밝히면 읽을 수 있는 정보가 된다. 밝히지 않으면 방금 서명한 사람이 「왜 반영이 안 됐지」로 오해한다.
  · 만료가 자동 판정이 아니다 — 기한이 지나도 시스템이 스스로 닫지 못해 어드민이 확인해 만료 처리한다(B7의 스텝·이력 주체를 「시스템」에서 「어드민」으로). 같은 이유로 체결 처리도 어드민이 모두싸인에서 확인해 진행하며 그때 PDF·감사추적인증서를 내려받아 업로드한다(B4b).
  · API 도입 시 되돌릴 지점을 좁혀 뒀다 — 「기준 시각」 한 줄과 [서명 안내 다시 받기] 버튼만 제거하면 되고 상태값·스텝퍼·3분기 구조는 건드리지 않는다.
  · 쇼룸 스튜디오(ui-studio-08-contracts rev.2)와 동일 마크업이다 — 서명 카드·스텝퍼·기준 시각 문구가 같고 「어드민」을 「운영자」로 쓰는 표기만 다르다.
[rev.5 · 전자서명 솔루션 확정으로 절차가 바뀌었다 — 이 파일의 근간] 모두싸인 조사 결과 기안자 선서명(발송 = 브랜드 서명)이 불가해, rev.2에서 택했던 순서 A를 폐기한다. 확정 절차는 브랜드 작성 → 어드민 검토 → 양측 동시 서명 요청 → 양측 각각 서명 → 어드민 체결 완료다.
  · 브랜드 버튼은 [계약서 발송]이 아니라 [검토 요청]이다 — 이 버튼은 서명도 결제도 하지 않는다. 발송이라 부르면 브랜드가 계약서가 나갔다고 오해하고, 실제로는 어드민 검토가 먼저다.
  · 서명은 이 화면 밖에서 일어난다 — 어드민 검토를 통과하면 전자서명 솔루션이 브랜드·인플루언서 양측에 메일·문자를 각각 발송하고, 서명은 그 링크에서 한다. 그래서 브랜드도 서명 대기 상태로 시작한다(B4) — 다만 서명 버튼은 두지 않는다(rev.7 · 링크를 우리가 갖지 못해 누를 대상이 없다) — rev.2의 「브랜드는 발송 시 서명 완료」는 사라졌다.
  · 양측 서명만으로 체결되지 않는다 — 어드민이 서명 결과를 확인해 체결 완료를 눌러야 계약이 성립하고 그때 공구가 생성된다. 그 사이 구간을 체결 처리 대기(B4b)로 세운 이유는, 서명을 끝낸 브랜드가 「끝났다」고 보고 준비 일정을 당겨 잡는 것을 막기 위해서다.
  · [rev.6] 선결제 자체를 없앴다 — MVP에서 고정 지급비는 플랫폼을 거치지 않는다. 계약 절차 어디에도 결제 단계가 없어 rev.5에서 고민했던 「선결제 시점」 문제가 사라졌다.
  · 상태값 9종(진행 6 + 종결 3) — 작성중 · 검토 대기(정보) · 검토 반려(경고 · 브랜드가 고쳐야 넘어간다) · 서명 진행중(정보) · 체결 처리 대기(정보) · 체결완료(성공) / 거절 · 만료 · 취소(중립·위험). 검토 반려만 경고인 이유는 유일하게 브랜드 조치로 풀리는 상태이기 때문이다.
  · 편집 잠금 구간이 넓어졌다 — 검토 요청 시점부터 잠긴다(검토 중에 내용이 바뀌면 어드민이 본 것과 달라지고, 서명 중에 바뀌면 서명 대상이 달라진다). 검토 반려에서만 다시 열린다.
[rev.4→6 · 지급 트리거는 브랜드가 고른다] rev.4는 「게시물 등록 + 운영자 오픈 승인 완료」를 지급 트리거로 고정했으나, MVP에서 플랫폼이 지급을 집행하지 않으므로 트리거를 플랫폼이 정할 근거가 없다. 브랜드가 계약서에 지급 시점을 기재하는 방식으로 바꿨다(공구 게시물 등록 후 / 공구 종료 후 / 정산 완료 후).
[rev.2→6 · 고정 지급비 = 금액 + 지급 시점만] 매출과 무관하게 인플루언서에게 지급하는 금액. 플랫폼은 중개하지 않고 브랜드가 직접 지급하며, 계약서에는 금액과 지급 시점만 기재된다(공구 게시물 등록 후 / 공구 종료 후 / 정산 완료 후 중 선택). 0원 초과를 입력하면 접히지 않는 고지 블록 + 확인 체크(필수)가 나타난다 — 지급 이후 콘텐츠 미이행은 환급되지 않고 회수도 실익이 없어, 계약 전 고지가 유일한 방어선이기 때문이다. 지급 여부를 플랫폼이 확인하거나 보증하지 않는다 — 미지급 분쟁은 이슈 스레드에서 운영자 중재로 다루고 계약서가 근거가 된다. 0원 초과 시 고지 블록과 확인 체크는 그대로 유지한다: 플랫폼이 보증하지 않는다는 사실 자체를 계약 전에 알려야 한다.
[권한 3분류] 계약 조건 전체(공구명·기간·상품 항목·고정 지급비·콘텐츠 의무·비고) = 검토 요청 전 ①직접 수정 / 검토 요청 후 ③변경 불가 — 검토 중에 바뀌면 어드민이 본 내용과 달라지고, 서명 중에 바뀌면 서명 대상이 달라진다. 예외는 검토 반려로, 이때만 편집이 다시 열린다. 서명 진행중 이후 수정하려면 취소 후 재작성 · 정산 조건·표준 조항 = ③변경 불가(표준 조항 자동 삽입, 브랜드 편집 불가) · 계약 상대 = 검토 요청 전에도 연결됨 상대만 선택 가능(스레드 경유 진입 시 변경 불가).
[rev.2 · 샘플·단독은 협의 변수가 아니라 표준 조항] 샘플 제공과 독점(단독) 여부를 삭제하고 표준 조항으로 옮겼다 — 두 항목이 마지막이라 「협의 조건」 카드 자체가 없어졌다 — 값이 하나로 고정돼 있어(샘플은 항상 무상 제공, 판매는 항상 단독) 선택지를 주는 것 자체가 거짓이다. 고를 수 없는 항목을 입력 필드로 두면 "아니오"인 계약이 존재하는 것처럼 읽힌다. 유상 샘플의 정산 상계가 불가능한 이유는 ① 자금 방향이 한 방향 ② 비사업자 원천징수 3.3%가 총액 기준이라 순액이 음수면 세무 처리가 성립하지 않음 ③ PG 3자 분배에 음수 배분이 없음. 규칙 없는 데이터가 쌓이는 것을 막기 위해 값 자체를 잠근다 — rev.1의 유상 샘플비 차감 안내는 삭제했다.
[원가 판정 없음] 공구가의 원가 이하 여부는 판정하지 않는다 — 상품 객체에 원가 필드가 없고, 브랜드 원가는 플랫폼이 알 권리가 없는 정보다.
[rev.2 · 하드 / 경고 2단 검증] 하드는 검토 요청을 막는다 — 공구가가 정가 초과·10원 단위 아님, 리워드율 0~90% 밖, 기간 3~30일 밖, 시작 일시가 검토 요청일+7일 미달, 콘텐츠 수량 합계 0, 상품 항목 0건, 고정 지급비 체크 미완. 경고는 막지 않고 검토 요청 확인 모달에서 열거 + 체크를 받는다 — 할인율 70% 초과, 리워드율 40% 초과, 기간 14일 초과, 시작일이 검토 요청일+60일 이후, 상품 10건 초과, 고정 지급비 100만원 초과. 통과된 경고는 어드민 계약 검토 화면에 그대로 전달된다(rev.5) — 계약 단계에 어드민 검토가 생겼으므로 공구 오픈 승인까지 미룰 이유가 없다. 브랜드가 체크로 통과시킨 항목을 어드민이 서명 요청 발송 전에 보고 반려할 수 있다(B3d).
[에러 문구 vs 비활성] 필수 미입력은 에러 문구 없이 [검토 요청] 비활성(B1). 에러 문구는 규칙 위반에만 쓴다(B2). 전량 통과 시 버튼이 활성된다(B3). 상품을 고르면 정가를 읽기 전용 컬럼으로 병기하고 예상 리워드를 자동 계산해 위반과 오해를 미리 막는다.
[rev.2 · 2차 활용 기간 되살림] 2차 활용권(허용/불허)과 2차 활용 기간(기간 지정 N개월 / 무기한)을 별도 행으로 둔다 — 허용일 때만 기간을 입력하고, 무기한을 고르면 개월 입력이 비활성된다(기본 12개월). 허용/불허만 두고 기간을 비고로 내렸던 처리를 되돌린 것이다 — 비고는 검증도 구조화도 없는 자유 입력이라, 기간이 비면 기한 없는 영구 허용으로 해석될 여지가 생긴다(wf-partner-03 [2026.07 추가]가 못박은 지점). 허용 범위는 문장이라 비고에 남긴다.
[rev.2 · 사전 검수 설명 명시] 있음/없음만으로는 무엇이 달라지는지 알 수 없어 한 줄을 붙였다 — 있음이면 인플루언서가 게시 전 초안을 연결·소통 스레드로 보내고, 브랜드 확인 없이 올린 콘텐츠는 이행으로 보지 않는다. 이행 판정의 조건이 바뀌는 항목이라 계약서 문구와 같은 수준으로 화면에 적어야 한다.
[rev.2 · 콘텐츠 의무 항목 정리] 게시 시점(공구 전/중)과 유지 기간(게시일로부터 N일)을 삭제했다 — 둘 다 외부 SNS 연동이 없어 시점·유지 여부를 시스템이 확인할 수 없고, 실제로 다투게 되는 건 약속한 수량을 언제까지 다 올렸는가 하나다. 그래서 콘텐츠 제출 기한 → 게시 완료 기한으로 바꿨다: "이 날짜까지 게시 포맷·수량 전부를 올린다"는 하나의 약속으로 통합하고 필수로 만든다. 이행 확인은 브랜드와 인플루언서가 연결·소통 스레드에서 직접 한다 — 운영자 수기 확인 경로를 두지 않는다(운영자가 개입할 근거도 수단도 없고, 두 당사자가 이미 상시 대화 채널을 갖고 있다). 미이행은 금전 회수가 아니라 계정 제재·재계약 차단으로 처리한다.
[rev.2 · 최소 물량은 상품 단위] 최소 준비 물량을 계약 단위 입력에서 계약 상품 항목의 열로 이동했다 — 상품이 여러 개인 계약에서 계약 하나에 물량 하나면 어느 상품 몫인지 알 수 없고, 판매·재고 대조도 상품 단위로만 가능하다.
[출생지 규칙] 계약 상품 항목이 공구가·리워드율·최소 물량의 출생지다. 리워드율은 상품 항목 단위(상품마다 차등)이며 정산이 이 값을 그대로 쓴다. 공구 기간은 계약 단위이고 공구가 이를 상속한다.
[공구명은 내부 식별명] 브랜드가 입력하는 내부 관리용 이름이다. 소비자에게 보이는 게시물 제목은 인플루언서가 쇼룸 스튜디오에서 따로 쓴다 — 두 값을 같은 것으로 취급하지 않는다.
[목록 진입] 행 전체 클릭. 관리 열에 [보기]·[이어 작성] 링크를 두지 않는다(v1.3 「목록 상호작용 규칙」) — 와이어의 관리 열은 삭제했다. 작성중 행을 클릭하면 작성 모드로, 나머지는 계약서 모드로 열린다.
[rev.2 · 기간은 달력에서만 선택] 공구 기간은 직접 입력 필드가 아니라 달력 모달(C1·C2)에서 고른다. 제한값은 에러로 알리는 게 아니라 선택 자체를 잠근다 — 검토 요청일 + 7일 미달, 기간 30일 초과는 회색 취소선으로 비활성된다. 그 결과 기간 관련 하드 오류 문구가 도달 불가능해져 B2의 에러는 직접 입력 필드(공구가)에만 남는다. 경고(기간 14일 초과 등)는 잠그지 않고 트리거 아래 힌트 + 검토 요청 확인 모달에서 처리한다. 시작 일시와 종료 일시는 각각 다른 모달이며, 종료 모달은 시작이 정해진 뒤에만 열린다 — 종료의 잠금 범위가 시작값에 의존하기 때문이다. 달력은 한 달씩 보여주고 ‹ › 로 이동한다(선택 가능일이 없는 방향은 잠금). 시각은 각 모달 하단에서 시 드롭다운(00~23) + 분 드롭다운(5분 단위)으로 고른다 — 자유 입력이 아니라 값 자체를 제한한다.
[rev.2 · 기간 규칙 확정] 공구 시작 일시는 검토 요청일 + 7일 이후(하드), 공구 기간은 3~30일(하드). 7일은 인플루언서 서명 → 게시물 등록 → 운영자 오픈 승인(SLA 3영업일)에 필요한 리드타임이고, 30일 상한은 상시 판매와의 구분·정산 지연 방지다. 서명 기한 = 공구 시작 일시 − 3일로 자동 설정된다(rev.1의 "발송일 + 7일" 잠정치는 폐기).
[근거 대기] ① 서명 시 본인확인 수준 ② 표준 조항·위약금 문안(법률 검토) ③ 대가관계(유료광고) 표시 의무 연동 [쟁점 A] ④ 어드민 검토 SLA(제출 후 며칠 내 통과·반려) ⑤ 검토 반려 후 재요청 횟수 제한 ⑥ 고정 지급비 지급 완료 기록의 효력 — 인플루언서가 미수령을 주장할 때 기록만으로 판단할지, 증빙(이체 내역) 첨부를 요구할지.
[rev.5·6에서 해소된 것] · 전자서명 업체 — 모두싸인 확정, 기안자 선서명 미지원이 확인돼 순서 A를 폐기하고 어드민 검토 + 양측 동시 서명으로 바꿨다(rev.5) · 인플루언서 서명 위치 — 스튜디오 내부가 아니라 메일·문자로 받는 외부 전자서명 링크이며 브랜드도 같다 · PG 수수료율·원천징수·PG 자문 문항8 — MVP에서 고정 지급비를 플랫폼이 중개하지 않으므로 이 화면의 결정 사항이 아니다(rev.6 · 정산 관리 소관).
상태값 9종(진행 6 + 종결 3) 자체는 확정이며, 남은 값 관련 결정은 위 「체결 후 해지 값이 없다」 하나다.
