ui-studio-06-account — 쇼룸 스튜디오 기본정보 관리 · 계정

근거: wf-studio-05-쇼룸기본정보 F3(기본정보 관리 — 계정) · ui-studio-04-connections.html(메인 셸 · 컴포넌트 재사용) · SHOWROOMZ 웹 디자인시스템 v1.3(셸 · 탭 · 액션 모달) · GNB #9 · 정산 정보 탭 포함(온보딩 ui-studio-03 입력값 기준) · 상태 15종(T1~T7 정산 정보 · S1~S8 계정)

[2026.10.07 · 리워드 지급 구조 반영] ①비사업자 상태(T1 · T2 · T3)에 주민등록번호 카드를 추가했다 — 리워드 지급자가 SHOWROOMZ이고 원천징수 신고(지급명세서 제출)에 필요하다. ②주민등록번호는 온보딩(rev.3) 필수 입력이고 기존 회원이 없어 미등록 상태를 두지 않는다(T1a · 정산 관리 D3a 삭제). ③사업자(T5)에는 주민번호 대신 「세금계산서는 SHOWROOMZ 앞으로 발행해요(리워드 + 부가세 10%)」 1회 안내. ④우측 「정산은 이렇게 진행됩니다」를 새 흐름(주문 종결 → 3영업일 확인 → 자동 확정 → +3영업일 · SHOWROOMZ 지급 · 고정 지급비는 브랜드 직접 지급)으로 교체했다.
[약관수정필요] 개인정보처리방침에 주민등록번호 수집 · 이용 목적(원천징수 신고) · 보관 기간 추가.
[스코프] GNB #9 기본정보 관리 — 정산 정보 탭(T1~T6) + 계정 탭(S1~S8). 계정 탭의 탈퇴 흐름은 승인제다.
[온보딩이 정본이다 · 「미등록」 빈 상태는 없다] 정산 정보는 온보딩(ui-studio-03)에서 이미 받는다 — 사업자 여부 · 은행 · 계좌번호 · 예금주 · 통장 사본(사업자면 사업자등록번호 · 사업자등록증). 온보딩을 마쳐야 스튜디오에 들어오므로 이 탭에서 계좌가 비어 있는 상태는 발생하지 않는다 — 그래서 「미등록」 빈 상태를 그리지 않고 최초 진입(T1) = 온보딩 값이 들어온 읽기 전용으로 시작한다. 이 탭에 오는 목적은 확인과 변경이다.
  · 필드 구성 · 제약을 온보딩과 일치시켰다 — 은행 드롭다운 · 계좌번호 숫자만 10~16자리 · 예금주 본인 인증값 마스킹 + 잠금(소*연) · 통장 사본 필수(최대 10MB · jpg · png · pdf). 같은 정보를 두 화면에서 다른 형태로 받으면 검증 규칙이 갈라진다.
  · 사업자는 등록번호 · 등록증 두 값만 받는다 — 온보딩이 그 둘만 받으므로 상호 · 대표자 · 업태를 화면에 만들지 않았다(받지 않는 정보를 표시할 수 없다). 상호는 사업자등록증으로 운영자가 확인하고, 승인 후 예금주 규칙이 「대표자명 또는 상호」로 바뀐다(온보딩 안내와 동일).
  · 온보딩은 사업자 선택을 「개인사업자 · 법인」 한 덩어리로 묶었지만 이 시안은 법인을 제외해 「개인사업자」로 표기했다 — 온보딩 라벨도 함께 정정이 필요하다.
[「사업자 여부 변경 요청」은 어느 상태에서 보이나] 이 버튼은 모든 상태에서 같은 자리에 있다 — 계좌 변경 중(T2 · T3)에도 숨기지 않는다. 계좌 변경과 사업자 전환은 서로 다른 절차이고 동시에 진행하지 못할 이유가 없으며, 같은 카드가 상태마다 있다 없다 하면 사용자는 「지금은 왜 없지?」를 매번 판단해야 한다. 요청을 누르면 사업자등록번호 · 사업자등록증을 받는 모달(T7)이 뜨고, 제출 후 확인 대기(T4)로 넘어간다. 유일한 예외는 그 확인 대기 상태다 — 이미 요청이 걸려 있으므로 같은 버튼 자리가 [요청 취소]로 바뀐다(같은 요청을 두 번 걸 수 없다).
[정산 정보 = 「지급받을 정보」만 관리한다] 이 탭에는 금액이 없다 — 확정 금액 · 지급일 · 명세 · 세금계산서 발행 대상은 정산 관리(#7)가 단일 소스이고, 여기는 어디로 · 어떤 세무 형태로 받을지만 정한다. 두 화면이 금액을 각각 말하면 어긋나는 순간 어느 쪽이 맞는지 알 수 없다. 우측 안내 카드도 절차 설명까지만 하고 숫자를 넣지 않는다.
[확인이 끝난 값은 편집 필드가 아니다] 계좌는 예금주 실명 확인을 통과한 값이라 그대로 두면 지급이 되고, 바꾸면 확인을 다시 거친다. 그래서 등록 후에는 읽기 전용 + [계좌 변경]이며(T2 · T4) 계좌번호는 마스킹한다 — 전체를 노출할 업무상 이유가 없다. 예금주는 본인 인증 실명 고정이라 처음부터 잠겨 있고 본인 명의 계좌만 등록된다(정산 대상자 = 실명 기준).
[정산 형태 변경은 셀프 저장이 아니다] 비사업자 ↔ 사업자는 세금 처리 자체가 바뀌는 일(원천징수 3.3% ↔ 세금계산서 발행)이라 사업자등록증 제출 + 운영자 확인을 거친다(T3). 중요한 건 심사 중에도 기존 형태로 정산이 계속된다는 점이다 — 확인을 기다리는 동안 지급이 멈추면 인플루언서가 형태 변경을 꺼리게 된다. 상태는 정보색(정상 진행 · 대기 · 원칙①)이고 요청 취소가 열려 있다.
[에러 문구를 쓰는 경계] 이 탭의 에러 문구는 파일 형식 · 용량 오류 하나다(T3) — 다른 파일을 골라야 해결되므로 문구가 필요하고 업로드 박스 바로 밑에 붙는다. 계좌번호는 형식 오류가 발생하지 않는다 — 숫자만 입력되고 하이픈 · 문자는 타이핑돼도 들어가지 않으므로 틀린 값이 화면에 남지 않는다. 미입력과 자리수 미달은 [변경하고 실명 확인] 비활성만으로 표현한다(T2) — 아직 다 적지 않은 것은 오류가 아니다. 예금주 불일치는 입력 오류가 아니라 실명 확인 절차의 응답이라 이 입력 화면에서 다루지 않는다.
[미등록은 실패가 아니라 기한이 있는 할 일이다] 계좌가 없어도 공구는 진행되므로 T1을 「등록하세요」로 몰지 않고 언제까지 필요한지(첫 정산 확정 전)를 밝힌다. 다만 돈을 받을 수 없다는 사실은 맨 위에서 먼저 말한다 — 신규 인플루언서가 가장 먼저 보는 상태다.
[표기 규칙] 계좌번호는 숫자만 입력 가능 · 10~16자리(하이픈 · 문자는 입력 단계에서 차단되므로 형식 에러 문구를 쓰지 않고, 자리수 미달은 버튼 비활성만이다 · 온보딩 maxlength=16 · acct-only와 동일) · 사업자등록번호는 하이픈 포함 표기(123-45-67890).
[설계 원칙 — 공개/비공개 분리] 쇼룸 관리(#8) = 공개 / 기본정보 관리(#9) = 비공개. 우측 카드는 두 메뉴의 역할 구분을 화면 안에서 알려주는 안내 카드(와이어 F3의 설계 원칙 메모를 실제 UI 문구로 번역 — 시안 주석을 UI에 넣지 않기 위해 값 형태로 재작성).
[본인 인증값] 이름 · 생년월일 · 휴대폰은 마스킹 + 잠금. 셀프 수정 불가이며 변경은 운영팀 확인 + 재인증. 세부 절차(재인증 방식)는 미확정이라 화면에 그리지 않고 안내 문구까지만.
[활동 채널 축소] 플랫폼 · 채널 주소 · 계정 아이디 · 팔로워 수 필드는 두지 않음(가입 신청 시 1회 확인 정보) — 업무 이메일 하나만 남기고 카드 안 작은 저장 버튼으로 축소(wf-studio-05 F3 2026.07 축소 근거).
[에러 문구 사용 범위] 필수 미입력은 버튼 비활성만(S2) · 형식 오류(S3) · 중복은 에러 문구. 탈퇴 불가(S4)는 사용자가 스스로 해결할 수 없는 제약이라 비활성 + 사유를 함께 밝힘 — 필수 미입력 규칙의 예외로 처리했다.
[탈퇴는 즉시 실행이 아니라 승인제다 · 확정] [스튜디오 탈퇴]를 눌러 바로 탈퇴되지 않는다 — 탈퇴 승인 요청 → 운영자 승인 → 탈퇴 완료 3단이다. 즉시 탈퇴로 두면 플랫폼이 확인해야 하는 것을 확인할 수 없다: ①원천징수 · 세금계산서 등 세무 종결, ②브랜드에게 남은 콘텐츠 의무, ③소비자에게 남은 배송 · 반품 책임. 이 셋은 시스템 조건으로 다 잡히지 않아 사람이 확인해야 한다.
  · 요청 자체에 조건을 건다 — 조건을 요청 이후 심사에서만 보면 운영자가 이미 시스템에 다 있는 사실을 매번 손으로 확인하게 되고, 인플루언서는 왜 반려됐는지 나중에 안다. 그래서 기계가 판정할 수 있는 5가지는 화면에서 먼저 잠근다: 진행중 공구 0건 · 유효 계약 0건 · 미정산 0건 · 열린 이슈 0건 · 미발행 세금계산서 0건. 다섯 개가 모두 충족돼야 [탈퇴 승인 요청]이 활성된다(S4 → S5).
  · 조건은 체크리스트로 보여준다 — "탈퇴할 수 없습니다" 한 줄로 끝내면 무엇을 끝내야 하는지 알 수 없다. 각 조건에 건수와 해당 화면 링크를 달아 스스로 해소할 수 있게 했다. 조건 미충족은 사용자가 스스로 해결할 수 있는 제약이라 필수 미입력 규칙(비활성만)의 예외로 사유를 함께 밝힌다.
  · 요청에는 사유가 필수다(S6) — 운영자가 승인 · 반려를 판단할 근거이고, 반려 시 무엇을 다시 확인해야 하는지가 사유에서 나온다. 미선택은 버튼 비활성만으로 표현한다.
  · 승인 대기 중에도 스튜디오는 계속 쓸 수 있다(S7) — 요청은 예약이지 정지가 아니다. 단 새 연결 수락과 계약 서명만 막는다: 탈퇴 심사 중에 새 의무가 생기면 조건이 다시 깨져 심사가 무의미해진다. 요청 취소는 언제든 가능하다.
  · 반려에는 사유와 다음 조치를 함께 준다(S8) — 반려는 거절이 아니라 아직 남은 것이 있다는 통보이므로 재요청 경로를 막지 않는다. 반려 안내는 [확인]으로 직접 닫는다(자동으로 사라지지 않는다) — 읽었는지 확인되지 않은 통보가 조용히 없어지면 왜 탈퇴가 안 되는지 모른 채 체크리스트만 남는다. 닫으면 S4 · S5의 체크리스트 화면으로 복귀하고, 사유와 이력은 운영자 쪽에 보존된다.
[탈퇴 후] 소비자 계정 유지 · 쇼룸 비공개 전환 · 계약 · 정산 이력은 법정 보존. 되돌릴 수 없어 요청 모달(S6)에서 목록으로 고지하고 확정 버튼은 위험색.
[스냅샷 높이] 본문이 1024px를 넘는 상태는 디자인시스템 v1.3 「1024 초과」 규격에 따라 .stage를 세로로 늘려 전체를 펼쳐 표시했다 — 실제 화면은 GNB · 탑바 고정 + 본문만 스크롤.
[확인 필요] ① 업무 이메일 변경 시 인증 메일 확인 절차가 와이어에 없음 — 알림 수신 주소이므로 검증 없이 저장하면 알림이 유실될 수 있다. 즉시 저장 / 인증 후 확정 중 어느 쪽인지 확정 필요.
②-A 정산 정보 확정 필요 — ㉠실명 확인 실패 횟수 제한 여부, ㉡사업자 승인 후 사업자 명의 계좌로의 교체를 강제할지(현재 시안은 안내만), ㉢지급 예정 건이 있을 때 계좌 변경을 막을지 허용하되 보류할지(현재 시안은 허용 + 보류), ㉣비사업자로 되돌릴 때 받을 서류(폐업사실증명 등) 확정 필요 · ㉤사업자 변경의 적용 시점(현재 "다음 정산부터" — 이미 확정된 건의 소급 여부 미정). [자문대기-세무]
②-B 온보딩 안내 문구 오류 — ui-studio-03의 「사업자 여부 · 정산 계좌는 입력 후에도 쇼룸 관리에서 계속 수정할 수 있어요」는 실제 위치가 기본정보 관리 › 정산 정보다. 온보딩 문구 정정 필요.
② 탈퇴 조건 5가지의 정확한 상태값 — 공구는 「준비중 · 준비완료 · 진행중」까지 막는지(종료 후 주문 종결 대기는 공구 조건이, 정산 생성 이후는 정산 조건이 잡는다), 계약은 「서명대기 · 유효」 전부인지, 정산은 「지급 완료」 전 전부인지를 상태정의서로 확정해야 한다.
②-1 승인 처리 기한(현재 시안 영업일 5일) · 무응답 시 자동 승인 여부 · 재요청 제한 미정.
