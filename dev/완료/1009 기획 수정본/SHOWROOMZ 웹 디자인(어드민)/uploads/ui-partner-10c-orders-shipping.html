[rev.5→6 · 감시 2단 확정 · 분실 신고 폐기] ① 배송 이상 감시를 2단으로 확정해 서술을 통일했다(집화 확인 필요 + 추적 정지) — 3단 서술은 변경 이력 블록에만 남는다. ② 반송 완료(브랜드 입고)도 연동 코드로 자동 감지돼 브랜드가 도착을 알리는 액션을 없앴다: 도착 시 운영자 큐에 자동 편입된다. 반송 건은 목록·상세 어디서도 송장 수정 불가 — 번호가 맞아도 물건이 돌아오는 중이라 수정이 무의미하다. ③ 추적 정지의 [분실 신고]를 폐기했다(rev.6) — 플랫폼은 분실·누락 판정에 관여하지 않는다. 택배사 조회는 소비자나 브랜드가 직접 하고, 누락이면 택배사가 배송완료로 처리, 분실이면 브랜드가 재발송한다. 분실 보상은 택배사와 브랜드 사이에서 끝나므로 플랫폼이 할 일은 재발송 송장을 받는 것뿐이고 액션은 [송장 수정] 하나다 — 사고 접수번호·증빙 폼(C7b2)은 삭제했다. ④ 설계 원리를 명문화했다(아래).
[rev.6 · 반송 사유는 화면에 쓰지 않는다] 추적 API가 주는 것은 반송 상태 코드와 시각뿐이고 「주소 불명」·「수취인 부재」 같은 사유는 표준 코드로 오지 않는다(대리점 메모로만 남는다). 확인되지 않은 사유를 단정하면 틀린 정보를 브랜드에게 확정처럼 보여주게 되므로, 화면에는 반송 처리 사실 · 감지 시각 · 타이머 정지만 쓰고 사유는 택배사 직접 조회로 안내한다.
[설계 원리] 돈의 시점(구매확정 D+7 · 정산)에 영향을 주는 상태 전환은 이해당사자가 만지지 않는다 — 자동 아니면 운영자다. 배송완료 처리 · 반송 후속 · 환불 집행이 전부 이 원칙을 따른다.
[파일 분할 · 참조 규약] 주문 관리는 탭별 5개 파일(10a 신규 · 10b 상품준비중 · 10c 배송중~구매확정 · 10d 취소 요청·취소 · 10e 전체)로 나뉘고 이 규칙 박스는 다섯 파일에 동일하게 실린다. 상태 참조에서 파일 접두가 붙은 것(예: 10c C7b)은 다른 파일에 있는 상태이고, 접두 없는 것은 이 파일 안에 있다. 반품·교환은 이 5개 파일에 포함되지 않는다.

  · 송장번호 자릿수·체크디지트는 하드 차단(경고 → 차단). 우리가 택배사별 자릿수 표를 하드코딩하지 않고 연동 업체가 최신 규칙으로 판정하며(무과금), 송장번호는 마지막 자리가 앞자리로 계산되는 체크디지트라 숫자 하나만 틀려도 잡힌다 — 오타를 통과시킬 이유가 없다. 문구는 「송장번호 형식이 올바르지 않습니다. 다시 확인해 주세요.」 하나이고 자릿수인지 체크디지트인지 구분하지 않는다(브랜드에게는 똑같이 "번호가 틀렸다"는 뜻이다).
  · 배송 이상은 3단 → 2단. 형식 오류가 등록 시점에 이미 차단되므로 24시간 미조회는 번호 문제가 아니라 픽업이 안 된 것이다 — 그래서 「송장 확인 필요」와 「집화 지연」을 「집화 확인 필요」 하나로 합쳤다(원인이 같아졌으니 단계를 나눌 이유가 없다). 송장 수정은 유지한다: 형식은 맞지만 다른 주문의 송장을 붙여넣은 경우가 남아 있다. 2단은 추적 정지(집화 후 7일 갱신 없음 · 위험 · [송장 수정]만).
  · 「반송 중」 신설(위험색) — 물건이 브랜드에게 돌아오는 중인데 화면에 계속 「배송중」으로 남으면 자동 구매확정 타이머가 돌아 못 받은 물건이 정산된다. 연동 업체가 반송을 코드로 구분해 주므로 자동 감지하고 타이머를 취소한다(화면에 「구매확정되지 않습니다」 표시) — 환불로 종결된다 — 이 주문으로 재발송하는 경로는 없다. 반송 완료(브랜드 입고)도 연동 코드로 자동 감지되어 브랜드가 누를 버튼이 없고 환불은 운영자가 실행한다 — 반송 물건을 브랜드가 임의 재발송하면 소비자 의사와 어긋날 수 있다. 요약 바 「배송 이상」에 합산한다.
  · 택배사 목록 확정 — CJ대한통운 · 롯데택배 · 한진택배 · 우체국택배 · 경동택배 · 대신택배 · 로젠택배 · 합동택배 · 쿠팡택배 · 우리택배 · CU편의점택배(사용 빈도순). 목록에서만 선택하고 자유 입력·「미지원 택배사」 옵션은 없다 — 연동이 지원하는 택배사만 노출되므로 추적 안 되는 송장이 애초에 등록되지 않는다. 발주서 다운로드 모달도 같은 목록이다.
[버전 표기] 제목의 rev.N은 파일 리비전(현재 rev.5)이고, 아래 [rev.N · …] 블록은 그 규칙이 도입·변경된 리비전을 가리키는 변경 이력이다 — 두 축이 다르므로 블록 번호가 제목보다 클 수 있다(한 리비전 안에서 여러 결정이 순차로 들어온 경우).
[이 화면의 성격 — 조회용 대시보드가 아니라 매일 여는 작업 큐다] 브랜드가 가장 먼저 알아야 할 것은 「지금 내가 처리해야 할 게 몇 건인가」다. ① 상단 처리 대기 요약 바 고정 ② 기본 진입 탭 신규(준비 대기) ③ 정렬 기본값 오래된 순 ④ 목록 관리 열에서 바로 처리 ⑤ 다건 선택 일괄 처리.
[단위가 3층이다] 주문(결제 1건) → 하위주문(공구·브랜드별 · 배송 단위) → 주문 항목(SKU · 취소·반품·교환 단위). 브랜드가 보는 기본 단위는 하위주문이고 타 브랜드 몫은 보이지 않는다. 하위주문 1건 안에서 일부 항목만 반품·교환될 수 있어 목록이 둘로 갈린다 — 배송은 하위주문(이 파일), 반품·교환은 항목 단위(10b).
[rev.2 · 상세를 전체 페이지에서 모달로 바꿨다] 목록의 스크롤 위치·필터·체크박스 선택을 잃지 않기 위해서다. 헤더의 [‹ 이전][다음 ›]으로 5건을 연속 처리할 때 목록으로 나갈 필요가 없다. 폭 1040px에 좌 본문 + 우 레일 2단이고, 뒤에 목록이 깔린다.
  · 모달 안에서 또 모달을 띄우지 않는다 — 송장 등록·수정은 필드가 2개뿐이라 우 레일 인라인 입력으로 펼친다(10b C2 · 10b C3 · 10b C4). 반면 준비 시작 확인·배송완료 요청는 경고 한 줄이라 작은 다이얼로그로 겹쳐도 된다(E8).
[rev.2 · 택배사 API는 「배송 추적」만 연동한다] 목적별로 나뉘는 API 중 이번 버전에 들어오는 것은 추적 하나다 — 송장 자동 발번 없음(브랜드가 자기 택배사에서 발급) · 배송 추적 있음(상태·위치 자동 조회 + 배송완료 자동 전환) · 반품 회수 접수 없음. 정리하면 송장은 사람이 넣고, 그 다음부터는 시스템이 따라간다. ui-partner-06의 「택배 연동 준비중」과 어긋나지 않는다 — 그 항목은 발번·회수 연동이고 여기서 들어오는 건 조회뿐이다.
[rev.2 · 엑셀 왕복이 이번 버전의 핵심 기능이다] 브랜드의 실제 작업은 발주서 엑셀 다운로드 → 택배사 시스템 업로드 → 송장 발급·스티커 출력 → 출고 → 송장 채운 엑셀 일괄 업로드 → 이후 자동이다. 이 왕복이 없으면 브랜드가 주소를 손으로 타이핑하게 되고 그게 오배송의 가장 흔한 원인이다. 그래서 발주서는 택배사별 양식으로 내려주고(E1), 업로드는 부분 성공을 허용한다(E3) — 50건 중 1건 틀렸다고 전부 막히면 브랜드는 처음부터 다시 한다.
[rev.2 · 배송완료는 자동이 주 경로, 요청이 폴백] 추적 데이터가 배송완료로 바뀌면 시스템이 전환하고 구매확정 카운트를 시작한다 — 브랜드가 누를 버튼이 없다(C8). 다만 지원하지 않는 택배사·해외 배송·자체 배송처럼 추적이 원래 안 잡히는 경우가 있어 수기 처리를 남긴다(C7·rev.3 삭제) — 이 버튼은 추적이 없는 건에만 나타나고 정상 추적 건에는 없다.
  · 배송완료일시는 구매확정 D+7의 기산점이자 정산 시점의 기준이라 출처를 항상 병기한다 — (자동 확인) 또는 (운영자 처리). 상세·이력 양쪽에 남기고, 요청 처리 건에는 소비자 이의 가능성까지 적는다(C9).
[rev.2 · 송장 검증은 강도가 다르다] 중복은 하드 차단(실무에서 가장 흔한 복붙 사고 · 어느 주문과 겹치는지 지목 — C3) / 숫자 외 문자는 하드 차단(공백·하이픈은 자동 제거 후 검사) / 택배사별 기대 자릿수 불일치는 경고만(택배사가 번호 체계를 바꿀 수 있어 차단하면 정상 송장이 막힌다 — C4) / 빈 값은 에러 없이 버튼 비활성.
[rev.2 · 집화 확인 필요 — 24시간 뒤에 경고한다] 집화 스캔 전에는 추적 데이터가 없는 게 정상이라 등록 직후에 경고하면 전부 경고가 된다. 등록 후 24시간이 지나도 조회되지 않으면 오등록 가능성이 높아 그때 알린다 — 목록 행 배지 + 요약 바 건수 + 상세 배너(C6)에서 [송장 수정]을 주 액션으로 승격. 송장 수정은 배송완료 전까지만 가능하고 이력에 남는다.
[rev.2 · 취소 처리 경로 신설] rev.1의 「취소」 탭은 이미 자동 취소된 건의 조회용일 뿐이어서, 준비 시작 이후 품절이 나거나 소비자가 마음을 바꾸면 브랜드가 할 수 있는 게 없었다. 두 경로를 넣었다 — ① 직권 취소(브랜드가 품절·하자로 스스로 · 상품준비중에서만 · 사유가 소비자에게 그대로 전달되고 취소율에 반영) ② 소비자 취소 요청 → 브랜드 승인·거부(「취소 요청」 탭 신설 · 소비자 요청이라 취소율에 반영되지 않는다).
  · [주문 취소]는 위험색이 아니라 중립 텍스트 버튼이다 — 파괴적이지만 품절 대응은 정상 업무이고, 위험색을 쓰면 매일 누르는 버튼이 매일 경고가 된다.
  · 준비 시작 되돌리기는 두지 않는다(확정). 상태는 앞으로만 진행하고, 문제가 생기면 직권 취소로 처리한다 — 되돌림을 열어두면 소비자 취소권이 열렸다 닫혔다 하는 상태가 생긴다.
  · 환불은 브랜드가 절대 실행하지 않는다 — 취소·반품 어느 경로든 운영자가 집행한다. 세 모달(E5·E6·E7) 모두 같은 문구로 적었다.
[rev.5 · 송장은 목록에서 직접 입력한다 — 모달을 하나 없앴다] 상품준비중 탭의 택배사·송장번호를 편집 가능한 열로 만들었다(A2a~A2c). 모달을 열지 않고 보면서 입력하는 게 이 작업의 본래 형태다 — 발주서·택배사 화면과 이 목록을 번갈아 보며 옮겨 적는 일이라, 모달이 목록을 가리면 대조가 끊긴다. 그리드 모달(rev.4의 E2b)은 폐기했다: 같은 일을 하는 화면이 둘이면 어느 쪽이 정본인지 흐려진다.
  · 입력과 확정을 분리한다 — 셀에 쳐도 즉시 저장되지 않고 [N건 송장 등록]을 눌러야 배송중으로 넘어간다. 입력 중 실수를 되돌릴 구간이 필요하고, 배송중 전환은 소비자에게 송장이 전달되는 되돌리기 힘든 사건이다.
  · 입력된 행은 배경 톤으로 구분하고 버튼에 건수를 박아 몇 건이 확정될지 누르기 전에 보인다. 검증 오류는 해당 셀에 인라인으로 띄우고 그 행만 제외하고 나머지는 등록한다(엑셀 업로드와 같은 원칙).
  · 택배사 일괄 적용을 헤더에 둔다 — 한 번에 보내는 건들은 택배사가 거의 같아서, 행마다 고르게 하면 순수한 반복 노동이 된다.
[rev.5 · 엑셀 업로드도 같은 확인 단계를 거친다] E3 검증 후 [목록에 채우기]는 상태를 바꾸지 않고 목록 셀을 채운다. 브랜드가 눈으로 확인한 뒤 [송장 등록]으로 확정한다 — 잘못 올린 파일을 되돌릴 수 있는 구간이 생기고, 수기 입력과 엑셀 업로드가 같은 확정 지점을 공유한다(10b A2b).
[rev.8→4 · 배송 지연 감시를 3단으로 쪼갰다 → 최종 2단] 24시간 「집화 확인 필요」 하나로 묶으면 멈춘 지점이 다른 세 상황이 같은 배지를 달게 된다 — 원인도 조치도 다르다.
  · 1단 · 등록 후 24시간 미조회 → 「집화 확인 필요」(경고) — 집화 전 · 번호 오류 의심 · 송장 셀 편집 + [수정]
  · 2단 · 등록 후 72시간 미조회 → 「집화 확인 필요」(경고) — 집화 전 · 물리적으로 픽업이 안 된 것 · 수정은 가능하되 안내 초점은 택배사 집화 확인(C7)
  · 집화 후 7일 갱신 없음 → 「추적 정지」(위험) — 배송완료 직전 · 송장 수정으로 해결되지 않는다(번호는 맞고 스캔 누락) · [송장 수정]만(rev.6 · C7b)
  · 「배송 지연」이라 부르지 않는다 — 발송기한(브랜드 의무)과 혼동된다. 최종 2단(추적 정지)은 브랜드 귀책이 아니라 택배사 추적 데이터가 멈춘 상태다.
  · 상단 요약 바는 세 단계를 합산해 「배송 이상 N건」 하나로 보여준다 — 요약은 손댈 일이 있는지만 알리고 구분은 목록이 한다.
[rev.8 · 배송완료에 브랜드가 관여하지 않는다] [배송완료 처리 요청]·[배송완료 수기 처리] 버튼과 요청 모달(rev.3 삭제)을 전부 삭제했다. 정상 경로는 추적 API 자동 전환(C8), 예외는 운영자 직권 처리(C9)뿐이다 — 요청 창구조차 두지 않은 이유는, 브랜드가 날짜를 제안할 수 있으면 협상 여지가 생기고 그 날짜가 구매확정 D+7과 정산 시점을 움직이기 때문이다. 「추적 정지」에는 [송장 수정]만 둔다(rev.6) — 분실·누락 판정에 플랫폼은 관여하지 않는다.
[rev.8 · 택배사는 목록에서만 고른다]전부 제거했다 — 자유 입력을 허용하면 추적이 불가능한 송장이 등록되고, 그건 「추적 정지」와 구분되지 않는다. 추적 연동 업체가 지원하는 택배사만 목록에 노출된다. [미정] 연동 업체 미확정이라 목록 자체가 잠정이다.
[rev.8 · 발송기한 판정 기준] 기산점은 결제완료 시각(브랜드가 준비 시작을 누르지 않아도 기한은 흘러간다), 판정은 송장 등록 시각(집화 아님 — 택배사 사정을 브랜드 귀책으로 돌리지 않는다). 열 헤더 툴팁에 이 두 문장을 넣었다. 「발송기한 경과」(위험 · 브랜드 귀책)와 「집화 확인 필요」(경고 · 택배사)은 별 배지이고 같은 행에 둘 다 뜰 수 있다 — 늦게 보낸 데다 픽업까지 안 된 건이 실제로 있다. [미정] 마감 시각·공휴일·영업일 기준.
[rev.7 · 탭마다 쓸 수 있는 액션만 남긴다] 모든 탭에 세 버튼을 다 띄우면 그 탭에서 쓸 수 없는 버튼을 눌러보고 실패한다. 액션도 탭별로 분기했다 — 전체는 액션 없음(조회 전용 · 체크박스·일괄 바 제거 · 관리 열은 [보기]), 신규는 [준비 시작]·[판매 취소] + 발주서, 상품준비중은 [N건 송장 등록]·[판매 취소] + 발주서·송장 업로드, 취소 요청은 [N건 처리]만(엑셀 없음), 배송중·배송완료·구매확정·취소는 체크박스·액션 바 자체를 없앴다.
  · [판매 취소]는 신규와 상품준비중 양쪽에 둔다 — 품절은 발주서를 뽑기 전에 발견되는 경우가 더 많다. 신규에 없으면 취소하려고 준비 시작을 먼저 눌러야 하는 이상한 순서가 된다.
  · 전체 탭은 없애지 않는다 — 주문번호·수취인명 검색은 상태를 모르는 상태에서 하는 행동이라 착지할 목록이 하나는 필요하고, 그래서 이 탭만 상태 열을 유지한다.
[rev.7 · 취소 요청도 목록에서 처리한다] 송장 입력과 같은 패턴이다(10d A2f) — 처리 드롭다운(승인/거부)과 거부 사유를 열로 두고 [N건 처리]를 눌러야 확정된다. 거부는 사유가 필수이고(비면 그 행은 제외 · 승인이면 사유 칸 비활성) 헤더의 처리 일괄 적용으로 대량 승인을 한 번에 한다. 엑셀 버튼은 두지 않았다 — 취소 승인은 파일로 주고받을 일이 아니다.
[rev.6 · 조회 기간은 탭 성격에 따라 다르다] 프리셋을 오늘 · 7일 · 1개월 · 3개월 · 직접 입력으로 바꾸고(3일 제거 · 최대 1년) 탭별 기본값을 분기했다 — 작업 큐 탭(신규·상품준비중·취소 요청)은 7일, 조회 탭(전체·배송중·배송완료·구매확정·취소)은 1개월. 처리할 일은 최근 것이지만 찾는 일은 과거를 뒤지는 행동이라 기본 창이 좁으면 매번 늘려야 한다.
[rev.6 · 상태 열도 탭별로 분기한다] 한 탭의 전 행이 같은 상태면 그 열은 정보가 0이다 — 신규·상품준비중·배송중·배송완료·구매확정·취소 요청 탭에서 상태 열을 뺐다. 대신 전체 탭은 유지한다: 주문번호·수취인명 검색은 상태를 모르는 상태에서 하는 행동이라 상태를 알려주는 목록이 하나는 있어야 한다. 취소 탭은 상태 열 자리에 「취소 사유」를 둔다(10d A2e) — 알아야 할 건 취소됐다는 사실이 아니라 누가 왜 끊었는지이고, 소비자 취소 / 취소 요청 승인 / 브랜드 직권 취소는 책임과 후속이 다르다.
[rev.6 · 경고 배지가 곧 편집 권한이다] 배송중 탭에서 배송 상태 상세 텍스트(최종 위치)를 뺐다 — 브랜드가 그 정보로 행동하지 않는다. 대신 「최종 갱신」을 넣었다: 위치가 어디인지보다 갱신이 멈춘 것이 문제 신호다. 송장 셀은 기본 읽기 전용이고 「집화 확인 필요」 배지가 있는 행만 편집 가능하다 — 실수로 건드리는 건 막으면서, 정작 고쳐야 할 행에서는 상세로 들어가지 않아도 되게 했다.
[rev.6 · 배송완료는 브랜드 처리에서 운영자 처리로 바꿨다] 브랜드가 배송완료일을 직접 넣으면 구매확정 D+7이 앞당겨져 청약철회 기간을 침해하고 정산도 앞당겨져 브랜드에게 직접 이익이 된다 — 자기 이익이 걸린 날짜를 자기가 정하는 구조를 베타에서 열 수 없다. 그래서 [배송완료 처리]으로 바꾸고 실제 처리는 운영자가 한다(요청 모달은 rev.3에서 삭제 — 브랜드에게 요청 창구조차 두지 않는다). 요청 뒤에는 액션이 사라지고 요청 내역만 남는다(C7b). 구매확정 출처 표기도 「(운영자 처리)」로 고쳤다.
[rev.5 · 탭마다 컬럼이 다르다] 한 표에 모든 상태를 담으면 열이 넘치고, 정작 그 탭에서 필요한 정보가 밀려난다. 상품준비중은 송장 입력이 전부라 공구명·주문일시를 빼고 택배사·송장번호 입력 폭을 확보했다. 배송중은 발송기한이 의미 없어 빼고 배송상태를 넣었으며, 송장 셀은 읽기 전용이다 — 목록에서 실수로 건드리는 건 막고, 고칠 일이 있으면 상세 모달의 [송장 수정]으로만 들어가게 한다(의도적 진입 · 배송완료 전까지). 신규는 현행 유지.
[rev.4 · 발주서 다운로드가 신규 탭의 주 액션이다] 발주서를 뽑는다는 건 이 주문들을 보내겠다는 결정이므로 [다운로드와 함께 준비 시작 처리]를 기본 체크로 묶었다(E1). 분리하면 준비 시작 후 대상이 신규 탭에서 사라져 상품준비중 탭에서 다시 골라야 하고, 같은 주문을 두 번 선택하게 된다. 체크를 해제하면 다운로드만 하고 상태는 그대로 둔다 — 견적·재고 확인용으로 먼저 받아보는 경우가 있다. 따라서 신규 탭의 주 액션은 [발주서 다운로드]이고 [준비 시작]은 개별·예외 처리용이다.
[rev.4 · 송장이 있으면 준비 시작을 묻지 않는다] 업로드 검증 결과(E3)에서 신규 상태 건도 함께 배송중으로 전환한다 — 송장이 있다는 건 이미 출고했다는 뜻이라 준비 시작을 따로 누르게 하는 건 형식일 뿐이다. 성공 블록에 「그중 신규 주문 N건」 하위 행으로 몇 건이 그 경로를 타는지 밝힌다.
[rev.3 · 메모 열을 빼고 발송기한 열을 넣었다] 컬럼 상한(9개 · 가로 스크롤 금지) 안에서 발송기한을 넣으려면 하나를 빼야 했고, 메모를 뺐다 — 배송 요청사항은 발주서와 상세 모달에 이미 있고 목록에서는 아이콘만 떠 실제로 읽으려면 어차피 열어야 했다. 반면 발송기한은 작업 큐의 우선순위 축이다: 무엇을 먼저 보낼지가 이 값으로 정해지므로 정렬 아이콘을 함께 뒀다(주문일시와 2개). 기한이 지난 건(현재 시각 기준 초과)은 경고색으로 표시하고, 이미 발송된 건은 기한이 의미 없어 —로 비운다.
[rev.3 · 목록 구조를 조회 화면 표준으로] 커머스 관리자 목록의 통용 구조에 맞췄다 — 조회 조건 블록 → 상태 탭 → 일괄 액션 바 → 표. 위에서 아래로 범위를 좁히고(조회) · 분류를 고르고(탭) · 골라 실행한다(일괄)는 순서다.
  · 조회 기준을 고르게 한다 — 같은 기간이라도 결제일 / 발주확인일 / 발송처리일 / 배송완료일 / 구매확정일 중 무엇을 기준으로 잡느냐에 따라 결과가 완전히 달라진다. 기본은 결제일 + 7일이고 프리셋으로 한 번에 바꾼다(10a A1b). 셀렉트 항목은 「발주확인일 / 발송처리일」이라는 업계 표준 날짜 필드명을 유지한다 — 버튼 라벨([준비 시작]·[송장 등록])과 다른 이유는, 버튼은 지금 할 행동이고 이쪽은 이미 기록된 시각의 이름이라 성격이 다르며, 정산·CS에서 쓰는 명칭과도 맞아야 한다.
  · 검색은 타입을 먼저 고른다 — 주문번호·수취인명·송장번호·상품명. 한 입력창에 전부 던지면 송장번호와 주문번호가 섞여 오조회가 난다.
  · 일괄 액션 바를 표 위에 상시 노출한다(하단 플로팅 바 폐기) — 선택 0건에도 자리를 지키고 비활성으로 보여줘 처음 온 사람도 무엇을 일괄 처리할 수 있는지 알게 한다. 좌측은 그 탭에서 쓸 수 있는 액션만(rev.7에서 탭별 분기 — 세 버튼이 동시에 뜨는 탭은 없다) — 행 관리 열·상세 모달과 같은 라벨을 쓴다(같은 동작에 이름이 둘이면 다른 기능으로 오해한다), 우측은 선택과 무관한 항상 활성([발주서 다운로드]·[송장 일괄 업로드]). 선택 건수는 버튼 옆에 붙여 대상이 몇 건인지 액션 바로 옆에서 읽게 한다.
  · 행 확장으로 항목을 미리 본다(10a A1c) — 목록은 하위주문 단위지만 발주 준비는 항목 단위다. 모달을 열지 않고 ▸ 하나로 확인할 수 있어야 하루 수십 건이 돌아간다.
  · 조회 결과 요약에 기간을 함께 적는다 — 건수만 있으면 무엇에 대한 86건인지 알 수 없다.
