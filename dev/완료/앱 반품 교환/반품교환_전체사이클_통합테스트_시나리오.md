## 1. 전제

### 1-1. 등장인물

| 역할 | 계정 | 비고 |
| --- | --- | --- |
| 소비자 C1 | 앱 유저 | 기본 배송지 「김수민 · 서울 강남구」 + 두 번째 배송지 1개 |
| 소비자 C2 | 앱 유저 | 격리 검증용 |
| 브랜드 A | 파트너센터 셀러 | 반품 수취 주소 설정 · 기본 배송비 3,000 · 무료배송 기준 50,000 |
| 브랜드 B | 파트너센터 셀러 | 격리 검증용 |
| 운영자 | 어드민 | 환불 집행 · 직권 완료 · 고지 · 폐기 — **받는 API가 없어 도메인 진입점을 직접 부른다**(6절) |

### 1-2. 기준 fixture

- 진행 중 공구 1건. 크림(공구가 27,200 · 옵션 「기본」 「리필」 같은 가격 · 재고 각 10) · 세럼(24,000).
- 주문 3종:

| 이름 | 구성 | 결제액 | 배송비 | `base_delivery_fee` |
| --- | --- | --- | --- | --- |
| 주문 P(유료배송) | 크림 1 | 30,200 | 3,000 냄 | 3,000 |
| 주문 F(무료배송) | 크림 1 + 세럼 1 | 51,200 | 0 | 3,000 |
| 주문 Q(수량) | 크림 3 | 81,600 | 0 | 3,000 |

- 설정: `order.claim.invoice-due-days=7` · `reship-pay-due-days=14` · `payment-pending-minutes=30` · `storage-required-notices=2` · `storage-months=3` · 구매확정 7일.
- 결제는 `FakePaymentGateway`(로컬) 또는 포트원 테스트 채널(스테이징).

### 1-3. 공통 확인 방법

1. 매 단계에서 **행위자 화면과 상대 서피스를 함께** 본다 — 소비자가 요청하면 브랜드 탭 카운트가, 브랜드가 판정하면 앱 상세가 바뀌어야 한다.
2. 돈에 닿는 값은 **DB 원값까지** 적는다 — `order_claim_collection.return_deduction · refund_amount` · `order_claim_charge.amount · status` · `order_refund_task.refund_amount` · `order_claim_payment.status` · `product_variant.stock`.
3. 구매확정에 닿는 단계마다 `OrderFulfillmentService.confirmIfDue(groupId, now)`를 불러 **확정되는지 / 안 되는지**를 적는다.
4. 실패 요청은 HTTP 상태 · `code`와 함께 부수 효과(이력 · 큐 · 재고 · 결제 행)가 남지 않았는지 본다.

## 7. 재현 방법 · 현행 제약

### 7-1. 사람이 없는 구간

| 구간 | 방법 |
| --- | --- |
| 주문 송장 추적 | `OrderFulfillmentService.applyTracking(group, Optional.of(TrackSnapshot), now, 24, 7)` |
| 회수 송장 추적 | `OrderClaimService.applyCollectionTracking(collectionId, carrier, 송장, TrackSnapshot, now)` |
| 재발송 송장 추적 | `OrderClaimService.applyReshipTracking(claimId, carrier, 송장, TrackSnapshot, now)` |
| 구매확정 | `OrderFulfillmentService.confirmIfDue(groupId, now)` — 미래 시각을 넘겨 「+8일」을 만든다 |
| 자동 취소 | `expireInvoice(collectionId, now)` — 미래 시각 |
| 초안 정리 · 취소 재시도 | `ClaimPaymentService.reconcile(now + 31분)` |
| 보관 기한 | `recordStorageNotice(…, 과거 시각)` → `disposeAfterStorage(…, now)` |

- 스캔 이력(`TrackSnapshot.events`)을 같이 넣어야 앱 조회 화면에 보인다. 이력은 **누적해서** 넣는다(앞 회차 + 새 스캔).
- 상태 컬럼을 SQL로 바꾸지 않는다 — 이력 · 이벤트 · 부수 효과가 빠진다. 시각 컬럼(`delivered_at` 등)만 당긴다.

### 7-2. 현행 제약

| 구간 | 제약 | 테스트 처리 |
| --- | --- | --- |
| 택배 추적 | `delivery.tracker.enabled=false` — 배치 미기동 | 7-1로 재현. 켠 뒤 실연동 라운드 별도 · `receive-before-arrival=false`로 내리고 R1-7을 「도착 전 입고 확인 불가」로 재검증 |
| 환불 집행 · 직권 완료 · 고지 · 폐기 | 어드민 API 없음 | 도메인 진입점 직접 호출이 판정선. PG 환불(`payment_cancel`)은 목표 케이스 |
| 알림 | `ClaimHistoryRecordedEvent`는 발행되지만 받는 쪽이 없다 | 발행 여부까지. J1-2 · C-3 · J4-2의 「알림으로 알려드려요」는 목표 케이스 |
| 수량 선택 UI | 앱 시안에 없다 | API로만 검증(`items[].quantity`) |
| 마이그레이션 | V157 ~ V163 MySQL 미실행 | 수동 라운드 첫 단계 — 보강 시나리오 DB-01 ~ 03 |
| 동시 실행 | H2에서 잠금을 재현할 수 없다 | 보강 시나리오 DB-04 ~ 11(실 MySQL) |
