1. **돈 → 공통 → 조회** 순. 단계 1 은 과다 · 과소 환불이 PG 로 나갈 수 있는 유일한 경로를 닫는다.

4. **마이그레이션이 없는 단계를 앞에** — 단계 1 ~ 4 는 스키마 변경 0건이라 되돌리기 쉽다. V177 은 단계 5 에서 한 번만 판다.

### 3-1. 도메인 — `OrderClaimService.acceptRejectionDispute` 재작성

현재(`OrderClaimService:1135`)는 `amount` 를 받아 그대로 큐 · `refunded_amount` 에 적고, 미결제 `REJECT_RESHIP` 청구만 `VOID` 한다. 바꿀 것:

| 순서 | 변경 | 참고 코드 |
| --- | --- | --- |
| ① 시그니처 | `acceptRejectionDispute(claimId, adminId, detail, now)` — `amount` 제거 · 반환을 `{ refundTaskId, amount }` 레코드로(응답 · 이력에 쓴다) | — |
| ② 가드 | `type = RETURN ∧ status ∈ {REJECT_HOLD, RESHIP_READY}` — `RESHIPPING` 이후는 409 `CLAIM_STATE_CHANGED` 유지 | 38 설계서 0-4 |
| ③ 금액 | `amount = orderProduct.price × claim.quantity` + **차감 환원분**(⑤) — 귀책 브랜드이므로 반품 배송비 차감 없음 | `ClaimRefundCalculator` 와 같은 단가 출처 |
| ④ 박스 규칙 | `othersOnHold` 판정을 `REJECT_HOLD ∨ RESHIP_READY` 로 넓힌다(남은 재발송 대상이 있으면 청구는 그 건의 것) | `OrderClaimService:1147` |
| ⑤ 청구 처리(남은 건이 없을 때만) | `PENDING → VOID`(지금과 같음) · **`PAID → REFUNDED`**(`charge.refund(now)` + `claimPaymentRepository.requestCancel(paidPaymentId, [PAID], now)` — `releaseAfterCancel`(`:1290`) 과 같은 선점 · 커밋 뒤 집행 경로) · **`DEDUCTED → VOID`** + 청구액을 ③ 에 가산 | `releaseAfterCancel` · `ClaimPaymentService.executeCancel` · 실패분은 `reconcile` 정리 배치 |
| ⑥ 환불 큐 | `enqueueOperatorRefund(group, claimId, amount, DISPUTE_ACCEPTED, detail, adminId, now)` — 지금과 같음 | — |
| ⑦ 클레임 종결 | `closeRejectedByDispute` 조건을 `status IN (REJECT_HOLD, RESHIP_READY)` 로 넓히고 `SET … faultChangedToSeller = true` 추가 | `OrderClaimRepository:170` |
| ⑧ 수량 · 이력 | `addReturnedQuantity` · `markReturnedIfFull` 그대로. 이력 detail 에 「N원 · 근거」 + 「재발송비 결제 취소」 / 「차감 환원 N원」 을 조건부로 덧붙인다 | 38 설계서 7절 #4 ⑦ |

**커밋 뒤 결제 취소 실행** — `releaseAfterCancel` 을 부르는 호출자(교환 철회 · 송장 만료)가 커밋 뒤 `ClaimPaymentService.executeCancel` 을 어떻게 트리거하는지 그 코드를 따라간다. 인용도 같은 방식으로 `AdminClaimService.acceptDispute` 가 트랜잭션 밖에서 호출한다. 결과를 못 받으면 `reconcile` 이 닫는다 — 새 경로를 만들지 않는다.
