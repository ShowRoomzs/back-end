## 36. 어드민 소통 스레드 — 운영팀 1:1 채널 — [v0.40 신설]

대상 화면: `ui-admin-20a-channels.html` (**rev.1 초안**), 상태 3종(브랜드 1:1 1 · 인플루언서 1:1 2). GNB **9 게시물·소통 모니터링 › 소통 스레드**. 짝 파일 `ui-admin-20b-issues`(3자 이슈 스레드)는 **미수령** — 화면은 하나(좌측 탭 이슈 스레드 / 브랜드 / 인플루언서)이고 기획만 두 파일로 나눴으며, 이 섹션은 **브랜드·인플루언서 탭**만 담는다. 상류는 `ui-partner-05-connections`((1) §13) · `ui-studio-04-connections`((1) §14)의 **운영팀 고정 채널**이고, 연동은 계약 관리(§25-3a · §28-7a)다.

**범위 밖** — 이슈 스레드(20b) · 계약 조치(계약 관리) · 재발송 실행(모두싸인) · 첨부 상태 화면((1) §13-7~§13-11 그대로).

### 36-0. 성격 — 운영자의 두 채널 — `FE`·`BE`

| 채널 | 참여자 | 생성 | 근거 파일 |
| --- | --- | --- | --- |
| **1:1 운영팀 채널** | 운영팀 ↔ 브랜드 1곳 / 운영팀 ↔ 인플루언서 1명 | **회원당 1개 · 항상 존재** | 20a(본 섹션) |
| 이슈 스레드 | 브랜드 · 인플루언서 · 운영팀 3자 | **미이행 제출 시 시스템 자동 개설**(§36-8) | 20b `[미수령]` |

| 이 화면에 없는 것 | 이유 |
| --- | --- |
| **「새 대화」** | 채널이 미리 있다. 찾기는 **검색**이다 |
| **이슈 스레드 직접 개설**(구 M3) | 이슈는 미이행 제출로만 열린다 |
| **우측 정보 패널**(1:1 채널) | 판단할 액션이 없는 대화에 300px을 상시 줄 이유가 없다 → 상단 접이식 정보 바(§36-2) |
| **계약 조치** | 처리는 **각 화면에서** 하고 이 화면은 **요청과 결과를 한 대화에 잇는다** — 같은 조치를 두 화면에서 만들지 않는다 |

### 36-1. 화면 구조 — `FE`

| 영역 | 규칙 |
| --- | --- |
| 규격 | 사이드바 240 · 탑바 56 · 본문 패딩 24 · **좌 목록 300** · 스레드 헤더 60 · 입력창 60 · 우 패널 300은 **이슈 스레드에만** |
| 탭 | **이슈 스레드**(기본 진입) / **브랜드** / **인플루언서** — 숫자 배지(의미 미정 §36-9 B-7) |
| 검색 | 브랜드 탭 「브랜드명 · 회원번호 · 담당자」 / 인플루언서 탭 「쇼룸명 · 회원번호」 |
| 목록 항목 | 아바타 · 이름 · 최근 시각 · **보조 줄**(브랜드 `회원번호 · 담당 {이름}` / 인플루언서 `회원번호 · 사업자/개인`) · 최근 메시지 1줄 · 안 읽은 수 |

| 스레드 헤더 | 이름 + `브랜드 · {회원번호} · 담당 {이름} · 운영팀 채널` / `인플루언서 · {회원번호} · 사업자/개인 · 운영팀 채널` |
| 고지 줄 | 「SHOWROOMZ 운영팀 채널 — 상대에게는 **SHOWROOMZ 운영팀**으로만 표시되고 담당자 이름은 보이지 않습니다.」 — 운영자에게 보이는 문구 |
| 입력창 | 첨부 · 입력 · 전송 — (1) §13과 같은 마크업 |

### 36-2. 접이식 정보 바 — `FE`·`BE`

**기본 접힘.** 접혀 있어도 요약 한 줄이 보이고, 펼치면 3칸이 가로로 놓인다. 브랜드·인플루언서는 **같은 3칸 골격**이고 칸 안의 항목만 다르다.

|  | 브랜드 채널 | 인플루언서 채널 |
| --- | --- | --- |
| 요약 줄 | 상태 · 계약(서명 진행중 · 체결) · 공구(진행중) · **미정산** | 상태 · 계약 · 공구 |
| ① 정보 | 회원번호 · 상태 · **담당자(이름 · 연락처)** · 가입일 · `회원 상세 ↗` | 회원번호 · 상태 · **사업자 여부**(+과세 유형) · **업무용 이메일** · 가입일 · `회원 상세 ↗` |
| ② 진행 중 | 계약(서명 진행중 N · 체결 N) · 공구(진행중 N) · **미정산 N건** | 계약 · 공구(진행중 N · 종료 N) · **연결 브랜드 N곳** · `인스타 ↗` |
| ③ 열린 이슈 스레드 | 목록 또는 「없음」 | 동일 |

| 항목 | 규칙 |
| --- | --- |
| 사업자 여부 | **정산 원천징수가 갈린다** — 담당자 대신 이 값을 둔다 |
| 업무용 이메일 | 실제 연락 창구 · 인플루언서 목록과 같은 기준 |
| **인플루언서에 미정산 행 없음** | 인플루언서 몫은 **브랜드 정산에 묶여** 있다 |
| 수치 | **각 모듈의 집계값**을 읽는다 — 이 화면에서 계산하지 않는다 `[집계 대기]` |

### 36-3. 메시지 — 말풍선과 시스템 카드 — `FE`·`BE`

| 종류 | 담는 것 | 표시 |
| --- | --- | --- |
| **말풍선** | 사람의 대화 | 상대 = 이름 + 역할 태그 / 운영자 = 「운영팀 · {이름}」 |
| **시스템 카드** | **절차의 기록** — 요청 · 처리 결과 (이슈 스레드: 미이행 사유 · 답변 기한 · 중재 의견 · 동의/반대) | 가운데 정렬 카드 · 제목 줄 + 본문 + 링크 |

| 항목 | 규칙 |
| --- | --- |
| **나누는 이유** | 절차가 말풍선에 섞이면 이후 대화에 묻히고, 분쟁 때 **「그 안내를 받았는가」**가 흐려진다. 반대 사유도 말풍선이 아니라 **카드로 고정**한다 |
| 카드 톤 | 운영자 조치가 필요한 **요청 = 경고 배경** / 처리 **결과 = 중립**(원칙 ①②) |
| 카드 데이터 | 메시지 타입(`text` / `system`) + 카드 종류 + **참조 객체**(계약번호) + **액션 상태**(전/후 · 시각 · 처리자) |

### 36-4. 운영자 표기 — 안팎이 다르다 — `FE`·`BE`

| 서피스 | 표기 |
| --- | --- |
| 어드민 | **「운영팀 · 김운영」** |
| 파트너센터 · 쇼룸 스튜디오 | **「SHOWROOMZ 운영팀」**만 |

| 항목 | 규칙 |
| --- | --- |
| 이유 | 운영자 개인이 아니라 **회사의 판단**이고, 담당이 바뀌어도 대화가 이어진다 |
| 저장 | 작성 운영자는 **내부 감사용으로 저장**한다 |
| **응답 분리** | 상대 서피스 응답에는 **운영자 개인 식별자를 내리지 않는다** — 화면에서 가리는 것으로는 부족하다 |
| `자동 안내` 태그 | **어드민에서만** 보인다. 상대에게는 일반 운영팀 메시지다 |

### 36-5. 자동 카드 ① — 서명 안내 재발송 요청 — `FE`·`BE`

```
서명 안내 다시 받기
  → 요청자의 운영팀 채널에 요청 카드 자동 등록
  → 운영자가 모두싸인에서 재발송
  → 카드 안 [재발송 완료 알림 보내기]
  → 정해진 문구가 운영자 말풍선으로 자동 전송 · 카드 버튼 자리 = 「✓ 재발송 완료 알림 전송됨 · 시각 · 처리자」
```

| 항목 | 규칙 |
| --- | --- |
| 카드 제목 | 「요청 · 서명 안내 다시 받기」 |
| 카드 본문 | **계약번호** · 공구명 · 「{요청자}이 계약 관리에서 요청」 · **요청 시각** · `계약 상세 ↗` |
| 버튼 | **`재발송 완료 알림 보내기`** + 보조 문구 「모두싸인에서 재발송한 뒤 누르세요」 |
| 버튼 톤 | **보조(흰 배경)** — 경고색 카드 위에 인디고를 얹으면 화면의 주 조치처럼 튄다 |
| **자동 문구** | 「모두싸인에서 서명 안내를 다시 보내드렸습니다. 메일함(스팸함 포함)을 확인해 주세요.」 — 매번 손으로 쓰지 않고, **사람마다 문구가 달라지지 않는다** |
| 전송 형태 | **운영자 말풍선** + `자동 안내` 태그(어드민 전용) |
| **중복 전송 방지** | 버튼 자리가 **전송됨 · 시각 · 처리자**로 굳는다. 전송과 카드 상태 전환은 **한 번에** 일어나야 한다 |
| **계약 관리에 처리 기록 없음** | **2026.09.28 확정** — 계약 상태를 바꾸지 않는 요청이다. v0.36의 `[재발송 처리 기록]`·계약 이력 기재를 대체한다(§25-3a · §28-5a 개정) |
| 버튼의 성격 | **「보냈다」는 운영자의 신고** — 모두싸인 API를 쓰지 않아 실제 재발송을 시스템이 검증하지 못한다 |
| 이후 | 대화는 평소처럼 이어진다 |
| 데이터 | `resendRequest: { contractId, threadId, cardMessageId, requestedBy, requestedAt, notifiedBy?, notifiedAt?, noticeMessageId? }` |

### 36-6. 자동 카드 ② — 계약 직권 취소 결과 — `FE`·`BE`

```
당사자가 운영팀 채널에 대화로 요청 → 운영자가 사정 확인
  → 계약 관리 C6 직권 취소(§28-7a) → 요청 채널에 결과 카드 자동 등록
```

| 항목 | 규칙 |
| --- | --- |
| 요청 | **일반 대화** — 재발송과 달리 자동 등록 카드가 아니다 |
| 결과 카드 | 제목 「계약 직권 취소 처리됨」 · 계약번호 · 공구명 · **사유** · 처리 시각 · 처리자 · 「양측에 통지됐습니다.」 · `계약 상세 ↗` |
| 톤 | **중립** — 취소는 종결이다(원칙 ②) |
| 등록 위치 | `cancel.requestThreadId`가 가리키는 채널. **상대방 채널에도 붙는지는 미정**(§36-9 A-5) |
| 이 화면의 역할 | 처리하지 않는다 — C6에서 처리하면 카드가 **자동으로** 붙는다 |

**자동 카드 ③** — 이행 확인 **미이행 제출** → 이슈 스레드 자동 개설. 20b 소관이다.

### 36-7. 컴포넌트 재사용 · 첨부 — `FE`

목록 아이템 · 말풍선 · 첨부 칩 · 입력창은 **`ui-partner-05-connections`와 같은 마크업**이다. 첨부 2축(20개 · 500MB) · 종류별 클릭 동작 · 전체 다운로드 · 전송 실패 · 첨부만 전송 시 타임스탬프는 **(1) §13-7~§13-11을 그대로 따르며 여기서 재기술하지 않는다.** 새로 생긴 것은 **정보 바 · 고지 줄 · 시스템 카드 · 역할 태그 · 자동 안내 태그**다.

### 36-8. 이슈 스레드 개설 규칙 — 2026.09.28 확정분 — `BE`

시안 규칙 박스가 기재한 확정 사항이다. **화면 상세는 20b 수령 후** 이 섹션에 이어 붙인다.

| 항목 | 규칙 |
| --- | --- |
| 개설 조건 | **정산액 조정이 필요한 경우에만** — 계약 이행 확인에서 **미이행이 제출**돼 정산이 보류될 때 |
| 개설 주체 | **시스템 자동.** 이슈 스레드가 열리는 **유일한 경로**다 |
| 그 밖의 이견 | 게시물 문구 · 고정 지급비 · 일정 등은 **양측이 1:1 스레드에서 직접 해결** — 운영자는 개입하지 않는다 |
| 운영자 직접 개설 | **없다**(구 M3 폐기) |
| 기본 진입 탭 | 이슈 스레드 — **운영자가 결론을 내야 끝나는 건**이 여기 있다 |

> ⚠️ **기존 기술과 4곳이 어긋난다** — §36-9 A-4.
