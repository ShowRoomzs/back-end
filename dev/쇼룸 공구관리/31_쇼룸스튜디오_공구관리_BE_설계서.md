## 0. 먼저 정한 6가지

### 0-1. 스튜디오는 30 설계 위에 선다 — **신규 테이블은 1개**다

30 설계 0-1이 "파트너 API만 먼저 열더라도 테이블은 어드민 판정과 **스튜디오 액션(게시물·연장 응답·이행 확인)까지** 수용하도록 판다"고 했다. 그 결과 스튜디오가 쓰는 컬럼은 거의 다 있다.

| 스튜디오 쓰기 | 쓰는 곳 (30 설계) |
| --- | --- |
| 게시물 작성·제출·수정 | `post` + `group_buy_post` (1-8) |
| 연장 수락·거절 | `group_buy_extension_request.status` · `reject_reason_code` · `reject_memo` · `group_buy.end_at` (1-5 · 3-4) |
| 중단 요청 | `group_buy_change_request` (`requester_type = CREATOR`) (1-6) |
| 이행 확인 | `group_buy_fulfillment_check` (`checker_side = CREATOR`) (1-9) |

**새로 만드는 것은 `group_buy_post_revision` 하나다**(2-6). 승인 후 자유 수정(§29-8)이 확정되면서 **승인받은 원문이 첫 수정에 덮어써지는** 구멍이 생겼고, 30 설계에는 그 구멍을 막을 자리가 없다.

### 0-2. 이 설계의 본체는 **공구 게시물 쓰기**다

§29-5 권한 3분류에서 스튜디오의 「직접 수정」은 **게시물 작성·수정** 하나다. 그런데 이 하나가 준비 게이트 ②를 채우는 유일한 경로다 — **스튜디오 게시물 API가 없으면 모든 공구가 `PREPARING`에 갇힌다**(30 설계 6절 "오픈 승인 · 게시물 API 없이는 공구가 안 열린다").

게시물 쓰기는 상태가 **넷**으로 갈린다.

| 게시물 심사 상태 | 쓰기 | 근거 |
| --- | --- | --- |
| 없음 · `DRAFT` · `REJECTED` | 임시저장 · 제출 | §31-2 · B1 · B3 |
| `PENDING` | **불가** — 취소·재제출도 불가 | 인플 제14조③ · B2 "취소하거나 재제출할 수도 없습니다" |
| `APPROVED` | **즉시 수정** · 재승인 없음 | 인플 제14조⑤ · §29-8 |
| 공구 종결 | **불가** — 원문 보관 | §29-8 · 30 설계 1-8 |

### 0-3. 공구 게시물의 `post.status`는 **소비자 노출 스위치**로만 쓴다

게시물 8종은 저장하지 않고 파생한다(30 설계 1-8 `GroupBuyPostStatus.of`). 그런데 뿌리 테이블 `post`에는 `status` 컬럼이 **NOT NULL로 이미 있고**, 소비자 쪽 코드는 그 값으로 노출을 판정한다.

| 기존 코드 | 판정 |
| --- | --- |
| `Post.isVisibleToConsumer()` | `status == PUBLISHED` |
| `UserPostService.getPostById()` | `isVisibleToConsumer()`가 아니면 404 |
| `PostRepositoryImpl.findPublished()` (피드 3종·추천) | `status = PUBLISHED` |

그래서 공구 게시물의 `post.status`는 **`PUBLISHED` ⇔ 파생 상태가 `EXPOSED`(노출중)** 인 투영값으로 둔다. 쓰는 값은 `DRAFT`(비노출) / `PUBLISHED`(노출) 둘뿐이다 — 30 설계 1-8이 "`DRAFT` / `PUBLISHED` / `DELETED`만 쓴다"로 열어 둔 범위 안이고, `DELETED`는 게시물 삭제가 `[확장 가능]`(§29-8)이라 MVP에서 쓰지 않는다.

| 기각한 안 | 문제 |
| --- | --- |
| `post.status`에 8종을 저장 | 공구를 따라가는 값을 따로 저장하면 어긋난다(30 설계 1-8) |
| `post.status`를 `DRAFT`로 고정 | 소비자 상세·좋아요·신고가 전부 404가 된다 — 24 설계가 **횡단 테이블을 공유하려고** 뿌리를 합쳤는데 그 이유가 무너진다 |
| 숨김에 `SUSPENDED` 사용 | **7일 뒤 원문이 영구 삭제된다**(30 설계 1-8 · `PostLifecycleService.expireOverdueSuspensions`) |
| 새 값 `CLOSED` 추가 | 일반 게시물 enum의 `tabMembers` · `isEditable` · 스튜디오 라벨 switch가 전부 영향을 받는다. 얻는 것은 이름 하나다 |

투영은 **`GroupBuyPostExposure.sync(groupBuy, post)` 한 메서드**가 하고, 노출을 바꾸는 모든 전이가 **같은 트랜잭션**에서 부른다(4-9). 30 설계 1-11의 상품 `groupBuyStatus` 재동기화와 같은 방식이다.

> **갱신(2026-09-26 · 공구 게시물 기능 설계서 4-1)** — 투영식이 넓어졌다. 끝난 공구의 게시물은 **종료 후 3일(72시간) 동안** 마감 상태로 `PUBLISHED`에 남는다.
>
> ```
> PUBLISHED ⇔ of(post, gb) == EXPOSED
>             ∨ (of(post, gb) == CLOSED ∧ post.publishedAt != null ∧ !숨김 ∧ gb.closeType != SUSPENDED
>                ∧ now < gb.endedAt + CLOSED_POST_RETENTION(72h))
> ```
>
> 3일 경과분은 `GroupBuyLifecycleScheduler`의 「마감 게시물 내리기」 단계가 같은 `sync`로 `DRAFT`로 내린다. 마감 중 좋아요는 `GroupBuyPostPolicy.canLike`가 잠근다(해제만).

### 0-4. 가시성은 **내 공구인가** 하나 — 남의 공구는 **404**다

계약과 달리 공구에는 "도착 전" 단계가 없다. 공구는 **체결 트랜잭션 안에서** 생기고(30 설계 0-2), 체결 시점에 인플루언서는 이미 양측 서명을 끝냈다. 그러므로 판정은 한 줄이다.

```sql
group_buy.creator_id = :me
```

다만 **남의 공구는 403이 아니라 404**다(27 설계 1-2와 같은 판단). 공구번호가 `GB-YYYYMMDD-NNN`으로 추측 가능하고(30 설계 1-10), 403은 "이 번호로 누군가의 공구가 있다"를 알려준다 — 경쟁 인플루언서의 거래 존재 여부가 새는 셈이다.

판정은 `CreatorGroupBuyReader.requireMine(creatorId, groupBuyId)` 하나에 두고 **모든 경로가 통과**한다. 리포지토리에 `creator_id` 조건이 없는 스튜디오용 조회 메서드를 두지 않는다.

### 0-5. 같은 공구지만 **응답 구성이 파트너와 다르다** — 덜어내는 것이 더 중요하다

§31-1이 7가지 차이를 적었다. 백엔드에서 남는 것은 **필드 집합의 차이**다(27 설계 0-4와 같은 원칙 — FE가 숨기는 게 아니라 서버가 안 내린다).

| 구분 | 파트너 | 스튜디오 |
| --- | --- | --- |
| 「내가 받는 금액」(`payout`) | 없음 | **있음** — 미보증 고지 포함(§29-9) |
| 최소 준비 물량 · 게이트 ① 확인 수량 | 있음 | **없음** — "브랜드 소관이라 표시하지 않습니다"(B1) |
| `remark`(비고 열) | 있음 | **없음** — §31-1 "목록의 비고 열도 두지 않는다" |
| 직권 중단 소명(`appeal`) | 쓰기 · 읽기 | **없음** — 브랜드↔운영자 사이의 제출물 |
| 상대가 낸 요청의 메모 | — | **없음** — 운영자에게 쓴 글이다(4-6) |
| `orderClosure` | 총·종결·미종결 | + **미종결 단계별 건수**(B7 "배송중 18 · 반품 처리중 6") |
| 종료(`ENDED`) KPI | **`null`**(§30-4) | **잠정치로 내린다**(B7) — 10-1 #4 |
| `permissions` | 8종 | **6종**(4-8) |

**응답 DTO를 파트너와 공유하지 않는다.** 공유하면 언젠가 파트너 전용 필드가 하나 붙고 그게 스튜디오로 샌다(27 설계 4-2).

### 0-6. **공구 게시물이 일반 게시물 경로로 새지 않게 먼저 막는다** — S0 선행

`post` 테이블에 `post_type = GROUP_BUY` 행이 들어오는 순간, **공구를 모르는 기존 경로**가 그 행을 만난다. 지금 코드를 대조한 결과 새는 자리가 넷이다.

| # | 경로 | 현재 | 결과 |
| --- | --- | --- | --- |
| ① | `ShowroomPostService.getMyPost()` → 수정·게시·삭제 | 소유·삭제 여부만 본다 | **일반 게시물 API로 공구 게시물을 수정·삭제**할 수 있다 — 승인대기 잠금 우회 · 사진 첨부 · 원문 삭제 |
| ② | `AdminPostService.suspend()` | `status == PUBLISHED`만 본다 | 노출중인 공구 게시물이 **일반 노출 중지**로 내려가고 **7일 뒤 영구 삭제** |
| ③ | `PostRepositoryImpl.findAdminPosts()` | 타입 조건 없음 | 어드민 일반 게시물 목록에 공구 게시물이 섞인다(②의 입구) |
| ④ | `findPublished()` · `countByCreator_IdAndStatus()` | 타입 조건 없음 | 노출중인 공구 게시물이 **일반 피드 카드 모양**(사진·비율 필수)으로 소비자 피드에 뜬다 · 쇼룸 게시물 수가 늘어난다 |

①~③은 **`post_type = GENERAL` 가드**로 막는다(9절 S0). ④는 소비자 앱의 공구 게시물 노출 설계(24 §9-5 ② "공구 상단 고정 + 일반 최신순")가 나올 때까지 **`GENERAL` 필터를 명시**한다 — 그 설계가 `contentType` 판별자로 두 타입을 함께 내리게 되면 필터를 걷는다.

> **갱신(2026-09-26 · 공구 게시물 기능 설계서 6절)** — ④의 `GENERAL` 필터를 걷었다. `findPublished()`는 `GroupBuyScope`(C1 일반 + 진행 중 공구 · C4 아래 피드 일반 + 마감 게시물 · C4 고정 섹션 진행 중만)를 받고, 공구 게시물은 `contentType = GROUP_BUY` + `groupBuy` 블록으로 나간다. `countByCreator_IdAndStatus()`는 타입을 가리지 않는다(10-2 #14·#15 해소).

그리고 **`GroupBuyPostPolicy` 빈이 반드시 함께 들어가야 한다.** `PostPolicies.of()`는 정책이 없는 타입에 `IllegalStateException`을 던지고, `UserPostService.likePost()`는 게시물 타입과 무관하게 `postPolicies.of(post).canLike(post)`를 호출한다. 공구 게시물이 존재하는데 정책이 없으면 **좋아요 한 번이 500**이 된다.

## 1. 가시성 · 탭 · 정렬

### 1-1. 탭 ↔ 상태 매핑 — **§29-2의 6종을 따른다**

| 탭 코드 | 상태 집합 |
| --- | --- |
| `ALL` | 전체 |
| `PREPARING` | `PREPARING` |
| `READY` | `READY` |
| `IN_PROGRESS` | `IN_PROGRESS`, `SUSPENSION_SCHEDULED` |
| `ENDED` | `ENDED`, `SETTLED` |
| `SUSPENDED` | `SUSPENDED` |

> ⚠️ **시안 A1은 탭이 5개다** — 「종료·정산 3」에 헤어 에센스(중단)가 들어 있다(립밤=종료 · 봄 클렌저=정산완료 · 헤어 에센스=중단). 반면 §29-2는 "목록 탭은 6종이다 — 전체 · 준비중 · 준비완료 · 진행중 · 종료 · **중단**"을 **3서피스 공통**으로 못박았고, 파트너 시안도 중단 탭이 따로 있다. **공통 명세를 따른다**(10-1 #1). 합치기로 확정되면 `CreatorGroupBuyTab`의 매핑만 바뀐다.

**탭 enum을 파트너와 공유하지 않는다** — `CreatorGroupBuyTab`을 따로 둔다. 지금은 매핑이 같지만 위 불일치가 스튜디오 쪽으로 확정되면 두 서피스가 갈린다(27 설계 1-3과 같은 판단).

### 1-2. 정렬 — 「시작일 빠른순」은 **단순 오름차순이 아니다**

시안 A1의 행 순서:

```
진행중  08.14 · 08.16 · 08.18 · 08.19
준비중  08.24   준비완료 08.26   준비중 08.29 · 09.01
종료    07.28   정산완료 07.20   중단 07.10
```

진행 전·진행 중인 공구는 시작일 **오름차순**, 종결 공구는 그 뒤에 시작일 **내림차순**이다. 순수 `start_at ASC`면 07.10 중단 건이 맨 위에 온다 — 끝난 지 한 달 된 공구가 오늘 할 일을 밀어낸다.

| `sort` | 정의 |
| --- | --- |
| `START_AT_ASC` (기본) | ① 종결 여부(비종결 먼저) ② 비종결은 `start_at ASC` ③ 종결은 `start_at DESC` ④ `group_buy_id DESC` |
| `ACTION_REQUIRED_FIRST` | ⓪ **내 조치 필요 여부**(1-3) 먼저 → 이후 `START_AT_ASC`와 같다 |

`(creator_id, status, start_at)` 인덱스(30 설계 1-1)가 첫 두 키를 다 받쳐주지는 못한다. 인플루언서 1명의 공구 수는 수십~수백 건이라 **정렬 비용은 문제가 아니고**, 필터 조건(`creator_id`)이 인덱스를 탄다.

> 30 설계 4-2의 파트너 `START_AT_ASC`도 같은 문제를 가진다(종결 건이 위로). 파트너 시안의 행 순서를 확인해 **같은 정의로 맞추기를 권한다**(10-1 #2).

### 1-3. 「내 조치 필요」 — 정의 하나를 세 곳이 쓴다

시안에 이 값이 세 곳에 나온다 — **GNB 배지**(「4 공구 관리 2」) · **목록 헤더**(「내 조치가 필요한 공구 3건」) · **정렬 옵션**(「내 조치 필요 먼저」).

| 포함 | 조건 | 화면 |
| --- | --- | --- |
| 게시물 작성 필요 | `PREPARING` ∧ 게시물 없음 또는 `DRAFT` | B1 — 체크리스트 ② 경고 톤 |
| 게시물 재등록 필요 | `PREPARING` ∧ `REJECTED` | B3 |
| 숨김 게시물 수정 필요 | 비종결 ∧ `APPROVED` ∧ 숨김 중 | B5a — "고칠 권한은 인플루언서"(§29-3) |
| 연장 응답 필요 | 연장 `PENDING` ∧ `IN_PROGRESS` ∧ `end_at > now` | B6 |
| 이행 확인 필요 | `ENDED` ∧ `CREATOR` 행 없음 | B7 |

| 넣지 않는 것 | 이유 |
| --- | --- |
| 승인대기(B2) · 준비완료(B4) | 공이 운영자·시간에게 있다 |
| 브랜드 중단 요청 검토 중(B10) | "내가 할 조치는 없습니다" |
| 직권 중단 사전통지(B13) | 액션 버튼이 없다(§31-6) |
| 내가 낸 중단 요청 대기 | 운영자 판정 대기 |

**세 곳이 같은 식을 쓴다.** `CreatorGroupBuyActionPredicate`가 QueryDSL `BooleanExpression`을 하나 만들고, `summary`의 카운트와 `ACTION_REQUIRED_FIRST`의 `CASE WHEN` 정렬 키가 그 식을 그대로 쓴다. 두 벌을 두면 배지는 3인데 "먼저" 정렬에서 위에 오는 건 2개인 화면이 된다.

> ⚠️ **시안 안에서 숫자가 갈린다** — A1 목록 헤더는 **3건**, 같은 화면 GNB 배지는 **2**. 위 정의로 A1 데이터를 세면 여름 수분 세럼(미작성) + 수분 토너(반려) + 립밤 3종(종료 · 이행 확인 대기로 가정) = **3**이다. 서버는 **한 값**만 내린다(10-1 #3).

### 1-4. 검색

`keyword` — **공구명(`contract.title`) + 브랜드명(`market` 조인) + 공구번호**. 파트너는 인플루언서 표시명을 검색하는데, 스튜디오에서 검색 대상 상대는 브랜드다.

## 2. 공구 게시물 — 작성 · 제출 · 수정

### 2-1. 엔티티 — 24 설계 §9-2의 `@MapsId` 확장을 따른다

```
post (뿌리)                          group_buy_post (1:1, post_id = PK·FK)
├ post_type = GROUP_BUY              ├ group_buy_id  UNIQUE NOT NULL
├ creator_id  = 공구의 creator_id     ├ title        VARCHAR(100) NOT NULL  (앱 검증 40자)
├ status      = DRAFT / PUBLISHED    ├ review_status DRAFT/PENDING/REJECTED/APPROVED
│               (0-3 노출 투영)       ├ submitted_at · reviewed_at · reviewed_by
├ content     = 본문 (TEXT)           ├ reject_* · hidden_* · unhidden_*
├ aspect_ratio = NULL                 └ last_edited_at        ← 이 설계가 추가(2-6)
└ post_image  = 0행 (사진 없음)
```

- `Post`에 팩토리 `Post.groupBuyDraft(Creator creator, String content)`를 추가한다 — `postType = GROUP_BUY` · `status = DRAFT` · `aspectRatio = null`. 기존 `draft()`/`publish()`는 `GENERAL` 고정이라 손대지 않는다.
- `GroupBuyPost`는 `@OneToOne @MapsId`로 `Post`를 참조한다. **JOINED 상속을 쓰지 않는다**(24 §9-2 — 기존 `Post` 참조 코드가 루트 타입을 쓴다).
- **`post.creator_id`는 요청자가 아니라 `group_buy.creator_id`에서 가져온다.** 요청자가 가시성(0-4)을 통과했으면 둘이 같지만, 소유의 원천을 공구에 두어야 게시물과 공구의 주인이 어긋날 경로가 없다.

**30 설계 V129에 반영할 것** — 30 설계 P1이 아직 머지되지 않았다(현재 최신 마이그레이션 `V123`). `last_edited_at DATETIME(6) NULL` 한 컬럼을 **V129 원안에 넣는다.** P1이 먼저 머지되면 `V132__alter_group_buy_post_add_last_edited_at.sql`로 분리한다.

### 2-2. `GroupBuyPostPolicy` — 정책 인터페이스의 공구 구현

| 메서드 | 공구 규칙 |
| --- | --- |
| `supports()` | `GROUP_BUY` |
| `validateForPublish(post)` | 제목 1~40자 · 본문 1~2,000자 · **사진 0장** — 이 메서드는 **제출(2-4)** 시 호출된다 |
| `validateEditable(post)` | 2-5의 판정 — 심사 상태 × 공구 상태 |
| `canLike(post)` | 파생 상태가 `EXPOSED` |
| `requiresAdDisclosure()` | `true` |

정책 빈은 `group_buy_post` · `group_buy`를 읽어야 하므로 리포지토리를 주입받는다(`GeneralPostPolicy`와 달리 상태가 게시물 밖에 있다).

> ⚠️ **기존 코드의 주석이 기획과 반대다** — `PostPolicy.validateEditable()` 주석 "공구는 **노출중 잠금**", `PostType.GROUP_BUY` 주석 "**노출중 잠금**", 24 설계 §9-3 "공구: 노출중 잠금". 24 설계 이후 인플 제14조⑤가 **"승인·오픈 이후에는 인플루언서가 본문을 수정할 수 있다"**로 확정됐다(§29-8). S0에서 **주석을 고친다** — 다음 사람이 주석을 믿고 잠그면 B4·B5의 "자유롭게 수정할 수 있습니다" 고지가 거짓말이 된다.

### 2-3. 임시저장 — `PUT /v1/creator/group-buys/{id}/post/draft`

```json
{ "title": "여름 수분 세럼, 제가 쓰던 그 조합", "content": "건조한 여름에도…" }
```

| 항목 | 규칙 |
| --- | --- |
| 허용 | 공구 `PREPARING` ∧ 게시물 없음 · `DRAFT` · `REJECTED` |
| 최초 호출 | `post` + `group_buy_post` INSERT (`review_status = DRAFT`) |
| 이후 호출 | 제목·본문 덮어쓰기 |
| 검증 | 제목 ≤ 40자 · 본문 ≤ 2,000자 · **둘 중 하나는 비어 있지 않을 것**(빈 임시저장 방지) |
| 빈 제목 | `''`로 저장 — 컬럼이 NOT NULL이고, 필수 검증은 **제출 시점**의 일이다 |
| 심사 상태 | **바뀌지 않는다.** `REJECTED`를 임시저장해도 `REJECTED` 그대로다 |
| 부수 효과 | 없음 — 이력·알림·리비전 없음 |

**반려 게시물을 임시저장해도 `DRAFT`로 돌리지 않는 이유** — 반려는 "운영자가 지적했고 아직 재등록하지 않았다"는 **사실**이다. `DRAFT`로 돌리면 반려 사유 카드(B3)가 사라지고 게시물 배지가 경고(반려)에서 중립(작성중)으로 내려간다 — 고치는 도중에 **무엇을 고쳐야 하는지가 화면에서 없어진다.**

**동시 최초 저장** — 두 탭에서 동시에 첫 저장을 누르면 `group_buy_post.group_buy_id` UNIQUE가 하나를 떨군다 → 409 `GROUP_BUY_STATUS_CONFLICT`(FE는 다시 조회해 수정 모드로 연다).

### 2-4. 등록하고 검토 요청 — `POST /v1/creator/group-buys/{id}/post/submission`

```json
{ "title": "…", "content": "…" }
```

**저장과 제출을 한 요청으로 받는다.** C4 모달은 임시저장 없이 바로 `[등록하고 검토 요청]`을 누를 수 있다 — 저장 API와 제출 API를 따로 호출하게 하면 둘 사이에 실패가 끼어 **저장은 됐는데 제출은 안 된** 상태가 생기고, 사용자는 제출했다고 믿는다.

| 순서 | 내용 |
| --- | --- |
| 1 | `group_buy` · `group_buy_post` 행을 **`PESSIMISTIC_WRITE`로 잠근다**(2-7) |
| 2 | 허용 확인 — 공구 `PREPARING` ∧ 게시물 없음 · `DRAFT` · `REJECTED` |
| 3 | `GroupBuyPostPolicy.validateForPublish` — 제목·본문 필수 · 상한 |
| 4 | 저장(없으면 INSERT) → `review_status = PENDING` · `submitted_at = now` · 반려 필드는 **보존** |
| 5 | 리비전 `SUBMITTED` append(2-6) |
| 6 | 이력 `POST_SUBMITTED`(CREATOR) — 재등록이면 detail `재등록` |
| 7 | 어드민 통지(오픈 승인 대기열) |

- **공구 상태는 바뀌지 않는다.** 제출은 게이트 ②를 채울 뿐 ③(운영자 승인)이 남아 있으므로 `READY` 판정을 하지 않는다(30 설계 3-2).
- **반려 필드를 지우지 않는다** — 재심사하는 운영자가 "이전에 무엇을 지적했는지"를 봐야 한다. 새 판정이 나면 어드민 API가 덮어쓴다.
- **시작 시각이 지난 `PREPARING`에서도 받는다** — 30 설계 7-2 #2(`startOverdue`) 규칙대로다. 막을지 여부는 그쪽 미결로 함께 확정한다.
- **본문에 대가관계 문구를 넣지 않는다.** 표시광고법 문구는 **렌더링 시점에 타입으로 붙는다**(2-8). 본문에 박으면 인플루언서가 승인 후 수정(2-5)에서 지울 수 있다 — §31-2 "사람이 지울 수 있으면 안 되는 문구".

### 2-5. 승인 후 수정 — `PATCH /v1/creator/group-buys/{id}/post`

```json
{ "title": "…", "content": "…" }
```

| 공구 \ 심사 | `DRAFT`·`REJECTED` | `PENDING` | `APPROVED` |
| --- | --- | --- | --- |
| `PREPARING` | 2-3·2-4 경로 | ❌ 409 `UNDER_REVIEW` | — (승인되면 게이트 판정으로 `READY`) |
| `READY` | — | — | ✅ |
| `IN_PROGRESS` | — | — | ✅ **숨김 중 포함** |
| `SUSPENSION_SCHEDULED` | — | — | ❌ 409 `NOT_EDITABLE` — 아래 |
| 종결 3종 | — | — | ❌ 409 `NOT_EDITABLE` |

- **즉시 반영 · 재승인 없음**(인플 제14조⑤). 심사 상태는 `APPROVED` 그대로다.
- **필수 검증은 제출과 같다** — 제목·본문을 비울 수 없다. 노출 중인 게시물의 제목이 사라지면 안 된다.
- `last_edited_at = now` · 리비전 `EDITED` append · 이력 **없음**(시안 이력에 수정 줄이 없다 — 수정 기록은 리비전이 맡는다).
- **숨김 중 수정 → 어드민 통지**(`POST_EDITED_WHILE_HIDDEN`). §29-8 해제 경로가 "인플루언서가 고치면 운영자가 바뀐 본문을 읽고 해제"인데, **고쳤다는 사실을 운영자가 모르면 숨김이 방치로 끝난다.** 통지만 하고 **해제하지 않는다**(§29-8 규칙 ③ "자동 복귀하면 같은 문구로 되돌려도 다시 열린다").

**중단 예정(`SUSPENSION_SCHEDULED`)에서 잠그는 이유** — 시안 B13의 상태 카드에 `[게시물 수정]`이 **없다**(B5 · B5a · B10에는 있다). 직권 중단 통지는 **통지 시점의 게시물·상품을 근거로** 집행 여부를 판정하는 절차다. 판정 도중에 근거가 바뀌면 "심사 대상이 도중에 바뀌면 안 된다"(인플 제14조③ — 승인대기 잠금의 근거)와 같은 문제가 생긴다. 철회되면 `IN_PROGRESS`로 돌아와 다시 열린다. **시안에서 읽은 규칙이라 기획 확인을 요청한다**(10-1 #13).

> 반대 논리도 있다 — 통지 사유가 **내 게시물 표현**(사유 1호 법령 위반)이면, 고칠 기회를 막는 것이 오히려 집행을 부른다. 다만 인플루언서에게는 소명 절차 자체가 없고(D-4), 이의는 "브랜드를 통해"(B13) 가도록 되어 있다. **D-4가 해소될 때 함께 푼다.**

### 2-6. `group_buy_post_revision` — **승인받은 원문을 지키는 테이블** (신규)

승인 후 자유 수정이 확정되면서 `post.content` · `group_buy_post.title`은 **마지막 값만 남는다.** 운영자가 승인한 원문 A를 인플루언서가 B로 고치면 A는 사라진다. 그런데 A는 세 곳에서 필요하다.

| 필요한 곳 | 이유 |
| --- | --- |
| 인플 제14조⑤ 책임 귀속 | "승인 후 수정한 내용으로 인한 법적 책임은 인플루언서가 부담" — **승인 후에 바뀐 부분**이 무엇인지 보여줄 수 없으면 이 조항을 집행할 수 없다 |
| 숨김 해제 판단(§29-8) | 운영자가 "숨김 이후 무엇이 바뀌었는지"를 대조해야 해제한다 |
| 직권 중단 사유 판정 | 통지 시점 본문이 무엇이었는지 |

| 컬럼 | 비고 |
| --- | --- |
| `revision_id` BIGINT PK | |
| `post_id` BIGINT FK → group_buy_post | |
| `revision_no` INT | 게시물 안에서 1부터 · `UNIQUE (post_id, revision_no)` |
| `kind` VARCHAR(16) | `SUBMITTED`(제출·재제출) / `EDITED`(승인 후 수정) |
| `title` VARCHAR(100) · `content` TEXT | 그 시점 스냅샷 |
| `created_at` DATETIME(6) · `created_by` BIGINT | 크리에이터 id |

- **append-only.** 리포지토리에 수정·삭제 메서드를 두지 않는다. `ON DELETE`는 두지 않는다 — 게시물은 삭제되지 않는다(0-3).
- **임시저장은 기록하지 않는다** — 공개된 적도 심사받은 적도 없는 글이다. 기록 대상은 **운영자가 본 글**(제출)과 **소비자가 본 글**(승인 후 수정)뿐이다.
- **「승인된 판」은 따로 표시하지 않는다** — `PENDING` 동안 수정이 불가하므로, 승인 시점의 원문은 **`reviewed_at` 이전 마지막 `SUBMITTED`** 로 유일하게 정해진다. 컬럼을 두면 같은 사실을 두 번 적는다.
- **스튜디오 API로 열람하지 않는다** — 시안에 수정 이력 화면이 없고 `[근거 대기 ①]` "수정 이력 열람"이 미정이다. 어드민 설계가 읽는다.

| 파일 | 내용 |
| --- | --- |
| `V132__create_group_buy_post_revision.sql` | 위 테이블 + `UNIQUE (post_id, revision_no)` + `INDEX (post_id, created_at)` |

### 2-7. 동시성 — 모든 게시물 쓰기는 **같은 행 잠금**을 탄다

| 경합 | 없으면 생기는 일 |
| --- | --- |
| 임시저장 vs 제출(다른 탭) | 제출이 `PENDING`으로 올린 뒤 늦게 도착한 임시저장이 본문을 덮는다 — **심사 중인 글이 바뀐다**(제14조③ 위반) |
| 제출 vs 어드민 반려 재판정 | 반려 필드를 쓰는 쪽과 읽는 쪽이 엇갈린다 |
| 승인 후 수정 vs 어드민 숨김 | 숨김 이후 수정인지 이전 수정인지가 흐려져 **해제 통지(2-5)가 누락**된다 |

→ 스튜디오의 게시물 쓰기 3종과 어드민의 승인·반려·숨김·해제는 **`group_buy_post` 행을 `PESSIMISTIC_WRITE`로 잠근 뒤** 상태를 읽고 판단한다. 최초 저장처럼 행이 아직 없으면 `group_buy` 행을 잠근다(30 설계 3-2의 게이트 판정과 같은 잠금 순서: **`group_buy` → `group_buy_post`**). 어드민 설계에 이 순서를 넘긴다 — 순서가 뒤집히면 교착이 난다.

**종결과 수정의 경합은 잠그지 않는다** — 23:55:00에 끝난 공구에 23:55:00.3의 수정이 들어가도 리비전에 **시각과 함께** 남는다. 종결 후 원문 보관(§29-8)의 목적은 **분쟁 근거**이고, 리비전이 그 근거를 전부 가진다.

### 2-8. 대가관계 표시 · 판매자 정보 — **저장하지 않고 서버가 조립한다**

```
유료 광고 포함 · ○○ 브랜드로부터 대가를 받아 진행하는 공동구매입니다
```

- `GroupBuyDisclosure.text(brandName)` **한 곳**에서 만든다. 스튜디오 모달 미리보기(C3·C4)와 소비자 앱 렌더링이 **같은 메서드**를 쓴다 — 법정 문구가 두 벌이면 한쪽이 반드시 어긋난다(30 설계 4-4 `fixedFee.displayText`와 같은 이유).
- **조사 문제** — "브랜드**로부터**"는 받침 없는 이름에만 맞다("△△ 코스메틱**으로부터**"). 템플릿이 조사를 이름에 붙이지 않는 문형이어야 한다. 법무 확인 대상 문구라 **문형 확정 전까지 받침 판별 유틸로 처리**하고 10-2 #7에 올린다.
- **판매자 정보**(상호·사업자등록번호·교환·반품 안내)는 소비자 렌더링 시점에 브랜드 정보로 붙는다. 스튜디오 응답에는 **"자동 표기된다"는 사실만**(`sellerInfoAutoAttached: true`) 싣고 값은 내리지 않는다 — 이 화면에서 쓸 곳이 없다.
- **상품·가격**은 `contract_item`에서 읽는다. `group_buy_post_product`를 만들지 않는다(30 설계 1-8).

### 2-9. 노출 투영 — `GroupBuyPostExposure.sync`

```java
// 공구 게시물의 post.status를 파생 상태에 맞춘다. 노출을 바꾸는 모든 전이가 같은 트랜잭션에서 호출한다.
PostStatus target = GroupBuyPostStatus.of(post, groupBuy) == EXPOSED ? PUBLISHED : DRAFT;
if (post.getStatus() != target) post.changeGroupBuyExposure(target, now);  // 최초 PUBLISHED 때만 publishedAt
```

| 호출 지점 | 소유 설계 | 결과 |
| --- | --- | --- |
| 스케줄러 오픈 | 30 · 3-3 | `PUBLISHED` · `published_at` 최초 기록 |
| 스케줄러 종료 · 조기 마감 승인 · 중단 승인 · 직권 중단 집행 | 30 · 3-3 / §32 | `DRAFT` |
| 숨김 / 해제 | §32 | `DRAFT` / `PUBLISHED` |
| 직권 중단 통지 · 철회 | §32 | **변화 없음** — 중단 예정도 노출중이다(B13 "예고만으로 게시물이 내려가지 않습니다") |
| 스튜디오 쓰기 전부 | 이 설계 | **변화 없음** |

**`published_at`은 재노출해도 갱신하지 않는다** — `Post` 주석 "게시일은 처음 세상에 나온 때다"를 따른다. 숨김 해제 후 피드 정렬이 튀지 않는다.

**스튜디오가 호출하지 않는데 여기서 정하는 이유** — 30 설계 1-8이 "공구 게시물의 `post.status` 쓰기 규칙은 스튜디오 설계 소관"으로 넘겼다. 규칙은 여기서 정하고, 호출은 전이를 소유한 설계(30 · §32)가 한다. **30 설계 P3(스케줄러)가 이 메서드를 부르지 않으면 오픈된 공구의 게시물이 소비자에게 404다** — P3의 선행 조건으로 올린다(9절).

### 4-3. `readiness` — 게이트 3개를 **내 관점으로** 판정한다

§29-4 "각 줄에 주체를 적고 **내 차례인 줄만 경고 톤**". 같은 게이트라도 파트너와 스튜디오에서 경고가 켜지는 줄이 다르므로 **서피스가 판정한다.**

| 게이트 | `actorType` | `state` 판정 (스튜디오) |
| --- | --- | --- |
| ① 최소 물량 | `SELLER` | `DONE`(확인 시각만) / `WAITING` — **수량은 내리지 않는다** |
| ② 내 게시물 | `CREATOR` | 없음·`DRAFT`·`REJECTED` → **`MY_TURN`** / `PENDING`·`APPROVED` → `DONE` |
| ③ 오픈 승인 | `ADMIN` | 미제출 → `WAITING` / `PENDING` → `IN_REVIEW` / `APPROVED` → `DONE` / `REJECTED` → `WAITING`(재등록 후 다시 검토) |

`tone`은 `MY_TURN`일 때만 `warning`이다. B2 "내 할 일이 끝나 경고 톤이 사라진다"가 이 판정이다.

**반려되면 ②가 `MY_TURN`으로 돌아간다** — B3 체크리스트 "! 내 공구 게시물 재등록 · 반려 사유 반영 필요". ②의 `done`을 `submitted_at IS NOT NULL`로 판정하면 반려 뒤에도 ✓가 남는다.

### 4-4. 등록 마감일 — **역산은 서버가 한다**

§31-2 "시작일만 알려주면 승인 SLA(영업일 3일)를 모르는 인플루언서가 시작 전날 등록해 공구를 못 여는 일이 생긴다".

| 필드 | 계산 |
| --- | --- |
| `post.expectedReviewDate` | `addBusinessDays(submittedAt의 날짜, SLA)` — 제출일은 세지 않는다 |
| `readiness.registrationDeadline` | `addBusinessDays(D, SLA) < start_at의 날짜`를 만족하는 **가장 늦은 D** — 승인이 **시작일 전날까지** 나야 한다 |
| `readiness.registrationOverdue` | `today > registrationDeadline` ∧ 게이트 ② 미완료 |
| `readiness.reviewSlaBusinessDays` | 설정값 `groupbuy.open-review.sla-business-days=3` — `[근거 대기 ⑦]` |

**B2가 기준식을 준다** — "08.18 21:14 제출 · 영업일 3일 · **08.21 예정**" = 수(1)·목(2)·금(3). 같은 식으로 시작일 08.24(월)에서 역산하면 금요일 08.21까지 승인이 나야 하므로 **등록 마감은 08.18(화)** 이다.

> ⚠️ **시안 B1의 "늦어도 2026.08.20까지"는 이 식과 맞지 않는다** — 08.20(목)에 제출하면 예상 승인은 08.25(화)로 시작일을 넘긴다. **B2의 식을 기준으로 삼고** B1 예시값 정정을 요청한다(10-1 #5). 서버가 계산하므로 FE가 날짜를 지어낼 일은 없다.

**영업일 계산기는 공용으로 둔다** — `BusinessCalendar`(`global/util`). 저장소에 아직 없고(`영업일`은 표시용 정수 설정값뿐이다), 30 설계·어드민 설계도 **통지일 +3영업일**(제17조②④)을 계산해야 한다. 한 곳에 두지 않으면 등록 마감과 소명 기한이 서로 다른 달력을 쓴다.

| 항목 | 처리 |
| --- | --- |
| 주말 | 토·일 제외 |
| 공휴일 | 설정 목록 `showroomz.business-calendar.holidays`(날짜 배열) — **출처 미정**(10-2 #6) |
| 시간대 | `Asia/Seoul` |

### 4-5. `payout` · `sales` · `settlement` — 금액 블록의 상태별 규칙

| 상태 | `payout` (내가 받는 금액) | `sales` · `basis` | `settlement` |
| --- | --- | --- | --- |
| `PREPARING` · `READY` | ✅ 고정 지급비 + 리워드 안내 | `null` | `null` |
| `IN_PROGRESS` · `SUSPENSION_SCHEDULED` | ✅ + `salesReward`(잠정) | `LIVE` | `null` |
| `ENDED` | **`null`** | **`PROVISIONAL`** | `null` |
| `SETTLED` | `null` | `SETTLED` | ✅ |
| `SUSPENDED` | `null` | `AT_SUSPENSION` | `null` |

**`payout` — 종결 3종에서 `null`** — 시안 B7~B12 · B8 · B9에 「내가 받는 금액」 카드가 없다. 종결 후 금액은 KPI(`sales`)와 정산 블록이 말한다. 27 설계 0-5와 같이 **FE가 숨기지 않고 서버가 안 내린다.**

```json
"payout": {
  "fixedFeeAmount": 1200000,
  "salesReward": { "amount": 762240, "basis": "LIVE" },
  "platformGuaranteed": false,
  "disputeChannel": { "threadId": 4012 }
}
```

- `platformGuaranteed: false` — §29-9 "「내가 받는 금액」 카드에 미보증 고지 필수 · 계약 관리 §27-5와 **같은 문장**". 문장은 FE 상수이고 서버는 **분기 값**을 준다(27 설계 4-3과 같은 필드).
- `disputeChannel.threadId` — 미보증 고지의 "이슈 스레드에서 운영자 중재를 요청할 수 있습니다"가 갈 곳. 계약 설계와 같이 **PAIR 스레드 id**를 내린다(10-2 #9).
- **공제 계산을 하지 않는다** — §31-7 · 시안 "공제 전 금액 · 실지급액은 정산 관리". `withholdingType`도 싣지 않는다 — 계약 상세에 이미 있고 이 화면에서 쓰지 않는다.

**`sales.basis = PROVISIONAL` — 파트너와 반대 결정이다.** 30 설계는 §30-4 "종료 화면에 KPI를 두지 않는다 — 잠정치가 지급액으로 오해된다"를 따라 `ENDED`에서 `null`을 내렸다. 그런데 스튜디오 B7은 "판매 실적(잠정) · **확정 시 변동**"을 그렸고, 머리말이 이 화면의 주제를 **"왜 아직 리워드가 확정되지 않는가"**로 적었다. §30-4는 **파트너 명세**이고 §29 공통에는 이 규칙이 없다. **스튜디오 시안을 따르되 `basis`로 잠정임을 못박고** 기획 확인을 요청한다(10-1 #4).

**`sales.ordersSinceHidden`** — B5a "주문 142 · **숨김 이후 0건**". 숨김이 판매에 준 영향을 인플루언서가 봐야 수정을 서두른다. 판매 포트에 `countOrdersSince(groupBuyId, since)`를 추가한다(8-1). 숨김이 아니면 `null`.

**`settlement`(B8)**

```json
"settlement": { "settledAt": "2026-08-24T11:00", "fixedFeeAmount": 600000,
                "confirmedReward": 867672, "totalBeforeDeduction": 1467672 }
```

`confirmedReward`는 정산 모듈이 확정한 값을 **그대로** 받는다(30 설계 5-2). `totalBeforeDeduction`은 두 값의 단순 합이고 **"공제 전"**이라는 이름에 의미를 싣는다 — 고정 지급비는 브랜드 직접 지급이라 **실제로 받았는지와 무관한 계약 금액**이다.

### 4-6. 상대방 정보 — **어디까지 내리는가**

| 블록 | 내린다 | 내리지 않는다 | 이유 |
| --- | --- | --- | --- |
| `activeRequest`(브랜드 요청) | 유형 · 사유 코드·라벨 · 요청 시각 · 요청자 | **메모** | 메모는 **운영자에게 쓴 글**이다(C2·C4 "운영자에게 전달할 내용"). 상대에게 보이는 줄 모르고 쓴 글을 노출하면 다음부터 운영자에게 사실을 적지 않는다 |
| `activeRequest`(내 요청) | 전부 | — | 내가 쓴 글 |
| `closure.decisionReason` | ✅ | — | 운영자가 **양측에** 쓰는 결론(M2 "상대에게는 처음 듣는 결론") |
| `adminSuspension` | 사유 호 · 통지 본문 · 집행 예정 · 통지 시각 | **소명 기한 · 소명 내용 · 첨부** | 소명은 브랜드↔운영자 절차다(§29-7 · D-4) |
| `readiness` 게이트 ① | 확인 시각 · 브랜드명 | **수량** | 0-5 |
| `afterEnd.fulfillment.theirs` | 결과 · 확인 시각 · 자동 여부 · 사유 | — | 브랜드의 미이행 사유는 **3자 스레드의 첫 글**이라 어차피 내가 읽는다 |

> ⚠️ **메모 비노출은 시안과 확인이 필요하다** — B10 "요청 사유 · **재고 소진 · 추가 생산 불가**"가 「사유 라벨 · 메모」로 읽힌다. 다만 **"재고 소진"은 브랜드 중단 사유 코드에 없다**(§29-2 "재고 소진은 중단이 아니라 조기 마감이다" — 30 설계 1-6). 예시 데이터 자체가 규칙과 어긋나 있어 메모 노출 의도로 단정할 수 없다. **비노출로 집행**하고 10-1 #7에 올린다.

**조기 마감 요청도 `activeRequest`로 내린다** — 스튜디오 시안에 브랜드 조기 마감 요청 **수신 화면이 없다.** 그러나 조기 마감은 인플루언서의 **남은 판매일을 줄이는** 요청이고, 중단 요청을 B10으로 알리는 이유("요청 소식만 듣고 멈춰버린다")가 그대로 적용된다. 값은 내리고 화면 추가를 요청한다(10-1 #10).

### 4-7. `afterEnd.fulfillment` — 확인의 방향이 반대다

```json
"fulfillment": {
  "mine":   null,
  "theirs": { "result": "FULFILLED", "reason": null, "checkedAt": "2026-09-01T09:12", "auto": false },
  "myTarget":    { "party": "BRAND",   "duties": ["ORDER_DELIVERY", "FIXED_FEE_PAYMENT"] },
  "theirTarget": { "party": "CREATOR", "duties": ["SHOWROOM_POST", "FEED", "REELS", "STORY"],
                   "counts": { "feed": 1, "reels": 1, "story": 3 } },
  "dueAt": "2026-09-03T23:59",
  "autoConfirmOnTimeout": false,
  "onHold": false, "threadId": null, "resolvedAt": null
}
```

- **`mine` = 내가 브랜드를 확인한 결과**(`checker_side = CREATOR`), **`theirs` = 브랜드가 나를 확인한 결과**. 30 설계 4-6 "확인 대상은 상대의 의무다"의 스튜디오 쪽이다.
- `theirTarget.counts`는 `contract.content_*_count`. B7 "쇼룸 공구 게시물 · 인스타그램 피드 1 · 릴스 1 · 스토리 3".
- **`autoConfirmOnTimeout`을 반드시 내린다.** 시안 B7·C5가 "기한까지 답하지 않으면 **이행으로 처리되어 정산이 자동으로 진행됩니다**"라고 말하는데, 30 설계 1-9가 이 규칙을 **D-1(약관 근거 없음) 때문에 스위치로 꺼 두었다.** 스위치가 꺼진 채 이 문구가 나가면 **인플루언서가 "놔두면 이행"이라 믿고 문제를 제기하지 않는다** — 불리한 쪽으로 틀린 안내다. FE는 이 값으로 문구를 고른다.
- `onHold` = `mine` 또는 `theirs`가 `UNFULFILLED` ∧ `resolvedAt IS NULL` — 30 설계 1-9의 파생식.
- `threadId` — 미이행 시 열린 3자 스레드(B12 `[연결·소통 열기]`).

**고정 지급비 지급 사실을 싣지 않는다** — C5·C6 모달의 "현재 상황 · 지급비 **08.21 입금 완료**"는 `contract.fixed_fee_paid_at`(브랜드 자기 신고)을 입금 사실로 바꿔 쓴 것이다. §29-9 "「지급 완료」 배지를 표시하지 않는다"와 27 설계 4-4("`PAID`라는 이름을 쓰지 않는다 — 브랜드 편에서 거짓말을 한 셈이 된다")에 정면으로 걸린다. 게다가 **이 모달은 인플루언서가 "브랜드가 지급했는가"를 판단하는 자리**다 — 판단 대상의 답을 화면이 브랜드 신고로 미리 채우면 확인이 검증력을 잃는다(§29-10 "자기 이행을 스스로 체크하는 방식은 검증력이 없다"). 받았는지는 **내 계좌가 안다**(시안 머리말). 10-1 #9.

### 4-8. `permissions` — 스튜디오 6종

| 필드 | 조건 |
| --- | --- |
| `canWritePost` | `PREPARING` ∧ 게시물 없음 · `DRAFT` · `REJECTED` — 임시저장과 제출이 같은 조건 |
| `canEditPost` | `APPROVED` ∧ 공구 `READY` · `IN_PROGRESS`(숨김 포함) |
| `canRespondExtension` | 연장 `PENDING` ∧ `IN_PROGRESS` ∧ `now < end_at` |
| `canRequestSuspension` | `IN_PROGRESS` ∧ `PENDING` 중단·조기 마감 요청 없음(요청자 무관) ∧ 숨김 아님 |
| `canCheckFulfillment` | `ENDED` ∧ `CREATOR` 행 없음 |
| `canOpenPairThread` | 계약 `connection`의 스레드가 있음 |

**실행 API는 같은 판정 메서드(`CreatorGroupBuyPermissionPolicy`)를 다시 호출해** 409로 막는다 — 버튼 판정과 집행 판정이 한 메서드라 어긋날 수 없다(30 설계 4-5).

**중단 요청이 `READY`에서 불가인 이유** — 스튜디오 머리말이 "요청할 수 있는 시점은 **진행중뿐**이다 — 시작 전에는 판매가 없어 중단할 대상이 없고, 조건을 무르는 일은 새 계약의 몫"으로 명시했다. 브랜드는 `READY`에서도 받는데(30 설계 4-6 C4) **스튜디오는 시안이 좁혔고 그 근거가 명시돼 있어** 따른다. 두 서피스의 비대칭은 10-1 #11에 기록한다.

**숨김 중 중단 요청 불가** — 파트너의 요청 차단 조건(30 설계 4-5 "숨김이 풀린 뒤에")과 같게 둔다. 시안 B5a의 액션도 `[게시물 수정]`·`[스레드 열기]`뿐이다. 숨김 중에 상품 하자를 발견했다면 **스레드 → 운영자 직권 중단** 경로가 남는다(30 설계 7-2 #13과 같은 판단).

**연장 대기 중 중단 요청은 가능** — B6 "연장 응답과 별개로 공구 중단은 언제든 요청할 수 있습니다". 연장 요청은 `group_buy_change_request`가 아니라 별 테이블이라 생성 컬럼 UNIQUE에 걸리지 않는다.

`canViewContract`는 두지 않는다 — 공구가 있으면 계약은 체결완료이고, 체결완료 계약은 항상 「도착한 계약」이다(27 설계 1-1). 링크 대상 `GET /v1/creator/contracts/{contractId}`가 스스로 판정한다.

### 4-9. `timeline` · `startOverdue`

- 일수 계산은 `Contract.periodDays()`와 같은 **양끝 포함 일자 계산**, 서버 `now`(Asia/Seoul) 기준 — 30 설계 4-4와 같다.
- `originalEndAt` = `contract.group_buy_end_at`. 연장 수락 뒤 B4d류 "8일 → 15일" 표기의 원본.
- `startOverdue` — 30 설계 7-2 #2. `PREPARING` ∧ `now >= start_at`. B1·B3 배너 문구가 "시작일에 열립니다"에서 "시작 시각이 지났습니다"로 바뀌어야 한다 — 문구는 FE.
- `post.hidden.hiddenDays` — B5a "게시물 숨김 **2일차**" · 상태 카드 "숨김 경과 2일". 공구 기간과 같은 양끝 포함 계산.
- `adminSuspension.businessDaysUntilExecution` — B13 "집행까지 **3영업일**". `BusinessCalendar`(4-4)로 계산한다. 헤더의 "D-3"은 FE가 같은 값으로 그린다.

## 5. 쓰기 — 연장 응답 · 중단 요청 · 이행 확인

### 5-1. 연장 수락 — `POST /{id}/extension/acceptance`

바디 없음. **불가역**(§31-3 C1).

```sql
-- ① 요청 행: PENDING → ACCEPTED
UPDATE group_buy_extension_request
   SET status='ACCEPTED', responded_at=:now, response_actor_type='CREATOR'
 WHERE group_buy_id=:gid AND status='PENDING';

-- ② 공구 종료일: 30 설계 3-4의 조건부 UPDATE 그대로
UPDATE group_buy SET end_at=:afterEndAt
 WHERE group_buy_id=:gid AND creator_id=:me
   AND status='IN_PROGRESS' AND end_at=:beforeEndAt AND end_at > :now;
```

| 결과 | 처리 |
| --- | --- |
| ① 0행 | 409 `GROUP_BUY_EXTENSION_NOT_PENDING` — 이미 응답했거나 만료 |
| ② 0행 | **트랜잭션 롤백** → `end_at <= now`면 409 `GROUP_BUY_EXTENSION_RESPONSE_CLOSED`, 아니면 `GROUP_BUY_STATUS_CONFLICT` |
| 성공 | 이력 `EXTENSION_ACCEPTED`(detail "종료일 {새 종료}로 변경") · 브랜드 통지 |

- **`end_at > :now`가 수락 기한 = 현재 종료 시각**(§29-6)을 서버에서 보장한다. 23:54:59 수락과 23:55:00 스케줄러 종료가 겹치면 **하나만** 통과한다(30 설계 3-4).
- **② 실패 시 ①도 되돌린다** — 요청은 `ACCEPTED`인데 종료일이 안 바뀐 상태가 가장 나쁘다. 스케줄러가 곧 `EXPIRED`로 닫는다.
- **상품 재동기화·게시물 투영은 필요 없다** — 상태가 바뀌지 않는다.
- **리워드율·고정 지급비는 건드리지 않는다** — 원래 계약 값이고 공구가 복사하지 않는다(30 설계 0-3). C1 고지 "연장으로 늘어나지 않습니다"는 구조적으로 참이다.
- **30일 상한을 다시 검사하지 않는다** — 요청 시점에 검사했고(30 설계 4-6), 요청 이후 `start_at`은 불변이며 `end_at`은 ②의 조건(`= beforeEndAt`)으로 고정돼 있다.

**`SUSPENSION_SCHEDULED`에서는 응답할 수 없다** — B13에 액션이 없고, ②의 `status = 'IN_PROGRESS'`가 막는다. 통지가 **철회되면** `IN_PROGRESS`로 돌아와 다시 응답할 수 있다(기한이 남아 있다면). 통지가 **집행되면** 대기 중인 연장을 `EXPIRED`로 닫는 것은 어드민 집행 트랜잭션의 몫이다 — 30 설계 3-3 `end`가 하는 일을 집행에도 넣으라고 **어드민 설계에 넘긴다**(10-2 #3).

### 5-2. 연장 거절 — `POST /{id}/extension/rejection`

```json
{ "reasonCode": "NEXT_SCHEDULE_BOOKED", "memo": "9월 첫 주에 다른 공구가 잡혀 있어요." }
```

| 항목 | 규칙 |
| --- | --- |
| 허용 | `canRespondExtension` — **수락과 같은 기한**(`end_at > now`) |
| 사유 | **선택**(§31-3 C2 "사유 선택") |
| `ETC` | 메모 **필수** — 시안 옵션이 "기타(**직접 입력**)"다 |
| 메모 | 선택 · 1,000자 · "브랜드에게 남길 메모" |
| 처리 | `status = REJECTED` · `reject_reason_code` · `reject_memo` · `response_actor_type = CREATOR` |
| 부수 효과 | 이력 `EXTENSION_REJECTED` · 브랜드 통지 · **공구 상태·종료일 불변** |

**거절 사유 4종** (`ExtensionRejectReason`)

| enum | 화면 |
| --- | --- |
| `NEXT_SCHEDULE_BOOKED` | 다음 일정이 잡혀 있음 |
| `CONTENT_PLAN_MISMATCH` | 콘텐츠 계획과 맞지 않음 |
| `TERMS_RENEGOTIATION` | 조건 재협의 필요 |
| `ETC` | 기타(직접 입력) |

**거절에도 기한을 건다** — 기한이 지나면 스케줄러가 이미 `EXPIRED`로 닫았다. 같은 요청에 "만료"와 "거절"이 둘 다 기록되면 30 설계 1-5가 구분한 **"거절당했다"와 "응답이 없었다"**가 흐려진다. `WHERE status='PENDING'` 조건부 UPDATE가 둘 중 하나만 남긴다.

**거절 메모는 브랜드에게 보인다** — "브랜드에게 남길 메모"라는 라벨이 수신자를 밝혔다. 4-6의 "운영자에게 쓴 메모는 상대에게 내리지 않는다"와 모순이 아니다 — **라벨이 수신자를 정한다.**

> ⚠️ C2 고지 "브랜드가 **다른 조건으로 다시 요청할 수 있습니다**"는 §29-6 "공구당 1회 · 수락되든 거절되든 기회는 소진되고 **재요청 경로가 없다**"와 충돌한다. 30 설계가 UNIQUE로 1회를 집행한다(1-5) — **이 문구는 거짓 안내**가 된다(10-1 #6).

### 5-3. 공구 중단 요청 — `POST /{id}/suspension-request`

```json
{ "reasonCode": "DELIVERY_FAILURE", "memo": "종료 후 3일이 지났는데 18건이…" }
```

| 검증 | 실패 |
| --- | --- |
| `canRequestSuspension`(4-8) | 409 `GROUP_BUY_ACTION_NOT_ALLOWED` |
| `reasonCode` 6종 | 400 |
| `memo` **필수** · 1,000자 | 400 — 시안 C7 "운영자에게 전달할 내용 **\***" |
| 생성 컬럼 `pending_group_buy_id` UNIQUE 위반 | 409 `GROUP_BUY_REQUEST_ALREADY_PENDING` — 브랜드 요청과 동시에 들어온 경우 포함 |

- INSERT `request_type = SUSPEND` · **`requester_type = CREATOR`** · `status_at_request = IN_PROGRESS` · 판매 스냅샷(포트가 있으면).
- 공구 상태 **불변**(제16조② "요청만으로 판매가 즉시 중단되지 않는다"). 이력 `SUSPENSION_REQUESTED`(CREATOR) · 어드민 통지 · **브랜드 통지**(30 설계 5-4 "+ 인플루언서 요청이면 브랜드").
- **메모를 필수로 받는 이유** — 브랜드 중단 요청은 `ETC`일 때만 메모가 필수다(30 설계 4-6). 스튜디오는 항상 필수다. C7 "브랜드와 먼저 스레드에서 협의했다면 그 내용도 함께 적어주세요 — **운영자가 판단하는 근거가 됩니다**". 인플루언서 요청은 **상대(브랜드)의 이행 문제를 주장하는 경우가 대부분**이라(사유 6종 중 4종) 운영자가 사실을 확인할 재료가 필요하다.

**인플루언서 중단 사유 6종** (`CreatorSuspensionReason`) — 30 설계 7-2 #10이 "스튜디오 설계로 이월"한 값

| enum | 화면 |
| --- | --- |
| `PRODUCT_DEFECT` | 상품에 문제가 있어 추천을 이어갈 수 없음 |
| `DELIVERY_FAILURE` | 배송 지연 · 미발송이 계속됨 |
| `CONSUMER_COMPLAINTS` | 소비자 불만이 반복적으로 접수됨 |
| `BRAND_UNREACHABLE` | 브랜드와 연락이 되지 않음 |
| `PERSONAL_REASON` | 개인 사정으로 진행이 어려움 |
| `ETC` | 기타(직접 입력) |

**브랜드 사유 enum과 분리한다** — 겹치는 값이 없고, 합치면 C7에 "가격·조건 오기" 같은 브랜드용 선택지가 뜰 수 있는 구조가 된다(27 설계 5-1 거절 사유와 같은 판단). `reason_code` 컬럼은 공유하되 해석은 `requester_type`이 정한다.

> ⚠️ 시안 머리말 `[근거 대기 ⑥]`이 "인플루언서 발신 중단의 **사유 구분 값과 남용 방지 장치**"를 미정으로 둔 반면 C7 모달은 6종을 그렸다. **시안 6종으로 잠정 집행**한다 — 컬럼이 VARCHAR라 값이 바뀌어도 스키마 변경이 없다(10-2 #4).

**`PERSONAL_REASON`의 무게** — 이 사유로 중단되면 **브랜드는 남은 판매 기간을 잃고, 고정 지급비는 회수되지 않는다**(§29-6). 변호사 답변 8번이 "인플루언서 귀책이면 환불 처리가 바람직"을 권고했고 시안 D-3이 단서 추가 여부를 묻는다. 서버는 사유 코드를 **통계로 남기는 것**까지만 하고 금전 처리를 하지 않는다 — 고정 지급비는 애초에 플랫폼을 지나가지 않는다(§29-9).

### 5-4. 계약 이행 확인 — `POST /{id}/fulfillment-check`

```json
{ "result": "UNFULFILLED", "reason": "공구 종료 후 3일이 지났는데 18건이 아직 배송 시작되지 않았습니다…" }
```

30 설계 4-6과 **같은 서비스 메서드**를 `checker_side = CREATOR`로 호출한다. 스튜디오 컨트롤러가 따로 구현하지 않는다 — 불가역·스레드 개설·보류 파생 규칙이 두 벌이 되면 한쪽만 고쳐진다.

| 항목 | 규칙 |
| --- | --- |
| 허용 | `canCheckFulfillment` |
| `UNFULFILLED` | `reason` 필수(2,000자) → **같은 트랜잭션에서** 3자 스레드 개설(첫 글 = `reason`) → `thread_id` 저장 → 정산 보류(파생) |
| 중복 | `UNIQUE(group_buy_id, checker_side)` 위반 = 409 `GROUP_BUY_FULFILLMENT_ALREADY_CHECKED` |
| 이력 | `FULFILLMENT_CONFIRMED` / `FULFILLMENT_DISPUTED` (CREATOR) |
| 통지 | 브랜드 · (미이행이면) 운영자 |
| 응답 | `{ result, checkedAt, threadId }` — B12 `[연결·소통 열기]` |

**스레드 포트 없이 배포하지 않는다**(30 설계 5-3 · 6절 P7과 같은 조건). 미이행 제출이 스레드를 못 열면 "첫 글로 등록되었습니다"(B12)가 거짓이 된다.

### 6-2. 이력 화이트리스트 — **쿼리에서 거르고, detail은 이벤트별로 정한다**

`group_buy_history`의 `detail`은 파트너 화면 문구에 맞춰 적힌다(30 설계 1-4). 그대로 내리면 **브랜드에게 쓴 문장**이 인플루언서에게 간다. 그래서 이벤트마다 **내릴지 · detail을 내릴지**를 따로 정한다.

| 이벤트 | 내림 | detail | 시안 문구 |
| --- | --- | --- | --- |
| `CREATED` | ✅ | — | 공구 생성 · 계약 조건 상속 · 시스템 |
| `STOCK_CONFIRMED` | ✅ | **❌ 버림** | 브랜드 준비 물량 확보 확인 · ○○ 브랜드 |
| `POST_SUBMITTED` | ✅ | ✅ | 게시물 등록 · 운영자 검토 요청 |
| `OPEN_APPROVED` · `OPEN_REJECTED` | ✅ | ✅(반려 사유 라벨) | 운영자 오픈 승인 반려 · 표시 · 광고 기준 |
| `OPENED` · `ENDED` | ✅ | — | 공구 시작 · 게시물 노출 시작 / 공구 종료 |
| `POST_HIDDEN` · `POST_UNHIDDEN` | ✅ | ✅(사유 라벨) | 운영자 게시물 숨김 · 화장품법 표현 지적 |
| `EXTENSION_*` 4종 | ✅ | ✅ | 브랜드가 기간 연장 요청 · +7일 |
| `SUSPENSION_REQUESTED` | ✅ | **사유 라벨만** — 메모 버림 | 브랜드 중단 요청 · 재고 소진 |
| `EARLY_CLOSE_REQUESTED` | ✅ | 사유 라벨만 | (시안 없음 — 4-6) |
| `*_REQUEST_REJECTED` · `SUSPENDED` · `EARLY_CLOSED` | ✅ | ✅ | 공구 중단 · 요청 승인 |
| `SUSPENSION_NOTICED` · `SUSPENSION_WITHDRAWN` | ✅ | ✅(호 라벨) | 운영자 직권 중단 사전 통지 · 법령 위반 우려 |

| `FULFILLMENT_*` | ✅ | ✅ | |

- 화이트리스트와 detail 정책을 `CreatorGroupBuyHistoryPolicy` **한 enum 맵**에 둔다. **`event_type IN (...)`을 쿼리에 박는다** — 전량 조회 후 걸러내면 걸러내기 전 목록이 메모리에 존재한다(27 설계 6-4).
- **detail을 문자열 가공으로 자르지 않는다** — "사유 라벨만"인 이벤트는 detail 원문을 버리고 **연결된 요청 행의 `reason_code`에서 라벨을 다시 만든다.** "· 이후를 잘라낸다" 같은 문자열 규칙은 detail 문형이 바뀌는 날 조용히 샌다. 이를 위해 30 설계 1-4의 이력 행에 **요청 id 참조가 필요하다** → `group_buy_history.ref_id BIGINT NULL`(요청·통지·확인 행 id) 한 컬럼을 **V125 원안에 추가**하도록 30 설계에 넘긴다(10-2 #1).
- **`actor_type = ADMIN`의 표시명은 「운영자」**(§29-13). 서버는 `actorType`만 내린다.

> ⚠️ **B1 이력의 "계약 체결완료 · 2026.08.14 09:30 · 뷰티_소연"** — 체결은 운영자의 행위이고(30 설계 2-1), 이 줄은 B1에만 있고 B2~B4에는 없다. 공구 이력은 공구 생성부터다 — **계약 이력을 합성하지 않는다**(10-1 #14).

## 7. 신규 `ErrorCode`

30 설계 4-7의 코드(`GROUP_BUY_NOT_FOUND` · `STATUS_CONFLICT` · `ACTION_NOT_ALLOWED` · `REQUEST_ALREADY_PENDING` · `FULFILLMENT_*`)는 그대로 쓰고 **9종**을 더한다.

| 코드 | HTTP | 문구 |
| --- | --- | --- |
| `GROUP_BUY_NOT_OWNED_BY_CREATOR` | 404 | 존재하지 않는 공구입니다. |
| `GROUP_BUY_POST_NOT_WRITABLE` | 409 | 지금은 게시물을 작성할 수 없습니다. |
| `GROUP_BUY_POST_UNDER_REVIEW` | 409 | 검토 중에는 게시물을 수정할 수 없습니다. |
| `GROUP_BUY_POST_NOT_EDITABLE` | 409 | 지금 상태에서는 게시물을 수정할 수 없습니다. |
| `GROUP_BUY_POST_EMPTY_DRAFT` | 400 | 제목이나 본문 중 하나는 입력해 주세요. |
| `GROUP_BUY_POST_REQUIRED_FIELD` | 400 | 제목과 본문을 모두 입력해 주세요. |
| `GROUP_BUY_POST_TOO_LONG` | 400 | 제목은 40자, 본문은 2,000자까지 입력할 수 있습니다. |
| `GROUP_BUY_EXTENSION_NOT_PENDING` | 409 | 응답할 연장 요청이 없습니다. |
| `GROUP_BUY_EXTENSION_RESPONSE_CLOSED` | 409 | 공구 종료 시각이 지나 연장 요청에 응답할 수 없습니다. |

- **`NOT_OWNED_BY_CREATOR`는 404이고 문구가 `NOT_FOUND`와 같다** — 0-4. 코드를 나누는 것은 **서버 로그에서만** 구분하기 위해서다(27 설계 7절과 같은 이유). 파트너의 `NOT_OWNED_BY_SELLER`(403)와 비대칭인 것이 의도다.
- **필수 미입력은 FE 버튼 비활성**(§31-2 "에러 문구 없이 버튼 비활성만"). `REQUIRED_FIELD` · `EMPTY_DRAFT`는 FE가 정상이면 **보이지 않는 에러**다 — 그래도 서버는 막는다.
- 길이는 **`String.length()`(UTF-16)** 로 센다 — 일반 게시물(`ShowroomPostService`)과 같은 방식. 이모지 1개가 2자로 세지는 문제는 두 게시물이 **같이** 갖는다. 한쪽만 코드포인트로 바꾸면 같은 문장이 한 화면에서는 들어가고 다른 화면에서는 안 들어간다.

**단계별 건수는 §29-11 "경로별 내역은 판매 관리 소관"과 충돌하지 않는다** — §29-11이 막은 것은 **종결 경로 5종의 내역 표**(무엇으로 끝났나)이고, B7이 요구하는 것은 **남은 건이 어디에 걸려 있나**다. "공구 화면은 **남은 건수만** 센다"의 범위 안에서 남은 건수를 둘로 쪼갠 것이다. 판정은 여전히 판매 모듈이 하고 공구는 숫자만 받는다.

**포트가 비어 있으면 `null`이지 0이 아니다**(30 설계 0-6). 특히 `ordersSinceHidden = 0`은 "숨김이 판매를 멈췄다"는 **사실 주장**이다 — 판매 모듈이 없어서 0이 나오면 거짓말이 된다.

**S0은 30 설계 P2(공구 생성)보다 늦으면 안 된다.** 공구 생성 자체는 게시물을 만들지 않지만, S3가 첫 게시물을 만드는 순간 ①의 수정·삭제 우회와 ②의 7일 뒤 삭제 경로가 열린다. S0은 공구 코드와 무관한 작은 PR이라 **가장 먼저** 넣는다.

**30 설계 P3(스케줄러)는 `GroupBuyPostExposure.sync`를 호출해야 한다** — 호출이 빠지면 오픈된 공구의 게시물이 `DRAFT`로 남아 소비자 상세가 404다(2-9). S1을 P3보다 먼저 넣는다.

**실판매까지의 최소 경로** — 30 P2(생성) → **S3(게시물 제출)** → 어드민 오픈 승인 API → 30 P5(브랜드 물량 확인) → 30 P3(자동 오픈). 스튜디오 S3 없이는 게이트 ②가 영원히 비어 있다.

**S5는 스레드 포트 없이 열지 않는다** — 30 설계 P7과 같은 조건이고 **같은 서비스 메서드**를 쓰므로(5-4) 두 PR을 함께 배포하는 편이 낫다.
