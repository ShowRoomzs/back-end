## 0. 먼저 정한 5가지

### 0-1. 계약은 파트너센터의 것이 아니라 **3서피스가 공유하는 하나의 객체**다

§25-0이 "세 화면은 같은 계약 객체를 다른 권한으로 다룬다"로 시작한다. 그래서 **테이블은 처음부터 9종 상태 · 어드민 입력값 10종 · 스튜디오 서명까지 전부 수용하도록 만든다.** 파트너 API만 먼저 열더라도 컬럼은 다 판다.

이유는 하나다 — 계약은 **상태 전이 이력이 곧 법적 근거**인 객체다. 파트너용으로 좁게 만들고 나중에 어드민 컬럼을 ALTER로 붙이면, 그 사이에 쌓인 계약들은 `review_approved_at`이 NULL인 채로 남는다. 이력이 비어 있는 계약은 분쟁에서 쓸 수 없다.

- 도메인: `showroomz.domain.contract.{entity, repository, type}` — **한 벌**
- API: `showroomz.api.seller.contract.*`(이번 범위) / `showroomz.api.creator.contract.*` / `showroomz.api.admin.contract.*`(다음)

### 0-2. 모두싸인 API를 쓰지 않으므로 **서명은 우리 도메인의 이벤트가 아니라 입력값**이다

§25-3 확정. 서버가 해야 할 일은 **서명을 처리하는 것이 아니라, 운영자가 옮겨 적은 값을 보관하고 그 값이 언제 기준인지 같이 보관하는 것**이다.

| 우리가 만들지 않는 것 | 대신 만드는 것 |
| --- | --- |
| 서명 요청 발송 API · 웹훅 수신 엔드포인트 | 어드민이 입력하는 `signature_requested_at` · `signature_deadline_at` |
| 서명 완료 콜백 | 어드민이 체크하는 `brand_signed_at` · `creator_signed_at` + **`signature_as_of`(기준 시각)** |
| 만료 자동 종결 배치 | 어드민 "만료 확인" 큐 조회 조건 (`signature_deadline_at < now` AND `status = SIGNING`) |
| PDF 자동 수신 | 어드민 업로드 `contract_document` 2종 |

**스케줄러를 만들지 않는다.** §25-3 "만료가 자동 판정이 아니다"가 명시적이고, 배치가 상태를 닫으면 §25-9 "모든 수동 처리에 처리자·시각이 남는다"가 깨진다. 만료 처리자는 반드시 사람이다.

### 0-3. 작성중 계약은 **필수값이 전부 비어 있는 행**이다 → NOT NULL을 걸 수 없다

목록 A1에 `(공구명 미입력) · 미설정`인 작성중 행이 실제로 있다. 그러므로:

- **DB 제약은 「형식」만** — 길이, 숫자 범위(CHECK), FK, 상태 enum
- **「필수」 판정은 전부 애플리케이션이, 그것도 상태 전이 시점(검토 요청)에** 한다
- 임시저장(`PUT`)은 **부분 저장을 허용**하고 형식 위반만 400으로 막는다

이 구분을 흐리면 임시저장이 실패하기 시작하고, 시안이 보장한 "검토 요청 전까지 임시저장할 수 있습니다"가 거짓이 된다.

### 0-4. 편집 잠금은 **화면 상태가 아니라 서버 권한**이다

§25-4의 잠금 구간(검토 대기 이후 전 구간, 검토 반려만 예외)은 FE 비활성으로 구현하면 안 된다. **쓰기 API 전부가 진입 시 상태를 먼저 판정**하고, 허용 집합 밖이면 409로 떨군다.

허용 집합은 딱 둘이다 — `DRAFT`, `REVIEW_REJECTED`.

### 0-5. 계약서에 박히는 값은 **스냅샷**으로 복사한다

계약 상품 항목은 `product_id`만 들고 있으면 안 된다. 종결된 계약(B6·B7·B8)도 **상품명 · 정가를 그대로 보여주고**, 그 사이 브랜드가 상품명을 바꾸거나 정가를 내렸을 수 있다. 계약서는 **서명 시점의 사실**을 보존해야 한다.

→ `contract_item`에 `product_name` · `regular_price`를 **복사해 저장**하고, 화면은 스냅샷을 읽는다. `product_id`는 공구 생성·정산 귀속용 참조로만 남긴다.

### 1-2. `ContractStatus` — 9종 · 3서피스 공통

| enum | 화면 라벨 | 종류 | 배지 |
| --- | --- | --- | --- |
| `DRAFT` | 작성중 | 진행 | 중립 |
| `REVIEW_PENDING` | 검토 대기 | 진행 | 정보 |
| `REVIEW_REJECTED` | 검토 반려 | 진행 | **경고** |
| `SIGNING` | 서명 진행중 | 진행 | 정보 |
| `CONCLUSION_PENDING` | 체결 처리 대기 | 진행 | 정보 |
| `CONCLUDED` | 체결완료 | 종료(성공) | 성공 |
| `DECLINED` | 거절 | 종료(실패) | **위험** |
| `EXPIRED` | 만료 | 종료(실패) | 중립 |
| `CANCELED` | 취소 | 종료(실패) | 중립 |

**배지 색은 서버가 내려준다.** 같은 상태가 세 화면에서 다른 색이면 안 된다는 것이 §25-2 원칙 ③인데, FE 3개가 각자 매핑표를 들고 있으면 반드시 어긋난다. 응답에 `status`(enum) · `statusLabel` · `statusTone`(`neutral`/`info`/`warning`/`success`/`danger`)을 함께 실어 **매핑을 서버 enum 한 곳에 둔다.**

**서명 진행중을 쪼개지 않는다**(§25-2). B4 · B4a · B4c는 전부 `SIGNING`이고, 화면 분기는 `brandSignedAt` · `creatorSignedAt` 두 값의 조합으로 FE가 고른다. 서버가 `SIGNING_MY_TURN` 같은 값을 만들면 조합 4개가 상태값으로 폭발한다.

### 1-5. 리워드율은 `DECIMAL`, 예상 리워드는 파생값

§25-5-3: "리워드율은 상품 항목 단위이며 **정산이 이 값을 그대로 쓴다**."

정산이 그대로 쓰는 값을 `DOUBLE`로 두면 15.0이 14.999999로 읽히는 날이 온다. **`DECIMAL(4,1)` + Java `BigDecimal`**로 고정한다.

예상 리워드 = `group_buy_price × reward_rate / 100` (1개당).

**단위는 1원 · 소수점은 버림(절사)으로 확정한다.**

```java
// 공유 유틸 — 계약·정산·계약서 PDF가 모두 이 메서드만 호출한다
public static long calcUnitReward(int groupBuyPrice, BigDecimal rewardRate) {
    return BigDecimal.valueOf(groupBuyPrice)
            .multiply(rewardRate)
            .divide(BigDecimal.valueOf(100))
            .setScale(0, RoundingMode.DOWN)   // 버림 — HALF_UP·FLOOR 아님
            .longValueExact();
}
```

| 항목 | 규칙 |
| --- | --- |
| 단위 | **1원** — 10원 단위로 맞추지 않는다. 10원 단위 제약은 **공구가**의 것이고(§25-5-3), 리워드는 그 파생값이다 |
| 소수점 | **버림** — `RoundingMode.DOWN` |
| 적용 지점 | **계약 응답 · 정산 · 계약서 PDF 3곳이 같은 메서드를 호출한다** |
| 저장 | **하지 않는다** — 순수 파생값이고, 저장하면 두 소스가 어긋난다(위 `contract_item` 주석) |

**`DOWN`이지 `FLOOR`가 아닌 이유** — 두 값은 양수에서 같지만 음수에서 갈린다. 리워드가 음수가 될 일은 없어야 하지만, **그 "없어야 한다"에 기대지 않는다.** 절사는 "소수부를 버린다"는 뜻이고 그것을 그대로 표현하는 모드는 `DOWN`이다.

**반올림이 아니라 버림인 이유** — 이 값은 **브랜드가 인플루언서에게 지급할 금액의 단가**다. 올림·반올림은 계약서에 적힌 리워드율보다 **실제로 더 주게 되는 조합**을 만들고, 그 차액은 수량만큼 곱해진다. 계약서에 근거가 없는 금액이 정산에 섞이면 §25-5-4의 분쟁 해결 경로(계약서가 근거)가 무너진다.

> **계약서 생성 규격과 일치한다.** `SHOWROOMZ_계약서_생성규격_v0.1.md` §4-4가 `개당리워드[n]`을 **「원 단위 절사」**로 이미 확정해 두었다. 계약서에 인쇄되는 값과 화면·정산이 다른 규칙을 쓰면 **계약서가 근거가 되지 못한다.**

### 1-6. 부수 테이블 3개 + 표준 조항

**`contract_history`** — append-only. 화면 「이력」 카드가 그대로 읽는다.

| 컬럼 | 비고 |
| --- | --- |
| `contract_history_id` PK / `contract_id` FK | |
| `event_type` VARCHAR(64) | `CREATED` `REVIEW_REQUESTED` `REVIEW_REQUEST_CANCELED` `REVIEW_APPROVED` `REVIEW_REJECTED` `SIGNATURE_SENT` `BRAND_SIGNED` `CREATOR_SIGNED` `SIGNATURE_UPDATED` `RESEND_REQUESTED` `CONCLUDED` `DECLINED` `EXPIRED` `CANCELED` `FIXED_FEE_PAID` `GROUP_BUY_CREATED` |
| `actor_type` VARCHAR(16) | `SELLER` / `CREATOR` / `ADMIN` / `SYSTEM` |
| `actor_id` BIGINT NULL | |
| `actor_display_name` VARCHAR(100) | **스냅샷** — 브랜드명·쇼룸명 |
| `detail` VARCHAR(500) NULL | "리워드율이 표준 범위를 넘습니다" 같은 부가 문구 |
| `occurred_at` DATETIME | |

- `INDEX (contract_id, occurred_at DESC)`
- **UPDATE·DELETE를 하지 않는다.** 서비스에서만 append하고 리포지토리에 수정 메서드를 두지 않는다.
- 호칭은 **읽는 서피스가 고른다** — §25-9에 따라 파트너는 `ADMIN` → 「어드민」, 스튜디오는 `ADMIN` → 「운영자」, 어드민은 실명이다. 그러므로 `actor_display_name`은 **서피스와 무관하게 같은 값**(브랜드명·쇼룸명)에만 쓰고, 운영자 주체는 `actor_type`만으로 내려 FE가 문구를 고르게 한다.

**`contract_document`** — 체결 문서 2종(§25-3 #3).

| 컬럼 | 비고 |
| --- | --- |
| `contract_id` FK · `document_type` VARCHAR(32) | `SIGNED_PDF` / `AUDIT_TRAIL` · **`UNIQUE(contract_id, document_type)`** |
| `s3_key` / `file_url` / `original_name` / `size_bytes` / `content_type` | |
| `uploaded_by` BIGINT · `uploaded_at` DATETIME | 어드민 |

**교체·삭제 API를 만들지 않는다**(§28-6 "서명 원본이 바뀌면 계약의 증거가 사라진다"). 유니크 제약이 실수로 인한 중복 업로드까지 함께 막는다.

**`contract_resend_request`** — `[서명 안내 다시 받기]`.

| 컬럼 | 비고 |
| --- | --- |
| `contract_id` FK · `requester_type`(`SELLER`/`CREATOR`) · `requester_id` | |
| `requested_at` · `handled_at` NULL · `handled_by` NULL | 어드민 「재발송 요청」 큐(§28-1) |

- `INDEX (handled_at, requested_at)` — 미처리 큐 조회
- **요청은 발송이 아니다.** 이 행이 생겨도 계약 상태는 변하지 않는다. 실제 재발송은 어드민이 모두싸인에서 한다.
- 횟수 제한·SLA는 §28-8 D #7로 미정 → **당장은 짧은 중복 억제만** 둔다(3-6).

**`contract_clause_version`** — 표준 조항의 버전 스냅샷.

§25-7의 조항은 브랜드가 편집할 수 없고 계약서에 자동 삽입된다. 문안이 개정되면 **이미 서명된 계약은 옛 문안으로 남아야** 하므로, 계약이 조항 **버전**을 참조한다.

- 구조는 기존 `TermsDocument` / `TermsVersion`(`domain/terms`)과 같은 패턴을 따른다 — 굳이 새 모양을 만들지 않는다.
- `contract.clause_version_id`는 **검토 요청 시점에 현행 버전으로 고정**한다. 작성중에는 비어 있고 화면은 항상 현행 버전을 읽는다.
- 문안 자체는 `[자문대기-법률]` 2건(조항 2 대가관계 표시 · 조항 8 손해배상)이 남아 있으므로, **테이블과 조회 API만 먼저 만들고 내용은 나중에 채운다.**

### 1-7. 계약번호 — `CTR-YYYYMMDD-NNN`

- **부여 시점: 검토 요청.** 작성 화면(B1·B2·B2a) 헤더에는 계약번호가 없고 B3c부터 나타난다. 초안을 만들 때마다 번호를 태우면 **버려진 초안이 번호를 먹어** 일련번호에 구멍이 생긴다.
- **생성 방식**: `contract_number_sequence(seq_date DATE PK, last_seq INT)` 테이블에 `INSERT … ON DUPLICATE KEY UPDATE last_seq = last_seq + 1` 한 방으로 뽑는다.
- ⚠️ 기존 `ProductService.generateProductNumber()`(`src/main/java/showroomz/api/seller/product/service/ProductService.java:217`)는 **`productRepository.findAll()`을 전량 메모리로 끌어와 max를 찾는다.** 동시 요청에서 같은 번호가 나오고 행이 늘수록 느려진다. **이 방식을 복제하지 않는다.**

### 1-8. 공구 생성 게이트

§25-1 "계약 1건 = 공구 1건", "체결완료가 공구 생성 게이트다".

계약 모듈이 책임지는 것은 **게이트뿐**이다.

| 계약이 하는 일 | 공구 모듈이 하는 일 |
| --- | --- |
| `status = CONCLUDED` 인지 판정 | 공구 엔티티 생성 |
| `group_buy_id IS NULL` 인지 판정(중복 차단) | 기간·공구가·리워드율·최소 물량 **상속** |
| 생성된 id를 조건부 UPDATE로 기록 | 오픈 승인 절차 |

중복 차단은 조건부 UPDATE 하나로 끝낸다.

```sql
UPDATE contract SET group_buy_id = :id
 WHERE contract_id = :cid AND status = 'CONCLUDED' AND group_buy_id IS NULL
```

`rowsAffected = 0`이면 409(`CONTRACT_GROUP_BUY_ALREADY_CREATED`). B5a의 "공구가 이미 생성돼 있어 추가로 만들 수 없습니다"가 이 한 줄로 성립한다.

> **공구 도메인은 아직 없다.** 이번 범위에서는 `group_buy_id` 컬럼과 위 게이트 검사만 만들고, `[공구 생성]` 버튼이 호출할 API는 **공구 모듈이 생길 때 계약 서비스의 게이트 메서드를 호출**하는 형태로 붙인다. 계약 쪽에 공구 생성 로직을 넣지 않는다.

## 2. 검증 — 서버가 전부 다시 본다

### 2-1. 검증이 도는 지점은 셋

| 지점 | 검증 |
| --- | --- |
| 임시저장 `PUT` | **형식만** — 길이, 숫자 범위, enum, 10원 단위 |
| **검토 요청 `POST`** | **하드 H1~H8 전량** + 소유·상태·상대·상품 재확인 |
| 재작성 `POST /duplicate` | 복사 직후 **하드 전량 재검증**해 결과를 함께 내려준다(§26-5) |

### 2-2. 하드 검증 H1~H8 — 검토 요청을 막는다

| # | 조건 | 서버 처리 |
| --- | --- | --- |
| H1 | 공구가 > 정가 | 400 · 항목 index 포함 |
| H2 | 공구가가 10원 단위 아님 | 400 |
| H3 | 리워드율 0~90% 밖 | 400 |
| H4 | 공구 기간 3~30일 밖 | 400 |
| H5 | 시작 일시 < **검토 요청 시각** + 7일 | 400 |
| H6 | 콘텐츠 수량 합계 0 | 400 |
| H7 | 상품 항목 0건 | 400 |
| H8 | 고정 지급비 > 0 인데 고지 확인 없음 | 400 |

서버가 추가로 보는 것 — **FE 달력·드롭다운이 보장하는 것들도 전부 다시 본다.**

| 항목 | 검증 |
| --- | --- |
| 계약 상대 | 이 브랜드와 **`CONNECTED` 상태 연결**이 있는 상대인가 |
| 상품 | 이 브랜드 소유인가 · `display_status = DISPLAY`(진열)인가 |
| 정가 | 스냅샷 정가와 **현재 상품 정가가 같은가** — 다르면 스냅샷을 갱신하고 H1을 다시 본다 |
| 필수값 | 공구명(2~40자) · 기간 2종 · 고정 지급비 · 지급 시점 · 게시 완료 기한 |
| 2차 활용 | `secondary_use_allowed = true` AND `period_type = FIXED`이면 `months` 필수 |

**H4·H5는 시안에서 "달력이 선택 자체를 잠근다"(§25-5-2)로 처리되지만, 서버가 안 보면 안 된다.** 잠금은 UI의 친절이고 규칙의 집행이 아니다. 특히 H5는 **기준이 「검토 요청일」**이라 임시저장 때 통과한 날짜가 3주 뒤 검토 요청 시점에는 위반이 된다 — **판정은 반드시 검토 요청 트랜잭션 안에서** 한다.

> ⚠️ **지급 시점 필수와 상한 1,000만원이 하드 목록에 없다**(§26-6 #6). 시안 힌트 문구에만 있으므로 **서버는 둘 다 집행**하고(필수 미입력 → `REQUIRED`, 상한 초과 → `RULE`), 기획 확정 시 목록에 추가한다.

### 2-3. 경고 W1~W6 — 막지 않고 **기록**한다

| # | 조건 |
| --- | --- |
| W1 | 할인율 70% 초과 |
| W2 | 리워드율 40% 초과 |
| W3 | 공구 기간 14일 초과 |
| W4 | 시작일이 검토 요청일 + 60일 이후 |
| W5 | 상품 10건 초과 |
| W6 | 고정 지급비 1,000,000원 초과 |

- 검토 요청 API가 **자체적으로 다시 판정**하고 결과를 `warning_flags`에 저장한다. **FE가 보낸 목록을 그대로 믿지 않는다.**
- 요청 바디의 `acknowledgedWarnings`는 **동의 여부 확인용**이다 — 서버가 판정한 경고 집합과 다르면 409(`CONTRACT_WARNING_MISMATCH`)로 되돌려 **모달을 다시 띄우게** 한다. 사용자가 모달을 본 뒤 다른 탭에서 값을 고쳤을 수 있다.
- 검증 API(2-4)를 따로 두어 FE가 모달을 열기 직전에 **서버 판정 경고 목록을 받아가게** 한다.

> ⚠️ **미결 #2 — 경고의 수신처가 정해지지 않았다**(§25-6 · §28-8 A). 파트너는 "통과된 경고가 어드민에게 전달된다"고 하고, 어드민 rev.1은 "MVP에 임계값이 없다"는 전제로 검토 체크리스트를 두지 않았다. **저장은 지금 하고 노출은 확정 후에 붙인다** — 저장을 미루면 확정된 뒤 과거 계약의 경고를 복원할 방법이 없다. 반대로 노출을 먼저 붙이면 어드민 화면에 근거 없는 영역이 생긴다.

### 2-4. 검증 전용 엔드포인트

`POST /v1/seller/contracts/{id}/validate` — 상태를 바꾸지 않고 하드·경고 판정만 돌려준다.

```json
{ "canSubmit": false,
  "hardViolations": [ { "code": "H1", "kind": "RULE",
                        "field": "items[0].groupBuyPrice",
                        "message": "공구가는 정가 이하여야 합니다." } ],
  "warnings": [ { "code": "W2", "message": "리워드율이 40%를 넘습니다." } ] }
```

쓰는 곳 둘 — ① 검토 요청 확인 모달(C3)이 열거할 경고를 받는다 ② 재작성 직후 위반 행을 표시한다.

### 2-5. 에러 문구 vs 비활성 — 서버도 같은 구분을 지킨다

프로젝트 절대 규칙(§25-6): **필수 미입력은 에러 문구 없이 버튼 비활성**, 에러 문구는 **규칙 위반에만**.

서버는 `hardViolations[].kind`를 `REQUIRED`(미입력) / `RULE`(위반)으로 나눠 내린다. FE가 이 구분 없이 메시지를 전부 뿌리면 빈 폼에 빨간 문구가 8개 뜬다.

## 3. 상태 전이

### 3-1. 전이표 — 누가, 어디서, 어디로

| # | 전이 | 주체 | API 소속 | 부수 효과 |
| --- | --- | --- | --- | --- |
| 1 | — → `DRAFT` | 브랜드 | **seller** | 빈 계약 생성 |
| 2 | `DRAFT` → `REVIEW_PENDING` | 브랜드 | **seller** | 계약번호 부여 · 조항 버전 고정 · 경고 저장 · **편집 잠금** |
| 3 | `REVIEW_PENDING` → `DRAFT` | 브랜드 | **seller** | **요청 취소** — 종결 아님 · 사유 없음 · **어드민에 통지** |
| 4 | `REVIEW_PENDING` → `SIGNING` | 어드민 | admin | 발송 일시·서명 기한 입력 |
| 5 | `REVIEW_PENDING` → `REVIEW_REJECTED` | 어드민 | admin | 사유 2단 · **편집 재개** |
| 6 | `REVIEW_REJECTED` → `REVIEW_PENDING` | 브랜드 | **seller** | 재요청 — 2번과 같은 경로 |
| 7 | `SIGNING` → `CONCLUSION_PENDING` | 어드민 | admin | 양측 서명 완료 체크의 결과 |
| 8 | `CONCLUSION_PENDING` → `SIGNING` | 어드민 | admin | **체크 해제**(§28-5) — 체결 전까지 가역 |
| 9 | `CONCLUSION_PENDING` → `CONCLUDED` | 어드민 | admin | **유일한 불가역** · 문서 2종 필수 · 공구 게이트 열림 |
| 10 | `SIGNING` → `DECLINED` | 인플루언서 | creator | 사유 + 메모 |
| 11 | `SIGNING` → `EXPIRED` | 어드민 | admin | 기한 경과 확인 후 **수동** |
| 12 | `SIGNING`·`CONCLUSION_PENDING` → `CANCELED` | 운영자 | **admin** | **계약 취소** — 브랜드에게는 계약 취소가 없다. 발송 전의 되돌림은 [요청 취소](검토 대기 → 작성중)뿐이고 반려는 수정 후 재요청만 한다(어드민 설계 10-A) |

**`CONCLUDED` 이후로 나가는 전이가 없다.** §25-2의 [결정 필요] 그대로다 — 체결 후 해지 값이 9종에 없다. **임의로 만들지 않는다.** 진행 중인 공구를 멈춰야 하면 공구 관리의 「중단」으로 처리한다(미결 #3).

### 3-2. 되돌림 2경로를 코드에서도 갈라놓는다

§25-4가 "혼동 금지"라고 적은 지점이다. 메서드 이름부터 다르게 둔다.

| | `cancelReviewRequest()` | `cancelContract()` |
| --- | --- | --- |
| 허용 상태 | `REVIEW_PENDING` **만** | `SIGNING` **만** — 양측 서명이 끝나면 불가 |
| 결과 | `DRAFT` — **종결 아님** | `CANCELED` — **항상 종결** |
| 사유 | 받지 않는다 | **필수**(`ETC`면 메모도 필수) |
| 상대 통지 | 없음 — 상대에게 아직 안 갔다 | **있음** |
| 어드민 통지 | **있음** — 이미 검토를 시작했을 수 있다 | 있음 |

**`REVIEW_PENDING`에서 `cancelContract()`는 404가 아니라 409로 막는다.** 서명 요청이 나간 뒤 `[요청 취소]`는 화면에서 사라지지만(§25-4), 서버가 상태를 안 보면 잘못된 호출 한 번에 종결된 계약이 작성중으로 돌아간다.

### 3-3. 모든 전이는 조건부 UPDATE로 쓴다

```java
int changed = contractRepository.updateStatus(contractId, FROM, TO, now);
if (changed == 0) throw new BusinessException(CONTRACT_STATUS_CONFLICT);
```

읽고-판정하고-저장하는 사이에 다른 요청이 상태를 바꿔도 **DB가 한 번 더 막는다.** 특히 위험한 조합 둘:

- 브랜드의 `[요청 취소]`와 어드민의 `[검토 통과]`가 **동시에** 들어오는 경우 — 하나는 반드시 409가 되어야 한다. 둘 다 통과하면 **작성중 상태인데 서명 요청이 발송된 계약**이 만들어진다.
- 브랜드의 `[요청 취소]`와 어드민의 **`[검토 승인]`** — 둘 다 `REVIEW_PENDING`에서 출발하므로 한쪽은 0행(409)이 되어야 한다. 둘 다 통과하면 **작성중인데 서명 요청이 나간** 계약이 생긴다.

### 3-4. 편집 충돌 — 낙관적 락

작성 화면은 항목 N개를 한 번에 저장하는 넓은 폼이고, 브라우저 탭 두 개로 같은 계약을 열 수 있다. `@Version`을 걸고 `PUT` 요청에 `version`을 함께 받아 충돌 시 409(`CONTRACT_MODIFIED_ELSEWHERE`)를 내린다.

### 3-5. 이력은 전이와 **같은 트랜잭션**에서 쓴다

`ContractHistoryRecorder`를 서비스 내부에서 호출하고 **이벤트 리스너로 분리하지 않는다.** 이력이 비면 화면의 「이력」 카드가 비고, 그건 분쟁에서 근거가 없다는 뜻이다. 비동기로 흘려보낼 종류의 데이터가 아니다.

### 3-6. 재발송 요청의 중복 억제

정책이 미결(§28-8 D #7)이므로 횟수 제한을 만들지 않되, 연타는 막는다 — **미처리(`handled_at IS NULL`) 요청이 이미 있으면 새 행을 만들지 않고 기존 요청을 200으로 돌려준다.** 어드민 큐에 같은 계약이 10줄 쌓이는 것만 막으면 된다.

## 4. 파트너센터 API — `/v1/seller/contracts`

인증은 기존 패턴 그대로(`UserPrincipal` → 셀러 이메일 → `Market` 해석). 모든 조회·조작은 **`contract.market_id`가 내 브랜드인지** 먼저 본다. 컨트롤러는 `SellerContractControllerDocs`를 implements 하고 문서 어노테이션은 docs 인터페이스에 둔다.

### 4-1. 조회

| Method | Path | 설명 |
| --- | --- | --- |
| `GET` | `/v1/seller/contracts` | 목록 · `tab` `keyword` `startDate` `endDate` `sort` + `PagingRequest`(20/50) |
| `GET` | `/v1/seller/contracts/summary` | **탭별 카운트 + GNB 배지** — 목록과 분리(4-4) |
| `GET` | `/v1/seller/contracts/{id}` | 상세 — 조건·서명·상태·이력 **한 번에** |
| `GET` | `/v1/seller/contracts/{id}/documents/{type}` | 체결 문서 다운로드 URL(`SIGNED_PDF` / `AUDIT_TRAIL`) |
| `GET` | `/v1/seller/contracts/clauses` | 표준 조항 전문(모달 C1) |
| `GET` | `/v1/seller/contracts/form-sources` | **작성 폼 선택지** — 연결된 상대 + 진열 상품(정가 동봉) |

- `sort`: `CREATED_DESC`(기본) · `START_AT_ASC`
- `keyword`: 공구명 + 계약 상대 표시명
- 목록 항목: `contractId` `contractNumber` `title` `counterpartyName` `itemCount` `startAt` `endAt` `createdAt` `status` `statusLabel` `statusTone` `entryMode`
- **`entryMode`** — `EDIT`(작성중·검토 반려) / `VIEW`(나머지). §26-1 "작성중·검토 반려 행 → 작성 모드"의 판정을 FE가 상태표를 들고 다시 하지 않게 **서버가 내려준다.**
- `title`이 NULL이면 **서버가 `(공구명 미입력)`으로 바꾸지 않는다.** NULL을 그대로 내리고 표시 문구는 FE가 고른다 — 서버가 표시 문자열을 지어내면 검색·정렬이 그 가짜 값에 걸린다.
- `form-sources`를 따로 두는 이유: 기존 `/v1/seller/connections`·`/v1/seller/products`는 목록용이라 페이징·필터가 계약 폼과 다르다. 드롭다운은 **연결됨 상대 전량 + 진열 상품 전량**이 한 번에 필요하다.

### 4-2. 작성 · 임시저장

| Method | Path | 허용 상태 |
| --- | --- | --- |
| `POST` | `/v1/seller/contracts` | — → `DRAFT` |
| `PUT` | `/v1/seller/contracts/{id}` | `DRAFT` · `REVIEW_REJECTED` |
| `POST` | `/v1/seller/contracts/{id}/validate` | `DRAFT` · `REVIEW_REJECTED`(상태 불변) |
| `DELETE` | `/v1/seller/contracts/{id}` | `DRAFT` **만** |

- `POST`는 **빈 초안을 만든다.** 스레드 경유 진입이면 `creatorId`를 함께 받아 **고정**하고(§25-5-1 "자동 지정 · 변경 불가"), 이후 `PUT`에서 `creatorId` 변경을 거부한다.
- `PUT`은 **전체 교체(PUT 시맨틱)** — 계약 폼은 항목 배열을 포함한 하나의 덩어리라 PATCH로 쪼개면 "3번째 행 삭제"를 표현할 수 없다. 항목은 요청 배열로 통째 교체하고 `sort_order`는 배열 index로 채운다.
- **상품을 바꾼 행은 공구가·리워드율·최소 물량이 초기화된다**(§25-5-3) — 이 규칙은 FE가 화면에서 지우지만, 서버도 `product_id`가 바뀐 행은 **세 값을 무시하고 NULL로 저장**한다. 그러지 않으면 A상품 가격 기준으로 통과한 값이 B상품에 그대로 얹힌다.
- `DELETE`는 **작성중 초안만.** 검토 요청 이후 계약은 지울 수 없다 — 되돌림은 취소이지 삭제가 아니다.

### 4-3. 상태 조작

| Method | Path | 전이 | 바디 |
| --- | --- | --- | --- |
| `POST` | `/{id}/review-request` | `DRAFT`·`REVIEW_REJECTED` → `REVIEW_PENDING` | `acknowledgedWarnings[]` |
| `POST` | `/{id}/review-request/cancel` | `REVIEW_PENDING` → `DRAFT` | 없음 |
| `POST` | `/{id}/resend-request` | 상태 불변(`SIGNING`) | 없음 |
| `POST` | `/{id}/fixed-fee/payment` | 상태 불변(`CONCLUDED`) | 없음 |
| `POST` | `/{id}/duplicate` | 새 `DRAFT` 생성 | 없음 |

**`/review-request` 한 트랜잭션이 하는 일** — 상태 판정 → 하드 전량 재검증 → 경고 판정·대조 → 스냅샷 정가 갱신 → **계약번호 부여** → 조항 버전 고정 → `review_requested_at` 기록 → 상태 전이 → 이력 append → 어드민 통지. **번호 부여가 전이와 같은 트랜잭션 안에 있어야** 번호 없는 `REVIEW_PENDING`이 생기지 않는다.

**`/cancel`의 사유** — 시안 C4의 5종: `CONDITION_REVIEW`(조건 재검토 필요) · `OUT_OF_STOCK`(상품 재고 부족) · `SCHEDULE_CHANGE`(공구 일정 변경) · `NEGOTIATION_STOPPED`(상대와 협의 중단) · `ETC`(기타). **`ETC`면 메모 필수** — 기존 `INQUIRY_DELETE_REASON_DETAIL_REQUIRED`와 같은 패턴이다.

**`/fixed-fee/payment`** — `CONCLUDED` + `fixed_fee_amount > 0` + `fixed_fee_paid_at IS NULL`에서만. 시안에 취소 버튼이 없으므로 **되돌리는 API를 만들지 않는다**(미결 #4 — 오기록 정정 경로).

**`/duplicate`(이 조건으로 새 계약 작성)** — §26-5 표 그대로.

| 구분 | 처리 |
| --- | --- |
| 복사 | 계약 상대 · 공구명 · 상품 항목(4열 전부) · 고정 지급비 금액 · 콘텐츠 의무 전부 · 비고 |
| **비운다** | `group_buy_start_at` · `group_buy_end_at` · `content_due_date` |
| **다시 받는다** | `fixed_fee_notice_agreed_at` → **NULL** |
| 승계 안 함 | 서명 이력 · 기한 · 계약번호 · 상태 · `warning_flags` · 문서 |
| 기록 | `source_contract_id` = 원 계약 |

- **원 계약은 그대로 종결 상태로 남는다.** 복사가 아니라 새 행 생성이다.
- 응답에 **복사 직후 재검증 결과**(2-4 형태)를 함께 싣는다 — 상품이 미진열로 바뀌었거나 정가가 내려갔을 수 있다. 이때 **스냅샷을 현재 상품 값으로 갱신하고** 위반을 알린다. 옛 정가를 들고 있으면 H1이 통과해버린다.
- 진행 중(`DRAFT`~`CONCLUSION_PENDING`) 계약에서도 복제를 허용할지는 시안에 없다. **종결 3종 + 체결완료에서만 허용**하고 나머지는 409로 막는다 — 같은 조건의 계약 2건이 동시에 검토 큐에 올라가는 상황을 기획이 다룬 적 없다.

### 4-4. `summary` — 목록과 분리하는 이유

GNB 배지(「4 계약 관리 1」)는 계약 화면이 아닌 곳에서도 폴링된다. 목록 API에 카운트를 얹으면 배지 하나 때문에 매번 20건을 조회하게 된다.

```json
{ "tabCounts": { "ALL": 14, "DRAFT": 2, "REVIEW": 2, "SIGNING": 2,
                 "CONCLUDED": 5, "CLOSED": 3 },
  "actionRequiredCount": 1 }
```

**`actionRequiredCount`(GNB 배지)의 정의** — 브랜드가 지금 조치해야 하는 건수.

| 포함 | 근거 |
| --- | --- |
| `REVIEW_REJECTED` | 브랜드 조치로만 풀리는 유일한 진행 상태(§25-2) |
| `SIGNING` AND `creator_signed_at IS NOT NULL` AND `brand_signed_at IS NULL` | **B4c** — §26-3 "이 파일에서 유일하게 서명 진행중이 「내가 조치해야 하는」 상태" |

`REVIEW_PENDING` · `CONCLUSION_PENDING` · B4는 **넣지 않는다.** 공이 상대에게 있는 정상 대기이고, 배지에 넣으면 브랜드가 할 수 없는 일로 배지가 켜진다.

### 4-5. 상세 응답 구조

상세 화면 13종(B2a·B3c·B3d·B4·B4a·B4b·B4c·B5·B5a·B5b·B6·B7·B8)이 **같은 응답 하나**를 쓴다. 화면 분기는 FE가 값으로 고른다.

```
contract        번호 · 공구명 · 상태(3필드) · 기간 · 일수 · 상대(+connectionId)
items[]         상품명 · 정가 · 공구가 · 리워드율 · 예상리워드 · 최소물량
fixedFee        amount · trigger · triggerLabel · paidAt · obligationAlive
content         feed/reels/story · dueDate · secondaryUse · preReview · note
review          requestedAt · approvedAt · rejectedAt · rejectReason{code,detail}
signature       requestedAt · deadlineAt · brandSignedAt · creatorSignedAt
                · asOf · counterpartyViewed
settlement      platformFeeRate=2 · pgFeeRate=null · withholdingType
closure         closedAt · actorType · reasonCode · memo
groupBuy        groupBuyId · 생성 가능 여부
documents[]     type · downloadUrl
permissions     canEdit · canRequestReview · canCancelRequest · canCancel
                · canRequestResend · canRecordPayment · canCreateGroupBuy
history[]       eventType · actorType · actorDisplayName · detail · occurredAt
```

**`permissions` 블록을 서버가 내려준다.** 버튼 노출 조건이 상태 × 서명 조합 × 지급 여부로 갈리고(§25-4의 "요청 취소는 검토 대기만", "검토 대기는 요청 취소만, 서명 요청 후 취소는 운영자만"), FE가 이 판정을 복제하면 **서버 허용 집합과 어긋나는 버튼**이 생긴다. 서버 판정을 한 번 내려주면 FE는 그대로 그리면 된다.

**`obligationAlive`** — 종결 3종에서 화면이 "지급 의무 소멸"로 바뀌는 근거. `status ∈ {DECLINED, EXPIRED, CANCELED}`이면 `false`.

**`counterpartyViewed`** — `creator_viewed_at`의 존재 여부. B7의 "계약서 열람 기록 없음"이 이 값으로 그려진다. **거절은 상대 메모가 있지만 만료는 없어**(§26-5) 그 공백을 이 사실로 메운다.

**`withholdingType`** — §25-5-6 "상대 계정 정보 기반 자동 전환". `Creator.businessType`이 `INDIVIDUAL`이면 `WITHHOLDING_3_3`, `BUSINESS`면 `TAX_INVOICE`. **실지급액은 계산하지 않는다**(세무 확정 전 · §25-5-6).

**`pgFeeRate`는 `null`로 내린다** — `[자문대기-PG]`. 0으로 내리면 화면이 "0%"로 읽고, 수수료가 없다는 뜻이 되어버린다. null과 0은 다르다.

### 4-6. 표준 조항 요약과 전문이 어긋나는 문제

§25-7 · §26-6 #2의 정합 오류 — **요약에 있는 「단독 판매」·「샘플 제공」이 전문 9조에 없고**, 요약 「가격 정책」과 전문 「제3조 최저가 정책」은 이름이 다르다.

서버는 **조항 1건을 `{code, summaryTitle, summaryDescription, fullTitle, fullBody}`로 저장**해 요약과 전문을 **같은 행에서 파생**시킨다. 두 목록을 따로 관리하면 어긋남이 또 생긴다. 현재 요약 11개 ↔ 전문 9조의 불일치는 **기획 확정 후 seed로 맞춘다**(미결 #5).

| 출력 | 공구 관리 | `CONCLUDED` → 공구 생성 게이트 | △ 게이트만(1-8) |
| 출력 | 정산 관리 | 항목별 리워드율 · **고정 지급비는 정산 대상 아님** | ❌ 정산 모듈 |
| 양방향 | 연결·소통 스레드 | 협의 · 이행 확인 · 분쟁 중재 | ✅ 링크만 |

**상품·연결은 참조만 하고 역방향 의존을 만들지 않는다.** 상품 삭제·연결 해제가 계약을 건드리면 안 된다 — 계약은 스냅샷으로 자립한다(0-5). 반대로 **계약이 상품을 잠그지도 않는다**(체결된 계약의 상품을 미진열로 바꿀 수 있는지는 공구 모듈 소관).

### 5-1. 알림

상태 전이마다 상대·어드민에게 알려야 하지만, **기존 푸시 인프라(`domain/notification`의 `DeviceToken`·`PushSender`)는 앱 유저(소비자) 대상**이다. 파트너센터·스튜디오·어드민은 전부 웹이다.

이번 범위에서는 **전이 지점마다 알림 훅 자리만 만들고 실제 발송은 스텁**으로 둔다. 채널(메일 / 웹 알림센터 / 둘 다)이 정해지지 않았고(미결 #6), 채널을 모르는 채로 만들면 버리는 코드가 된다. 훅 자리는 다음과 같다.

| 전이 | 받는 쪽 |
| --- | --- |
| 검토 요청 · 요청 취소 | 어드민 |
| 검토 통과 · 반려 | 브랜드 |
| 서명 요청 발송 | 양측(실제 발송은 모두싸인) |
| 상대 서명 완료 | 반대편 |
| 거절 · 취소 | 반대편 |
| 체결 완료 | 양측 |
| **서명 기한 임박** | 양측 — §28-8 D #9 미정(D-3 · D-1) |

## 6. 구현 단계 (PR 분할)

| 단계 | 내용 | 산출물 |
| --- | --- | --- |
| **P1** | 마이그레이션 V116~V121 + 엔티티·리포지토리 + `ContractStatus` 전이 규칙 | 부팅(`validate` 통과) |
| **P2** | 조회 — 목록 · `summary` · 상세 · `form-sources` · 조항 | A1·A2·A2a + 상세 읽기 전용 |
| **P3** | 작성 — `POST`/`PUT`/`DELETE` + 형식 검증 + 낙관적 락 | B1·B2·B2a |
| **P4** | 검증 — 하드 H1~H8 · 경고 W1~W6 · `/validate` | B3 · C3 모달 |
| **P5** | 전이 — 검토 요청 · 요청 취소 · 계약 취소 + 계약번호 + 이력 | B3c·B3d·C4·C7 |
| **P6** | 체결 이후 — 재발송 요청 · 지급 완료 기록 · 문서 다운로드 · 재작성 | B4~B8 |
| **P7** | 어드민·스튜디오 API(별도 설계서) | §27 · §28 |

P1~P2는 **어드민·스튜디오와 공유하는 자산**이라 먼저 간다. P5에서 이력과 상태 전이가 함께 들어가므로 **P5 전에는 어떤 계약도 `DRAFT`를 벗어나지 않는다** — 중간 배포 상태가 안전하다.
