# 쇼룸 포스트(일반 게시물) — BE 개발 계획

대상 기획: `기능 명세.txt` (§24) · `ui-studio-07-posts.html` · `C4 쇼룸.dc.html` · `C5 공구 게시물.dc.html`
대상 코드: `domain/post/**` · `api/creator/post/**` · `api/app/post/**` · `api/creator/showroom/**`
Flyway 다음 버전: **V111** (현재 최신 `V110__create_terms_document_and_version.sql`)

**전제 — 기존 post 데이터는 전량 폐기한다.** 스키마를 ALTER·백필로 끌고 가지 않고 **DROP 후 최종형으로 재생성**한다. 이 전제가 아래 설계 전반을 바꾼다(§0-2).

이 문서는 두 가지를 다룬다.

1. **지금 만드는 것** — §24 일반 게시물
2. **공구 게시물이 들어올 때의 테이블 설계** — 지금 만들지 않지만 **지금 결정해야 스키마를 두 번 갈아엎지 않는 것** (§9)

## 0. 결론 먼저

### 0-1. 판단 요약

| 질문 | 답 |
| --- | --- |
| 기존 코드를 전부 지우고 다시 쓰는가 | **구역마다 다르다.** 스튜디오 API는 전액 폐기 후 신규, 도메인·소비자 API는 수정 (근거 §2) |
| 기존 `post` 테이블을 유지하는가 | **아니다. DROP 후 재생성한다.** 데이터 폐기가 승인되어 백필·2단계 마이그레이션이 전부 불필요해졌다 |
| 일반 / 공구를 한 테이블에 담는가 | **공통 뿌리 `post` 1개 + 타입별 확장 테이블**. 완전 분리도, 단일 테이블도 아니다 (근거 §9-1) |
| 공구 테이블을 지금 만드는가 | **만들지 않는다.** `post_type` 판별자만 두고, 공구 전용 필드는 확장 테이블이 생길 때 함께 만든다 |
| 지금 안 만들면 소급 불가한 것 | 노출 로그 · 좋아요 시각 · 제재/이의신청 이력 · 알림 이력 · 게시 시각. 전부 **기록**이라 나중에 만들어도 과거가 안 생긴다 → 이번에 포함 |
| 나중에 해도 소급되는 것 | 인사이트 집계 롤업 · 연령/성별 분포 (원천 로그만 있으면 재계산 가능) → 원천만 지금, 화면은 뒤에 |

### 0-2. 데이터 폐기 전제가 바꾼 것

| 항목 | 데이터 보존 시 | **폐기 전제(확정)** |
| --- | --- | --- |
| `title` | `post`에 nullable로 남겼다가 공구 도입 때 `group_buy_post`로 이사 | **`post`에서 아예 제거.** 공구 도입 시 `group_buy_post.title NOT NULL`로 신설 — 이사 과정 자체가 없다 |
| `is_display` | 백필 후 다음 릴리스에서 DROP (2단계) | **처음부터 없다.** `status` 하나만 존재 |
| `post_images` (ElementCollection) | `post_image`로 승격 백필 후 DROP | **DROP.** `post_image`를 새로 만든다 |
| `post_product` | `post_type='GROUP_BUY'` 백필 후 공구 도입 때 이관 | **DROP.** 공구 도입 시 `group_buy_post_product` 신설 |
| `post_wishlist` | 테이블명 유지(마이그레이션 비용 회피), API 용어만 `like`로 | **`post_like`로 개명.** 비용이 0이 됐으므로 기획 용어와 일치시킨다 |
| `view_count` / `wishlist_count` | 컬럼명 유지 | **`impression_count` / `like_count`로 개명** — 기획의 "노출"·"좋아요"와 일치 |
| 구현 단계 | 7단계 (마지막이 컬럼 정리 PR) | **6단계.** 정리 PR 소멸 |

**폐기 범위 — `post` · `post_images` · `post_product` · `post_wishlist` 4개 테이블 전량.**
`showroom_visit` · `creator_follow` · `users` · `product`는 **건드리지 않는다**(§4-6의 컬럼 추가만).
소비자가 눌렀던 게시물 좋아요가 함께 사라진다는 점만 확인하고 진행한다.

> 선례 — `V69__post_market_to_creator.sql`이 이미 같은 방식(`DELETE FROM post` 전량 삭제 후 스키마 변경)으로 처리한 적이 있다. 이번은 그 연장선이고, 다른 점은 **삭제가 아니라 재생성**이라 최종형이 한 번에 나온다는 것이다.

## 1. 갭 분석 — 현재 코드가 기획과 어긋나는 지점

현재 구현은 §24가 나오기 전에 만들어진 것으로, **일반 게시물과 공구 게시물을 한 엔티티에 "이미지 모드 / 상품 모드"로 욱여넣은 형태**다.

```java
// ShowroomPostService.createPost — 현재
boolean hasImage = ...; boolean hasProducts = ...;
if (hasImage && hasProducts) throw new BusinessException(INVALID_INPUT_VALUE);
```

이 분기가 사실상 "일반 게시물이냐 공구 게시물이냐"다. §24는 이 둘을 **한 목록에 섞지 않는다**고 못박았으므로, 이 분기는 타입 컬럼으로 승격되어야 한다.

### 1-1. 필드 단위 갭

| 기획(§24) | 현재 코드 | 처리 |
| --- | --- | --- |
| 제목 **없음** | `title VARCHAR(200) NOT NULL` + `@NotBlank` | **컬럼 제거** |
| 사진 **최대 20장 · 순서 · 대표 = 첫 장** | `@ElementCollection post_images(image_url)` — **순서 보장 없음**(`@OrderColumn` 없음) | **`post_image` 신설** |
| 사진당 20MB · **JPG/PNG만** | `ImageService`: 20MB 제한은 있음. 단 허용 확장자가 `jpg/jpeg/png/**gif**` 공통이고 **확장자 문자열로만** 판정 | **보완** — `POST` 타입 gif 제외 · 매직 넘버 판정 |
| 장수 최대 20장 | 검증 없음 | **신설** |
| 비율 1.91:1 ~ 4:5 클램프 · **게시물 단위 통일** · 서버가 비율값을 내려줘야 함 | 개념 자체 없음 | **신설** — `post.aspect_ratio` |
| 본문 **선택** · 2,000자 | `content TEXT`, 길이 검증 없음 | **보완** — `@Size(max=2000)` |
| 상태 **3종**(작성중/게시중/노출중지) | `is_display BOOLEAN` 2값 | **`status` enum으로 교체** |
| 상품 연결 **없음** | `post_product` 매핑 + `productIds` API | **제거** (공구 도입 시 별도 테이블로) |
| 삭제 = 불가역 + **서버 비공개 N개월 보관** | `postRepository.delete(post)` — **하드 삭제** | **soft delete + 파기 스케줄** |
| 운영자 노출중지 · 이의신청 1회 · 사유/처리자/기한 고지 | 없음 | **신설** |
| 노출·좋아요·행동 귀속·연령/성별 인사이트 | `view_count`, `wishlist_count` **누적 카운터만** | **원천 로그 신설** |
| 게시 시각 | `created_at`으로 대용 중 | **`published_at` 신설** |

### 1-2. 이 변경이 건드리는 다른 화면 — 반드시 같이 고친다

| 영향처 | 내용 |

## 2. 코드 처리 방침 — 구역별로 다르다

전체 2,436줄. 규모가 작아 "수정이냐 재작성이냐"는 비용이 아니라 **재사용할 축이 남느냐**로 갈린다.

| 구역 | 줄수 | 처리 | 근거 |
| --- | --- | --- | --- |
| `api/creator/post/**` (컨트롤러·서비스·DTO·docs) | **891** | **전액 폐기 후 신규** | 전부 `title`/`productIds`/`isDisplay` 축 위에 서 있고 §24가 이 3개를 모두 없앤다. 재사용되는 건 `getCurrentUserEmail()` 관례 정도다 |
| `api/app/post/**` | **746** | **수정** | 소비자 API는 **계약**이다. 경로·응답 구조를 유지하고 `status` 조건 교체 + `aspectRatio` 추가만 한다 |
| `domain/post/**` | **426** | **수정 (엔티티 이름 유지)** | `ShowroomStatsService`·`TopContentItem`·`ShowroomFollowService` 3개 모듈이 `Post` 타입과 `PostRepository`를 직접 참조한다. 엔티티를 지우고 새로 만들면 §22 쇼룸 관리가 함께 무너진다 — **테이블은 재생성하되 엔티티 클래스명 `Post`는 유지하고 내부만 교체**한다 |

**개명은 하되 클래스는 살린다** — `PostWishlist` → `PostLike`는 참조가 5개 파일(전부 post 도메인 + `UserPostService`)로 닫혀 있어 안전하다. 반면 `Post`는 외부 3개 모듈이 물고 있으므로 이름을 바꾸지 않는다.

**테스트 공백 주의** — post 관련 테스트는 **0개**다. `ShowroomStatsServiceTest`가 `PostRepository`를 `@Mock`으로 잡고 있어 **레포 메서드 시그니처를 바꾸면 깨진다**. `persistence/RepositoryQueryParsingTest`가 JPQL 파싱은 잡아주므로 `isDisplay → status` 전환 실수는 빌드에서 걸린다. 이번 작업에 스튜디오 서비스 테스트를 함께 넣는다.

## 3. 설계 원칙 5가지

**① 노출 상태와 판매 상태를 한 컬럼에 섞지 않는다.**
`post.status`는 **노출 축**(작성중/게시중/노출중지)만 담당한다. 공구의 `D-3`·`품절`·`공구 마감`은 상품·공구 데이터에서 **파생**되는 값이지 게시물의 상태가 아니다(C5: "일부만 품절이면 배지는 D-3 그대로"). 섞으면 공구 게시물이 들어오는 순간 상태 enum이 12종으로 폭발한다.

**② 카운터는 신뢰하되 원천 로그를 남긴다.**
`like_count`·`impression_count`는 조회 성능을 위해 유지하되, **인사이트 3단은 로그에서 계산**한다. 카운터만 있으면 기간 필터(최근 30일)·연령 분포·귀속을 영원히 못 만든다.

**③ 삭제는 상태 전이다.**
§24-6이 "인플루언서 기준의 삭제 ≠ hard delete"라고 명시했다. `deleted_at` + `purge_at` 2단계로 두고, 물리 삭제는 파기 배치만 한다. **S3 객체 삭제도 파기 시점에 같이** 한다(그 전에 지우면 원본 내려받기와 자료 요청 대응이 깨진다).

**④ 기록은 이벤트 테이블로 남긴다.**
제재·이의신청·알림은 현재 값(`status`)만 보면 "누가 왜 언제"가 사라진다. §24-5는 사유·근거 규정·조치 시각·처리자·기한을 **화면에 남기라**고 요구한다 → 이력 테이블 필수.

**⑤ 알림 발송 인프라는 이번 범위 밖, 그러나 알림 이력은 이번에 만든다.**
프로젝트에 발송 인프라가 없다(`NotificationSetting`은 수신 설정값일 뿐). §24-6은 "알림 이력에 **영구 보존**"을 요구하므로, **이력 테이블에 기록하고 발송 어댑터는 no-op 스텁**으로 둔다. 어드민 회원관리 계획의 `IdentityVerificationService` 스텁 경계와 같은 패턴이다.

## 4. 데이터 모델 — V111 (단일 마이그레이션)

파일명: `V111__rebuild_post_for_showroom_posts.sql`

### 4-0. 폐기

```sql
-- 자식부터 — FK 역순
DROP TABLE IF EXISTS `post_wishlist`;
DROP TABLE IF EXISTS `post_product`;
DROP TABLE IF EXISTS `post_images`;
DROP TABLE IF EXISTS `post`;
```

> `post_product`가 `product`를, `post_wishlist`가 `users`를 참조하고 있으므로 **반드시 이 순서**로 지운다. 부모 테이블(`product`·`users`·`creator`)은 건드리지 않는다.

### 4-1. `post` — 공통 뿌리

```sql
CREATE TABLE `post` (
  `post_id`          BIGINT       NOT NULL AUTO_INCREMENT,
  `creator_id`       BIGINT       NOT NULL,
  `post_type`        VARCHAR(20)  NOT NULL DEFAULT 'GENERAL' COMMENT 'GENERAL / GROUP_BUY',
  `status`           VARCHAR(20)  NOT NULL COMMENT 'DRAFT/PUBLISHED/SUSPENDED/UNDER_REVIEW/DELETED',
  `content`          TEXT         NULL COMMENT '본문 — 선택 · 2,000자(서버 검증)',
  `aspect_ratio`     DECIMAL(6,4) NULL COMMENT '첫 사진 기준 가로/세로. 1.9100(1.91:1) ~ 0.8000(4:5)',
  `impression_count` BIGINT       NOT NULL DEFAULT 0 COMMENT '노출 — 기획 용어. 구 view_count',
  `like_count`       BIGINT       NOT NULL DEFAULT 0 COMMENT '좋아요 — 구 wishlist_count',
  `published_at`     DATETIME(6)  NULL COMMENT '작성중→게시중 전환 시각. 재게시해도 갱신하지 않는다',
  `deleted_at`       DATETIME(6)  NULL,
  `delete_reason`    VARCHAR(32)  NULL COMMENT 'SELF / APPEAL_REJECTED / APPEAL_EXPIRED / ADMIN',
  `purge_at`         DATETIME(6)  NULL COMMENT '비공개 보관 만료 — 이후 파기 배치가 물리 삭제',
  `created_at`       DATETIME(6)  NOT NULL,
  `modified_at`      DATETIME(6)  NULL,
  PRIMARY KEY (`post_id`),
  KEY `idx_post_creator_status_published` (`creator_id`, `status`, `published_at`),
  KEY `idx_post_purge` (`purge_at`),
  CONSTRAINT `fk_post_creator` FOREIGN KEY (`creator_id`) REFERENCES `creator` (`creator_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**`title`이 없다.** 일반 게시물은 제목이 없고(§24-3), 공구 게시물의 제목은 §9-4에서 `group_buy_post.title NOT NULL`로 만든다. 뿌리에 nullable로 두면 "일반인데 제목이 들어온" 데이터를 DB가 막지 못한다.

**`post_type`은 지금부터 둔다.** 공구가 아직 없어도 판별자가 있어야 §9의 확장이 스키마 변경 없이 붙는다. 지금은 전부 `GENERAL`이다.

**`status` 5종**

| 값 | 의미 | 진입 | 화면 |
| --- | --- | --- | --- |
| `DRAFT` | 작성중(임시저장) | 임시저장 | 정보 배지 |
| `PUBLISHED` | 게시중 | 게시하기 / 이의신청 승인 | 성공 배지 |
| `SUSPENDED` | 노출 중지 | 운영자 조치 | 위험 배지 |
| `UNDER_REVIEW` | 이의 심사 중 | 이의 신청 | **배지는 여전히 "노출 중지"** (§24-5: 사실이 바뀐 게 아니다) |
| `DELETED` | 영구 삭제(비공개 보관) | 본인 삭제 / 반려 / 기한 경과 | 목록에서 제외 |

`UNDER_REVIEW`를 별도 값으로 두는 이유 — 이 상태에서만 **삭제가 금지**된다(§24-5). `SUSPENDED`와 합치면 삭제 가능 여부를 매번 이의신청 테이블 조인으로 판정해야 한다.

### 4-2. `post_image`

```sql
CREATE TABLE `post_image` (
  `post_image_id` BIGINT NOT NULL AUTO_INCREMENT,
  `post_id`       BIGINT NOT NULL,
  `sort_order`    INT    NOT NULL COMMENT '0 = 대표 사진. 셀 드래그 순서 변경의 결과',
  `image_url`     VARCHAR(512) NOT NULL COMMENT '표시용(크롭 반영)',
  `original_url`  VARCHAR(512) NOT NULL COMMENT '원본 — 유예 기간 내려받기·재크롭용. 파기 시점까지 보존',
  `width`         INT NULL,
  `height`        INT NULL,
  `file_size`     INT NULL,
  `created_at`    DATETIME(6) NOT NULL,
  PRIMARY KEY (`post_image_id`),
  UNIQUE KEY `uk_post_image_order` (`post_id`, `sort_order`),
  CONSTRAINT `fk_post_image_post` FOREIGN KEY (`post_id`) REFERENCES `post` (`post_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**`original_url`을 따로 두는 이유** — §24-6의 "반려 통지 후 유예 기간 동안 **본인만 사진 원본을 내려받을 수 있게** 한다". 크롭본만 갖고 있으면 이 요구를 만족할 수 없다. FE는 크롭 결과와 원본을 **둘 다 업로드**한다(§6-2).

**`sort_order` UNIQUE의 함정** — 순서 재배열 시 `(1,2,3) → (2,1,3)` 중간 상태에서 유니크 충돌이 난다. 서비스는 **전체 DELETE 후 재INSERT**(장수 20 이하라 비용 무시 가능)로 처리한다.

**최대 20장은 DB가 아니라 서비스에서 막는다.** 체크 제약으로 표현할 수 없는 조건이고, 초과 시 필요한 응답이 "몇 장 초과"라는 도메인 메시지다.

### 4-6. `post_impression` — 노출 원천 로그

```sql
CREATE TABLE `post_impression` (
  `impression_id` BIGINT NOT NULL AUTO_INCREMENT,
  `post_id`       BIGINT NOT NULL,
  `creator_id`    BIGINT NOT NULL COMMENT '집계 조인 제거용 비정규화',

  `viewed_at`     DATETIME(6) NOT NULL,
  PRIMARY KEY (`impression_id`),
  KEY `idx_post_impression_post_time` (`post_id`, `viewed_at`),

) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

`viewer_key` 규칙을 `showroom_visit`과 **같게** 맞추는 것이 핵심이다. §24-7의 라스트 터치 귀속이 이 키의 일치로만 성립한다.

**중복 노출 처리** — `showroom_visit`이 30분 세션을 *적재 시점*에 적용한 것과 같은 방식으로, `(post_id, viewer_key)`가 **30분 내 재등장하면 적재하지 않는다**. §22-4와 지표 정의를 맞춰야 §24-7의 "쇼룸 관리와 용어 통일"이 성립한다.

### 4-7. 귀속 — 기존 테이블에 컬럼 추가 (여기는 ALTER)

```sql
ALTER TABLE `showroom_visit`
  ADD COLUMN `attributed_post_id` BIGINT NULL COMMENT '§24-7 라스트 터치 — 방문 24h 이내 마지막으로 본 게시물',
  ADD KEY `idx_showroom_visit_attributed` (`attributed_post_id`, `visited_at`);

ALTER TABLE `creator_follow`
  ADD COLUMN `attributed_post_id` BIGINT NULL,
  ADD KEY `idx_creator_follow_attributed` (`attributed_post_id`, `created_at`);
```

**이 두 테이블은 실데이터가 있으므로 DROP 대상이 아니다.** 컬럼만 추가하고 기존 행은 `NULL`(귀속 불명)로 남긴다.
**FK를 걸지 않는다** — `post`가 파기되면 방문·팔로우 행까지 막히거나 지워진다. 귀속은 참조 무결성이 필요한 관계가 아니라 통계 태그다.

**`creator_follow`의 구멍 하나** — 언팔로우하면 행이 삭제되므로 과거에 귀속된 팔로우 수가 **줄어든다**. 인사이트는 시점 성과라 줄면 안 된다.

| 안 | 내용 | 평가 |
| --- | --- | --- |
| (a) `creator_follow_event` 로그 신설 | FOLLOW/UNFOLLOW를 append-only로 | 정확. 테이블 1개 추가 |
| (b) 현행 유지 + 감소 감수 | 구현 0 | **인사이트가 과거를 거슬러 바뀐다** — 부적합 |

**(a)를 권장하되 이번 범위에는 넣지 않는다.** 팔로우 로그는 쇼룸 관리(§22-4 팔로워 행동)와 공유 자산이라 그쪽 작업과 함께 설계하는 게 맞다. 이번에는 `attributed_post_id`만 넣고, 인사이트 API의 팔로우 수치가 **로그 도입 전까지 감소 가능**이라는 점을 주석으로 남긴다.

### 4-8. `post_notification_log` — 알림 이력 (발송은 스텁)

```sql
CREATE TABLE `post_notification_log` (
  `log_id`     BIGINT NOT NULL AUTO_INCREMENT,
  `post_id`    BIGINT NOT NULL COMMENT '게시물이 파기돼도 남는다 — FK를 걸지 않는다',
  `creator_id` BIGINT NOT NULL,
  `event_type` VARCHAR(40) NOT NULL COMMENT 'SUSPENDED / APPEAL_RECEIVED / APPEAL_APPROVED / APPEAL_REJECTED / DELETED_BY_EXPIRE / PUBLISHED_TO_FOLLOWERS',
  `payload`    JSON NULL COMMENT '사유·근거 규정·기한 등 통지 당시 문구를 그대로 굳힌다',
  `sent_at`    DATETIME(6) NOT NULL,
  `delivered`  BOOLEAN NOT NULL DEFAULT FALSE COMMENT '발송 인프라 도입 전에는 항상 FALSE',
  PRIMARY KEY (`log_id`),
```

**`post_id`에 FK를 걸지 않는 유일한 테이블이다.** §24-6이 "삭제 이력은 알림 이력에 **영구 보존**"을 요구하는데, 게시물은 N개월 후 파기된다. FK가 있으면 파기 배치가 이력을 같이 지우거나 막힌다.

## 5. 상태 전이 · 정책

```
        [작성] ──임시저장──> DRAFT ──게시하기──> PUBLISHED
                              │                    │
                              └──게시하기──────────>│
                                                   │ 운영자 조치
                                                   ▼
                        DELETED <──본인 삭제──  SUSPENDED ──이의 신청──> UNDER_REVIEW
                           ▲                       │                        │
                           │       기한 경과(미신청)│                  반려  │  승인
                           └───────────────────────┘                        │  │
                           └──────────────────────────────────────────────-─┘  │
                                                   PUBLISHED <────────────────-─┘
```

| 액션 | 허용 상태 | 서버 규칙 |
| --- | --- | --- |
| 수정 | `DRAFT` · `PUBLISHED` | `SUSPENDED`/`UNDER_REVIEW`면 **409** (§24-5 심사 대상이 도중에 바뀌면 안 된다) |
| 삭제 | `DRAFT` · `PUBLISHED` · `SUSPENDED` | `UNDER_REVIEW`면 **409** (§24-5) |
| 이의 신청 | `SUSPENDED` **AND** `now <= appeal_deadline` | 게시물당 1회(DB 유니크) |
| 게시 | `DRAFT` | 사진 ≥ 1장 |
| 임시저장 | `DRAFT` | 사진 ≥ 1장 **또는** 본문 ≥ 1자 |

**서버는 버튼 활성 조건도 검증한다.** FE는 "에러 문구 없이 비활성만"으로 표현하지만(§24-3), 서버까지 안 막으면 API 직접 호출로 빈 게시물이 생긴다. 서버는 `INVALID_INPUT_VALUE`로 거절하고, FE가 그 상태에 도달할 일이 없으므로 문구 정책과 충돌하지 않는다.

**재게시(승인) 시 좋아요·인사이트 복원** — 별도 복원 로직이 **없다**. 카운터를 깎지 않고 로그를 지우지 않으므로 `status`만 되돌리면 그대로 복원된다. §3-② 원칙의 부수 이득이다.

## 6. API 설계

### 6-1. 크리에이터 스튜디오 — `/v1/creator/posts` (전면 재작성)

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| `GET` | `/v1/creator/posts?status=&page=&size=` | 목록. **응답에 탭 카운트 4종 동봉**(전체·게시중·노출중지·작성중) — 탭에 개수가 함께 보여야 한다(§24-1) |
| `POST` | `/v1/creator/posts` | 생성. `action: DRAFT \| PUBLISH` |
| `GET` | `/v1/creator/posts/{postId}` | 상세 — 사진·본문·상태·조치 정보(사유/근거/시각/처리자/기한) |
| `PUT` | `/v1/creator/posts/{postId}` | 수정 (사진 전체 교체 방식) |
| `POST` | `/v1/creator/posts/{postId}/publish` | 작성중 → 게시중 |
| `DELETE` | `/v1/creator/posts/{postId}` | soft delete |
| `GET` | `/v1/creator/posts/{postId}/insights?period=30d` | 인사이트 3단 |
| `POST` | `/v1/creator/posts/{postId}/appeal` | 이의 신청 (1회) |
| `GET` | `/v1/creator/posts/{postId}/originals` | 유예 기간 원본 내려받기 URL 목록 (본인 · `grace_until` 이내) |

**목록 응답에 카운트를 함께 싣는 이유** — 탭 4개를 각각 호출하면 요청이 4배가 되고 탭 전환마다 숫자가 흔들린다. 한 트랜잭션에서 `GROUP BY status`로 뽑는다.

**기존 API는 하위 호환을 고려하지 않는다.** `@Hidden`으로 스웨거 미공개 상태이고 데이터도 폐기하므로, 경로만 유지한 채 요청·응답을 새 스펙으로 교체한다. FE와 교체 시점만 맞춘다.

### 6-2. 사진 업로드 — 기존 인프라 재사용 + 검증 추가

업로드는 `POST /v1/creator/images?type=POST`(기존)를 그대로 쓴다. `ImageService`에는 이미 20MB 제한(`MAX_FILE_SIZE`), 타입별 허용 확장자 분기(`getAllowedExtensions`), 대표 이미지 전용 검증(`validateSquareThumbnail`)이 있으므로 **같은 패턴으로 3가지를 얹는다**.

1. **`POST` 타입 전용 허용 확장자** — 현재 공통 목록이 `jpg/jpeg/png/gif`인데 **기획은 JPG·PNG만**이다. `SIGNUP_DOCUMENT`가 이미 별도 목록을 갖고 있으므로 같은 방식으로 분기한다.
2. **매직 넘버 판정** — 지금은 파일명 확장자 문자열만 본다. 와이어의 실패 케이스가 정확히 `아침루틴_영상.mp4`이고, 확장자만 `.jpg`로 바꾸면 그대로 통과한다. `ImageIO.read()`가 `null`을 반환하면 거절하는 것으로 충분하다(`validateSquareThumbnail`이 이미 쓰는 방식).
3. **응답에 `width`·`height` 추가** — 현재 `ImageUploadResponse`는 URL만 돌려준다. FE의 비율 계산과 서버의 클램프 검증이 같은 값을 봐야 한다.

**원본/크롭 2회 업로드** — FE가 `originalUrl`과 크롭 결과 `imageUrl`을 각각 올리고, 게시물 저장 시 둘 다 보낸다.
**서버 측 비율 검증** — `aspect_ratio`는 첫 사진에서 계산해 `0.8000 ~ 1.9100` 범위인지 확인한다. 벗어나면 `INVALID_INPUT_VALUE`. 크롭 자체는 FE가 하고 **서버는 결과를 검증만** 한다(서버 이미지 처리 파이프라인을 새로 들이지 않는다).

### 6-3. 소비자 — 기존 API 수정

| 경로 | 변경 |

### 6-4. 어드민 — `/v1/admin/posts` (신설, 최소 범위)

| 메서드 | 경로 | 설명 |

| `POST` | `/v1/admin/post-appeals/{appealId}/approve` | 승인 → 재게시 |
| `POST` | `/v1/admin/post-appeals/{appealId}/reject` | 반려 → `DELETED` + 유예 시작 |

> 신고 접수(소비자 → 운영자) 화면은 §24 범위 밖이고 어드민 신고 모듈도 아직 없다. **조치 API만 만들고 진입은 어드민 수동 조작**으로 시작한다.

## 7. 인사이트 집계 (§24-7)

| 단 | 지표 | 산식 |
| --- | --- | --- |
| ① 반응 | 노출 | `COUNT(*) FROM post_impression WHERE post_id=? AND viewed_at IN period` |
| | 좋아요 | `COUNT(*) FROM post_like WHERE post_id=? AND created_at IN period` |
| | 좋아요율 | 좋아요 ÷ 노출 (분모 0이면 `null` — 0%로 표시하지 않는다) |
| ② 행동 | 쇼룸 방문 | `COUNT(*) FROM showroom_visit WHERE attributed_post_id=?` |
| | 팔로우 | `COUNT(*) FROM creator_follow WHERE attributed_post_id=?` |
| | 전환율 | 각 ÷ 노출 |
| ③ 본 사람 | 연령대·성별 | `post_impression` × `users` 조인, `viewer_key` **중복 제거 후** 분포. `user_id IS NULL` 또는 생년월일/성별 미제공 = **미확인** |

**"중지 시점까지 누적"(S8/S11 화면)** — `period` 대신 `post_suspension.suspended_at`을 상한으로 넣으면 같은 쿼리로 나온다. 별도 저장 불필요.

**롤업은 지금 만들지 않는다.** `post_impression`이 수천만 행이 되면 일별 집계 테이블이 필요하지만, **로그만 있으면 언제든 소급 생성된다**. 초기 트래픽에서는 인덱스 조회로 충분하다. **행 수 1천만 또는 인사이트 응답 500ms 초과를 도입 기준선으로 정한다.**

## 8. 배치 — `global/scheduler`

기존 `TermsEffectuationScheduler` 패턴을 따른다.

| 잡 | 주기 | 동작 |
| --- | --- | --- |
| `PostAppealDeadlineScheduler` | 1시간 | `appeal_deadline < now` AND 신청 없음 → `DELETED`(`APPEAL_EXPIRED`), `purge_at = now + N개월`, 알림 이력 적재 |
| `PostPurgeScheduler` | 1일 | `purge_at < now` → **행·이미지·S3 객체 물리 삭제**. `post_notification_log`는 남긴다 |
| `PostImpressionRetentionScheduler` | 1일 | 원천 로그 보관 기간 경과분 삭제 (기간 미정 — §11 ⓔ) |

**파기 배치는 드라이런 모드를 먼저 넣는다.** 되돌릴 수 없는 유일한 배치이고, `purge_at` 계산이 틀리면 보관 의무 자료가 사라진다. 첫 배포는 대상 목록만 로그로 남기고 실제 삭제는 다음 릴리스에서 켠다.

## 9. 공구 게시물이 들어올 때의 테이블 설계

### 9-1. 세 가지 안 비교

| 안 | 구조 | 평가 |
| --- | --- | --- |
| **A. 단일 테이블 + 타입 컬럼** | `post` 하나에 `title`·`product`·사진을 전부 nullable로 | **부적합.** 지금 코드가 이 상태이고 이미 `if (hasImage && hasProducts) throw`라는 방어 코드가 생겼다. 타입별 필수 조건이 정반대(제목: 없음↔필수 / 사진: 필수↔없음)라 **DB 제약을 하나도 못 건다** |
| **B. 완전 분리 2테이블** | `post` · `group_buy_post` 독립 | **부적합.** 게시물 본문은 다르지만 **주변부는 전부 같다** — 좋아요·신고·노출중지·이의신청·알림 이력·피드 노출. B로 가면 이 6개가 전부 두 벌이 되거나 `(target_type, target_id)` 다형 키가 되어 **FK를 잃는다** |
| **C. 공통 뿌리 + 타입별 확장** ✅ | `post`(공통) + `group_buy_post`(1:1 확장) | **채택.** 횡단 테이블이 `post_id` 하나로 FK를 유지하고, 타입 전용 필드는 확장 테이블에서 `NOT NULL`을 걸 수 있다 |

**결정의 축은 "본문이 얼마나 비슷한가"가 아니라 "무엇이 게시물을 참조하는가"다.** 좋아요·제재·신고·알림은 두 타입에 **똑같이** 걸린다(§24-5 확인필요 ⓓ가 "공구 게시물의 운영자 수동 숨김과 명칭을 노출 중지로 통일하자"고 이미 제안하고 있다). 참조하는 쪽이 하나의 ID를 원하므로 뿌리를 공유한다.

### 9-2. 채택 구조

```
post (공통 뿌리 — title 없음)
├─ post_id · creator_id · post_type · status · content
├─ published_at · deleted_at · purge_at · like_count · impression_count
│
├── [GENERAL]   post_image (1:N, 최대 20)  ← aspect_ratio는 post에
│               ※ 일반 전용 확장 테이블은 만들지 않는다 (전용 필드가 없다)
│
└── [GROUP_BUY] group_buy_post (1:1)
                ├─ post_id(PK,FK) · title NOT NULL · group_buy_id
                ├─ is_sponsored (대가관계 = 유료 광고 포함 배지)
                └─ 상품은 group_buy_post_product (1:N, sort_order)

횡단 테이블 — 전부 post_id 단일 FK
post_like · post_suspension · post_appeal
post_impression · post_notification_log · (post_report)
```

**JPA 매핑은 `@Inheritance(JOINED)`를 쓰지 않고 `@OneToOne @MapsId` 확장으로 간다.** JOINED 상속은 `Post` 조회마다 서브클래스 조인이 붙고, 이미 `Post`를 참조하는 코드(`PostLike`, `TopContentItem`, 피드 3종)가 전부 루트 타입을 쓰고 있어 상속 계층으로 바꾸면 광범위한 수정이 따라온다. `Post` + `GroupBuyPost(@MapsId)`가 같은 스키마를 만들면서 기존 코드를 건드리지 않는다.

### 9-3. 타입별로 갈리는 규칙은 정책 객체로 분리

```java
public interface PostPolicy {
    void validateForPublish(Post post);
    void validateEditable(Post post);   // 공구: 노출중 잠금 / 일반: 상시 허용
    boolean canLike(Post post);         // 공구: 마감이면 false / 일반: 항상 true
    boolean requiresAdDisclosure();     // 공구: true
}
// GeneralPostPolicy / GroupBuyPostPolicy — post_type으로 선택
```

`if (postType == GROUP_BUY)` 분기가 서비스 곳곳에 퍼지는 것을 처음부터 막는다. 갈리는 규칙은 4개뿐이다: **제목 필수 여부 · 사진 허용 여부 · 수정 가능 시점 · 대가관계 표시**.

일반 게시물만 있는 지금도 **`PostPolicy` 인터페이스와 `GeneralPostPolicy`를 만들어 둔다.** 구현체 1개짜리 인터페이스가 과하다고 느껴질 수 있으나, 이 4개 규칙은 공구가 들어오는 순간 **반드시** 갈린다. 나중에 도입하면 이미 서비스에 흩어진 검증을 걷어내야 한다.

### 9-4. 공구 게시물 도입 시 마이그레이션 (V1xx, 이번 아님)

```sql
CREATE TABLE `group_buy_post` (
  `post_id`      BIGINT NOT NULL COMMENT 'post와 1:1',
  `group_buy_id` BIGINT NULL COMMENT '공구 1건당 게시물 1개 — 공구 엔티티 확정 후 UNIQUE',
  `title`        VARCHAR(200) NOT NULL,
  `is_sponsored` BOOLEAN NOT NULL DEFAULT TRUE COMMENT '대가관계 자동 삽입 — §24 비교표',
  PRIMARY KEY (`post_id`),
  CONSTRAINT `fk_group_buy_post_post` FOREIGN KEY (`post_id`) REFERENCES `post` (`post_id`)
);

CREATE TABLE `group_buy_post_product` (
  `id` BIGINT NOT NULL AUTO_INCREMENT,
  `post_id` BIGINT NOT NULL, `product_id` BIGINT NOT NULL,
  `sort_order` INT NOT NULL COMMENT 'C5 상품 목록 노출 순서',
  PRIMARY KEY (`id`), UNIQUE KEY `uk_gbp_product` (`post_id`, `product_id`),
  CONSTRAINT `fk_gbp_post` FOREIGN KEY (`post_id`) REFERENCES `post` (`post_id`),
  CONSTRAINT `fk_gbp_product` FOREIGN KEY (`product_id`) REFERENCES `product` (`product_id`)
);
```

**이게 전부다 — 데이터 이관도, `post` 변경도 없다.** V111에서 데이터를 폐기하고 `title`을 뿌리에서 없앤 덕분에, 공구 도입은 **CREATE 2개**로 끝난다. 데이터를 보존했다면 여기서 `title` 이사 + `post_product` 이관 + 뿌리 컬럼 DROP 3단계가 더 붙었을 것이다.

### 9-5. 지금 확정해 두면 나중이 편해지는 3가지

| # | 항목 | 지금의 결정 |
| --- | --- | --- |
| ① | **공구의 판매 상태를 `post.status`에 넣지 않는다** | `D-3`·`품절`·`공구 마감`은 상품/공구에서 파생 계산. §3-① |
| ② | **`FeedItemResponse.contentType`을 판별자로 확정** | 이미 필드가 있다. 값을 `GENERAL`/`GROUP_BUY`로 정의해 두면 쇼룸 피드(공구 상단 고정 + 일반 최신순)가 응답 구조 변경 없이 확장된다 |
| ③ | **좋아요 정책 차이는 `post_like`가 아니라 `PostPolicy.canLike()`로** | C5: 공구 마감이면 새 좋아요 차단, 품절은 허용. 테이블은 그대로 둔다 |
