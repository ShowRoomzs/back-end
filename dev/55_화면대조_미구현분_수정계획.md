**결론**

- **먼저 고칠 결함은 3건이다.**
  - S1: 인플루언서가 계좌 변경을 요청하면 지급을 보류하는데, 이 보류가 다음 지급 배치에서 풀려 **확인 전에 기존 계좌로 지급된다.**
  - S2: 사업자 구분 변경 취소 API가 요청 유형을 보지 않는다. 계좌 변경 요청이 취소되고 지급 보류는 남는다.
  - M3-1: 어드민 소비자 상세가 누적 구매액 · 주문 수 · 기본 배송지를 **하드코딩한 더미 값**으로 내린다.
- **화면 단위로 없는 것은 어드민 인플루언서 회원 목록(M1) 하나다.** 브랜드 목록 보강(M2)과 한 골격으로 만든다.

- 나머지는 응답 필드 보강, 시안 문구 반영, Swagger 문서 정리다.
- **무료배송 기준 0원(P3)은 시안대로 「0원 = 무료배송 미적용」으로 고친다(D1 확정, 2026-10-24).** 결제 금액이 바뀌는 문제라 결함과 함께 1단계에서 처리한다.
- DB 변경은 3건이다(8절).
  - V214: 무료배송 기준 0 → NULL(P3)
  - V215: 탈퇴 반려 사유 enum 데이터 이행(M7). 코드와 같은 배포에 나가야 한다.
  - V216: 소비자 개인정보 열람 로그(M3-3)
- 기획 결정은 26건이다(6절). D1은 확정했고, 나머지 25건은 권장 기본값으로 진행한다.

  - 6단계 부분 구현

## 2. 파트너센터(브랜드)

### 2-1. 성과 KPI 「정산 합산」 범위 (P1)

**현재**

- `SellerPerformanceQueryService.getSummary`(:94-97)가 KPI 모집단을 `PAID`로만 거른다. `PAID`에는 분배 실패가 포함된다.
- 응답 `SellerPerformanceAssembler`(:91-136)는 `Population(PerformanceStatus.PAID, n)` 하나이고, 근거 문장은 「지급 완료 %d건 합산」(:123)이다. 성비 근거(:132-133)도 같은 문장이다.
- DTO `SellerPerformanceDto`(:89-93)의 `status`는 「항상 PAID」로 문서화돼 있다.
- 시안 rev.7은 「정산 2건 합산(지급 예정 1 · 지급 완료 1)」이다. 조정 협의 · 확인 중은 빠진다.

**변경**

- `PerformanceStatus`(`domain.performance.type`)에 `KPI_POPULATION = EnumSet.of(PAYOUT_SCHEDULED, PAID)`를 둔다. `getSummary`의 필터가 이것을 쓴다.
- `Population`을 `{ count: long, statuses: List<PerformanceStatus>, breakdown: Map<PerformanceStatus, Long> }`로 바꾸고 `status`는 없앤다.
  - `breakdown`은 이미 계산한 상태별 건수에서 두 키만 뗀다. 쿼리는 늘지 않는다.
- 근거 문장은 「정산 %d건 합산(지급 예정 %d · 지급 완료 %d)」로 바꾼다. 한쪽이 0건이어도 둘 다 표기한다.
- ROAS 분모(`settlement.rewardAmount`)는 지급 예정에도 정산 행이 있어 그대로 성립한다.
- 문서: `SellerPerformanceControllerDocs`(:75-89), `SellerPerformanceDocsExamples`(:55 · 70)
- **FE 공지**: `population.status` 필드가 없어진다.

**테스트**

- 깨지는 것: `SellerPerformanceListIntegrationTest:306`(`population/status`), `:317`(근거 문장)
- 추가할 케이스
  - 지급 예정 1 + 지급 완료 1이면 count 2이고 breakdown이 맞는지
  - 조정 협의 · 확인 중은 빠지는지
  - 분배 실패는 PAID에 들어가는지

### 2-3. 무료배송 기준 0원 (P3) — 시안대로 수정 (D1 확정 · 2026-10-24)

> **확정(2026-10-24)** — 시안 06 「0원이면 무료배송을 적용하지 않습니다」를 따른다. 아래 선택지 A로 구현하고, B는 채택하지 않는다.

**현재**

## 3. 쇼룸 스튜디오(인플루언서)

### 3-1. 결함 — 계좌 변경 확인 중 지급 보류가 배치에서 풀림 (S1)

**현재** — 코드 경로로 확인했다.

1. `CreatorSettlementInfoService.changeAccount`(:84-121)는 변경 요청을 만들고, `payoutHolds.hold(CREATOR, creatorId, CREATOR_ACCOUNT_UNVERIFIED)`로 지급을 보류한다. 그러나 크리에이터의 `accountVerificationStatus`는 바꾸지 않는다. 요청 중에는 기존 값(VERIFIED 등)이 그대로다.
2. 지급 스케줄러 `SettlementPayoutScheduler` → `SettlementPayoutService.releaseBlocked`(:177-188)가 BLOCKED 행을 다시 판정한다. `CREATOR_ACCOUNT_UNVERIFIED`는 `PayoutBlockReason.PARTNER_CODES`에 없으므로 재판정 대상이다.
3. `SettlementPayoutTransitions.releaseIfUnblocked`(:414-423)가 `PayoutBlockPolicy.blockReasons`(:34-50)로 판정한다. 이 판정은 `accountVerificationStatus.blocksPayout()`만 보고 **열린 계좌 변경 요청은 보지 않는다.**
4. 그래서 비사업자의 보류 행이 SCHEDULED로 올라가고, **확인이 끝나기 전에 기존 계좌로 지급된다.** 1021 8-0 ② 「확인 끝날 때까지 보류」에 어긋난다.
5. 같은 구멍이 두 군데 더 있다.
   - 사업자는 세금계산서 대조(M4, `SettlementTaxDocumentService.verify`:202-205)가 같은 판정으로 보류를 푼다.
   - 요청 중에 새로 확정되는 정산도 보류되지 않는다.

**변경**

- `domain.settlement.port`에 `PendingAccountChangeReader.hasPending(creatorId)` 포트를 둔다.
- 구현은 변경 요청 도메인이 맡는다. `ChangeRequestRepository.findOpenForCreator`에 유형 `CREATOR_ACCOUNT` 필터를 건다.
- `PayoutBlockPolicy.blockReasons`는 이 값이 참이면 `CREATOR_ACCOUNT_UNVERIFIED`를 추가한다.
- `cancelAccountChange`는 요청을 취소한 뒤 해제 재판정을 하므로 그대로 통과한다.

**테스트** — 결함을 테스트로 먼저 재현한 뒤 고친다.

### 5-8. 소통 스레드 「소명 미확인」 상단 고정 (A8)

**판정식** — 아래를 모두 만족하면 「소명 미확인」이다.

### 12-2. 계획과 다르게 한 것

- **M3-1 구매액** — 계획은 「운임 환급 몫 제외」였지만 빼지 않았다. 귀책 변경 운임 환급은 반품 때 차감한 운임을 돌려주는 것이라, 빼면 실제로 낸 돈보다 순구매액이 커진다. 중복 결제 자동 취소(주문 결제가 아님)와 결제액을 넘는 계좌 송금 환급(PG 취소 아님)은 빠진다.
- **M3-1 기본 배송지** — 열람 해제 전에는 시 · 군 · 구까지만 내린다(시안 A1 · A4). M3-3 이 붙은 뒤 배송지 상세도 열람 해제 대상(`fields` 에 `ADDRESS`)이다.
- **P5 정산 내역** — 51 설계서의 쿼리 둘 대신 판정식과 같은 WHERE 한 쿼리를 정산 상태 · 브랜드 행 상태 · 보류 사유로 나눠 센다(「내역 합 = 조건 건수」가 구조적으로 맞는다). 정지 보류 행의 `target` 은 사업자 정보 허위 기재 정지면 `BUSINESS_INFO`.
- **M10 메일** — 51 설계서의 브랜드 전용 메서드 대신 브랜드 · 인플루언서 공통 메서드 2개(`WithdrawalAudience`).
- **A9 브랜드 미정산** — 처음엔 `countUnpaidForMarket` 이었는데, P5-1 과 숫자를 맞추려고 브랜드 몫 기준 + 회수 대기 차감으로 바꿨다(`9009ba29`).
- **M1 · M2 정렬 값** — 공통 `MEMBER_NO` 로 통일하되 브랜드의 옛 값 `BRAND_NO` 도 받는다(D13-4 · FE 미연동 여부를 몰라서).
- **P4** — 계획의 「선택」이던 CSV 일괄 등록을 구현했다. 도서산간 범위가 코드의 제주 범위와 겹치면 409 로 막는다(겹치면 제주가 우선이라 등록해도 적용되지 않는다).
- **A3** — 입점 심사 · 오픈 승인 대기 행 문구는 「D-1 1건은 위 기한 임박에」 대신 「기한 초과 N건 · 기한 임박 N건은 위에」(기한 임박에 오늘 마감이 섞여 D-1 로 고정할 수 없다).
- **A4** — CANCEL_FAILED 의 시작 시각은 `COALESCE(cancelRequestedAt, modifiedAt)`(결제 상태 전이가 벌크 UPDATE 라 `modifiedAt` 이 전이 시각이 아니다).
- **A7** — 상세 API 가 `tab · sort · keyword` 에 더해 목록의 `showroomId` 좁히기도 받는다.
- **A8** — 네이티브로 바꾸지 않고 JPQL 을 유지했다(H2 통과 · MySQL 8 은 ORDER BY 식 · 상관 서브쿼리 허용 · DISTINCT 없음).
- **S3** — 계좌 쪽 비활성 사유 문구를 「사업자 구분 확인이 끝난 뒤 요청할 수 있어요」로 정했다.
